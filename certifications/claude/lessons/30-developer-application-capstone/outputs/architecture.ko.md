# 주문 상태 어시스턴트 아키텍처 기록

## 결정

읽기 전용 인프로세스 도구 하나, 결정론적 정책, 엄격한 출력 검증, 명시적인 에스컬레이션을 갖춘, 범위가 한정된 Claude 보조 워크플로를 사용합니다.

## 컨텍스트

사용자는 정확한 공개 주문 ID로 검증된 주문 상태가 필요합니다. 경로는 알려져 있고, 조작된(가짜) 동작의 비용은 큽니다. 오늘날 이 능력을 소유한 것은 애플리케이션 하나뿐입니다.

## 구성 요소

1. 입력 검증기가 공개 ID 형식을 추출합니다.
2. 신뢰 경계(trust boundary)가 사용자 입력과 검색된 내용을 신뢰할 수 없음(untrusted)으로 표시합니다.
3. Claude는 타입이 지정된 도구 계약을 통해 `lookup_order`를 제안할 수 있습니다.
4. 정책 게이트는 인수 하나짜리 읽기 전용 호출만 허용합니다.
5. 신뢰할 수 있는 통합 코드가 인증된 사용자와 테넌트 신원을 바인딩합니다.
6. 주문 서비스는 최소화된 검증된 상태를 반환합니다.
7. Claude는 구조화된 최종 응답을 만듭니다.
8. 애플리케이션이 스키마, 증거, 라우팅 상태, 트레이스를 검증합니다.

## 결정과 트레이드오프

### 자율 에이전트 대신 워크플로

순서가 정해져 있습니다. 범용 에이전트는 핵심 사용자 성과를 개선하지 못하면서 도구 선택과 루프 위험만 더합니다.

### MCP 대신 직접 도구

하나의 호스트가 하나의 능력을 사용합니다. 직접 만든 타입 지정 핸들러가 운영 경계가 더 적습니다. 승인된 호스트 둘 이상이 공유 탐색과 거버넌스를 필요로 하게 되면 MCP로 이전합니다.

### 자동 실행은 읽기 전용 능력으로 한정

조회(lookup)는 스키마와 정책 검사 후 자동으로 실행될 수 있습니다. 환불, 취소, 주소 변경, 외부 메시지는 별도의 도구, 외부 승인, 멱등성(idempotency), 새로운 평가(eval)를 요구합니다.

### 구조화된 출력 + 로컬 검증

프로바이더의 제약 생성(constrained generation)이 구문 오류를 줄여 줍니다. 그래도 로컬 스키마, 의미, 인가 검사는 필수입니다.

### 기본은 확장 사고(extended thinking) 없이

이 워크플로는 단순 조회입니다. 추론 예산을 늘리려면 도입 전에 측정된 품질 향상이 필요합니다.

## 기각된 대안

- 자유 형식 셸 또는 데이터베이스 도구: 권한이 과도하고 검증이 어렵습니다.
- 하나의 넓은 `manage_order` 도구: 읽기와 변경(mutation) 권한이 섞입니다.
- 대화 텍스트를 승인으로 취급: 인증되지 않았고 인젝션에 취약합니다.
- 무제한 재시도: 비용과 부수 효과의 모호함을 만듭니다.
- 첫 버전에 MCP 도입: 상호 운용성 이점이 아직 서버 운영 비용을 정당화하지 못합니다.

## 보안 경계

- 크리덴셜은 신뢰할 수 있는 통합 코드 안에 남습니다.
- 모델 인수는 절대 신원이나 테넌트를 확정하지 않습니다.
- 신뢰할 수 없는 콘텐츠는 능력(capability)을 부여할 수 없습니다.
- 알 수 없는 도구와 인수 필드는 실패 시 닫힌다(fail closed) 방식으로 처리합니다.
- 도구 결과는 모델 컨텍스트에 들어가기 전에 최소화됩니다.
- 트레이스에는 시크릿 대신 타입이 지정된 요약, 버전, 핑거프린트가 담깁니다.

## 검증

- 단위 테스트가 검증, 정책, 도구 동작, 계약 형태, 에스컬레이션을 다룹니다.
- 행동 평가(behavioral eval)가 알려짐, 알 수 없음, 입력 누락, 인젝션 케이스를 다룹니다.
- 프로덕션(운영 환경) 배포는 실제 API 직렬화 테스트, 인증된 소유권 검사, 레이트 리밋 처리, 카나리아 평가를 추가해야 합니다.

## 제품 세부 사항 고지

모델 ID, SDK 메서드, 구조화 출력 필드, 중지 사유(stop reason), 구성 접점은 구현과 업그레이드 시 반드시 현재 공식 문서와 대조해 확인해야 합니다.
