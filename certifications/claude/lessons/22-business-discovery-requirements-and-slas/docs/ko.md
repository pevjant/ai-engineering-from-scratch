# 비즈니스 디스커버리, 요구사항, SLA


> 첫 번째 아키텍처 결정은 "내가 실제로 어떤 문제를 풀 책임이 있는가"를 밝히는 일입니다.

**유형:** 참고 자료
**언어:** Python
**선수 지식:** 페이즈 11, 레슨 13 / 페이즈 14, 레슨 12 / 페이즈 17, 레슨 08
**소요 시간:** 약 120분

## 학습 목표

- 막연한 AI 요청을 측정 가능한 문제 정의로 바꿀 수 있다
- 기능, 품질, 인프라, 안전, 라이프사이클 요구사항을 분리할 수 있다
- 성공 지표, 서비스 수준 목표, 에스컬레이션 경계를 정의할 수 있다
- 아키텍처 작업에 들어가기 전에 근거가 필요한 가정들을 식별할 수 있다
- 기술 담당자와 비즈니스 담당자 모두 승인할 수 있는 디스커버리 브리프(요구사항 요약서)를 만들 수 있다

## 문제 상황

지원팀 디렉터가 "모든 티켓을 자동으로 해결하는 에이전트"를 만들어 달라고 요청합니다.
말은 구체적으로 들리지만, 사실 전혀 구체적이지 않습니다.

어떤 종류의 티켓이 범위에 들어오는지, '해결'이 무엇을 의미하는지, 에이전트가 어떤
시스템을 변경할 수 있는지, 얼마나 큰 재무 권한을 가지는지, 사용자가 어느 정도의
지연 시간까지 견딜 수 있는지, 어떤 행동에는 사람의 개입이 필요한지 알 수 없습니다.
진짜 문제가 응답 시간인지, 일관성 없는 정책 적용인지, 처리 지연(backlog)인지,
비용인지, 고객 만족도인지도 알 수 없습니다.

모델과 도구 목록부터 정하면 가정 하나를 최적화하는 꼴이 됩니다. 기술적으로는
인상적인 시스템이라도, 엉뚱한 지표를 개선하거나, 금지된 단계를 자동화하거나,
총 업무량을 줄이지 못한 채 일을 에이전트에서 검토자에게 옮기기만 하면 실패합니다.

전문가의 아키텍처 작업은 디스커버리(문제 파악)에서 시작합니다. 시험에서는 비즈니스
의도를 솔루션으로 번역하고 그 트레이드오프를 방어할 수 있는지 평가합니다. 실무에서는
이 능력이 몇 달짜리 재작업을 막아 줍니다.

## 핵심 개념

### 기능이 아니라 결정에서 시작하기

요청을 "담당자, 근거, 결과가 있는 결정"으로 다시 써 보세요.

약한 문제 정의:

```text
Claude 지원 에이전트를 만들어라.
```

결정 형태의 문제 정의:

```text
결제 관련 문의에 대해 정책에 맞는 첫 응답까지 걸리는 중위 시간을 11분에서
3분 미만으로 줄이되, 근거 없는 환불 처리 행동은 0건을 유지하고, 팀 기준
금액을 초과하는 환불에는 사람의 승인을 유지한다.
```

두 번째 정의는 무엇을 측정해야 하는지 알려 줍니다. 무엇을 자동화하면 안 되는지도
알려 줍니다.

첫 디스커버리 세션에서 다섯 가지 질문을 사용하세요:

1. 관측 가능한 어떤 결과가 바뀌어야 하는가?
2. 그 결과의 담당자는 누구인가?
3. 산출물 뒤에 이어지는 행동은 무엇인가?
4. 잘못된, 늦은, 없는 답변의 비용은 얼마인가?
5. 어떤 제약 조건은 트레이드오프로 포기할 수 없는가?

### 우선순위를 정하기 전에 요구사항을 분류하기

모든 요청을 "요구사항"이라는 무의미한 글머리 기호 하나에 몰아 넣으면 아키텍트는
정보를 잃습니다. 명시적인 분류를 사용하세요.

| 분류 | 질문 | 지원팀 예시 |
|------|------|-------------|
| 기능 | 시스템이 무엇을 해야 하는가? | 티켓 읽기, 정책 찾기, 답변 초안 작성 |
| 품질 | 얼마나 좋아야 하는가? | 평가된 초안의 98%에서 활성 정책 버전을 인용 |
| 성능 | 얼마나 빠르고, 어느 규모까지? | 초당 40건 요청에서 P95 초안 지연 시간 8초 미만 |
| 보안 | 누가 무엇을 보거나 바꿀 수 있는가? | 배정된 상담사만 계정 컨텍스트를 볼 수 있음 |
| 안전 | 어떤 결과를 예방하거나 승인해야 하는가? | 검증된 권한 판단 없이는 절대 환불을 실행하지 않음 |
| 운영성 | 장애를 어떻게 감지하고 복구하는가? | 검색 데이터 신선도와 도구 오류율에 알림 설정 |
| 라이프사이클 | 누가 갱신, 승인, 폐기를 담당하는가? | 정책팀은 원본 데이터 신선도를, 플랫폼팀은 런타임을 담당 |

이 분류를 하면 모순이 드러납니다. "즉시 답변한다"는 "3개 출처에 대한 컴플라이언스
검토를 수행한다"와 충돌합니다. "모든 환불을 자동화한다"는 사람의 승인 요구와
충돌합니다. 디스커버리는 코드가 이런 충돌을 장애로 바꾸기 전에 드러내 줍니다.

### 현재 워크플로 매핑하기

슬라이드에 적힌 이상적인 프로세스를 보고 설계하지 마세요. 실제 업무를 관찰하세요.

```mermaid
flowchart LR
    I["티켓 도착"] --> T["상담사가 의도 분류"]
    T --> P["상담사가 정책 검색"]
    P --> A["상담사가 계정 권한 확인"]
    A --> D["상담사가 초안 작성 또는 에스컬레이션"]
    D --> R["검토자가 위험 행동 승인"]
    R --> O["답변과 행동이 기록됨"]
    O --> F["결과가 피드백이 됨"]
```

각 단계마다 다음을 기록하세요:

- 입력과 출력
- 원본 시스템(system of record)
- 담당 역할
- 판단 규칙
- 자주 발생하는 예외
- 지연과 재작업
- 데이터 분류
- 보관되는 근거

가장 가치 높은 개입 지점은 정책 단계를 위한 검색 기능일 수도 있고, 접수 단계의
좁은 분류기일 수도 있고, 더 나은 승인 인터페이스일 수도 있습니다. 자율 에이전트는
가능한 패턴 중 하나일 뿐입니다.

### 가치와 능력 분리하기

Claude가 답변 초안을 작성할 수 있는 것과, 비즈니스 가치가 있는 것은 다릅니다.
비즈니스 가치는 그 초안이 검토 후 총 처리 시간을 줄이는지, 일관성을 높이는지,
새로운 서비스 수준을 가능하게 하는지에 달려 있습니다.

간단한 가치 가설을 사용하세요:

```text
[사용자 또는 팀]에게, [워크플로 단계]를 [범위가 제한된 기능]으로 바꾸면
[비즈니스 지표]가 [베이스라인]에서 [목표]로 개선되고, [가드레일]은
침해하지 않는다. [평가 기간]이 지나면 알 수 있다.
```

모든 칸은 근거로 채우거나 가임(assumption)이라고 명시해야 합니다. 확신에 찬
아키텍처 다이어그램 안에 불확실성을 숨기지 마세요.

### 리스크를 검토 경계로 바꾸기

사람의 검토는 만능 안전 장치가 아닙니다. 트리거, 검토자, 근거 패킷, 시간 예산,
폴백이 반드시 필요합니다.

각 행동에 대해 다음을 추정하세요:

- 잘못됐을 때의 영향
- 되돌릴 수 있는지 여부
- 근거에서 얻을 수 있는 신뢰도
- 규제 또는 정책상 의무
- 악용 가능성
- 검토 비용

영향이 작고 되돌릴 수 있는 초안은 자동으로 진행해도 됩니다. 영향이 크거나
되돌릴 수 없는 행동에는 결정론적 검사와 명시적인 권한이 필요합니다. 중간
리스크는 보통 샘플링, 임계값 기반 검토, 사후 감사가 필요합니다.

### SLI, SLO, SLA를 올바르게 정의하기

서비스 수준 지표(SLI)는 측정하는 신호입니다. 서비스 수준 목표(SLO)는 내부
목표입니다. 서비스 수준 협약(SLA)은 비즈니스적 또는 계약상 결과가 따르는
약속입니다.

| 계층 | 예시 |
|------|------|
| SLI | 활성 정책에 대한 유효한 인용이 붙은 초안의 비율 |
| SLO | 최근 7일 롤링 윈도우에서 98% 이상 |
| SLA | 계약된 지원 시간 안의 고객 대면 첫 응답 |

측정 대상 모집단, 레이블, 측정 방법, 목표 미달 시 대응을 정의하지 않은 채로는
모델 정확도 SLA를 약속하지 마세요. "모델 정확도가 95%"라는 말만으로는 운영적으로
의미가 없습니다.

AI 시스템이라면 여러 종류의 지표를 포함하세요:

- 과제 품질: 사실성, 완전성, 정책 준수
- 시스템 성능: 지연 시간, 가용성, 처리량
- 경제성: 성공 과제당 비용, 캐시 적중률, 검토 노력
- 안전: 차단된 위험 행동 수, 오탈 차단, 에스컬레이션 정밀도
- 운영: 검색 데이터 신선도, 도구 실패, 롤백 시간

### 비목표(Non-Goals)를 명시하기

비목표는 시스템을 조용한 범위 확장(silent scope creep)으로부터 보호합니다.

예시:

- 첫 릴리스는 답변 초안을 작성하지만 보내지는 않는다.
- 결제 FAQ는 처리하지만 계정 해지는 처리하지 않는다.
- 환불 금액은 추천하지만 환불을 실행할 수는 없다.
- 파일럿 기간에는 영어 티켓만 지원한다.

이해관계자가 동의하지 않는다면, 디스커버리가 담당자를 정해야 하는 결정 하나를
찾아낸 것입니다. 그것은 진전입니다.

이제 가정 감사(assumption audit)를 실행하세요. 각 진술을 사실, 추정치, 선호,
제약으로 표시합니다. 사실에는 출처가, 추정치에는 신뢰 구간이, 선호에는 담당자가,
제약에는 권한 근거가 필요합니다.

### 오류 비용으로 우선순위 정하기

후보 유스케이스마다 이 의사결정 표를 사용하세요:

| 차원 | 낮음 | 중간 | 높음 |
|------|------|------|------|
| 잘못된 출력의 영향 | 사소한 수정 | 고객 불편 | 재무, 법률, 안전 피해 |
| 되돌릴 수 있는지 | 클릭 한 번으로 실행 취소 | 수동 수정 | 되돌릴 수 없거나 어려움 |
| 데이터 민감도 | 공개 | 내부 | 규제 대상 또는 비밀 |
| 행동 권한 | 초안만 | 제한된 쓰기 | 파괴적 또는 재무 쓰기 |
| 근거 품질 | 직접 출처 | 부분적 출처 | 모호하거나 없음 |

점수가 높다고 해서 AI 사용이 자동으로 금지되는 것은 아닙니다. 대신 아키텍처가
더 좁은 범위, 결정론적 게이트, 더 강한 근거, 사람의 승인, 더 보수적인 롤아웃
방향으로 바뀝니다.

## 활용하기

세 가지 아키텍처 후보에 브리프를 적용해 보세요:

1. 사람의 승인이 있는 검색 보조 초안 생성.
2. 분류와 초안 작성에만 Claude를 호출하는 결정론적 워크플로.
3. 티켓, 정책, 계정, 환불 도구를 갖춘 적응형 에이전트.

각 후보를 요구사항에 대해 채점해 보세요. 가장 유능한 옵션이 자동으로 최선은
아닙니다. 워크플로가 안정적이고 알려져 있다면, 결정론적 오케스트레이션이 지연
시간, 비용, 실패 지점을 줄이는 경우가 많습니다. 실행 중에 발견되는 근거에 따라
경로가 달라지고, 추가적인 유연성이 통제 부담을 감수할 가치가 있을 때
에이전트를 사용하세요.

선택을 아키텍처 결정 기록(ADR)에 남기세요:

```markdown
# ADR: 지원 해결 패턴

## 상태
제안(Proposed)

## 배경
결정, 제약, 근거, 미해결 가정.

## 옵션
1. 검색 보조 초안 워크플로
2. 결정론적 다단계 워크플로
3. 적응형 도구 사용 에이전트

## 결정
선택한 옵션과 그것이 가장 잘 충족하는 요구사항.

## 기각된 대안
현재 제약 아래에서 각 대안이 왜 떨어지는지.

## 결과
새로운 운영 업무, 잔여 리스크, 되돌리기 계획.

## 검증
오프라인 평가, 파일럿 가드레일, SLO, 재검토 날짜.
```

## 시험 의사결정 패턴

시나리오가 막연한 비즈니스 요청으로 시작한다면, 가장 강한 첫 단계는 보통
기술을 고르기 전에 모호함을 줄이는 것입니다.

다음과 같은 답을 선호하세요:

- 비즈니스 결과와 현재 베이스라인을 확립한다
- 사용자, 원본 시스템, 후속 행동을 식별한다
- 하드 제약과 선호를 분리한다
- 품질과 운영 지표를 정의한다
- 검토와 라이프사이클 담당을 지정한다
- 가장 위험한 가정을 범위가 제한된 파일럿으로 검증한다

가장 큰 모델을 곧바로 고르거나, 에이전트를 추가하거나, 권한과 오류 비용을
명확히 하지 않은 채 자동화를 약속하는 답은 의심하세요.

## 흔한 함정

### 모든 요청을 에이전트로 만들기

에이전트의 유연성에는 비용이 있습니다: 더 많은 도구 호출, 더 넓은 공격 표면,
더 어려운 테스트, 예측하기 어려운 지연 시간. 적응형 계획이 요구사항일 때만
선택하세요.

### 사람의 검토를 공짜로 여기기

검토 대기열이 새로운 병목이 될 수 있습니다. 검토 시간, 합의율, 에스컬레이션
품질을 측정하세요.

### 분모 없이 정확도 말하기

데이터셋, 모집단, 레이블, 평가자, 시간 윈도우를 명시하세요. 그렇지 않으면 그
숫자는 운영 결정에 쓸 수 없습니다.

### 출시 후 담당 공무하기

모든 프롬프트, 출처, 도구, 통제 장치, 지표, 에스컬레이션 경로에 담당자가
필요합니다. 담당자 없는 통제 장치는 조용히 부패합니다.

## 연습 문제

1. "AI 애널리스트를 만들어 달라"를 베이스라인, 목표, 가드레일, 담당자가 있는
   결정 형태의 문제 정의로 다시 써 보세요.
2. 실제 워크플로를 매핑하고, 모델 호출보다 결정론적 규칙이 더 나은 단계를
   하나 찾아 보세요.
3. 검색 보조 컴플라이언스 워크플로를 위한 SLI 다섯 개를 정의하세요. 품질,
   안전, 경제성, 운영성 신호를 최소 하나씩 포함해야 합니다.
4. 모델이 그 일을 할 수 있음에도 에이전트 아키텍처를 기각하는 ADR을
   작성해 보세요.
5. 시스템에 프로덕션(운영 환경) 쓰기 권한을 주지 않고 가장 위험한 가정을
   검증하는 파일럿을 설계하세요.

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|--------------------|-----------|
| 요구사항 | 요청받은 기능 | 솔루션이 충족해야 하는 검증 가능한 조건 |
| 제약 | 불편한 무언가 | 아키텍처가 트레이드오프로 포기할 수 없는 경계 |
| SLI | SLA 목표 | 서비스 행동을 판단하는 데 쓰이는 측정 신호 |
| SLO | 벤더의 약속 | 지표에 대한 내부 목표 |
| SLA | 아무 성능 목표 | 정의된 결과가 따르는 서비스 약속 |
| 비목표 | 조용히 연기된 작업 | 범위 확장을 막는 명시적 경계 |
| ADR | 다이어그램 | 배경, 옵션, 결정, 결과를 남기는 영구 기록 |
