# 이해관계자 커뮤니케이션, ADR, 라이프사이클 담당


> 다이어그램이 완성됐을 때 아키텍처가 전달되는 것이 아닙니다. 다음 담당자가 그
> 결정을 운영할 수 있게 되었을 때 전달되는 것입니다.

**유형:** 참고 자료
**언어:** Python
**선수 지식:** [비즈니스 디스커버리, 요구사항, SLA](../../22-business-discovery-requirements-and-slas/), [엔터프라이즈 거버넌스, 컴플라이언스, 사람의 검토](../../27-enterprise-governance-compliance-and-hitl/) / 페이즈 17, 레슨 23
**소요 시간:** 약 135분

## 학습 목표

- 하나의 아키텍처를 경영진, 제품, 엔지니어링, 통제 수준에서 각각 전달할 수 있다
- 트레이드오프와 되돌리기 조건을 보존하는 결정 기록을 작성할 수 있다
- 설계를 구현 가이던스, 출시 게이트, 명명된 담당 체계로 바꿀 수 있다
- 인수인계(handoff) 수용 기준과 운영 준비성을 정의할 수 있다
- 시스템 라이프사이클 전반에 걸쳐 피드백과 변경 관리를 수행할 수 있다

## 문제 상황

어떤 아키텍트가 경영진 스티어링 그룹에 상세한 멀티 에이전트 다이어그램을
발표합니다. 다이어그램에는 모델 라우트, MCP 서버, 벡터 인덱스, 이벤트 대기열,
평가기, 트레이싱이 담겨 있습니다. 하지만 아무도 세 가지 기본 질문에 답하지 못합니다:

- 어떤 비즈니스 결정을 승인하는 것인가?
- 제안된 통제 장치 뒤에 어떤 리스크가 남아 있는가?
- 출시 후에 시스템의 담당자는 누구인가?

같은 설계가 나중에 슬라이드 한 장으로 엔지니어링 팀에 넘겨집니다. 중요한 선택은
회의 기억 속에만 존재합니다. 운영팀은 SLO나 롤백 규칙을 받지 못합니다. 정책팀은
지식 신선도를 자신이 담당한다는 사실을 모릅니다. 검토자들은 파일럿 중에야 자신의
대기열을 발견합니다.

설계는 기술적으로 옳으면서도 여전히 전달 불가능할 수 있습니다. 커뮤니케이션과
라이프사이클 담당 체계도 아키텍처의 책임입니다.

## 핵심 개념

### 하나의 시스템에는 여러 관점이 필요하다

이해관계자마다 필요한 것은 서로 다른 결정이지, 서로 다른 진실이 아닙니다.

| 청중 | 주된 질문 | 최소한의 근거 |
|------|-----------|---------------|
| 경영진 | 잔여 리스크와 투자를 감수할 가치가 있는가? | 결과, 베이스라인, 목표, 옵션, 비용 범위, 리스크 결정 |
| 제품과 운영 | 워크플로와 사용자 경험이 어떻게 바뀌는가? | 여정(journey), 예외, 검토, SLO, 도입 계획 |
| 엔지니어링 | 무엇을 만들어야 하고 경계는 어떻게 동작하는가? | 컴포넌트, 계약, 신원, 오류, 버전, 테스트 |
| 보안과 개인정보 | 데이터와 권한이 어디서 경계를 넘는가? | 데이터 맵, 위협 모델, 통제, 보존, 근거 |
| 도메인 담당자 | 출력이 실제 과제에 타당한가? | 평가 케이스, 출처, 정책, 에스컬레이션, 변경 담당 |
| SRE와 지원팀 | 실패를 어떻게 감지, 제한, 복구하는가? | 텔레메트리, 알림, 런북, 롤백, 의존성 |

결정을 빼 버림으로써 단순화하지 마세요. 같은 결정을 각 청중이 사용하는 근거의
언어로 번역하세요.

### 아키텍처 서사(narrative) 만들기

유용한 검토는 결정의 순서를 따릅니다:

1. 현재 워크플로와 측정 가능한 문제.
2. 솔루션의 모양을 만드는 제약과 리스크.
3. 검토된 옵션들.
4. 권장 아키텍처와 그것이 이기는 이유.
5. 결과와 기각된 대안들.
6. 검증과 출시 계획.
7. 잔여 리스크와 필요한 승인.
8. 운영과 변경에 걸친 담당 체계.

컴포넌트 다이어그램부터 보여 주면 청중은 이 논리를 스스로 재구성해야 합니다.
논리를 먼저 주세요.

### 다이어그램은 하나의 질문에 답하는 데 쓰기

```mermaid
flowchart LR
    D["디스커버리\n결과와 제약"] --> A["아키텍처\n옵션과 결정"]
    A --> B["구축\n계약과 테스트"]
    B --> V["검증\n오프라인 근거"]
    V --> P["파일럿\n통제된 프로덕션 근거"]
    P --> O["운영\nSLO와 장애 대응"]
    O --> I["반복\n피드백과 변경 검토"]
    I --> D
```

컨텍스트 다이어그램은 무엇이 시스템 경계를 넘는지에 답합니다. 데이터 흐름
다이어그램은 민감한 데이터가 어디로 이동하는지에 답합니다. 시퀀스 다이어그램은
하나의 경로가 어떻게 동작하는지에 답합니다. 배포 다이어그램은 런타임 담당 체계에
답합니다. 통제 맵은 리스크가 어디서 예방되고, 탐지되고, 교정되는지에 답합니다.

기능을 다 얹은 다이어그램 하나는 어느 것에도 잘 답하지 못합니다.

### 회의록이 아니라 결정을 기록하기

ADR은 읽을 수 있을 만큼 짧고, 다시 찾아볼 수 있을 만큼 완전해야 합니다.

필수 필드:

- 상태와 결정 담당자
- 배경과 제약
- 옵션과 근거
- 결정과 논리
- 결과와 잔여 리스크
- 기각된 대안
- 검증 계획
- 되돌리기 조건과 재검토 날짜

기각된 대안이 중요합니다. 기각 기록이 없으면 미래의 팀이 같은 분석을 반복하거나,
어떤 제약을 깨는지 모른 채 설계를 바꿔 버립니다.

명시적인 확신도를 사용하세요. 검증되지 않은 지연 시간이나 비용 수치를 사실처럼
제시하는 것보다 "우리는 이렇게 추정한다"가 더 정직하고 유용합니다.

### 아키텍처를 계약으로 바꾸기

구현 가이던스에는 기계 검증 가능한 경계가 필요합니다:

- 요청 및 응답 스키마
- 신원과 인가 요구사항
- 버전 관리와 호환성 규칙
- 타임아웃, 재시도, 취소, 멱등성(idempotency) 동작
- 구조화된 오류 카테고리
- 데이터 분류와 보존
- 프롬프트, 모델, 도구, 지식의 담당
- 평가 픽스처와 출시 게이트
- 관측 가능성 필드와 비식별화(redaction)

아키텍처 패킷은 이런 계약들을 가리켜야 합니다. 구현의 모든 줄을 복제해서는 안
됩니다.

### 결정 단위로 담당자 정의하기

"AI 팀이 담당한다"는 너무 넓습니다.

다음 각각의 담당자를 지정하세요:

- 비즈니스 결과
- 제품 워크플로와 사용자 커뮤니케이션
- 프롬프트와 출력 계약
- 모델 선택과 라우팅
- 도구와 통합 서비스
- 지식 출처의 신선도
- 신원과 권한
- 평가 레이블과 수용 임계값
- 안전 및 컴플라이언스 통제
- 런타임 SLO와 장애 대응
- 벤더와 비용 관리
- 지원 중단(deprecation)과 폐기

변경을 권고하는 사람과, 그 리스크를 수용할 권한이 있는 사람을 분리하세요.

### 인수인계 수용 설계하기

인수인계는 문서 링크를 보냈을 때 완료되는 게 아니라, 받는 팀이 시스템을 안전하게
운영하고 변경할 수 있을 때 완료됩니다.

수용 기준:

- 담당자와 에스컬레이션 연락처 확인 완료
- 아키텍처와 ADR이 최신 상태
- 의존성과 접근 권한 프로비저닝 완료
- 대시보드와 알림 구동 중
- 장애 훈련을 통해 런북 리허설 완료
- 평가 스위트 실행 가능 및 베이스라인 저장
- 롤백 테스트 완료
- 데이터 보존 및 삭제 검증 완료
- 검토 대기열 인력 배치 완료
- 알려진 한계 전달 완료
- 변경 및 장애 프로세스 합의 완료

공동 수용 검토를 진행하세요. 받는 쪽 담당자가 시뮬레이션된 장애에서의 복구를
시연해야 합니다.

### 도입(adoption)을 워크플로의 일부로 계획하기

AI 시스템은 사람들이 일하는 방식을 바꿉니다. 인터페이스 훈련만으로는 부족합니다.
사용자는 다음을 알아야 합니다:

- 어떤 과제가 범위 안인지
- 어떤 근거를 살펴봐야 하는지
- 언제 수정, 기각, 에스컬레이션해야 하는지
- 어떤 데이터를 입력해도 되는지
- 시스템이 무엇을 기록하는지
- 유해하거나 잘못된 동작을 어떻게 보고하는지
- 서비스를 사용할 수 없을 때 무슨 일이 일어나는지

도입은 로그인 수만이 아니라 결과와 품질로 측정하세요. 높은 사용량 수치가 강제된
프로세스나 반복되는 재작업을 반영할 수도 있습니다.

### 장애를 영향과 결정으로 커뮤니케이션하기

장애가 발생하면 확인된 사실, 현재 영향, 완화 조치, 미지의 사항을 분리하세요.

```text
영향: 어떤 사용자, 과제, 레코드가 영향을 받을 수 있는가?
근거: 어떤 텔레메트리나 평가가 이를 확인하는가?
차단: 어떤 기능이 비활성화되었거나 안전하게 라우팅되었는가?
복구: 복구 전에 무엇이 통과해야 하는가?
후속 조치: 어떤 통제, 담당자, 가정이 바뀌는가?
```

모델의 의도를 추측하지 마세요. 관측 가능한 시스템 동작과 통제 대응을
설명하세요.

### 라이프사이클 근거를 연결된 상태로 유지하기

각 프로덕션 결과는 다음으로 거슬러 올라갈 수 있어야 합니다:

- 요구사항과 결정
- 시스템 및 구성 버전
- 테스트와 승인 근거
- 배포와 런타임 트레이스
- 사람의 검토 또는 수정(override)
- 다운스트림 결과
- 근거가 문제를 드러낼 경우의 변경 요청

이 사슬이 디버깅, 거버넌스, 합리적인 반복 개선을 지원합니다.

## 캡스톤 연계

검증된 전달 패킷을 Architect Professional 캡스톤의 마지막 인수인계 섹션으로
사용하세요.

다섯 개 산출물로 전달 패킷을 만드세요.

### 1. 경영진 결정 브리프

한 페이지: 문제, 베이스라인, 목표, 옵션, 권고안, 투자 범위, 주요 리스크,
검증, 요청하는 결정.

### 2. 아키텍처 결정 기록(ADR)

선택된 패턴과 최소 두 개의 기각된 대안을 담으세요. 되돌리기 조건도 포함합니다.

### 3. 엔지니어링 계약 인덱스

```markdown
| 경계 | 계약 | 담당자 | 버전 규칙 | 실패 규칙 | 테스트 |
|------|------|--------|-----------|-----------|--------|
```

### 4. 운영 준비성 체크리스트

대시보드, 알림, 런북, 접근 권한, 평가, 롤백, 의존성, 검토 용량, 장애
커뮤니케이션을 포함하세요.

### 5. 담당 및 변경 맵

```markdown
| 결정 또는 자산 | 운영 담당자 | 변경 승인자 | 근거 | 재검토 트리거 |
|----------------|-------------|-------------|------|----------------|
```

탁상 훈련(tabletop exercise)을 실행하세요. 낡은 검색이 안전하지 않은 추천을
만드는 상황, 인가 서비스 실패, 평가기 드리프트를 시뮬레이트합니다. 받는 팀이
영향을 식별하고, 기능을 차단하고, 알려진 안전 버전에서 복구하고, 후속 담당을
기록해야 합니다.

엔터프라이즈 리서치 어시스턴트라면 다음 관점들을 제공하세요:

- 경영진: 애널리스트 사이클 시간 단축, 근거 품질 목표, 예산, 잔여 기밀성 리스크.
- 제품: 쿼리 여정, 근거 부족 상태, 인용 경험, 피드백 경로.
- 엔지니어링: 검색, 모델, 도구, 신원, 평가 계약.
- 보안: 테넌트 경계, 출처 권한, 로그, 보존, 장애 통제.
- 운영: 신선도, 지연 시간, 비용, 오류, 품질 대시보드와 롤백 규칙.

사실은 일관되게 유지됩니다. 세부 사항은 각 청중이 담당하는 결정을 따라갑니다.

파일럿이 끝나면 정확도만 검토하지 마세요. 애널리스트 시간, 인용 확인 행동,
검토자 업무량, 과제 클래스별 도입률, 승인된 보고서당 비용, 장애를 비교하세요.
확대, 수정, 제한, 중단 중 하나를 결정하세요.

## 시험 의사결정 패턴

시나리오가 트레이드오프를 어떻게 전달할지 묻는다면, 비즈니스 결과, 기술적 근거,
기각된 대안, 잔여 리스크를 청중에 맞는 언어로 진술하세요.

다음과 같은 답을 선호하세요:

- 확정 전에 구조화된 디스커버리를 수행한다
- 배경, 옵션, 결과를 문서화한다
- 프롬프트, 데이터, 도구, 통제, 지표, 운영에 담당자를 지정한다
- 구현 계약과 실패 계약을 정의한다
- 운영 준비성과 인수인계 수용을 요구한다
- 피드백을 버전화된 변경 결정에 연결한다

SLO, 런북, 평가기, 담당 체계, 롤백 없이 다이어그램만 넘기는 답은 피하세요.

## 흔한 함정

### 모든 청중을 위한 하나의 발표 자료

경영진은 구현 세부에 빠져 죽거나, 엔지니어는 막연한 주장을 받게 됩니다. 결정에
맞게 조율된 일관된 관점들을 사용하세요.

### 출시용 산출물로서의 아키텍처

아키텍처는 근거, 규모, 의존성, 리스크에 따라 바뀝니다. 운영 기간 내내 결정과
다이어그램을 버전 관리하세요.

### 팀 이름으로 하는 담당 배정

팀 레이블은 낡은 출처를 갱신하는 사람, 평가 변경을 수용하는 사람, 알림에
대응하는 사람을 특정하지 못합니다. 구체적인 결정을 배정하세요.

### 도입 = 가치라는 등식

품질, 검토 부담, 총 처리 시간이 나빠지는 동안에도 사용량은 늘 수 있습니다.
결과를 측정하세요.

## 연습 문제

1. 기술 아키텍처를 한 페이지짜리 경영진 결정 브리프로 바꿔 보세요.
2. 측정 가능한 되돌리기 조건이 있는 ADR을 작성해 보세요.
3. 도구가 부분 결과를 반환하기 시작하는 상황의 인수인계 훈련을 만들어 보세요.
4. RAG 애플리케이션에서 변경 가능한 모든 산출물에 담당자를 배정해 보세요.
5. 품질, 재작업, 사용자 신뢰를 포함하는 도입 스코어카드를 설계해 보세요.

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|--------------------|-----------|
| 이해관계자 | 회의에 초대된 사람 | 결정이나 결과를 소유하거나, 영향을 주거나, 떠안는 사람 또는 집단 |
| ADR | 아키텍처 문서화 | 하나의 결정, 그 배경, 대안, 결과에 대한 집중 기록 |
| 인수인계 | 문서를 보냄 | 근거와 함께 운영 능력과 수용된 책임을 이전 |
| 운영 준비성 | 배포 성공 | 담당, 통제, 관측 가능성, 복구, 평가, 지원이 입증됨 |
| 도입(adoption) | 사용자 수 | 숨겨진 부담 없이 의도된 결과를 만드는 지속적인 워크플로 사용 |
| 되돌리기 조건 | 확신 부족 | 계획된 아키텍처 또는 범위 변경을 촉발하는 근거 |
