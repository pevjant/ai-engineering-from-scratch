## 2. 메시지

모든 메시지는 JSON-RPC 2.0을 따르며, 여기에 다음 MCP 규칙이 붙습니다:

- **요청(Request)**: `{"jsonrpc":"2.0","id":<string|integer>,"method":...,"params":{...}}`. id는 null이어서는 안 되고(MUST NOT), 아직 응답을 기다리는 id를 재사용해서도 안 됩니다.
- **결과 응답(Result response)**: 요청과 같은 id. `result`는 반드시 `resultType`을 포함해야 합니다(MUST).
  - `"complete"`: 최종 콘텐츠.
  - `"input_required"`: `InputRequiredResult`(MRTR, 7절).
  - 확장은 캐퍼빌리티로 광고한 경우에만 값을 추가할 수 있습니다(MAY). 태스크 확장은 `"task"`를 추가합니다.
  - 클라이언트는 모르는 `resultType`을 무효한 것으로 다뤄야 하고(MUST), `resultType`이 없는 경우(레거시 서버)는 `"complete"`로 다뤄야 합니다.
- **오류 응답(Error response)**: `{"jsonrpc":"2.0","id":...,"error":{"code":<int>,"message":...,"data":...}}`. id를 생략하는 것은 잘못된 형태의 요청에서 id를 읽을 수 없었던 경우뿐입니다.
- **알림(Notification)**: `method`와 선택적 `params`로 이루어지며 id를 절대 포함해서는 안 됩니다. 받는 쪽은 절대 응답해서는 안 됩니다.
- JSON-RPC 배칭은 없습니다(2025-06-18에 제거). Streamable HTTP에서 각 POST 본문은 정확히 하나의 요청 또는 알림입니다.

## 3. `_meta`와 요청별 프로토콜 필드

키 이름: 선택적 접두사(점으로 구분된 라벨들에 `/`를 더한 형태, 역방향 DNS 권장)와 영숫자로 시작하고 끝나는 이름으로 이루어집니다. 두 번째 라벨이 `modelcontextprotocol` 또는 `mcp`인 접두사는 MCP용으로 예약되어 있습니다(`io.modelcontextprotocol/`, `dev.mcp/`); `com.example.mcp/`는 예약되지 않았습니다.

모든 클라이언트 요청에 필요합니다(하나라도 빠지면 요청은 잘못된 형태가 됩니다: JSON-RPC `-32602`, HTTP `400 Bad Request`):

| 키 | 필수 여부 | 의미 |
|---|---|---|
| `io.modelcontextprotocol/protocolVersion` | 예 | 예: `"2026-07-28"` |
| `io.modelcontextprotocol/clientCapabilities` | 예 | 이 요청과 관련된 캐퍼빌리티(`{}`일 수 있음) |
| `io.modelcontextprotocol/clientInfo` | 아니오(SHOULD) | `Implementation`: `name`, `version`, 선택적 `title`, `description`, `websiteUrl`, `icons` |
| `io.modelcontextprotocol/logLevel` | 아니오 | 이 요청의 최소 로그 레벨(deprecated된 로깅 기능) |
| `progressToken` | 아니오 | 이 요청이 `notifications/progress`를 받도록 등록함 |

결과에는 서버가 `result._meta`에 `io.modelcontextprotocol/serverInfo`를 넣는 것이 좋습니다(SHOULD).
`clientInfo`와 `serverInfo`는 스스로 보고한 값입니다. 표시, 로깅, 디버깅에는 쓸 수 있지만 보안 결정에는 절대 쓰지 마세요.

그 밖의 예약된 키: `io.modelcontextprotocol/subscriptionId`(`subscriptions/listen` 스트림의 모든 메시지에 붙음), 그리고 `traceparent`, `tracestate`, `baggage`(OpenTelemetry 컨텍스트, W3C Trace Context와 W3C Baggage 형식; 접두사 규칙의 유일한 예외, SEP-414).

최소한의 모던 요청:

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {"location": "Pune"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {"name": "ExampleClient", "version": "1.0.0"}
    }
  }
}
```

## 4. 무상태성(Statelessness)

- 요청을 처리하는 데 필요한 모든 정보는 요청 안에 있습니다. 서버는 캐퍼빌리티, 버전, 신원을 위해 같은 연결의 이전 요청에 의존해서는 안 됩니다(MUST NOT).
- stdio 프로세스나 HTTP 연결은 세션이 아닙니다. 클라이언트는 하나의 전송(transport) 위에서 서로 관련 없는 요청을 섞어 보낼 수 있습니다.
- 요청들에 걸치는 상태(오래 도는 작업, 장바구니, 브라우저 컨텍스트)는 클라이언트가 매 요청마다 넘겨주는 명시적인 식별자로 참조해야 합니다(MUST). 도구 결과로 돌려 받아 일반 인자로 다시 넘기는, 서버가 발급한 핸들(handle)이 그 식별자입니다(SEP-2567). 핸들은 이름이지 캐퍼빌리티가 아닙니다. 호출할 때마다 그 핸들 기준으로 호출자를 인가하고, 핸들을 불투명(opaque)하게 유지하며, 수명을 도구 설명에 밝히고, 만료된 핸들은 도구 실행 오류로 보고하세요.
- `tools/list`, `resources/list`, `prompts/list`는 연결마다 달라져서는 안 되고(MUST NOT), 다른 요청의 부수 효과로 달라져서도 안 됩니다. 요청이 제시한 인가에 따라 달라지는 것은 허용됩니다(MAY).
- 이유: 어떤 레플리카(replica)든 어떤 요청이든 처리할 수 있고, 재시도를 어디로 라우팅해도 안전하며, 로드 밸런서에 스티키(sticky) 세션이 필요 없습니다.

| 코드 | 이름 | 용도 |

| -32600 | Invalid Request | 유효한 요청 객체가 아님 |
| -32601 | Method not found | 모르는 메서드(HTTP에서는 `404 Not Found`) |
| -32602 | Invalid params | 모르는 도구; 필수 `_meta` 누락; 리소스 없음; 잘못된 프롬프트 이름 또는 프롬프트 인자 누락; 잘못된 커서; 잘못된 로그 레벨 |
| -32603 | Internal error | 서버 내부 실패 |
| -32020 | HeaderMismatch | HTTP 헤더가 본문과 불일치하거나 필수 헤더가 없음(HTTP `400`) |
| -32021 | MissingRequiredClientCapability | `data.requiredCapabilities`가 클라이언트가 선언해야 할 것을 나열함(HTTP `400`) |
| -32022 | UnsupportedProtocolVersion | `data.supported`(목록)와 `data.requested` 제공(HTTP `400`) |

할당 정책(2026-07-28):

- `-32000`~`-32019`: 레거시 영역. 새 코드를 여기에 할당해서는 안 되고(MUST NOT), 새 구현은 아예 이 영역을 쓰지 않는 것이 좋습니다(SHOULD).
- `-32020`~`-32099`: MCP 명세 예약 영역. 이 범위에서 정의되지 않은 코드를 내보내는 것은 금지됩니다.
- 이 리비전의 구현은 `-32002`나 `-32042`를 내보내서는 안 됩니다(MUST NOT). 클라이언트는 여전히 오래된 서버의 `-32002`를 "리소스 없음"으로 받아들이는 것이 좋습니다(SHOULD).
- 애플리케이션이 정의하는 오류 코드는 `-32768`~`-32000` 밖에 두는 것이 좋습니다(SHOULD).

도구의 두 오류 채널(시험에 가장 많이 나오는 구분):

1. **프로토콜 오류**(JSON-RPC `error`): 모르는 도구(`-32602`), `CallToolRequest` 스키마를 통과하지 못하는 요청, 서버 오류.
2. **도구 실행 오류**(`isError: true`와 설명이 되는 `content`를 담은 정상 결과): API 실패, 잘못된 날짜 형식이나 범위를 벗어난 값 같은 입력 검증 오류, 비즈니스 로직상의 거절, 만료된 핸들. 이것들은 모델에게 되돌아가 스스로 고칠 수 있게 합니다(SEP-1303, 2025-11-25).

모르는 도구는 `-32601`이 아니라 `-32602`입니다. 도구의 `inputSchema`를 위반하는 인자는 `-32602`가 아니라 도구 실행 오류입니다.

## 6. `server/discover`와 버전 협상

- 서버는 `server/discover`를 구현해야 합니다(MUST). 요청은 표준 `_meta`만 실습니다.
- `DiscoverResult`(캐시 가능한 결과): `resultType`, `supportedVersions`, `capabilities`, 선택적 `instructions`(모델을 위한 자연어 안내), `_meta["io.modelcontextprotocol/serverInfo"]`, `ttlMs`, `cacheScope`.
- 이를 호출하는 것은 선택입니다. 클라이언트는 아무 요청이나 바로 보내고, `UnsupportedProtocolVersionError`가 오면 `data.supported`에 있는 버전으로 재시도해 처리할 수 있습니다.
- stdio에서는 듀얼 era 클라이언트가 먼저 `server/discover`로 탐지(probe)하는 것이 좋습니다(SHOULD). `DiscoverResult`가 오면 모던입니다. `-32022` 같이 알아볼 수 있는 모던 오류가 오면 버전만 다른 모던입니다(폴백 금지). 그 밖의 오류나 타임아웃이면 레거시입니다(`initialize`로 폴백). 폴백 판정이 특정 오류 코드 하나에만 매여서는 안 됩니다(MUST NOT).
- HTTP에서는 듀얼 era 클라이언트가 모던 요청을 시도하고 `400` 본문을 살펴봅니다. 알아볼 수 있는 모던 JSON-RPC 오류면 모던, 그 밖이면 레거시입니다.
- 시대 판정은 서버 프로세스별(stdio) 또는 오리진(origin)별(HTTP)로 캐시하세요.
- 모던 전용 서버는 `initialize`에 대해 돌려주는 오류에 자기가 지원하는 버전을 밝히는 것이 좋습니다(SHOULD).

서버 캐퍼빌리티: `tools {listChanged}`, `resources {listChanged, subscribe}`, `prompts {listChanged}`, `completions {}`, `logging {}`(deprecated), `extensions {...}`, `experimental {...}`.
클라이언트 캐퍼빌리티: `elicitation {form, url}`, `sampling {context, tools}`(deprecated), `roots {}`(deprecated), `extensions {...}`, `experimental {...}`.
서버는 클라이언트가 그 요청에서 선언하지 않은 캐퍼빌리티에 의존해서는 안 됩니다(MUST NOT). 필요하면 `-32021`을 돌려줍니다.

## 7. 다중 왕복 요청(MRTR, Multi Round-Trip Requests)

모든 서버 주도 요청을 대체합니다(SEP-2322). 호환성을 깨는 변경입니다.

1. 클라이언트가 요청을 보냅니다.
2. 서버는 `{"resultType":"input_required","inputRequests":{...},"requestState":"..."}`를 돌려줍니다. `inputRequests` 또는 `requestState` 중 최소 하나는 반드시 포함해야 합니다(MUST).
3. `inputRequests`는 서버가 고른 키에서 요청 객체로의 맵이며, 각 값은 `elicitation/create`, `sampling/createMessage`, `roots/list` 중 정확히 하나입니다. 서버는 클라이언트가 캐퍼빌리티를 선언하지 않은 요청 유형을 포함해서는 안 됩니다(MUST NOT).
4. 클라이언트는 답을 모아 **새 JSON-RPC id로 원래 요청을 재시도**하며, `params.inputResponses`(같은 키)를 더하고 `params.requestState`를 바이트 단위로 그대로 되돌려 줍니다. 받은 적이 없다면 `requestState`를 포함해서는 안 됩니다(MUST NOT).
5. 서버는 최종 결과로 완료하거나, 또 다른 `InputRequiredResult`로 다시 묻습니다.

`tools/call`, `prompts/get`, `resources/read`만이 `InputRequiredResult`를 돌려줄 수 있습니다.
`requestState`는 공격자가 조작할 수 있는 입력입니다. 인가, 리소스 접근, 비즈니스 로직에 영향을 준다면 HMAC이나 AEAD로 보호하고, 인증된 주체(principal), 짧은 만료 시간, 원래 요청의 다이제스트에 묶어야 합니다. 일회성은 서버 쪽에서 강제되어야 합니다.
`input_required` 결과와 MRTR 재시도는 절대 캐시되지 않습니다.

## 8. 알림, 구독, 진행 상황, 취소

- `subscriptions/listen`은 오래 유지되는 스트림을 엽니다. `params.notifications`는 필터입니다. `toolsListChanged`, `promptsListChanged`, `resourcesListChanged`(불리언)와 `resourceSubscriptions`(URI 목록). 서버는 요청하지 않은 유형을 보내서는 안 됩니다(MUST NOT).
- 첫 메시지는 반드시 `notifications/subscriptions/acknowledged`여야 하고(MUST), 서버가 지켜 줄 부분집합을 되돌려 보여 줍니다. 스트림의 모든 메시지는 `_meta["io.modelcontextprotocol/subscriptionId"]`를 실으며, 그 값은 `subscriptions/listen` 요청의 JSON-RPC id입니다.
- 스트림 알림: `notifications/tools/list_changed`, `notifications/prompts/list_changed`, `notifications/resources/list_changed`, `notifications/resources/updated`(`uri` 포함).
- 요청 범위(request-scoped) 알림(`notifications/progress`, `notifications/message`)은 자기가 속한 요청의 응답 스트림으로만 흐르며, 절대 listen 스트림으로 흐르지 않습니다.
- 진행 상황: 클라이언트가 `_meta.progressToken`을 설정합니다(문자열 또는 정수, 활성 요청들 사이에서 고유). `notifications/progress`는 `progressToken`과 끊임없이 증가하는 `progress`, 선택적 `total`과 `message`를 실으며, 요청이 끝나면 알림도 멈춥니다.
- 취소: Streamable HTTP에서는 요청의 SSE 응답 스트림을 닫는 것이 곧 취소입니다(별도 메시지 없음). stdio에서는 클라이언트가 `requestId`와 선택적 `reason`을 담아 `notifications/cancelled`를 보냅니다. 서버가 `notifications/cancelled`를 보내는 경우는 `subscriptions/listen` 스트림을 해체할 때뿐입니다. 취소된 요청에 늦게 도착한 응답은 무시합니다. 경쟁 상태(race)는 정상입니다.
- 모든 요청에 타임아웃이 있어야 하고(SHOULD), 진행 알림이 오고 있어도 딱 잘라 최대 시간이 있어야 합니다.
- 구독을 우아하게 끝내는 서버는 `resultType: "complete"`와 `_meta` 안의 구독 id를 담은 `subscriptions/listen` 결과를 보내는 것이 좋습니다(SHOULD).

## 9. 전송(Transport)

**stdio**

- 클라이언트가 서버를 서브프로세스로 실행합니다. 줄바꿈으로 구분된 JSON-RPC이며, 안에 줄바꿈을 포함하지 않습니다.
- `stdout`에는 MCP 메시지만 흐르고, `stderr`에는 로그가 흐릅니다(반드시 오류일 필요는 없음).
- 서버는 요청을 `stdout`에 절대 쓰지 않습니다. 모든 메타데이터는 `_meta` 안에 인라인입니다(헤더 계층 없음).
- 종료: 클라이언트가 `stdin`을 닫고 기다린 뒤 단계를 올립니다(SIGTERM, SIGKILL). 예상 밖의 종료가 발생하면 클라이언트는 서버를 다시 띄우고 잃어버린 요청을 재시도하며 `subscriptions/listen`을 다시 보냅니다.
- 인가: stdio 구현은 OAuth 흐름을 쓰지 말아야 하고(SHOULD NOT) 대신 환경에서 자격 증명을 읽어야 합니다.

**Streamable HTTP**

- POST를 받는 하나의 MCP 엔드포인트(예: `https://example.com/mcp`). 모든 클라이언트 메시지는 각자 자기 POST입니다.
- `Accept`는 `application/json`과 `text/event-stream`을 모두 나열합니다. 요청에 대한 응답은 JSON 객체 하나이거나 그 요청에 한정된 SSE 스트림이며, 클라이언트는 둘 다 지원해야 합니다(MUST).
- 알림 POST는 본문 없이 `202 Accepted`를 돌려줍니다.
- SSE 스트림은 요청 관련 알림을 실은 뒤 최종 응답을 실습니다. 서버는 어떤 스트림으로도 요청을 보내서는 안 됩니다(MUST NOT).
- GET 엔드포인트 없음, `Mcp-Session-Id` 없음, `Last-Event-ID` 없음. 모던 전용 서버는 GET이나 DELETE에 `405`로 답하고 세션·이벤트 id 헤더는 무시합니다.
- 보안: DNS 리바인딩(rebinding)을 막기 위해 `Origin`을 검증하고(존재하는데 잘못됐다면 `403`으로 답함), 로컬일 때는 `127.0.0.1`에 바인딩하고, 인증하세요.
- 필수 헤더: 모든 POST에 `MCP-Protocol-Version`(`_meta` 버전과 일치해야 하며, 아니면 `400`과 `-32020`); 모든 요청에 `Mcp-Method`; `tools/call`, `resources/read`, `prompts/get`에 `Mcp-Name`(`params.name` 또는 `params.uri`에서 가져옴).
- 도구 입력 스키마의 `x-mcp-header`는 프리미티브 인자(정수, 문자열, 불리언. 절대 `number`가 아니며, 스키마 루트에서 정적으로 도달 가능한 속성만)를 `Mcp-Param-{Name}`으로 미러링합니다. 헤더 값은 중개자에게 보이기 때문에 서버 개발자는 민감한 매개변수(비밀번호, API 키, 토큰, 개인 식별 정보)를 표시하지 말아야 합니다(SHOULD NOT). 평범한 ASCII가 아닌 값은 `=?base64?...?=` 센티널을 씁니다. HTTP의 클라이언트는 `x-mcp-header` 값이 제약을 위반하는 도구를 `tools/list` 결과에서 제외하는 방식으로 반드시 거절해야 합니다(MUST). 서버는 본문과 불일치하는 헤더를 반드시 거절해야 합니다(`-32020`).
- 상태 코드: 지원하지 않는 버전은 `400`과 `-32022`; 캐퍼빌리티 누락은 `400`과 `-32021`; 모르는 메서드는 `404`와 `-32601`; 토큰 누락 또는 무효는 `401`; 스코프 부족은 `403`.
- 2024-11-05 전송 방식인 HTTP+SSE는 2025-03-26부터 Deprecated 상태입니다(SEP-2596). 가장 이른 제거 시점은 SEP-2596이 Final에 도달한 지 석 달 후입니다.

## 10. 서버 프리미티브(Primitive)

제어 모델: 도구는 **모델이 제어(model-controlled)**하고, 리소스는 **애플리케이션이 주도(application-driven)**하며, 프롬프트는 **사용자가 제어(user-controlled)**합니다.

**도구(Tools)**

- `tools/list`는 페이지네이션과 캐싱을 지원하며, 결정적인 순서로 정렬되는 것이 좋습니다(SHOULD). 클라이언트 캐싱과 LLM 프롬프트 캐시 적중을 위해서입니다.
- 도구 정의: `name`, 선택적 `title`, `description`, 선택적 `icons`, `inputSchema`(JSON Schema 객체. 절대 null이 아니며, 매개변수가 없으면 `{"type":"object","additionalProperties":false}` 사용), 선택적 `outputSchema`, 선택적 `annotations`, 선택적 `_meta`.
- 이름은 1~128자의 `A-Za-z0-9_-.`이면 좋고(SHOULD), 대소문자를 구별하며 서버 안에서 고유해야 합니다. 애그리게이터(aggregator)는 이름 앞에 서버 식별자를 붙이는 것이 좋습니다. `serverInfo.name`은 고유하지 않습니다.
- 어노테이션은 힌트일 뿐이며 서버를 신뢰할 수 없다면 신뢰할 수 없는 것으로 다뤄야 합니다(MUST). `title`, `readOnlyHint`(기본 false), `destructiveHint`(기본 true, read-only가 아닐 때만 의미 있음), `idempotentHint`(기본 false), `openWorldHint`(기본 true).
- `tools/call` 매개변수: `name`, `arguments`, 그리고 재시도 시에는 `inputResponses`와 `requestState`.
- `CallToolResult`: `content`(콘텐츠 블록 목록), 선택적 `structuredContent`(아무 JSON 값이나 가능. `outputSchema`가 있으면 그에 맞아야 하고, 텍스트 블록으로 직렬화도 하는 것이 좋음(SHOULD)), 선택적 `isError`.
- 콘텐츠 블록: `text`; `image`(`data`, `mimeType`); `audio`; `resource_link`(`uri`, `name`, 선택적 `description`, `mimeType`); `resource`(임베디드 내용). 모두 `annotations`를 받습니다(`audience`: `user` 또는 `assistant`; `priority` 0~1; `lastModified`).
- 사람이 호출을 거절할 수 있어야 합니다(SHOULD). 서버는 입력을 검증하고, 접근 제어를 집행하고, 요청 속도를 제한하고, 출력을 정화(sanitize)해야 합니다(MUST). 클라이언트는 민감한 작업을 확인받고, 호출 전에 입력을 보여 주고, 결과를 검증하고, 타임아웃을 정하고, 사용 기록을 남기는 것이 좋습니다(SHOULD).

**리소스(Resources)**

- `resources/list`, `resources/read`, `resources/templates/list`(RFC 6570 URI 템플릿). 내용은 `{uri, mimeType, text}` 또는 `{uri, mimeType, blob}`입니다.
- 캐퍼빌리티는 `resources {listChanged, subscribe}`. 업데이트는 `resourceSubscriptions`을 곁들인 `subscriptions/listen`으로 도착합니다.
- 리소스가 없으면 `-32602`(빈 `contents` 배열을 돌려주면 안 됨). 내부 오류는 `-32603`. 레거시 `-32002`는 받아들입니다.
- URI 스킴: `https://`는 클라이언트가 직접 가져올 수 있을 때만; `file://`(실제 파일시스템일 필요는 없으며, 경로 탐색(traversal) 공격에 대비해 경로를 정화해야 함); `git://`; 그 밖의 커스텀 스킴은 RFC 3986을 따릅니다.

**프롬프트(Prompts)**

- `prompts/list`, 그리고 `arguments`를 곁들인 `prompts/get`. 결과는 `role`(`user` 또는 `assistant`)과 콘텐츠 블록을 담은 `messages`를 실습니다.
- 오류: 잘못된 이름이나 필수 인자 누락은 `-32602`, 내부 오류는 `-32603`입니다.

**완성(Completion)**: `completion/complete`는 `ref`(이름으로는 `ref/prompt`, URI나 템플릿으로는 `ref/resource`), `argument {name, value}`, `context.arguments`를 받습니다. 최대 100개의 `values`에 `total`과 `hasMore`를 더해 돌려줍니다. 캐퍼빌리티는 `completions {}`입니다.

**페이지네이션(Pagination)**: 불투명한(opaque) `cursor`와 `nextCursor`. 페이지 크기는 서버가 정합니다. 빈 문자열도 유효한 커서이며, 잘못된 커서는 `-32602`입니다.

**캐싱(Caching)**(SEP-2549): `server/discover`, `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read`의 `resultType: "complete"` 결과는 반드시 `ttlMs`(0 이상의 정수)와 `cacheScope`(`"public"` 또는 `"private"`)를 실어야 합니다(MUST). `ttlMs`는 신선도 힌트이지 폴링 주기가 아닙니다. list-changed 알림이 오면 캐시가 즉시 무효화됩니다. `"private"` 캐시는 절대 인가 컨텍스트를 넘지 않습니다. `cacheScope`는 절대 접근 제어가 아닙니다.

## 11. 클라이언트 기능

**일리시테이션(Elicitation)**(MRTR `inputRequests`를 통해, 메서드는 `elicitation/create`)

- 폼 모드: `mode: "form"`(선택적), `message`, `requestedSchema`(프리미티브 속성의 평면적인 객체). URL 모드: `mode: "url"`, `message`, `url`(OAuth 동의 화면이나 결제 같은 밴드 외(out-of-band) 페이지로, 민감한 데이터가 클라이언트를 거쳐 가면 안 되는 곳).
- `ElicitResult.action`: `accept`(폼 모드에서는 `content`와 함께), `decline`, `cancel`.
- 클라이언트 캐퍼빌리티: `elicitation {form, url}`.

**폐기 예정(deprecated) 기능**(명세의 deprecated 레지스트리. 제거되기 전까지는 전부 여전히 동작합니다):

| 기능 | Deprecated를 지정한 SEP | Deprecated가 된 리비전 | 이전 방법 | 가장 이른 제거 시점 |
|---|---|---|---|---|
| Roots | SEP-2577 | 2026-07-28 | 디렉터리를 도구 매개변수, 리소스 URI, 서버 설정으로 전달 | 2027-07-28 이후 최초로 출시되는 리비전 |
| Sampling | SEP-2577 | 2026-07-28 | LLM 제공자 API를 직접 호출 | 2027-07-28 이후 최초로 출시되는 리비전 |
| Logging | SEP-2577 | 2026-07-28 | `stderr`(stdio)로 기록하거나 OpenTelemetry 사용 | 2027-07-28 이후 최초로 출시되는 리비전 |
| 동적 클라이언트 등록(Dynamic Client Registration) | PR #2858 | 2026-07-28 | Client ID Metadata Documents | 2027-07-28 이후 최초로 출시되는 리비전 |
| `includeContext: "thisServer" \| "allServers"` | SEP-2596 | 2025-11-25 | 생략하거나 `"none"` 사용 | Sampling을 따름 |
| HTTP+SSE 전송 | SEP-2596 | 2025-03-26 | Streamable HTTP | SEP-2596이 Final에 도달한 지 석 달 후 |

로깅은 여전히 요청별로 동작합니다. `_meta["io.modelcontextprotocol/logLevel"]`을 실은 요청은 자기 응답 스트림 위에서 `notifications/message`(RFC 5424의 syslog 레벨)를 받을 수 있습니다. 그 키가 없다면 서버는 절대 내보내서는 안 됩니다(MUST NOT).

## 12. 인가(HTTP 전송)

- 전체적으로는 선택입니다. HTTP 구현은 따르는 것이 좋고(SHOULD), stdio는 따르지 말아야 합니다(SHOULD NOT. 환경 자격 증명을 사용).
- 역할: MCP 서버는 OAuth 2.1 리소스 서버, MCP 클라이언트는 OAuth 2.1 클라이언트이고, 인가 서버가 토큰을 발급합니다.
- MCP 서버는 Protected Resource Metadata(RFC 9728)를 반드시 구현해야 하고(MUST), `authorization_servers`에 최소 한 개 항목을 나열해야 합니다. 디스커버리는 `401`에 붙는 `WWW-Authenticate: Bearer resource_metadata="..."` 또는 잘 알려진(well-known) URI를 통해 이루어집니다. 경로별 `/.well-known/oauth-protected-resource/<path>`를 먼저 보고 그다음 루트를 봅니다.
- 인가 서버 메타데이터: RFC 8414 또는 OpenID Connect Discovery. 경로가 있는 발급자(issuer)라면 클라이언트는 `/.well-known/oauth-authorization-server/<path>`, `/.well-known/openid-configuration/<path>`, `<path>/.well-known/openid-configuration` 순서로 시도합니다. 메타데이터의 `issuer`는 URL을 만드는 데 쓴 발급자와 정확히 같아야 합니다(MUST).
- PKCE는 필수이며, 가능하면 `S256`을 씁니다. `code_challenge_methods_supported`가 없다면 클라이언트는 진행을 거절해야 합니다(MUST).
- 리소스 인디케이터(RFC 8707): `resource` 매개변수는 인가 요청과 토큰 요청 양쪽에 붙으며, 정준(canonical) 서버 URI를 담습니다(스킴 + 호스트, 프래그먼트 없음, 관례상 끝 슬래시 없음). 인가 서버가 무시하더라도 클라이언트는 보냅니다.
- 토큰은 모든 HTTP 요청에서 `Authorization: Bearer <token>`으로 이동하며, 절대 쿼리 문자열에 넣지 않습니다.
- 서버는 오디언스(audience)를 검증해야 하고(MUST. 이 서버를 위해 발급된 토큰인지), 다른 토큰을 받아들이거나 그대로 전달해서는 안 됩니다(MUST NOT). 업스트림 API 호출에는 별도의 토큰을 씁니다(토큰 패스스루(passthrough)는 금지).
- 발급자 검증(RFC 9207): 클라이언트는 리다이렉트 전에 기대하는 발급자를 기록해 두고, 돌아온 `iss`와 정확히 비교합니다(정규화 없음). 불일치는 거절하며, 오류 응답일 때도 마찬가지입니다. 이것이 mix-up 공격에 대한 방어입니다.
- 스코프: 첫 번째 `WWW-Authenticate` 챌린지의 `scope`를 쓰고, 없으면 `scopes_supported`를 씁니다. 런타임에 스코프가 부족하면 `403`과 `error="insufficient_scope"`, 그리고 필요한 스코프 전체를 한 번의 챌린지로 돌려줍니다. 클라이언트는 기존 스코프와 새 스코프의 합집합으로 제한된 횟수만큼 재시도하며 단계를 올립니다.
- 리프레시 토큰: 발급된다고 가정하지 마세요. 퍼블릭 클라이언트의 리프레시 토큰은 회전(rotate)됩니다. 서버가 `offline_access`를 요구하는 일은 없어야 합니다.
- 상태 코드: `401`(토큰 없음 또는 무효), `403`(스코프 부족), `400`(잘못된 형태의 인가 요청).

**클라이언트 등록 우선순위**: (1) 미리 등록한 자격 증명; (2) 인가 서버가 `client_id_metadata_document_supported`를 광고할 때의 Client ID Metadata Documents; (3) `registration_endpoint`가 있을 때의 동적 클라이언트 등록(deprecated); (4) 사용자에게 묻기.

- CIMD: `client_id`는 경로를 가진 HTTPS URL이며, 최소한 `client_id`(URL과 정확히 같음), `client_name`, `redirect_uris`를 담은 JSON을 가리킵니다. 인가 서버는 이를 가져와 검증하고, 리다이렉트 URI를 검증하며, SSRF를 경계합니다. localhost 전용 리다이렉트 URI에는 추가 경고를 보여 주고, 리다이렉트 호스트명은 항상 표시합니다. CIMD id는 인가 서버들 사이에서 이동 가능(portable)합니다.
- DCR: 클라이언트는 반드시 `application_type`을 보내야 합니다(MUST. 데스크톱, CLI, localhost 앱은 `native`, 원격 브라우저 앱은 `web`).
- 인가 서버 바인딩: 저장해 둔 자격 증명은 발급자를 키로 하며, 다른 인가 서버와 절대 재사용하지 않고, 인가 서버가 바뀌면 다시 등록합니다.
- 혼동된 대리자(confused deputy): 정적 클라이언트 id를 쓰는 MCP 프록시는 제3자 인가 서버로 전달하기 전에 동적으로 등록된 클라이언트 각각에 대해 사용자 동의를 받아야 합니다(MUST).
- 통신: 인가 서버의 모든 엔드포인트는 HTTPS를 씁니다. 리다이렉트 URI는 localhost 또는 HTTPS이고 정확히 등록되며, `state`를 쓰고 검증하세요.

**인가 확장**(기본으로는 절대 활성화되지 않으며 `extensions`로 협상됨): 머신 대 머신 클라이언트(CI, 데몬)를 위한 OAuth Client Credentials, 중앙 IdP 정책을 위한 Enterprise-Managed Authorization.

## 13. 인가를 넘어선 보안 체크리스트

- 도구 설명, 어노테이션, 아이콘, 결과는 모델에게 신뢰할 수 없는 입력입니다(오염(poisoning), 프롬프트 인젝션, 정의를 바꿔 버리는 러그 풀(rug pull)).
- 아이콘: `https:` 또는 `data:` URI만 사용, 가져올 때 자격 증명을 실어 보내지 않기, 서버와 같은 오리진, SVG는 실행 가능할 수 있는 것으로 다루기.
- JSON Schema: 네트워크 `$ref`를 절대 자동 역참조하지 않기(옵트인만 허용, 호스트 허용 목록, 사설 주소 금지, 타임아웃 설정). 조합(composition) 키워드는 서비스 거부(denial of service)에 대비해 상한을 둘 것.
- Streamable HTTP: `Origin` 검증, localhost 바인딩, 인증.
- MRTR `requestState`: 무결성 보호, 주체 바인딩, 만료, 요청 바인딩.
- 로그에는 자격 증명, 비밀, 개인 데이터를 절대 담지 않습니다.
- 캐싱: `"public"` 응답은 사용자와 토큰을 넘어 공유될 수 있습니다. 프리미티브별 접근 제어는 여전히 필요합니다.

## 14. 확장(Extensions)

- 식별자: `_meta` 이름 규칙을 따르는 `{vendor-prefix}/{name}`. 공식 확장은 `io.modelcontextprotocol/`을 쓰고, 제3자는 자기 소유 도메인의 역방향 표기(`com.example/my-extension`)를 씁니다.
- 협상: 클라이언트는 매 요청의 `io.modelcontextprotocol/clientCapabilities.extensions`에서 지원을 선언하고, 서버는 `server/discover`의 `capabilities.extensions`에서 선언합니다. 값은 그 확장의 설정 객체입니다(`{}`는 설정 없이 지원한다는 뜻).
- 한쪽만 확장을 지원하면, 지원하는 쪽이 코어 동작으로 폴백하거나 적절한 오류로 요청을 거절합니다. 확장은 기본으로 비활성이며 명시적인 옵트인이 필요합니다. 호환성을 깨는 변경에는 새 식별자(예: `-v2`)가 필요합니다.
- 절차: SEP-2133(Extensions Track SEP, 공식 SDK 안의 참조 구현, 코어 메인테이너의 리뷰). 실험 저장소는 `experimental-ext-` 접두사를 쓰며 워킹 그룹 또는 인터레스트 그룹에 속합니다.
- 공식 확장:
  - **Tasks** `io.modelcontextprotocol/tasks`(SEP-2663): 서버는 지원하는 요청에 `resultType: "task"`로 답할 수 있습니다(`taskId`, 상태, TTL, 권장 폴링 간격을 담은 `CreateTaskResult`). 클라이언트는 `tasks/get`으로 폴링하고, 진행 중인 입력은 `tasks/update`(`inputResponses`)로 공급하며, `tasks/cancel`(협조적)을 보낼 수도 있습니다. 상태: `working`, `input_required`, `completed`(`result`를 실음), `failed`(`error`를 실음), `cancelled`. `tasks/result`는 없고 `tasks/list`도 없습니다.
  - **MCP Apps** `io.modelcontextprotocol/ui`(SEP-1865): 도구의 `_meta.ui`는 `resourceUri`를 실습니다. 이것은 평범한 `resources/read`로 가져오는 `text/html;profile=mcp-app` 타입의 `ui://` 리소스를 가리키며, `visibility`(기본 `["model", "app"]`; 도구에 `"model"`이 없으면 호스트는 그 도구를 에이전트에게 절대 나열해서 안 되고(MUST NOT), `"app"`이 없는 도구에 대한 앱의 `tools/call`은 반드시 거절해야 합니다)도 실습니다. UI 리소스 자체의 `_meta.ui`(`resources/read` 콘텐츠 항목에 붙음)는 `csp`(선택적인 `connectDomains`, `resourceDomains`, `frameDomains`, `baseUriDomains` 오리진 목록을 담은 객체)와 `permissions`(선택적인 `camera`, `microphone`, `geolocation`, `clipboardWrite` 플래그를 `{}`로 담은 객체)를 실습니다. 호스트는 CSP를 반드시 선언된 도메인들로 만들어야 하고(MUST), 선언되지 않은 도메인을 절대 허용해서는 안 되며, 더 제한해도 되고(MAY), `csp`가 빠졌다면 제한적인 기본값(`connect-src 'none'`)을 반드시 적용해야 합니다. `permissions`를 존중해도 되며(MAY), 앱은 권한이 부여됐다고 가정하지 말아야 합니다(SHOULD NOT). 뷰는 샌드박스 처리된 iframe에서 실행됩니다(웹 호스트는 다른 오리진의 샌드박스 프록시로 감쌉니다). 앱과 호스트는 `ui/` 메서드를 가진 JSON-RPC 방언으로 대화하며, 앱의 `ui/initialize`로 시작합니다. 이는 제거된 코어의 `initialize`와는 무관합니다. 확장이 없는 호스트를 위해 도구는 여전히 의미 있는 텍스트를 돌려줍니다.
  - **Skills over MCP** `io.modelcontextprotocol/skills`(SEP-2640): `skills/list`와 `skills/get`이며, 스킬 파일은 `resources/read`로 제공됩니다. `SKILL.md`를 읽는 것이 스킬을 활성화하지는 않습니다. 스킬 콘텐츠는 출처 서버가 표시된 신뢰할 수 없는 입력이고, 스킬을 아예 불러올지는 명시적인 사용자 정책이 결정합니다. 호스트는 불러오기 전에 사용자가 스킬을 검사할 수 있게 해야 하고(SHOULD), 스킬별 승인 없이 스킬 콘텐츠가 호스트 쪽 코드 실행을 일으키게 해서는 안 되며(MUST NOT), 사용자가 그 권한을 승인하지 않았다면 MCP로 제공되는 스킬의 `allowed-tools` 같은 권한을 넓히는 frontmatter는 반드시 무시해야 합니다(MUST).
  - **인가 확장**(`ext-auth`): OAuth Client Credentials와 Enterprise-Managed Authorization.

## 15. 거버넌스, 수명 주기, 생태계

- 기능 수명 주기(SEP-2596): Active, Deprecated(여전히 명세에 있음. 이전 경로가 필요함. deprecated로 지정한 리비전이 출시된 시점부터 최소 12개월의 기간), Removed. 가장 이른 제거 시점은 그 기간이 끝난 시점 이후에 출시되는 첫 리비전이고, 실제 제거는 코어 메인테이너의 결정입니다. deprecated된 기능은 이를 대체하는 SEP로 복원될 수 있습니다.
- SEP: `seps/` 폴더의 파일로 진행하는 PR 기반 워크플로(SEP-1850); 거버넌스(SEP-932); 워킹 그룹과 인터레스트 그룹(SEP-1302); Final SEP는 적합성(conformance) 테스트가 필요합니다(SEP-2484).
- SDK 등급(SEP-1730): Tier 1은 적합성 테스트 100% 통과, 명세 릴리스 전 기능 출시, 영업일 기준 2일 내 분류(triage), 7일 내 치명적 버그 수정. Tier 2는 80% 통과와 6개월 내 기능 출시. Tier 3은 실험 단계. 어느 등급도 확장 구현은 필수가 아닙니다. 실패가 4주 이어지면 SDK는 강등됩니다.
- 레지스트리(프리뷰): 패키지(npm, PyPI, Docker 등)나 원격 URL을 가리키는 메타데이터만 담습니다(`server.json`). 역방향 DNS 네임스페이스는 GitHub, DNS, HTTP 챌린지로 검증합니다(`io.github.user/server`, `com.example/server`). 공개 서버만 다룹니다(사설 서버는 OpenAPI 명세를 구현한 자기 레지스트리를 직접 운영). 호스트가 직접 소비하기보다 애그리게이터가 쓰도록 만들어졌고, 보안 스캐닝은 패키지 레지스트리와 애그리게이터에 위임됩니다. `server.json` 스키마 버전은 MCP 프로토콜 버전과 독립적입니다.
- 관리 주체: MCP는 Agentic AI Foundation(Linux Foundation)의 프로젝트입니다.
- 규모(MCP 블로그, 2026-07-28 릴리스 포스트): Tier 1 SDK를 합쳐 한 달에 거의 5억 건의 다운로드. TypeScript SDK와 Python SDK는 각각 누적 다운로드 10억을 넘었습니다.

## 16. 시험이 노릴 수 있는 함정

| 잘못된 믿음 | 올바른 2026-07-28 사실 |
|---|---|
| 연결이 `initialize`로 시작한다. | 핸드셰이크 없음. 모든 요청이 `_meta`에 버전과 캐퍼빌리티를 실으며, `server/discover`는 클라이언트에게는 선택이고 서버에게는 필수다. |
| 세션 id가 호출 사이의 상태를 보관한다. | 세션 없음. 서버가 발급한 핸들을 명시적 인자로 쓴다. |
| 모르는 도구는 `-32601`을 돌려준다. | `-32602`다. `-32601`은 메서드 자체를 모른다는 뜻이다. |
| 스키마에 맞지 않는 인자는 `-32602`를 돌려준다. | 도구 실행 오류다. 모델이 행동에 쓸 수 있는 피드백과 함께 `isError: true`다. |
| 서버가 클라이언트에 요청(sampling, elicitation)을 밀어 넣는다. | MRTR이다. `input_required` 결과를 주고, 클라이언트가 `inputResponses`와 새 id로 재시도한다. |
| 재시도가 원래 요청 id를 재사용한다. | 재시도는 반드시(MUST) 새 id를 쓰고 `requestState`를 정확히 되돌려 줘야 한다. |
| 리소스 감시는 `resources/subscribe`다. | `resourceSubscriptions`을 곁들인 `subscriptions/listen`이다. |
| 도구 어노테이션은 강제되는 보증이다. | 힌트일 뿐이며, 서버를 신뢰하지 않는 한 신뢰할 수 없다. |
| `cacheScope: "public"`이 데이터를 보호한다. | 사용자 간 공유를 허용하는 것일 뿐이며, 접근 제어는 별개다. |
| 진행 및 로그 알림은 listen 스트림으로 온다. | 자기 요청의 응답 스트림으로만 온다. |
| stdio 프로세스를 닫으면 요청이 취소된다. | stdio는 `notifications/cancelled`로 취소하고, HTTP는 그 요청의 스트림을 닫아 취소한다. |
| 새 서버는 커스텀 오류에 `-32001`을 써야 한다. | `-32000`~`-32019`는 레거시이고, `-32020`~`-32099`는 예약 영역이며, 앱 코드는 `-32768`~`-32000` 밖으로 나간다. |
| 리소스 없음은 `-32002`다. | 2026-07-28에서는 `-32602`다(오래된 서버의 `-32002`는 받아들인다). |
| roots, sampling, logging은 제거됐다. | deprecated일 뿐이며 여전히 동작하고, 2027-07-28 이후 출시되는 리비전부터 제거 대상이 될 수 있다. |
| 동적 클라이언트 등록이 권장 등록 방식이다. | deprecated다. 미리 등록한 다음에는 Client ID Metadata Documents가 선호된다. |
| 서버가 사용자 토큰을 업스트림으로 전달해도 된다. | 토큰 패스스루는 금지이며, 오디언스 검증은 필수다. |
| `clientInfo`가 인가 결정을 주도할 수 있다. | 스스로 보고한 값일 뿐이며, 표시와 로깅 전용이다. |
| 스트림은 `Last-Event-ID`로 재개할 수 있다. | 제거됐다. 스트림이 끊기면 요청도 잃으며, 새 id로 다시 보낸다. |

## 17. 작성 과정에서 해결된 출처 간 충돌

1차 문서들끼리 서로 다를 때는 규범적인 기록이 이깁니다. 메시지 형태는 `schema.ts`,
2026-07-28에 무엇이 존재하는지는 변경 로그와 현재 명세 페이지가 기준이며, 공개된 리비전을
제치고 과거의 SEP 초안을 따르는 일은 결코 없습니다. "미지정(unspecified)"으로 표시된 지점을
단일 규칙처럼 시험해서는 안 됩니다.

| 지점 | 문서들의 내용 | 해결 |
|---|---|---|
| `logging/setLevel`과 `notifications/roots/list_changed` | SEP-2577은 이 둘을 deprecated된 Logging과 Roots 기능 안에 나열함. 변경 로그 5번 항목과 SEP-2575는 두 메서드 모두 제거됐다고 말함 | 두 메서드는 2026-07-28에서 제거됐다. Roots, Sampling, Logging 기능 자체는 deprecated이며, 살아남은 표면은 MRTR 입력 요청으로서의 `roots/list`와 `sampling/createMessage`, 그리고 `notifications/message`와 함께하는 요청별 `logLevel`이다. |
| 임베디드 리소스의 어노테이션 | 도구 페이지 예제는 `annotations`을 `resource` 안에 중첩시킴. `schema.ts`는 `EmbeddedResource.annotations`을 `resource` 옆에 정의하고, `ResourceContents`에는 `annotations`이 없음 | `schema.ts`를 따른다. 어노테이션은 `resource` 옆에 위치한다. |
| 알림 POST의 헤더 | SEP-2243의 표는 알림에 대한 `Mcp-Method`를 나열함. 2026-07-28 Streamable HTTP 페이지는 알림 POST에 대한 헤더 요구 사항이 정의되지 않았다고 말하고, 코어 프로토콜은 HTTP 위의 클라이언트→서버 알림을 정의하지 않음 | 2026-07-28에서는 미지정. |
| 검증에 실패한 `requestState`의 거절 | MRTR은 서버가 반드시(MUST) 거절한다고 말하지만 채널을 이름으로 밝히지 않음 | 미지정. 도구 실행 오류든 새 `input_required` 결과든 둘 다 정당하다. |
| `-32700`, `-32600`, `-32603`의 HTTP 상태 | Streamable HTTP는 빠진 `_meta`, `-32020`, `-32021`, `-32022`에 대해 `400`을, `-32601`에 대해 `404`를 지정하지만 이 셋에 대해서는 아무 말도 없음 | 미지정. |
| 구독을 끝내는 서버 | 구독 페이지는 서버가 우아한 종료를 위해 listen 요청에 `complete` 결과로 답해야 한다고(SHOULD) 말함. 취소 페이지는 서버가 `notifications/cancelled`를 보내는 유일한 목적이 listen 스트림 해체라고 말함 | 둘 다 맞다. 우아한 종료는 `complete` 결과이고, listen 스트림 해체가 서버가 `notifications/cancelled`를 보낼 수 있는 유일한 목적이다. |
| 도구 이름 형식 | SEP-986은 다른 길이를 제안하고 `/`를 허용했음 | 공개된 도구 페이지가 이긴다. `A-Za-z0-9_-.`의 1~128자, `/` 없음. |
