# 위협-통제 매트릭스

MCPA '보안과 거버넌스' 도메인을 위한 한 페이지 참고 자료입니다. MCP 2026-07-28 기준입니다. 올바르게 인가된 스테이트리스 배포도 여전히 마주하는 열 가지 위협, 각각에 답하는 통제, 그리고 상세 메커니즘을 찾을 곳을 담습니다.

## 열 가지 위협

| 위협 | 어떤 모습인가 | 통제 | 찾을 곳 |
|---|---|---|---|
| 메타데이터 오염 | 도구 설명이나 어노테이션이 도구가 하는 일과 무관한 지시문을 끼워 넣음 | 설명과 어노테이션을 신뢰할 수 없는 것으로 취급. 등록 때와 모든 변경 때 스캔 | 이 레슨, `scan_for_injection` |
| 결과를 통한 프롬프트 인젝션 | 성공한 CallToolResult가 모델을 다른 방향으로 돌리려는 텍스트를 실어 옴 | 결과를 설명과 똑같이 신뢰할 수 없는 것으로 취급. 서버의 출력에 메타데이터보다 더 큰 신뢰를 주지 않음 | 보안 모범 사례, 도구 결과 |
| 러그 풀(rug pull) | 이전에 승인된 이름, 설명, 스키마, 어노테이션이 변경됨. 흔히 이름은 그대로 둔 채 | 전체 디스크립터를 해시로 고정. 어떤 변경이든 검역하고 재검토까지 보류. 이름 검사만으로 끝내지 않음 | 이 레슨, `RiskGateway.observe`와 `approve` |
| 도구 가려내기(shadowing) | 두 서버가 같은 한정되지 않은 도구 이름을 노출하고 탐색 순서가 조용히 하나를 고름 | 통합된 이름 앞에 안정적인 서버 식별자를 붙임. 충돌을 도착 순서로 해결하지 않음 | 레슨 06(호스트, 클라이언트, 서버), 레슨 09(매니페스트 검토) |
| 혼동된 대리자 | 프록시 서버가 속아서 자신의 위임된 권한을 공격자를 위해 씀 | 제3자 인가 서버로 중계하기 전 클라이언트별 동의. 정적 client id만 믿지 않음 | 인가 보안 고려 사항, Confused Deputy Problem |
| 토큰 전달(passthrough) | 핸들러가 클라이언트의 MCP 범위 bearer 토큰을 무관한 업스트림 API로 전달 | 토큰 audience 검증. 업스트림 범위의 별도 자격 증명 발행. 들어온 토큰을 전달하지 않음 | 이 레슨, `RiskGateway.call`의 업스트림 검사. 인가, 12절 |
| requestState 변조 | 클라이언트가 그대로 에코해야 하는 불투명한 MRTR 상태가 서버 동작을 바꾸도록 수정됨 | HMAC 또는 AEAD 무결성, 주체 바인딩, 짧은 만료, 원래 요청의 다이제스트, 서버 측 일회용 강제 | 레슨 14(MRTR), MRTR Security Considerations |
| SSRF (CIMD 가져오기, 네트워크 $ref) | 서버가 준 URL(Client ID Metadata Document나 스키마 $ref 등)이 맹목적으로 가져와짐 | 기본으로 네트워크 URI를 자동 역참조하지 않음. 허용 목록·사설 대역 차단·HTTPS·타임아웃 뒤의 옵트인 fetch | 이 레슨, `find_network_ref`. 보안 모범 사례, SSRF |
| DNS 리바인딩 | 호스트명이 검증 때는 안전한 주소로, 요청 때는 내부 주소로 풀림 | Origin 검증. Host 헤더를 믿는 대신 로컬 HTTP 서버를 루프백에 바인딩 | 레슨 19(전송과 HTTP 헤더), Streamable HTTP 보안 |
| 공급망 표류 | 레지스트리 목록, 패키지 버전, 실행 중인 엔드포인트가 승인 후 독립적으로 바뀜 | 네임스페이스를 인증된 소유자와 대조 검증. 다이제스트로 고정. 승인 후 살아있는 서버를 다시 관찰 | 레슨 30 (`phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift`) |

## 세 개의 거부 채널

| 상황 | 채널 | 예 |
|---|---|---|
| 요청 자체가 잘못된 형식 | JSON-RPC 프로토콜 오류 | 모르는 도구: `-32602` |
| 호출이 거부된 이유가 요청 모양이 아니라 정책 | `isError: true`를 담은 정상 결과 | 발동된 속도 제한, 러그 풀 이후 보류된 도구, 토큰 전달 시도 |
| 커스텀 애플리케이션 코드가 진짜로 필요함 | `-32768`부터 `-32000` 밖의 애플리케이션 정의 코드 | 거의 필요하지 않음. 먼저 `isError`를 택하는 것이 좋음 |

`-32000`부터 `-32019`(구버전 범위), `-32002`나 `-32042`(은퇴), 또는 `-32020`부터 `-32099` 안의 정의되지 않은 코드(명세 예약)를 절대 내보내지 않습니다. 모델이 읽어야 할 정책 거부는 `isError`에 들어가야지 지어낸 프로토콜 오류 코드에 들어가면 안 됩니다.

## 실무 체크리스트

- 모든 도구의 전체 디스크립터(이름, 설명, inputSchema, 어노테이션)를 승인 시점에 설명만이 아니라 해시로 고정한다.
- 모든 설명과 모든 결과가 모델에 닿기 전에 끼워 넣은 지시문을 스캔한다. 적중을 자동 판결이 아니라 검토 트리거로 취급한다.
- 통합된 도구 이름 앞에 안정적인 서버 식별자를 붙여 두 서버가 서로를 가릴 수 없게 한다.
- 모든 들어오는 토큰의 audience를 검증한다. 그대로 업스트림에 전달하지 않고, 업스트림 범위의 별도 자격 증명을 발행한다.
- `requestState`를 공격자가 조작한 입력으로 취급한다. 서명하거나 암호화하고, 주체·만료·요청 다이제스트에 묶고, 서버 측에서 일회용을 강제한다.
- 명시적인 허용 목록과 사설·링크 로컬 대역 차단 없이는 네트워크 URI(CIMD 가져오기, 스키마 `$ref`, 리디렉트 대상)를 자동 역참조하지 않는다.
- `Origin`을 검증하고 로컬 HTTP 서버를 루프백에 바인딩해 DNS 리바인딩을 막는다.
- 서버 자신의 오리진에서 온 `https:` 또는 `data:` 아이콘 URI만 받고, SVG는 실행 가능한 것으로 취급한다.
- 레지스트리 네임스페이스를 인증된 소유자와 대조 검증하고, 패키지와 원격 소스를 다이제스트로 고정하고, 승인 후 살아있는 서버를 다시 관찰한다.
- 모든 자동 거부는 올바른 채널로 보낸다. 잘못된 형식의 요청에는 `-32602`, 정책 거부에는 `isError: true`. `-32000`부터 `-32099` 사이의 지어낸 코드는 절대 없다.
