# MCP 도구 호출을 위한 위험·안전 통제

> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [en.md](en.md)

> 도구 설명은 모델이 우연히 보게 되는 문서가 아닙니다. 모델이 지시문으로 읽어 들이는 문자열입니다. 그래서 겉보기에 완전히 잠겨 있는 시스템을 공격하기에 가장 비용이 적게 드는 지점이 됩니다.

**유형:** 참고 자료
**언어:** Python
**선수 지식:** 레슨 25
**시간:** 약 45분

## 학습 목표

- 올바르게 인가되고 상태를 저장하지 않는(stateless) 2026-07-28 배포라도 여전히 노출하는 공격 표면을 꼽을 수 있습니다: 메타데이터 오염(metadata poisoning), 러그 풀(rug pull), 도구 섀도잉(tool shadowing), 혼동된 대리자(confused deputy), 토큰 전달(token passthrough), requestState 변조, SSRF, DNS 리바인딩, 악성 아이콘, 공급망 드리프트
- 도구 정의를 해시로 고정(핀)하고, 이전 승인 뒤에서 설명자(descriptor)가 나중에 바뀌는 순간을 탐지합니다
- 도구의 설명, 어노테이션, 결과를 "사람이 이미 검증한 문서"가 아니라 "모델이 지시문으로 읽는 신뢰할 수 없는 입력"으로 다룹니다
- 토큰 전달을 차단해서, MCP 서버 범위로 한정된 자격 증명이 무관한 업스트림 API까지 가지 않도록 합니다
- 호출이 거부된 이유가 형식이 잘못된 요청이 아니라 정책일 때는, 지어낸 프로토콜 오류 코드 대신 `isError` 도구 실행 결과를 선택합니다

## 문제 상황

어떤 지원 게이트웨이가 열두 개의 MCP 서버를 모아서, 하나의 어시스턴트가 티켓을 검색하고, 내부 문서를 읽고, 처리 완료된 케이스를 청구 시스템에 밀어 넣을 수 있게 해 준다고 합시다. 모델의 눈에 그 서버들은 전부 그저 텍스트일 뿐입니다: 이름, 설명, 스키마, 그리고 도구 호출이 우연히 돌려주는 내용. 프로토콜은 그 텍스트가 정직한지 묻지 않습니다. 메시지가 잘 구성되어 있는지만 묻고, 메시지는 도구가 무엇을 하는지에 대해 거짓말하면서도 완벽하게 잘 구성되어 있을 수 있습니다.

레슨 22는 신뢰 경계를 그렸고, 레슨 25는 파괴적인 호출이 실행되기 전에 사람에게 묻는 동의 게이트를 만들었습니다. 그러나 둘 중 어느 하나만으로는 일이 끝나지 않습니다. 동의 게이트는 사람이 실제로 보는 호출에만 관문을 세울 뿐, 모델이 어떤 호출을 할지 정하려고 이미 읽어 버린 설명이나, 아무도 하나하나 검토하지 않는 일상적이고 파괴적이지 않은 호출에는 아무런 역할도 하지 못합니다. 게이트웨이에는 아무도 지켜보지 않을 때에도 유지되는 통제, 그리고 문제가 확인 대화상자에 닿기도 전에 잡아내는 통제가 필요합니다.

## 핵심 개념

보안과 거버넌스는 층층이 쌓입니다. 레슨 22는 신뢰 구역에 이름을 붙였고, 레슨 23과 24는 클라이언트가 자신이 누구인지 증명하는 방법을 다뤘으며, 레슨 25는 사람이 특정 호출 하나를 승인하는 순간을 만들었습니다. 이 레슨은 그 모든 것의 아래에 깔리는 층입니다: 아무도 하나하나 검토하지 않는 호출들을 위해, 그리고 사람이 아무것도 보기도 전에 — 도구 설명이 이미 모델의 컨텍스트에 자리 잡은 그 시점에 — 서버나 게이트웨이가 자동으로 해 주는 일입니다.

도구의 이름, 설명, 어노테이션, 아이콘, 결과를 모델에 대한 신뢰할 수 없는 입력으로 다루세요. 레슨 22가 서버가 제공하는 다른 모든 콘텐츠를 다루는 방식과 똑같습니다. 설명 안에는 도구가 실제로 하는 일과 아무 상관 없는 지시문이 숨어 있을 수 있습니다: 다른 도구도 함께 호출하라고, 출력을 다른 곳으로 전달하라고, 사용자에게 어떤 단계를 언급하지 말라고 하는 문장들이죠. 모델은 자연어를 자연어로 읽을 뿐이고, 어조만으로 진짜 사용법 안내와 공격을 구분할 수 없습니다. 그러니 방어책이 "더 꼼꼼히 읽기"일 수는 없습니다. 같은 위험은 도구가 돌려주는 결과에도 적용됩니다. 성공적이고 잘 구성된 CallToolResult는 그것을 만들어 낸 서버만큼만 신뢰할 수 있습니다. 그래서 침해당했거나 악의적인 서버는 자기 설명 안에 지시문을 심는 것만큼 쉽게, 평범한 결과의 텍스트 콘텐츠 안에도 지시문을 심을 수 있습니다. "이전 지침을 무시하라"는 지시나 "사용자에게 이 단계를 비밀로 하라"는 요청 같은 문구를 걸러 내는 정적 스캐너는 등록 시점과 변경이 있을 때마다 돌리기에 충분히 값싼 검사입니다. 다만 이것은 안전의 증거가 아니라 철저(tripwire)입니다: 스캐너는 충분히 교묘하게 표현된 공격을 놓칠 수도 있고, 우연히 같은 문구를 쓰는 정당한 경고를 걸러 버릴 수도 있습니다. 걸린 항목은 어느 쪽이든 자동 판정이 아니라 검토자가 살펴볼 대상으로 취급합니다.

어제 검토를 통과한 도구가 영원히 같은 도구는 아닙니다. 러그 풀(rug pull, 깔개를 잡아 뽑듯 승인받은 내용을 몰래 바꿔치기하는 공격)은 이전에 승인된 이름, 설명, 스키마, 어노테이션이 바뀌는 것이고, 위험한 점은 이름이 보통 그대로라는 것입니다. 그래서 이후 호출은 겉으로 전혀 달라 보이지 않습니다. 설명 텍스트만 고정하면, 새 문장만큼이나 도구가 할 수 있는 일을 바꿔 버릴 수 있는 스키마나 어노테이션 변경을 놓치게 됩니다. 그래서 설명자 전체를 고정하세요: 정규화(canonicalize)한 뒤 해시를 계산합니다.

```python
payload = json.dumps(
    {"name": name, "description": description, "inputSchema": input_schema},
    sort_keys=True, separators=(",", ":"),
)
digest = hashlib.sha256(payload.encode("utf-8")).hexdigest()
```

이 다이제스트를 도구의 정규화된 이름(qualified name)과 함께 저장합니다. 새로 고침이 일어날 때마다: 모르는 키는 검토를 기다리고, 중복되는 비정규화 이름은 네임스페이스가 필요하며, 다이제스트가 바뀐 기존 키는 러그 풀입니다 — 도구를 격리하고 재검토를 위해 보류하고, 누군가 실제로 살펴본 후에야 새 다이제스트를 받아들입니다. 해시가 같다는 것은 안전이 아니라 변하지 않았다는 뜻일 뿐입니다. 오염된 설명자는 완벽하게 고정되어 있어도 여전히 오염된 상태입니다. 그래서 핀(pin)은 설명 스캔 위에 얹는 변경 탐지기일 뿐, 결코 그 대체물이 아닙니다.

두 서버가 서로의 존재를 모른 채 각각 문자 그대로 search라는 이름의 도구를 노출할 수 있습니다. 둘을 모아서 발견(discovery) 순서대로 조용히 한쪽을 고르게 두면, 그것이 도구 섀도잉(tool shadowing)입니다: 한 서버의 search로 향하던 호출이 다른 쪽으로 라우팅될 수 있고, 요청 어디에도 그 실수가 드러나지 않습니다. 레슨 06이 정확히 이 이유로 모아진 이름 앞에 서버 식별자를 붙였고, 레슨 09의 매니페스트 검토는 충돌 위험이 있는 비정규화 이름을 그 자체로 지적할 만한 발견 사항으로 다룹니다. 승인, 감사, 해시 핀, 라우팅은 모두 설명이나 서버가 스스로 보고하는 serverInfo가 아니라 정규화된 이름을 기준으로 해야 합니다.

클라이언트를 대신해 서드파티 API를 호출하는 MCP 서버는 그 자체가 OAuth 클라이언트이고, 그래서 대리자(deputy)입니다: 다른 이로부터 위임받은 권한으로 행동하는 존재죠. 혼동된 대리자(confused deputy) 공격은 그 대리자를 속여서 공격자를 위해 자기 권한을 쓰게 만듭니다. 가장 흔한 경로는 정적인 클라이언트 ID와, 이전의 정상적인 흐름에서 남은 동의 쿠키를 아직 들고 있는 브라우저입니다. 같은 실수의 일상적인 버전은 더 단순하고 더 흔합니다: 토큰 전달(token passthrough)은 핸들러가 클라이언트가 MCP 서버 자신에게 인증할 때 쓴 베어러 토큰을 그대로 꺼내서, 무관한 업스트림 API에 전달해 버리는 것입니다.

```json
{
  "http": {"headers": {"Authorization": "Bearer client-bearer-9f2c"}},
  "message": {
    "jsonrpc": "2.0", "id": 5, "method": "tools/call",
    "params": {
      "name": "sync_upstream_ticket",
      "arguments": {"ticket_id": "T-88", "upstream_credential": "client-bearer-9f2c"}
    }
  }
}
```

`arguments.upstream_credential`의 값은 인바운드 베어러 토큰과 똑같은 문자열입니다. 이것을 전달하는 핸들러는 MCP 서버 자신의 오디언스(audience, 토큰이 발급된 대상)에 대해서만 검증된 자격 증명을 업스트림 API에 건네준 셈입니다. 해법은 더 영리한 파싱이 아닙니다. 전달을 거부하고, 대신 업스트림 전용으로 별도 발급한(upstream-scoped) 자격 증명을 쓰는 것입니다. 인가 보안 고려사항이 요구하는 바로 그것입니다: 서버는 토큰이 자신의 오디언스에 대해 발급된 것인지 검증해야 하고, 클라이언트로부터 받은 토큰을 업스트림 호출에 그대로 통과시켜서는 절대 안 됩니다.

레슨 14에서 다중 왕복 요청(MRTR, Multi Round-Trip Requests)을 자세히 다루지만, 그 레슨의 `requestState` 필드는 이 레슨의 위협 목록에도 올라야 합니다. 서버를 떠나는 순간부터는 공격자가 통제할 수 있는 값이기 때문입니다. 클라이언트가 그것을 그대로 돌려준다고 믿어서는 안 됩니다. `requestState`가 인가 결정, 리소스 접근, 비즈니스 로직에 영향을 주는 일이 있다면 서명하거나 암호화하고, 인증된 주체(principal), 짧은 만료 시간, 그것이 속한 요청의 다이제스트에 묶어 두고, 클라이언트가 착실하게 행동하기를 바라는 대신 서버에서 일회성 사용을 강제하세요.

MCP의 여러 표면은 클라이언트, 서버, 인가 서버에게 남이 제공한 URL을 가져오도록 요청합니다. 그 URL을 무작정 따라가면 각각이 서버 사이드 요청 위조(SSRF, Server-Side Request Forgery) 기회가 됩니다: 인가 서버가 Client ID Metadata Document를 가져오는 경우, 클라이언트가 `WWW-Authenticate` 챌린지의 `resource_metadata` URL을 따라가는 경우, 검증기가 도구의 inputSchema 안의 `$ref`를 풀어보는 경우가 그렇습니다. 규칙은 모든 경우에 같습니다: 네트워크 URI를 기본으로 자동 참조 해제하지 않는다. 가져오는 것이 정말 필요하다면 명시적인 옵트인 동작으로, 프라이빗/링크 로컬 주소 대역을 차단하고 HTTPS를 강제하며 타임아웃을 적용하는 허용 목록(allowlist) 뒤에서만 하세요. 검증 시점에 평범해 보이던 URL도 요청이 실제로 실행되는 시점에는 내부 주소로 해석될 수 있기 때문입니다. DNS 리바인딩은 같은 빈틈을 로컬 HTTP 서버에 적용한 것입니다: 어떤 호스트명이 처음에는 안전한 주소로 풀리다가 다음 조회에서는 루프백이나 내부 주소로 풀리는 것이죠. 그래서 레슨 19의 Origin 검증과 localhost 바인딩이 존재합니다. 아이콘은 같은 위험을 이미지 형태로 더 작게 품고 있습니다: `https:`나 `data:` URI만 받고, 아이콘을 선언한 서버와 같은 오리진을 요구하며, SVG는 그림이 아니라 실행 가능한 콘텐츠로 다루세요. SVG는 스크립트를 담을 수 있습니다.

공급망 위험은 이 모든 것보다 앞서 나타납니다. 레지스트리 목록 항목, 패키지 버전, 실제로 요청에 응답하는 엔드포인트는 서로 다른 세 권위에서 나온 서로 다른 세 사실이며, 레지스트리에 있다는 것을 자동적인 신뢰로 취급하면 셋이 하나로 뭉개집니다. 네임스페이스는 단순 문자열 비교가 아니라 인증된 소유자와 대조해 검증해야 합니다. 접두사 검사만으로는 닮은꼴 가짜 네임스페이스를 진짜만큼 쉽게 받아들입니다. 패키지나 원격 소스는 다이제스트로 고정해야 합니다. 떠다니는(floating) 버전 태그는 검토 때 가리키던 바이트와 내일은 다른 바이트를 가리킬 수 있기 때문입니다. 또한 승인된 뒤에도 실행 중인 서버를 계속 관찰해야 합니다. 검토를 통과한 서버도 나중에 도구를 추가할 수 있고, 그것은 이름만 다른 공급망 러그 풀입니다. 이 검사들 중 어떤 것도 다른 것을 대신하지 못합니다.

정책 엔진이 거부를 표현할 수 있는 통로는 정확히 세 개이고, 잘못된 통로를 집는 것 자체가 이름 붙일 가치가 있을 만큼 흔한 실수입니다. 서버가 등록한 적 없는 도구 이름을 부르는 것처럼 형식이 잘못된 요청은 JSON-RPC 프로토콜 오류입니다: 코드 `-32602`, 레슨 02가 알려지지 않은 도구에 썼던 바로 그 통로죠. 반면 모델이 읽고 경우에 따라 대응해야 할 거부 — 호출 한도(rate limit)가 걸렸거나 러그 풀로 도구가 보류된 경우 — 는 `isError: true`와 내용에 설명을 담은 정상 결과에 들어가야 합니다. JSON-RPC 오류도, 지어낸 코드도 절대 아닙니다. 유혹은 `-32001` 같은 코드를 집는 것입니다. 레거시용 `-32000`부터 `-32019` 블록이 사용자 지정 거부 코드를 위한 빈 공간처럼 보이니까요. 아닙니다: 그 블록은 레거시 구현만을 위해 존재하고, `-32020`부터 `-32099`는 사양 자체를 위해 예약되어 있으며, 애플리케이션 정의 코드가 정말 필요하다면 `-32768`부터 `-32000` 범위 밖, 완전히 바깥에 있어야 합니다. 대부분의 정책 거부는 그런 코드가 필요 없습니다. `isError`가 이미 모델이 읽고, 사용자에게 설명하고, 때로는 바로잡을 수 있는 통로를 주고 있기 때문입니다.

이 통제들 중 어느 것도 작동하는 데 사람의 개입이 필요하지 않습니다. 그것이 요점입니다. 신뢰할 수 없는 입력을 읽고, 민감한 데이터를 만지고, 결과가 큰 행동을 한 번에 다 하는 단일 자동 단계 — 이 목록의 모든 위협이 닿으려 하는 바로 그 형태입니다. 그 단계를 쪼개는 것, 즉 설명자가 조용히 바뀌기 전에 고정하고, 설명이 모델에 닿기 전에 스캔하고, 자격 증명이 서버를 떠나기 전에 오디언스를 검증하고, 네트워크 참조를 가져오기도 전에 거부하는 것이, 한 번 놓친 검토가 사고로 번지지 않게 막아 줍니다. 호출 한도, 타임아웃, 권한을 낮춘 샌드박스 프로세스에서 도구 핸들러를 실행하는 것은 한층 더 둔합니다: 어느 것도 공격이 어떻게 생겼는지 이해하지 못하지만, 그것이 바로 이들의 가치입니다. 더 영리한 검사들이 상류에서 뭔가를 놓쳤을 때에도 피해의 상한을 정해 주기 때문입니다.

## 인터랙티브 랩

그림은 중앙의 게이트웨이 노드 주위에 여덟 개의 위협을 배치합니다: 꼭대기 근처에 오염된 설명과 러그 풀, 오른쪽에 도구 섀도잉과 토큰 전달, 아래쪽에 requestState 변조와 네트워크 `$ref`, 왼쪽에 DNS 리바인딩과 공급망 드리프트. 다이어그램의 어느 것도 기발하지 않습니다. 모든 축(spoke)은 같은 아이디어의 변형입니다 — 서버, 레지스트리, 클라이언트가 공급한 무언가를 게이트웨이가 신뢰하는 대신 검증하기로 선택한 것. 중앙에는 여덟 개 모두에 답하는 세 가지 동작이 적혀 있습니다: 설명자를 고정해서 나중의 변경이 보이게 하기, 설명이 모델에 닿기 전에 스캔하기, 그리고 모든 개별 호출이 각자는 정당해 보여도 단일 호출자나 단일 도구가 할 수 있는 일을 제한하기.

## 실습 랩

`code/main.py`를 열어 보세요. 이 코드는 두 도구 `search_helpdesk`와 `sync_upstream_ticket`을 앞세운 `RiskGateway`를 만들고, 스키마가 네트워크 `$ref`를 참조하는 세 번째 도구와 설명에 주입된 지시문을 담은 네 번째 도구를 등록합니다.

```bash
python3 code/main.py
```

인쇄된 실행 기록을 개념 섹션과 대조하며 읽어 보세요. `bulk_import`의 등록 줄은 `accepted=False`를 보여 줍니다: 네트워크 `$ref` 때문에 도구가 카탈로그에 닿기도 전에 거부됩니다. `draft_reply_wizard`의 등록 줄은 `accepted=True`와 함께 걸린 문구를 지목하는 이유를 보여 줍니다: 오염된 도구도 기록은 되지만 그 자리에서 격리됩니다. 요청 로그에서 첫 번째 `search_helpdesk` 호출은 성공하고, 이어서 `gateway.observe()`가 스키마가 바뀐 설명자 새로 고침을 시뮬레이션하면, 같은 도구에 대한 바로 다음 호출이 `isError: true`로 돌아옵니다 — 도구 이름은 끝까지 바뀌지 않았는데도 러그 풀로 검토 보류된 것이죠. `gateway.approve()`가 보류를 풀고 해시를 다시 고정하면 그다음 호출은 다시 성공합니다. `sync_upstream_ticket`이 두 번 호출되는 것을 지켜 보세요: 한 번은 `upstream_credential`이 클라이언트가 인증에 쓴 것과 같은 토큰으로 설정되어 토큰 전달로 거부되고, 또 한 번은 별개의 업스트림 전용 자격 증명으로 성공합니다. 마지막 `search_helpdesk` 호출들은 설정된 `rate_limit` 4를 넘기고, 다섯 번째가 될 호출은 조용히 대기열에 쌓이거나 죽지 않고 실행 오류로 돌아옵니다. 그다음에는 `SUSPICIOUS_PHRASES`에 문구를 하나 추가하고, 그것을 설명에 담은 새 도구를 등록해서, 아무도 호출하기도 전에 등록되는 순간 격리되는지 확인해 보세요.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 메타데이터 오염(Metadata poisoning) | 도구의 이름, 설명, 어노테이션에 심어진, 도구가 실제로 하는 일과 아무 상관 없는 지시문 |
| 러그 풀(Rug pull) | 이전에 승인된 도구 설명자의 변경. 흔히 도구 이름은 그대로 둔 채 일어난다 |
| 정의 고정(Definition pinning) | 승인 시점에 도구 설명자 전체를 해싱해서 나중 변경을 탐지할 수 있게 하는 것 |
| 도구 섀도잉(Tool shadowing) | 두 서버가 같은 비정규화 도구 이름을 노출해 발견 순서가 조용히 한쪽을 고르게 되는 것 |
| 혼동된 대리자(Confused deputy) | 위임받은 자기 권한을 공격자를 위해 쓰도록 속임을 당한 중개자 |
| 토큰 전달(Token passthrough) | 클라이언트의 MCP 서버 범위 베어러 토큰을 무관한 업스트림 API로 전달하는 것 |
| requestState 변조(requestState tampering) | 클라이언트가 그대로 되돌려 보내야 할 불투명한 MRTR 상태를 변경하는 것 |
| SSRF | 서버 사이드 요청 위조: 내부 또는 의도치 않은 URL을 가져오도록 부추기는 것 |
| DNS 리바인딩(DNS rebinding) | 호스트명이 검증 중에는 안전한 주소로, 요청 시점에는 내부 주소로 풀리는 것 |
| 공급망 드리프트(Supply chain drift) | 레지스트리 목록 항목, 패키지, 실행 중인 엔드포인트가 승인 후 각자 따로 바뀌는 것 |
