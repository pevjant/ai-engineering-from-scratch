# 동의와 최소 권한

> 세상에 무언가를 바꾸는 도구 호출은, 모델이 호출하기로 결정했다는 이유만으로 돌아가서는 안 됩니다. 사람이 바로 그 특정 호출에 예스라고 말했기 때문에 돌아가야 하고, 클라이언트는 그 호출이 실제로 필요로 하는 것보다 더 많은 접근 권한을 쥐고 있어서도 안 됩니다.

**유형:** 참조(Reference)
**언어:** Python
**선수 지식:** 레슨 24
**시간:** 약 45분

## 학습 목표

- MCP에 승인을 위한 서버에서 클라이언트로의 푸시가 없는 이유와, 다중 왕복 요청(MRTR) 일러시테이션(elicitation)이 대신 동의 질문을 어떻게 실어 나르는지 설명합니다
- 도구별 동의 범위 설정과 무차별적인 '이 서버를 신뢰함' 부여를 구별하고, 도구의 어노테이션이 그 판단에 정보를 주면서도 집행을 허락받지는 못하는 이유를 설명합니다
- HTTP 403 `insufficient_scope` 챌린지를 읽고, 클라이언트가 다음에 청해야 할 스코프를 계산합니다. 이미 갖고 있던 것과 챌린지가 요구하는 것의 합집합입니다
- 스텝업(step-up) 인가 반복에 재시도 상한을 적용해, 필요한 스코프에 이를 길이 없는 클라이언트가 영원히 재시도하는 대신 크게 실패하게 만듭니다
- `tools/list` 같은 결과가 호출자의 부여된 스코프에 따라 달라지면서도, 같은 호출자의 같은 요청에 대해서는 두 번 다르지 않을 수 있는 이유를 설명합니다

## 문제 상황

도구 접근을 가진 에이전트는 사람이 쉽게 되돌릴 수 없는 일을 할 수 있습니다. 파일을 지우고, 결제를 보내고, 고객에게 메시지를 보내고, 계정을 철회합니다. 그런 일을 하는 도구는 클라이언트가 쓰지 않은 서버 위에서, 언제 부를지 고르는 모델에 의해 움직입니다. 두 설계 모두 실패합니다. 서버가 연결되는 순간 모든 호출을 미리 승인된 것으로 다루면, 무성의하거나 침해당한 서버 하나가 사람이 뭘 하려는지 들여다볼 지점 하나 없이 사용자의 전체 권한으로 움직일 수 있습니다. 반대로 데이터만 읽는 호출까지 전부 새 프롬프트가 필요한 것으로 다루면, 프롬프트는 사용자가 읽지도 않고 클릭해 치우는 소음이 됩니다. 그것은 동의가 아니라, 동의의 가면을 쓴 피로입니다.

MCP에서 이것을 제대로 하는 일은 정책 하나 고르는 일보다 어렵습니다. 프로토콜이 기댈 지름길을 주지 않기 때문입니다. 2026-07-28 개정판에는 세션도 서버가 먼저 시작하는 푸시도 없습니다. 서버가 호출 도중에 클라이언트를 가로채 질문하는 식 — 오래된 연결 지향 프로토콜이 그랬던 것처럼 — 이 불가능합니다. 그리고 사람의 게이트 밑에 혼동하기 쉬운 두 번째 게이트가 있습니다. 누군가 무언가를 승인하기로 청해지기도 전에, 클라이언트 자신의 접근 토큰이 그 작업을 시도할 만큼의 OAuth 스코프를 아예 실고 있어야 합니다. 동의는 '이 특정 행동이 일어나야 하는가'에 답합니다. 스코프는 '이 클라이언트가 애초에 그런 행동을 시도할 자격이라도 있는가'에 답합니다. 둘 중 하나만 다루는 레슨은 보안과 거버넌스 도메인의 절반을 다루지 않은 채 남겨 둡니다.

## 개념

### 세션 없이 묻기: MRTR 위의 일러시테이션

도구는 모델이 통제합니다. 언제 부를지는 모델이 결정합니다. 명세는 특정 상호작용 모델을 의무화하지 않지만, 언제나 호출을 거부할 능력을 가진 사람이 루프 안에 있어야 하고, 애플리케이션은 어떤 도구가 노출됐는지 보여 주고, 도구가 실행될 때 표시하며, 민감한 작업이 일어나기 전에 확인해야 한다는 점은 명확히 말합니다. 서버 푸시가 없으므로 그 확인은 서버에 더 많은 정보가 필요한 모든 사례가 쓰는 같은 메커니즘, 즉 다중 왕복 요청(Multi Round-Trip Request)으로 이동합니다. 서버는 `tools/call`에 결과 대신 `resultType: "input_required"`로 답합니다. `elicitation/create` 요청들을 항목으로 하는 `inputRequests` 맵과, (답이 같은 호출로 돌아와야 할 때) `requestState` 문자열입니다. 클라이언트는 답을 모아서, 완전히 새로운 JSON-RPC id로 정확히 같은 작업을 재시도합니다. 답은 서버가 이름 댄 것과 같은 방식으로 키잉된 `inputResponses` 아래에, `requestState`는 바이트 단위로 그대로 되돌려 실립니다.

```json
{
  "jsonrpc": "2.0",
  "id": 4,
  "result": {
    "resultType": "input_required",
    "inputRequests": {
      "confirm": {
        "method": "elicitation/create",
        "params": {
          "mode": "form",
          "message": "Allow delete_file to run with arguments {\"path\": \"notes.txt\"}?",
          "requestedSchema": {
            "type": "object",
            "properties": {"approved": {"type": "boolean", "title": "Approve this call"}},
            "required": ["approved"]
          }
        }
      }
    },
    "requestState": "eyJ0b29sIjogImRlbGV0ZV9maWxlIn0.9f2c..."
  }
}
```

사용자의 답은 세 가지 행동 중 하나로 돌아오며, 맨얼굴의 예스/노는 아닙니다. `accept`(폼 모드의 경우 요청된 스키마에 맞는 `content`와 함께), `decline`(사용자가 명시적으로 아니라고 말함), `cancel`(사용자가 결정하지 않은 채 자리를 떠남). 셋 모두 호출의 실행을 막지만, 동의인 것은 `accept`뿐입니다. `cancel`을 `decline`으로 다루거나, 둘 중 하나를 조용히 재시도할 것으로 다루는 클라이언트는 사용자의 마음을 추측하고 있는 것입니다. 이 모든 것은 프로토콜 오류가 아닙니다. 동의가 거부됐다는 이유로 도구 실행을 사양하는 서버는 모든 비즈니스 거절을 보고하듯 그렇게 보고합니다. 모델이 읽을 수 있는 텍스트를 실은 `isError: true`의 정상적인 `tools/call` 결과이지, JSON-RPC 오류도 새로 지어낸 코드도 결코 아닙니다. 2026-07-28 오류 표 어디에도 '동의 필요' 자리는 없고, 있어서도 안 됩니다.

`requestState`는 신뢰 경계를 넘어 나중에 되돌아오는 어떤 값에든 주어야 할 바로 그 의심을 받을 만합니다. 서버를 떠나는 순간 공격자가 통제할 수 있는 입력이기 때문입니다. 그것이 무엇이 실행되는지에 영향을 주도록 허용된다면, 서명하고(대부분의 서버에는 HMAC이나 AEAD로 충분합니다), 발급된 특정 호출에 묶고, 한 번 쓰면 소모하십시오. 어떤 재시도가 한 호출의 `requestState`를 내밀면서 다른 인자 집합의 실행을 청한다면, 그것은 합법적인 재시도가 아니라 사람이 확인한 뒤에 바뀐 요청입니다. 그것을 걸러내야 하는 것은 회선 형식이 아니라 서버 자신의 서명 검사입니다.

### 동의를 서버 하나가 아니라 도구 하나에 묶기

사용자가 부여하는 동의는 정확히 그것이 부여된 도구에 범위가 한정돼야 합니다. `delete_file`을 승인하는 것이 `send_payment`를 승인하는 것은 아닙니다. 같은 서버에서도, 같은 대화에서도, 잠시 후에도 아닙니다. '이 서버를 신뢰함' 부여는 도구를 하나하나 이름 대는 발상의 전부를 무너뜨립니다. 하나의 구체적이고 정보에 입각한 결정을, 사용자가 실제로 한 적 없는 무차별적 결정으로 바꿔 버립니다. 여기서 도구의 `annotations`이 제 값을 하면서 동시에 한계를 바로 드러냅니다. `readOnlyHint`, `destructiveHint`, `openWorldHint`는 클라이언트가 프롬프트가 언제 손볼 일인지 판단하는 데 필요한 바로 그 신호입니다. 데이터만 읽는 호출은 보통 프롬프트 없이 진행될 수 있고, 쓰거나, 지우거나, 보내거나, 열린 세상으로 손을 뻗는 호출은 보통 그래서는 안 됩니다. 그러나 어노테이션은 서버가 자기 자신에 대해 설정하는 힌트이고, 명세는 그 서버 자체가 신뢰되지 않는 한 클라이언트가 이를 신뢰할 수 없는 것으로 다뤄야 한다고 분명히 말합니다. 읽기 전용이라고 거짓말하는 도구가 `annotations`이 그렇다고 말한다고 해서 안전해지지는 않습니다. 클라이언트가 어노테이션 위에 어떤 정책을 세우든, 실제 집행 — 사람이 실제로 어떤 이름의 도구를 승인했는지의 기록 — 은 클라이언트 안에 살아야 하지, 서버가 자기 도구에 대해 주장하는 무엇 안에 살아서는 안 됩니다. 기본값이 함축하는 바도 짚고 넘어가십시오. `destructiveHint`와 `openWorldHint`는 둘 다 true가 기본이고, `readOnlyHint`는 false가 기본입니다. 어노테이션을 아예 실지 않고 나온 도구는 기본적으로 안전한 것이 아니라 파괴적이고 개방된 세상의 도구로 다뤄집니다. 프로토콜은 서버가 아무 말도 하지 않을 때 일부러 보수적으로 움직입니다.

### 스텝업 인가: 다른 게이트, 한 단계 아래

동의에 도달하기도 전에 호출이 완전히 다른 이유로 실패할 수 있습니다. 그것을 받쳐 주는 토큰이 충분한 스코프를 실지 않았기 때문입니다. 이것은 전송 계층의 일이고 OAuth가 다스리며, 동의와는 다른 질문에 답합니다. 스코프가 불충분한 요청이 도착하면, 서버는 `403 Forbidden`과 `WWW-Authenticate` 헤더로 답하는데, 작업에 필요한 모든 스코프를 하나의 챌린지에 이름 대 줍니다. 여러 왕복에 걸쳐 하나씩 내주는 방식이 아닙니다:

```http
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope",
                         scope="payments:write",
                         resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource"
```

클라이언트의 응답은 이미 갖고 있던 스코프와 이 챌린지의 스코프의 합집합을 계산하는 것이지, 한 집합을 다른 집합으로 바꾸는 것이 결코 아닙니다. 작업별로 챌린지를 던지는 서버 때문에 클라이언트가 앞서 벌어 둔 스코프를 잃어버려서는 안 됩니다. 클라이언트는 그 합집합을 위해 다시 인가하고 재시도합니다. 이것은 초기 스코프를 고르는 흐름과는 다릅니다. 클라이언트가 처음으로 인가하는 중이고 초기 `401`이 `scope` 파라미터를 아예 실지 않았다면, 서버가 정의해 온 모든 것을 청하는 대신, 서버의 보호 리소스 메타데이터에서 `scopes_supported`를 최소 출발 집합으로 물러섭니다. 두 규칙은 같은 이유로 존재합니다. 필요할 때 필요한 것만 청하고, 여러 왕복에 걸쳐 권한을 조금씩 새어 내는 대신 한 번의 깔끔한 점프로 스텝업하십시오. 스텝업 반복에는 한계도 필요합니다. 클라이언트는 재인가를 작고 유한한 횟수만 재시도해야 하고, 그 상한을 넘기면 영원히 받지 못할 스코프를 향해 반복하는 대신 그 작업을 영구적인 인가 실패로 다뤄야 합니다.

### 서버가 자기 소유를 밝히는 것에서의 최소 권한

스테이트리스함은 `tools/list`가 다른 요청의 부수 효과로 변하는 일이 결코 없어야 하고, 같은 인가 아래 같은 호출자에게는 매번 같은 도구를 돌려줘야 한다는 뜻입니다. 그러나 두 다른 호출자 사이에서는 명시적으로 달라도 됩니다. 요청 위의 스코프는 연결 상태가 아니라 입력의 일부이기 때문입니다. 모든 도구를 누구에게나 보여 주기만 하다가, 호출자가 실제로 호출을 시도할 때 그 호출을 거절하는 서버는, 호출자가 볼 생각이 없었던 커패시티의 존재와 형태를 새어 내보이고, 실패할 것이 분명한 호출을 시도하도록 모델을 훈련시키는 셈입니다. 최소 권한의 움직임은 실제로 제시된 스코프로 `tools/list`를 걸러 내는 것이고, 그 결과를 `"public"`이 아니라 `cacheScope: "private"`로 표시하는 것입니다. 캐시된 공개 사본은 한 사용자의 도구 표면을 다른 사용자에게 새기 때문입니다.

```figure
mcpa-25-consent-gates
```

## 인터랙티브 랩

이 그림은 하나의 `tools/call`이 무언가를 하기 전에 만날 수 있는 두 게이트를 모두 거치며 따라갑니다. 먼저 인가 경계를 넘습니다. 토큰의 스코프가 불충분하면 서버는 `403`과 필요한 스코프로 튕겨내고, 클라이언트는 그 스코프를 이미 갖고 있던 것과 합집합하여 다시 시도합니다. 인가가 통과한 뒤에야 호출은 동의 게이트에 닿습니다. 도구가 사람의 판단을 필요로 하고 그 정확한 도구에 대한 기록이 없다면, 서버는 아무것도 실행하는 대신 `input_required`로 답하고, 클라이언트는 재시도하기 전에 `elicitation/create` 왕복으로 그것을 해소합니다. 두 게이트는 독립적이고 순서가 있다는 점에 주목하세요. 완전히 인가된 클라이언트도 여전히 동의를 청해질 수 있고, 동의 문제가 전혀 없는 클라이언트도 여전히 스코프가 부족할 수 있습니다. 도구는 두 게이트 중 하나 뒤에, 둘 다 뒤에, 또는 어느 쪽 뒤에도 앉아 있을 수 있습니다.

## 실습 랩

`code/main.py`를 열어 보세요. 이 코드는 네 개의 도구를 가진 서버 하나를 만듭니다. `list_files`(읽기 전용, 닫힌 세계, 즉시 실행), `search_web`(읽기 전용이지만 개방된 세계이며, openWorldHint가 true이므로 여전히 동의 게이트를 거침), `delete_file`(파괴적, 동의 게이트, 작은 메모리 내 파일시스템이 받쳐 주어 decline이 파일을 그대로 두는 것을 눈으로 볼 수 있음), 그리고 `send_payment`(파괴적이고 `payments:write` 스코프의 게이트를 받아, 두 게이트를 한꺼번에 시험합니다).

```bash
python3 code/main.py
```

전사를 위의 안내와 겨뎌 읽어 보세요. `delete_file`의 `input_required` 결과, `notes.txt`를 그대로 두는 `decline`, 그 뒤에 이어지는 새 일러시테이션(decline에 대한 동의는 기억되지 않습니다), 그리고 마침내 삭제에 성공하는 받아들여진 재시도를 찾아 보세요. 그다음 일부러 틀린 항목을 찾아 보세요. 유효한 `requestState`를 그대로 되돌리면서, 사용자에게 보여졌던 파일이 아닌 다른 파일의 삭제를 청하는 재시도입니다. 전사에서 `violation`으로 표시되어 있는데, 서버의 서명 검사가 재시도를 믿는 대신 불일치를 걸러내기 때문입니다. 별도로 `send_payment`가 스코프 챌린지로 튕겨 나오고, 클라이언트가 `payments:read`와 챌린지된 `payments:write`의 합집합을 계산하고, 그제서야 자기만의 독립적인 동의 프롬프트에 닿는 것을 지켜 보세요. 마지막으로 `payments:read`만 있을 때 `tools/list`가 돌려주는 것과, `payments:write`까지 부여된 뒤 돌려주는 것을 겨뎨 보세요.

## 캡스톤 연계

캡스톤 시스템의 부수 효과를 내는 모든 도구는 자기 이름에 한정된 동의 결정이 필요합니다. 형제 도구로부터 물려받는 것도, 서버 자신이 제공한 어노테이션에서 가정하는 것도 결코 아닙니다. 스코프 게이트를 받는 모든 도구는 교체가 아니라 합집합으로 동작하는 스텝업 경로와, 얼마나 계속 시도할지의 한계가 필요합니다. 캡스톤이 호출자가 볼 수 있고 할 수 있는 것의 근거를 대라고 물으면, 이 레슨의 두 게이트에서 답하십시오. 사람이 명시적으로 승인한 것, 그리고 손에 쥔 토큰이 실제로 인가하는 것. 그리고 주어진 실패가 둘 중 어느 쪽에 속하는지 말할 준비를 해 두십시오.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 일러시테이션(elicitation) | 사용자 입력을 위한 서버의 MRTR 요청. `inputRequests` 안의 `elicitation/create` 항목으로 전달됨 |
| requestState | 재시도가 바이트 단위로 그대로 되돌려야 하는, 서버가 발행한 불투명한 문자열. 신뢰할 수 없는 입력으로 다루며, 중요한 경우 서명하고 한 번만 씀 |
| 도구별 동의 범위 설정 | 하나의 이름 대어진 도구에 기록되는 승인. 서버, 범주, 이름 패턴에 대해서는 결코 기록되지 않음 |
| 어노테이션 힌트 | `destructiveHint` 같은 서버 선언 속성. 클라이언트의 프롬프트 정책에 정보를 주지만, 집행 보장으로는 결코 신뢰되지 않음 |
| 스텝업 인가 | `403 insufficient_scope` 응답 뒤에, 이전에 갖고 있던 스코프와 새로 챌린지된 OAuth 스코프의 합집합을 위해 다시 인가하는 것 |
| 스코프 합집합 | 클라이언트의 이전 스코프와 챌린지의 필요 스코프의 결합. 재인가가 이전 부여를 잃어버리지 않게 함 |
| 목록 결과의 최소 권한 | 호출자의 현재 인가가 허용하는 것만으로 걸러진 `tools/list`(또는 유사) 결과. `cacheScope: "private"`로 캐시됨 |
