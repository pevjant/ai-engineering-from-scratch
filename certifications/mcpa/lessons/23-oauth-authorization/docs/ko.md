# MCP 서버 접근 권한 부여(인가)

> 베어러 토큰이 증명하는 것은 클라이언트가 이 서버에 자격 증명을 발급받았다는 것뿐, 서버가 토큰 소유자가 청하는 모든 것을 믿어야 한다는 뜻이 아닙니다. 그래서 프로토콜은 클라이언트에게 매번, 단 한 번의 예외도 없이 토큰을 증명하고, 오디언스(audience)를 증명하고, 발급자(issuer)를 증명하게 합니다.

**유형:** 참조(Reference)
**언어:** Python
**선수 지식:** 레슨 22
**시간:** 약 45분

## 학습 목표

- MCP 서버가 OAuth 2.1 리소스 서버 역할을 하고, MCP 클라이언트가 OAuth 클라이언트 역할을 하며, 별도의 인가 서버가 토큰을 발급하는 이유와, stdio 서버에게 이 흐름을 아예 건너뛰라고 말하는 이유를 설명합니다
- 401 응답의 `WWW-Authenticate` 헤더에서 시작해, 헤더가 침묵할 때 클라이언트가 쓰는 잘 알려진(well-known) URL 대안 순서까지, 보호 리소스 메타데이터(Protected Resource Metadata) 디스커버리의 흐름을 따라갑니다
- 경로를 가진 발급자(path-scoped issuer)와 루트 발급자에 대한 인가 서버 메타데이터 디스커버리를 따라가고, 돌아온 `issuer` 값이 요청을 만들 때 쓴 것과 일치해야 하는 이유를 설명합니다
- 표준 라이브러리만으로 코드 검증자(code verifier)에서 PKCE S256 코드 챌린지를 만들고, 인가 서버가 `code_challenge_methods_supported`를 광고하지 않을 때 클라이언트가 진행을 거부해야 하는 이유를 설명합니다
- RFC 8707의 `resource` 파라미터를 적용해 토큰 요청을 하나의 정규화된(canonical) 서버 URI에 묶고, 들어오는 토큰의 오디언스를 그 같은 URI와 겨뎌 검증합니다
- RFC 9207의 네 행 `iss` 검증 표를 적용해 믹스업(mix-up) 공격을 방어하고, MCP 서버의 인가 응답에서 401, 403, 400을 구별합니다

## 문제 상황

이 트랙이 지금까지 다룬 대부분은 요청이 형태만 갖춰지면 적법하다고 가정했습니다. 올바른 `_meta`, 알려진 도구, 유효한 인자. 그 가정은 MCP 서버가 지킬 가치가 있는 것 — 고객 기록 데이터베이스, 키 교체 도구, 청구 시스템 — 을 손에 넣는 순간 깨집니다. 그런 프리미티브를 노출하는 서버는 모든 문법적으로 유효한 `tools/call`을 통과시킬 수 없습니다. 호출자가 되돌릴 수 없는 무엇을 하기 전에, 누가 묻는지, 누구의 권한으로인지, 무엇을 위해서인지 알아야 합니다.

MCP의 인가(authorization)는 프로토콜 수준에서는 선택입니다. 로컬 stdio 서버에는 필요가 없습니다. 프로세스 경계와 사용자 자신의 환경이 이미 신뢰를 세워 주기 때문이고, 그 자리의 구현체는 OAuth 흐름을 아예 돌리지 말아야 하며(SHOULD NOT) 대신 환경에서 자격 증명을 읽습니다. 그러나 서버가 원격의 HTTP 기반 배포로 옮겨가는 순간 그 경계는 사라지고, 명세는 HTTP 구현체가 이 레슨이 다루는 인가 흐름에 부합하라고 말합니다(SHOULD). 어려운 부분은 암호화도 전송도 아닙니다. 둘 다 이미 이 계층 아래에서 처리됩니다. 어려운 부분은 모든 요청마다, 손에 쥔 토큰이 정확히 이 서버를 위해, 클라이언트가 실제로 믿는 인가 서버에 의해, 실제로 동의한 사용자를 위해 발급된 것임을 증명하는 것입니다. 기댈 세션은 없이 말입니다.

## 개념

세 역할이 흐름 전체를 짊어지고, 명세의 언어가 이 어휘를 정확하게 쓰기 때문에 어휘 자체가 중요합니다. MCP 서버는 **OAuth 2.1 리소스 서버**입니다. 보호된 프리미티브를 쥐고 베어러 토큰을 받아들이거나 거절합니다. MCP 클라이언트는 **OAuth 2.1 클라이언트**입니다. 사용자를 대신해 브라우저 기반 인가 흐름을 밀고 나가며 요청에 토큰을 붙입니다. **인가 서버(authorization server)** 는 세 번째 역할로, 흔히 호스팅된 신원 공급자 같은 완전히 별개의 서비스이며, 사용자를 인증하고 토큰을 발행하는 책임을 집니다. 이 세 역할 중 어느 것도 모델이 아닙니다. 인가는 전송 계층에서 일어나며, 모델이 보는 어떤 것보다도 아래에 있습니다. 이전 레슨에서 그린 신뢰 구역들은 이 세 번째 역할을 호스트의 경계 밖에 아예 놓습니다. 클라이언트가 그것과 직접 말하고, MCP 서버 자신은 사용자의 원래 자격 증명을 결코 보지 못할 수도 있습니다. 저편에서 나온 토큰만 볼 뿐입니다.

흐름은 거절에서 시작합니다. 클라이언트가 토큰 없이 평범한 `tools/call`을 보내면, 서버는 JSON-RPC 오류가 아니라 그냥 HTTP `401 Unauthorized`로 답합니다. 이 시점에서 요청은 프로토콜 메시지로 파싱될 만큼도 가지 못했으므로, `result`도 `error` 본문도 없이 오직 HTTP 계층 자신의 상태와 헤더만 있습니다. 서버는 어디서 더 알아볼 수 있는지 밝히는 `WWW-Authenticate` 헤더를 실어 주는 것이 좋습니다(SHOULD):

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource/mcp"
```

그 URL은 **보호 리소스 메타데이터**(Protected Resource Metadata) 문서(RFC 9728)를 가리키며, 모든 MCP 서버는 이를 반드시(MUST) 구현합니다. 헤더에서 `resource_metadata`를 찾은 클라이언트는 정확히 그 URL을 불러옵니다. 찾지 못한 클라이언트 — 헤더는 인프라 사정으로 없을 수도 있고 단순히 그 파라미터를 담지 않을 수도 있습니다 — 는 반드시(MUST) 잘 알려진 URI를 스스로 만들어 시도해야 하며 순서가 있습니다. 경로별 위치 먼저, `/.well-known/oauth-protected-resource`에 MCP 엔드포인트 자신의 경로를 더한 것, 그다음 루트, 경로 없는 `/.well-known/oauth-protected-resource`입니다. `https://mcp.example.com/mcp` 엔드포인트에 읽을 헤더가 없다면, 시도할 URL은 정확히 두 개이고 경로별이 먼저입니다. 돌아온 문서는 이 리소스 뒤에 있는 인가 서버 또는 인가 서버들을 이름 대 줍니다:

```json
{
  "resource": "https://mcp.example.com/mcp",
  "authorization_servers": ["https://auth.example.com/tenant-a"],
  "scopes_supported": ["vault:rotate"]
}
```

인가 서버가 식별되면 클라이언트는 그 엔드포인트들을 디스커버리합니다. MCP는 자기만의 접미사를 발명하는 대신 RFC 8414의 기본 `oauth-authorization-server` well-known 접미사를 재사용하고, 발급자는 경로 구성 요소를 가진 채로도 없는 채로도 나타나기 때문에, 클라이언트는 반드시(MUST) 한 가지 형태보다 더 시도해야 합니다. 경로를 가진 발급자, `https://auth.example.com/tenant-a`는 이 순서로 시도합니다. `.well-known` 뒤에 경로를 끼워 넣은 OAuth 메타데이터, 같은 방식으로 경로를 끼워 넣은 OpenID Connect 디스커버리, 그다음 `.well-known` 앞에 경로를 붙인 OpenID Connect 디스커버리. 경로가 없는 발급자는 경로 삽입 없이 바로 앞의 두 형태로 갑니다. 어느 URL이 답하든, 문서 자신의 `issuer` 필드는 반드시(MUST) 그 URL을 만들 때 쓴 발급자 식별자와 글자 하나까지 같아야 합니다. `https://attacker.example/.well-known/oauth-authorization-server`에서 받아 온 문서가 `"issuer": "https://honest.example"`라고 주장한다면 반드시(MUST) 즉시 거절해야 합니다. 이를 받아들이면, 호스트명 하나를 장악한 공격자가 완전히 다른 인가 서버의 신원을 보증할 수 있게 됩니다.

사용자의 브라우저를 어디로든 리디렉트하기 전에 클라이언트는 PKCE 짝을 생성합니다. MCP는 PKCE를 무조건 요구하고, 클라이언트가 기술적으로 가능하다면 특별히 `S256` 메서드를 요구하기 때문입니다. OAuth 2.1도 PKCE도 인가 서버가 PKCE를 지원하는지 물어보는 방법을 정의하지 않으므로, MCP 클라이언트는 대신 메타데이터 문서에서 `code_challenge_methods_supported`를 읽습니다. 그 필드가 없다면 클라이언트는 반드시(MUST) 진행을 거부해야 합니다. 더 할 나위 없이, 그게 없으면 PKCE가 존중될지 알 방법이 전혀 없기 때문입니다. 검증자(verifier)는 클라이언트가 자기만 품고 있는 무작위 문자열이고, 회선 위로 오가는 것은 챌린지(challenge)입니다:

```python
import base64
import hashlib
import secrets

verifier = base64.urlsafe_b64encode(secrets.token_bytes(32)).rstrip(b"=").decode("ascii")
digest = hashlib.sha256(verifier.encode("ascii")).digest()
challenge = base64.urlsafe_b64encode(digest).rstrip(b"=").decode("ascii")
```

두 값이 더 인가 요청과 나중의 토큰 요청 양쪽에 실려 갑니다. `resource` 파라미터(RFC 8707)는 클라이언트가 실제로 그 토큰을 쓰고 싶은 MCP 서버의 정규 URI를 이름 대 줍니다. 스킴과 호스트는 소문자, 프래그먼트 없음, 슬래시가 의미를 가지는 경우가 아니라면 끝의 슬래시도 없음. 인가 서버가 무시하더라도 이를 보내는 것은 의무입니다. 조심스러운 인가 서버가 발급해 온 모든 리소스가 아니라 정확히 하나의 리소스에 묶인 토큰을 주조할 수 있게 해 주는 것이 바로 이 파라미터이기 때문입니다. `state` 파라미터는 요청마다 새로 만들어 돌아올 때 검사되며, 공격자가 클라이언트가 실제로 시작한 인가 응답 대신 다른 응답을 바꿔 끼우는 것을 막는 장치입니다.

인가 서버는 코드를 발행하고 리디렉트로 보고합니다. 클라이언트는 그 리디렉트의 무엇을 믿기 전에 RFC 9207의 `iss` 검사를 적용합니다. 그렇지 않으면 클라이언트가 우연히 믿는 인가 서버 하나를 장악한 공격자가, 한 발급자를 위해 발급된 인가 코드를 완전히 다른 발급자에게 보내도록 속일 수 있기 때문입니다. 이것이 믹스업(mix-up) 공격입니다. 리디렉트 전에 기록해 둔 발급자가 반환된 `iss`와 겨뎨지는데, 규칙은 이 네 가지입니다:

| 서버가 `authorization_response_iss_parameter_supported`를 광고 | 응답의 `iss` | 클라이언트 행동 |
|---|---|---|
| true | 있음 | 기록된 발급자와 정확히 비교 |
| true | 없음 | 응답을 거절 |
| false 또는 없음 | 있음 | 기록된 발급자와 정확히 비교 |
| false 또는 없음 | 없음 | 진행 |

정확한 일치만이 진행합니다. 비교 전에 대소문자 접기, 포트 생략, 끝 슬래시 정규화는 일절 없습니다. 이 검사는 오류 응답에도 적용됩니다. 불일치일 때 클라이언트는 `error`, `error_description`, `error_uri`를 행동에 쓰거나 표시해서도 안 됩니다. 클라이언트가 고른 적 없는 발급자에게서 왔기 때문입니다. 코드가 검증되면 클라이언트는 그것을 토큰 엔드포인트에서 바꿉니다. 같은 `resource` 파라미터와 PKCE `code_verifier`를 보내 인가 서버가 앞서 본 `code_challenge`와 겨뎌 볼 수 있게 합니다. 돌아오는 것은 베어러 토큰입니다.

그 토큰을 쓰는 일은 이 트랙이 이미 세워 온 규율을 되풀이합니다. 자격 증명은 모든 요청에 새로 헤더로 실려 갑니다. `_meta`가 연결 시작 때 한 번이 아니라 모든 요청에 프로토콜 버전과 커패시티를 실어 가는 것과 같은 방식이고, 이전 레슨의 스테이트리스 코어와 맞닿아 있습니다. 구체적으로는 서버로 가는 모든 HTTP 요청에 `Authorization: Bearer <token>`을 붙이고, 접근 토큰은 반드시(MUST NOT) URI 쿼리 문자열에 나타나서는 안 됩니다. 거기서는 로그, 프록시, 브라우저 이력으로 샐 것입니다. 토큰을 받는 것과 토큰을 믿는 것은 다릅니다. 리소스 서버는 반드시(MUST) 토큰의 오디언스가 특별히 이 서버를 이름 대는지 검증해야 합니다. `resource` 파라미터의 그 같은 정규 URI 말입니다. 그 외의 것은 모두 반드시(MUST) 거절합니다. 다른 MCP 서버가 자기 몫으로 발급한 완벽하게 유효한 토큰조차 예외가 아닙니다. 이 서버가 사용자를 대신해 더 상위의 API를 부른다면, 거기서는 자기 자신이 OAuth 클라이언트로서 행동하고 그 한 홉(hop)을 위해 별도의 토큰을 씁니다. 방금 받은 토큰을 전달하는 것, 토큰 패스스루(token passthrough)는 금지가 명백합니다. 상위 API가 이 서버의 권한을 원래 호출자의 권한으로 착각하게 만들고, 상위가 실제로 부여하려던 스코프를 무시하고 지나가게 하기 때문입니다.

세 가지 HTTP 상태 코드가 결과를 실으며, 시험은 이 셋을 흐리게 놀리기를 좋아합니다. `401 Unauthorized`는 토큰이 없거나 유효하지 않다는 뜻입니다. 빠졌거나, 만료했거나, 파싱할 수 없거나, 잘못된 오디언스에 묶였거나. `403 Forbidden`은 인증은 되지만 필요한 스코프가 부족한 토큰이라는 뜻이고, `400 Bad Request`는 토큰이 그림에 들어오기도 전에 인가 요청 자체의 형태가 잘못됐다는 뜻입니다. 클라이언트 등록(애초에 `client_id`를 어떻게 얻는지)과, 토큰이 이미 있을 때 더 많은 스코프를 청하는 것은 둘 다 다음 레슨들을 값어치 있게 만들 만큼 무겁습니다.

```figure
mcpa-23-oauth-flow
```

## 인터랙티브 랩

이 그림은 자격 증명 교체 호출 하나를 세 개 레인 모두를 거치며 따라갑니다. 위 레인에서 클라이언트의 첫 시도는 토큰을 하나도 실지 않고, 서버의 유일한 답은 `WWW-Authenticate` 헤더를 단 HTTP 401입니다. JSON-RPC 본문은 없습니다. 거절이 메시지가 프로토콜 메시지로 파싱되기도 전에 일어나기 때문입니다. 가운데 레인에서 클라이언트는 그 헤더를 보호 리소스 메타데이터 불러오기로 풀고, 이어 경로 발급자 순서로 인가 서버 메타데이터를 불러오고, PKCE 짝을 만들고, 어디로든 리디렉트하기 전에 기록해 둔 것과 겨뎨 보는 코드와 `iss` 값을 들고 인가 서버에서 돌아옵니다. 아래 레인에서 클라이언트는 정확히 같은 `tools/call`을 이번에는 `Authorization: Bearer`를 붙여 되풀이하고, 서버의 리소스 서버 계층은 토큰의 오디언스가 이 서버 자신의 정규 URI이기 때문에 이를 받아들입니다. 그제서야 요청은, 이 트랙이 이전 레슨들부터 세워 온 평범한 도구 처리 코드에 도달합니다.

## 실습 랩

`code/main.py`를 열어 보세요. `simulate_authorization_flow`는 메타데이터 디스커버리, PKCE, 리소스 인디케이터, 발급자 검사를 전부 Python 데이터로, 실제 클라이언트가 계산하는 방식 그대로 만듭니다. 그 부분 어디에도 JSON-RPC는 없습니다. 보호 리소스 메타데이터를 위한 `dict` 하나, 인가 서버 메타데이터를 위한 `dict` 하나, 두 OAuth 요청을 위한 `AuthorizationRequest`와 `TokenRequest` 데이터클래스입니다. 별도로 `McpServer`와 `McpClient`는 MCP 쪽만 모델링합니다. 도구 하나(`rotate_credential`)가 `ResourceServer`의 보호를 받는데, 이 서버는 발급된 토큰 둘을 쥐고 있습니다. 하나는 오디언스가 이 서버의 정규 URI와 맞고, 하나는 완전히 다른 서버를 위해 발급된 것입니다. 레슨 디렉터리에서 실행하세요:

```bash
python3 code/main.py
```

출력된 디스커버리 순서를 먼저 개념 절과 겨뎌 읽어 보세요. 보호 리소스 메타데이터 URL 두 개(경로별, 그다음 루트), 인가 서버 메타데이터 URL 세 개 — 데모에 쓰인 발급자가 경로 구성 요소를 가지고 있기 때문입니다. 그다음 두 전사 항목을 읽어 보세요. 첫 번째는 인증 없는 `tools/call`로, 실제로 실어 갔던 HTTP 상태와 헤더가 함께 감싸져 있습니다. `401`, `result` 없음, `error` 없음. 거절이 JSON-RPC 계층 아래에서 일어날 때 명세가 만들어내는 바로 그 형태입니다. 두 번째 짝은 유효한 베어러 토큰으로 재시도한 같은 호출입니다. 감싸진 요청은 이제 `Authorization: Bearer tok_valid_abc`와 상태 `200`을 실고, 그 뒤에 새 요청 id를 가진 평범한 `resultType: "complete"` 결과가 이어집니다. `foreign_token`의 값을 유효한 호출에 쓴 것으로 바꾸고 다시 실행해 보세요. `https://other-server.example.com/mcp`를 위해 발급된 토큰이, 토큰 자체는 완벽한 형태인데도, 이 서버의 오디언스 검사에 걸려 거절되는 모습을 볼 수 있습니다.

## 완성된 산출물

`outputs/authorization-flow-checklist.md`는 한 페이지 버전입니다. 보호 리소스 메타데이터와 인가 서버 메타데이터 양쪽의 디스커버리 순서, PKCE 거부 규칙, `resource` 파라미터의 요건, `iss` 의사결정 표, 그리고 세 상태 코드와 각각이 실제로 뜻하는 바. 원격 MCP 서버의 인가를 처음 세울 때 옆에 두세요.

레슨 디렉터리에서 테스트를 실행하세요:

```bash
python3 -m unittest discover code/tests
```

테스트는 이 레슨의 주장들을 검증합니다. 보호 리소스 메타데이터 디스커버리는 `WWW-Authenticate` 헤더의 `resource_metadata` 값을 선호하고 그렇지 않으면 경로별-다음-루트 순서의 well-known URL로 물러남, 인가 서버 메타데이터 디스커버리는 경로 발급자에게 세 URL을 루트 발급자에게 두 URL을 순서대로 시도함, `issuer`가 요청한 것과 맞지 않는 메타데이터 문서는 거절됨, PKCE `S256` 챌린지는 독립적으로 계산한 `base64url(sha256(verifier))`과 같음, `code_challenge_methods_supported`가 없는 인가 서버는 리디렉트가 일어나기 전에 거부됨, `resource` 파라미터는 정규화되어 인가 요청과 토큰 요청 양쪽에 실려 감, 네 행 `iss` 표가 양방향으로 집행됨, 다른 서버의 오디언스를 위해 발급된 토큰은 그 외에는 유효하더라도 `401`로 거절됨, 그리고 토큰이 URL에 놓이는 일이 결코 없음. 저장소의 와이어 검사기도 레슨의 전사를 2026-07-28 규칙으로 검증합니다:

```bash
python3 scripts/check_mcpa_wire.py certifications/mcpa/lessons/23-oauth-authorization
```

## 캡스톤 연계

캡스톤의 엔드투엔드 교환에는 오디언스를 검증하고 다른 서버를 위해 발급된 토큰을 거절하는 리소스 서버가 포함되어 있습니다. 여기서 만든 바로 그 검사입니다. 캡스톤이 그 단계에 대해 가정하는 모든 것 — 베어러 토큰은 자기가 주조된 오디언스만큼만 신뢰할 수 있다는 것, HTTP 계층의 거절은 JSON-RPC 본문을 만들지 않는다는 것, 정규 리소스 URI가 토큰이 실제로 묶이는 대상이라는 것 — 은 이 레슨에서 바로 나옵니다.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 리소스 서버 | OAuth 2.1에서 MCP 서버가 맡는 역할. 베어러 토큰을 받아들이거나 거절함 |
| 인가 서버 | 사용자를 인증하고 토큰을 발행하는 별개의 서비스 |
| 보호 리소스 메타데이터 | 리소스 서버의 인가 서버(또는 인가 서버들)를 이름 대는 RFC 9728 문서 |
| PKCE | 훔친 인가 코드가 다른 곳에서 상환되는 것을 막는 검증자-챌린지 짝 |
| S256 | 의무 PKCE 메서드. 챌린지는 base64url(sha256(verifier))과 같음 |
| 리소스 인디케이터 | 토큰 요청을 하나의 정규 서버 URI에 묶는 RFC 8707 `resource` 파라미터 |
| iss 검증 | 인가 응답의 발급자를 리디렉트 전에 기록한 것과 비교하는 것(RFC 9207) |
| 오디언스 검증 | 리소스 서버가 토큰을 받아들이기 전에 토큰이 특별히 자기를 위해 발급됐음을 확인하는 것 |
| 토큰 패스스루 | 별도 토큰을 쓰는 대신 클라이언트의 토큰을 상위 API로 전달하는 것. 금지됨 |
| 401 vs 403 vs 400 | 각각 토큰 없음 또는 무효, 스코프 부족, 형태가 잘못된 인가 요청 |
