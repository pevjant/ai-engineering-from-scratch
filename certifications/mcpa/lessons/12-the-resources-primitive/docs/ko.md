# 리소스(Resources): 상태 없는 서버를 위한 주소 지정 가능한 콘텐츠

> 도구는 무언가를 해서 질문에 답합니다. 리소스는 호스트가 이미 모델을 가리키게 할 수 있는 무언가가 됨으로써 답합니다. 이름으로 호출되는 게 아니라 URI로 주소가 지정되는 거죠.

**유형:** 참고 자료
**사용 언어:** Python
**선수 지식:** 레슨 11
**소요 시간:** 약 45분

## 학습 목표

- `resources/list`, `resources/templates/list`, `resources/read`를 각자 다른 결과를 내놓는 세 개의 별개 메서드로 읽습니다.
- RFC 6570 URI 템플릿을 구체적인 URI로 확장한 뒤, 다른 리소스처럼 읽습니다.
- 존재하지 않는 리소스가 왜 빈 `contents` 배열을 실은 결과가 아니라 `data.uri`를 곁들인 JSON-RPC 오류 `-32602`인지 설명합니다.
- 읽기의 콘텐츠가 공유 대상인지 한 호출자의 것인지에 따라 `ttlMs`와 `cacheScope`를 고릅니다.
- URI가 저장소에 닿기 전에 소독(sanitize)해서, 템플릿이 서버 자신의 루트 밖을 읽는 데 쓰일 수 없게 만듭니다.

## 문제 상황

프로젝트의 README, 티켓 본문, 사용자가 저장한 노트를 모델의 컨텍스트에 넣고 싶어 하는 호스트는 모델에게 무언가를 해달라고 부탁하는 게 아닙니다. 모델이 답하기 전에 이미 알고 있어야 할 것을 고르는 중일 뿐이죠. 이 선택을 도구로 우회시키면 원치 않는 도구 의미론을 물려받습니다. 모델이 호출할지 말지를 결정하고, 호출이 인자 검증에 실패할 수도 있고, 평범한 읽기 하나하나가 트랜스크립트에서는 동작처럼 보이게 됩니다. 반대로 호스트 내부에서 디스크의 파일을 곧장 읽는 식으로 MCP를 완전히 우회하면, MCP가 만들어진 목적인 단 하나의 것을 잃습니다. 호스트가 코드 한 줄도 고치지 않고도 서버가 다른 기계로 옮겨가고, 다른 트랜스포트 뒤에 앉고, 다른 팀에 소속될 수 있다는 것 말입니다.

리소스는 바로 이 간극을 메웁니다. 리소스는 동작이 아니라 콘텐츠이고, 이름으로 호출되는 게 아니라 URI로 주소가 지정되며, 컨텍스트에 언제 들어올지는 모델이 아니라 애플리케이션이 정합니다. `notes://alice/welcome`을 노출하는 노트 서버는 호스트가 사이드바에 렌더링하든, 모델에게 자동으로 먹이든, 특정 턴에서 아예 손대지 않든 똑같이 행동합니다. 프로토콜의 임무는 콘텐츠를 묘사하고 읽기 요청에 올바르게 답하는 데서 끝납니다. 리소스를 읽어들인 뒤 호스트가 그것으로 무엇을 할지는 애플리케이션의 결정으로 남는데, 도구가 프롬프트와 인터페이스를 애플리케이션에 맡겨두었던 것과 같은 방식입니다.

## 핵심 개념

리소스는 MCP의 제어 분할에서 애플리케이션 주도 쪽에 자리합니다. 도구는 모델 제어, 프롬프트는 사용자 제어, 그리고 리소스는 호스트가 고릅니다. 클라이언트는 무엇이 이용 가능한지 발견하고 호스트의 방식대로 요청합니다. 자동 휴리스틱일 수도, 인터페이스의 선택기일 수도, 호스트가 항상 포함하는 고정 집합일 수도 있습니다.

세 메서드가 전체 표면을 커버합니다. `resources/list`는 현재 호출자에게 보이는 리소스들을 돌려줍니다. `uri`, `name`, 선택적 `description`, `mimeType`, `icons`입니다. 이 집합은 비어 있을 수도, 시간이 지나며 바뀔 수도 있지만, 커넥션별로 달라져서는 안 되고 오직 요청에 실린 인가에 따라서만 달라집니다. 레슨 04의 상태 없는 코어가 서버가 지난번에 어떤 커넥션이 물었는지 기억하는 것을 금지하기 때문입니다. `resources/templates/list`는 하나씩 나열하기엔 너무 크거나 너무 역동적인 리소스 계열을 위해 RFC 6570 템플릿으로 기술된 파라미터화된 URI, 가령 `file:///project/{+path}`를 돌려줍니다. `resources/read`는 `uri`를 받아 하나 이상의 콘텐츠 항목을 `contents`에 담아 돌려줍니다.

콘텐츠 항목은 두 모양 중 하나를 취합니다. 텍스트 콘텐츠는 `{uri, mimeType, text}`입니다. 바이너리 콘텐츠는 `{uri, mimeType, blob}`이고, `blob`은 base64로 인코딩된 바이트입니다. 한 번의 읽기가 콘텐츠 항목을 둘 이상 돌려줄 수도 있습니다. 디렉터리를 나타내는 리소스는 그 아래의 모든 파일을 하나의 `contents` 배열로 읽어 돌려줄 수 있고, 각 항목은 자신의 `uri`와 `mimeType`을 실습니다.

URI 스킴은 격식 문제가 아니라 설계 결정입니다. `https://`는 역량 있는 클라이언트가 서버를 거치지 않고도 웹에서 같은 콘텐츠를 직접 가져올 수 있을 때만 쓰세요. 서버가 콘텐츠로 가는 유일한 길이라면 RFC 3986에 맞춰 `file://`, `git://`, 혹은 자기만의 스킴을 선호하세요. `file://` URI가 실제 파일시스템의 실제 경로를 가리켜야 하는 건 아닙니다. 서버가 이해하는 안정적이고 네임스페이스가 붙은 식별자이기만 하면 됩니다. 그렇기 때문에 서버는 인메모리 트리에서 `file:///project/{+path}`를 서비스하면서도 마치 실제 디렉터리를 걸어 내려가는 것처럼 모든 확장을 소독할 수 있는 것입니다. 경로 세그먼트를 조회하기 전에 가상의 루트에 맞춰 정규화해서, 어떤 `..` 세그먼트 나열도 조회가 그 루트 밖으로 걸어나갈 수 없게 만드는 거죠.

오류가 여기서는 도구와 다른 방식으로 중요합니다. 요청된 URI가 존재하지 않으면 서버는 JSON-RPC 오류, 즉 `-32602`(Invalid params) 코드를 `data.uri`와 함께 돌려 무엇이 요청되었는지 밝힙니다. SEP-2164가 이 오류를 일부러 여기에 놓았습니다. `-32602`는 잘못된 파라미터의 평범한 의미이고, 존재하지 않는 URI는 정확히 그것, 즉 서버가 갖고 있는 그 어떤 것에도 해당하지 않는 클라이언트가 공급한 인자이기 때문입니다. 구형 서버들은 `-32002`를 썼는데, 이는 명세가 이 의미로 공식적으로 예약한 적 없는 JSON-RPC 서버 오류 범위의 코드입니다. 2026-07-28 서버는 이를 내보내서는 안 되지만, 잘 행동하는 클라이언트는 우연히 대화하게 된 레거시 상대로부터 이 코드를 받으면 여전히 알아봐야 합니다. 어느 쪽 코드든 서버가 절대 해서는 안 되는 것은 빈 `contents` 배열을 실은 정상 결과를 돌려주는 일입니다. 빈 배열은 리소스가 존재하는데 우연히 비어 있는 것인지, 아예 존재하지 않는 것인지 말해줄 수 없습니다. 그래서 프로토콜은 부재를 뚜렷이 구분되는 오류 모양의 답으로 만들어 그 모호함을 닫아버립니다.

`resources/read`는 complete 결과가 캐싱 힌트를 실어야 하는 여섯 메서드 중 하나입니다. `ttlMs`는 클라이언트가 답을 몇 밀리초까지 신선하다고 취급해도 되는지이고, `cacheScope`는 `public`이나 `private`입니다. 모든 호출자에게 똑같이 읽히는 리소스, 가령 공개 체인지로그는 긴 `ttlMs`를 곁들인 `public`을 쓸 수 있습니다. 한 사용자의 데이터로 범위가 한정된 리소스는 `private`을 써야 합니다. 캐시가 어떤 호출자의 읽기로 다른 호출자의 요청을 충족시키는 일이 없도록 하려는 것이죠. `cacheScope`는 누가 캐시 사본을 공유할 수 있는지를 기술할 뿐, 그 자체로 접근 제어를 수행하지 않습니다. 그래서 서버는 나중에 어떤 스코프를 보고하든 상관없이 모든 읽기를 여전히 인가해야 합니다.

리소스는 선택적 어노테이션인 `audience`, `priority`, `lastModified`, 즉 호스트가 무엇을 먼저 드러낼지 판단하는 데 쓸 수 있는 힌트도 실습니다. 그리고 캐퍼빌리티 플래그 `subscribe`는 클라이언트가 은퇴한 독립형 subscribe 호출 대신, `resourceSubscriptions` 필터를 곁들인 `subscriptions/listen`으로 URI의 변화를 지켜볼 수 있게 해줍니다. 그 스트림의 전체 메커니즘, 즉 승인 응답, 디멀티플렉싱, 취소는 나중에 자기 몫을 다루지만, 요청의 모양은 봉투(envelope) 레슨 이래 써온 그 상태 없는 요청별 `_meta`와 같습니다.

```figure

```

## 인터랙티브 랩

그림은 하나의 URI가 템플릿에서 결과까지 가는 과정을 따라갑니다. 왼쪽에서 템플릿 `file:///project/{+path}`가 경로 세그먼트를 구체적인 URI로 확장합니다. `+`는 평범한 `{path}` 확장이라면 이스케이프했을 중첩 경로의 슬래시를 그대로 남겨둡니다. 가운데 상자는 `resources/read` 자신으로, 조회를 수행하기 전에 확장된 URI를 서버의 루트에 맞춰 소독합니다. 거기서 다이어그램은 갈라집니다. 실존하는 무언가로 해석되는 URI는 `contents`, `ttlMs`, `cacheScope`를 실은 complete 결과를 돌려주고, 아무것으로도 해석되지 않는 URI, 즉 처음부터 등록된 적 없거나 `..` 세그먼트가 루트 밖으로 걸어나가려다 실패한 URI는 `data.uri`에 그 URI를 밝힌 `-32602`를 돌려주며, 조용히 빈 `contents` 배열을 돌려주는 일은 결코 없습니다. 코드로 넘어가기 전에 두 경로를 모두 추적해 보세요. 모든 리소스 서버가 올바르게 구현해야 하는 바로 그 두 결과입니다.

## 실습 랩

`code/main.py`를 열어 보세요. 이 코드는 인메모리 워크스페이스 서버 하나를 만듭니다. `README.md`, `src/` 아래 두 파일을 담은 디렉터리, 바이너리 `logo.png`, `git://` URI 아래 버전 관리되는 체인지로그, 그리고 `user://` URI 아래의 비공개 노트 하나가 그 대상입니다. 레슨 디렉터리에서 실행하세요.

```bash
python3 code/main.py
```

출력된 트랜스크립트를 개념 섹션과 대조하며 읽어 보세요. `resources/list`는 URI 순으로 정렬된 카탈로그를 돌려주고, 각 항목은 `cacheScope: public`과 `ttlMs`를 실습니다. `resources/templates/list`는 템플릿 하나, `file:///project/{+path}`를 돌려줍니다. 데모는 이를 `path=src/utils.py`로 확장하고 결과를 곧장 읽어 돌려줍니다. 디렉터리 항목인 `file:///project/src`를 읽으면 하나의 `contents` 배열에 콘텐츠 항목 두 개, 그 아래 파일당 하나씩 돌아옵니다. `logo.png`를 읽으면 `text` 대신 `blob` 필드가 돌아옵니다. 이를 디코딩해 원본 바이트와 맞는지 확인해 보세요. `user://alice/notes/welcome`을 읽으면 짧은 `ttlMs`를 곁들인 `cacheScope: private`가 돌아옵니다. 그 콘텐츠는 서버에 닿을 수 있는 모든 이의 것이 아니라 한 사용자의 것이기 때문입니다. 마지막 두 읽기는 일부러 만든 실패입니다. 한 번도 등록된 적 없는 URI는 `data.uri`가 채워진 `-32602`로 돌아오고, `..` 세그먼트로 프로젝트 루트 밖을 걸어나가 만든 URI는 아무것으로도 해석되지 않아 같은 식으로 실패하며, 샌드박스 루트 바깥의 어떤 파일에도 닿지 않습니다. 템플릿이 확장할 파일을 바꾸거나 리소스를 직접 추가하고 다시 실행해 보면, 클라이언트는 전혀 고치지 않았는데도 카탈로그와 읽기가 모두 이를 반영하는 모습을 볼 수 있습니다.

## 캡스톤 연계

캡스톤의 단일 엔드투엔드 트랜스크립트에는 도구 호출과 동의(consent) 흐름 곁에 리소스 읽기가 최소 하나 필요하고, 그 읽기의 오류 처리가 이 레슨이 검사하는 것과 같은 규칙 아래에서 맞아야 합니다. 빠진 리소스는 `data.uri`를 곁들인 `-32602`이지 텅 빈 `contents` 배열이 아니며, 모든 complete 읽기는 `ttlMs`와 `cacheScope`를 실어야 합니다. 조회 전에 소독한다는 습관도 계속 끌고 가세요. 캡스톤의 인가 검사가 의지하는 바로 그 규율입니다.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 리소스(Resource) | URI로 식별되는 애플리케이션 주도 콘텐츠 |
| `resources/list` | 호출자에게 보이는 리소스 카탈로그를 캐시 힌트와 함께 돌려준다 |
| `resources/templates/list` | 리소스 계열을 위한 RFC 6570 URI 템플릿을 돌려준다 |
| `resources/read` | URI에 대해 하나 이상의 콘텐츠 항목을 `contents`에 담아 돌려준다 |
| 텍스트 콘텐츠 | `{uri, mimeType, text}` |
| 바이너리 콘텐츠 | `{uri, mimeType, blob}`, base64 인코딩 |
| `-32602` | Invalid params. 빠졌거나 잘못된 리소스 URI의 코드이며 `data.uri`를 실는다 |
| `ttlMs` | 클라이언트가 캐시된 읽기를 몇 밀리초까지 신선하다고 취급할 수 있는지 |
| `cacheScope` | `public`(공유 가능) 또는 `private`(하나의 인가 컨텍스트에 묶임) |
| `subscriptions/listen` | 리소스 변화를 지켜보는 현대적 방법. 은퇴한 `resources/subscribe`를 대체한다 |
