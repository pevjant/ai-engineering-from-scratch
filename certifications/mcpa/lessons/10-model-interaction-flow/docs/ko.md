# 모델 상호작용 흐름

> 도구 호출은 와이어 오가는 메시지 한 건이 아닙니다. 호스트가 사용자, 모델, 서버 사이에서 돌리는 루프이고, 그 루프의 매 턴마다 모델이 다음에 무엇을 보게 되는지가 결정됩니다.

**유형:** 참고 자료
**사용 언어:** Python
**선수 지식:** 레슨 09
**소요 시간:** 약 45분

## 학습 목표

- 사용자 요청이 호스트가 만든 모델 컨텍스트, 도구 선택, 확인 게이트, `tools/call`, 서버 실행, 그리고 모델에게 돌아오는 결과까지 전체 경로를 추적합니다
- 매 턴마다 모델이 정확히 무엇을 보는지 말할 수 있습니다. 호출 전에는 도구 이름, 설명, 스키마를, 호출 후에는 콘텐츠나 `isError` 플래그를 봅니다
- 매니페스트 읽기 레슨의 어노테이션 기본값을 활용해, 파괴적인 호출이 와이어에 나가기 전에 사람에게 도구의 초안 입력을 보여주는 확인 게이트를 적용합니다
- 결정론적 도구 순서가 클라이언트 자신의 캐시와 모델 제공자의 프롬프트 캐시를 모두 지켜주는 이유를 설명합니다
- `input_required` 중단, 도구 실행 오류, 프로토콜 오류를 각각이 루프의 다음 행동을 어떻게 바꾸는지로 구분합니다

## 문제 상황

지난 몇 레슨은 서버가 클라이언트에게 건네는 문서들을 다뤘습니다. discover 결과, 도구 목록, 의심하는 눈으로 읽을 가치가 있는 매니페스트였죠. 하지만 그 어느 것도 사람이 요청을 입력하는 순간 실제로 무슨 일이 일어나는지는 설명해주지 않습니다. `tools/list`에 담겨 있는 도구 정의는 무언가가 그것을 결정과 와이어 호출, 답변으로 바꿔주기 전까지는 잠자 있는 정의일 뿐입니다. 그 무언가가 바로 호스트가 돌리는 루프지, 단일 요청이 아닙니다. 이 루프를 공부하지 않고 지나가면 메시지 모양에 대한 질문은 여전히 맞출 수 있지만, 동작에 대한 질문은 놓치게 됩니다. 클라이언트가 잘못 만들어진 호출을 재시도하는지, 파괴적인 동작을 보내기 전에 사람에게 보여주는지, 턴 사이에 도구 배열을 다시 정렬하면 모델 제공자가 의존하던 캐시가 조용히 깨지는지 같은 것들요.

이 루프에는 서로 다른 두 종류의 실수가 살고, 시험은 둘 다 파고듭니다. 첫 번째는 프로토콜 실수입니다. 날것의 JSON-RPC 오류를 모델에게 그대로 되돌려주고 알아서 고치길 기대한다든지, `input_required` 결과 뒤의 재시도에는 새 id와 `requestState`의 정확한 에코가 필요하다는 사실을 잊는다든지요. 두 번째는 와이어에는 전혀 닿지 않는 호스트 설계 실수입니다. 확인 프롬프트를 건너뛴다든지, 민감한 호출 전에 도구의 초안 인자를 사용자에게 숨긴다든지, 매 턴 도구 목록을 뒤섞는다든지요. 클라이언트가 와이어 상에서는 명세에 완벽히 부합하면서도 이 루프를 틀리게 만들 수 있습니다. 루프의 절반은 명세가 권고만 할 뿐인 호스트 정책이기 때문입니다.

## 핵심 개념

호스트, 클라이언트, 서버 레슨의 구분을 떠올려 보세요. 호스트는 서버 하나당 클라이언트 하나를 돌리고 모델과의 대화를 소유하는 반면, 클라이언트는 결정을 요청으로 바꿔주는 얇은 계층일 뿐입니다. 이 레슨이 추적하는 루프에는 다섯 단계가 있고, 각 단계는 다음 단계로 바통을 넘깁니다.

첫째, 호스트가 모델 컨텍스트를 만듭니다. 호스트는 이미 캐시해 둔 `tools/list` 결과(디스커버리 레슨에서 온)를 갖고 있고, 각 항목을 모델이 보게 될 것과 정확히 같은 것으로 바꿉니다. `name`, `description`, `inputSchema`, 그리고 서버가 신경 써서 보냈다면 `annotations`입니다. 도구가 어떻게 구현되었는지에 대한 정보는 이 경계를 넘지 않습니다. 모델은 서버 코드나 자격 증명, 매니페스트의 레지스트리 메타데이터를 결코 보지 못하고, 매니페스트 레슨에서 리뷰어가 읽는 바로 그 필드들만 봅니다.

둘째, 모델이(이 랩에서는 LLM을 대신하는 작은 결정론적 함수입니다) 컨텍스트와 사용자의 요청을 읽고 도구 이름과 인자를 초안으로 작성합니다. 이 시점에는 아직 와이어 메시지가 하나도 없습니다. 호스트 내부의 결정일 뿐입니다.

셋째, 클라이언트가 무언가를 보내기 전에 호스트가 확인 게이트를 돌립니다. 명세는 사람이 호출을 거부할 수 있어야 하고 클라이언트가 호출 전에 도구 입력을 보여줘야 한다고 말하며, 매니페스트 레슨의 어노테이션 기본값이 이 게이트가 발동하는 시점을 정합니다. `readOnlyHint`의 기본값은 false이고 `destructiveHint`의 기본값은 true라서, `annotations` 블록이 아예 없는 도구는 기본값상 파괴적이며 어디로 나가기 전에 yes가 필요합니다. 게이트가 거부하면 루프는 바로 거기서 끝납니다. 클라이언트는 `tools/call`을 아예 만들지 않으므로, 거부된 동작은 와이어에 어떤 흔적도 남기지 못하고, 호스트가 자기 상태에 적어두는 메모만 남습니다.

넷째, 승인된 호출은 이 커리큘럼의 다른 모든 요청처럼 프로토콜 버전과 캐퍼빌리티를 담은 `params._meta`를 실은 평범한 `tools/call`이 됩니다. 서버는 이제 세 가지 방법으로 답할 수 있고, 각각은 루프를 다른 곳으로 보냅니다.

```json
{"jsonrpc": "2.0", "id": 5, "result": {"resultType": "input_required", "inputRequests": {"priority": {"method": "elicitation/create", "params": {"mode": "form", "message": "What priority should this ticket have?", "requestedSchema": {"type": "object", "properties": {"priority": {"type": "string"}}, "required": ["priority"]}}}}, "requestState": "eyJ0aXRsZSI6IlZQTiBkcm9wcyJ9"}}
```

`resultType`가 `complete`이고 `isError`가 false인 경우가 쉬운 길입니다. 모델이 `content`를 읽고, 도구가 `outputSchema`를 정의했다면 `structuredContent`를 읽고, 호스트는 그것을 곧장 답변으로 접어 넣습니다. `isError`가 true인 `complete` 결과는 도구 실행 오류입니다. 통합 문제 레슨에서 나눠둔 두 오류 채널이 루프 안에서 적용된 모습입니다. 모델은 설명을 읽고 새 id로 인자를 고쳐 재시도할 수 있습니다. `inputResponses`는 여기에 관여하지 않습니다. 이건 그저 또 하나의 평범한 호출이지 멀티 라운드 트립 패턴이 아니기 때문입니다. `input_required` 결과가 바로 그 패턴입니다(요약 브리프 7절). 서버가 자신이 갖고 있지 않은 무언가를 필요로 해서 `elicitation/create`, `sampling/createMessage`, `roots/list`로 전달하고, 호스트는 답을 모아서 같은 호출을 새 JSON-RPC id로 재시도해야 합니다. 이때 `inputResponses`는 서버가 붙인 키 그대로 사용하고, `requestState`는 정확히, 바이트 하나까지 그대로 돌려보냅니다. 클라이언트는 그 문자열을 열어 읽지 않습니다. 마지막으로 알 수 없는 도구에 대한 `-32602` 같은 JSON-RPC 오류는 프로토콜 오류로, 루프는 동일한 요청을 재시도해서는 안 됩니다. 요청에서 바뀐 것이 아무것도 없으니 결과도 아무것도 바뀌지 않을 테니까요.

다섯째, 호스트가 `complete` 결과를 받았거나 어떤 분기가 지원되지 않는다고 판단하면, 콘텐츠를 모델의 진행 중인 컨텍스트에 다시 먹이고, 모델은 도구가 실제로 돌려준 것을 근거로 하는 답변을 만들어냅니다. 그것과 무관하게 지어낸 추측이 아니어야 합니다.

이 루프의 모든 턴에 걸쳐 있는 성질이 하나 더 있습니다. 밑에 깔린 집합이 바뀌지 않았다면 `tools/list`는 매번 같은 순서를 돌려줘야 합니다. 이건 겉모습 문제가 아닙니다. 호스트는 보통 모델 컨텍스트 배열을 한 번 만들어 턴마다 재사용하고, 대부분의 모델 제공자는 그 배열이 들어 있는 프롬프트 접두사를 캐시합니다. 배열을 재정렬하면, 새로 발견한 도구를 끝에 붙이는 게 아니라 가운데 끼워 넣는 것만으로도 그 캐시가 무효화되어 정의 자체보다 많은 토큰 비용이 들 수 있습니다. 결정론적 순서 덕분에 클라이언트는 자기 캐시를 믿을 수 있고, 모델 제공자의 캐시는 턴마다 따뜻하게 유지됩니다.

## 인터랙티브 랩

그림은 하나의 요청이 다섯 단계를 모두 지나가는 과정을 추적합니다. 위쪽 행을 따라가 보세요. 사용자의 요청에서 출발해 호스트가 컨텍스트를 만들고, 모델이 도구를 고르고, 확인 게이트에 이릅니다. 게이트에서 두 갈래가 나갑니다. 승인된 호출은 오른쪽으로 서버까지 이어지고, 거부된 호출은 아래 점선 상자로 곧장 떨어져 보류된 채 끝까지 전송되지 않습니다. 서버 아래에서는 세 가지 결과가 갈라집니다. complete 결과는 아래로 흘러 답변이 되고, 도구 실행 오류와 `input_required` 결과는 둘 다 위로 루프를 돌아 모델에게 돌아가는데, 점선은 그것들이 앞으로 나아가는 게 아니라 재시도라는 표시입니다. 그림에서 두 재시도 경로는 비슷해 보이지만 같은 메커니즘이 아니라는 점에 주목하세요. 새 id와 `requestState` 에코를 실어 나르는 것은 둘 중 하나뿐입니다.

## 실습 랩

`code/main.py`를 열고 레슨 디렉터리에서 실행하세요:

```bash
python3 code/main.py
```

트랜스크립트는 요청과 응답 아홉 쌍을 출력합니다. 먼저 처음의 두 `get_forecast` 호출을 읽어 보세요. 모델이 빈 인자 집합을 초안으로 작성하고, 서버는 빠진 필드를 짚으며 `isError: true`로 답하고, 그제야 모델은 사용자의 문장에 이미 있던 도시를 채워 새 id로 다시 호출합니다. 다음은 두 `open_ticket` 호출입니다. 첫 번째는 유효한 `title`을 갖고도 `input_required`로 돌아옵니다. 이 서버는 모델이 우선순위를 추측하게 두지 않고 항상 사람에게 확인을 요구하기 때문이며, 재시도는 `inputResponses`와 서버가 돌려준 `requestState` 문자열을 읽지도 고치지도 않은 채 그대로 실어 나릅니다. 그다음 출력의 확인 게이트 섹션을 보세요. `close_ticket`은 `annotations` 블록 없이 배포되므로, 호스트는 명세의 기본값에 따라 파괴적으로 취급하고 무언가를 보내기 전에 두 건의 예정된 호출을 모두 사람에게 보여줍니다. 한 티켓은 승인되어 와이어에 도달하고, 다른 하나는 낮은 우선순위 티켓에는 두 번째 검토자가 필요하다는 이유로 거부되어 끝까지 `tools/call`이 되지 못합니다. 마지막으로 모델은 이 서버가 노출하지 않는 `archive_ticket`이라는 도구를 시도했다가 `-32602`를 받고, 동일한 호출을 다시 시도하지 않습니다. 맨 아래의 최종 답변 줄은 요약을 지어내는 게 아니라 성공한 호출의 실제 콘텐츠를 인용합니다. `choose_priority`나 `approve_close`를 바꿔서 다시 실행해 보면 같은 루프를 지나는 다른 경로를 볼 수 있습니다.

## 제공되는 산출물

`outputs/interaction-flow-trace.md`는 한 페이지짜리 추적 자료와 의사결정 표입니다. 호출 전후로 모델이 보는 것, `tools/call` 결과가 루프를 보내는 세 방향, 그리고 호출 전에 입력을 보여주고 프로토콜 오류를 동일하게 재시도하지 않는 호스트 루프를 만들기 위한 체크리스트가 담겨 있습니다.

## 검증하기

레슨 디렉터리에서 테스트를 실행하세요:

```bash
python3 -m unittest discover code/tests
```

테스트는 이 레슨의 주장들을 검사합니다. `tools/list`가 매번 같은 결정론적 순서로 도구 정의를 돌려주는지, 세션의 모든 요청이 `_meta`에 프로토콜 버전과 캐퍼빌리티를 실고 있는지, `_meta`가 빠진 요청이 `-32602`로 거부되는지, `annotations` 블록 없는 도구는 기본값상 파괴적으로 확인이 필요한 반면 명시적으로 읽기 전용이거나 비파괴적인 도구는 그렇지 않은지, 확인 게이트가 거부된 `close_ticket` 호출은 와이어에 못 나가게 막고 승인된 호출은 나가게 하는지, `get_forecast` 도구 실행 오류가 되먹임되고 고쳐진 호출이 새 id로 성공하는지, `open_ticket`의 `input_required` 결과가 답변될 때까지 루프를 실제로 중단시키는지, 재시도가 새 id로 `requestState`를 정확히 에코하는지, `archive_ticket` 프로토콜 오류가 동일하게 재시도되지 않는지, 그리고 최종 답변이 실제 결과 콘텐츠를 인용하는지입니다. 저장소의 와이어 검사기도 이 레슨의 트랜스크립트를 2026-07-28 규칙에 대해 검증합니다:


## 캡스톤 연계

캡스톤의 엔드투엔드 교환은 이 루프를 실제로 돌려본 것입니다. 컨텍스트를 만들고, 모델이 고르게 두고, 민감한 무언가가 나가기 전에 확인하고, 돌아온 세 가지 결과 중 무엇이든 읽고, 도구가 실제로 말한 것에서 답을 만듭니다. 캡스톤이 어떤 호출이 끝까지 전송되지 않은 이유나 재시도가 새 id를 쓴 이유를 물으면, 그 답은 와이어 규칙만이 아니라 이 레슨에서 나옵니다.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 모델 컨텍스트 | 각 도구의 name, description, inputSchema, annotations. 모델이 도구를 고르기 전에 보여지는 것 그 자체 |
| 확인 게이트 | 호스트 쪽 검사(절대 와이어에 나가지 않음)로, 민감한 호출을 보내기 전에 초안 입력을 사람에게 보여준다 |
| 도구 실행 오류 | isError가 true인 complete 결과. 모델이 읽고 인자를 고쳐 새 id로 재시도할 수 있다 |
| input_required | MRTR 중단. 호스트가 빠진 입력을 모아 새 id와 에코한 requestState로 재시도한다 |
| 프로토콜 오류 | -32602 같은 JSON-RPC 오류. 루프는 동일한 요청을 재시도하지 않아야 한다 |
| 결정론적 순서 | tools/list가 매번 같은 순서를 돌려주는 것. 클라이언트 캐싱과 모델 제공자의 프롬프트 캐시를 모두 지킨다 |
| requestState | MRTR 재시도에서 클라이언트가 읽거나 고치지 않고 정확히 에코해 돌려보내는 불투명한 문자열 |
| 어노테이션 기본값 | 도구가 annotations 없이 배포되면 readOnlyHint false, destructiveHint true. 확인 게이트가 적용하는 규칙 |
