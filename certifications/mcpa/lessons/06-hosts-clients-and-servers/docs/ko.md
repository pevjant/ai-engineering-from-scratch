# 호스트, 클라이언트, 서버: MCP의 프로세스 토폴로지

> 호스트는 서버와 직접 이야기하지 않습니다. 서버 하나당 클라이언트 하나를 통해서만 이야기합니다. 바로 이 하나의 묶음이 MCP가 신뢰 경계를 긋는 곳이고, 많은 서버를 모으는 호스트가 이름 충돌 해결을 시작해야 하는 곳입니다.

**유형:** 레퍼런스
**언어:** Python
**선수 지식:** 레슨 05
**시간:** 약 45분

## 학습 목표

- MCP 시스템의 세 참여자(호스트, 클라이언트, 서버)의 이름을 말하고 각자 무엇에 책임이 있는지 밝히기
- 호스트가 하나의 클라이언트로 여러 서버를 돌리는 대신, 서버 연결당 정확히 하나의 클라이언트를 두는 이유 설명하기
- 로컬 stdio 서버와 원격 Streamable HTTP 서버를 구분하고, 각각의 신뢰가 실제로 어떤 경계를 따르는지 설명하기
- 서버 프리미티브(툴, 리소스, 프롬프트, completion) 각각과 클라이언트 기능 각각이 누구에게 통제되는지(누가 제공하는지) 짝짓기
- 연결된 여러 서버의 툴을 하나의 레지스트리로 모으고, 서버 id 접두사로 이름 충돌을 해결하고, 서버가 자기 보고한 serverInfo.name이 결코 라우팅 키가 될 수 없는 이유 설명하기

## 문제 상황

세 시스템에 한꺼번에 연결된 어시스턴트를 상상해 보세요. 파일 서버, 노트 서버, 메트릭 서비스입니다. 그 연결들은 모두 앞선 레슨들의 상태 비저장 코어와 시대 협상 작업에서 이미 본 것과 같은 상태 비저장 요청 모양을 실어 다닙니다. 각 요청이 자기 프로토콜 버전과 기능을 찍고, 어떤 연결도 호출 사이에 아무것도 기억하지 않죠. 앞선 레슨들이 답하지 않은 것은 다른 질문입니다. 호스트가 세 서버와 동시에 이야기할 때 누가 누구에게 말하는지, 그리고 그중 두 서버가 자신들을 똑같이 묘사하거나 같은 이름의 툴을 노출하면 무슨 일이 생기는지 말입니다.

순진한 설계는 세 서버를 전부 하나의 바쁜 연결 객체로 평평하게 눌러 담고, 어떤 서버가 무엇을 보냈는지 추적합니다. 그 설계에는 결과가 어느 서버에게서 왔는지 말할 깨끗한 자리가 없고, 한 서버가 선언한 기능이 다른 서버를 위한 호출로 새어 들어가는 것을 막을 방법이 없으며, 두 서버가 자기 기술에서 우연히 둘 다 스스로를 "primary"라고 부르는 것을 알게 된 순간 둘을 구분할 방법이 없습니다. 이것은 코너 케이스가 아닙니다. 둘 이상의 MCP 서버에 연결하는 모든 호스트가 풀어야 하는 문제이고, 사양의 아키텍처는 규율이 아니라 구조로 그것을 해결합니다. 고정된 역할, 짝(pairing)당 하나의 연결, 그리고 서로를 모르는 채 따로 작성된 두 서버가 만났을 때 무슨 일이 일어날지에 대한 명명 규칙으로요.

## 개념

세 참여자가 MCP 시스템을 이루며 각자 좁은 임무를 갖습니다. **호스트**는 사용자가 실제로 실행 중인 단 하나의 애플리케이션 프로세스입니다. 챗 어시스턴트, IDE, 배치 파이프라인 같은 것이죠. 호스트는 클라이언트를 만들고, 어떤 연결이 존재해도 되는지 통제하고, 툴이 실행되기 전에 동의(consent)를 강제하며, 연결된 서버들이 돌려준 컨텍스트를 모읍니다. 시스템에서 연결된 모든 서버에 걸친 전체 그림을 보는 당사자는 호스트뿐입니다.

**클라이언트**는 호스트가 만드는 객체로, 모든 클라이언트는 그 연결이 살아 있는 동안 정확히 하나의 서버에 스코프가 묶입니다. 이것은 권고가 아닙니다. 아키텍처가 서버들이 서로에게 스며들지 못하게 하는 방식입니다. 호스트에 두 번째 서버가 필요하면 첫 클라이언트의 연결을 재사용하지 않고 두 번째 클라이언트를 만듭니다. 활성 서버 세 개를 둔 호스트는 클라이언트 객체 세 개를 둔 호스트이며, 각각은 자기 서버에 연결되고, 상태 비저장 코어에서 본 것과 같은 요청별 프로토콜 버전과 기능을 찍고, 나머지 두 클라이언트가 무엇을 하는지 결코 보지 못하게 유지됩니다. 클라이언트의 또 다른 임무는 와이어로 새어 나가지 않는 장부 관리입니다. 요청 id의 상관(correlation) 관리, 서버가 선언한 기능의 추적, 그리고 자기가 어느 서버에게 툴 호출을 요청해도 되는지 아는 일입니다.

**서버**는 별개의 프로그램이며 **로컬**이거나 **원격**일 수 있습니다. 로컬 서버는 보통 서브프로세스로 실행되어 stdio, 즉 헤더 계층 없는 줄바꿈 구분 JSON-RPC로 접근하므로 메시지 전체가 `_meta` 안에 삽니다. 원격 서버는 보통 장기 실행 서비스로 Streamable HTTP, 즉 메시지당 POST 하나로 접근하며, `_meta`에 이미 있는 버전과 함께 필수 헤더에도 프로토콜 버전을 반복해서 실습니다. 신뢰는 그 서버가 실제로 넘어서는 경계를 따릅니다. 로컬 stdio 서버는 프로세스 경계를 넘습니다. 보통 같은 사용자 아래에서 실행되고 자격 증명을 환경에서 바로 읽으며, 사양은 stdio 구현이 OAuth 흐름을 아예 실행하지 말라고 합니다. 원격 Streamable HTTP 서버는 네트워크 경계를 넘습니다. 보통 다른 팀이나 다른 회사가 운영하며, 인가 프레임워크(베어러 토큰, 보호 리소스 메타데이터, 오디언스 검증)가 만들어진 대상 전송 계층입니다. 어느 경계도 기본적으로 더 강하지 않습니다. 그저 서로 다른 경계일 뿐이고, 호스트는 "서버"를 하나의 무차별적인 범주로 다루는 대신 각 연결된 서버를 그것이 실제로 넘는 경계 기준으로 판단해야 합니다.

사양은 여기서 붙들어 둘 만한 설계 원칙도 명시합니다. 서버는 대화 전체를 읽을 수 없어야 하고, 서로를 들여다볼 수 없어야 한다는 것입니다. 클라이언트가 보내는 모든 요청은 그 요청 하나에 필요한 것만 실지, 호스트의 전체 이력은 결코 실지 않습니다. 그리고 연결된 두 서버 사이의 격리는 상냥한 배려가 아니라 구조적으로 강제됩니다. 서로 메모를 비교한 적 없는, 서로 다른 클라이언트 객체와 이야기하는 서로 다른 프로세스이기 때문입니다.

서버 프리미티브는 누가 통제하느냐로 갈립니다. **툴**은 모델 통제형입니다. 모델이 이름, 설명, 입력 스키마를 보고 언제 호출할지 결정합니다. **리소스**는 애플리케이션 주도형입니다. 호스트가 무엇을 가져와 컨텍스트에 넣을지 결정하고, 리소스 자체는 URI와 콘텐츠일 뿐입니다. **프롬프트**는 사용자 통제형입니다. 사람이 모델이 자기 멋대로 집어 드는 게 아니라 템플릿을 명시적으로 고릅니다. 네 번째 서버 기능인 **completion**은 프롬프트나 리소스 템플릿의 인자 자동완성을 제공하며, 애플리케이션을 따릅니다. 사용자가 타이핑하는 동안 무엇을 제안할지 결정하는 쪽이 호스트이기 때문입니다. 클라이언트 기능은 반대 방향, 즉 서버가 클라이언트에게 무언가를 요구하는 방향으로 흐릅니다. **유도(elicitation)** 는 서버가 호출 도중 사용자에게 정보를 요구하게 해 주는데, `input_required` 결과로 전달되고 클라이언트는 `inputResponses`를 실어 재시도함으로써 답합니다. 이 개정판에서 완전히 활성 상태입니다. **샘플링(sampling)** 과 **roots**는 2026-07-28부터 둘 다 폐기(deprecated)되었습니다. 샘플링은 서버가 클라이언트에게 자기를 대신해 모델 완성을 실행해 달라고 요청하는 것이었고, 새 서버는 대신 LLM 제공자의 API를 직접 호출해야 합니다. roots는 클라이언트가 파일시스템 경계를 광고하는 것이었고, 새 서버는 대신 디렉터리를 툴 인자나, 리소스 URI나, 서버 설정으로 받아야 합니다. 폐기는 제거가 아닙니다. 둘 다 여전히 동작하며, 둘 중 하나가 제거될 수 있는 가장 빠른 시점은 2027-07-28과 같거나 이후에 릴리스되는 개정판입니다.

서버 여럿을 하나의 호스트 뒤에 두면 진짜 설계 문제가 나타납니다. 바로 집계(aggregation)입니다. 툴 이름은 하나의 서버 안에서만 고유하면 됩니다. 서로를 한 번도 들어 본 적 없는 두 서버가 둘 다 `search`라는 툴을 노출할 수 있고, 둘 다 `server/discover` 결과에서 같은 `serverInfo.name`을 자기 보고할 수 있습니다. 그 필드는 서버 운영자가 넣기로 한 무엇이든 될 수 있기 때문입니다. 자기 보고된 이름으로 집계 레지스트리의 키를 만들거나, 두 번째 `search`가 첫 번째를 조용히 덮어쓰게 두는 호스트는, 아무도 눈치채지 못한 채 모델의 툴 호출을 잘못된 서버로 라우팅하는 무언가를 만든 것입니다. 해결책은 두 부분입니다. 첫째, 레지스트리의 모든 항목과 모든 라우팅 결정은 호스트가 연결할 때 스스로 할당한 연결 식별자(설정 키, 슬롯 인덱스 등 호스트 자신이 통제하는 무엇이든)를 기준으로 삼고, `serverInfo.name`을 기준으로 삼지 않습니다. 둘째, 두 서버가 같은 툴 이름을 선언하면 첫 번째 이름은 그대로 표준(canonical) 항목으로 유지하고, 뒤에 온 충돌 항목은 서버 id 접두사 아래 노출해 두 툴이 서로 다른 이름으로 계속 도달 가능하게 합니다. 툴을 소유한 서버는 호스트가 어떻게 집계했든 자기 오류를 여전히 스스로 강제합니다. 알 수 없는 툴은 여전히 `-32602`이고, 잘못된 인자는 여전히 툴 실행 오류로 돌아옵니다. 집계가 그림에 들어오기 전에 본 것과 정확히 같습니다.

## 인터랙티브 랩

그림은 하나의 호스트 프로세스 안에 클라이언트 박스 세 개를 보여 주고, 각각은 오른쪽의 자기 서버 박스에 연결되어 있습니다. files와 notes는 로컬 stdio 전송 서버로 그려져 있고, 둘 다 의도적으로 같은 `serverInfo.name`인 "primary"를 자기 보고합니다. metrics는 원격 Streamable HTTP 서버로 그려져 있으며, 선언한 기능은 tools가 아니라 resources뿐입니다. 그림의 아래쪽을 읽어 보세요. 레지스트리는 files가 `search`를 먼저 선언했기 때문에 `search`를 files로 가리키고, notes의 충돌하는 `search`는 `notes/search`로 노출합니다. 그 레지스트리 어디에도 등장하지 않는 것에 주목하세요. files와 notes가 공유하는 자기 보고 이름 "primary"입니다. 호스트는 라우팅 방법을 결정하기 전에 어느 서버에게도 자기를 뭐라고 부르는지 묻지 않았습니다.

## 연습 랩

`code/main.py`를 열어 보세요. 표준 라이브러리만으로 세 서버를 만듭니다. 네트워크도 SDK도 없지만 메시지 모양은 2026-07-28 스키마를 정확히 따릅니다. `build_host()`는 `Host`를 `files`, `notes`, `metrics`에 서버 하나당 별개의 `Client` 객체로 연결한 뒤, `build_registry()`를 호출해 그들의 툴을 집계합니다.

```bash
python3 code/main.py
```

출력을 위의 개념 절과 대조하며 읽으세요. 첫 번째 블록은 각 연결의 호스트 할당 id 옆에 서버의 자기 보고 이름을 보여 줍니다. files와 notes가 둘 다 "primary"를 보고하는데, 자기 보고 정체가 안전한 키가 아니라는 요점을 증명하는 장면입니다. 두 번째 블록은 집계된 레지스트리를 보여 줍니다. `search`는 files에 매핑되고, `notes/search`는 notes에 매핑되며, 레지스트리에서 metrics를 가리키는 항목은 없습니다. metrics는 `tools` 기능을 선언한 적이 없고 호스트도 `tools/list` 요청을 보낸 적이 없기 때문입니다. 이어지는 클라이언트별 교환은 모든 요청의 `_meta` 블록과 모든 결과의 `resultType`을 보여 주며, 마지막 두 항목도 포함됩니다. 빠진 인자가 있는 라우팅된 호출이 `isError: true`로 돌아오는 것, 그리고 notes 서버에 없는 툴을 이름으로 부르는 직접 호출이 JSON-RPC 오류 `-32602`로 돌아오는 것. 둘 다 앞선 레슨의 두 오류 채널 규칙이 예측한 그대로입니다.

그다음 뭔가를 바꾸고 다시 실행해 보세요. `serverInfo.name`이 "primary"와 또 충돌하지만 호스트 할당 id는 새로운 네 번째 서버를 추가하고, 레지스트리가 여전히 id 기준으로 올바르게 라우팅하는지 확인하세요. 또는 files와 notes 사이에 충돌하는 툴 이름을 하나 더 추가하고, `Host.route`를 건드리지 않고도 접두사 규칙이 다시 적용되는지 확인하세요.

## 제공되는 산출물

`outputs/architecture-roles-map.md`는 한 페이지짜리 참조 자료입니다. 세 역할과 각자의 책임, 로컬 대 원격 비교 표, 각 항목을 누가 통제하는지 표시한 서버 기능 대 클라이언트 기능 표, 그리고 "호출이 어떻게 집계되었든 수신 서버는 자기 오류를 스스로 강제한다"는 규칙으로 끝나는 6단계 집계 체크리스트가 담겨 있습니다. 상태 비저장 코어와 프로토콜 시대 참조 자료 옆에 두세요. 셋이 합쳐서 요청이 어떻게 만들어지고 호스트가 보낼 올바른 곳을 어떻게 찾는지 다룹니다.

## 검증하기

레슨 디렉터리에서 테스트를 실행하세요.

```bash
python3 -m unittest discover code/tests
```

테스트는 이 레슨의 주장들을 확인합니다. 각 클라이언트가 정확히 하나의 서버 객체에 묶여 있는지. 디스커버리가 서버별로 독립 실행되어 files, notes, metrics가 각자 자기 기능을 얻는지. 충돌하는 툴 이름이 서버 id 접두사로 구분되는지. 표준 이름과 접두사 이름으로의 라우팅이 올바른 서버에 도달하는지. 호스트가 tools 기능을 선언하지 않은 서버에게 툴 목록을 요청하지 않는지. 같은 자기 보고 이름을 공유하는 두 서버가 여전히 독립적으로 라우팅되는지. 특정 서버의 알 수 없는 툴이 여전히 프로토콜 오류인지. 빠진 인자가 있는 라우팅된 호출이 여전히 툴 실행 오류인지. 그리고 레지스트리를 두 번 다시 만들어도 같은 결과가 나오는지. 저장소의 와이어 체커도 이 레슨의 전송 기록을 2026-07-28 규칙에 맞춰 검증합니다:

```bash
python3 scripts/check_mcpa_wire.py certifications/mcpa/lessons/06-hosts-clients-and-servers
```

## 캡스톤 연결

캡스톤은 동작하는 MCP 배포를 처음부터 끝까지 묘사하라고 요구하며, 리뷰어가 가장 먼저 묻는 질문 중 하나가 이것입니다. 호스트가 실제로 도달하는 서버가 몇 개인지, 모델이 선택한 툴 호출이 어떻게 올바른 서버에 도달하는지 말입니다. 이 레슨의 어휘로 답하세요. 호스트가 할당한 각 연결 id의 이름을 밝히고, 그것이 묶인 서버를 말하고, 그 서버가 로컬인지 원격인지 그리고 신뢰가 어느 경계를 따르는지 말하며, 이름 충돌을 해소하는 레지스트리 항목을 가리키세요. 라우팅 결정을 정당화하려고 서버의 자기 보고 이름을 손에 들어 올리는 캡스톤 답변은 아직 이 레슨을 배우지 못한 것입니다.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 호스트(Host) | 사용자가 실행하는 단 하나의 애플리케이션 프로세스. 클라이언트를 만들고 관리한다 |
| 클라이언트(Client) | 호스트가 만드는 객체로, 연결이 살아 있는 동안 정확히 하나의 서버에 묶인다 |
| 서버(Server) | 툴, 리소스, 프롬프트를 노출하는 별개 프로그램. 로컬(stdio) 또는 원격(Streamable HTTP) |
| 로컬 서버 | stdio로 접근하는 서브프로세스. 신뢰는 프로세스 경계를 따른다 |
| 원격 서버 | Streamable HTTP로 접근하는 서비스. 신뢰는 네트워크 경계를 따른다 |
| 통제 모델 | 툴은 모델 통제형, 리소스는 애플리케이션 주도형, 프롬프트는 사용자 통제형 |
| 유도(Elicitation) | 서버가 MRTR 왕복을 통해 사용자에게 입력을 요구하게 해 주는 클라이언트 기능 |
| serverInfo.name | 서버의 자기 보고 정체. 표시와 로깅 전용이며 결코 라우팅 키가 아니다 |
| 서버 id 접두사 | 호스트가 충돌하는 툴 이름에 적용하는 구분 기법. 예: `notes/search` |
