# MCP Apps 검토 체크리스트

UI 능력을 가진 도구가 가리키는 것을 호스트가 렌더링하기 전에 검토하기 위한 한 페이지 참고 자료입니다. MCP 2026-07-28과 MCP Apps 명세(2026-01-26) 기준입니다.

## `ui://` 리소스를 믿기 전에

- 확장이 이 요청 위에서 협상됐는지: 클라이언트가 `io.modelcontextprotocol/clientCapabilities.extensions`에 `io.modelcontextprotocol/ui`를 선언했고, 서버가 `server/discover`의 `capabilities.extensions`에 같은 식별자를 적었는지.
- 도구 정의가 `_meta.ui.resourceUri`를 실고 있는지. 그리고 그 필드는 도구 정의의 나머지와 마찬가지로 누가 묻는지에 따라 바뀌지 않는지.
- 도구의 `_meta.ui.visibility`(생략 시 기본 `["model", "app"]`)가 누가 그것에 닿을 수 있는지 결정합니다. `"model"`을 빼면 에이전트 자신의 도구 목록에 절대 나타나지 않아야 하고, `"app"`을 빼면 앱 자신이 `tools/call`을 시도할 때 호스트가 그것을 거부해야 합니다. 앱 전용 도구로의 서버를 넘나드는 호출은 언제나 막힙니다.
- 리소스는 특별한 메서드가 아니라 평범한 `resources/read`로 가져와졌는지. 기본 와이어에 `ui://` 리소스를 다른 방식으로 가져오는 길은 없습니다.
- 결과의 `mimeType`이 정확히 `text/html;profile=mcp-app`인지. `charset` 매개변수가 있든 없든 평범한 `text/html`은 마크업이 아무리 잘 생겼어도 렌더링 가능한 앱이 아닙니다. 이것 하나는 경정책이 아니라 강한 MUST입니다.
- 결과의 `_meta.ui.csp`는 목록이 아니라 객체입니다: `connectDomains`, `resourceDomains`, `frameDomains`, `baseUriDomains`, 각각 오리진들의 선택 배열. 호스트는 정확히 그 도메인들로 자신의 Content Security Policy를 만들어야 하고(MUST), 리소스가 선언하지 않은 오리진을 허용해서는 안 되며(MUST NOT), 실제로 존중할 것을 그보다 더 제한할 수는 있습니다(MAY). `csp`를 통째로 빼면 호스트는 반드시(MUST) 제한적인 기본값(아웃바운드 연결 없음, same-origin 스크립트와 스타일만)으로 떨어집니다. `frameDomains`를 빼면 `frame-src`는 `'none'`입니다. `baseUriDomains`를 빼면 `base-uri`는 `'self'`입니다.
- 결과의 `_meta.ui.permissions`는 빈 객체 플래그들의 객체입니다: `camera`, `microphone`, `geolocation`, `clipboardWrite`. 호스트는 그중 무엇이든 iframe `allow` 속성을 통해 존중할 수 있습니다(MAY). 의무는 절대 아니며, 부여되지 않은 권한은 리소스를 거부할 이유가 아닙니다. 잘 만들어진 앱은 요청한 권한이 부여됐다고 가정해서는 안 됩니다(SHOULD NOT).
- 결과가 `ttlMs`와 `cacheScope`를 실었는지, 그리고 private 스코프의 읽기는 다른 인가 컨텍스트에서 재사용되지 않는지.

## 렌더링과 브리지

- 앱은 호스트가 통제하는 샌드박스 iframe 안에서 렌더링됩니다. 호스트 페이지의 쿠키, 로컬 스토리지, DOM을 읽을 수 없고 부모 페이지를 이동시킬 수도 없습니다.
- 호스트가 웹 페이지라면 뷰와 직접 대화해서는(MUST NOT) 안 됩니다. 호스트 자신과 다른 오리진 위의 샌드박스 프록시로 뷰를 감싸고, 그 프록시가 브리지 메시지를 양방향으로 전달합니다.
- 앱에서 호스트로 가는 모든 통신은 클라이언트-서버 연결과는 별개의 `postMessage` JSON-RPC 방언을 넘어갑니다. 일부 메서드 이름은 공유되고(`tools/call`) 대부분은 `ui/` 접두사가 붙은 새것입니다(`ui/initialize`).
- 그 브리지 핸드셰이크는 코어 프로토콜에서 제거된 `initialize` 요청이 아닙니다. iframe 하나의 채널을 호스트 프레임에 연결할 뿐, 프로토콜 버전을 협상하거나 세션을 만들지 않습니다.
- 앱이 시작한 도구 호출은 서버에 닿기 전에 독립된 두 게이트를 통과해야 합니다: 대상 도구의 `visibility`가 `"app"`을 포함할 것, 그리고 호스트 자신의 동의. 어느 게이트 하나만으로도 막을 수 있습니다. 전달된 호출은 새 id와 온전한 `_meta`를 가진 평범한 `tools/call`입니다.

## 폴백

- UI 능력을 가진 도구라도 모든 `tools/call`에서 유용한 `content` 텍스트 답을 돌려줍니다. 확장이 선언됐는지와 무관하게요.
- 확장을 지원하지 않는 호스트는 `ui://` 리소스를 아예 읽지 않습니다. 다른 어떤 도구처럼 도구의 텍스트 콘텐츠를 씁니다.
- 여기에도 어디에나 적용되는 일반 확장 규칙이 그대로 적용됩니다. 지원이 없는 쪽은 요청이 그냥 실패하는 대신 코어 동작으로 폴백합니다.

## 판단 표

| 검사 | 통과 | 실패 |
|-------|--------|-------|
| 확장이 이 요청 위에서 협상됨 | 리소스 가져오기로 계속 | 도구의 텍스트 콘텐츠를 씀. 리소스를 절대 가져오지 않음 |
| 도구 `visibility`가 호출자를 포함(`model` 또는 `app`) | 계속(에이전트가 보거나, 앱이 호출할 수 있음) | 에이전트의 도구 목록에서 빠지거나, 앱의 호출이 거부됨 |
| `mimeType`이 `text/html;profile=mcp-app` | CSP 구성으로 계속 | 평범한 리소스로 취급, 앱이 아님. 텍스트로 폴백 |
| 선언된 모든 CSP 도메인이 호스트 정책 안에 있음 | 선언된 도메인들로 만든 CSP로 렌더링 | 텍스트로 폴백. 호스트 정책상의 판단이지 프로토콜 실패가 아님 |
| 요청된 `permissions` | 호스트 정책이 허용하는 부분집합을 부여. 어느 쪽이든 렌더링 | 리소스를 거부할 이유가 절대 아님 |
| 앱이 시작한 도구 호출이 visibility와 동의를 모두 갖춤 | 평범한 `tools/call`로 전달 | 전달하지 않음. 서버에 아무것도 닿지 않음 |

## 시험을 위해 기억하기

- 확장 식별자는 `io.modelcontextprotocol/ui`이며, 다른 모든 확장처럼 요청별로 협상됩니다. 연결당 한 번이 아닙니다.
- `_meta.ui.csp`는 평평한 배열이 아니라 도메인 목록 키들의 객체이고, `_meta.ui.permissions`는 문자열 목록이 아니라 빈 객체 플래그들의 객체입니다.
- 틀린 MIME 타입은 강한 MUST 위반입니다. 정책 밖의 CSP 도메인은 호스트가 '더 제한할 여지'를 행사하는 것이지 명세가 명령한 거부가 아니고, 누락된 권한 부여는 렌더링을 전혀 막지 못합니다.
- `visibility`의 기본값은 `["model", "app"]`입니다. 어느 이름을 빼느냐에 따라 걸리는 호출자가 달라지고, 서버를 넘나드는 앱 전용 호출은 언제나 막힙니다.
- `ui/initialize`는 앱-호스트 브리지의 일부이지 제거된 코어 `initialize` 요청이 아니며, 웹 호스트는 중간의, 다른 오리진의 샌드박스 프록시를 통해서만 뷰에 닿습니다.
