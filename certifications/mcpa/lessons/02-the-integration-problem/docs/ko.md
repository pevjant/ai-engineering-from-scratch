# MCP가 해결하는 통합 문제

> AI 애플리케이션에 연결하는 모든 시스템은 하나의 계약입니다. MCP는 그 계약을 어디서나 같은 모양으로 만들어서, 한 번 본 적 없는 서버도 클라이언트가 바로 쓸 수 있게 합니다.

**유형:** 레퍼런스
**언어:** Python
**선수 지식:** 레슨 01
**시간:** 약 45분

## 학습 목표

- N×M 통합 문제가 무엇인지, 그리고 공유 프로토콜 하나가 이것을 N+M으로 줄여 주는 방식 설명하기
- MCP가 AI 애플리케이션과 외부 시스템 사이에서 표준화하는 것과, 의도적으로 표준화하지 않고 남겨 두는 것 구분해서 말하기
- MCP 시스템의 참여자들과 세 가지 서버 프리미티브를 각각 한 문장으로 말하기
- 디스커버리(discovery) 요청, 툴 목록, 툴 호출을 요청별 메타데이터를 실은 평범한 JSON-RPC 메시지로 읽기
- 프로토콜 오류와 툴 실행 오류를 구분하고, 그 차이가 모델에게 왜 중요한지 설명하기

## 문제 상황

AI 애플리케이션을 외부 시스템에 연결하는 일은 예전에는 접착제(glue) 코드를 작성하는 일이었습니다. 여러분의 파일, 티켓 큐, 데이터베이스가 필요한 어시스턴트라면 통합 작업 세 개가 필요했고, 각 통합은 자기만의 방식으로 "내가 무엇을 할 수 있는지"를 묘사하고, 자기만의 인자 형식을 만들고, 자기만의 오류 모양을 갖고, 누가 호출할 수 있는지에 대한 자기만의 개념을 갖고 있었습니다. 네 번째 시스템이 생기면 네 번째 통합이 필요합니다. 두 번째 AI 애플리케이션이 생기면 그 모든 것을 처음부터 다시 작성해야 합니다. 첫 번째를 위해 작성한 것이 두 번째에는 맞지 않기 때문입니다.

이것이 바로 N×M 문제입니다. 애플리케이션 네 개와 시스템 여섯 개면 통합이 스물네 개 필요하고, 그 하나하나가 형식이 흐트러지고 보안 가정이 흐려지는 지점입니다. 비용이 크게 드는 부분은 첫 번째 통합이 아닙니다. 스무 번째 통합, 그리고 그 스무 개를 한꺼번에 머릿속에서 추론해야 하는 리뷰입니다.

Model Context Protocol은 N×M을 N+M으로 바꿉니다. 각 애플리케이션은 MCP를 딱 한 번 배우면 되고, 각 시스템은 MCP 서버를 딱 한 번 노출하면 됩니다. 그러면 어떤 현대적 클라이언트든 어떤 현대적 서버든 사용할 수 있습니다. 양쪽이 하나의 메시지 형식, 하나의 기능(capability) 기술 방식, 하나의 툴 호출 및 결과 읽기 방식에 합의했기 때문입니다. 애플리케이션 네 개와 시스템 여섯 개의 비용이 이제 구현 열 개이고, 새 시스템 하나가 추가될 때마다 비용도 하나씩만 늘어납니다.

## 개념

MCP는 제품이 아니라 프로토콜입니다. AI 애플리케이션과, 그 애플리케이션에 컨텍스트를 주고 행동을 허용하는 시스템들 사이의 대화를 표준화합니다. 서버가 자신을 어떻게 묘사하는지, 클라이언트가 서버의 제공 항목을 어떻게 묻는지, 툴이 어떻게 호출되는지, 결과와 오류가 어떻게 돌아오는지 말이죠. 반면 모델 자체, 호스트가 어떤 모델을 쓰는지, 호스트가 프롬프트를 어떻게 조립하는지, 사용자 인터페이스가 어떤 모습인지는 의도적으로 표준화하지 않습니다. 그것들은 애플리케이션의 결정으로 남습니다.

참여자는 많지 않습니다. **호스트(host)** 는 사용자가 작업하는 애플리케이션입니다. 챗 어시스턴트나 편집기 같은 것이죠. 호스트 내부에서 **클라이언트(client)** 가 하나의 **서버(server)** 와의 대화를 담당하며, 호스트는 사용하는 서버 하나당 클라이언트 하나를 실행합니다. 서버는 세 종류의 **프리미티브(primitive)** 를 노출합니다. **툴(Tools)** 은 이름과 설명, 스키마로 유형이 정의된 동작으로, 모델이 호출을 결정할 수 있습니다. **리소스(Resources)** 는 URI로 식별되는 읽기 가능한 데이터로, 애플리케이션이 컨텍스트에 넣을지 선택합니다. **프롬프트(Prompts)** 는 사용자가 명시적으로 골라 쓰는 재사용 가능한 템플릿입니다. 누가 통제하느냐가 각각 다릅니다. 툴은 모델이 통제하고, 리소스는 애플리케이션이 주도하며, 프롬프트는 사용자가 통제합니다.

모든 메시지는 JSON-RPC 2.0입니다. 요청은 `id`, `method`, `params`를 가집니다. 응답은 같은 `id`와 함께 `result` 또는 `error`를 실어 돌아옵니다. MCPA 시험이 기준으로 삼는 개정판인 2026-07-28에서는 모든 요청이 `params._meta`에 자신만의 프로토콜 메타데이터도 함께 실습니다. `io.modelcontextprotocol/protocolVersion` 키 아래의 프로토콜 버전, `io.modelcontextprotocol/clientCapabilities` 아래의 클라이언트 기능, 그리고 권장 사항으로 `io.modelcontextprotocol/clientInfo` 아래의 클라이언트 이름과 버전이 그것입니다. 오프닝 핸드셰이크도 세션도 없습니다. 각 요청이 스스로 완결적이기 때문에, 서버의 어떤 레플리카(replica)든 그 요청에 답할 수 있습니다.

모든 결과는 `resultType`을 실고 있습니다. 지금 단계에서 보게 될 것은 `complete`로, 결과가 최종 콘텐츠를 담고 있다는 뜻입니다. 이후 레슨에서는 `input_required`를 소개합니다. 서버가 일을 마치기 전에 사용자에게 뭔가를 받아야 할 때 주는 답입니다.

디스커버리는 코드가 아니라 데이터입니다. 클라이언트는 `server/discover`를 호출해 서버가 지원하는 프로토콜 버전, 제공하는 기능, 이름을 알아낼 수 있고, `tools/list`를 호출해 각 툴의 이름, 설명, 입력 스키마를 받을 수 있습니다. 클라이언트에 미리 컴파일되는 것은 아무것도 없습니다. 이것이 상호 운용성 논리의 전부를 담은 한 문장입니다. 오늘 작성된 클라이언트가 내년에 작성된 서버를 구동할 수 있는 이유는, 서버가 프로토콜 안에서 자기 자신을 묘사하기 때문입니다.

오류는 두 종류로 나오고, 시험은 이 차이를 중요하게 봅니다. **프로토콜 오류(protocol error)** 는 JSON-RPC 오류입니다. 요청 자체가 잘못된 경우로, 서버에 없는 툴 이름을 부르는 호출이 여기 해당하며 코드 `-32602`(Invalid params)입니다. **툴 실행 오류(tool execution error)** 는 `isError: true`를 담은 정상 결과로, 콘텐츠 안에 설명이 붙어 있습니다. 툴이 모델이 고칠 수 있는 문제, 예컨대 빠진 인자에 부딪힌 것이죠. 모델은 툴 실행 오류를 보고 인자를 고쳐 재시도할 수 있습니다. 반면 프로토콜 오류에서 배울 수 있는 것은 훨씬 적습니다.

```figure
mcpa-02-n-by-m
```

## 인터랙티브 랩

그림은 같은 애플리케이션 네 개와 시스템 여섯 개를 두 번 보여 줍니다. 왼쪽에서는 모든 애플리케이션이 모든 시스템에 연결되어 있습니다. 커스텀 접착제 선 스물네 개입니다. 오른쪽에서는 각 애플리케이션과 각 시스템이 공유 프로토콜에 한 번씩 연결됩니다. 총 연결 열 개입니다. 그다음 한 클라이언트에서 한 서버로 가는 단일 요청을 따라가 보세요. 요청은 메서드 이름을 밝히고 자기 버전과 기능을 실으며, `resultType`이 complete라고 말해 주는 결과를 돌려받습니다. 오른쪽에 없는 것에 주목하세요. 첫 유용한 요청 이전에 이루어지는 준비 대화가 전혀 없습니다.

## 연습 랩

`code/main.py`를 열어 보세요. 네트워크도 SDK도 없는 표준 라이브러리 모델이지만, 메시지 형태는 2026-07-28 스키마를 따릅니다. 서로 관련 없는 두 서버(날씨 서비스와 티켓 서비스)와, 어느 쪽을 위해서도 작성되지 않은 클라이언트 클래스 하나를 만듭니다. 클라이언트는 각 서버를 디스커버하고, 툴을 나열하고, 호출합니다.

```bash
python3 code/main.py
```

출력된 교환을 개념 절과 대조하며 읽으세요. 모든 요청의 `_meta` 블록과 모든 결과의 `resultType`을 찾아 보세요. 그다음 일부러 만든 세 가지 실패를 찾아 보세요. 도시 없이 호출한 `get_forecast`는 `isError: true`를 담은 정상 결과로 돌아옵니다. 존재하지 않는 툴에 대한 호출은 JSON-RPC 오류 `-32602`로 돌아옵니다. 프로토콜 버전을 `1999-01-01`이라고 주장하는 요청은 오류 `-32022`로 돌아오고, 그 `data`에는 서버가 실제로 지원하는 버전들이 나열됩니다. 도시를 바꾸고, 티켓 서버에 세 번째 툴을 추가한 뒤 다시 실행해 보세요. 클라이언트는 하나도 바꾸지 않았는데 디스커버리가 새 툴을 잡아 내는 모습을 확인할 수 있습니다.

캡스톤은 디스커버리부터 감사(audit)된 툴 호출까지, 2026-07-28 교환 전체를 조립합니다. 그 모든 것은 이 레슨의 그림 위에 서 있습니다. 서버 하나당 클라이언트 하나를 두는 호스트, 데이터로서 자신을 묘사하는 서버들, 자기 메타데이터를 실은 요청들, 자신이 어떤 종류의 결과인지 말해 주는 결과들이요. 캡스톤이 설계를 정당화하라고 요구할 때, 여러분은 N+M 모델과, 프로토콜 오류와 툴 실행 오류의 구분을 근거로 논의하게 됩니다.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 호스트(Host) | 사용자가 작업하는 애플리케이션. 서버 하나당 클라이언트 하나를 실행한다 |
| 클라이언트(Client) | 호스트 안에서 하나의 서버와 통신하는 구성 요소 |
| 서버(Server) | MCP 위에서 툴, 리소스, 프롬프트를 노출하는 프로그램 |
| 툴(Tool) | 이름, 설명, 입력 스키마를 가진 모델 통제형 동작 |
| 리소스(Resource) | URI로 식별되는 애플리케이션 주도형 읽기 가능 데이터 |
| 프롬프트(Prompt) | 사용자가 명시적으로 선택하는 사용자 통제형 템플릿 |
| `_meta` | 버전, 기능, 클라이언트 정체를 실는 요청별 메타데이터 블록 |
| `resultType` | 결과가 complete인지, 입력이 더 필요한지를 알려 주는 필드 |
| 프로토콜 오류 | 요청 자체가 잘못된 경우의 JSON-RPC 오류. 예: 알 수 없는 툴(`-32602`) |
| 툴 실행 오류 | 모델이 읽고 수정할 수 있는 `isError: true`를 담은 정상 결과 |
