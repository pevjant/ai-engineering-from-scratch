# 현대식 MCP 서버와 구버전 서버 구분하기

> 현대식 MCP에는 오프닝 핸드셰이크가 없습니다. 그래서 현행 서버와 구버전 서버를 모두 다뤄야 하는 클라이언트는, 어느 쪽이든 미리 선언해 주는 것이 아니라 아주 첫 교환이 어떻게 동작하는지 보고 상대가 어느 종류인지 판단해야 합니다.

**유형:** 레퍼런스
**언어:** Python
**선수 지식:** 레슨 04
**시간:** 약 45분

## 학습 목표

- 2024-11-05부터 2026-07-28까지의 개정판 연표와 각 개정판이 만든 대표 변경 사항 말하기
- modern, legacy, dual-era를 정의하고, 클라이언트 시대와 서버 시대의 모든 조합에 대해 호환성 매트릭스 읽기
- stdio 위의 서버를 `server/discover`로 탐침(probe)하고 그 응답을 modern, 다른 버전의 modern, legacy로 분류하기. 판단을 특정 오류 코드 하나에 묶지 않고서
- 클라이언트가 `UnsupportedProtocolVersionError`(코드 -32022) 이후 핸드셰이크 없이 버전을 어떻게 협상하는지 설명하기
- 2026-07-28이 통째로 제거한 것, 그리고 modern 버전만 말하는 서버가 오래된 연결 시도를 거부하면서도 자기 지원 버전을 여전히 이름으로 밝히는 이유 말하기

## 문제 상황

실제 배포 환경은 한 번에 다 업그레이드되지 않습니다. 클라이언트 라이브러리는 오늘 만들어지지만 몇 달, 몇 년 간격으로 작성된 서버들과 여전히 이야기해야 합니다. 어떤 서버는 새 개정판이 나온 당일에 업데이트되고, 어떤 서버는 설치된 그대로 방치되어 있죠. 2026-07-28 개정판은 이런 상황을 정리하는 데 쓰이던 핵심 장치, 즉 실제 작업이 시작되기 전에 버전을 이름으로 밝히는 오프닝 교환을 제거했습니다. 이제 모든 현대식 요청은 스스로를 기술합니다. 그래서 프로토콜이 상태 비저장이 될 수 있었던 것이지만, 그 덕분에 클라이언트와 서버가 기본 규칙에 합의하는 전용 순간도 사라졌습니다.

그래서 그렇게 넓게 흩어진 서버들 사이에서 쓸모 있으려고 만들어진 클라이언트는, 쓸모 있어지기도 전에 풀어야 할 진짜 문제가 있습니다. 아직 아무것도 모르는 연결이 주어졌을 때, 반대편에 있는 것이 현대식 요청별 메타데이터를 읽는지, 아니면 옛 방식의 인사를 기대하는지 싸고 믿을 수 있게 판단해야 합니다. 잘못 추측하면 교환은 혼란스러운 방식으로 실패합니다. 현대식 서버는 자기가 모르는 메서드를 받은 것처럼 보이고, 구버전 서버는 자기가 기대하는 것이 하나도 없는 요청을 해석하려 듭니다. 이 레슨은 그 판단을 우연이 아니라 사양이 정의한 방식대로 의도적으로 수행하는 방법에 관한 것입니다.

## 개념

아래 표는 프로토콜의 이름 붙은 모든 개정판과 그 개정판을 정의하는 변경 사항을 나열합니다. 가장 최근 것만 modern이고, 그 이전은 전부 legacy입니다.

| 개정판 | 시대 | 대표 변경 사항 |
|---|---|---|
| 2024-11-05 | Legacy | 첫 공개 개정판: stdio와 HTTP+SSE 전송 계층, 그리고 모든 연결을 열던 핸드셰이크. |
| 2025-03-26 | Legacy | Streamable HTTP가 HTTP+SSE를 대체; OAuth 2.1 인가; 툴 어노테이션; 오디오 콘텐츠. |
| 2025-06-18 | Legacy | 구조화된 툴 출력; 리소스 링크; 유도(elicitation); OAuth 리소스 서버 분류; MCP-Protocol-Version 헤더; JSON-RPC 배치 처리 제거. |
| 2025-11-25 | Legacy | 아이콘; 점진적 스코프 동의; 툴 이름 가이드; URL 모드 유도; 실험적 tasks; 검증 오류가 프로토콜 오류 대신 툴 실행 오류로 변경. |
| 2026-07-28 | Modern | 상태 비저장 코어, 핸드셰이크와 세션의 소멸; `server/discover`, 다중 왕복 요청(MRTR), `resultType`, `subscriptions/listen` 추가; tasks를 확장으로 이동; roots, sampling, logging, Dynamic Client Registration 폐기. |

이 레슨의 나머지를 짊어지는 세 단어가 있습니다. **Modern**은 버전, 정체, 기능이 요청별 메타데이터로 이동하는 개정판을 뜻합니다. 2026-07-28과 그 이후 전부입니다. **Legacy**는 `initialize` 핸드셰이크로 연결을 열고 세션 동안 상태를 보관하는 개정판을 뜻합니다. 2025-11-25와 그 이전 전부입니다. **Dual-era**는 둘 다 지원하는 구현체(클라이언트든 서버든)를 묘사하며, 다른 무엇을 파싱하기 전에 상대가 어느 쪽인지 명시적으로 결정합니다.

Dual-era 클라이언트의 모든 임무는 결국 하나의 탐침으로 귀결됩니다. stdio에서는, 중요한 어떤 요청을 보내기 전에 자신이 선호하는 버전을 `_meta`에 실은 `server/discover`를 보내고 돌아오는 것을 읽습니다.

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32022,
    "message": "Unsupported protocol version",
    "data": {
      "supported": ["2026-07-28", "2025-11-25"],
      "requested": "1900-01-01"
    }
  }
}
```

세 가지 결과, 세 가지 결론입니다. `DiscoverResult`가 오면 서버는 modern입니다. `supportedVersions`에서 버전 하나를 골라 계속 진행합니다. 인식 가능한 modern 오류 — 위에 보이는 `UnsupportedProtocolVersionError`가 그것 — 는 여전히 서버가 modern이라는 뜻입니다. 다만 클라이언트가 먼저 시도한 버전이 아닐 뿐이죠. 새 요청 id를 써서 `data.supported`에 나열된 버전 중 하나로 재시도하고, 이것을 modern 경로를 포기할 이유로 취급하지 않습니다. 그 밖의 모든 것 — 클라이언트가 소수의 modern 오류 모양으로 인식하지 못하는 오류, 합리적인 시간 안의 무응답 — 은 서버가 legacy라는 뜻입니다. 구버전 `initialize` 핸드셰이크로 폴백(fallback)하세요. 여기서 중요한 규율은 세 번째 경우입니다. 폴백은 결코 특정 오류 코드 하나에 묶여서는 안 됩니다. 구버전 서버는 낯선 메서드에 같은 방식으로 두 번 답할 의무가 없기 때문입니다. Method not found로 답할 수도, Invalid params로 답할 수도, 그냥 멈춰 버릴 수도 있습니다. "legacy"를 식별하는 것은 인식 가능한 modern 답변의 부재이지, 어떤 특정 답변의 존재가 아닙니다.

Streamable HTTP 전송 계층에서는 같은 생각이 다른 모양을 취합니다. modern 서버도 여러 평범한 이유로 `400 Bad Request`로 답하기 때문입니다. 지원하지 않는 버전, 빠진 기능, 본문과 어긋나는 헤더 등이요. Dual-era 클라이언트는 modern 요청을 먼저 시도하고, 400이 오면 무엇을 결정하기 전에 응답 본문을 먼저 읽습니다. 그 본문에 인식 가능한 modern JSON-RPC 오류가 있다면 여전히 modern이라는 뜻이므로, 클라이언트는 폴백 대신 요청을 고치거나 지원되는 버전으로 재시도합니다. 비어 있는 본문이거나 인식 가능한 modern 오류로 파싱되지 않는 본문이면 legacy라는 뜻이고, 클라이언트는 오래된 핸드셰이크로 폴백하고, 거기서 더 나아가 Streamable HTTP 이전의 폐기된 전송 계층까지 내려가기도 합니다.

시대(era)는 단일 요청이 아니라 서버의 속성이므로, 클라이언트는 그 판단을 stdio에서는 연결 프로세스가 살아 있는 동안, HTTP에서는 오리진(origin) 단위로 캐시해야 하며, 같은 설정의 재시작을 넘어 그 가정을 유지할 수도 있습니다. 캐시된 가정이 나중에 틀린 것으로 드러나면 — 예컨대 서버가 업그레이드되어서 — 클라이언트는 낡은 답을 영원히 믿는 대신 다시 탐침을 보내도 됩니다.

한 가지 규칙이 더 있습니다. 그 혜택을 가장 적게 받는 사용자를 보호하는 규칙이기 때문에 알아 둘 가치가 있습니다. modern 버전만 말하는 서버라도, `initialize` 요청에 돌려 주는 모든 오류 안에 자기가 지원하는 버전들을 여전히 이름으로 밝혀야 합니다. 그 클라이언트에는 스스로 앞으로 나아갈(fall-forward) 경로가 없습니다. 사람에게 보여 줄 수 있는 유일한 진단 정보는 서버가 그 한 메시지에 담아 준 것뿐이기 때문입니다.

2026-07-28은 구버전 오프닝 시퀀스 전체를 통째로 제거했지, 좁혀 놓은 게 아닙니다. `initialize` 요청과 그 뒤를 따르던 `notifications/initialized` 알림은 사라졌습니다. 프로토콜 세션과 그것을 식별하던 헤더, 독립 GET 스트림과 그에 딸린 세션 해체(teardown), 그리고 `subscriptions/listen`으로 대체된 두 리소스 감시 메서드도 사라졌습니다. 살 곳을 잃은 세션 스코프 메서드들도 몇 개 있고, 이벤트 id 기반의 스트림 재개(resumability)도 사라졌으며, 서버는 클라이언트가 보낸 무언가에 대한 답장 외에 클라이언트를 향해 말을 걸 수 없게 되었습니다. 이 중 어느 것도 modern을 자처하는 전송 기록에 속하지 않습니다. 호환성 예제로 보여 줄 일이 생기면 그것이 무엇인지 분명히 표시하세요.

## 연습 랩

`code/main.py`를 열어 보세요. `LEGACY_EXAMPLES`가 `True`로 설정되어 있는데, 이 레슨에는 옛 방식의 오프닝 교환을 구성할 정당한 이유가 있습니다. Dual-era 클라이언트가 그쪽으로 폴백하는 모습을 보여 주고, modern 서버가 자기 버전들을 이름으로 밝히면서 그것을 거부하는 모습을 보여 주기 위해서입니다. 그런 메시지는 전송 기록에서 모두 `{"legacy": true, "message": {...}}`로 랩핑됩니다. 파일의 다른 모든 메시지는 평범한 modern 요청이나 결과이며 결코 랩핑되지 않습니다.

```bash
python3 code/main.py
```

데모는 서버 네 개를 만들고 각각을 같은 `DualEraClient`로 탐침합니다. `modern-server`는 `2026-07-28`만 지원하므로 첫 탐침이 곧바로 `DiscoverResult`를 반환합니다. `modern-other-version-server`는 이 랩을 위해 만들어진 순수 가상의 두 번째 modern 서버로, 재시도 경로를 볼 수 있게 가상의 더 나중 버전에 고정되어 있습니다. 첫 탐침이 `-32022`로 돌아오고, 클라이언트는 폴백 경로를 전혀 건드리지 않은 채 `data.supported`에 이름이 밝혀진 버전으로 자동 재시도합니다. `legacy-error-server`는 인식 못하는 메서드에 단순한 Method not found 오류로 답하는데, 클라이언트는 이를 올바르게 legacy로 읽습니다. `legacy-timeout-server`는 탐침에 아예 답하지 않는데, 클라이언트는 이것도 legacy로 읽습니다. 폴백이 어떤 특정 오류를 받는 것에 의존하지 않는다는 것이 증명됩니다. `modern-server`를 두 번째로 탐침해 보고 그 전후의 로그 길이를 비교하세요. 시대가 이미 캐시되어 있으므로 새로 보내는 것이 없습니다. 마지막으로 `modern-only-server`가 오래된 방식의 오프닝 요청을, 자기 지원 버전들을 나열하는 오류로 거부하는 모습을 지켜 보세요. modern 전용 서버가 그래야 하는 바로 그대로입니다.

## 제공되는 산출물

`outputs/era-compatibility-matrix.md`는 한 페이지짜리 참조 자료입니다. 개정판 연표, 세 가지 시대 용어, 나란히 놓인 stdio와 HTTP 탐침 알고리즘, 클라이언트와 서버 시대의 모든 조합에 대한 전체 호환성 매트릭스, 그리고 시험 전에 외워 둘 가치가 있는 몇 가지 사실이 담겨 있습니다. 여러분이 작성하지 않은 서버들과 접촉해도 살아남아야 하는 무언가를 만들 때 곁에 두세요.

레슨 33의 캡스톤 교환은 전부 modern 용어로 작성되어 있고 그 안 어디에도 탐침이 없습니다. 그것이 안전할 수 있는 이유는 이 레슨이 존재하기 때문입니다. 그 교환의 상류 어딘가에서 클라이언트가 이미 이 레슨이 가르치는 탐침을 실행했고, 그 연결을 modern으로 다뤄도 된다고 결정했기 때문입니다. 설계가 시대 감지를 건너뛰어도 되는 이유를 정당화하라고 요구받으면, 답은 가정이 아니라 이 레슨입니다.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| Modern | 버전과 기능이 요청별 메타데이터로 이동하는 개정판(2026-07-28 이후) |
| Legacy | 핸드셰이크로 연결을 열고 세션을 유지하는 개정판(2025-11-25 이전) |
| Dual-era | 두 시대를 모두 지원하는 구현체. 무엇을 파싱하기 전에 명시적으로 결정한다 |
| `initialize`(legacy) | 2026-07-28 이전에 구버전 연결을 열던 핸드셰이크. modern 시대에는 사라짐 |
| `server/discover` | Dual-era 클라이언트가 stdio에서 서버의 시대를 탐침할 때 쓰는 요청 |
| `DiscoverResult` | 서버를 modern으로 식별하고 지원 버전들을 나열하는 응답 |
| UnsupportedProtocolVersionError | 코드 -32022. 재시도를 유발하는 인식 가능한 modern 오류. 절대 폴백이 아님 |
| 시대 캐싱(Era caching) | 모든 요청마다 탐침하는 대신 서버 프로세스 또는 오리진별로 탐침 결론을 저장하는 것 |
| 호환성 매트릭스 | 클라이언트 시대와 서버 시대의 모든 조합에 대한 결과 표 |
| 400 본문 검사 | HTTP에서 legacy로 가정하기 전에 400 응답 본문에서 인식 가능한 modern 오류를 찾는 것 |
| Modern 전용 거부 | modern 전용 서버가 오래된 방식의 오프닝 요청을 거부하면서 자기 지원 버전들을 밝히는 것 |
