# 확장 프레임워크

> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [en.md](en.md)

> 확장(extension)은 어느 쪽도 지원할 의무가 없는 기능입니다. 필수 벤더 접두사로 이름 붙고, 모든 요청의 메타데이터에 매번 새로 선언되며, 무시해도 안전합니다. 그래서 핵심 프로토콜은 특정 벤더의 아이디어에 맞춰 늘어날 필요가 전혀 없습니다.

**유형:** 참고 자료
**언어:** Python
**선수 지식:** 레슨 29
**시간:** 약 45분

## 학습 목표

- 필수 벤더 접두사를 기준으로 잘 구성된 확장 식별자를 판별하고, 실존하는 공식 확장 하나와 실존하는 서드파티 확장 하나를 이름 댑니다
- 클라이언트가 어디서 확장 지원을 선언하고 서버가 어디서 자기 것을 선언하는지, 그리고 왜 둘 다 일회성 핸드셰이크가 아니라 요청별 `_meta`에 사는지 설명합니다
- 클라이언트가 요구하는 것과 서버가 실제로 지원하는 것으로부터, 그 요청에 활성인 확장 집합을 계산합니다
- 우아한 성능 저하(graceful degradation)를 적용합니다: 선택적 확장은 핵심 동작으로 폴백하고, 양쪽이 서로 활성화하지 못한 필수 확장이 필요한 요청은 거부합니다
- 확장의 수명 주기를 Extensions Track SEP에서 실험 저장소를 거쳐 공식 식별자에 이르기까지 추적하고, 새 식별자를 강제하는 것이 무엇인지 말합니다

## 문제 상황

MCP의 핵심 사양은 모든 구현이 온전히 지원할 수 있는 무엇이어야 합니다. 그 보장 덕분에 어떤 클라이언트든 한 번도 본 적 없는 서버를 발견하고 구동할 수 있는 것이죠. 그러나 실제 배포는 핵심이 모두를 위해 표준화할 리 없었던 것들을 원합니다: 텍스트 벽 대신 대화형 차트를 렌더링하는 도구, 느린 작업을 넘겨놓고 나중에 폴링하는 방법, 브라우저를 전혀 거치지 않는 머신 대 머신 인증, 일회용 도구 대신 재사용 가능한 플레이북을 게시하는 방법. 핵심이 이것들을 전부 흡수하면 사양은 끝나는 날이 없고, 2년 전에 지어진 서버는 — 자신이 요구한 적도 필요로 한 적도 없는 기능이 사양에 추가된 그날 — 조용히 MCP의 완전한 구현이 아니게 됩니다.

공유된 관례 없이 이런 기능들을 발명하는 것은 아예 없는 것보다 나쁩니다. 같은 문제 — 가령 서버가 UI를 렌더링하게 하기 — 를 푸는 두 벤더는 서로 다른 `_meta` 필드 이름을 고를 것이고, 클라이언트는 서버가 특정 필드를 이해하는지 물을 믿을 만한 방법이 없을 것이고, 보안 검토자는 그 필드가 대체 무슨 뜻인지 찾아볼 단일한 장소가 없을 것입니다. 구체적인 실패는 이렇게 생겼습니다: 어떤 서버 팀은 호출자가 쓸 수 있을 때 더 풍부한 응답을 도구가 돌려주길 원하지만, 기본 사양 어디에도 그 풍부함을 광고하는 방법이 없어서 오래된 클라이언트가 한 번도 본 적 없는 필드에 목이 메지 않게 할 수 없습니다. 그리고 어떤 클라이언트 팀은 어딘가 읽은 기능을 중심으로 요청을 꾸미기 전에, 이 특정 서버가 이 특정 호출에서 그 기능을 실제로 구현하는지 알고 싶어 합니다.

## 핵심 개념

MCP 확장은 사양에 대한 선택적 추가입니다: 핵심 프로토콜을 넘어서는 기능으로, 어느 쪽이든 구현할 수도 안 할 수도 있고, 무관한 벤더들이 절대 충돌하지 않도록 이름이 붙습니다. 식별자는 `{vendor-prefix}/{extension-name}` 형태이고, 접두사는 선택 사항이 아닙니다: 형식은 `_meta` 키와 같은 규칙을 따르지만, 여기서는 접두사가 필수입니다. MCP 자신이 유지보수하는 공식 확장은 `io.modelcontextprotocol` 접두사를 씁니다. 예컨대 `io.modelcontextprotocol/oauth-client-credentials`처럼요. 그 외에 확장을 만드는 모두는 자신이 실제로 통제하는 도메인 이름을 뒤집은 것을 써야 합니다 — Java 패키지가 쓰는 것과 같은 관례로, example.com을 소유한 회사는 `com.example/my-extension`을 게시합니다. 슬래시 없는 맨 단어는 애초에 유효한 확장 식별자가 아닙니다. 두 벤더를 구분해 줄 접두사가 없으니 아무도 협상할 수 없죠.

양쪽 모두 이 개정판의 다른 모든 것을 광고하듯 확장 지원을 광고합니다: 메시지에 붙는 데이터로, 결코 일회성 설정 단계가 아니요. 클라이언트는 주어진 호출을 위해 원하는 확장을 그 요청 자신의 메타데이터 안, `_meta["io.modelcontextprotocol/clientCapabilities"].extensions` 아래에 선언합니다. 식별자에서 설정 객체로 가는 맵입니다:

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {"location": "New York"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {
        "extensions": {
          "io.modelcontextprotocol/ui": {"mimeTypes": ["text/html;profile=mcp-app"]}
        }
      }
    }
  }
}
```

서버는 자신이 구현하는 확장을 `server/discover` 결과 안, `capabilities.extensions` 아래에 선언합니다. 같은 모양입니다:

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "resultType": "complete",
    "supportedVersions": ["2026-07-28"],
    "capabilities": {
      "tools": {},
      "extensions": {"io.modelcontextprotocol/ui": {}}
    },
    "ttlMs": 3600000,
    "cacheScope": "public"
  }
}
```

빈 설정 객체 `{}`는 완전하고 유효한 선언입니다: 설정할 것이 없는 채로 지원된다는 뜻이죠. 값이 채워진 객체는 그 특정 확장이 정의한 세밀한(fine-grained) 구성을 실습니다. 위의 `mimeTypes` 목록 같은 것이요. 이것이 `_meta`를 타고 모든 호출마다 다시 보내지므로, 어떤 요청에서 선언된 것이 다음 요청으로 넘어가는 것은 없습니다. 프로토콜 버전과 다른 모든 요청별 기능을 다스리는 바로 그 상태 없음(statelessness)이지, 확장을 위해 새로 지어낸 특별 사례가 아닙니다.

확장이 주어진 호출에 대해 활성(active)이 되는 것은 양쪽이 모두 그것을 이름 댈 때뿐입니다: 클라이언트가 이 요청에서 요구했고, 서버 자신의 capabilities가 그것을 구현한다고 말할 때요. 그 집합을 계산하는 것은 식별자 기준으로 두 맵의 교집합을 구하는 것이고, 형식이 잘못된 식별자 — 필수 접두사가 빠진 것 — 는 설령 우연히 양쪽에 나타나더라도 결과에 절대 속하지 않습니다. 식별자의 형태를 검증하는 것은 활성 집합 계산의 일부이지, 건너뛸 수 있는 별도 단계가 아닙니다.

그다음에 무엇이 일어나는지는 그 특정 호출에 대해 그 확장이 선택적이었는지 필수였는지에 달립니다. 선택적이라면 — 이미 동작하는 행위 위에 얹는 증강이니까 — 지원하는 쪽은 상대가 지원하지 않을 때 핵심 동작으로 폴백합니다. 대화형 대시보드를 렌더링할 수 있는 도구도 UI 확장을 선언하지 않은 클라이언트에게는 의미 있는 텍스트 콘텐츠를 돌려줍니다. 반면 그 호출에 그 확장이 필수라면 — 가령 클라이언트가 그것 없이는 폴링할 수 없는 내구성 있는 작업 핸들을 돌려주는 것처럼, 의미 있는 핵심 전용 동작이 없는 연산 — 요청은 절반만 답하는 대신 거부됩니다. 거부는 레슨 07이 빠진 클라이언트 기능 아무 거나 위해 소개한 바로 그 기능 게이트를 재사용합니다: `MissingRequiredClientCapabilityError`, `-32021`, 그 `data.requiredCapabilities`가 호출이 필요로 한 확장이 정확히 무엇인지 `{"extensions": {"<identifier>": {}}}` 모양으로 이름 대 줍니다. 이 오류에는 확장 전용 장치가 전혀 없습니다. 그저 평범한 요청별 기능 게이트가 핵심 기능 대신 확장 식별자에 적용된 것일 뿐입니다. 확장은 양쪽에서 모두 옵트인이기도 합니다: SDK가 완전한 프로토콜 적합성을 주장하는 데 어떤 확장도 구현할 필요는 절대 없고, 확장을 구현한다면 개발자가 명시적으로 켜기 전까지는 꺼진 채로 출시됩니다.

확장은 핵심 기능이 그렇듯 사양에 들어오지 않습니다. 메인 MCP 저장소에서 별개의 SEP 유형, 즉 Extensions Track SEP로 시작하고, Standards Track SEP와 달리 코어 메인테이너가 검토 자체를 시작하기 전에 공식 SDK 안에 동작하는 참조 구현이 이미 있어야 합니다. 승인되면 그 확장의 사양은 modelcontextprotocol GitHub 조직 안의 확장 저장소에서 삽니다. `ext-` 접두사로 이름 붙은 것으로, 인가 확장들의 `ext-auth`나 MCP Apps의 `ext-apps` 같은 것이죠. 코어 메인테이너가 그곳에 게시되는 모든 것에 대한 최종 권한을 유지하지만, 일상적인 변경은 그 저장소 자신의 메인테이너에게 위임되며 추가 핵심 검토가 필요 없습니다. 워킹 그룹이나 인터레스트 그룹은 아이디어가 SEP가 될 준비가 되기 전에 `experimental-ext-` 접두사로 이름 붙은 저장소 안에서 아이디어를 보육(incubate)할 수도 있는데, 비공식임이 명확히 표시되어 아무도 프로토타이핑을 약속으로 착각하지 않게 합니다. 코어 메인테이너는 여전히 자기 재량으로 이런 것들을 보관 처리하거나 제거할 수 있습니다.

확장은 핵심 프로토콜과, 그리고 서로와 독립적으로 버전이 매겨지고, 새 확장 릴리스에는 핵심 검토가 전혀 필요 없습니다. 단 하나의 엄격한 규칙이 파괴적 변경을 다룹니다: 필드를 제거하거나 이름을 바꾸는 것, 필드의 타입을 바꾸는 것, 기존 동작의 의미를 바꾸는 것, 새 필수 필드를 추가하는 것. 이들 중 어느 것도 옛 식별자 아래로는 출시될 수 없습니다. 확장은 대신 새 식별자를 얻습니다. 보통 접미사를 붙여서, `io.modelcontextprotocol/my-extension-v2`처럼요. 그래야 옛 식별자를 계속 선언하는 구현이 조용히 깨지는 대신 옛, 수정되지 않은 동작을 계속 얻습니다. 새 선택적 필드나 설정 객체 안의 버전 마커는 파괴적 변경이 아니며 새 식별자가 필요 없습니다.

오늘날 네 부류의 공식 확장이 존재합니다. Tasks(`io.modelcontextprotocol/tasks`, SEP-2663)는 레슨 21의 내구성 있는 작업 핸들입니다: 서버가 봉쇄(blocking)하는 대신 작업으로 요청에 답하고, 클라이언트가 그것을 폴링하죠. MCP Apps(`io.modelcontextprotocol/ui`, SEP-1865)는 도구가 텍스트만이 아니라 샌드박스 처리된 렌더링 가능한 인터페이스를 가리킬 수 있게 합니다. 다음에서 다루죠. Skills over MCP(`io.modelcontextprotocol/skills`, SEP-2640)는 서버가 재사용 가능한 워크플로 지침을 게시하고 클라이언트가 이미 갖고 있는 리소스 프리미티브를 통해 발견하고 읽을 수 있게 합니다. `resources/read`로 스킬의 `SKILL.md`를 읽는 것은 텍스트를 검색할 뿐입니다: 이 확장은 스킬 콘텐츠를 신뢰할 수 없는 입력으로 취급하고, 스킬이 애초에 모델 컨텍스트에 로드될지를 전적으로 명시적인 사용자 정책에 맡기며, 호스트에게 로드 전에 사용자가 스킬을 검사하게 하라고 알리고, 사용자가 그 권한을 승인하지 않는 한 MCP 서빙 스킬의 `allowed-tools` 같은 권한 확대 frontmatter는 무시합니다. 인가 확장들은 `ext-auth` 저장소에서 게시되며, 핵심 인가 모델 위에 OAuth의 클라이언트 자격 증명 흐름과 엔터프라이즈 관리 인가 프레임워크를 얹습니다. 이것들 모두에 대한 지원은 클라이언트마다 옵트인이고 독립적이므로, 확장 사이트는 어느 클라이언트가 어느 것을 구현하는지 계속 갱신되는 매트릭스를 유지합니다. 설계가 특정 확장의 존재에 기대기 전에 확인하세요. 실제 클라이언트와 백엔드 서버 사이에 앉는 게이트웨이는 그 백엔드에게 스스로가 클라이언트이고, 원래 호출자가 선언한 것을 그대로 전달하는 게 아니라 무엇을 선언할지 독립적으로 결정해야 합니다. 게이트웨이가 실제로 올바르게 중개할 수 없는 확장을 광고하는 것은 아예 광고하지 않는 것보다 나쁩니다.

이 개정판 이전에는 확장이 한 번만 선언됐습니다. `initialize` 요청의 `capabilities.extensions` 안에서 선언되고 `initialize` 응답에서 한 번 에코되며, 그 단일 선언이 연결의 나머지 동안 유지된다고 가정했죠. 당시 출시된 것의 기록으로 보존된 SEP-2133 자신의 역사적 문서도 여전히 그 형태를 보여 줍니다. 2026-07-28에는 연결 수명 핸드셰이크도 없고 선언을 호출 사이에 붙잡아 둘 곳도 없어서, 그 가정은 앞으로 이어지지 않습니다. 선언은 이제 모든 요청의 `_meta`를 타고 이동하고, 서버는 이번 호출에서 클라이언트의 확장 지원이 그것이 이전 호출에서 선언했던 것, 또는 다른 어떤 클라이언트가 선언했던 것과 일치한다고 가정해서는 안 됩니다.

```figure
mcpa-30-extension-negotiation
```

## 인터랙티브 랩

그림은 클라이언트가 선언한 확장과 서버가 선언한 확장을 나란히 놓습니다. 하나의 식별자, `com.example/priority-routing`은 양쪽 상자에 모두 나타나 가운데의 활성 상자로 수렴합니다: 이 호출은 강화된 동작을 얻습니다. `io.modelcontextprotocol/ui`는 클라이언트 쪽에만, `io.modelcontextprotocol/tasks`는 서버 쪽에만 나타납니다. 둘 다 수렴하지 않습니다. 협상은 양쪽이 같은 식별자를 이름 대야 하기 때문입니다. 그 아래 세 가지 결과가 개념 섹션과 나란히 놓입니다: 양쪽이 선언한 선택적 확장은 활성화되어 응답을 강화하고, 한쪽만 선언한 선택적 확장은 핵심 동작으로 폴백하며, 서로 활성화되지 못한 필수 확장은 `-32021`로 거부되며 빠진 것이 정확히 무엇인지 이름이 밝혀집니다.

## 실습 랩

`code/main.py`를 열어 보세요. `negotiate_extensions`는 하나의 함수에 담긴 메커니즘 그 자체입니다: 클라이언트가 선언한 확장을 훑으며 잘 구성된 것들 중 서버가 자신의 `extensions` 맵에도 올려 둔 것만 남기고, 그 교집합을 클라이언트의 설정 객체와 짝지어 돌려줍니다. 그 위에 두 도구가 놓입니다. `summarize_incidents`는 `com.example/priority-routing`을 선택적으로 취급합니다: 아무것도 선언하지 않고 호출하면 평범한 "3 open incidents"를 돌려주고, 확장을 빈 설정 객체로 선언해 호출하면 여전히 활성화되며 "standard" 등급이 기본이 됩니다 — `{}`가 '설정 없이 지원됨'을 뜻한다는 것이 실제로 이런 모습이라는 것이죠. `{"tier": "gold"}`로 선언하면 같은 도구가 그 등급을 위해 정렬합니다. `export_dataset`은 `com.example/bulk-export`를 필수로 취급합니다: 선언 없이 호출하면 서버는 인자조차 보지 않고 즉시 `-32021`과 그 확장을 이름 대는 `data.requiredCapabilities`로 답하고, 선언하고 호출하면 같은 호출이 정상적으로 완료됩니다.

```bash
python3 code/main.py
```

실행하고 여덟 개의 교환을 순서대로 따라가 보세요. 일곱 번째는 지어낸 식별자 `no-slash-here`을 유효한 것과 함께 선언합니다. 유효한 것은 여전히 활성화되는 동안 그것이 협상에서 조용히 떨어져 나가는 것을 지켜 보세요. 요청의 다른 어떤 것이 잘못 보이지 않을 때에도 `is_well_formed_extension_id`가 보장하려는 바로 그것입니다. 한 번에 두 확장을 요구하는 세 번째 도구를 추가해 보고, `_call`이 빠진 것 중 어느 쪽을 먼저 보고하는지 확인해 보세요.

## 완성 산출물

`outputs/extension-negotiation-guide.md`는 식별자 형식, 각 쪽의 선언이 회선 위 어디에 사는지, 선택적·활성 / 선택적·폴백 / 필수·거부를 위한 세 행짜리 결정 표, SEP에서 `ext-` 저장소까지의 수명 주기 체크리스트, 그리고 각자의 실제 식별자를 곁들인 공식 확장 명단을 요약본을 인용해 모아 놓습니다.

## 캡스톤 연결

캡스톤의 도구 생태계는 모든 설계 선택을 기본 사양에 대입해 정당화해야 하고, 확장은 정당화를 올바르게 해야 하는 선택 중 하나입니다: 어떤 동작이 도구의 핵심 응답에 속하는지, 호출자가 없을지도 모르는 확장 뒤에 속하는지, 그리고 없을 때 폴백이 어떤 모습인지. 캡스톤의 서버가 세 핵심 프리미티브를 넘어서는 무언가를 제공할 때마다 이 레슨의 활성 집합 계산과 `-32021` 거부를 집어 들고, 원하는 동작이 왜 핵심 사양에 단순히 직접 추가되지 않는지 설명해야 할 때마다 수명 주기 규칙을 집어 드세요.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 확장(Extension) | 핵심 프로토콜을 넘어서는 MCP의 선택적 추가. `{vendor-prefix}/{extension-name}`으로 식별된다 |
| 벤더 접두사(Vendor prefix) | 확장 식별자의 필수 네임스페이스. 공식 확장은 `io.modelcontextprotocol`, 그 외 모두는 뒤집은 도메인 이름 |
| 설정 객체(Settings object) | 기능 선언 안의 확장별 구성 값. `{}`는 설정할 것이 없는 채로 지원된다는 뜻 |
| 활성 확장 집합(Active extension set) | 주어진 요청이 실제로 협상한 식별자들. 클라이언트가 선언한 기능과 서버의 것 양쪽에 모두 존재한다 |
| 우아한 성능 저하(Graceful degradation) | 선택적 확장이 서로 활성화되지 않았을 때 요청을 실패시키는 대신 핵심 동작으로 폴백하는 것 |
| `MissingRequiredClientCapabilityError` | `-32021`. 호출이 확장 또는 임의의 기능을 필요로 하는데 이 요청의 `clientCapabilities`가 선언하지 않았을 때 돌아온다 |
| 확장 저장소(Extension repository) | modelcontextprotocol GitHub 조직 안의 `ext-` 접두사 저장소. 하나 이상의 공식 확장을 담는다 |
| 실험 확장(Experimental extension) | `experimental-ext-` 저장소에 있는 보육 중인 확장. 워킹 그룹이나 인터레스트 그룹에 묶여 있고 아직 공식 SEP가 아니다 |
