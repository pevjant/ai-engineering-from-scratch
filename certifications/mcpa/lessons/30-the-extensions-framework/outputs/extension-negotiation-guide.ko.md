# 확장 협상 가이드

MCPA '사용 사례와 생태계' 도메인을 위한 한 페이지 참고 자료입니다. MCP 2026-07-28 기준입니다.

## 식별자 형식

`{vendor-prefix}/{extension-name}`. 접두사가 필수입니다(`_meta` 키와 같은 규칙이되, 접두사를 생략할 수 없다는 점만 다름).

| 주체 | 접두사 | 예 |
|-----|--------|---------|
| 공식 확장 | `io.modelcontextprotocol` | `io.modelcontextprotocol/oauth-client-credentials` |
| 제3자 확장 | 작성자가 소유한 역방향 도메인 | `com.example/my-extension` |
| 잘못됨 | 접두사가 아예 없음 | `my-extension`(필수 슬래시와 접두사 누락) |

## 각 쪽이 지원을 선언하는 곳

| 쪽 | 위치 | 모양 |
|------|----------|-------|
| 클라이언트 | `params._meta["io.modelcontextprotocol/clientCapabilities"].extensions`, 모든 요청 위에 | 식별자에서 설정 객체로 가는 맵 |
| 서버 | `server/discover` 결과의 `capabilities.extensions` | 식별자에서 설정 객체로 가는 맵 |

빈 설정 객체, `{}`는 '지원됨, 설정할 것 없음'을 뜻합니다. 선언은 요청별입니다. 이전 호출에서 넘어오는 것은 아무것도 없습니다. 2026-07-28에는 `initialize` 핸드셰이크도, 그것을 담아 둘 세션도 없기 때문입니다.

## 협상 판단 표

| 클라이언트가 선언 | 서버가 선언 | 이 호출에 확장이 필수 | 결과 |
|---|---|---|---|
| 예 | 예 | 아니요(선택) | 활성: 강화된 동작이 돌아감 |
| 예 | 예 | 예 | 활성: 강화된 동작이 돌아감 |
| 아니요, 또는 잘못된 형식의 식별자 | 예 또는 아니요 | 아니요(선택) | 코어 동작으로 폴백 |
| 아니요, 또는 잘못된 형식의 식별자 | 예 또는 아니요 | 예 | 거부됨: `-32021 MissingRequiredClientCapability`, `data.requiredCapabilities`가 그것을 지목 |
| 예 | 아니요 | 어느 쪽이든 | 비활성: 서버가 구현한 적이 없으므로 돌아갈 수 없음 |

잘못된 형식의 식별자, 즉 필수 접두사가 없는 식별자는 마침 양쪽에 나타났더라도 활성화되지 않습니다. 식별자의 모양을 검증하는 것이 활성 집합을 계산하는 일의 일부입니다.

## 수명 주기 체크리스트

1. **제안**: 표준 SEP 가이드라인에 따라 메인 `modelcontextprotocol/modelcontextprotocol` 저장소의 Extensions Track SEP로 제안합니다.
2. **구현**: 공식 SDK 안의 동작하는 참조 구현. Core Maintainers가 검토 자체를 시작하기 전에 반드시 필요합니다.
3. **검토**: Core Maintainers가 SEP를 검토하고 수용에 대한 최종 권한을 쥡니다.
4. **게시**: 풀 리퀘스트가 확장 저장소, 즉 `modelcontextprotocol` GitHub 조직 아래 `ext-` 접두사로 지어진 저장소(예: `ext-auth`, `ext-apps`)에 그것을 추가합니다.
5. **채택**: 다른 클라이언트, 서버, SDK가 구현할 수 있습니다. 아무도 의무가 아닙니다.

SEP가 아예 존재하기 전에는 워킹 그룹이나 관심 그룹이 `experimental-ext-` 저장소에서 아이디어를 키울 수 있으며, 공식이 아니라고 명확히 표시됩니다. Core Maintainers는 재량으로 그것을 보관 처리하거나 제거할 수 있습니다.

확장은 코어 프로토콜과, 그리고 서로와, 독립적으로 버전이 매겨집니다. 파괴적인 변경(필드 제거나 이름 바꾸기, 필드 타입 변경, 기존 동작의 의미 변경, 새 필수 필드 추가)은 반드시 새 식별자 아래로 출시해야 합니다. 보통 `-v2` 접미사를 붙이는 식이며, 절대 옛 식별자 아래로 나오지 않습니다.

## 오늘날의 공식 확장

| 확장 | 식별자 | SEP | 한 줄 요약 |
|-----------|-----------|-----|----------|
| Tasks | `io.modelcontextprotocol/tasks` | SEP-2663 | 장기 실행 작업을 위한 내구적인 작업 핸들. 블로킹 대신 폴링 |
| MCP Apps | `io.modelcontextprotocol/ui` | SEP-1865 | 도구가 텍스트만이 아니라 샌드박스에 갇힌 렌더링 가능한 인터페이스를 가리킴 |
| Skills over MCP | `io.modelcontextprotocol/skills` | SEP-2640 | 리소스 프리미티브를 통해 재사용 가능한 워크플로 지침을 탐색하고 읽음 |
| OAuth Client Credentials | `ext-auth`에서 게시 | -- | 브라우저 없는 머신 간 인증 |
| Enterprise-Managed Authorization | `ext-auth`에서 게시 | -- | 기업 아이덴티티 제공자를 위한 중앙화된 접근 통제 |

이것들 모두의 지원은 클라이언트별 옵트인입니다. 설계가 특정 클라이언트가 이미 구현했다고 가정하기 전에 확장 사이트의 클라이언트 지원 매트릭스를 확인하세요.

## 시험을 위해 기억하기

- 확장 식별자의 접두사는 관례가 아니라 필수입니다.
- 선언은 요청별이며 `_meta`와 `server/discover`에 있습니다. 한 번 하는 핸드셰이크가 아닙니다.
- 선택 확장은 코어 동작으로 폴백합니다. 필수 확장이 서로 활성화되지 못하면 `-32601`이나 `-32602`가 아니라 `-32021`로 거부됩니다.
- 확장의 파괴적 변경에는 새 식별자가 필요합니다. 파괴적이지 않은 추가에는 필요 없습니다.
- 확장은 클라이언트와 서버 양쪽에서 기본적으로 비활성입니다. 코어 명세의 적합성이 그중 어떤 것의 구현도 요구하지 않습니다.
