# 일에 맞는 MCP 형태 고르기

> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [en.md](en.md)

> 네 가지 질문 — 누가 호출을 시작하는가, 데이터가 얼마나 민감한가, 작업이 얼마나 오래 도는가, 사람이 그것을 봐야 하는가 — 늘어진 요청을 프리미티브, 전송 방식, 인가 경로, 확장에 대한 구체적인 선택으로 바꿔 줍니다.

**유형:** 참고 자료
**언어:** Python
**선수 지식:** 레슨 28
**시간:** 약 45분

## 학습 목표

- 일곱 부류의 운영 사용 사례 — 개발자 도구, 데이터 접근, 엔터프라이즈 기록 시스템, 장기 실행 워크플로 자동화, 대화형 UI, 재사용 가능한 워크플로, 머신 대 머신 통합 — 을 각각에 맞는 MCP 프리미티브, 전송 방식, 확장에 대응시킵니다
- 도구, 리소스, 프롬프트 중에서는 "이 동작을 누가 통제하는가"를 물어서 고릅니다: 모델, 애플리케이션, 아니면 사용자
- MCP가 그 일에 잘못된 도구인 순간을 알아보고, 대신 무엇을 집어 들어야 하는지 말합니다
- 모든 사용 사례 설계가 답해야 하는 네 가지 운영 관심사 — 인가 경로, 캐시 범위, 동의, 관측 가능성(옵저버빌리티) — 에 대해 추론합니다
- `server/discover` 결과와 `tools/call` 교환을 읽고, 그 안의 캐시 힌트와 확장 선언을 그것을 만들어 낸 사용 사례로 되돌아 연결합니다

## 문제 상황

MCP의 메시지 형태를 배운 팀도 실제 프로젝트가 책상 위에 올라오는 순간 더 어려운 질문에 부딪힙니다: 이 일이 주어졌을 때, 프로토콜의 형태 중 무엇이 실제로 맞는가? 회선 규칙은 5초짜리 조회에도, 20분짜리 파이프라인에도 똑같이 적용되므로, JSON-RPC 봉투 자체는 선택을 강요하지 않습니다. 직관에 맡기면 두 가지 실수가 끊임없이 나옵니다. 어떤 팀은 모든 것에 도구를 집어 듭니다 — 호스트가 스스로 컨텍스트에 읽어 들이면 그만인 데이터까지. 그러면 모든 조회가 애플리케이션의 결정이 아니라 모델의 결정이 되고, 모든 답이 모델이 이름을 대고 요청해야만 하는 왕복 비용을 치릅니다. 다른 팀은 하나의 프로세스를 절대 벗어나지 않는 문제에 MCP를 기본 통합 계층처럼 취급합니다 — 통화 포맷터나 문자열 템플릿을 아무도 호출하지 않을 서버로 감싸고, 상호운용성 이점은 0인 채 프로토콜의 오버헤드만 지불하죠. 실제 운영 업무는 기본 메시지 형태가 저절로 풀어 주지 않는 관심사도 겹겹이 쌓아 옵니다: 아무도 지켜보지 않을 때 누가 호출을 인가하는가, 지난주의 캐시된 목록을 이 사용자에게 재사용해도 안전한가, 감사인이 결과를 그것을 만들어 낸 요청으로 어떻게 거슬러 올라가는가. 이 도메인은 수험생이 그 질문들에 답할 수 있는지 보는 시험 부분입니다 — 정답이 붙은 다이어그램이 아니라 일에 대한 설명만 듣고요.

## 핵심 개념

이 과정에서 이미 얻은 규칙에서 시작합니다: 도구는 모델이 통제하고, 리소스는 애플리케이션이 주도하며, 프롬프트는 사용자가 통제합니다. 그 구분이 사용 사례가 묻는 첫 번째이자 가장 큰 질문 — 이 기능이 실행된다고 결정하는 것은 누구인가 — 에 답합니다. 모델이 대화 도중에 집어 드는 코드 검색은 도구입니다. 모델이 답하기도 전에 호스트가 조용히 컨텍스트에 끼워 넣는 티켓의 현재 상태는 리소스입니다. 사용자가 메뉴에서 명시적으로 고르는 코드 리뷰 체크리스트는 프롬프트이고, 그 체크리스트가 사실 템플릿 하나가 아니라 보조 파일을 갖춘 카탈로그화된 다단계 절차라면, Skills over MCP 확장(`io.modelcontextprotocol/skills`)이 그 지침을 이 트랙이 이미 다루는 바로 그 `resources/read` 호출로 서빙합니다. `skills/list`와 `skills/get`으로 먼저 발견되는 것이죠.

설계를 완성하는 질문이 네 개 더 있습니다. 이것이 감싸는 시스템이 호스트와 같은 머신에 있는가, 아니면 어딘가 원격인가? 로컬 파일시스템이나 로컬 데이터베이스는 stdio로 답하고, stdio 구현은 OAuth 흐름을 아예 돌리지 않습니다 — 자격 증명을 환경에서 읽습니다. 원격 시스템은 Streamable HTTP로 답하고, 이제 인가가 그림에 들어옵니다: 리다이렉트를 승인하는 사람이 있는 경우 핵심 프레임워크의 대화형 OAuth 2.1 흐름을, 아무도 지켜보지 않는 백그라운드 작업은 OAuth 클라이언트 자격 증명 인가 확장(`io.modelcontextprotocol/oauth-client-credentials`)을, 중앙 ID 공급자를 둔 조직은 모든 직원에게 모든 서버를 개별 승인시키는 대신 Enterprise-Managed Authorization 확장(`io.modelcontextprotocol/enterprise-managed-authorization`)을 씁니다.

작업은 얼마나 오래 걸리는가? 하나의 요청-응답 쌍 안에 끝낼 수 있는 호출은 그냥 평범한 결과로 남습니다. 몇 분씩 돌지 모르는 배포 파이프라인이나 배치 임포트는 대신 tasks 확장(`io.modelcontextprotocol/tasks`)의 `CreateTaskResult`를 돌려줍니다. 클라이언트가 타임아웃을 향해 연결을 붙잡고 있는 대신 내구성 있는 `taskId`를 폴링하도록요:

```json
{
  "jsonrpc": "2.0",
  "id": 9,
  "result": {
    "resultType": "task",
    "taskId": "task_4471",
    "status": "working",
    "ttlMs": 3600000,
    "pollIntervalMs": 2000
  }
}
```

결과에 대화형 표면이 필요한가? 숫자나 짧은 단락은 그냥 평범한 콘텐츠로 남습니다. 사용자가 실제로 클릭해 보고 싶은 대시보드는 MCP Apps(`io.modelcontextprotocol/ui`)를 부릅니다 — 정의가 `ui://` 리소스를 가리키는 도구로, 호스트가 샌드박스 처리된 iframe 안에서 렌더링하는 것이죠. 다만 호출자가 확장을 선언했을 때만입니다:

```json
{
  "_meta": {
    "io.modelcontextprotocol/clientCapabilities": {
      "extensions": { "io.modelcontextprotocol/ui": {} }
    }
  }
}
```

이것을 잘 지원하는 서버는 그 블록을 선언하지 않은 호출자에게도 오류 대신 평범한 텍스트 콘텐츠로 답합니다. 확장 프레임워크가 양쪽 모두에게 기대하는 우아한 성능 저하(graceful degradation)입니다.

데이터는 얼마나 민감한가, 그리고 판단에 참여할 사람이 있는가? 민감한 결과는 그것을 만들어 낸 여섯 캐시 가능 연산 중 해당하는 것에 `cacheScope: "private"`을 실습니다. 그 자체로 접근 통제가 결코 아니고, 한 사용자의 캐시된 답을 다른 사용자에게 건네지 않겠다는 약속일 뿐입니다. 민감하거나 느린 동작에 사람이 곁에 있다면, 서버가 확정하기 전에 구체적인 세부를 확인하는 MRTR 엘리시테이션(elicitation)이 값을 합니다 — 이 트랙이 다른 곳에서 이미 만드는 재시도 패턴과 같은 맥락이죠. 아무도 없다면 호출은 이미 부여받은 범위 안에서 실행되고, 답할 엘리시테이션도 없습니다. 그러나 모든 경로는 감사인에게 똑같이 끝납니다: `_meta`의 트레이스 컨텍스트가 모든 홉을 넘어 호출을 따라가고, 감사 레코드는 토큰이 이름 대는 인증된 주체에 키가 매겨지지, 클라이언트가 무엇이든 넣을 수 있는 자기 보고식 `clientInfo`에 매겨지지 않습니다.

모든 일이 프로토콜 경계의 기준을 통과하는 것은 아닙니다. 하나의 프로세스를 절대 벗어나지 않는 기능 — 문자열 포맷팅, 숫자 반올림, 로컬 변수로 프롬프트 조립하기 — 에는 MCP의 상호운용성이 값을 정산해 줄 두 번째 소비자가 없고, 클라이언트와 서버가 그 사이에 설 만큼 별개의 시스템도 없습니다. 이런 것에 서버를 세우는 것은 이미 잘 동작하던 함수 호출 위에 JSON-RPC 봉투, 발견(discovery) 왕복, 인가 결정 하나를 얹는 것입니다. 위의 일곱 사용 사례 부류는 두 번째 소비자, 두 번째 호스트, 또는 지킬 가치가 있는 경계가 실제로 작동하는 경우들입니다. 그것들이 하나도 해당하지 않으면 라이브러리 호출이 정답이지, 부실하게 지은 MCP 서버가 아닙니다.

## 인터랙티브 랩

그림은 이 레슨의 카탈로그 항목 중 여섯 개를, 그것을 가장 뚜렷이 만드는 질문들과 나란히 놓습니다: 누가 프리미티브를 통제하는가, 어떤 전송 방식을 타는가, 어떤 확장(있다면)을 선언하는가. 먼저 개발자 도구 행을 따라가 보세요: 도구, stdio, 확장 없음 — 로컬 머신에서 모델이 촉발하는 코드 검색에는 자기 환경을 읽는 신뢰된 서브프로세스 이상이 필요 없으니까요. 그다음 아래 세 행을 따라가 보세요: 긴 작업이 tasks 확장을 끌어 오고, 대화형 대시보드가 ui 확장을 끌어 오고, 머신 대 머신 동기화가 OAuth 클라이언트 자격 증명 확장을 끌어 옵니다. 각 확장이 네 질문 중 서로 다른 하나 — 소요 시간, 대화형 여부, 인가할 사람의 존재 — 에 답한다는 것을 눈치채세요. 가운데 두 행, 데이터 접근과 재사용 가능한 흐름은 다른 프리미티브 구분을 보여 줍니다: 애플리케이션이 조용히 티켓 컨텍스트를 읽는 것은 리소스가 되고, 사용자가 명시적으로 체크리스트를 고르는 것은 프롬프트가 됩니다. 둘 다 같은 원격 전송을 타는데도요.

## 실습 랩

`code/main.py`를 열어 보세요. `CATALOG`는 여덟 개의 `UseCaseProfile` 항목을 담고 있습니다: 위의 일곱 사용 사례 부류 각각에 하나, 그리고 MCP가 전혀 맞지 않는 프로세스 내부(in-process) 경우 하나. `recommend()`는 각 프로필을 자기만의 `reasoning` 흔적을 실은 `Recommendation`으로 바꿉니다. 실행해 보세요:

```bash
python3 code/main.py
```

인쇄된 카탈로그를 위의 개념 섹션과 대조해 읽은 뒤, `run_scenario()`을 찾아 보세요. 이 함수는 하나의 `opsdesk` 서버를 `server/discover` 호출, `tools/list` 호출, 성공한 `search_internal_docs` 호출, 그리고 `usage_dashboard`에 대한 두 호출 — ui 확장을 선언하지 않은 호출 하나, 선언한 호출 하나 — 로 이끌고, 존재하지 않는 도구에 대한 호출로 끝냅니다. `tools/list` 결과는 `cacheScope: "private"`을 실는 반면 `server/discover`는 `"public"`을 실는지 확인하세요. 서버 자신의 기능 설명은 그 뒤에 있는 도구들이 민감하더라도 민감하지 않으니까요. 그다음 자신이 고른 사용 사례로 `CATALOG`에 아홉 번째 프로필을 추가해 보세요 — 가령 10분간 침묵 후 사람을 호출하는 모니터링 알림 — 필드를 채우고, 스크립트를 다시 실행하기 전에 `recommend()`가 무엇을 돌려줄지 예측해 보고, 인쇄된 추론과 자신의 예측을 대조해 보세요.

## 확인하기

레슨 디렉터리에서 테스트를 실행하세요:

```bash
python3 -m unittest discover code/tests
```

테스트는 이 레슨의 주장들을 확인합니다: 로컬 시스템은 환경 자격 증명을 곁들인 stdio 위의 도구를 추천한다, 애플리케이션이 시작한 경우는 리소스를 추천한다, 사용자가 시작한 템플릿은 프롬프트와 skills 확장을 추천한다, 긴 작업은 tasks 확장을 추천한다, 머신 대 머신 경우는 client credentials 확장을 추천한다, 대화형 대시보드는 텍스트 폴백을 곁들인 MCP Apps를 추천한다, 민감한 데이터는 private 캐시 범위를 추천한다, 공개 데이터는 public 캐시 범위를 추천한다, 엔터프라이즈 관리 배포는 엔터프라이즈 인가 확장을 추천한다, 외부 시스템이 없는 사용 사례는 MCP 자체를 추천받지 않는다, 데모 실행 기록의 discover와 list 결과는 올바른 캐시 힌트를 실는다, 대시보드 도구는 ui 확장 없이는 텍스트로 폴백한다, 알려지지 않은 도구는 프로토콜 오류이다, 메타데이터가 빠진 요청은 거부된다, 지원하지 않는 버전은 서버가 지원하는 버전들을 이름 대 준다. 저장소의 와이어 검사기도 이 레슨의 실행 기록을 2026-07-28 규칙과 대조해 검증합니다:


## 캡스톤 연결

캡스톤 준비도 검토는 끝까지 방어되는 하나의 설계를 요구합니다. 다섯 도메인을 따로따로 암송하는 것이 아니라요. 이 레슨이 그 방어의 출발점입니다: 시나리오가 주어지면, 메시지를 한 줄 쓰기 전에 프리미티브, 전송 방식, 인가 경로, 확장, 캐시 범위를 이름 대세요 — 이 레슨의 추천기가 코드로 답하는 바로 그 네 질문입니다. 캡스톤 시나리오가 중간에 장기 실행 단계나 대화형 결과를 끼워 넣으면, 위의 카탈로그처럼 tasks 확장이나 MCP Apps를 집어 들고, 시나리오의 어떤 조각이 결국 MCP를 전혀 필요로 하지 않으면, 서버를 억지로 둘러대는 대신 그렇게 솔직하게 말하세요.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 운영 사용 사례(Operational use case) | 설계가 MCP에 맞춰야 하는 구체적인 일: 개발자 도구, 데이터 접근, 엔터프라이즈 기록, 장기 자동화, 대화형 UI, 재사용 가능한 워크플로, 머신 대 머신 통합 |
| 통제 구분(Control split) | 도구는 모델이 통제하고, 리소스는 애플리케이션이 주도하며, 프롬프트는 사용자가 통제한다는 규칙 |
| Tasks 확장(Tasks extension) | `io.modelcontextprotocol/tasks`. 하나의 봉쇄(blocking) 요청으로는 너무 긴 작업에 내구성 있는 `taskId`를 돌려준다 |
| MCP Apps | `io.modelcontextprotocol/ui`. 도구 결과를 샌드박스 처리된 iframe 안의 대화형 표면으로 렌더링한다. 텍스트 폴백이 있다 |
| Skills over MCP | `io.modelcontextprotocol/skills`. 카탈로그화된 다단계 절차의 지침을 `resources/read`로 서빙한다 |
| 인가 확장(Authorization extension) | 핵심 대화형 흐름 너머의 옵트인 인가 경로. 무인 호출자에게는 client credentials, 중앙 ID 공급자에게는 enterprise-managed |
| cacheScope | 캐시 가능한 결과에 붙는 `public` 또는 `private` 표시. 인가 컨텍스트 간 공유를 제한한다. 그 자체로 접근 통제는 결코 아니다 |
| 우아한 성능 저하(Graceful degradation) | 호출자가 서버가 제공하는 확장을 선언하지 않았을 때, 서버가 핵심 동작으로 폴백하거나 명확한 오류로 거부해야 할 의무 |
