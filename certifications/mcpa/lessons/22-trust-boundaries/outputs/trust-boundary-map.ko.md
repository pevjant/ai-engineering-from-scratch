# 신뢰 경계 지도

MCPA '보안과 거버넌스' 도메인을 위한 한 페이지 참고 자료입니다. MCP 2026-07-28 기준입니다.

## 다섯 개의 구역

| 구역 | 정체 | 기본 신뢰 |
|------|------------|----------------|
| 사용자와 호스트 | 사람, 그리고 그 사람이 돌리는 애플리케이션 | 신뢰의 뿌리. 다른 모든 구역은 여기서 내린 선택으로부터 신뢰를 얻는다 |
| 클라이언트 | 호스트 안에서 하나의 서버와 대화하는 구성 요소 | 완전히 신뢰함. 호스트가 소유하고 끼워 넣은 것 |
| 서버 | 별도 프로그램. 흔히 제3자 것이며 로컬이거나 원격 | 기본적으로 신뢰하지 않음. 로컬 stdio 파이프 위라도 마찬가지 |
| 업스트림 시스템 | 서버 자신이 호출하는 대상들 | 신뢰하지 않으며, 보통 클라이언트에게는 전혀 보이지 않음 |
| 모델 | 조립된 컨텍스트를 읽는 언어 모델 | 모든 구역의 하류. 서버에서 온 콘텐츠는 지시문이 아니라 데이터로 취급해야 함 |

## 신뢰할 수 없는 채로 모델에게 들어가는 것들

- 도구의 `name`, `description`, `icons`, `annotations`
- `tools/call` 결과의 `content` 블록과 `structuredContent`
- `resources/read`의 텍스트와 blob 내용
- `server/discover`의 `instructions` 텍스트
- 위 어느 것 안에라도 끼어 있는 모든 것. 지시문처럼 보이는 텍스트 포함

## 적용할 규칙

- **스스로 보고한 식별 정보**: `clientInfo`와 `serverInfo`는 표시, 로깅, 디버깅 전용입니다. 신뢰 판단은 호스트가 자기 기록에 남긴 '어느 서버에 연결했는지'로 하지, 그 연결이 자칭하는 이름으로 하지 않습니다.
- **신뢰할 수 없는 어노테이션**: 선언한 서버가 호스트의 신뢰 목록에 있지 않다면 `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`를 신뢰하지 않는 값으로 취급합니다. 안전 판단에는 안전한 기본값(false, true, false, true)으로 떨어집니다.
- **아이콘 안전**: `https:`와 `data:` 아이콘 URI만 받습니다. `javascript:`, `file:`, `ftp:`와 그 밖의 스킴은 거부합니다. 자격 증명 없이 가져오고, SVG 페이로드는 실행 가능할 수 있는 것으로 취급합니다.
- **다중 서버 격리**: 한 서버의 콘텐츠 안에 끼어 있는 지시문이 그것만으로 다른 서버의 도구 호출을 정당화해서는 안 됩니다. 그 경계를 넘을 수 있는 건 모델이 스스로 내린 선택뿐이고, 그 선택조차 부수 효과가 있는 호출이라면 동의 게이트를 통과해야 합니다.
- **로컬 서버 동의(SEP-1024)**: 원클릭 로컬 서버 설치를 제공하는 클라이언트는 정확한 명령을 생략 없이 보여 주고, 실행 전에 명시적인 사용자 승인을 받아야 합니다.
- **DNS 리바인딩**: 로컬 HTTP 서버는 `Origin` 헤더를 검증해 알아볼 수 없는 것은 거부합니다. `127.0.0.1`에 닿은 요청을 전부 믿는 방식이 아니라요.
- **stdio 자격 증명**: 자격 증명은 환경에서 읽습니다. stdio 전송 위에서 OAuth 인가 흐름을 돌리지 않습니다.

## 경고 신호 체크리스트

- 도구 결과 콘텐츠에 다른 서버나 도구 이름을 지목하는 지시문이 들어 있다
- 아이콘 URI가 `https`나 `data`가 아닌 스킴을 쓴다
- 허용 목록에 없는 서버가 주장한 `destructiveHint: false`를 믿고 넘어간다
- 로컬 실행 명령을 호스트의 설정이 아니라 돌아온 콘텐츠에서 읽었다
- 로컬 HTTP 서버가 `Origin` 헤더와 무관하게 요청을 받아들인다
- `serverInfo.name`이 인가나 신뢰 판단 어딘가에 쓰였다

## 시험을 위해 기억하기

- `clientInfo`와 `serverInfo`는 절대 보안 판단이 아니라 표시일 뿐입니다.
- 도구 어노테이션은 보장이 아니라 힌트입니다. 호스트가 조금은 신뢰하는 서버에서 온 것이라도 마찬가지입니다.
- 로컬 서버 침해 시나리오는 SEP-1024의 동의 요구로 거슬러 올라갑니다.
- 서버를 넘나드는 끼워 넣은 지시문에 대한 해법은 호스트에서의 거부이지 JSON-RPC 오류가 아닙니다. 그 와이어 교환 자체는 완벽하게 유효할 수 있습니다.
