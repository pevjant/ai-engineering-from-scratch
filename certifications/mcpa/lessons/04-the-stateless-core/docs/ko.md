# MCP의 상태 비저장 코어

> 모든 요청은 서버가 답하기 위해 필요한 모든 것을 실고 옵니다. 이전 요청에서 물려받는 것은 아무것도 없습니다. 같은 연결 위에서조차요.

**유형:** 레퍼런스
**언어:** Python
**선수 지식:** 레슨 03
**시간:** 약 45분

## 학습 목표

- 상태 비저장성(statelessness)을 프로토콜 불변식으로 설명하기: 모든 요청은 스스로를 기술하며, 서버는 같은 연결 위의 이전 요청으로부터 기능, 버전, 정체를 추론해서는 안 된다
- 상태 비저장성이 운영상 왜 중요한지 설명하기: 어떤 레플리카든 어떤 요청이든 답할 수 있고, 재시도는 어디로든 안전하게 라우팅되며, 로드 밸런서에 스티키(sticky) 설정이 필요 없다
- 연결이나 stdio 프로세스와 세션/대화를 구분하고, 목록 결과가 연결 정체와 어떻게 관련되는지, 요청에 제시된 인가와는 어떻게 관련되는지 말하기
- SEP-2567 패턴을 따라, 클라이언트가 평범한 툴 인자로 되돌려 주는 명시적이고 불투명한(opaque) 서버 발급 핸들로 요청 간 상태 설계하기
- 2026-07-28이 상태 비저장을 기본값으로 만들기 위해 무엇을 제거했는지 찾아내고, 제거된 각 조각을 대신한 것 이름 말하기

## 문제 상황

2026-07-28 이전에는 MCP 서버에 연결을 열면 `initialize` 요청을 보내는 일이었습니다. 그 요청은 프로토콜 버전을 협상하고, 기능(capability)을 교환하고, 클라이언트와 서버의 정체를 기록했고, 그 결과는 연결이 유지되는 동안 세션 상태로 보관되었습니다. 그 연결 위의 이후 모든 요청은 핸드셰이크가 확립한 것에 기댔습니다. 서버는 "우리가 어떤 버전으로 이야기하고 있지?"나 "이 클라이언트가 무엇을 할 수 있지?"를 다시 물을 필요가 없었습니다. 기억하고 있는 한, 이미 알고 있었으니까요.

바로 그 기억이 문제입니다. 하나의 연결에 묶인 세션은 그 연결을 열어 두고 있는 프로세스에도 묶입니다. 평범한 로드 밸런서 뒤에 서버 플릿(fleet)을 두면, 클라이언트의 두 번째 요청이 첫 번째와 다른 레플리카에 도착할 수 있습니다. 그 레플리카는 핸드셰이크를 본 적이 없으니 어떤 버전과 기능에 합의했는지 전혀 모릅니다. 흔한 해결책은 스티키 라우팅이었습니다. 세션이 살아 있는 동안 클라이언트를 특정 백엔드 하나에 못 박는 것이죠. 스티키 라우팅은 그 백엔드가 재시작하거나, 새 버전을 배포하거나, 이웃이 놀고 있는데도 혼자 과부하에 걸릴 때까지는 동작합니다. 그 시점에 클라이언트의 세션 상태는 사라지고, 클라이언트는 다시 연결해서 핸드셰이크를 처음부터 다시 해야 합니다. 서버 작성자마다 클라이언트별 세션 상태를 만들고, 추적하고, 나중에 가비지 컬렉션하는 코드를 작성해야 했고, 클라이언트 작성자마다 끊긴 연결에서 살아남기 위한 코드를 짝지어 작성해야 했습니다. 이 복잡성의 어느 것도 서버가 하는 실제 작업과는 상관이 없었습니다. 세션이 만들어 낸 다음 필수로 만들어 버린 오버헤드였을 뿐입니다.

## 개념

MCP 2026-07-28은 상태 비저장 프로토콜입니다. 요청을 처리하는 데 필요한 모든 정보는 요청 자신 안에 들어 있습니다. 서버는 각 요청을 독립적으로 처리하며, 앞서 도착한 어떤 요청으로부터도 — 같은 연결이나 스트림 위로 온 것이더라도 — 기능, 프로토콜 버전, 클라이언트 정체를 추론해서는 안 됩니다. 레슨 03이 이미 그것이 의존하는 메커니즘을 보여 줬습니다. 모든 요청이 `params._meta`에 `io.modelcontextprotocol/protocolVersion`과 `io.modelcontextprotocol/clientCapabilities`를 실는다는 것. 그래서 누가 묻는지, 무엇을 지원하는지에 관한 정보는 요청 사이에서 기억될 필요가 전혀 없습니다.

```json
{
  "jsonrpc": "2.0",
  "id": 12,
  "method": "tools/call",
  "params": {
    "name": "add_item",
    "arguments": {"basket_id": "bsk_3f2a9c11", "sku": "tent"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
```

서버는 이 클라이언트를 한 번도 본 적 없어도, 그 사이에 무관한 요청 천 개를 처리한 프로세스에서도 이 요청에 답할 수 있고, 답은 동일할 것입니다. 이것이 요점 전부입니다. 요청은 "무엇을 할지"에 대한 완전하고 독립된 설명이기 때문입니다.

한 가지 귀결이 바로 따라옵니다. 열려 있는 연결은 대화가 아닙니다. stdio 프로세스나 HTTP 연결은 전송 계층(transport)이고, 전송 계층은 세션 경계가 아닙니다. 클라이언트는 서로 다른 작업, 서로 다른 사용자, 서로 다른 대화에 속한 무관한 요청들을 같은 전송 계층 위에 섞어서 보낼 수 있으며, 서버는 연결이나 프로세스의 정체를 대화의 연속성 대용으로 다뤄서는 안 됩니다. 하나의 stdio 프로세스가 어떤 사용자의 요청을 실은 직후 전혀 다른 사용자의 무관한 요청을 실을 수 있고, 서버는 같은 파이프로 도착했다는 이유만으로 둘이 한 세트라고 가정하지 않은 채 양쪽을 모두 올바르게 처리해야 합니다.

같은 규칙이 목록 결과를 형성합니다. `tools/list`, `resources/list`, `prompts/list`는 누가 어떤 연결로 물었는지에 따라 달라져서는 안 되며, 서버는 그 목록들이 반환하는 내용을 다른 요청의 부수 효과로 바꿔서도 안 됩니다. 구버전 시절 서버가 그랬던 것처럼, 같은 연결에서 먼저 `connect_database`가 호출된 뒤에야 `query`가 `tools/list`에 나타나게 만드는 식으로요. 목록은 진짜 이유가 있으면 달라져도 됩니다. 요청 자신이 제시하는 인가입니다. 더 낮은 권한의 토큰에게 더 적은 툴을 반환하는 서버는 그 스코프(scope)를 현재 요청에서 읽는 것이고, 이것이야말로 상태 비저장성이 요구하는 그대로입니다. 결코 해서는 안 되는 것은, 같은 연결 위의 이전 요청이 선언했던 것에 대한 기억에서 그 스코프를 읽는 일입니다.

상태 비저장성은 운영상 무엇을 사다 주는지 때문에 그 규율을 치를 가치가 있습니다. 어떤 요청도 프로세스 메모리에 보관된 것에 의존하지 않으므로, 로드 밸런서 뒤의 어떤 레플리카든 어떤 요청이든 답할 수 있습니다. 평범한 라운드 로빈 라우팅이 동작하고 스티키 세션이 불필요해집니다. 도중에 실패한 요청은 다른 레플리카를 향해 안전하게 재시도할 수 있습니다. 재시도에 이전 상태를 기억하는 단 하나의 프로세스를 찾아낼 필요가 없기 때문입니다. 충돌하거나 재시작한 레플리카는 프로토콜에 중요한 것을 아무것도 잃지 않습니다. 프로토콜에 중요한 것은 애초에 거기 저장되지 않았기 때문입니다.

이것이 서버가 아무것도 기억할 수 없다는 뜻은 아닙니다. 쇼핑 바구니, 열려 있는 브라우저 컨텍스트, 장기 실행 작업 모두 둘 이상의 툴 호출에 걸쳐 살아남아야 하고, MCP는 그것을 암묵적인 세션이 아니라 명시적이고 서버가 발급한 핸들(handle)로 다룹니다. 생성 툴이 불투명한 식별자를 발급(mint)해서 `structuredContent`로 반환하고, 모델이 그 식별자를 계속 들고 있다가, 필요할 때마다 평범한 인자로 되돌려 주는 것이죠.

```json
// tools/call: create_basket
{"name": "create_basket", "arguments": {}}

// result
{
  "content": [{"type": "text", "text": "Created basket bsk_3f2a9c11"}],
  "structuredContent": {"basket_id": "bsk_3f2a9c11"},
  "resultType": "complete"
}
```

`basket_id`에 관한 어떤 것도 프로토콜 기능이 아닙니다. 툴 결과 속 평범한 문자열이고 툴 인자 속 평범한 문자열이며, 와이어 입장에서는 툴이 반환하는 다른 어떤 데이터와도 구별되지 않습니다. 핸들을 잘 동작하게 만드는 설계 지침은 프로토콜이 강제하지 않으므로 서버 작성자의 몫입니다. 핸들은 클라이언트가 파싱하거나 추측할 수 있는 구조를 인코딩하지 말고 불투명하게 유지할 것. 모든 호출에서 호출자를 그 핸들에 대해 인가할 것. 이름을 갖고 있다는 것이 그것을 쓸 수 있다는 뜻은 아니기 때문입니다. 그리고 생성 툴의 설명에 핸들의 수명을 밝혀서, 모델이 상태를 만들기로 결정하기 전에 정책을 볼 수 있게 할 것. 만료되었거나, 존재한 적 없거나, 다른 호출자에게 속한 핸들로 호출이 도착하면, 올바른 응답은 툴 실행 오류입니다. 즉 문제를 이름으로 밝히는 `isError: true`를 담은 정상 결과이지 JSON-RPC 프로토콜 오류가 아닙니다. 만료되었거나 남의 핸들은 모델이 새 바구니를 만들어 복구할 수 있는 비즈니스 결과이지, 잘못된 요청이 아닙니다.

이것은 여러 서브에이전트를 구동하는 오케스트레이터에게 중요한 질문에도 답합니다. 목록 결과는 누가 어떤 연결로 물었는지에 따라 달라질 수 없으므로, 같은 인증된 주체(principal)에 속한 두 번째 연결, 예컨대 오케스트레이터가 띄운 서브에이전트의 연결은 오케스트레이터가 본 것과 정확히 같은 `tools/list` 결과를 보며, 다시 묻는 대신 캐시된 사본을 안전하게 재사용할 수 있습니다. 세션 스코프의 목록 결과는 그런 보장을 절대 제공할 수 없었습니다. 세션의 존재 이유 자체가 하나의 특정 연결에 묶이는 것이었으니까요.

상태 비저장을 기본값으로 만들기 위해서는 상태 저장성(statefulness)이 의존하던 장치들을 제거해야 했습니다. 오프닝 핸드셰이크는 없습니다. `initialize` 요청과 `notifications/initialized`는 모두 사라지고, 요청별 `_meta`와 레슨 03의 선택적 `server/discover` 호출로 대체되었습니다. `Mcp-Session-Id` 헤더도 없습니다. 헤더가 가리킬 세션이 없기 때문입니다. 기능(capability)은 더 이상 연결에 스코프를 두지 않습니다. 모든 요청에서 새로 선언되므로, 서버는 세 요청 전에 기억한 기능이 아직 유효한지 궁금해할 일이 없습니다.

## 인터랙티브 랩

그림은 alice와 bob이라는 두 클라이언트가 라운드 로빈 라우터를 거쳐 A, B 두 레플리카로 요청을 보내는 모습을 보여 줍니다. 어느 레플리카도 바구니 상태를 메모리에 보관하지 않습니다. 둘 다 같은 공유 스토어를 읽고 쓰며, 키는 생성 툴이 반환한 불투명 핸들입니다. 그래서 라우터가 다음으로 무엇을 고르든, 직전 호출을 어떤 레플리카가 처리했든 상관없이 올바르게 답합니다. 하나의 바구니가 생성된 뒤 다른 레플리카에 도착하는 호출까지 이어지는 과정을 따라가 보세요. 답은 변하지 않고, 그 교환에서 서로 다른 두 프로세스가 관여했다는 힌트는 아무것도 드러나지 않습니다.

## 연습 랩

`code/main.py`를 열어 보세요. 하나의 `SharedStore`를 공유하는 레플리카 두 개와, 라운드 로빈으로 요청을 분배하는 `Router`를 만들고, 그 배포를 향해 세 명의 호출자를 돌립니다. alice, 같은 주체를 가진 alice의 두 번째 연결, 그리고 완전히 다른 주체인 bob입니다.

```bash
python3 code/main.py
```

출력된 교환을 개념 절과 대조하며 읽으세요. alice의 첫 번째 연결과 두 번째 연결은 `tools/list`를 호출하고 동일한 툴 목록을 돌려받습니다. 라운드 로빈 라우터가 서로 다른 두 레플리카로 답했는데도요. 각 결과의 `_meta`를 읽어 보면 `serverInfo.name`이 `basket-replica-A`와 `basket-replica-B` 사이에서 바뀌는 동안 `tools` 배열 자체는 바이트 단위로 완전히 같다는 것을 확인할 수 있습니다. alice가 한 레플리카에서 바구니를 만들고, 라우터가 우연히 다른 레플리카로 보내는 호출로 그 바구니에 물건을 추가하는 모습을 지켜 보세요. 바구니가 어느 레플리카의 메모리가 아니라 공유 스토어에 살고 있기 때문에 물건은 올바르게 추가됩니다. 그다음 일부러 만든 두 가지 실패를 찾아 보세요. bob은 alice의 바구니에 물건을 추가하려다가, 그 바구니가 다른 주체에게 속한다고 설명하는 `isError: true`를 담은 정상 결과를 돌려받습니다. 이후 시나리오의 시계가 바구니의 수명을 지나자, alice의 두 번째 연결이 같은 바구니를 결제하려고 시도했다가 이번에는 바구니가 만료되었다고 설명하는 `isError: true`를 다시 받습니다. 어느 쪽 실패도 JSON-RPC 오류가 아닙니다. 둘 다 모델이 행동에 옮길 수 있는 결과이기 때문입니다. 새 바구니를 만들고 계속 진행하면 되죠.

## 캡스톤 연결

캡스톤의 엔드투엔드 교환은 어떤 레플리카가 어떤 요청에 답하든 동작해야 하고, 그 장기 실행 작업과 동의(consent) 흐름은 둘 이상의 왕복에 걸쳐 살아남아야 합니다. 둘 다 이 레슨 위에 서 있습니다. 서버가 소유하는 상태는 프로토콜 계층에 아예 존재하지 않거나, 클라이언트가 자기 요청들을 통해 실어 나르는 명시적 핸들로 참조되어야 한다는 것이죠. 캡스톤이 설계가 수평 확장에 안전한 이유를 정당화하라고 요구하면, 여러분은 상태 비저장 코어와, 세션 없이도 상태가 존재할 수 있게 해 주는 핸들 패턴으로 거슬러 올라가 근거를 대게 됩니다.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 상태 비저장성(Statelessness) | 모든 요청이 스스로를 기술하며 이전 요청과 독립이라는 프로토콜 불변식 |
| 연결(Connection) | 전송 계층의 채널(stdio 프로세스 또는 HTTP 연결). 세션이나 대화가 아니다 |
| 레플리카(Replica) | 서로 교체 가능한 여러 서버 프로세스 중 하나. 사유 상태를 갖지 않으므로 어떤 요청이든 답할 수 있다 |
| 서버 발급 핸들(server-minted handle) | 생성 툴이 반환하는 불투명 식별자로, 호출들 사이에서 상태를 참조하려고 평범한 인자로 되돌려 준다 |
| 공유 스토어(Shared store) | 모든 레플리카가 읽고 쓰는 내구성 있는 저장소. 상태가 어느 한 프로세스 안에 살지 않게 한다 |
| 툴 실행 오류 | `isError: true`를 담은 정상 결과. 만료되었거나, 알 수 없거나, 남의 핸들에 대한 올바른 채널 |
| `Mcp-Session-Id` | 프로토콜 수준 세션을 가리키던 구버전 헤더. 2026-07-28에서 제거됨 |
