# 모든 MUST에는 책임자가 필요합니다

> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [en.md](en.md)

> 사양은 자신의 MUST를 호스트, 클라이언트, 서버에게 넘깁니다. 그러나 실제 배포는 그것을 사람들에게 넘깁니다. 그리고 아무도 맡겠다고 손을 드지 않은 MUST가 가장 먼저 무너지는 MUST입니다.

**유형:** 참고 자료
**언어:** Python
**선수 지식:** 레슨 27
**시간:** 약 45분

## 학습 목표

- 실제 MCP 배포 뒤에 있는 여섯 역할 — 서버 작성자, 호스트·클라이언트 개발자, 플랫폼 또는 게이트웨이 운영자, 보안·거버넌스 담당자, 레지스트리 게시자, 최종 사용자 — 각각이 실제로 소유하는 사양 요구사항을 배정합니다
- 세 가지 도입 경로, 즉 로컬 stdio, OAuth를 곁들인 원격 Streamable HTTP, 게이트웨이 앞세운 엔터프라이즈 배포를 따라가며, 같은 요구사항의 책임자가 어떻게 바뀌는지 추적합니다
- MCP 거버넌스 구조를 설명합니다: Agentic AI Foundation 아래의 운영(stewardship), 리드 메인테이너·코어 메인테이너·메인테이너 위계, 워킹 그룹과 인터레스트 그룹의 차이
- 하나의 제안이 아이디어에서 SEP 워크플로를 거쳐 Final 지위에 이르는 과정을 따라가고, 그 워크플로를 요구사항이 출시된 뒤 거치는 기능 수명 주기와 연결합니다
- SDK 등급(tier) 선택을 체크박스가 아니라 역할이 내리는 도입 결정으로 다룹니다. 등급 시스템의 적합성(conformance) 및 응답 시간 약속을 읽고서요

## 문제 상황

사양을 끝까지 읽으면 참여자 셋이 나옵니다: 호스트, 클라이언트, 서버. 실제 MCP 도입을 끝까지 읽으면 최소 여섯 부류의 사람이 나오고, 조직도 어디에도 "호스트"라는 이름은 없습니다. 누군가는 서버를 쓰고 유지보수합니다. 또 누군가는 호스트 애플리케이션과 그 안의 클라이언트를 만들거나 설정합니다. 세 번째 직능은 프로덕션(운영 환경)에서 프로세스를 구동합니다 — 공유 머신에서 stdio 서브프로세스를 띄우든, 원격 연결을 종단하는 리버스 프록시를 운영하든. 네 번째 직능은 배포가 토큰, 스코프, 로그로 무엇을 할 수 있는지 검토합니다. 다섯 번째는 다른 팀이 서버를 찾을 수 있게 게시합니다. 여섯 번째, 최종 사용자는 도구가 실행되기 직전 실제로 동의를 누르는 사람입니다.

사양의 모든 MUST와 SHOULD는 그 여섯 직능 중 하나에 떨어지지만, 사양은 어느 것인지 말해 주지 않고, 말해 줄 수도 없습니다: 같은 프로토콜이 stdio로 로컬 도구를 돌리는 1인 개발자도, 게이트웨이로 수십 개의 내부 서버를 앞세운 플랫폼 팀도 지원하기 때문입니다. Origin 헤더 검증 같은 요구사항의 올바른 책임자는 두 경우에서 같은 사람이 아닙니다. "사양이 서버에게 MUST라고 한다"를 저절로 지켜질 일로 취급한 팀은, 보통 보안 검토 때 뼈아프게 배웁니다. 이름이 붙지 않은 MUST는 실제로 아무도 하지 않은 MUST라는 것을요. 이것이 Use Cases and Ecosystem 도메인을 암기 문제가 아니라 시나리오 문제로 시험하는 부분입니다: 배포 형태가 주어지면, 요구사항만이 아니라 역할을 이름 대세요.

## 핵심 개념

여섯 직능에 이름을 붙이면 시험의 역할 문제가 추상적이지 않게 됩니다. 서버 작성자는 사양 — 버전 2026-07-28 — 을 기준으로 하나의 구현을 쓰고 유지보수합니다: 어떤 도구가 존재하는지, 각 입력 스키마가 무엇을 요구하는지, `server/discover`가 어떻게 답하는지. 호스트·클라이언트 개발자는 사람이 실행하는 애플리케이션과, 그 안에서 회선 프로토콜을 말하는 클라이언트를 만듭니다: 기능(capability) 선언, 전송 방식이 원격일 때의 OAuth 클라이언트, 호출이 나가기 전 사용자가 보는 동의 화면. 플랫폼 또는 게이트웨이 운영자는 프로세스를 구동합니다: 올바른 환경으로 stdio 서브프로세스를 띄우거나, Streamable HTTP 연결을 종단하고, 네트워크 정책을 적용하고, 요청이 서버 구현에 닿기 전에 게이트웨이가 무엇을 검사할지 정합니다. 보안·거버넌스 담당자는 위의 모든 것을 가로지르는 요구사항, 즉 토큰 처리, `requestState` 보호, 동의 정책, 그리고 어느 한 구현자에게 깔끔히 귀속되지 않는 공통(cross-cutting) MUST에 대해 책임 집니다. 레지스트리 게시자는 `server.json`, 그것이 주장하는 네임스페이스, 그리고 레지스트리가 서비스하는 항목이 정확한지를 소유합니다. 최종 사용자는 호스트가 자기를 대신해 하는 일에 대한 책임 당사자이고, 사양이 "사람이 호출을 거부할 수 있어야 한다"고 말할 때마다 조용히 지켜 주는 바로 그 역할입니다.

이것은 아키텍처 레슨의 호스트·클라이언트·서버 역할을 대체하지 않습니다. 그 위에 얹히는 것이고, 작은 팀에서는 한 사람이 여섯 직능 중 둘이나 셋을 맡을 수도 있습니다. 시험에 중요한 것은 하나의 요구사항이 배포가 성장하면서 직능 사이를 이동할 수 있다는 점입니다. 이 도메인이 기대하는 세 가지 도입 경로를 따라 하나의 요구사항을 추적해 봅시다: 로컬 stdio, OAuth를 곁들인 원격 Streamable HTTP, 확장(extensions)을 곁들인 게이트웨이 앞세운 엔터프라이즈 배포. Streamable HTTP 전송은 DNS 리바인딩 공격을 막기 위해 서버가 모든 인커밍 연결에서 Origin 헤더를 검증해야 한다(MUST)고 명시합니다. 서버를 공개 인터넷에 바로 세우면 그 MUST는 서버 작성자에게 떨어집니다. 소켓과 요청 핸들러 사이에 서 있는 코드가 서버 자신의 코드뿐이기 때문입니다. 같은 서버를 엔터프라이즈 게이트웨이 앞에 세우면 MUST는 사라지지 않고 이동합니다: 이제 Origin 헤더를 처음 보는 코드가 플랫폼/게이트웨이 운영자의 엣지이므로 운영자가 제대로 해야 하고, 서버 작성자의 일은 이제 남이 강제하는 네트워크 경계를 신뢰하는 것으로 좁아집니다. 큐레이션된 요구사항 레코드로 만든 책임 매트릭스는 이것을 추적해야 합니다: 요구사항은 고정, 형태는 바뀌고, 책임자는 그에 따라 바뀝니다.

같은 규율이 stdio에도 적용됩니다. STDIO 전송을 쓰는 구현은 OAuth 인가 흐름을 따르지 않는 것(SHOULD NOT)이 맞고 대신 환경에서 자격 증명을 가져오므로, stdio 배포는 호스트·클라이언트 개발자에게 OAuth 클라이언트 만들기를 요구하지 않습니다. 대신 플랫폼/게이트웨이 운영자에게 — 노트북 한 대라면 프로세스를 띄우는 그 사람에게 — 서브프로세스가 시작되기 전에 올바른 자격 증명이 이미 환경에 들어 있도록 확인하라고 요구합니다. 이 소유권 질문을 건너뛰면 stdio 도구는 자격 증명이 필요한 첫 호출에서 실패하거나, 더 나쁘게는 아무도 검토하지 않는 설정 파일에 누군가 자격 증명을 박아 넣습니다.

거버넌스는 관련되었지만 별개의 질문에 답합니다: 하나의 MUST가 다음에 무엇이 될지는 누가 정하나. MCP는 Agentic AI Foundation의 프로젝트이고, 기술 방향은 작은 위계를 통과합니다. 리드 메인테이너(Lead Maintainers)는 최종 거부권을 쥡니다. 코어 메인테이너(Core Maintainers)는 사양과 프로젝트 전체 방향을 조종합니다. 메인테이너(Maintainers)는 각자 하나의 특정 영역 — 어떤 SDK, 문서, 또는 워킹 그룹 — 을 운영합니다. 기여자(Contributors)는 이슈나 풀 리퀘스트를 여는 모든 사람이고, 꾸준한 기여자는 멤버(Members)가 되며, 6개월 이상된 멤버는 후원자와 코어 메인테이너의 승인으로 메인테이너가 될 수 있습니다. 이 기간들은 최소치이지 보장이 아닙니다. 그 층들 사이에서 협업을 수행하는 두 부류의 그룹이 있습니다. 인터레스트 그룹(Interest Group)은 문제를 토론하고 구속력 없는 권고, 사용 사례, 요구사항을 만듭니다. 아무도 설계에 약속하기 전에 "MCP가 이것을 지원해야 하나"를 꺼내는 자리죠. 워킹 그룹(Working Group)은 구체적인 산출물을 만듭니다. 보통 사양 개선 제안(SEP, Specification Enhancement Proposal)과 그 참조 구현이고, 아이디어가 엔지니어링 시간을 들일 만큼 지지를 받았을 때입니다. SEP는 `draft`, `in-review`를 거쳐 `accepted` 또는 `rejected`로 이동하고, 승인된 Standards Track SEP는 참조 구현이, 그리고 관찰 가능한 프로토콜 동작이 있는 것이라면 적합성 테스트까지, 둘 다 착지하기 전까지는 `final`이 아닙니다. 이것은 사양 읽기 레슨의 그 기능 수명 주기와 같은 것으로, 요구사항이 은퇴하는 순간이 아니라 태어나는 순간에 적용한 것입니다: 기능은 Active가 되고, 선택적으로 필수 마이그레이션 경로와 최소 기간을 두고 Deprecated가 되며, 언젠가 Removed가 됩니다.

SDK 등급은 이 레슨이 역할에게 넘기는 마지막 도입 결정입니다. 보통은 기반으로 삼을 것을 고르는 호스트·클라이언트 개발자나 서버 작성자죠. Tier 1 SDK는 적합성 테스트 100퍼센트를 통과하고, 사양 릴리스와 함께 또는 그보다 먼저 새 프로토콜 기능을 출시하며, 이슈를 2영업일 안에 분류(triage)하고, 치명적인 버그를 7일 안에 고칩니다. Tier 2는 더 긴 시계로 같은 목적지를 약속합니다: 80퍼센트 적합성과 새 기능에 6개월의 여유. Tier 3은 명시적으로 실험적이며 타임라인 약속이 전혀 없습니다. 프로덕션 게이트웨이에 Tier 3 SDK를 고르는 것은 기술적 지름길이 아니라 그 SDK의 유지보수 위험을 떠안기로 하는 결정이고, 그렇게 — 이름을 붙여 — 말할 수 있는 수험생은 이 도메인이 묻는 시나리오 문제에 답하고 있는 것입니다.

## 인터랙티브 랩

그림은 세 개의 패널을 나란히 놓습니다: 로컬 stdio 배포, 게이트웨이 없는 평범한 원격 HTTP 배포, 그리고 같은 서버에 게이트웨이가 앞에 놓인 모습. 각 패널은 그 형태의 요구사항 표본을 소유하는 역할을 이름 붙입니다. 표시된 행이 움직이는 것을 보세요. 평범한 HTTP에서는 서버 작성자가 Protected Resource Metadata 바로 옆에서 Origin 검증을 소유합니다. 게이트웨이를 추가하면 표시된 행이 플랫폼/게이트웨이 운영자로 뛰어갑니다. 이제 요청이 처음 닿는 것이 게이트웨이이기 때문입니다. 두 번째 패널과 세 번째 패널 사이에서 근본적인 MUST는 아무것도 바뀌지 않았습니다. 바뀐 것은 어느 패널, 어느 배포 형태가 그것을 주장할 수 있는가입니다.

## 실습 랩

`code/main.py`를 열어 보세요. `REQUIREMENTS`는 큐레이션된 `Requirement` 레코드들의 튜플이고, 각 레코드는 요약본이나 사양에서 그대로 인용한 정확한 MUST 또는 SHOULD에, 적용되는 배포 형태와 기본 책임자 역할을 태그로 붙인 것입니다. `build_responsibility_matrix(shape)`는 카탈로그를 하나의 형태로 걸러 내고, 적용 가능한 각 요구사항에 책임자를 배정하며, 책임자가 `None`인 MUST는 `gaps` 목록에 모읍니다. 실행해 보세요:

```bash
python3 code/main.py
```

세 형태의 매트릭스를 나란히 인쇄한 것을 읽어 보세요. `stdio-env-credentials`는 플랫폼/게이트웨이 운영자에게 떨어지는지, `prm-implemented`는 `http`와 `gateway` 양쪽 모두에서 서버 작성자에게 떨어지는지, 그리고 `origin-validation`이 두 형태 사이에서 책임자가 바뀌는 유일한 행인지 — `http`에서는 `server_author`, `gateway`에서는 `platform_gateway_operator` — 확인하세요. 그다음 `error-code-allocation`을 보세요. 이것의 `default_role`은 의도적으로 `None`입니다. 요약본 5절의 MUST NOT으로, 여섯 역할 중 어느 하나에 깔끔히 대응되지 않고, 매트릭스는 어떤 형태에 적용해도 이것을 gap으로 보고합니다. 자신만의 열세 번째 `Requirement`를 추가해 보세요 — 이미 읽은 레슨에서 하나 골라서, 여섯 역할 중 누가 소유해야 하는지 정하고, 적용되는 형태에 태그를 붙이고, 스크립트를 다시 실행해 추가한 것이 매트릭스에서 자리를 잡는지 보세요.

## 완성 산출물

`outputs/roles-responsibility-matrix.md`는 한 페이지짜리 현장 참고 자료입니다: 여섯 역할을 각각 한 줄로, 세 가지 도입 경로와 각 단계에서 새 책임을 얻는 역할, 같은 Origin 검증 예제를 손으로 풀어 쓴 것, 그리고 메인테이너 위계, 워킹 그룹 대 인터레스트 그룹, SEP 상태 목록, 세 SDK 등급을 다루는 짧은 거버넌스·SDK 등급 치트시트. 호스트·클라이언트·서버 레슨의 아키텍처 역할 지도 곁에 두세요. 그것은 회선 토폴로지를 그리고, 이것은 그 토폴로지에 누가 책임지는지 이름 붙입니다.

## 확인하기

레슨 디렉터리에서 테스트를 실행하세요:

```bash
python3 -m unittest discover code/tests
```

테스트는 이 레슨의 주장들을 확인합니다: 모든 배포 형태가 비어 있지 않은 매트릭스로 해석된다, stdio는 환경 자격 증명을 플랫폼/게이트웨이 운영자에게 넘긴다, 평범한 HTTP 배포는 Protected Resource Metadata를 서버 작성자에게 넘긴다, 게이트웨이 앞세운 배포는 Origin 검증을 플랫폼/게이트웨이 운영자에게 옮기는 반면 평범한 HTTP 배포는 그것을 서버 작성자에게 둔다, 의도적으로 책임자 없이 둔 MUST는 gap으로 보고되는 반면 책임자 없는 SHOULD는 그렇지 않다, 적용 가능한 모든 요구사항이 형태마다 정확히 한 번씩 배정되며 빠지거나 중복되는 것이 없다, 여섯 역할 모두가 카탈로그 어딘가에 나타난다, 인식할 수 없는 배포 형태는 거부된다, 예시 교환은 회선 위에 자격 증명을 절대 실지 않는다. 저장소의 와이어 검사기도 이 레슨의 실행 기록을 2026-07-28 규칙과 대조해 검증합니다:

```bash
python3 scripts/check_mcpa_wire.py certifications/mcpa/lessons/28-roles-and-adoption
```

## 캡스톤 연결

캡스톤의 통합 시나리오는 메시지 형태를 묘사하는 것만이 아니라 전체 배포를 방어하라고 요구합니다. 이 레슨은 그 방어가 어휘를 얻는 곳입니다: 검토자가 "당신 설계에서 Origin 헤더는 누가 검증하나"라고 물으면, 답은 서버가 MUST라고 검증한다는 말을 반복하는 것이 아니라 역할과 배포 형태를 이름 붙여야 합니다. 책임 매트릭스를 가져가고, 시나리오가 언급하는 모든 MUST에 대해 "이 특정 팀에서 방금 누가 그것을 맡기로 했나"를 묻는 습관을 가져가세요.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 서버 작성자(Server author) | 사양을 기준으로 하나의 MCP 서버 구현을 쓰고 유지보수하는 역할 |
| 호스트·클라이언트 개발자(Host and client developer) | 애플리케이션과, 기능을 선언하고 회선 프로토콜을 말하는 클라이언트를 만드는 역할 |
| 플랫폼·게이트웨이 운영자(Platform or gateway operator) | 프로세스를 구동하는 역할: 환경과 함께 stdio 서브프로세스를 띄우거나 원격 연결을 종단하고 감시한다 |
| 보안·거버넌스 담당자(Security and governance owner) | 어느 한 구현자가 자연스럽게 소유하지 않는 공통 요구사항, 예컨대 토큰 처리와 동의 정책에 책임지는 역할 |
| 레지스트리 게시자(Registry publisher) | 서버의 server.json, 그 네임스페이스, 레지스트리가 서비스하는 정보의 정확성을 소유하는 역할 |
| 최종 사용자(End user) | 동의를 부여하고, 호스트가 자기를 대신해 하는 일에 대한 책임 당사자인 역할 |
| 워킹 그룹(Working Group) | 구체적인 산출물, 보통 SEP와 그 참조 구현을 만드는 그룹 |
| 인터레스트 그룹(Interest Group) | 문제를 토론하고 구속력 없는 권고를 만드는 그룹. 설계를 만들지는 않는다 |
| SEP | Specification Enhancement Proposal. 새 기능이나 파괴적 변경을 위한 PR 기반 워크플로 |
| SDK 등급(SDK tier) | SDK 메인테이너가 서명하는 적합성·응답 시간 약속. Tier 1부터 Tier 3까지 |
