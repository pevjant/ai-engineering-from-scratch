# 감사와 텔레메트리 필드 브리프

MCPA '보안과 거버넌스' 도메인의 감사 가능성(auditability) 학습 목표를 위한 한 페이지 참고 자료입니다. 즉, 프로토콜 활동을 추적하고 귀속시키고 검토할 수 있도록 감사 가능성과 관측 가능성(observability)을 설계하는 것입니다. MCP 2026-07-28 기준입니다.

## traceparent 필드 배치

`traceparent`는 하이픈으로 구분된 네 개의 세그먼트이며, 항상 소문자 16진수, 고정 길이입니다. `_meta`에 실려 다니며 역방향 DNS 접두사 규칙의 유일한 예외입니다(SEP-414):

| 세그먼트 | 길이 | 의미 |
|---------|--------|---------|
| version | 16진수 2자 | 형식 버전. 현재 쓰이는 값은 `00` |
| trace id | 16진수 32자 | 전체 연산을 지칭. 모든 홉(hop)에서 일정 |
| parent id | 16진수 16자 | 스팬 하나를 지칭. 매 홉마다 새로 만들어짐 |
| flags | 16진수 2자 | 비트 플래그. 예: 추적이 샘플링되는지 |

전부 0인 trace id나 parent id는 잘못된 것이며 반드시 거부해야 합니다. `tracestate`(공급업체 상태)와 `baggage`(사용자 정의 컨텍스트)는 `traceparent`와 함께 다니는 별개의 `_meta` 키입니다. 이 레슨의 서버들은 매 홉에서 둘 다 그대로 전달합니다.

## 자식 스팬 만들기

다른 서비스를 호출하기 전에 trace id는 유지하고 새 parent id를 만듭니다:

```python
def child_traceparent(value):
    parsed = parse_traceparent(value)
    return make_traceparent(parsed["trace_id"], new_span_id(), sampled=parsed["flags"] != "00")
```

## 감사 항목의 다섯 필드

| 필드 | 출처 | 절대 쓰지 말 것 |
|-------|--------|-----------|
| who | 검증된 자격 증명이 풀리는 인증된 주체 | `clientInfo.name`(스스로 보고, 표시 전용) |
| what | 메서드, 도구 이름, 표시된 필드를 가려낸 인자 | 가려내지 않은 원시 인자 값 |
| when | 항목을 기록할 때 찍은 타임스탬프 | 클라이언트가 제공한 시간 주장 |
| result channel | complete, isError, protocol_error 중 호출이 실제로 끝난 것 | 모든 결과를 하나의 일반 상태로 뭉개기 |
| correlation | 요청 id(이 홉) 더하기 trace id(전체 연산) | 서비스 경계를 넘는 요청 id 단독 |

## 가려내기(redaction) 규칙

도구는 표시된 인자 필드 이름들의 집합과 함께 등록됩니다. 항목이 만들어지기 전에 표시된 모든 필드의 값은 고정된 마커로 대체됩니다. 이것은 항목이 기록되기 전에, 그리고 해시되기 전에 일어나므로, 원시 값은 내구적인 기록이나 그 백업, 해시 계산 어디에도 존재하지 않습니다. 도구의 핸들러는 여전히 실제 값을 받습니다. 가려지는 것은 감사 기록의 복사본뿐입니다. 각 서버는 자기 로그에 자기 가려내기 정책을 독립적으로 적용합니다.

## 해시 체인 검증, 절차로서

1. 제네시스 값을 기대되는 이전 해시로 삼아 시작합니다.
2. 각 항목을 순서대로: 저장된 `prev_hash`가 기대되는 이전 해시와 같은지 확인합니다. 항목 자신의 저장된 필드들로 다이제스트를 다시 계산해 저장된 `hash`와 일치하는지 확인합니다. 그다음 기대되는 이전 해시를 이 항목의 `hash`로 갱신하고 계속합니다.
3. 깨끗한 체인은 모든 항목을 검사하고 끝납니다. 변조된 체인은 저장된 해시가 내용과 더 이상 맞지 않는 첫 항목에서 멈춥니다. 공격자가 그 항목 자신의 해시까지 손봤다면 대신 바로 다음 항목에서 멈춥니다. 그 항목의 `prev_hash`는 여전히 원래 값을 가리키기 때문입니다.

이것은 변조 '증거'이지 변조 '방지'가 아닙니다. 하부 저장소에 쓰는 것을 막아 주는 건 아무것도 없습니다. 하지만 편집은 그 뒤의 모든 항목을 순서대로 다시 쓰지 않는 한 보이지 않게 만들어질 수 없습니다.

## clientInfo가 who일 수 없는 이유

`clientInfo`와 `serverInfo`는 보내는 쪽이 스스로 보고한 것이며 프로토콜이 검증해 주지 않습니다. 명세는 구현체들이 보안 판단에 이것들에 의존하지 말라고 합니다. `clientInfo.name`을 who 필드로 쓰는 감사 기록이라면 어떤 호출자든 자신이 책임지는 로그에 자기가 원하는 이름을 골라 적을 수 있습니다. 기록이 기록되기도 전에 그 목적이 무너지는 것이지요.

## 홉을 넘어 연결하기

같은 연산 위의 두 서버는 두 개의 별개 해시 체인을 유지합니다. 공유 로그도 없고, 같은 연산에 대해 한 서버의 요청 id가 다른 서버의 것과 일치해야 한다는 요구도 없습니다. 각 홉은 자기 것을 새로 만듭니다. 홉의 양쪽에서 동일하다고 보장되는 유일한 값은 trace id입니다. 그래서 검토자나 트레이싱 백엔드가 그것을 조인 키로 삼아, 하나의 연산이 건드린 모든 서비스에 걸친 전체 경로를 재구성합니다.
