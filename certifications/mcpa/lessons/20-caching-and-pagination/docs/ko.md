# 캐시 신선도와 커서 기반 페이지네이션

> 캐시 가능한 결과는 클라이언트에게 그 사본을 얼마나 오래 믿을 수 있는지, 그리고 누가 그 사본을 재사용할 수 있는지를 정확히 알려 줍니다. 페이지네이션 결과는 불투명한 책갈피(cursor)를 건네줄 뿐, 페이지 번호를 주는 일은 결코 없습니다.

**유형:** 참조(Reference)
**언어:** Python
**선수 지식:** 레슨 19
**시간:** 약 45분

## 학습 목표

- `CacheableResult`를 돌려주는 여섯 가지 작업을 이름으로 짚고, 각각에서 `ttlMs`와 `cacheScope`가 무슨 뜻인지 말할 수 있습니다
- 2026-07-28 클라이언트가 지켜야 하는 신선도 규칙을 적용합니다: `ttlMs`가 `0`이면 즉시 상함(stale), 음수는 `0`으로 취급, 필드가 없어도 기본값은 `0`
- `cacheScope`가 `public`인지 `private`인지에 따라 누가 캐시된 응답을 재사용할 수 있는지가 정해지는 이유와, 그 선택이 결코 접근 제어 판단이 되어서는 안 되는 이유를 설명합니다
- 불투명한 커서를 `resources/list`에 통과시켜 봅니다. 커서가 없으면 처음부터 시작, 빈 문자열은 목록 중간의 유효한 위치, 알 수 없는 커서는 `-32602`
- `list_changed` 알림이 남은 TTL과 무관하게 캐시를 즉시 무효화하는 이유와, MRTR 요청을 재시도해서 만든 결과는 결코 캐시에 담아서는 안 되는 이유를 설명합니다

## 문제 상황

레슨 04의 스테이트리스 코어 덕분에 서버는 요청 사이에 클라이언트를 기억하지 않습니다. 따라서 클라이언트가 두 번 묻기를 피하려고 기댈 수 있는 따뜻한 연결 상태 같은 것도 없습니다. 그런데 한편, 클라이언트가 묻는 대부분의 것은 거의 변하지 않습니다. 도구 카탈로그는 일주일에 한 번 고쳐질 수도 있고, 리소스의 바이트 내용은 한 시간 동안 그대로일 수도 있습니다. 모델이 결정을 내릴 때마다 `tools/list`를 부르고 같은 리소스를 읽는다면, 움직이지도 않은 데이터 때문에 왕복 횟수가 폭증하고, 인터넷 너머의 서버라면 그 왕복 하나하나가 실제 지연 시간을 치러야 합니다.

또 하나, 별개의 비용이 큰 결과 집합을 가진 서버에서 나타납니다. 항목 만 개짜리 리소스 카탈로그가 하나의 JSON 배열로 돌아온다면, 첫 몇 개의 이름만 필요한 클라이언트조차 목록 전체의 값을 치르게 됩니다. 모든 것을 한 번에 돌려주는 방식은 서버가 밑바닥 저장소를 바꾸거나, 항목을 추가하거나, 카탈로그를 샤딩할 때 고정된 응답 형태를 믿고 있던 모든 클라이언트를 깨뜨리게 만들기도 합니다.

MCP는 첫 번째 비용에 대해, 기억해 둘 가치가 있는 결과에 캐시 봉투(envelope)를 붙이는 방식으로 답합니다. 살아 있는 시간(time to live)과, 캐시된 바이트를 누가 공유할 수 있는지 밝히는 스코프입니다. 두 번째 비용에는 커서 기반 페이지네이션으로 답합니다. 서버가 관리 가능한 조각만 건네주고 나머지를 위한 책갈피를 함께 주는 불투명한 토큰이며, 안정적인 페이지 수나 고정된 페이지 크기는 약속하지 않습니다. 두 메커니즘 모두 이 시대 프로토콜의 다른 모든 것과 같은 규율에 들어맞습니다. 클라이언트가 필요로 하는 모든 사실 — 응답이 얼마나 신선한지든, 목록의 어디부터 이어갈지든 — 은 메시지 자체에 명시적으로 실려 이동하며, 우연히 아직 열려 있는 연결이 함축해 주는 일은 없습니다.

## 개념

여섯 가지 작업이 `CacheableResult`를 돌려줍니다: `server/discover`, `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read`. 이 중 하나가 `resultType: "complete"`를 돌려줄 때마다 결과는 두 필드를 실립니다. `ttlMs`는 0 이상의 정수로, 클라이언트가 응답을 몇 밀리초 동안 신선하다고 여겨도 되는지 알려 줍니다. HTTP의 `Cache-Control: max-age`와 같은 발상입니다. `cacheScope`는 `"public"` 또는 `"private"`이며, 누가 사본을 붙잡고 있을 수 있는지 말해 줍니다.

리소스를 받아온 클라이언트는 응답을 받은 현지 시각을 기록한다고 합시다. 이를 `t_received`라 부릅니다. `now < t_received + ttlMs`인 동안 응답은 신선합니다. 시험에 나오는 경계 사례가 셋 있습니다. `ttlMs`가 `0`이면 응답은 즉시 상한 것이고, 클라이언트는 다음에 필요해질 때 다시 받아올 수 있습니다. 서버가 음수 `ttlMs`를 보내면, 규격에 맞는 클라이언트는 부호를 무시하고 `0`으로 취급합니다. `ttlMs`가 아예 없다면(이 메커니즘 이전의 오래된 서버에만 일어나야 하는 일입니다) 클라이언트는 역시 `0`을 가정하고 자기만의 휴리스틱이나 변경 알림으로 물러섭니다. 이 모든 것이 TTL을 폴링 주기로 만들지는 않습니다. 클라이언트는 타이머가 울려 백그라운드에서 다시 받아오는 것이 아니라, 다음에 데이터가 필요해질 때 느긋하게(lazily) 신선도를 확인합니다. 그래도 폴링을 하기로 한 구현체라면 많은 클라이언트가 같은 박자에 다시 받아오지 않도록 지터(jitter)와 백오프를 반드시 더해야 합니다.

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "resultType": "complete",
    "resources": [
      {"uri": "note://private/journal", "name": "journal"},
      {"uri": "note://private/vault", "name": "vault"}
    ],
    "nextCursor": "",
    "ttlMs": 120000,
    "cacheScope": "public"
  }
}
```

`cacheScope`는 다른 질문에 답합니다. 얼마나 오래가 아니라, 누구를 위한 것인가입니다. `"public"`은 응답이 호출자별 내용을 아무것도 담지 않는다는 뜻이므로, 어떤 클라이언트, 게이트웨이, 프록시든 이를 한 번 저장해 완전히 다른 호출자에게 서빙해도 됩니다. 모든 사용자에게 똑같은 도구 카탈로그가 평범한 `public` 사례입니다. `"private"`은 콘텐츠가 누가 물었는지에 따라 달라진다는 뜻이므로, 캐시된 사본은 같은 인가 컨텍스트에 대해서만 다시 재생(replay)될 수 있고, 다른 토큰에 넘겨지는 일은 없습니다. 공유 readme 읽기는 `public`이고, 호출자 자신의 개인 노트 읽기는 `private`입니다. 요청이 회선 위에서는 똑같아 보여도 바이트는 호출자마다 다르기 때문입니다. `cacheScope`는 보안 경계가 아니라 캐시 지시로 다뤄야 합니다. `public` 스코프는 사용자별 데이터가 없는 바이트를 공유해도 된다고 캐시에게 말할 뿐이고, 애초에 그 메서드를 호출할 권한을 누구에게 주는 것도 아니며, 서버는 마지막 캐시 응답이 뭐라고 주장했든 상관없이 모든 요청에 대해 자기만의 프리미티브별 접근 제어를 그대로 집행합니다.

캐시 항목은 요청 메서드와 결과에 영향을 주는 파라미터들이 함께 식별합니다. `resources/read`의 `uri`, 페이지네이션된 목록의 `cursor`가 그 예입니다. 클라이언트는 절대, 그 캐시를 만든 요청과 메서드 또는 관련 파라미터가 다른 요청에 캐시된 응답을 서빙해서는 안 됩니다. 그리고 다중 왕복 교환(레슨 14의 패턴)으로 요청을 재시도해서 만들어진 결과는 아예 캐시하면 안 됩니다. 그 결과는 캐시 키에 속하지 않는 `inputResponses`에 의존했기 때문입니다. 중간 결과인 `input_required`도 캐시할 수 없으며, 애초에 `ttlMs`나 `cacheScope` 필드를 아직 실지 않습니다. 아직 답하지 않은 질문에 대해 기억해 둘 것은 없습니다.

TTL과 푸시 알림은 경쟁 관계가 아니라 상호 보완입니다. 서버는 `listChanged: true`를 광고하지 않은 채 `ttlMs`만 실을 수도 있고, 그 경우 TTL이 클라이언트의 유일한 신선도 신호입니다. 둘 다 광고할 수도 있습니다. 그 경우 알림 사이의 쓸데없는 재요청은 TTL이 막아 주고, 알림(레슨 16에서 깊이 다룹니다)은 실제로 무언가가 바뀐 바로 그 순간 즉시 무효화로 작동합니다. 캐시된 응답이 아직 TTL 창 안에 살아 있는 동안 클라이언트가 구독 스트림으로 `notifications/resources/list_changed`, `notifications/tools/list_changed`, `notifications/prompts/list_changed`를 받으면, 알림이 이깁니다. 캐시된 사본은 시계에 남은 시간이 얼마든 상관없이 즉시 상한 것이 됩니다.

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/resources/list_changed",
  "params": {"_meta": {"io.modelcontextprotocol/subscriptionId": 7}}
}
```

페이지네이션은 페이지 번호 대신 불투명한 커서를 씁니다. `resources/list`, `resources/templates/list`, `prompts/list`, `tools/list` 모두 같은 방식으로 이를 지원합니다. 응답이 `nextCursor`를 포함할 수 있고, 포함했다면 클라이언트는 다음 호출에서 그 문자열을 그대로 `cursor`로 보내 이어갈 수 있습니다. 페이지 크기는 서버가 정합니다. 클라이언트는 그것이 고정돼 있다고 가정해서도, 커서의 내용을 파싱하거나 디코딩하거나 추리해서도 안 됩니다. 그 문자열은 그것을 발행한 서버에만 의미를 갖기 때문입니다. `nextCursor`가 없으면 목록의 끝입니다. 이 지점에서 시험이 좋아하는 함정은 빈 문자열입니다. 커서는 합법적으로 `""`일 수 있고, 그것은 진짜 위치입니다. 목록이 끝났다는 신호도, 처음부터 다시 시작하라는 요청도 아닙니다. `if cursor is not None:` 대신 `if cursor:`를 검사하는 클라이언트는, 서버가 빈 토큰을 발행하는 바로 그 한 번에 조용히 페이지네이션을 일찍 접어 버립니다. 알 수 없는 커서 — 서버가 발행한 적 없거나 더 이상 풀어 낼 수 없는 커서 — 는 `-32602 Invalid params`로 돌아옵니다.

```json
{
  "jsonrpc": "2.0",
  "id": 4,
  "error": {"code": -32602, "message": "Invalid cursor: 'not-a-real-cursor'"}
}
```

페이지네이션과 캐싱이 맞물리는 방식도 몇 가지 외워 둘 가치가 있습니다. 각 페이지는 자기만의 `ttlMs`를 가진 독립적으로 캐시 가능한 응답이고, 특정 페이지의 신선도 시계는 그 페이지를 받은 시점에 시작하지, 목록의 첫 페이지를 받은 시점에 시작하지 않습니다. 서버는 앞쪽의 안정적인 페이지에는 더 긴 TTL을, 변덕스러운 마지막 페이지에는 더 짧은 TTL을 고르기도 합니다. 페이지 간 일관성 보장은 없습니다. 두 페이지를 받는 사이에 밑바닥 목록이 바뀌면 클라이언트는 어떤 항목을 두 번 보거나 아예 놓칠 수 있습니다. HTTP 페이지네이션이 늘 안고 간 트레이드오프이며, 진짜 스냅샷이 필요한 클라이언트는 커서 없이 처음부터 다시 받아와야 합니다. 서버가 해서는 안 되는 것은 하나의 목록 응답에서 페이지마다 `cacheScope`를 다르게 고르는 것입니다. `resources/list` 호출의 첫 페이지가 `private`이라면 그 호출의 모든 뒷 페이지도 `private`입니다.

마지막으로 순서입니다. `tools/list`와 다른 목록 작업은 똑같은 호출 사이에서 안정적이고 결정적인 순서로 결과를 돌려줘야 합니다. 이것이 중요한 이유는 두 겹입니다. 클라이언트 자신의 캐시와 페이지네이션 장부가 예측 가능하게 동작하게 해 주고, 상위 대규모 언어 모델 공급자의 프롬프트 캐시가 다음에 같은 도구 카탈로그가 시스템 프롬프트로 직렬화될 때 바이트 단위로 동일한 접두사를 알아차리게 해 줍니다. 이것은 MCP 캐시와는 무관한, 실제 지연 시간과 비용 절감이며, 회선 출력을 안정적으로 유지하는 일과만 관련됩니다.

## 인터랙티브 랩

이 그림은 캐시된 응답 하나를 타임라인 위에 놓습니다. 응답이 `t_received`에 착지하고, 음영 띠가 `ttlMs`만큼 앞으로 뻗습니다. 그 띠 안에서는 클라이언트가 회선 트래픽 없이 전부 캐시로 답합니다. 같은 타임라인의 두 번째 사본에서 무슨 일이 일어나는지 지켜 보세요. `list_changed` 알림이 TTL 띠가 끝나기 한참 전에 도착하고, 신선도 선이 정확히 그 지점에서 잘립니다. 그림의 캡션이 이것이 시험하는 규칙을 짚어 줍니다. 알림은 도착하는 순간 무효화하고, 남은 TTL은 그 순간부터 아무 의미가 없습니다.

```bash
python3 code/main.py
```

출력되는 전사를 개념 절과 겨뎌 읽어 보세요. 처음 다섯 번의 교환은 `resources/list`를 페이지별로 넘나듭니다. 두 번째 호출은 조용한데 캐시에 걸리기 때문이고, 세 번째는 `cursor: ""`를 보내 첫 페이지가 아니라 중간 페이지를 돌려받고, 네 번째는 `nextCursor`를 따라 마지막 페이지에 이르며, 다섯 번째는 서버가 발행한 적 없는 커서를 보내 `-32602`를 돌려받습니다. 그다음 블록은 노트를 읽습니다. alice와 bob은 공개 readme의 캐시 사본 하나를 함께 씁니다. 거기의 `cacheScope`가 `"public"`이기 때문입니다. 하지만 비공개 저널은 각자 자기 몫을 받아옵니다. `"private"` 항목은 공유 캐시 안에서조차 토큰을 건너지 않기 때문입니다. 이어서 alice가 `subscriptions/listen` 스트림을 열고, 서버의 목록이 바뀌면, TTL이 끝나지 않았는데도 바로 다음 `resources/list` 호출은 회선으로 되돌아갑니다. 비공개 볼트 노트를 읽으면 `elicitation/create` 요청을 실은 `input_required` 결과가 트리거됩니다. 클라이언트가 그것에 답하고, 새 id와 돌아온 `requestState`로 재시도하며, 완료된 읽기는 일부러 캐시에 담기지 않습니다. 볼트를 두 번 읽으면 두 번 묻는 이유입니다. 전사의 마지막 항목은 클라이언트가 보낸 것이 아닙니다. 고의적인 위반으로 감싸져 있는데, `ttlMs`와 `cacheScope`를 아예 생략한 가상의 SEP-2549 이전 서버의 `resources/list` 응답입니다. 규격에 맞는 클라이언트를 `ttlMs: 0` 기본값으로 되돌려 보내는 바로 그 형태입니다.

## 완성된 산출물

`outputs/caching-decision-guide.md`는 `ttlMs`와 `cacheScope` 값을 고르고 클라이언트 측 캐시를 올바르게 구현하기 위한 한 페이지 의사결정 가이드로, 브리프를 인용합니다. `resources/list`, `resources/read`, `tools/list`, `prompts/list`, `resources/templates/list`, `server/discover`를 부르는 코드 옆에 두고 쓰면 좋습니다.

## 캡스톤 연계

캡스톤의 전체 교환은 하는 캐시 가능한 호출마다 그 답을 얼마나 믿을지, 호출자들 사이에서 공유해도 안전한지를 결정해야 하고, 페이지 수를 가정하지 않고 최소 하나의 큰 목록을 페이지별로 통과해야 합니다. 두 결정 모두 이 레슨 위에 섭니다. 캐싱 정책을 발명하는 대신 결과에서 `ttlMs`와 `cacheScope`를 읽어 내고, 캐시 키를 메서드와 실제로 결과에 영향을 주는 파라미터로 정하고, 빈 커서를 끝이 아니라 데이터로 다루고, 재시도되거나 중간인 결과가 재사용 가능한 것처럼 캐시에 앉아 있는 일을 절대 허용하지 마세요.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| `CacheableResult` | 여섯 `complete` 결과가 실고 다니는 `ttlMs`와 `cacheScope`의 봉투 |
| `ttlMs` | 클라이언트가 응답을 신선하다고 여겨도 되는 밀리초. `0`이거나 없으면 즉시 상함, 음수는 `0`으로 접힘 |
| `cacheScope` | `public`(어떤 캐시든 공유 가능) 또는 `private`(같은 인가 컨텍스트만 재사용 가능). 결코 접근 제어가 아님 |
| 캐시 키 | 요청 메서드에 결과에 영향을 주는 파라미터(예: `uri`, `cursor`)를 더한 것 |
| 커서(cursor) | 목록에서 위치를 표시하는, 서버가 고른 불투명한 토큰. 클라이언트는 파싱하거나 고정 페이지 크기를 가정해선 안 됨 |
| `nextCursor` | 페이지네이션을 이어가는 토큰. 목록이 끝났음을 뜻하는 것은 빈 문자열이 아니라 이 토큰의 부재 |
| `list_changed` 알림 | 남은 TTL과 무관하게 캐시된 목록을 즉시 무효화하는 푸시 신호 |
| MRTR 재시도 결과 | `input_required` 왕복 뒤에 이어지는 완료. 캐시 자격이 결코 없음 |
