# 캐싱과 페이지네이션 판단 가이드

MCP 클라이언트와 서버를 올바르게 구현하기 위한 한 페이지 참고 자료입니다. MCP 2026-07-28 기준입니다.

## 이 결과에 ttlMs와 cacheScope가 필요한가?

캐시 가능한 연산은 여섯 개뿐이고, `resultType`이 `"complete"`일 때만 그렇습니다:

| 연산 | 일반적인 cacheScope | 비고 |
|-----------|--------------------|-------|
| `server/discover` | public | 서버의 모든 호출자에게 동일 |
| `tools/list` | public(보통) | 도구 집합 자체가 호출자마다 달라질 때만 private |
| `prompts/list` | public(보통) | tools/list와 같은 규칙 |
| `resources/list` | public 또는 private | 목록 자체가 호출자별로 걸러질 때는 private |
| `resources/templates/list` | public | 템플릿은 호출자마다 달라지는 일이 드묾 |
| `resources/read` | 리소스에 따라 다름 | 사용자별 내용이면 private |

`input_required` 결과는 캐시되는 일이 없고 두 필드 중 어느 것도 실지 않습니다. MRTR 요청을 재시도해서 나온 결과도 캐시하지 않습니다. 그 결과가 여전히 두 필드를 보고하더라도요.

## ttlMs 고르기

- 거의 바뀌지 않는 데이터에는 긴 TTL(정적 참조 문서, 안정적인 도구 카탈로그).
- 자주 바뀌거나 낡아지는 게 비싼 대가를 치르게 되는 데이터에는 짧은 TTL(실시간 큐 깊이, 잔액).
- 응답을 항상 낡은 것으로 취급해야 한다면 `0`. 예컨대 서버가 알림으로 회수할 수 없는 콘텐츠를 다루는 리소스.
- 음수는 절대 안 됩니다. 클라이언트 입장에서 음수 값을 받았다면 `0`으로 자릅니다.
- 오래된 서버가 `ttlMs`를 빠뜨린 것도 `0`을 의미합니다. 긴 기본값을 가정하지 마세요.

## cacheScope 고르기

- `"public"`: 바이트 안에 호출자별 내용이 전혀 없습니다. 어떤 클라이언트, 게이트웨이, 프록시든 저장했다가 다른 호출자에게 재생(replay)해도 됩니다.
- `"private"`: 바이트가 누가 물었는지에 따라 달라집니다. 같은 인가 컨텍스트만 캐시 복사본을 재사용할 수 있습니다.
- `cacheScope`는 캐싱 지시이지 절대 접근 통제가 아닙니다. 서버는 여전히 모든 요청에 자신의 프리미티브별 인가를 강제하고, 클라이언트도 여전히 모든 호출을 정상적으로 인증합니다. 스코프는 캐시가 이미 갖고 있는 것을 공유해도 되는지만 말합니다.

## 클라이언트 캐시 체크리스트

- 모든 캐시 항목의 키는 요청 메서드에 결과에 영향을 주는 매개변수를 더한 것으로 합니다(`resources/read`의 `uri`, 페이지네이션된 목록 호출의 `cursor`).
- private 항목은 호출자의 인가 컨텍스트별로 분할합니다. 어떤 토큰을 위해 저장한 private 항목이 다른 토큰의 조회에 답하는 일이 없도록 합니다.
- `input_required` 결과는 절대 저장하지 않습니다.
- MRTR 재시도의 완료 결과도 절대 저장하지 않습니다.
- 관련된 `list_changed` 알림이 오면 영향받는 캐시 항목을 즉시 무효화합니다. TTL이 아직 남았더라도요.
- 백그라운드에서 TTL 타이머로 폴링하지 마세요. 신선도는 데이터가 다음으로 필요할 때 게으르게 확인합니다.
- 다시 가져오기가 실패하면(네트워크 오류, 서버 중단) 호출자를 그냥 실패시키는 대신 낡은 항목을 제공해도 됩니다.

## 페이지네이션 체크리스트

- `cursor`는 불투명한(opaque) 문자열로 취급합니다. 파싱도, 디코딩도, 내용으로부터 위치 추론도 하지 않습니다.
- 고정된 페이지 크기를 가정하지 마세요. 서버가 정하며 페이지 사이에서 바꿀 수도 있습니다.
- `nextCursor`가 존재하면 값이 `""`인 경우를 포함해 목록이 이어집니다. 목록이 끝났다는 뜻은 `nextCursor`의 부재뿐입니다.
- 알아들을 수 없는 커서는 `-32602 Invalid params`를 돌려줍니다. 이 오류가 나면 그 목록의 캐시된 페이지를 버리고, 전체 집합이 필요하다면 처음부터 다시 시작합니다.
- 페이지를 넘나드는 일관성 보장은 없습니다. 진짜 스냅샷이 필요하면 커서 없이 처음부터 다시 가져오세요.
- 서버는 하나의 목록 요청의 모든 페이지에서 같은 `cacheScope`를 써야 합니다.

## 시험을 위해 기억하기

- `ttlMs`는 신선도 힌트이지 하부 데이터가 바뀌지 않았다는 보장이 아닙니다.
- 빈 문자열 커서는 유효하며 목록의 끝이 아닙니다.
- MRTR 재시도 결과는 캐시되지 않습니다. 명세가 그 결과에도 ttlMs와 cacheScope를 요구하더라도요.
- 결정적인 목록 순서는 클라이언트 자신의 캐시에도, LLM 제공자의 프롬프트 캐시가 바이트 단위로 동일한 접두사를 재사용하는 데도 도움이 됩니다.
