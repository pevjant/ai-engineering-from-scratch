# 인가 서버에 클라이언트 신원 증명하기

> MCP 클라이언트와 새 서버를 지키는 인가 서버는 보통 서로 본 적이 없습니다. 그래서 무엇이든 인가되기 전에, 인가 서버는 먼저 그 클라이언트가 자기가 자칭하는 그 신원이라고 믿을지 말지를 결정해야 합니다.

**유형:** 참조(Reference)
**언어:** Python
**선수 지식:** 레슨 23
**시간:** 약 45분

## 학습 목표

- MCP의 상호운용성 약속이 클라이언트와 인가 서버 사이에 미리 맺어진 관계가 없는 경우를 흔하게 만드는 이유와, 그것이 등록 방식을 어떻게 빚어 내는지 설명합니다
- 명세의 네 갈래 등록 우선순위를 적용합니다: 미리 등록된 자격 증명, 클라이언트 ID 메타데이터 문서, 동적 클라이언트 등록, 그리고 사용자에게 묻기
- 인가 서버가 해야 하는 방식으로 클라이언트 ID 메타데이터 문서를 검증합니다. 정확한 `client_id` 일치, 경로가 있는 https URL, 필수 메타데이터 필드
- 저장해 둔 클라이언트 자격 증명을 그것을 발행한 인가 서버에 묶고, 인가 서버가 바뀌면 재등록이 강제되는 이유를 설명합니다
- 정적 client id를 쓰는 프록시가 만드는 착란하는 부관(confused deputy) 위험을 알아보고, 무인 접근이나 기업 접근을 위해 OAuth Client Credentials 익스텐션과 Enterprise-Managed Authorization 익스텐션 사이에서 고릅니다

## 문제 상황

MCP의 전체 사정은 한 발상 위에 섭니다. 오늘 쓰인 클라이언트는 한 번도 본 적 없는 서버를 쓸 수 있어야 하고, 오늘 쓰인 서버는 저자가 한 번도 들어 본 적 없는 클라이언트에게 쓰일 수 있어야 합니다. 바로 평범한 OAuth가 세워지지 않은 시나리오입니다. OAuth 2.1은 클라이언트가 미리 인가 서버에 등록해 클라이언트 id를 받고, 그 이후 모든 요청에 그 id를 재사용한다고 가정합니다. 한 회사가 자기 인가 서버와 대화하는 하나의 모바일 앱을 만들 때는 미리 등록이 쉽습니다. 그러나 누군가 만든 어떤 MCP 클라이언트가, 누군가 운영하는 어떤 MCP 서버와, 그 서버 운영자가 마침 쓰고 있는 인가 서버를 통해 대화해야 할 수도 있다면 쉽지 않습니다.

이전 레슨이 역할들을 다뤘습니다. MCP 서버는 OAuth 리소스 서버이고, MCP 클라이언트는 OAuth 클라이언트이며, 별개의 인가 서버가 토큰을 발행합니다. 이 레슨은 그 모든 것보다 먼저 일어나야 하는 단계를 다룹니다. 양쪽이 결코 조율된 적 없을 수 있는데, 클라이언트가 인가 서버가 받아줄 클라이언트 id를 애초에 어떻게 손에 넣는가. 이 단계를 잘못 밟으면 인가 흐름의 나머지는 아예 시작되지 않고, 클라이언트 신원을 가짜로 둔갑시킨 공격자가 사칭에서 앞서 나가며, 잘못된 자격 증명을 잘못된 인가 서버에 재사용하는 클라이언트는 애초에 자기를 위해서가 아니었던 토큰을 넘겨 주게 됩니다.

## 개념

명세는 클라이언트에게 정확히 하나의 우선순위를 줍니다. 순서가 중요한 이유는 각 선택지가 바로 앞의 것이 실패했을 때에만 의미가 있기 때문입니다. 첫째, 이 인가 서버에 대해 이미 갖고 있는 미리 등록된 클라이언트 정보가 있으면 그것을 씁니다. 둘째, 인가 서버가 지원을 광고하면 클라이언트 ID 메타데이터 문서를 씁니다. 셋째, 인가 서버가 등록 엔드포인트를 제공하면 동적 클라이언트 등록으로 물러섭니다. 넷째, 그때에만, 클라이언트를 쓰는 사람에게 클라이언트 정보를 손으로 입력해 달라고 청합니다.

**미리 등록(pre-registration)** 은 간단한 사례입니다. 클라이언트 개발자가 특정하고 알려진 인가 서버를 위해 클라이언트 id를 하드코딩하거나, 서버 운영자가 사용자가 손으로 등록한 뒤 설정 화면을 통해 클라이언트 id를 건네줍니다. 양쪽이 이미 서로를 알 때 잘 맞는데, 이는 기업 자체의 내부 서버에서는 흔하지만 MCP가 만들어진 열린 생태계에서는 드뭅니다.

**클라이언트 ID 메타데이터 문서(Client ID Metadata Documents, CIMD)** 는 흔한 MCP 사례 — 사전 관계가 전혀 없음 — 에 대한 답입니다. CIMD 클라이언트는 인가 서버가 발급한 불투명한 문자열 대신 HTTPS URL을 자기 클라이언트 id로 씁니다. 그 URL, 예컨대 `https://app.example.com/oauth/client-metadata.json`은 클라이언트가 자기가 직접 호스팅하는 JSON 문서를 가리킵니다:

```json
{
  "client_id": "https://app.example.com/oauth/client-metadata.json",
  "client_name": "Example MCP Client",
  "client_uri": "https://app.example.com",
  "redirect_uris": ["http://127.0.0.1:3000/callback", "http://localhost:3000/callback"],
  "grant_types": ["authorization_code"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "none"
}
```

인가 서버가 인가 요청에서 URL 모양의 클라이언트 id를 보면, 그 URL을 불러와 문서를 클라이언트의 등록으로 다룹니다. 문서에는 최소한 `client_id`, `client_name`, `redirect_uris`가 있어야 하고, 인가 서버는 문서 안의 `client_id` 필드가 불러온 URL과 정확히 일치하는지 확인해야 합니다. 바로 그 동일성 검사가 URL을 자기 주장만으로 이루어진 주장이 아니라 믿을 만한 식별자로 만듭니다. 그 HTTPS 경로를 통제하는 사람만이 그 끝에 일치하는 `client_id`를 놓을 수 있기 때문입니다. 인가 서버는 또 인가 요청의 모든 리디렉션 URI를 문서에 나열된 것들과 겨뎨 검증하고, 불러온 문서를 매 로그인마다 다시 가져오기보다 평범한 HTTP 캐시 헤더를 존중하며 캐시해야 합니다. 이 길을 지원하는 서버는 자기 메타데이터에 `"client_id_metadata_document_supported": true`로 광고하고, 이것이 바로 클라이언트가 CIMD 로그인을 시도하기 전에 검사하는 것입니다.

클라이언트가 제공한 URL을 불러오는 일에는 두 가지 위험이 따릅니다. 인가 서버는 공격자가 닿을 수 있는 입력에 기반해 외부로 나가는 HTTP 요청을 하게 되므로, 서버 측 요청 위조(SSRF)를 막아야 합니다. 불러오기 전에 URL과 그것이 풀리는 주소를 검증하고, 응답 크기를 제한하고, 타임아웃을 적용하는 것입니다. 그리고 CIMD 클라이언트 id는 그것 자체로는 누군가 `localhost`에서 합법적인 클라이언트를 사칭하는 것을 막지 못합니다. 공격자는 진짜 클라이언트의 메타데이터 URL을 주장하고 같은 루프백 포트에 바인딩할 수 있습니다. 그래서 명세는 인가 서버에게 localhost 전용 리디렉션 URI에 대해 별도의 경고를 보여 주고, 동의 화면 동안 리디렉션 호스트명을 언제나 표시해 달라고 청합니다. 이런 단서들에도 CIMD id에는 DCR id가 한 번도 가진 적 없는 실질적인 장점이 있습니다. 이식성입니다. id는 인가 서버가 필요할 때 풀어 보는 URL일 뿐이므로, 같은 클라이언트 id가 클라이언트가 말을 건 모든 인가 서버에서 변함없이 통합니다.

**동적 클라이언트 등록(Dynamic Client Registration, DCR)** 은 CIMD가 존재하기 전 MCP가 의지하던 방식이고, 명세는 이제 이를 deprecated로 표시합니다. 아직 CIMD 지원을 더하지 않은 인가 서버에 클라이언트가 여전히 등록할 수 있도록 남겨 둔 것입니다. DCR로 떨어진 클라이언트는 자기 메타데이터를 `registration_endpoint`로 보내고 새로 주조된, 인가 서버별 클라이언트 id를 돌려받습니다. 여기서도 시험에 나오는 디테일 하나가 있습니다. 인가 서버가 DCR 위에 OpenID Connect를 구현했다면, 클라이언트가 선언한 `application_type`에 따라 다른 리디렉션 URI 규칙을 집행할 수 있습니다. 네이티브 애플리케이션, 즉 데스크톱 앱, 모바일 앱, CLI 도구, 또는 `localhost`로 닿는 로컬 호스팅 앱은 `application_type: "native"`를 선언해야 합니다. 원격 브라우저 기반 애플리케이션은 `"web"`을 선언해야 합니다. 이 필드를 빼먹으면 OIDC에서 `"web"`으로 기본 설정되는데, 루프백 포트로 리디렉트하는 CLI 도구에게는 정확히 틀린 값이고, 그 결과 등록이 거절될 수 있습니다.

어느 길이 만들어 냈든, 저장된 자격 증명은 하나의 인가 서버에 속합니다. 추상적인 MCP 서버나 배포에 속하는 것이 결코 아닙니다. 명세는 클라이언트가 저장된 자격 증명을 그것을 발행한 발급자(issuer)로 키잉할 것을 요구하고, 한 인가 서버의 자격 증명을 다른 인가 서버에 재사용하는 것을 금합니다. 클라이언트는 자기가 호출하는 MCP 서버의 보호 리소스 메타데이터를 지켜보며 인가 서버의 변화를 감지합니다. 그 메타데이터가 이제 다른 인가 서버를 이름 댄다면, 오래된 자격 증명은 잘못된 발급자를 위한 것이므로, 클라이언트는 조용히 시도하는 대신 재등록해야 합니다. CIMD 자격 증명은 대부분 이 문제를 우회합니다. 같은 URL 기반 id가 어디서나 유효하기 때문입니다. DCR 자격 증명은 그렇지 않습니다. 각 인가 서버가 자기만의 id를 주조했기 때문입니다.

등록 신원은 명세가 이름을 대며 지적하는 특정 공격에도 영향을 줍니다. 착란하는 부관(confused deputy) 문제입니다. 하나의 공유된 정적 클라이언트 id로 수많은 다운스트림 동적 등록 클라이언트를 제3자 인가 서버로 전달하는 MCP 프록시는, 사용자가 실제로 승인한 클라이언트가 아닌 다른 다운스트림 클라이언트에 속한 인가 코드를 전달하도록 속일 수 있습니다. 완화책은 암호학적이 아니라 절차적입니다. 프록시는 정적 클라이언트 id에 대한 동의를 그 뒤에 숨어 있는 모든 클라이언트에 대한 동의로 다루는 대신, 동적으로 등록된 각 다운스트림 클라이언트의 요청을 앞으로 전달하기 전에 사용자의 동의를 각각 따로 얻어야 합니다.

지금까지의 모든 길은 승인을 눌러 줄 사람이 곁에 있다고 가정합니다. 그 가정이 깨지는 사례를 두 개의 공식 인가 익스텐션이 커버하고, 둘 다 다른 MCP 익스텐션과 정확히 같은 방식으로 협상됩니다. 클라이언트가 각 요청의 `io.modelcontextprotocol/clientCapabilities.extensions`에 지원을 선언하고, 서버가 `server/discover`가 돌려주는 커패시티에 자신의 지원을 광고하며, 어느 쪽도 지원할 의무는 없습니다.

```json
{
  "io.modelcontextprotocol/clientCapabilities": {
    "extensions": {
      "io.modelcontextprotocol/oauth-client-credentials": {}
    }
  }
}
```

**OAuth Client Credentials**은 백그라운드 서비스, CI 파이프라인, 무언가를 대화형으로 승인해 줄 사람이 없는 채로 주기적으로 MCP 서버를 호출해야 하는 데몬에 맞습니다. 클라이언트는 자기 자신의 자격 증명으로 인가 서버에게 직접 인증합니다. 자기가 서명한 JWT 베어러 어설션(assertion)을 쓰거나(명세가 권하는 방식으로, 서명 키가 클라이언트를 떠날 필요가 없습니다), 토큰 엔드포인트로 보내는 클라이언트 시크릿을 씁니다(더 간단하지만, 훔친 사람에게 접근을 허락하는 장수 자격 증명입니다). **Enterprise-Managed Authorization**은 정반대 형태의 문제에 맞습니다. 조직은 각 개별 MCP 서버의 인가 서버가 아니라 자기 자신의 신원 공급자가 누가 무엇에 닿을 수 있는지 결정하는 자리이기를 원합니다. 직원은 평범한 회사 SSO 세션으로 MCP 클라이언트에 로그인하고, 클라이언트는 그 신원을 기업 신원 공급자로부터 ID-JAG라 부르는 단명 토큰으로 바꾸며, ID-JAG를 MCP 접근 토큰으로 바꿉니다. 사용자를 MCP 인가 서버 자신의 로그인 페이지로 보내는 일은 한 번도 없습니다. 결정을 그곳에 중앙화하면 관리자는 직원이 각각 승인해 둔 모든 MCP 클라이언트-서버 짝을 일일이 사냥하는 대신, 신원 공급자에서 한 번만 접근을 철회합니다.


## 인터랙티브 랩

이 그림은 네 갈래 우선순위를 위에서 아래로 펼쳐 놓고, 각 상자에 클라이언트가 시도하기 전에 성립해야 하는 조건을 표시하며, 클라이언트가 다음 경로로 떨어지는 지점을 "if unavailable"이라는 화살표로 보여 줍니다. 세 번째 상자, 동적 클라이언트 등록은 점선 테두리로 그려 deprecated임을 표시합니다. 제거된 것이 아니라는 뜻입니다. 여전히 동작하지만 클라이언트가 시작해야 할 자리는 더 이상 아닙니다. 사다리 옆의 작은 체크리스트는 인가 서버가 클라이언트 ID 메타데이터 문서에 대해 실제로 검증하는 것과, 자격 증명이 서버별이 아니라 발급자별로 키잉되게 되는 이유를 되풀이합니다. 코드를 열기 전에 클라이언트의 결정을 상자들 사이로 따라가 보세요. 이 인가 서버에 대해 이미 서류상 뭔가를 갖고 있는가, 인가 서버 자신의 메타데이터가 CIMD 지원을 언급하는가, 등록 엔드포인트를 노출하는가, 아니면 사람에게 묻는 것만 남았는가.

## 실습 랩

`code/main.py`를 열어 보세요. 이 코드는 다른 커패시티를 가진 세 개의 인가 서버를 모델링합니다. 하나는 CIMD 지원을 광고하고, 하나는 DCR `registration_endpoint`만 제공하며, 하나는 둘 다 제공하지 않습니다. `choose_registration_path`는 개념 절과 같은 우선순위를 걷습니다. 빈 미리 등록 저장소로 첫 번째 인가 서버에 대해 돌리면 `cimd`를 고릅니다. 그 인가 서버의 발급자가 이미 미리 등록 저장소에 들어 있는 채로 다시 돌리면, CIMD가 이용 가능함에도, 정확히 미리 등록이 먼저 검사되기 때문에 미리 등록이 대신 이깁니다. 두 번째 인가 서버에는 CIMD 지원이 없으므로 플래너는 `dcr`로 물러서고 결정에 deprecated 표시를 합니다. 세 번째는 둘 다 없으므로 플래너는 `ask-user`를 보고합니다.

```bash
python3 code/main.py
```

`validate_cimd`는 URL 모양의 클라이언트 id를 받았을 때 인가 서버의 몫을 연기합니다. URL이 실제 경로가 있는 https인지 검사하고, 문서에 `client_id`, `client_name`, `redirect_uris`가 있는지 검사하고, 문서의 `client_id`가 불러온 URL과 정확히 일치하는지 검사하며, 모든 리디렉션 URI가 https 또는 루프백 주소인지 검사합니다. 데모를 돌리고 네 개의 문서를 그것과 겨뎨 보세요. 유효한 하나는 문제 없이 통과하고, 하나는 자기 URL과 맞지 않는 `client_id`를 가지며, 하나는 `https` 대신 `http`를 쓰고, 하나는 `redirect_uris`가 아예 없습니다. 이어서 `CredentialStore`가 인가 서버 바인딩을 집행합니다. 자격 증명을 그것을 발행한 발급자 아래 등록하고, 다른 발급자로 `.use()`를 부르면 자격 증명이 실제로 속한 발급자가 정확히 이름 대어지는 `ValueError`를 던집니다. `ProxyConsentLedger`는 착란하는 부관 완화를 프록시가 명시적인 동의를 받은 정적-client-id와 다운스트림-client-id 짝들의 작은 집합으로 모델링합니다. `may_forward`는 그 정확한 짝에 대해 `record_consent`가 불리기 전까지는 false를 보고합니다. 마지막으로 `recommend_auth_extension`은 시나리오 설명에서 두 인가 익스텐션 사이를 고르고, 데모의 마지막 교환은 등록된 `acme-ops-cli` 클라이언트가 이미 client-credentials 토큰을 들고 실제 `server/discover`와 `tools/call`을 회선 위로 보내는 모습을 보여 줍니다. 토큰은 요청의 HTTP 헤더에 기록되는데, Streamable HTTP 요청이 실제로 실는 바로 그 헤더들입니다.

## 캡스톤 연계

캡스톤의 엔드투엔드 교환에는 인가된 호출이 포함되고, 그 호출에 제시할 토큰이 존재하는 것은 이 레슨의 어떤 등록 경로가 이미 돌았기 때문입니다. 미리 등록된 id, 불러와 검증한 CIMD, 또는 요즘은 덜하지만 DCR 왕복이요. 캡스톤의 클라이언트가 어느 길을 택했든, 그 자격 증명은 이곳에서 `CredentialStore`가 만드는 바로 그 형태인, 발급자로 키잉된 저장소에 앉아 있어야 합니다. 다음 레슨은 이 레슨이 멈춘 자리에서 바로 이어받습니다. 클라이언트가 자기가 누구인지 증명하고 나면, 동의가 실제로 무엇을 허락받는지를 결정합니다.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 클라이언트 등록 | MCP 클라이언트가 토큰을 청하기 전에 인가 서버가 알아볼 클라이언트 id를 손에 넣는 방법 |
| 클라이언트 ID 메타데이터 문서(CIMD) | 클라이언트가 자기 client_id URL에 직접 호스팅하는 HTTPS 문서로, 인가 서버가 필요할 때 불러와 검증함 |
| 동적 클라이언트 등록(DCR) | deprecated된 RFC 7591 등록 엔드포인트 흐름. 아직 CIMD 지원을 더하지 않은 인가 서버를 위해 남겨 둠 |
| 미리 등록 | 인가 서버와 미리 세워 둔 클라이언트 정보. 하드코딩되거나 사람이 입력함 |
| 인가 서버 바인딩 | 저장된 클라이언트 자격 증명을 그것을 발행한 발급자로 키잉하고, 다른 인가 서버에 절대 재사용하지 않는 것 |
| application_type | DCR 파라미터로, native 또는 web. OIDC 인가 서버에게 어떤 리디렉션 URI 형태를 기대해야 하는지 말해 줌 |
| 착란하는 부관(confused deputy) | 클라이언트별 동의 없이 하나의 정적 클라이언트 id로 수많은 다운스트림 클라이언트를 대신하는 프록시 |
| 인가 익스텐션 | 클라이언트가 토큰을 얻는 방식을 바꾸는 옵트인 협상 메커니즘. 예: OAuth Client Credentials, Enterprise-Managed Authorization |
