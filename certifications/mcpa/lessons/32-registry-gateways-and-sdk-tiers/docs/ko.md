# 서버를 찾고, 라우팅하고, 신뢰하기

> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [en.md](en.md)

> 레지스트리의 이름은 누가 서버를 게시했는지에 대한 주장이지, 그 서버가 무엇을 하는지에 대한 보장이 아닙니다. 게이트웨이는 요청이 그 서버에 닿아도 되는지를 정합니다. SDK의 등급은 그 구현이 프로토콜을 실제로 얼마나 말하는지를 말해 줍니다. 별개의 세 질문, 별개의 세 답입니다.

**유형:** 참고 자료
**언어:** Python
**선수 지식:** 레슨 31
**시간:** 약 45분

## 학습 목표

- MCP 레지스트리가 무엇을 저장하고 무엇을 의도적으로 저장하지 않는지, 왜 공개 접근 가능한 서버만 받는지, 그리고 왜 현재 프리뷰 단계인지 설명합니다
- 서버의 역방향 DNS 네임스페이스를 레지스트리가 하는 방식 그대로 검증합니다 — GitHub 인증 또는 도메인 기반 인증으로 — 그리고 그것을 패키지 레지스트리가 검사하는 소유권 증명과 분리합니다
- server.json 항목의 packages와 remotes를 읽고, 그 스키마 버전이 왜 서버가 런타임에 실제로 말하는 프로토콜 버전과 독립인지 설명합니다
- 상태 없는(stateless) 게이트웨이가 책임지는 것을 설명합니다: 요청 본문과 대조해 Mcp-Method와 Mcp-Name을 검증하고, 그 헤더 쌍으로 라우팅하고, 자기만의 캐시 권위를 발명하는 대신 cacheScope를 존중하는 것
- SDK의 적합성 등급을 이식성·신뢰 신호로 쓰고, 등급이 어떻게 얻어지고 어떻게 잃어지는지 설명합니다

## 문제 상황

한 팀이 서드파티 MCP 서버를 내부 어시스턴트에 추가하기로 결정합니다. 별개의 세 질문이 즉시 나타나고, 셋이 하나의 답을 공유하지 않습니다. 팀은 후보 서버를 어디서 찾고, 그것이 게시된 이름이 실제로 그 이름이 주장하는 회사에 — 그 이름을 폼에 먼저 타이핑한 누군가가 아니라 — 속한다는 것을 어떻게 아나요? 서버가 승인되면, 모든 내부 클라이언트가 어떻게 하나의 앞문을 거쳐 도달하게 하면서, 누가 무엇을 호출할 수 있는지 강제하는 곳을 하나 두고, 그 앞문이 라우팅만 하려고 모든 요청 본문을 완전히 이해해야 하는 두 번째 파서가 되지 않게 할까요? 소비만 하다가 자기 서버를 지을 준비가 됐을 때, 어떤 SDK 위에 지어도 안전할까요 — 프로토콜 자체가 2년 동안 네 번이나 움직였는데요.

그 세 질문은 프로토콜 안이 아니라 그 주위에 있는 세 조각의 인프라에 대응합니다: MCP 레지스트리, 게이트웨이, SDK 등급 시스템. 이것들을 하나의 연속된 공급망처럼 취급하고 싶어집니다 — 레지스트리에 게시하고, 게이트웨이로 라우팅하고, SDK를 신뢰하고. 그러나 각 층은 좁고 서로 다른 것을 증명하며, 시험은 한 층의 보장이 어디서 끝나고 다음 층의 보장이 어디서 시작하는지 정확히 아는 것에 값을 줍니다. 레지스트리는 누가 이름을 게시했는지 증명합니다. 그 이름 뒤의 코드를 취약점 검사하지 않고, 서버를 실행해서 행동을 지켜보지도 않습니다. 게이트웨이는 요청이 잘 구성되어 있고 진행이 허용되었음을 증명합니다. 라우팅하는 백엔드를 원래 누가 게시했는지는 알지도, 보증하지도 않습니다. SDK의 등급은 하나의 구현에 대한 유지보수·완성도 신호입니다. 그 SDK로 지어진 어떤 특정 서버에 대해서도, 게시된 어떤 특정 목록 항목에 대해서도 아무 말도 하지 않습니다. 이 셋을 뒤섞는 것이 바로 Use Cases and Ecosystem 도메인이 시험하도록 설계된 시나리오 문제 유형입니다.

## 핵심 개념

### 레지스트리: 메타데이터, 코드가 아님

MCP 레지스트리는 공개 접근 가능한 MCP 서버를 위한 공식, 중앙 호스팅 메타데이터 인덱스이며, 명시적으로 프리뷰입니다: 메인테이너들은 일반 공급(GA)에 이르기 전에 파괴적 변경이나 데이터 초기화가 일어날 수 있다고 경고합니다. 저장하는 것은 게시된 버전별 `server.json` 문서입니다: 역방향 DNS 이름, 제목과 설명, 버전 문자열, 그리고 `packages` 배열, `remotes` 배열, 또는 둘 다. 레지스트리는 서버 자체를 결코 호스팅하지 않습니다. `packages` 항목은 `registryType`(`npm`, `pypi`, `nuget`, `cargo`, `oci`, 그리고 미리 빌드된 바이너리 릴리스를 위한 `mcpb`)과, npm·PyPI·Docker Hub 같은 패키지 레지스트리가 실제로 서빙하는 `identifier`를 이름 댑니다. `remotes` 항목은 전송 방식 — `streamable-http` 또는 폐기된 `sse` — 와 서버가 직접 답하는 URL을 이름 대고, 다중 테넌트 URL 템플릿을 위한 `variables`와 클라이언트가 보내야 할 값들을 위한 `headers`를 둘 수 있습니다. 레지스트리는 둘을 한꺼번에 실을 수 있어서 호스트가 선호하는 설치 경로를 고를 수 있습니다.

```json
{
  "$schema": "https://static.modelcontextprotocol.io/schemas/2025-12-11/server.schema.json",
  "name": "io.github.acme/weather-mcp",
  "title": "Weather",
  "version": "1.0.0",
  "packages": [
    {"registryType": "npm", "identifier": "@acme/weather-mcp", "version": "1.0.0", "transport": {"type": "stdio"}}
  ],
  "remotes": [
    {"type": "streamable-http", "url": "https://weather.acme.example/mcp"}
  ]
}
```

`$schema` 필드에 주목하세요: 이것은 `server.json` 자체의 모양을 묘사하는 스키마 개정판 — 이 예제에서는 `2025-12-11` — 을 이름 댑니다. 그 날짜는 실행 중인 서버가 클라이언트가 `server/discover`를 호출하는 순간 회선 수준에서 실제로 협상하는 MCP 프로토콜 버전, `2026-07-28`, 과 아무 관련이 없습니다. 레지스트리 항목은 더 새로운 개정판이나 더 오래된 개정판에 대해 검증을 통과할 수 있으면서, 그 뒤의 서버는 자기가 좋아하는 프로토콜 버전을 말할 수 있습니다. 두 날짜는 완전히 별개로 추적되고 버전이 매겨지며, 그것들을 같은 사실로 읽는 것이 바로 시나리오 문제가 파 놓은 함정입니다.

이름 자체가 레지스트리의 신뢰 메커니즘입니다. 이름은 역방향 DNS 형식을 따릅니다. GitHub 인증 게시자에게는 `io.github.username/server`나 `io.github.orgname/server`, 그리고 `example.com` 도메인을 통제함을 증명한 게시자에게는 — DNS TXT 레코드나 잘 알려진 경로의 HTTP 파일을 통해 — `com.example/server`. 이 네임스페이스 인증이 자기가 대표하지 않는 회사의 이름을 딴 서버를 무관한 당사자가 게시하는 것을 막습니다: 레지스트리는 주어진 권위 아래의 게시를, 그 권위를 소유했음을 증명한 게시자에게만, 게시 시점에, 매번 받아들입니다. 그 검사는 패키지 레지스트리가 기반이 되는 아티팩트에 대해 수행하는 소유권 검사와 별개입니다: npm은 `package.json`의 `mcpName` 필드를 찾고, PyPI·NuGet·Cargo는 렌더링된 README에서 `mcp-name: name` 문자열을 찾으며(Cargo는 보이는 텍스트로 필요로 합니다. crates.io가 PyPI와 NuGet이 보존하는 HTML 주석을 벗겨 내기 때문입니다), Docker나 OCI 이미지는 `io.modelcontextprotocol.server.name` 레이블을 찾습니다. 두 개의 별개 증명 — 레지스트리의 이름에 대한 것과 이름이 가리키는 아티팩트에 대한 것 — 이 모두 `server.json`과 일치해야 목록 항목이 신뢰할 수 있습니다.

버전 관리에는 암기해 둘 만한 좁은 규칙들이 있습니다. 버전 문자열은 게시마다 고유해야 하고 게시된 뒤에는 불변입니다. 시맨틱 버저닝이 권장되며 레지스트리가 목록 항목에 "latest"를 자동으로 표시하게 하지만, 하나의 정확한 버전이 아니라 버전 범위처럼 보이는 문자열 — `^1.2.3`, `~1.2.3`, `>=1.2.3`, `1.x` — 은 완전히 금지됩니다. 레지스트리는 범위를 하나의 아티팩트로 해석할 방법이 없기 때문입니다. 레지스트리는 무엇을 아예 목록에 올릴지에 대해서도 의도적으로 좁습니다: 공개 접근 가능한 서버만 받습니다. 즉 패키지가 공개 패키지 레지스트리에 있거나 원격 URL이 공개 인터넷에 응답해야 합니다. 프라이빗 네트워크나 프라이빗 패키지 피드 안에서만 도달 가능한 서버는 여기에 게시될 수 없고, 그것이 필요한 팀은 같은 공개 OpenAPI 인터페이스를 구현하는 자기만의 레지스트리를 운영합니다. 보안 스캔은 외부에 위임됩니다 — 기반이 되는 패키지 레지스트리와 다운스트림 애그리게이터에게요. 그리고 레지스트리 자신의 관리(modertaion)는 의도적으로 관대합니다: 불법 콘텐츠, 악성코드, 스팸, 동작하지 않는 서버는 제거하지만, 저품질이거나 버그가 있거나 취약하거나 다른 것의 중복이라는 이유만으로 서버를 제거하지는 않는다고 명시합니다. 호스트 애플리케이션은 공식 레지스트리를 직접 조회하도록 만들어진 것이 아예 아닙니다: 다운스트림 애그리게이터나 마켓플레이스를 소비하도록 만들어졌고, 그것이 레지스트리의 읽기 전용 REST API를 드문 주기로 폴링하고, 자기 사본을 유지하며, 그 위에 큐레이션, 평점, 자체 보안 스캔을 얹을 수 있습니다.

### 게이트웨이: 신뢰가 아니라 회선으로 라우팅

게이트웨이는 하나 이상의 백엔드 MCP 서버 앞에 앉아 그 뒤의 모든 클라이언트에게 하나의 MCP 엔드포인트를 내보입니다. 상태 없는 핵심이 세션을 제거했기 때문에, 게이트웨이는 세션을 아는 설계가 한때 그러했듯 클라이언트를 하나의 백엔드 복제본에 고정할 필요가 없습니다. 어떤 건강한 인스턴스든 어떤 자기 완결적 요청이든 답할 수 있습니다. 레슨 04의 복제본들이 요청을 자유롭게 주고받게 한 바로 그 보장이죠. 게이트웨이가 정말로 필요한 것은 요청이 어디로 가는지, 그리고 애초에 그곳으로 가도 되는지를 빠르게 결정하는 방법이고, 이것이 바로 레슨 19의 Streamable HTTP 헤더 미러가 존재하는 이유입니다. 모든 POST는 `MCP-Protocol-Version`과 `Mcp-Method`를, 그리고 `tools/call`, `resources/read`, `prompts/get`에는 `Mcp-Name`을 실습니다. 게이트웨이는 그 헤더들을 읽어 경로를 고르고 정책을 적용합니다. 빠른 경로에서는 JSON-RPC 본문을 역직렬화하고 완전히 이해하기 전에요.

헤더는 라우팅 지름길이지, 결코 두 번째 진실의 원천이 아닙니다. 게이트웨이(또는 그 뒤의 백엔드)가 요청을 유효한 것으로 취급하기 전에, 헤더 값이 대응하는 본문 필드와 일치하는지 확인해야 합니다: `Mcp-Method`는 `method`와, `Mcp-Name`은 `params.name` 또는 `params.uri`와, `MCP-Protocol-Version`은 `params._meta["io.modelcontextprotocol/protocolVersion"]`와요. 불일치는 어떤 백엔드 조회도 일어나기 전에 `HeaderMismatch`, 코드 `-32020`, HTTP `400`으로 거부됩니다. 그 검사를 건너뛰는 것은 작은 지름길이 아닙니다: 헤더만 보고 라우팅하고 본문을 실행하는 게이트웨이는, 로깅과 호출 한도를 한 도구에 적용하면서 실제로는 완전히 다른, 더 민감한 도구가 실행되는 속임수에 넘어갈 수 있습니다.

```http
POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: prompts/get
Mcp-Name: lookup_account

{"jsonrpc": "2.0", "id": 7, "method": "tools/call", "params": {"name": "lookup_account", "arguments": {"accountId": "acct-1"}, "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28", "io.modelcontextprotocol/clientCapabilities": {}}}}
```

```json
{"jsonrpc": "2.0", "id": 7, "error": {"code": -32020, "message": "Header mismatch: Mcp-Method", "data": {"headers": ["Mcp-Method"]}}}
```

게이트웨이의 다른 책임들도 전부 같은 규율 — 프로토콜이 부여한 적 없는 권위를 더하지 않으면서 정책을 더하는 — 에서 나옵니다. 어떤 주체(principal)가 어느 백엔드와 도구에 도달할 수 있는지 강제하고, 레거시 `-32000`부터 `-32019` 코드를 재발행하지 않으며, 사양이 이미 정의한 것 위에 `-32020`부터 `-32099` 예약 대역 안에서 새 코드를 발명하지도 않습니다. 캐시 가능한 결과를 전달할 때 — `server/discover`, `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read` — 벗겨내는 대신 `ttlMs`와 `cacheScope`를 그대로 통과시킵니다. 호출하는 클라이언트가 그 힌트에 의존하기 때문입니다. 시험이 좋아하는 세부는 `cacheScope` 안에 있습니다: `"private"` 결과는 요청이 그 외에는 똑같아 보이더라도 서로 다른 두 호출자에게 절대 서빙될 수 없고, `"public"` 결과는 자유롭게 공유될 수 있습니다. 게이트웨이 자신의 캐시는 원본 서버의 힌트 위에 얹는 최적화일 뿐, private 결과를 편해서 그냥 공유로 승격시킬 수 있는 새 권위가 결코 아니며, 모든 private 캐시 항목을 인증된 호출자로 분할합니다. 요청의 모양만으로가 아니요요. 마지막으로, 게이트웨이는 한 호출자의 토큰을 종단하고 업스트림을 호출할 때 다른 토큰을 발행하거나 재사용하는 장소가 아닙니다. 토큰 전달은 프로토콜의 어느 곳에서나 금지되는 것과 같은 이유로 금지됩니다 — 레슨 23에서 완전히 다뤘죠. 그리고 호출자의 정체로 로그를 남기거나 캐시 항목을 분할하는 게이트웨이라도, 그 정체를 백엔드에 전달하는 JSON-RPC 메시지 안에 넣어서는 안 됩니다.

### SDK 등급: 스캔이 아니라 이식성 신호

이 커리큘럼의 모든 서버와 클라이언트는 어떤 SDK를 기준으로 쓰여 있고, SDK 등급 시스템(SDK Tiering System)은 생태계가 주어진 SDK 빌드가 장기 인프라를 지을 수 있을 만큼 안전한지를 측정하는 방법입니다. Tier 1은 자동화된 적합성(conformance) 테스트 스위트에서 100퍼센트 통과율, 다음 사양 릴리스와 함께 또는 그보다 먼저 새 프로토콜 기능 출시, 이슈 분류(확인과 라벨링이지 반드시 수정이 아니라)를 2영업일 안에, 치명적 등급 버그를 7일 안에 수정, 문서화된 파괴적 변경 정책을 갖춘 안정적 비프리릴리스 버전 최소 하나, 포괄적인 문서, 공개된 의존성 업데이트 정책, 공개된 로드맵을 요구합니다. Tier 2는 80퍼센트 적합성, 6개월 안의 새 기능, 한 달 안의 분류, 2주 안의 치명적 버그 수정, 안정 릴리스 하나, 기본 문서, 그리고 Tier 1을 향한 계획 또는 Tier 2에 머무는 명시된 이유를 요구합니다. Tier 3은 그 어느 것에도 최소 기준이 없습니다: 실험적이거나 부분 구현이거나 좁게 특화된 SDK가 타임라인 약속 전혀 없이 여기 삽니다. Tasks나 MCP Apps 같은 확장은 어느 등급에도 절대 요구되지 않습니다. 확장은 설계상 옵트인이므로 SDK가 주어진 확장을 구현하지 않은 채 핵심 프로토콜의 완전 적합 Tier 1 구현일 수 있습니다.

등급은 일회성 인증서가 아닙니다. 적합성은 현재 안정 릴리스를 기준으로 계속 측정되고, 어떤 적합성 테스트든 4주 연속 실패하는 SDK는 Tier 1에서 Tier 2로 떨어지며, 테스트의 20퍼센트 이상을 4주간 실패하면 Tier 2에서 Tier 3으로 떨어집니다. 2개월 동안 해결되지 않은 채 앉아 있는 이슈도 강등을 촉발할 수 있습니다. 등급을 올리는 것은 반대 방향으로 흐릅니다: 메인테이너가 공개된 요구사항을 기준으로 자가 평가하고, 뒷받침 증거와 함께 이슈를 열고, 자동화된 적합성 스위트를 통과하고, SDK 워킹 그룹의 서명을 받습니다. 이것이 레슨 02의 N+M 이식성 논거로 돌아가는 연결 조직입니다. 준수를 주장하는 회선 형식과 모든 필수 동작을 실제로 올바르게 구현하는 SDK는 같은 것이 아닙니다. Tier 2나 Tier 3 SDK는 `_meta`를 조용히 잘못 처리하거나, 필수 헤더를 건너뛰거나, 레슨 14의 MRTR 재시도에서 오작동할 수 있습니다. 클라이언트 간 이식성은 미리 외워 둔 고정된 표가 아닙니다. 런타임과 빌드 타임에 검사하는 두 가지의 조합입니다: 클라이언트가 레슨 07의 `server/discover`에서 만드는 요청별 기능 선언, 그리고 당신이 의지하는 클라이언트나 서버 뒤에 실제로 앉아 있는 SDK의 등급.

## 인터랙티브 랩

그림은 하나의 서버가 게시에서 실제 호출까지 가는 과정을 추적합니다. 왼쪽에서는 네임스페이스의 소유권을 증명한 게시자가 `server.json`을 제출하고, 레지스트리는 네임스페이스 검사와 공개 전용 검사 둘 다 통과한 뒤에야 그것을 받아들입니다. 애그리게이터는 자기 주기로 레지스트리를 폴링해 호스트 애플리케이션 쪽으로 재게시하며, 반대 방향은 절대 아닙니다. 오른쪽에서는 클라이언트의 게이트웨이 요청이 본문과 함께 `Mcp-Method`와 `Mcp-Name`을 실어 옵니다. 게이트웨이의 헤더 대 본문 검사는 두 갈래로 나뉩니다. 일치하면 올바른 백엔드로 진행하고, 불일치하면 어떤 백엔드도 건드리기 전에 `-32020`으로 변합니다. 그 아래 세 개의 등급 배지는 이 레슨의 코드가 데이터로 인코딩하는 같은 적합성 백분율을 보여 줍니다. 하나의 이름을 왼쪽 끝에서 오른쪽 끝까지 따라가 보고, 올바르게 등록되었다는 것이 게이트웨이에서 요청에게 특별한 대우를 주지 않는다는 것을 눈치채세요. 그 둘은 별개의 관문입니다.

## 실습 랩

`code/main.py`를 열어 보세요. `admit_to_registry`는 레지스트리 자신의 승인 검사를 작은 순수 함수로 모델링합니다: 주장된 이름을 `split_namespace`로 권위(authority)와 슬러그로 쪼개고, 호출한 게시자가 검증한 적 없는 네임스페이스를 거부하고, `"private"`인 `visibility`를 거부하고, `looks_like_version_range`가 표시하는 버전 문자열을 거부합니다. 어떤 게시자로 자기 자신의 검증된 네임스페이스에 대해 한 번, 다른 게시자로 같은 주장된 이름에 대해 한 번 실행하고, 각각의 `reason` 문자열을 비교해 보세요. `resolve_install_target`은 서버 설치 방법을 정하는 호스트가 그러듯 `packages` 또는 `remotes` 항목을 읽습니다. `schema_version_from_url`은 `$schema` URL에서 스키마 날짜를 끄집어 내서, 그것이 `PROTOCOL_VERSION` 바로 옆에 — 그리고 그것과 독립적으로 — 앉아 있는 것을 볼 수 있게 합니다.

`Gateway` 클래스가 실제 MCP를 말하는 부분입니다. `call_tool`과 `read_resource`는 평범한 요청을 만들고, Streamable HTTP 클라이언트가 보낼 헤더를 `_headers_for`로 계산하고, `self.routes.get(headers["Mcp-Name"])`으로 라우팅합니다. 헤더 값 자체로요. 본문을 다시 읽는 것이 아닙니다. 이름을 헤더로 미러링하는 것의 요점이 바로 그것입니다. `_validate_headers`를 읽고 무엇이 백엔드에 닿기 전에 세 필드를 모두 검사하는지 확인하세요. 그다음 `call_tool_with_mismatched_method_header`를 읽어 보세요: 완벽하게 유효한 요청 본문을 만든 뒤 `Mcp-Method` 헤더만 바꾸고, 게이트웨이 운영자가 회선에서 볼 것을 정확히 볼 수 있게 그 한 항목을 `"violation"`으로 감싸 로그에 남긴 뒤, 바로 이어서 실제 `-32020` 응답을 보여 줍니다. 시나리오를 실행하고 `token-alice`가 private 리소스를 두 번 읽고 `token-bob`이 같은 URI를 한 번 읽은 뒤의 `accounts.read_count`를 지켜 보세요. 개수는 3이 아니라 2입니다. alice의 두 번째 읽기는 캐시 히트였고 bob의 것은 아니었기 때문입니다. private 캐시가 둘 사이를 절대 넘지 않았다는 증명이죠. 같은 두 호출자가 public 리소스를 읽은 뒤의 `status.read_count`와 비교해 보세요. 개수는 1에 머뭅니다. 마지막으로, 그 토큰으로 `call_tool`을 호출한 뒤 `gateway.log`의 모든 항목에서 리터럴 문자열 `"secret-token-value"`를 검색해 보세요. 절대 나타나지 않습니다. 토큰은 게이트웨이 자신의 캐시 분할 로직 안에서만 존재하고, 그것이 전달하는 메시지 안에는 결코 없기 때문입니다.

```bash
python3 code/main.py
```

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| MCP 레지스트리(MCP Registry) | 공개 접근 가능한 server.json 목록 항목들의 공식 프리뷰 단계 메타데이터 인덱스 |
| server.json | 레지스트리 항목이 저장하는 메타데이터 문서: 이름, 버전, 그리고 packages 또는 remotes |
| 네임스페이스 검증(Namespace verification) | 게시자가 주장된 이름의 권위를 통제함을 증명하는 것. GitHub 또는 도메인 챌린지를 통해 |
| 애그리게이터(Aggregator) | 레지스트리의 REST API를 폴링해 호스트 애플리케이션 쪽으로 재게시하는 다운스트림 소비자 |
| 서브레지스트리(Subregistry) | 호스트 애플리케이션을 위해 레지스트리 자신의 OpenAPI 인터페이스까지 구현하는 애그리게이터 |
| 게이트웨이(Gateway) | 하나 이상의 백엔드 앞의 단일 MCP 엔드포인트. 요청별로 라우팅하고 정책을 강제한다 |
| HeaderMismatch | 미러링된 헤더가 요청 본문과 어긋날 때 게이트웨이나 서버가 돌려주는 `-32020` 오류 |
| cacheScope | 캐시 가능한 결과에 붙는 `public` 또는 `private` 힌트. private 항목은 절대 호출자를 넘지 못한다 |
| SDK 등급(SDK tier) | 테스트 결과를 기준으로 계속 측정되는 적합성·유지보수 평점(Tier 1, 2, 3) |
| 강등(Relegation) | 4주 연속의 적합성 실패 뒤 SDK의 등급을 떨어뜨리는 규칙 |
