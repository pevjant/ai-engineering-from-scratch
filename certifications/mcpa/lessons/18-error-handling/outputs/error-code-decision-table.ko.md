# 오류 코드 판단 표

MCP 2026-07-28 요청이 실패했을 때 올바른 채널, 코드, 데이터 모양, HTTP 상태를 고르기 위한 한 페이지 참고 자료입니다. 전체 풀이는 `docs/en.md`와 함께 보세요. 출처: `certifications/mcpa/research/mcp-2026-07-28-brief.md`, 5절.

## 단계 1: 채널 고르기

| 실패의 대상 | 채널 | 모양 |
|---|---|---|
| 요청 자체: 모르는 메서드, 모르는 도구, 잘못된 형식의 봉투(envelope), 서버 고장 | 프로토콜 오류 | `{"jsonrpc": "2.0", "id": ..., "error": {"code": ..., "message": ..., "data": ...}}` |
| 도구가 실행된 뒤 마주한 것: 잘못된 입력, 실패한 API 호출, 비즈니스 규칙, 만료된 핸들 | 도구 실행 오류 | 정상적인 `complete` 결과: `{"content": [...], "isError": true}` |

어느 쪽이 맞는지 확실하지 않다면 도구 실행 오류를 택하세요. 프로토콜 오류 채널에 속하는 건 모르는 도구, 잘못된 형식의 요청, 서버 고장뿐입니다. 모델은 프로토콜 오류를 `isError` 콘텐츠처럼 읽고 대응할 수 없습니다.

## 단계 2: 코드 고르기 (프로토콜 오류만)

| 코드 | 이름 | 발동 조건 | HTTP 상태 |
|---|---|---|---|
| -32700 | Parse error | 바디가 유효한 JSON이 아님. 읽을 수 있었던 id가 없어서 `id`는 `null` | 명세가 정하지 않음. 보통 400 |
| -32600 | Invalid Request | 유효한 JSON이지만 잘 만들어진 JSON-RPC 2.0 객체가 아님 | 명세가 정하지 않음 |
| -32601 | Method not found | 메서드 자체가 이 서버가 구현한 목록에 없음 | 404 |
| -32602 | Invalid params | 모르는 도구, 필수 `_meta` 누락, 리소스를 찾을 수 없음, 잘못된 프롬프트 이름이나 인자, 잘못된 커서, 잘못된 로그 레벨 | 400 |
| -32603 | Internal error | 서버 자신이 실패함 | 명세가 정하지 않음 |
| -32020 | HeaderMismatch | HTTP 헤더가 바디와 불일치하거나 필수 헤더가 없음 | 400 |
| -32021 | MissingRequiredClientCapability | 서버에 기능이 필요한데 이 요청의 `clientCapabilities`가 그것을 선언하지 않았음. `data.requiredCapabilities`를 실음 | 400 |
| -32022 | UnsupportedProtocolVersion | 요청된 프로토콜 버전이 지원되지 않음. `data.supported`와 `data.requested`를 실음 | 400 |

## 단계 3: 절대 내보내지 않는 것들

| 코드 | 금지된 이유 |
|---|---|
| -32000부터 -32019 | 2026-07-28 할당 정책 이전의 구버전 하위 범위. 새 구현체는 이 범위의 코드를 할당하거나 사용해서는 안 됩니다. |
| -32002 | 2025-11-25까지의 리소스-not-found 코드였습니다. SEP-2164가 이를 -32602로 대체했습니다. |
| -32042 | URL 일러시테이션 필요 코드였습니다. 2025-11-25 전용이며 대체 코드가 없습니다. 대신 일러시테이션 흐름을 사용하세요. |
| 그 밖의 -32020부터 -32099 | MCP 명세를 위해 예약됨. 정의된 것은 -32020, -32021, -32022뿐이며, 이 범위 안의 정의되지 않은 코드는 금지됩니다. |

규격을 따르는 구현체는 이런 코드들 중 하나가 소켓에 도달한 '후'가 아니라 도달하기도 '전에' 만드는 것을 거부해야 합니다. 오류 응답을 조립하는 함수(예: `code/main.py`의 `safe_error`)에 거부 로직을 심어 두면 금지된 숫자가 프로세스 밖으로 나갈 수 없습니다.

## 단계 4: 애플리케이션 정의 코드를 올바른 자리에 놓기

정의된 MCP 코드도 `isError`도 맞지 않는다면 새 코드는 `-32768`부터 `-32000`까지의 범위 밖에 있어야 합니다(예: 자기 클라이언트와 서버끼리 합의한 작은 양의 정수). 그 전에 먼저 `isError`를 택하는 것이 좋습니다. SEP-1303은 바로 모델이 스스로 읽고 고칠 수 있는 문제에 구현체들이 코드를 만들어 내는 일을 막기 위해 존재합니다.

## JSON-RPC 코드가 없는 전송 계층 이벤트

| 이벤트 | HTTP 상태 | JSON-RPC 오류를 실어 오나? |
|---|---|---|
| 알림 POST 수락됨 | 202 Accepted | 아니요, 바디 자체가 없음 |
| MCP 엔드포인트로의 GET 또는 DELETE | 405 Method Not Allowed | 아니요 |
| bearer 토큰 누락 또는 무효 | 401 Unauthorized | 아니요, OAuth 계층의 응답 |
| 불충분한 스코프(scope) | 403 Forbidden | 아니요, OAuth 계층의 응답 |

## "요청 id는 언제나 에코한다"의 유일한 예외

오류 응답이 `id`를 생략하는 경우는 id를 아예 읽을 수 없었을 때뿐입니다. 예를 들어 원시 바디의 파싱 실패가 그렇습니다. 그 외의 모든 응답(결과든 오류든)은 요청이 실었던 바로 그 id를 실습니다.
