# 요청이 실패하는 두 가지 경로

> 실패한 요청이 제 멋대로 새 오류 표현을 만들어내는 일은 없습니다. MCP 2026-07-28은 작은 숫자 집합을 고정해 두고, 모든 실패를 두 채널 중 하나로 분류하며, 절대 써서는 안 되는 숫자 목록까지 확실하게 막아 둡니다.

**유형:** 참조(Reference)
**언어:** Python
**선수 지식:** 레슨 17
**시간:** 약 45분

## 학습 목표

- 프로토콜 오류와 도구 실행 오류를 구별하고, 주어진 실패에 대해 서버가 어느 쪽 채널을 써야 하는지 알아봅니다
- MCP가 예약한 세 개의 오류 코드(-32020, -32021, -32022)와 각 코드가 담고 있는 데이터를 짚어 봅니다
- 2026-07-28 오류 코드 할당 정책을 적용해 봅니다: 레거시 하위 범위, 예약 하위 범위, 그리고 애플리케이션이 직접 정의한 코드가 속할 자리
- JSON-RPC 오류 코드를, Streamable HTTP 서버가 함께 반환해야 하는 HTTP 상태 코드와 짝지어 봅니다
- 2026-07-28 구현체가 -32002와 -32042를 절대 내보내면 안 되는 이유와, 각각을 대신한 것은 무엇인지 설명합니다

## 문제 상황

실패에 대해 깊이 고민해 본 적 없는 서버는 코드를 작성하다가 그때그때 제 맘대로 오류 표현을 만들어 댑니다. 빠진 인자에는 임시방편 코드 하나, 하위 서비스 타임아웃에는 또 다른 코드 하나, 권한 문제는 메시지 필드 깊숙이 만들어 낸 문자열 하나로 처리됩니다. 그런 오류는 아무 데도 전달되지 않습니다. 다른 팀이 만든 클라이언트 입장에서는 어떤 서버가 화요일에 마음 내킨 대로 고른 숫자가 실제로 무슨 뜻인지 알 방법이 없고, 똑같이 편해 보이는 숫자(예: -32001)를 손에 댄 두 서버가 서로 전혀 관련 없는 의미로 그 숫자를 쓰고 있을 수도 있습니다. 이건 가정이 아닙니다. 2026-07-28 할당 정책이 생기기 전에는 공식 MCP SDK들끼리도 '리소스 없음' 하나만 놓고 코드가 서로 달랐습니다. 넷은 -32002를 썼고, 하나는 -32602를, 하나는 -32603을 썼으며, 하나는 그냥 0을 썼습니다. 서버들 사이에서 "리소스를 찾을 수 없음"을 안정적으로 감지하고 싶은 클라이언트는 SDK마다 특수 처리를 해야 했습니다.

비용은 판단 여지가 가장 적은 참여자에게 제일 크게 돌아옵니다. 바로 다음에 뭘 할지 결정하는 모델입니다. 도구 호출이 실패했는데 불투명한 JSON-RPC 오류로 돌아오고, 그 오류를 클라이언트가 모델의 컨텍스트에 닿기도 전에 삼켜 버리면 모델은 배울 게 아무것도 없습니다. 모델은 똑같이 깨진 호출을 되풀이하거나, 인자 하나만 고쳤으면 끝났을 작업을 그대로 포기해 버립니다. 레슨 17의 라이프사이클 체크포인트가 이미 윤곽을 그려 놓았습니다. 검증, 커패시티 확인, 실행 각각이 실패할 수 있고, 모든 실패를 똑같이 취급하면 호출자가 복구에 쓸 수 있었던 정보를 그냥 버리는 셈입니다. 이 레슨은 정확한 숫자, 각 숫자가 실리는 정확한 채널, 그리고 영원히 사용이 금지된 숫자들까지 채워 넣습니다.

## 개념

MCP의 모든 실패는 두 채널 중 정확히 하나에 실려 돌아옵니다. 그리고 어떤 채널을 고를지가, 명세 자체의 표현을 빌리면, 오류 모델 전체에서 가장 많이 시험에 나오는 구분점입니다.

**프로토콜 오류(protocol error)** 는 요청 자체가 잘못됐다는 뜻입니다. 메서드가 존재하지 않거나, 이름을 부른 도구가 이 서버에 없거나, 필수 필드가 빠졌거나, 서버 내부에서 고장이 났습니다. 이건 표준 JSON-RPC 오류 객체이고, 클라이언트는 보통 이걸 모델에 보여 주지 않고 자기 손으로 처리합니다:

```json
{
  "jsonrpc": "2.0",
  "id": 6,
  "error": {
    "code": -32602,
    "message": "Unknown tool: delete_everything"
  }
}
```

**도구 실행 오류(tool execution error)** 는 요청 자체는 정상이었고 서버도 도구를 실행했으며, 도구가 호출자가 고칠 수 있는 문제에 부딪혔다는 뜻입니다. 빠졌거나 형태가 틀린 인자, 하위 API 실패, 입력이 어긴 비즈니스 규칙, 만료된 핸들이 그 예입니다. 이건 `isError: true`가 붙은 정상적인 `complete` 결과이며, 모델이 읽고 스스로 고칠 수 있는 내용이 그대로 담긴 유일한 채널입니다:

```json
{
  "jsonrpc": "2.0",
  "id": 4,
  "result": {
    "resultType": "complete",
    "content": [{"type": "text", "text": "resolution is required for close_ticket"}],
    "isError": true
  }
}
```

2026-07-28 이전에는 이 구분에 관한 명세의 안내 자체가 모호했습니다. 초판 개정안은 "잘못된 인자(invalid arguments)"는 프로토콜 오류로, "잘못된 입력 데이터(invalid input data)"는 도구 실행 오류로 묘사했지만 둘 사이에 깔끔한 경계선은 그어 주지 않았습니다. SEP-1303이 이 간극을 메워서 둘 다 도구 실행 오류로 통합했습니다. 필수 필드 누락, 잘못된 타입, 범위를 벗어난 값 — 이 모든 것은 `isError: true`이고, 결코 `-32602`가 아닙니다. 알 수 없는 도구(unknown tool)만이 프로토콜 오류로 남습니다. 인자에는 뭘 고칠 여지가 없고, 그 도구 자체가 존재하지 않기 때문입니다.

표준 JSON-RPC 2.0 코드들이 기본 프로토콜 실패를 담당합니다: `-32700` 파싱 오류(본문이 유효한 JSON이 아니라서 읽어 낼 `id`가 없었기에 `id`가 `null`로 보고됨), `-32600` 잘못된 요청(JSON은 유효하지만 형태가 갖춰진 JSON-RPC 객체가 아님), `-32601` 메서드 없음(그 메서드 자체가 이 서버가 구현하지 않은 것), `-32602` 잘못된 파라미터(알 수 없는 도구, 필수 `_meta`가 빠진 요청, 존재하지 않는 리소스, 잘못된 프롬프트 인자, 잘못된 페이지네이션 커서), `-32603` 내부 오류(서버 자신이 실패함). `-32601`과 `-32602` 사이의 간극은 이것만 따로 외워 둘 가치가 있습니다. `-32601`은 *메서드*에 관한 것이고, `-32602`는 *요청의 그 밖의 모든 문제*, 즉 서버가 한 번도 들어 본 적 없는 도구 이름까지 포함합니다.

JSON-RPC는 `-32000`부터 `-32099`까지를 구현체가 정의하는 서버 오류 영역으로 예약해 두고, 2026-07-28 할당 정책이 이 공간을 깔끔하게 나눕니다. `-32000`부터 `-32019`까지는 레거시입니다. 이 정책이 생기기 전에 구현체들이 가져다 쓰던 코드들입니다. 새 구현체는 이곳에 아무것도 할당해서는 안 되며, 하위 범위 전체를 피하는 것이 좋습니다. `-32020`부터 `-32099`까지는 명세 자체를 위해 예약된 영역이고, 그중 정의된 코드는 세 개뿐입니다:

```json
{"code": -32020, "message": "Header mismatch: Mcp-Name header value 'foo' does not match body value 'bar'"}
```

`-32020`은 `HeaderMismatch`입니다. HTTP 헤더가 요청 본문과 어긋나거나, 필수 헤더가 빠졌습니다. `-32021`은 `MissingRequiredClientCapability`입니다. 이 특정 요청의 `clientCapabilities`가 선언하지 않은 커패시티가 서버에 필요했고, 오류는 빠진 것이 무엇인지 이름을 대는 `data.requiredCapabilities`를 실어 나릅니다. 레슨 07에서 본 요청 단위 협상을 떠올리게 하는 부분입니다. `-32022`는 `UnsupportedProtocolVersion`입니다. 요청이 부른 프로토콜 버전을 서버가 지원하지 않으며, `data.supported`(목록)와 `data.requested`를 실어 나릅니다. 레슨 05에서 소개한 버전 협상 형태입니다. 이 세 개 말고 `-32020`부터 `-32099` 사이의 다른 코드를 내보내는 것은 금지가 명백히 정해져 있습니다.

두 코드는 공개적으로 은퇴했으므로 2026-07-28 응답에 절대 나타나면 안 됩니다. `-32002`는 2025-11-25까지 리소스-없음(resource-not-found) 코드였습니다. SDK들 사이의 불일치 때문에 옛 권고가 더 이상 성립할 수 없게 되자 SEP-2164가 이를 `-32602`로 대체했습니다. `-32042`는 URL 모드 일러시테이션(elicitation)이 필요할 때 쓰던 더 좁은 용도의 코드였고, 2025-11-25 개정판에만 존재했습니다. 전용 오류 대신 URL 모드 일러시테이션이 이제는 평범한 MRTR 흐름으로 협상되기 때문에, 이 코드의 직접적인 후계자는 없습니다. 너그럽게 만들어진 클라이언트는 하위 호환을 위해 오래된 서버가 보낸 `-32002`를 여전히 받아줄 수는 있지만, 2026-07-28 서버가 이 코드를 만들어내서는 안 됩니다.

정의된 MCP 코드도 `isError`도 아닌 애플리케이션 정의 코드는 JSON-RPC 예약 전체 범위인 `-32768`부터 `-32000` 바깥에 완전히 놓여야 합니다. 실제로 이 경우는 드물어야 합니다. SEP-1303이 존재하는 이유 자체가, 구현체가 새 숫자를 찾기 전에 먼저 `isError`에 손을 뻗도록 만들기 위해서입니다.

Streamable HTTP에서는 이 코드들 중 몇몇이 문서화된 HTTP 상태와 짝을 이룹니다. 헤더 불일치, 빠진 커패시티, 지원하지 않는 버전, `_meta`가 빠진 잘못된 요청은 모두 `400 Bad Request`와 짝을 이룹니다:

```http
POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/list

```

이 요청의 헤더가 본문과 어긋났거나, `_meta`가 본문에서 아예 빠졌다면, 응답은 `400`이며 그 안에 짝이 맞는 JSON-RPC 오류가 실립니다. 알 수 없는 메서드는 대신 `404 Not Found`를 받습니다. 그 실패는 메시지 형태가 아니라 엔드포인트 자체의 라우팅에 관한 것이기 때문입니다. JSON-RPC 계층을 완전히 벗어나서, 몇 가지 전송 및 인가 이벤트는 JSON-RPC 오류 없이 HTTP 상태만 실어 나릅니다. 서버가 받아들인 알림(notification)은 본문 없이 `202 Accepted`를 돌려주고, 현대적 MCP 엔드포인트로 보낸 `GET`이나 `DELETE`는 `405 Method Not Allowed`를 받고, 베어러 토큰이 없거나 잘못됐으면 `401 Unauthorized`, OAuth 스코프가 부족하면 `403 Forbidden`을 받습니다.

마지막으로, 그 외에는 절대적인 규칙에 대한 하나의 좁은 예외입니다. 오류 응답은 언제나 요청의 `id`를 그대로 돌려주지만, 애초에 JSON으로 파싱이 실패한 본문처럼 id를 읽을 수 없었던 경우는 예외입니다. 그 응답은 `id: null`을 보고합니다. 돌려줄 id가 애초에 존재하지 않았기 때문입니다.

## 인터랙티브 랩

이 그림은 두 채널을 나란히 보여 줍니다. 왼쪽 열에는 이 레슨의 시나리오에서 프로토콜 오류가 실을 수 있는 다섯 개의 코드가 나열되어 있고, 각각은 클라이언트가 읽고 자기 손으로 처리하는 작은 상자입니다. 오른쪽 열은 카드 한 장입니다. 원인이 무엇이든 도구 수준의 문제는 모두 똑같은 `isError: true` 형태가 되고, 이것이 모델에게 평범한 콘텐츠로 도달하는 유일한 채널입니다. 맨 아래의 점선 띠는 금지 구역입니다. 레거시 하위 범위와 공개적으로 은퇴한 두 코드로 이루어진 경계로, 규격에 맞는 구현체는 어느 방향으로도 이 선을 넘지 않습니다.

## 실습 랩

`code/main.py`는 도구 두 개를 가진 작은 헬프데스크 서버와, 이 레슨이 설명하는 모든 시나리오를 그 서버에 대해 밀어붙여 보는 클라이언트를 만듭니다: 깔끔한 디스커버리와 도구 호출, 빠진 인자, 잘못된 열거(enum) 값, 존재하지 않는 도구에 대한 호출, 요청이 선언하지 않은 커패시티가 필요한 호출, 지원하지 않는 프로토콜 버전, 그리고 `_meta`가 아예 빠진 요청. 저장소 루트에서 실행하세요:

```bash
python3 certifications/mcpa/lessons/18-error-handling/code/main.py
```

먼저 가드를 읽어 보세요. `is_forbidden_error_code`는 할당 정책을 순수 함수로 구현한 것이고, `safe_error`는 어떤 오류 응답이든 만들기 전에 이 함수를 부릅니다. 이 서버가 돌려주는 모든 오류는 `safe_error`를 통과하므로, 금지된 코드가 우연히 소켓에 실릴 일이 없습니다. 전사(transcript) 끝부분에는 `violation` 표시가 붙은 항목 두 개가 있습니다. 규격을 지키지 않는 서버가 옛 "도구 호출 실패" 코드와 은퇴한 리소스-없음 코드를 무엇을 잘못 돌려줬을지를 보여 주는 것으로, 각각 반례임이 분명히 드러나도록 감싸여 있습니다. 실제 프로토콜 동작이 아닙니다. 셸에서 직접 `main.safe_error(1, -32050, "made up")`을 불러 보세요. 응답이라고 부를 만한 것이 만들어지기도 전에 `ForbiddenErrorCode`가 발생하는 걸 볼 수 있습니다. 그다음 세 개의 정의된 예약 코드 중 하나인 `main.safe_error(1, -32021, "fine")`을 불러 보면 성공하는 것을 확인할 수 있습니다.

## 완성된 산출물

`outputs/error-code-decision-table.md`는 네 단계 의사결정 표입니다. 채널을 고르고, 코드를 고르고, 금지 목록에 없는지 확인하고, 그래도 맞는 게 없다면 애플리케이션 정의 코드를 올바른 자리에 놓습니다. HTTP 상태 매핑과, JSON-RPC 오류를 아예 실지 않는 전송 이벤트들도 함께 담고 있습니다. 서버의 오류 처리를 검토할 때 옆에 펼쳐 두면 좋습니다.

## 캡스톤 연계

캡스톤의 엔드투엔드 교환은 안에서 무언가 잘못될 때마다 이 레슨에 의지합니다. 스키마에 어긋나는 도구 호출은 실행이 계속되기 전에 모델이 스스로 고칠 수 있도록 `isError`로 돌아와야 하고, 변조된 MRTR `requestState`는 그 자리에 맞춤 코드를 새로 만들지 않고 거절되어야 하며, 잘못된 오디언스(audience)에 발급된 토큰은 레슨 23이 설명하는 방식으로 거부되어야지 임시변통의 프로토콜 오류에 섞여 들어가면 안 됩니다. 캡스톤이 실패 응답의 근거를 대라고 물을 때, 답은 언제나 두 채널 중 하나와 이 레슨 표에 있는 코드입니다. 그 자리에서 지어낸 숫자는 결코 답이 아닙니다.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 프로토콜 오류 | 요청 자체가 잘못됐을 때 쓰는 JSON-RPC 오류 객체: 알 수 없는 메서드, 알 수 없는 도구, 형태가 깨진 봉투, 서버 고장 |
| 도구 실행 오류 | `isError: true`가 붙은 정상적인 `complete` 결과로, 모델이 읽고 스스로 고칠 수 있는 콘텐츠 |
| 할당 정책 | `-32000`부터 `-32099`까지를 레거시 하위 범위와 명세 예약 하위 범위로 나누는 2026-07-28 규칙 |
| `HeaderMismatch` | `-32020`. HTTP 헤더가 요청 본문과 어긋나거나 필수 헤더가 빠졌을 때 반환됨 |
| `MissingRequiredClientCapabilityError` | `-32021`. 요청이 자기 `clientCapabilities`가 선언하지 않은 커패시티를 필요로 할 때 `data.requiredCapabilities`와 함께 반환됨 |
| `UnsupportedProtocolVersionError` | `-32022`. 요청이 서버가 구현하지 않은 버전을 부를 때 `data.supported`와 `data.requested`와 함께 반환됨 |
| 은퇴한 코드 | 과거 개정판이 정의했지만 2026-07-28이 내보내기를 금지한 코드. 예: `-32002`, `-32042` |
| `safe_error` | 이 레슨의 가드: 어떤 응답이든 만들어지기 전에 금지된 코드의 구성을 거부함 |
