# 휴먼 인 더 루프(Human-in-the-Loop): 제안-후-확정

> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [en.md](en.md)

> HITL에 대한 2026년의 합의는 구체적입니다. 그것은 "에이전트가 묻고 사용자가 승인을 클릭한다"가 아닙니다. 제안-후-확정(propose-then-commit)입니다: 제안된 행동이 멱등성 키와 함께 내구 저장소에 영속되고; 의도, 데이터 계보(data lineage), 건드리는 권한, 폭발 반경, 롤백 계획과 함께 검토자에게 제시되며; 긍정적 확인 이후에만 확정되고; 실행 후 부작용이 실제로 일어났는지 검증됩니다. LangGraph의 `interrupt()`와 PostgreSQL 체크포인팅, Microsoft Agent Framework의 `RequestInfoEvent`, Cloudflare의 `waitForApproval()`이 모두 같은 형태를 구현합니다. 정형화된 실패 양상은 고무도장 승인(rubber-stamp approval)입니다: "승인할까요?"가 검토 없이 클릭됩니다. 문서화된 완화책은 명시적 체크리스트가 있는 챌린지-앤드-리스폰스(challenge-and-response)입니다.

**유형:** 학습(Learn)
**언어:** Python (표준 라이브러리, 멱등성이 있는 제안-후-확정 상태 머신)
**선수 지식:** 페이즈 15 · 12 (내구 실행), 페이즈 15 · 14 (트리프와이어)
**시간:** 약 60분

## 문제

에이전트가 행동을 취합니다. 사용자는 결정해야 합니다: 승인할까 말까. 결정이 즉각적이라면, 아마 그것은 검토가 아닙니다. 결정이 구조화되어 있다면, 느리지만 신뢰할 수 있습니다. 공학적 질문은 구조화된 검토를 가장 저항이 적은 길로 만드는 방법입니다.

2023년 시절의 HITL 패턴은 동기 프롬프트였습니다: "에이전트가 X에게 본문 Y로 이메일을 보내려 합니다 — 승인할까요?" 사용자가 승인을 클릭합니다. 모두가 시스템이 안전하다고 느낍니다. 실제로 이 표면은 고무도장으로 덮입니다: 사용자는 빠르게 승인하고, 승인은 거의 아무것도 예측하지 못하며, 에이전트가 잘못됐을 때 감사 기록은 사용자가 기억하지 못하는 긴 승인 이력을 보여줍니다.

2026년 패턴 — 제안-후-확정 — 은 HITL을 내구 기반 위로 옮기고, 구조화된 메타데이터를 붙이고, 긍정적 확정을 요구합니다. 모든 관리형 에이전트 SDK가 한 버전씩 출시합니다: LangGraph `interrupt()`, Microsoft Agent Framework `RequestInfoEvent`, Cloudflare `waitForApproval()`. API 이름은 다르지만 형태는 다르지 않습니다.

## 개념

### 제안-후-확정 상태 머신

1. **제안.** 에이전트가 제안된 행동을 만들어냅니다. 내구 저장소(PostgreSQL, Redis, Durable Object)에 영속됩니다. 포함하는 것:
   - 의도 (에이전트가 왜 이것을 하는가)
   - 데이터 계보 (어떤 출처가 이 제안으로 이끌었는가)
   - 건드리는 권한 (어떤 스코프/파일/엔드포인트)
   - 폭발 반경 (최악의 경우가 무엇인가)
   - 롤백 계획 (확정됐다면 어떻게 되돌리는가)
   - 멱등성 키 (제안마다 고유; 재제출은 같은 레코드를 반환)
2. **제시.** 검토자는 모든 메타데이터와 함께 제안을 봅니다. 검토자는 사람입니다 (에이전트가 자기 자신을 검토하는 것이 아님).
3. **확정.** 긍정적 확인. 행동이 실행됩니다.
4. **검증.** 실행 후 부작용이 다시 읽혀 확인됩니다. 검증 단계가 실패하면 시스템은 알려진 나쁜 상태에 있고 경보가 발동됩니다.

### 멱등성 키

멱등성 키가 없으면, 일시적 실패 뒤의 재시도가 승인된 행동을 이중 실행할 수 있습니다. 구체적인 예: 사용자가 "A에서 B로 $100 이체"를 승인합니다. 네트워크가 잠깐 끊깁니다. 워크플로가 재시도합니다. 사용자는 한 번 승인했지만 이체는 두 번 실행됩니다. 멱등성 키는 승인을 단 하나의 고유한 부작용에 묶습니다; 두 번째 실행은 no-op입니다.

이것은 Stripe와 AWS API가 쓰는 것과 같은 멱등성 패턴입니다. 에이전트 승인에 이것을 재사용하는 것은 Microsoft Agent Framework 문서에 명시되어 있습니다.

### 내구성: 왜 승인이 프로세스보다 오래 사는가

승인 대기실은 에이전트가 소유하지 않은 상태 조각입니다. 워크플로는 일시 정지되어 있습니다(레슨 12). 승인이 도착하면 워크플로는 정확히 그 지점에서 재개합니다. 이것이 LangGraph가 `interrupt()`를 메모리 상태가 아니라 PostgreSQL 체크포인팅과 짝짓는 이유입니다 — 이틀 뒤의 승인도 여전히 온전한 워크플로를 찾습니다.

### 고무도장 승인과 챌린지-앤드-리스폰스 완화책

HITL의 기본 UI("승인"/"거부" 버튼)는 진짜 검토 없이 빠른 승인을 만들어냅니다. 문서화된 완화책: 승인 버튼이 활성화되기 전에 특정 질문들에 긍정적으로 답하도록 요구하는 챌린지-앤드-리스폰스 체크리스트. 구체적인 형태:

- "이것이 어떤 리소스를 건드리는지 이해하고 있나요? [ ]"
- "폭발 반경이 수용 가능함을 확인했나요? [ ]"
- "실패했을 때 되돌릴 계획이 있나요? [ ]"

관료제 자체를 위한 관료제가 아니라 — 강제 장치(forcing function)입니다. 체크박스에 체크할 수 없는 검토자는 명확화를 요청하거나(확대), 거절합니다(안전한 기본값). Anthropic의 에이전트 안전 연구는 고무도장 승인 패턴에 대한 완화책으로 체크리스트 기반 HITL을 명시적으로 인용합니다.

### 무엇이 중대 행동인가

모든 행동이 제안-후-확정이 필요한 것은 아닙니다. 2026년 가이던스:

- **중대 행동** (항상 HITL): 되돌릴 수 없는 쓰기, 금융 거래, 외부 커뮤니케이션, 프로덕션 데이터베이스 변경, 파괴적인 파일 시스템 작업.
- **되돌릴 수 있는 행동** (때때로 HITL): 로컬 파일 편집, 스테이징 환경 변경, 명확한 롤백이 있는 되돌릴 수 있는 쓰기.
- **읽기와 점검** (절대 HITL 아님): 파일 읽기, 리소스 나열, 읽기 전용 API 호출.

### 행동 후 검증

"확정이 실행됐다"는 "부작용이 일어났다"와 같지 않습니다. 네트워크 분할과 경쟁 조건은, 백엔드가 영속하지 못했는데 워크플로는 성공했다고 믿는 상황을 만들 수 있습니다. 검증 단계는 확정 뒤 대상 리소스를 다시 읽어 확인합니다. 이것은 `RETURNING` 절을 쓰는 데이터베이스 트랜잭션이나 `PutObject` 뒤의 AWS `GetObject`와 같은 패턴입니다.

### EU AI Act 제14조

제14조는 EU의 고위험 AI 시스템에 효과적인 사람 감독을 의무화합니다. "효과적"은 장식이 아닙니다. 규제 언어는 고무도장 패턴을 구체적으로 배제합니다. 챌린지-앤드-리스폰스를 곁들인 제안-후-확정이 Microsoft Agent Governance Toolkit 컴플라이언스 문서에서 제14조 심사를 견디는 형태입니다.


## 사용해 보기

`code/main.py`는 표준 라이브러리 파이썬으로 제안-후-확정 상태 머신을 구현합니다. 내구 저장소는 JSON 파일입니다. 멱등성 키는 (thread_id, action_signature)의 해시입니다. 드라이버는 세 가지 경우를 시뮬레이션합니다: 깨끗한 승인 흐름, 일시적 실패 뒤의 재시도(이중 실행해서는 안 됨), 그리고 고무도장 기본값 vs 챌린지-앤드-리스폰스 흐름.

## 출시해 보기

`outputs/skill-hitl-design.md`는 제안된 HITL 워크플로를 제안-후-확정 형태 기준으로 검토하고, 빠진 메타데이터, 멱등성, 검증, 또는 챌린지-앤드-리스폰스 계층을 표시합니다.

## 연습 문제

1. `code/main.py`를 실행해 보세요. 승인된 제안의 재시도가 내구 레코드를 사용하고 재실행하지 않음을 확인하세요. 이제 멱등성 키에 타임스탬프를 포함시켜 재시도가 이중 실행됨을 보여주세요.

2. 제안 레코드에 `rollback` 필드를 추가해 보세요. 검증 단계가 실패하는 실행을 시뮬레이션하세요. 롤백이 자동으로 발동함을 보여주세요.

3. Microsoft Agent Framework의 `RequestInfoEvent` 문서를 읽어 보세요. 장난감 엔진에 없는 메타데이터 필드 하나를 찾으세요. 그것을 추가하고 무엇을 보호하는지 설명하세요.

4. 특정 행동(예: "공개 트위터 계정에 게시")을 위한 챌린지-앤드-리스폰스 체크리스트를 설계해 보세요. 검토자가 답해야 할 세 가지 질문은 무엇인가요? 왜 그 세 가지인가요?

5. 동기식 "승인할까요?" 프롬프트로 충분한(내구 저장소가 필요 없는) 사례 하나를 골라 보세요. 왜 그런지 설명하고, 여러분이 감수하는 위험 부류를 명명하세요.

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|---|---|---|
| 제안-후-확정 | "2단계 승인" | 영속된 제안 + 긍정적 확정 + 검증 |
| 멱등성 키 | "재시도 안전 토큰" | 제안마다 고유; 두 번째 실행은 no-op |
| 데이터 계보 | "어디서 왔나" | 제안으로 이끈 구체적인 출처 콘텐츠 |
| 폭발 반경 | "최악의 경우" | 행동이 잘못됐을 때 영향의 범위 |
| 고무도장 | "빠른 승인" | 진짜 검토 없이 "승인" 클릭 |
| 챌린지-앤드-리스폰스 | "강제 체크리스트" | 검토자가 특정 질문에 긍정적으로 확인해야 함 |
| RequestInfoEvent | "MS Agent Framework 프리미티브" | 구조화된 메타데이터가 있는 내구 HITL 요청 |
| `interrupt()` / `waitForApproval()` | "프레임워크 프리미티브" | 같은 형태의 LangGraph / Cloudflare 등가물 |
