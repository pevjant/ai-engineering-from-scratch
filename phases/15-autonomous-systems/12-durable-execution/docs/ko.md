# 장시간 실행 백그라운드 에이전트: 내구 실행(Durable Execution)

> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [en.md](en.md)

> 프로덕션(운영 환경)의 장기 에이전트는 `while True`로 돌지 않습니다. 모든 LLM 호출이 체크포인트, 재시도, 리플레이를 갖춘 액티비티가 됩니다. Temporal의 OpenAI Agents SDK 통합은 2026년 3월 정식 출시(GA)되었습니다. Claude Code Routines(Anthropic)는 영속적인 로컬 프로세스 없이 예약된 Claude Code 호출을 실행합니다. 세션은 사람 입력에서 일시 정지하고, 배포를 견디며, `thread_id`로 식별되는 최신 체크포인트에서 재개합니다. 새로운 편의성 뒤에는 오래된 패턴 — 워크플로 오케스트레이션 — 이 자리하고 있으며, 여기에 하나의 새로운 입력이 더해졌습니다: 복구 시 결정론적으로 리플레이되어야 하는, 비결정론적 액티비티로서의 LLM 호출입니다.

**유형:** 학습(Learn)
**언어:** Python (표준 라이브러리, 미니멀한 내구 실행 상태 머신)
**선수 지식:** 페이즈 15 · 10 (권한 모드), 페이즈 15 · 01 (장기 에이전트)
**시간:** 약 60분

## 문제

네 시간 동안 돌아가는 에이전트를 생각해 봅시다. 도구를 세 번 호출하고, 사용자에게 두 번 묻고, LLM 호출을 마흔 번 합니다. 한가운데서, 실행 중이던 호스트가 재부팅됩니다. 무슨 일이 벌어질까요?

- 순진한 `while True` 루프에서는: 모든 것이 사라집니다. 실행이 처음부터 다시 시작됩니다. (실제 부작용이 있는) 세 번의 도구 호출이 다시 실행됩니다. 사용자는 이미 승인한 것들을 다시 승인하라는 요청을 받습니다. 마흔 번의 LLM 호출에 요금이 다시 청구됩니다.
- 내구 실행에서는: 실행이 가장 최근 체크포인트에서 재개됩니다. 이미 완료된 액티비티는 재실행되지 않습니다; 그 결과는 내구 로그에서 리플레이됩니다. 사용자는 이미 승인한 것을 다시 승인하지 않습니다. 이미 이뤄진 LLM 호출에 요금이 다시 청구되지 않습니다.

이것은 워크플로 엔진들이 10년 동안 출시해 온 것과 같은 패턴입니다(Temporal, Cadence, Uber의 Cherami). 새로운 것은 LLM 호출이 이제 한 종류의 액티비티라는 점입니다 — 비결정론적이고, 비싸고, 부작용이 있는 — 그리고 이 패턴에 깔끔하게 들어맞습니다.

이 레슨의 반복 주제: 장기 신뢰성은 감쇠합니다(METR이 "35분 감쇠"를 관찰 — 성공률이 수행 시간에 대해 대략 이차적으로 떨어집니다). 내구 실행은 신뢰성 프로필이 감당하는 것보다 더 긴 실행을 가능하게 하는데, 이는 설계가 옳다면 안전하게 실패하는 새로운 방법이고, 설계가 틀리면 안전하지 않게 실패하는 새로운 방법입니다.

## 개념

### 액티비티, 워크플로, 그리고 리플레이

- **워크플로**: 결정론적 오케스트레이션 코드입니다. 액티비티의 순서, 분기, 대기를 정의합니다. 이벤트 로그에서 놀랍게 어긋나지 않고 리플레이되려면 반드시 결정론적이어야 합니다.
- **액티비티**: 비결정론적이고 실패할 수 있는 작업 단위입니다. LLM 호출, 도구 호출, 파일 쓰기, HTTP 요청. 각 액티비티는 입력과 (완료되면) 출력과 함께 로그에 기록됩니다.
- **이벤트 로그**: 내구적인 백킹 스토어입니다. 모든 액티비티의 시작, 완료, 실패, 재시도와 모든 워크플로 결정이 기록됩니다.
- **리플레이**: 복구 시 워크플로 코드가 처음부터 다시 실행됩니다; 이미 완료된 액티비티는 재실행 없이 기록된 결과를 반환합니다. 완료되지 않았던 액티비티만 실제로 실행됩니다.

이것은 가상 DOM을 상대로 한 React 재렌더링, 혹은 커밋들로부터 작업 트리를 재구축하는 Git과 같은 형태입니다. 오케스트레이터의 결정론성이 내구성을 값싸게 만듭니다.

### LLM 호출이 이 패턴에 맞는 이유

LLM 호출은:
- 비결정론적입니다 (temperature > 0; temperature 0조차 모델 버전 사이에서 표류합니다).
- 비쌉니다 (돈과 지연 시간).
- 실패할 수 있습니다 (속도 제한, 타임아웃).
- 부작용이 있습니다 (도구를 호출하는 경우).

이것이 정확히 액티비티 프로필입니다. 모든 LLM 호출을 액티비티로 감싸면 지수 백오프를 곁들인 재시도, 재시작을 건너는 체크포인팅, 그리고 디버깅용 재생 가능한 트레이스를 얻습니다.

### `thread_id`로 식별되는 체크포인트

LangGraph, Microsoft Agent Framework, Cloudflare Durable Objects, Claude Code Routines는 모두 같은 API 형태로 수렴했습니다: `thread_id`(또는 동등한 것)가 세션을 식별하고; 각 상태 전이는 백엔드(PostgreSQL 기본, 개발용 SQLite, 캐시용 Redis)에 영속되고; 재개는 최신 체크포인트를 읽습니다.

백엔드 선택이 중요합니다:

- **PostgreSQL**: 내구적, 질의 가능, 배포를 견딤. LangGraph의 기본값.
- **SQLite**: 로컬 개발 전용; 호스트가 바뀌면 데이터가 사라짐.
- **Redis**: 빠르지만 AOF/스냅샷을 설정하지 않으면 휘발적.
- **Cloudflare Durable Objects**: 투명하게 분산됨; 고유 키로 범위가 한정됨; 수 시간에서 수 주까지 유지.

### 일급 시민으로서의 사람 입력

제안-후-확정(레슨 15)은 내구적인 "사람 대기 중" 상태를 필요로 합니다. 워크플로가 일시 정지하고, 외부 큐가 보류 중인 요청을 쥐고 있고, 승인이 오면 바로 그 지점에서 재개합니다. 내구성이 없으면 이것은 최선 노력(best-effort)에 불과합니다; 내구성이 있으면, 밤새 승인이 도착해도 워크플로가 아침에 그것을 이어 받습니다.

### 35분 감쇠

METR은 측정된 모든 에이전트 부류가 약 35분을 넘는 연속 운전에서 신뢰성이 감쇠함을 관찰했습니다. 태스크 지속 시간을 두 배로 늘리면 실패율은 대략 네 배가 됩니다. 내구 실행은 이것을 고치지 않습니다; 신뢰성 프로필이 감당하는 것보다 더 오래 돌릴 수 있게 해줄 뿐입니다. 안전한 패턴은 내구성을, 재진입 시 새로운 HITL을 요구하는 체크포인트, 그리고 벽시계 시간과 무관하게 총 컴퓨트를 제한하는 예산 킬 스위치(레슨 13)와 결합하는 것입니다.

### 내구 실행이 잘못된 답인 경우

- 사람 입력 없이 몇 분 안에 끝나는 실행. 오버헤드 > 이득.
- 철저히 읽기 전용인 정보 검색.
- 정확성이 하나의 컨텍스트 윈도우 안에서 엔드투엔드로 요구되는 태스크 (일부 추론 태스크; 일부 원샷 생성).

## 사용해 보기

`code/main.py`는 표준 라이브러리 파이썬으로 미니멀한 내구 실행 엔진을 구현합니다. 지원하는 것:

- 입력과 출력을 JSON 이벤트 로그에 기록하는 `@activity` 데코레이터.
- 액티비티를 순서화하는 워크플로 함수.
- 완료된 액티비티를 재실행 없이 리플레이하는 `run_or_replay(workflow, event_log)` 함수.

드라이버는 세 액티비티 워크플로를 시뮬레이션하고, 한가운데서 크래시를 일으키고, (a) 순진한 재시도가 모든 것을 재실행하는 것과 (b) 리플레이가 빠진 액티비티만 실행하는 것을 보여줍니다.

## 출시해 보기

`outputs/skill-durable-execution-review.md`는 제안된 장시간 에이전트 배포를 올바른 내구 실행 형태 기준으로 검토합니다: 액티비티, 결정론성, 체크포인트 백엔드, 사람 입력 상태, 재개 시 HITL 정책.

## 연습 문제

1. `code/main.py`를 실행해 보세요. 순진한 재시도와 리플레이 사이의 액티비티 실행 횟수 차이를 관찰하세요. 크래시 지점을 바꾸고 리플레이 횟수가 그에 따라 바뀌는지 보여주세요.

2. 장난감 엔진이 `thread_id`를 명시적으로 쓰도록 바꿔 보세요. 엔진을 공유하는 두 개의 동시 세션을 시뮬레이션하고 그들의 이벤트 로그가 충돌하지 않음을 확인하세요.

3. 장난감 엔진의 액티비티 하나를 가져가 보세요. 비결정론성(워크플로 결정 안의 벽시계 타임스탬프)을 도입하세요. 리플레이에서의 어긋남을 시연하고, 실제 엔진이 이것을 어떻게 다루는지 설명하세요(부작용 등록, `Workflow.now()` API).

4. LangChain의 "Runtime behind production deep agents" 포스트를 읽어 보세요. 런타임이 영속하는 모든 상태를 나열하고, 각각이 어떤 실패 양상을 커버하는지 밝히세요.

5. 6시간 자율 코딩 태스크를 위한 체크포인트 정책을 설계해 보세요. 어디에 체크포인트를 찍을까요? 크래시 후 재개는 어떤 모습인가요? 무엇이 새로운 HITL을 요구하나요?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|---|---|---|
| 워크플로 | "에이전트의 스크립트" | 결정론적 오케스트레이션 코드; 이벤트 로그에서 리플레이 가능 |
| 액티비티 | "하나의 단계" | 비결정론적 단위 (LLM 호출, 도구 호출); 전후로 로그 기록 |
| 이벤트 로그 | "백킹 스토어" | 모든 상태 전이의 내구적 기록 |
| 리플레이 | "이어서 실행" | 워크플로를 다시 실행; 완료된 액티비티는 재실행 없이 기록된 결과를 반환 |
| 체크포인트 | "저장 지점" | thread_id로 식별되는 영속 상태; 재개 시 최신 것이 이김 |
| thread_id | "세션 키" | 내구 상태의 범위를 정하는 식별자 |
| 35분 감쇠 | "신뢰성 감쇠" | METR: 성공률이 수행 시간에 대해 약 이차적으로 하락 |
| 비결정론성 | "리플레이 시 표류" | 벽시계, 난수, LLM 출력; 부작용으로 등록되어야 함 |
