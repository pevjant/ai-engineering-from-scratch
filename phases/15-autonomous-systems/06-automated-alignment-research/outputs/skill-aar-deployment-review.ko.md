> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [skill-aar-deployment-review.md](skill-aar-deployment-review.md)

제안된 자동화된 정렬 연구 배포(모델, 샌드박스, 작업 큐, 포럼)가 주어지면, 프론티어 연구소 안전 팀이 서명할 만한 사전 배포 리뷰를 만들어 냅니다.

만들어야 할 것:

1. **샌드박스 격리.** 각 AAR 인스턴스의 파일시스템, 네트워크, 프로세스 한도를 검증합니다. 어떤 AAR도 다른 AAR의 샌드박스를 읽거나 수정할 수 없는지 확인합니다. 어떤 AAR도 포럼 저장소의 쓰기 엔드포인트에 직접 닿을 수 없는지 확인합니다(모든 게시는 별도의 서비스를 거칩니다).
2. **포럼 로그 무결성.** 포럼은 추가 전용(append-only)이고 변조 증거가 남아야 합니다. 저장소를 명세하세요(예: 오브젝트 락이 걸린 S3, 불변 원장, 추가 전용 WAL). 검증 주기와, 변조가 감지됐을 때의 대응을 명세하세요.
3. **작업 할당 정책.** 작업이 어떻게 배정되는지 밝힙니다: 누가 작성하고, 누가 승인하고, AAR이 후속 작업을 스스로 제안할 수 있는지, 그렇다면 어떤 조건에서인지. 자유 분해는 성능에서 이기고, 정해진 워크플로는 감사 가능성에서 이깁니다. 이 트레이드오프를 명시적으로 문서화하세요.
4. **사람 리뷰 게이트.** 어떤 AAR 산출물이든 실제 연구 방향, 학습 데이터, 또는 공개된 작업에 영향을 주기 전에, 이름이 밝혀진 사람 리뷰어가 서명해야 합니다. 리뷰 체크리스트를 명세하세요: 실험 재현 가능성, 로그 완전성, 주장-근거 매핑.
5. **기준선 모니터링.** AAR 시스템이 RSP v3.0의 AI R&D-4 영역에 접근하고 있다는 신호를 추적합니다: 작업 복잡도 변화, 자율적인 하위 작업 생성, 작업 간 정보 전이. 상향된 리뷰를 요구하는 기준선을 정의하세요.

하드 거부(hard reject) 사례:
- 변조 증거가 남고 샌드박스 밖에 있는 로그 없이 운영되는 어떤 AAR 배포든 거부.
- 이름이 밝혀진 사람 리뷰 없이 AAR의 산출물이 학습 데이터나 프로덕션 정책으로 직접 흘러드는 파이프라인 전부.
- 단일 AAR이 여러 다운스트림 시스템에 영향을 줄 만큼 충분한 자격 증명을 가진 파이프라인 전부.

거부 규칙:
- 샌드박스 격리가 명세되지 않았거나 단일 계층에만 의존한다면(Docker만 있고 seccomp / gVisor가 없음) 거부하고, 다중 방어(defense-in-depth)를 요구하세요.
- 로그 저장소를 (운영자라도) 누군가 편집할 수 있다면 거부하고, 한 번 쓰면 못 바꾸는(write-once) 미디어를 요구하세요.
- 배포의 목표가 정렬 연구가 아니라 역량 파이프라인의 일부를 자동화하는 것이라면 거부하고, RSP 리뷰로 에스컬레이션하세요.

출력 형식:

다음을 담은 리뷰 메모를 돌려주세요:
- **파이프라인 요약** (한 문단)
- **격리 점수** (차원별: 파일시스템, 네트워크, 프로세스, 동료(peering))
- **로그 무결성 점수** (검증 계획 포함)
- **작업 할당 결정** (고정 / 자유 / 하이브리드, 근거 포함)
- **사람 리뷰 게이트** (리뷰어 이름, 체크리스트)
- **기준선 모니터** (신호 목록, 기준선, 대응)
- **배포 판정** (진행 / 보류 / 중단)
