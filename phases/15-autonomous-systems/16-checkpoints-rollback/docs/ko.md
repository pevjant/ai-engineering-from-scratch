# 체크포인트와 롤백

> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [en.md](en.md)

> 모든 그래프 상태 전이가 영속됩니다. 워커가 크래시하면 리스가 만료되고 다른 워커가 최신 체크포인트에서 이어받습니다. Cloudflare Durable Objects는 수 시간에서 수 주까지 상태를 유지합니다. 제안-후-확정(레슨 15)은 행동마다 롤백 계획을 정의합니다. 행동 후 검증이 루프를 닫습니다. EU AI Act 제14조는 고위험 시스템에 효과적인 사람 감독을 의무화합니다 — 실무적으로 이것은 체크포인트가 질의 가능해야 하고, 롤백은 리허설되어야 하며, 감사 기록이 배포를 견뎌야 함을 뜻합니다. 날카로운 실패 양상: 멱등성 키와 사전 조건 검사가 없으면, 일시적 실패 뒤의 재시도가 이미 승인된 행동을 이중 실행할 수 있습니다. 이것을 잡아내는 것이 행동 후 검증입니다.

**유형:** 학습(Learn)
**언어:** Python (표준 라이브러리, 체크포인트와 롤백 상태 머신)
**선수 지식:** 페이즈 15 · 12 (내구 실행), 페이즈 15 · 15 (제안-후-확정)
**시간:** 약 60분

## 문제

내구 실행(레슨 12)은 크래시한 에이전트를 재개 가능하게 만듭니다. 제안-후-확정(레슨 15)은 승인된 행동을 감사 가능하게 만듭니다. 이 레슨은 둘을 잇습니다: 승인된 행동이 부분적으로 실행되고, 크래시하고, 재개하면 무슨 일이 벌어지는가? 롤백은 언제, 어떤 상태를 상대로 실행되는가?

실제 시스템들은 이것을 각기 다르게 연결합니다:

- **LangGraph**는 모든 그래프 상태 전이를 PostgreSQL에 체크포인트합니다. 워커 크래시 시 리스가 해제되고 다른 워커가 최신 체크포인트에서 재개합니다. 워크플로는 `interrupt()`에서 일시 정지하는데, 그 자체도 영속됩니다.
- **Cloudflare Durable Objects**는 키별 상태를 수 시간에서 수 주까지 유지합니다. 승인된 행동에 대해 연산을 저장소와 같은 곳에 둡니다.
- **Microsoft Agent Framework**는 워크플로 API에서 `Checkpoint` 프리미티브를 노출합니다; 리플레이와 멱등성이 재시도를 커버합니다.

어느 경우든 실제로 작동하는 조합은: 멱등성 키 (이중 실행 방지) + 사전 조건 검사 (상태가 아직 승인했던 것과 일치함) + 행동 후 검증 (부작용이 실제로 일어남) + 검증 실패 시 롤백입니다.

## 개념

### 모든 전이가 영속된다

그래프 상태 전이란 워크플로를 한 명명된 상태에서 다른 상태로 옮기는 어떤 단계입니다. 순진한 구현은 특정 커밋 지점에서만 영속합니다; 프로덕션 구현은 모든 전이를 영속합니다. 비용(추가 쓰기 몇 번)은 신뢰성 이득(리플레이가 어디서든 착지, 정밀한 리스 복구)에 비해 작습니다.

### 리스 복구

워커가 크래시해도 워크플로는 사라지지 않습니다; 리스(이 워커가 이 실행을 수행하고 있다는 짧은 수명의 클레임)가 단순히 만료됩니다. 다른 워커가 최신 체크포인트를 이어받아 재개합니다. 리스 메커니즘이 프로덕션 시스템이 진행 중인 작업을 잃지 않고 롤링 배포를 견디게 해 주는 것입니다.

### 멱등성과 사전 조건

멱등성만으로는 충분하지 않습니다. 생각해 봅시다: 워크플로가 "잔액이 $1000을 넘을 때 A에서 B로 $100을 이체"하도록 승인됐습니다. 워크플로가 확정되고, 실행 중간에 크래시하고, 재개합니다. 멱등성 키만 검사되고 실행이 재개되면 이체는 한 번 실행됩니다(올바름). 하지만 크래시와 재개 사이에 다른 워크플로를 통해 A의 잔액이 $500으로 떨어졌다고 합시다. 멱등성 검사는 여전히 통과합니다; 사전 조건은 통과하지 못합니다. 사전 조건 검사가 없으면 우리는 초과 인출을 출시하게 됩니다.

모든 중대 행동은 둘 다 필요로 합니다:

- **멱등성 키**: 이중 실행을 막습니다.
- **사전 조건 검사**: 상태가 아직 승인된 것과 일치함을 확인합니다.

### 행동 후 검증

"도구가 200을 반환했다"는 검증이 아닙니다. 진짜 검증은 대상 상태를 다시 읽어 부작용이 실제로 일어났음을 확인합니다. 패턴:

- 데이터베이스 갱신: `UPDATE ... RETURNING *` 후 반환된 행이 의도한 상태와 일치하는지 단언.
- 이메일 발송: 제출 뒤 sent 폴더에서 메시지 ID 확인.
- 파일 쓰기: 파일을 다시 읽어 해시 비교.
- API 호출: 대상 리소스에 후속 `GET`.

검증이 실패하면 워크플로는 알려진 나쁜 상태입니다. 롤백이 발동됩니다.

### 롤백 계획

제안-후-확정(레슨 15)의 모든 중대 행동은 롤백 계획을 갖습니다. 유형:

- **인밴드 롤백**: 부작용을 직접 되돌립니다 (`INSERT` 뒤의 `DELETE`, 발송 뒤의 정정 이메일 발송).
- **보상 트랜잭션**: 원래 것을 중화하는 새로운 행동 (표준 SAGA 패턴).
- **아웃오브밴드 롤백**: 사람에게 경보를 보내고, 워크플로를 일시 정지하고, 나쁜 상태를 조사를 위해 남겨 둡니다.

no-op 롤백("이것은 되돌릴 수 없습니다")은 제안에 명시되어야 합니다. 롤백이 없는 행동은 확정 시점에 더 강한 HITL을 요구합니다(레슨 15 챌린지-앤드-리스폰스).

### EU AI Act 제14조의 실무적 읽기

제14조는 고위험 시스템에 "효과적인 사람 감독"을 요구합니다. 실무적 용어로 구현자들은 이렇게 읽습니다:

- 체크포인트는 감사자가 질의할 수 있어야 합니다.
- 롤백은 리허설됩니다 (최소 한 번 엔드투엔드로 테스트됨).
- 감사 기록은 배포를 견딥니다 (체크포인트 백엔드가 휘발적이지 않음).
- 실패한 검증은 조용히 로그로 남는 것이 아니라 경보를 울립니다.

확정 중간에 크래시하고, 재개하고, 검증 + 롤백 경로 없이 부작용을 완료하는 워크플로는 제14조 시험을 견디지 못합니다.

### 날카로운 실패 양상: 이중 실행

이 분야의 가장 흔한 프로덕션 사고:

1. 행동이 승인됨, 멱등성 키 k.
2. 확정이 시작되고, 실행되고, 200을 반환.
3. "확정됨" 상태를 영속하기 전에 워크플로가 크래시.
4. 워크플로가 재개; "승인됐지만 확정 안 됨"을 보고; 재실행.
5. 부작용이 두 번 발화.

완화책: 실행 전에 "진행 중(in-flight)" 의도를 영속하고, 멱등성 키로 실행하고, 그다음 행동 후 검증이 성공한 뒤에만 "확정됨"으로 표시합니다. 행동이 발화했는데 상태 쓰기가 실패하면, 검증하고 (필요하면) 다시 발화해야 함을 압니다. 상태 쓰기가 성공했는데 행동이 실패하면, 검증하고 복구 경로를 통해 정확히 한 번 발화합니다.

## 사용해 보기

`code/main.py`는 멱등성, 사전 조건, 검증, 롤백을 갖춘 체크포인트 워크플로를 구현합니다. 드라이버는 네 가지 시나리오를 시뮬레이션합니다: 깨끗한 실행, 크래시 뒤의 재시도(멱등성이 잡음), 사전 조건 실패(발화 없이 워크플로 중단), 검증 실패(롤백 발동).

## 연습 문제

1. `code/main.py`를 실행해 보세요. 네 가지 시나리오를 검증하세요. 확정 중 크래시 사례에서 재시도를 거쳐 행동이 정확히 한 번 발화함을 확인하세요.

2. "먼저 완료로 표시한 뒤 실행" 패턴을, 상태 쓰기가 행동 뒤에 발화하도록 바꿔 보세요. 크래시 시나리오를 다시 실행하세요. 중복 행동이 몇 번 발화하는지 측정하세요.

3. 특정 프로덕션 행동(예: "Slack 채널에 게시")에 대한 롤백 계획을 설계해 보세요. 인밴드, 보상, 또는 아웃오브밴드로 분류하세요. 선택을 정당화하세요.

4. 여러분이 아는 워크플로 하나를 가져가 보세요. 모든 상태 전이를 식별하세요. 각각에 내구성 요건(영속 / 비영속)을 표시하세요. 현재 영속하고 있지 않은 것들의 개수를 세어 보세요.

5. 리허설된 롤백 테스트: 실제 워크플로를 실행하고, 크래시시키고, 롤백 경로가 발동함을 확인하는 엔드투엔드 테스트를 설계해 보세요. 테스트는 무엇을 단언하나요?
