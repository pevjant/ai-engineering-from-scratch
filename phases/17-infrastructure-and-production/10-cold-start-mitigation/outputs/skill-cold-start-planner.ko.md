> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [skill-cold-start-planner.md](skill-cold-start-planner.md)

모델 크기, SLA(TTFT P99), 트래픽 형태(꾸준함 vs 버스트), 예산 입장이 주어지면 콜드 스타트 완화 계획을 만듭니다.

산출물:

1. 콜드 스타트 예산. 날것의 콜드 스타트 경로를 분해합니다(노드 프로비저닝, 이미지 풀, 가중치 → HBM, 엔진 초기화, 첫 포워드). 명시된 모델 크기에 대해 2026년 표준 초 단위를 씁니다.
2. 계층 선택. 총 시간을 SLA 이하로 만드는 최소 계층 수를 고릅니다: 사전 시드 이미지(L1), 모델 스트리머(L2), GPU 스냅샷(L3), 웜 풀(L4), 계층형 로딩(L5). 각 계층이 노리는 특정 페이즈를 대조하며 근거를 댑니다.
3. 웜 풀 크기. 주 경로의 `min_workers`를 명시합니다. 70B 이상 모델에서 SLA가 TTFT P99 < 60초라면, 비용과 무관하게 웜 풀을 의무화합니다.
4. 비용 추산. 선택한 웜 풀의 월간 GPU 비용과, 하루 예상 콜드 스타트 횟수.
5. 꼬리 정책. 새 레플리카에 도달한 첫 사용자는 어떻게 되나요 — 웜 레플리카로 큐에 보내지나요, 아니면 콜드 스타트 세금을 내나요? 구체적인 정책 이름을 붙입니다(예: "첫 요청은 10초 안의 아무 웜 레플리카로 라우팅; 없으면 콜드로 통과").
6. 장애 양상. 세션 도중 웜 레플리카가 죽으면 어떻게 되나요. 복구가 자동인가요(라이브 마이그레이션), 아니면 다음 요청에서 콜드 스타트인가요?

하드 리젝(절대 금지):

- 월간 비용을 계산하지 않고 "웜 풀만 넣자"고 제안하는 것.
- 노리는 특정 페이즈를 밝히지 않고 완화 기법을 주장하는 것(예: 180초 이미지 풀을 없앤다는 말 없이 "Bottlerocket을 쓰자").
- GPU 스냅샷의 GPU 토폴로지별 제약을 무시하는 것 — 플랫폼이 SKU를 옮기면 스냅샷은 무효입니다.

거절 규칙:

- 웜 풀 없이 새 70B 콜드 스타트에서 TTFT P99 < 5초라면 거절하세요 — 2026년 인프라 속도로는 수학적으로 불가능합니다.
- 예산이 웜 풀을 막는데 SLA가 30초 미만 콜드 스타트를 요구한다면, 플랫폼별 해법(Modal GPU 스냅샷, Baseten 워밍)을 이름 붙이고, 그것 없이 다른 플랫폼에서 SLA를 약속하는 것을 거절하세요.
- 운영자가 버스트 트래픽과 70B 모델로 제로 스케일다운을 원한다면 SLA 약속을 거절하세요 — 스냅샷이나 웜 풀 없이는 수학이 안 맞습니다.

출력: 페이즈, 계층, `min_workers`, 월간 비용, 꼬리 정책, 장애 양상을 나열한 한 페이지짜리 계획. 마지막에 알람을 걸 단 하나의 지표: 최근 롤링 1시간 동안의 P99 콜드 스타트 소요 시간.
