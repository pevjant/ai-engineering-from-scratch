# 서버리스 LLM을 위한 콜드 스타트 완화

> 20GB 모델 이미지가 차가운 상태에서 서빙 가능까지 걸리는 시간은 7B 기준 5~10분, 70B 기준 20분 이상입니다. 진짜 서버리스 세계에서 이건 워밍업이 아니라 장애입니다. 완화 기법은 다섯 계층에서 동작합니다. 사전 시드된(pre-seeded) 노드 이미지(AWS의 Bottlerocket, 듀얼 볼륨 구조), 모델 스트리밍(NVIDIA Run:ai Model Streamer, vLLM에 기본 내장), GPU 메모리 스냅샷(Modal 체크포인트, 재시작 최대 10배 가속), 웜 풀(`min_workers=1`), 계층형 로딩(ServerlessLLM의 NVMe→DRAM→HBM 파이프라인, 지연 10~200배 절감), 그리고 KV 캐시(GB)가 아니라 입력 토큰(KB)을 옮기는 라이브 마이그레이션. Modal은 콜드 스타트 2~4초를 하한으로 공표하고, Baseten은 기본 5~10초, 워밍 시 1초 미만입니다. 이 레슨은 다섯 계층을 측정하고, 예산을 세우고, 겹쳐 쌓는 법을 가르칩니다.

**유형:** Learn
**언어:** Python (표준 라이브러리, 장난감 수준 콜드 스타트 경로 시뮬레이터)
**선수 지식:** Phase 17 · 02 (추론 플랫폼 경제학), Phase 17 · 03 (GPU 오토스케일링)
**시간:** 약 60분

## 학습 목표

- 콜드 스타트 완화의 다섯 계층을 열거하고 각 계층의 도구나 패턴을 하나씩 말할 수 있다.
- 70B 모델의 총 콜드 스타트 시간을 (노드 프로비저닝) + (가중치 다운로드) + (HBM에 가중치 로드) + (엔진 초기화)의 합으로 계산할 수 있다.
- 라이브 마이그레이션이 KV 캐시(GB)가 아니라 입력 토큰(KB)을 전송하는 이유와 그 대가(재계산)를 설명할 수 있다.
- 웜 풀의 트레이드오프(놂 GPU 비용 지불 또는 콜드 스타트 꼬리 감수)와, `min_workers > 0`이 강제되는 SLA 기준선을 말할 수 있다.

## 문제 상황

여러분의 서버리스 LLM 엔드포인트는 밤새 제로로 스케일다운됩니다. 아침 8시에 트래픽이 치솟습니다. 첫 요청은 이걸 기다립니다:

1. Karpenter가 GPU 노드를 프로비저닝: 45~60초.
2. 컨테이너가 가중치를 포함한 30GB 이미지를 풀: 120~300초.
3. 엔진이 가중치를 HBM에 로드: 모델 크기와 저장소 속도에 따라 45~120초.
4. vLLM이나 TRT-LLM이 CUDA 그래프, KV 캐시 풀, 토크나이저를 초기화: 10~30초.

합계: 토큰 하나가 돌아오기까지 220~510초(약 3~8분). 여러분의 SLA는 2초입니다. 웜 풀(`min_workers=1`)을 넣으면 문제가 사라진 것 같습니다 — 하지만 이제 놂 GPU 한 장을 24시간 연중무휴 지불합니다. 서비스가 5개 제품이고 각각 웜 레플리카 하나씩 갖고 있다면, 사용자가 한 명도 전화하지 않아도 5 × 24 × 30 = 월 3,600 GPU시간입니다.

콜드 스타트 완화란, 항상 켜져 있는(always-on) 지연에 근접하면서도 서버리스의 경제성을 지키는 기술입니다.

## 개념

### 계층 1 — 사전 시드된 노드 이미지 (Bottlerocket)

AWS에서 Bottlerocket의 듀얼 볼륨 구조는 OS와 데이터를 분리합니다. 컨테이너 이미지가 미리 풀려 있는 데이터 볼륨을 스냅샷으로 찍고, `EC2NodeClass`에 그 스냅샷 ID를 참조시킵니다. 새 노드는 가중치가 이미 로컬 NVMe에 있는 채로 부팅됩니다 — 2단계와 3단계의 일부가 증발합니다. Karpenter와 기본 연동됩니다. 대형 모델 기준 콜드 스타트당 보통 2~4분 절약입니다.

GCP의 동급 기능: 컨테이너 레이어를 구운 커스텀 VM 이미지. Azure: 같은 패턴의 매니지드 디스크 스냅샷.

### 계층 2 — 모델 스트리밍 (Run:ai Model Streamer)

첫 요청에 답하기 전에 파일 전체를 불러오는 대신, 가중치를 레이어별로 GPU 메모리에 스트리밍해서 첫 트랜스포머 블록이 자리 잡는 즉시 처리를 시작합니다. NVIDIA Run:ai Model Streamer는 vLLM 2026에 기본 탑재되어 있습니다. S3, GCS, 로컬 NVMe와 동작합니다. I/O와 컴퓨트 준비를 겹치게 해서 대형 모델의 가중치 로드 시간을 대략 절반으로 줄입니다.

### 계층 3 — GPU 메모리 스냅샷 (Modal)

Modal은 첫 로드 이후 GPU 상태(가중치, CUDA 그래프, KV 캐시 영역)의 체크포인트를 찍습니다. 이후 재시작은 직렬화를 풀어 HBM에 바로 올립니다 — 재초기화보다 10배 빠릅니다. "따뜻한 GPU를 2초 만에 부팅"과 가장 가까운 것입니다. 트레이드오프: 스냅샷은 GPU 토폴로지별로 묶여 있어서, Karpenter가 다른 SKU로 옮기면 다시 체크포인트해야 합니다.

### 계층 4 — 웜 풀 (min_workers=1)

가장 단순한 완화: 레플리카 하나를 항상 준비 상태로 둡니다. 비용은 GPU 한 장의 시간당 요금 24시간 연중무휴입니다. 산수는 작은 모델에서는 잔인합니다(30초 콜드 스타트를 피하려고 시간당 $0.85~$1.50 지불) 큰 모델에서는 관대합니다(5분 콜드 스타트를 피하려고 시간당 $4 지불). 웜 풀이 필수가 되는 SLA 기준선: 보통 70B 이상 모델에서 TTFT P99 < 60초입니다.

### 계층 5 — 계층형 로딩 (ServerlessLLM)

ServerlessLLM은 저장소를 계층으로 다룹니다: NVMe(빠르지만 큼), DRAM(중간이지만 계층화됨), HBM(작지만 즉시). 가중치를 DRAM에 미리 올려 두고, 필요할 때 HBM으로 로드합니다. 논문은 순진한 디스크→HBM 대비 콜드 로드 지연이 10~200배 감소했다고 보고합니다. 프로덕션(운영 환경) 채택은 초기 단계지만 vLLM 통합이 존재합니다.

### 계층 6 — 라이브 마이그레이션 (보너스 패턴)

노드가 사용 불가가 되면(스팟 회수, 노드 드레인) 전통적 패턴은 다른 레플리카를 콜드 스타트하고 요청 큐를 비우는 것이었습니다. 라이브 마이그레이션은 입력 토큰(킬로바이트)을 모델이 이미 로드된 목적지로 옮기고, 목적지에서 KV 캐시를 재계산합니다. GB 단위 KV 캐시를 네트워크로 전송하는 것보다 재계산이 쌉니다. 분리형 배포에 적용됩니다.

### 웜 풀 산수

TTFT SLA가 2초인 서비스라면 질문은 "웜 풀 넣을까 말까"가 아니라 "웜 레플리카를 몇 개, 어떤 경로에 둘까"입니다.

- 고가치 대화형 경로(라이브 채팅, 음성 에이전트): `min_workers=1-2`.
- 백그라운드 배치 경로(야간 분류): 제로 스케일다운을 수용, 5~10분 콜드 스타트 허용 가능.
- 프리미엄 티어: 전용 용량으로 테넌트별 `min_workers`.

### 최적화 전에 측정하라

새 노드에서 70B 모델의 콜드 스타트 해부(예시):

| 페이즈 | 시간 | 완화 기법 |
|-------|------|-----------|
| 노드 프로비저닝 | 50초 | Bottlerocket + 사전 시드 이미지, 웜 풀 |
| 이미지 풀 | 180초 | 사전 시드 데이터 볼륨(제거) |
| 가중치 → HBM | 75초 | 모델 스트리머(절반); GPU 스냅샷(제거) |
| 엔진 초기화 | 20초 | 지속 CUDA 그래프 캐시 |
| 첫 포워드 | 3초 | 고유 최소 지연 |
| **콜드 총계** | **328초** | |
| **완화 적용 시 총계** | **약 15초** | 22배 절감 |

### 기억해야 할 숫자들

- Modal 콜드 스타트: 2~4초(GPU 스냅샷 사용).
- Baseten 기본 콜드 스타트: 5~10초; 워밍 시 1초 미만.
- 날것의 70B 콜드 스타트: 3~8분.
- Run:ai Model Streamer: 가중치 로드 약 2배 가속.
- ServerlessLLM 계층형 로딩: 지연 10~200배 절감(논문 숫자).

## 연습 문제

1. `code/main.py`를 실행하세요. 웜 레플리카 하나가, SLO를 넘기는 요청 유실이라는 콜드 스타트 세금을 내는 것보다 싸지는 손익분기 요청률을 계산하세요.
2. P99 TTFT SLA가 3초인 13B 모델을 배포합니다. 이를 달성하는 최소 완화 스택(가장 적은 계층)을 고르세요.
3. Bottlerocket 사전 시딩은 이미지 풀을 없애지만, 가중치는 여전히 스냅샷에서 HBM으로 로드됩니다. 스냅샷 기반 NVMe가 7GB/s로 읽는다면 70B 모델의 실제 소요 시간(wall-clock)을 계산하세요.
4. 여러분의 서버리스 프로바이더는 GPU 스냅샷(Modal)을 제공하는데 팀이 "스냅샷이 개인정보를 새나온다"며 거부합니다. 양쪽 논리를 펼치세요 — 현실적인 위험은 무엇이고, 완화책(휘발성 스냅샷, 암호화, 네임스페이스 격리)은 무엇인가요?
5. 계층형 웜 풀 정책을 설계하세요: 유료 사용자, 체험 사용자, 배치 워크로드에 각각 웜 레플리카 몇 개? 계산 과정을 보이세요.

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| 콜드 스타트 | "그 유명한 큰 멈춤" | 새 레플리카에서 요청부터 첫 토큰까지의 시간 |
| 웜 풀 | "항상 켜는 최소치" | 최소 한 레플리카를 준비 상태로 유지하는 `min_workers >= 1` |
| 사전 시드 이미지 | "구운 AMI" | 컨테이너 가중치가 미리 들어 있는 노드 이미지 |
| Bottlerocket | "AWS 노드 OS" | 듀얼 볼륨 스냅샷을 지원하는 AWS 컨테이너 최적화 OS |
| 모델 스트리머 | "스트리밍 로드" | 가중치 I/O와 컴퓨트 준비를 겹침 |
| GPU 스냅샷 | "HBM으로 체크포인트" | 로드 후 GPU 상태를 직렬화; 재시작 시 역직렬화 |
| 계층형 로딩 | "NVMe + DRAM + HBM" | 저장 계층의 위계. 필요할 때 로드 |
| 라이브 마이그레이션 | "토큰만 옮기기" | 입력(KB)을 전송하고 목적지에서 KV 재계산 |
| `min_workers` | "웜 레플리카" | 서버리스 최소 유지 수 |
| 제로 스케일다운 | "풀 서버리스" | 유휴일 때 비용 없음. 콜드 스타트 세금 전액 감수 |
