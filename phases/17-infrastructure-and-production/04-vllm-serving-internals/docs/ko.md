# 서빙 엔진 내부 구조 — PagedAttention, 컨티뉴어스 배칭, 청크드 프리필

> 최신 서빙 엔진의 처리량은 하나의 마법 기술이 아니라, 서로 겹쳐 효과를 내는 세 가지 기본 설정에서 나옵니다. PagedAttention은 항상 켜져 있습니다. 컨티뉴어스 배칭(continuous batching)은 디코드 반복 사이사이에 새 요청을 활성 배치에 끼워 넣습니다. 청크드 프리필(chunked prefill)은 긴 프롬프트를 잘게 나눠서 디코드 토큰이 굶지 않게 합니다. 셋을 모두 켜면 H100 SXM5 한 장에서 Llama 3.3 70B FP8이 동시 128 기준 초당 2,200~2,400 토큰을 밀어냅니다 — vLLM 기본값보다 약 25% 높고, 순진한 PyTorch 루프의 3~4배입니다. 이 레슨은 세 기술 모두의 레퍼런스 엔진인 vLLM의 스케줄러와 어텐션 커널을 그림을 그릴 수 있는 수준까지 읽어 보고, 마지막에 vLLM과 같은 방식으로 프리필과 디코드를 스케줄링하는 장난감 컨티뉴어스 배처를 `code/main.py`로 만들어 봅니다.

**유형:** Learn
**언어:** Python (표준 라이브러리, 장난감 수준 컨티뉴어스 배칭 스케줄러)
**선수 지식:** Phase 17 · 01 (모델 서빙), Phase 11 (LLM 엔지니어링)
**시간:** 약 75분

## 학습 목표

- PagedAttention을 KV 캐시 할당자로서 설명할 수 있다: 블록, 블록 테이블, 그리고 프로덕션(운영 환경) 부하에서 파편화가 4% 미만으로 유지되는 이유.
- 컨티뉴어스 배칭을 반복(iteration) 수준에서 그림으로 그릴 수 있다: 끝난 시퀀스가 배치를 떠나고 새 시퀀스가 비우지 않고(join without draining) 합류하는 방식.
- 청크드 프리필을 한 문장으로 설명하고, 어떤 지연 시간 지표를 보호하는지 말할 수 있다(힌트: 평균 처리량이 아니라 TTFT 꼬리).
- 모든 최적화를 한꺼번에 켰다가 다치는 팀들이 있는 2026년 vLLM v0.18.0의 함정을 말할 수 있다.

## 문제 상황

순진한 PyTorch 서빙 루프는 요청을 하나씩 처리합니다: 토큰화 → 프리필 → EOS까지 디코드 → 반환. 사용자가 한 명이면 잘 돌아갑니다. 백 명이면 인내심 있는 사람들의 줄이 됩니다. 뻔한 해법인 정적 배칭(static batching)은 모든 요청을 윈도우 내 가장 긴 프롬프트에 맞춰 패딩하고, 모든 디코드를 가장 긴 예상 출력에 맞춰 패딩한 뒤, 배치 전체가 가장 느린 시퀀스에 맞춰 멈춥니다. 쓰지도 않는 패딩 값을 지불하고, 빠른 요청들은 느린 요청을 기다립니다.

vLLM은 세 문제를 한 번에 해결합니다. PagedAttention은 고전적인 연속 할당이 그러하듯 KV 캐시 파편화가 GPU 메모리의 60~80%를 잡아먹는 것을 막습니다. 컨티뉴어스 배칭은 디코드 반복 사이마다 요청이 배치에 들어오고 나갈 수 있게 해서, 배치가 항상 진짜 일로 가득 차게 합니다. 청크드 프리필은 32k 토큰짜리 프롬프트를 약 512토큰 조각으로 쪼개 디코드와 섞어서 실행하기 때문에, 긴 프롬프트 하나가 GPU의 모든 디코드 토큰을 얼려 버리는 일이 없습니다.

2026년의 프로덕션(운영 환경) 기본값은 셋 모두 켜기입니다. 각각이 무엇을 하는지 이해해야 하는 이유는, 장애 양상이 전부 모델이 아니라 스케줄러 쪽에 있기 때문입니다.

## 개념

### 가상 메모리 시스템으로서의 PagedAttention

KV 캐시는 시퀀스 하나당 `num_layers × 2 × num_heads × head_dim × seq_len × bytes_per_element`입니다. 8192 토큰 기준 Llama 3.3 70B에서는 BF16으로 시퀀스 하나당 대략 1.25GB입니다. 모든 요청에 8192 슬롯을 미리 잡아 두는데 평균 요청이 1500 토큰만 쓴다면, 예약해 둔 HBM의 약 82%를 낭비하는 셈입니다. 고전적 배칭은 이 낭비를 그대로 지불합니다.

PagedAttention은 OS 가상 메모리에서 아이디어를 빌려 옵니다. KV 캐시는 시퀀스별로 연속적이지 않습니다. 고정 크기 블록(기본 16토큰) 단위로 할당됩니다. 각 시퀀스는 자신의 논리적 토큰 위치를 물리적 블록 ID로 매핑하는 블록 테이블을 갖습니다. 시퀀스가 할당된 블록을 넘어 자라면 블록 하나를 더 붙입니다. 끝나면 그 블록들은 풀로 돌아갑니다.

파편화는 60~80%(고전적)에서 4% 미만(PagedAttention)으로 떨어집니다. PagedAttention은 플래그로 켜는 게 아닙니다 — vLLM이 제공하는 유일한 할당자입니다. 손잡이(knob)는 `--gpu-memory-utilization`(기본 0.9)이고, 이것은 가중치와 활성값을 올린 뒤 KV 블록용으로 얼마나 HBM을 예약할지 vLLM에게 알려 줍니다.

### 반복 수준의 컨티뉴어스 배칭

옛날 "다이내믹 배칭"은 윈도우(예: 10ms)가 차서 배치가 채워지길 기다렸다가, 프리필 + 디코드 + 디코드 + 디코드...를 모든 시퀀스가 끝날 때까지 돌렸습니다. 빠른 시퀀스는 일찍 끝났는데도 GPU가 느린 것들을 마저 끝낼 때까지 놀아야 했습니다.

컨티뉴어스 배칭은 각 디코드 스텝 '사이'에서 동작합니다. 실행 중인 시퀀스 집합을 `RUNNING` 리스트라고 부릅니다. 매 반복마다:

1. `RUNNING`에 있던 시퀀스 중 방금 EOS 또는 max_tokens에 도달한 것을 제거합니다.
2. 스케줄러는 대기 큐를 봅니다. 여유 KV 블록이 있으면 새 시퀀스(프리필 또는 재개)를 받아들입니다.
3. 포워드 패스는 이 시점의 `RUNNING`에 있는 것들 전부에 대해 돌고, 시퀀스마다 새 토큰 하나씩을 내놓습니다.

배치 크기는 고정 숫자로 패딩되는 일이 없습니다. 출력의 서로 다른 위치에 있는 시퀀스들이 하나의 퓨즈드(fused) 포워드를 공유합니다. 2026년 vLLM에서는 이것을 `V1 scheduler`라고 부릅니다. 핵심 불변식: 스케줄러는 요청당 한 번이 아니라 디코드 반복당 한 번 돈다.

### 청크드 프리필은 TTFT 꼬리를 지킨다

프리필은 컴퓨트 바운드입니다. Llama 3.3 70B에서 32k 토큰 프롬프트 하나에 H100 한 장 기준 순수 프리필로 약 800ms가 듭니다. 프리필이 도는 동안 배치 안 다른 모든 시퀀스의 디코드 토큰은 기다립니다. 서빙 루프에서는 한 명의 긴 프롬프트가 만든 첫 토큰 지연(TTFT)이, 수십 명의 다른 사용자에게 토큰 간 지연(ITL) 스파이크로 전가됩니다.

청크드 프리필은 프리필을 고정 크기 청크(기본 512토큰)로 쪼개고 각 청크를 스케줄링 단위로 삼습니다. 청크와 청크 사이에 스케줄러는 디코드 시퀀스를 한 토큰씩 진행시킬 수 있습니다. 절대적인 프리필 지연을 조금 희생하고(청크당 몇 ms) 그 대신 디코드 시점의 지터(jitter)를 크게 줄이는 거래입니다. 공개 벤치마크 기준으로 혼합 부하에서 P99 ITL은 약 50ms에서 약 15ms로 떨어집니다.

### 세 기본 설정은 서로를 전제한다

세 기능은 서로를 전제합니다. PagedAttention은 스케줄러에게 세밀하게(fine-grained) 나눠 거래할 수 있는 KV 자원을 줍니다. 컨티뉴어스 배칭은 그 세밀한 자원이 있어야 새 시퀀스를 받아들일 때 전역 재배치가 필요하지 않습니다. 청크드 프리필은 같은 `RUNNING` 리스트에 대해 스케줄러가 내리는 결정입니다 — 별개의 시스템이 아니라 스케줄러 정책 하나일 뿐입니다.

모든 플래그를 외울 필요는 없습니다. 스케줄러가 무엇을 최적화하는지만 알면 됩니다: KV 블록 예산 안에서, 청크드 프리필 슬라이싱이라는 조건 하의 굿푸트(goodput)입니다.

### 2026년 v0.18.0의 함정

vLLM v0.18.0에서는 `--enable-chunked-prefill`을 드래프트 모델 기반 스페큘러티브 디코딩(`--speculative-model`)과 조합할 수 없습니다. 문서에 기재된 예외는 V1 스케줄러의 N-gram GPU 스페큘러티브 디코딩입니다. 릴리스 노트를 안 읽고 플래그를 전부 켠 팀은 소프트한 성능 저하가 아니라 시작 시점의 런타임 에러를 만납니다. 스페큘러티브로 얻는 이득이 청크드 프리필을 켤 만하다면 선택을 다시 검토하세요 — 2026년의 올바른 답은 대개 '청크드 프리필 없는 EAGLE-3'이지, 컴파일조차 안 되는 드래프트 모델 + 청크드 프리필이 아닙니다.

### 기억해야 할 숫자들

- Llama 3.3 70B FP8, H100 SXM5, 동시 128, 셋 모두 켬: 2,200~2,400 tok/s.
- 같은 모델, vLLM 기본값(청크드 프리필 없음): 약 1,800 tok/s.
- 같은 모델, 순진한 PyTorch 포워드 루프: 약 600 tok/s.
- 프로덕션(운영 환경) 부하에서 PagedAttention의 KV 파편화 낭비: 4% 미만.
- 혼합 부하에서 P99 ITL: 청크드 프리필 사용 시 약 15ms, 미사용 시 약 50ms.

### 스케줄러의 모습

```
while True:
    finished = [s for s in RUNNING if s.is_done()]
    for s in finished: release_blocks(s); RUNNING.remove(s)

    while WAITING and have_free_blocks_for(WAITING[0]):
        s = WAITING.pop(0)
        allocate_initial_blocks(s)
        RUNNING.append(s)

    # 프리필 청크 + 디코드를 하나의 배치로 스케줄링
    batch = []
    for s in RUNNING:
        if s.in_prefill:
            batch.append(next_prefill_chunk(s))   # 예: 512토큰
        else:
            batch.append(decode_one_token(s))     # 1토큰

    run_forward(batch)                            # 퓨즈드 GPU 호출 한 번
```

`code/main.py`는 정확히 이 루프를, 가짜 토큰 수와 가짜 포워드 지연으로 표준 라이브러리 파이썬으로 옮긴 것입니다. 실행해 보면 긴 프리필이 진행되는 동안 청크드 프리필이 디코드 시퀀스를 어떻게 살아 있게 하는지 보입니다.

## 직접 써보기

`code/main.py`는 기능을 켜고 끌 수 있는 vLLM식 스케줄러를 시뮬레이션합니다. 실행해 보면:

- `NAIVE` 모드: 한 번에 요청 하나, 배칭 없음.
- `STATIC` 모드: 패딩하고 기다리는 고전적 배칭.
- `CONTINUOUS` 모드: 반복 수준의 입장과 퇴장.
- `CONTINUOUS + CHUNKED` 모드: 프리필 조각을 디코드와 섞어서 실행.

출력에는 총 처리량(가상 초당 토큰), TTFT 평균, P99 ITL이 나옵니다. 혼합 트래픽에서는 `CONTINUOUS + CHUNKED` 행이 가장 좋아야 합니다.

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| PagedAttention | "KV 트릭" | KV 캐시용 고정 크기 블록 할당자. 파편화 4% 미만 |
| 블록 테이블 | "페이지 테이블" | 시퀀스별로 논리 토큰 위치를 물리 KV 블록으로 매핑한 표 |
| 컨티뉴어스 배칭 | "제대로 만든 다이내믹 배칭" | 매 디코드 반복마다 입장/퇴장 결정을 내림 |
| 청크드 프리필 | "프리필 분할" | 긴 프리필을 512토큰 조각으로 쪼개 디코드와 섞어 실행 |
| TTFT | "첫 토큰 시간" | 프리필 + 대기 + 네트워크. 긴 프롬프트에서는 프리필이 지배 |
| ITL | "토큰 간 지연" | 연속된 디코드 토큰 사이의 시간. 배치 크기가 지배 |
| 굿푸트(Goodput) | "SLO를 충족하는 처리량" | 모든 요청이 TTFT와 ITL 목표를 지키는 조건의 초당 토큰 수 |
| V1 scheduler | "새 스케줄러" | vLLM의 2026년 스케줄러. N-gram 스펙 디코드가 청크드 프리필 호환 경로 |
| `--gpu-memory-utilization` | "메모리 손잡이" | 가중치와 활성값을 제외한 HBM 중 KV 블록으로 예약할 비율 |
