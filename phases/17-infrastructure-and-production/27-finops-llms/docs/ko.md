# LLM을 위한 FinOps — 단위 경제학과 멀티 테넌트 비용 귀속

> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [en.md](en.md)

> 전통적인 FinOps는 LLM 지출 앞에서 무너집니다. 비용이 리소스 가동 시간이 아니라 토큰 트랜잭션으로 발생하기 때문입니다. 태그도 맞지 않습니다 — API 호출은 자산이 아니라 트랜잭션입니다. 그리고 엔지니어링 결정(프롬프트 설계, 컨텍스트 윈도우, 출력 길이)이 곧 재무 결정입니다. 2026년의 플레이북은 첫날부터 계측해야 하는 세 가지 귀속(attribution) 차원을 말해 줍니다. 사용자별(`user_id`) — 좌석(seat) 가격 책정과 확장 대화용, 작업별(`task_id` + `route`) — 제품 영역별 비용과 우선순위용, 테넌트별(`tenant_id`) — 단위 경제학과 갱신 협상용. 토큰 계층은 네 가지 — 프롬프트, 도구, 메모리, 응답 — 이고, 한 바구니에 섞으면 지출이 가려집니다. 멀티 테넌트 제품의 집행 사다리: 테넌트별 속도 제한(예상 피크의 2~3배, 명확한 429 + retry-after), 일일 지출 한도(계약 상한의 1.5~3배, 속도 강화 + 알림 트리거), 지출 z-점수 > 4에서 킬 스위치(자동 일시정지 + 온콜 호출). 귀속 패턴: 태그 후 집계, 텔레메트리 조인(trace-ID → 청구, 가장 정확), 샘플링 후 외삽, 모델 기반 배분, 이벤트 소싱, 실시간 스트리밍. 단위 지표: 해결된 쿼리당 비용, 생성된 산출물당 비용 — $/M 토큰이 아닙니다. 사후 태깅은 언제나 놓치는 게 생깁니다. 요청 생성 시점에 계측하세요.

**유형:** Learn
**언어:** Python (표준 라이브러리, 킬 스위치가 있는 장난감 수준의 비용 귀속 시뮬레이터)
**선수 지식:** 페이즈 17 · 13 (관측 가능성), 페이즈 17 · 14 (캐싱)
**시간:** 약 60분

## 학습 목표

- 전통적인 FinOps(태그 + 등급)가 LLM 지출 앞에서 왜 무너지는지 설명하고, 세 가지 새로운 귀속 차원을 말할 수 있습니다.
- 네 가지 토큰 계층(프롬프트, 도구, 메모리, 응답)과, 한 바구니 청구가 비용을 왜 가려 버리는지 설명할 수 있습니다.
- 멀티 테넌트 제품을 위한 집행 사다리(속도 제한 → 지출 한도 → 킬 스위치)를 설계할 수 있습니다.
- $/M 토큰 대신 단위 지표(해결된 쿼리당 / 산출물당 비용)를 고를 수 있습니다.

## 문제 상황

청구서에 40,000달러가 찍혀 있습니다. 하지만 모르는 것들:
- 어느 테넌트가 쓴 돈인지.
- 어떤 제품 기능이 이 지출을 만들었는지.
- 특정 사용자가 남용했는지 여부.
- 범인이 프롬프트 비대, 도구 호출, 메모리 증폭 중 무엇인지.

공급자 측 태그 후 집계는 태그가 라인 아이템까지 전파되는 클라우드 리소스(EC2, S3)에서는 잘 통합니다. 하지만 LLM API 호출은 자동 태깅이 안 됩니다 — 호출 지점에서 user/task/tenant를 직접 도장 찍고 끝까지 끌고 가야 합니다. 사후 귀속은 언제나 예외 케이스를 놓칩니다.

## 개념

### 세 가지 귀속 차원

**사용자별** (`user_id`): 누가 얼마를 쓰는가. 좌석 가격 책정, 확장 대화, 파워 유저 식별을 이끕니다.

**작업별** (`task_id` + `route`): 어떤 제품 영역이 얼마를 쓰는가. 기능 우선순위, 비싼 기능 쳐내기 결정을 이끕니다.

**테넌트별** (`tenant_id`): 어느 고객이 수익을 내는가. 단위 경제학, 갱신 가격, 등급 기준점을 이끕니다.

첫날부터 호출 지점에서 셋 모두 계측하세요. 사후 처리는 언제나 더 나쁩니다.

### 네 가지 토큰 계층

| 계층 | 예시 | 전체에서 차지하는 비중(일반적) |
|-------|---------|---------------------|
| 프롬프트 | 시스템 + 사용자 입력 | 40-60% |
| 도구 | 되먹임되는 도구 호출 결과 | 20-40% (에이전트 워크로드) |
| 메모리 | 이전 대화 / 검색된 문서 | 10-30% |
| 응답 | 모델 출력 | 10-30% |

네 계층을 한 바구니에 넣으면 최적화가 눈먼 상태가 됩니다. 귀속 스키마에서 분리해서 기록하세요.

### 집행 사다리

1. **속도 제한** 테넌트별. 예상 피크의 2~3배. `Retry-After`가 붙은 429를 반환합니다. 테넌트는 불편을 느끼지만, 깜짝 청구서는 받지 않습니다.

2. **일일 지출 한도** 테넌트별. 계약 상한의 1.5~3배. 트리거: 속도 제한 강화 + 고객 성공(CS) 팀 알림.

3. **킬 스위치** 지출 z-점수가 테넌트 베이스라인 대비 4를 넘을 때. 테넌트 자동 일시정지. 온콜 호출. 운영 + CS 에스컬레이션.

### 귀속 패턴

- **태그 후 집계**: 메타데이터 헤더를 찍고 나중에 집계. 단순하지만 대략적.
- **텔레메트리 조인**: 트레이스 ID로 트레이스와 청구를 조인. 가장 정확합니다. 성숙한 팀의 방식.
- **샘플링 + 외삽**: 5~10%를 샘플링해 곱함. 대략적인 지출 파악엔 비용 효율적, 꼬리는 놓침.
- **모델 기반 배분**: 회귀로 비용 원인을 추정. 태그 없는 레거시 데이터용.
- **이벤트 소싱**: 비용을 스트림(Kafka / Kinesis) 속 이벤트로. 실시간.
- **실시간 스트리밍**: 대시보드가 1초 미만으로 갱신.

### X당 비용이 단위 지표

$/M 토큰은 벤더의 언어입니다. 제품 지표는 이렇습니다:

- 해결된 지원 티켓당 비용.
- 생성된 아티클당 비용.
- 성공한 에이전트 작업당 비용.
- 사용자 세션 1분당 비용.

비용을 제품 성과에 묶으세요. 그렇지 않으면 최적화가 닻 없이 떠다닙니다.

### 비용 귀속 트레이스 형태

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

모든 호출에서 내보냅니다(emit). 데이터 레이크에 저장하고 차원별로 집계합니다. 페이즈 17 · 13의 관측 가능성 스택이 이 데이터가 사는 곳입니다.

### 복리 효과가 있는 절감 스택

스택: 캐시 + 배치 + 라우팅 + 게이트웨이. 넷 모두를 갖추면:
- 캐시 L2 (페이즈 17 · 14): 입력 비용 약 10배 절감.
- 배치 (페이즈 17 · 15): 50% 할인.
- 저렴한 모델로 라우팅 (페이즈 17 · 16): 비용 60% 절감.
- 게이트웨이 효율화 (페이즈 17 · 19): 중복 제거 + 재시도.

최상의 경우 누적 절감: 순진한 베이스라인의 약 5~10%. 대부분의 팀은 2~3개 레버만 당기고 있고, 넷을 쌓은 팀은 드뭅니다.

### 기억해야 할 숫자들

- 귀속 차원: 사용자별, 작업별, 테넌트별.
- 네 가지 토큰 계층: 프롬프트, 도구, 메모리, 응답.
- 킬 스위치: 지출 z-점수 > 4.
- 단위 지표: 해결된 쿼리당 비용, $/M 토큰이 아님.
- 누적 최적화: 베이스라인의 약 5~10%까지 가능.

## 연습 문제

1. `code/main.py`를 실행해 보세요. 킬 스위치는 몇 z-점수에서 발동할까요? 임계값은 어떻게 고를까요?
2. 테넌트별, 작업별 비용 대시보드를 설계하세요. 처음 만들 5개 뷰는 무엇인가요?
3. 가장 큰 테넌트의 단위 경제가 적자입니다. 고객에게 미치는 영향 순으로 개입 방법 세 가지를 제안하세요.
4. 지원 제품의 해결된 티켓당 비용을 계산하세요: 티켓당 3M 토큰, 하루 약 800티켓, GPT-5 캐시 요금.
5. 사후 태깅이 성공할 수 있는 경우가 있는지 논증해 보세요. 허용될 수 있는 때는 언제일까요?
