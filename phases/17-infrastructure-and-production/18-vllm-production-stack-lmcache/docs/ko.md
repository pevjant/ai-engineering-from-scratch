# 프로덕션(운영 환경) 서빙 스택 — KV 오프로딩과 캐시 인지 라우팅

> 프로덕션 서빙 스택은 라우터, 엔진, 관측 도구를 하나의 Kubernetes 배포로 묶습니다 — 그리고 KV 캐시를 GPU를 떠날 수 있는 자원으로 다룹니다. KV 오프로딩은 KV 캐시를 GPU 메모리에서 꺼내 쿼리와 엔진 사이에서 재사용합니다(CPU DRAM, 그다음 디스크/Ceph). vLLM의 production-stack이 참조 배포이고, LMCache가 오프로딩 계층입니다. vLLM 0.11.0 KV Offloading Connector(2026년 1월)는 Connector API(v0.9.0+)를 통해 이 과정을 비동기이자 플러그형으로 만들었습니다. 오프로드 경로는 보통 요청 경로에서 숨겨지지만, 캐시 미스와 프로모션(승격)이 종단 지연을 더할 수는 있습니다. 공개된 벤치마크(16x H100, 80GB HBM, 4개 a3-highgpu-4g)에 따르면: KV 캐시가 HBM을 넘으면 네이티브 CPU 오프로드와 LMCache 모두 처리량을 크게 개선합니다; KV 발자국이 작을 때는 모든 구성이 약간의 오버헤드만 더하며 베이스라인과 같습니다.

**유형:** 학습
**언어:** Python (표준 라이브러리, KV 유출(spill) 시뮬레이터 장난감 버전)
**선수 지식:** 페이즈 17 · 04 (서빙 엔진 내부 구조), 페이즈 17 · 06 (SGLang/RadixAttention)
**시간:** 약 60분

## 학습 목표

- vLLM production-stack의 계층을 그림으로 그릴 수 있습니다: 라우터, 엔진, KV 오프로드, 관측.
- KV Offloading Connector API(v0.9.0+)를 설명하고, 0.11.0 비동기 경로가 어떻게 오프로드 지연을 숨기는지 설명할 수 있습니다.
- LMCache CPU-DRAM이 도움되는 시점(KV > HBM)과 오버헤드만 더하는 시점(KV가 HBM에 충분히 들어감)을 수치화할 수 있습니다.
- 배포 제약 조건에 따라 네이티브 vLLM CPU 오프로드와 LMCache 커넥터 중 하나를 고를 수 있습니다.

## 문제 상황

vLLM 서빙에서 동시성이 오를 때마다 HBM이 100%가 되고 선점(preemption) 이벤트가 터집니다. 요청이 추방(evict)되고 다시 큐에 들어가고, 같은 2K 토큰 프롬프트를 1분에 네 번 다시 프리필합니다. GPU 연산은 중복 프리필에 소모되고; 굿풋(goodput, 실효 처리량)은 원시 처리량보다 한참 아래입니다.

GPU를 더 사면 비용이 선형으로 늘어납니다. HBM을 더 얹는 것은 불가능합니다. 하지만 CPU DRAM은 쌉니다 — 소켓 하나에 512 GB 이상이 들어가고, 지연 시간은 HBM보다 몇 자릿수 나쁘지만 "잠시 따뜻하게 보관하는" KV 캐시로는 충분합니다.

LMCache는 KV 캐시를 CPU DRAM으로 꺼내서 선점된 요청이 빨리 복구되게 하고, 엔진들 가운데 반복되는 프리픽스가 각자 다시 프리필하지 않고 캐시를 공유하게 합니다.

## 개념

### vLLM production-stack

`github.com/vllm-project/production-stack`이 참조 Kubernetes 배포입니다:

- **라우터** — 캐시 인지(페이즈 17 · 11). KV 이벤트를 소비합니다.
- **엔진** — vLLM 워커. GPU당 하나 또는 TP/PP 그룹당 하나.
- **KV 캐시 오프로드** — LMCache 배포 또는 네이티브 커넥터.
- **관측** — Prometheus 스크레이프, Grafana 대시보드, OTel 트레이스.
- **컨트롤 플레인** — 서비스 디스커버리, 설정, 롤링 업데이트.

Helm 차트 + 오퍼레이터로 제공됩니다.

### KV Offloading Connector API (v0.9.0+)

vLLM 0.9.0은 플러그형 KV 캐시 백엔드를 위한 Connector API를 도입했습니다. 엔진이 블록을 커넥터에 오프로드하면; 커넥터가 저장합니다(RAM, 디스크, 오브젝트 스토리지, LMCache). 요청이 블록을 필요로 하면 커넥터가 다시 불러옵니다.

vLLM 0.11.0(2026년 1월)은 비동기 오프로드 경로를 추가했습니다 — 일반적인 경우 엔진이 멈추지 않도록 오프로드가 백그라운드에서 일어날 수 있습니다. 다만 종단 지연과 처리량은 여전히 워크로드 형태, KV 캐시 적중률, 시스템 부하에 달려 있습니다; vLLM 자체 노트도 커스텀 커널 오프로드는 낮은 적중률에서 처리량을 떨어뜨릴 수 있다고, 그리고 비동기 스케줄링은 추측 디코딩(speculative decoding)과 알려진 상호작용 문제가 있다고 짚고 있습니다.

### 네이티브 CPU 오프로드 vs LMCache

**네이티브 vLLM CPU 오프로드**: 엔진 로컬. KV 블록을 호스트 RAM에 저장합니다. 구현이 빠르고, 네트워크 홉이 없습니다. 엔진을 넘지 못합니다.

**LMCache 커넥터**: 클러스터 규모. 블록을 공유 LMCache 서버(CPU DRAM + Ceph/S3 티어)에 저장합니다. 블록에 어떤 엔진이든 접근할 수 있습니다. 16x H100 벤치마크 공개.

엔진 하나에 HBM 압박이 있으면 네이티브를 고르세요. 여러 엔진이 프리픽스를 공유한다면(공통 시스템 프롬프트의 RAG, 공유 템플릿의 멀티테넌트) LMCache를 고르세요.

### 벤치마크 동작

16x H100(80 GB HBM)를 4개 a3-highgpu-4g에 펼친 테스트:

- 낮은 KV 발자국(짧은 프롬프트, 낮은 동시성): 모든 구성이 베이스라인과 같고, LMCache는 약 3-5% 오버헤드를 더합니다.
- 중간 발자국: LMCache가 엔진 간 프리픽스 재사용에서 도움되기 시작합니다.
- KV가 HBM을 초과: 네이티브 CPU 오프로드와 LMCache 모두 처리량을 크게 개선; LMCache가 교차 엔진 공유 덕에 더 큰 이득.

### LMCache가 결정적인 경우

- 시스템 프롬프트가 테넌트들 사이에서 공유되는 멀티테넌트 서빙.
- 문서 청크가 쿼리들 사이에서 반복되는 RAG.
- 같은 베이스 모델 위의 파인튜닝 변형(LoRA) — 베이스 모델 KV 재사용이 중복 작업을 줄입니다.
- 선점이 잦은 워크로드: CPU에서 복구하는 것이 다시 프리필보다 쌉니다.

### 켜면 안 되는 경우

- HBM 압박이 작음 — 이득 없이 오버헤드만 냅니다.
- 짧은 컨텍스트(1K 토큰 미만) — 전송 시간 > 재프리필.
- 단일 테넌트 단일 프롬프트 워크로드 — 챙길 재사용이 없습니다.

### 분리 서빙과의 통합

페이즈 17 · 17의 분리 서빙 + LMCache는 시너지를 냅니다: 프리필 풀에서 디코드 풀로 옮겨간 KV가 쓰이지 않으면 LMCache에 안착하고; 이후 쿼리는 LMCache에서 꺼냅니다. 페이즈 17 · 11의 캐시 인지 라우터는 로컬 캐시든 LMCache 공유 캐시든 매칭되는 엔진으로 라우팅할 수 있습니다.

### 기억해야 할 숫자들

- vLLM 0.9.0: Connector API 출시.
- vLLM 0.11.0 (2026년 1월): 비동기 오프로드 경로; 종단 지연 영향은 워크로드, KV 적중률, 시스템 부하에 달림(절대적 보장 아님).
- 16x H100 벤치마크: KV 발자국이 HBM을 넘을 때 LMCache가 도움됩니다.
- HBM 압박이 작을 때: 이득 없이 3-5% 오버헤드.

## 연습 문제

1. `code/main.py`를 실행하세요. 어떤 HBM 사용률에서 LMCache가 값을 내기 시작하나요?
2. 어떤 테넌트가 6K 토큰 시스템 프롬프트를 시간당 200개 쿼리에 걸쳐 공유합니다. 테넌트당 예상 LMCache 절감액을 계산하세요.
3. LMCache 서버는 단일 장애점입니다. HA 전략을 설계하세요(복제본, 네이티브로의 폴백).
4. LMCache가 회전 디스크의 Ceph에 저장합니다. 70B FP8에서 4K 토큰 KV(500 MB)라면 읽기 시간은 재프리필과 비교해 얼마나 될까요?
5. vLLM 0.11.0 비동기 경로가 "공짜"인지 논증해 보세요 — 오버헤드는 어디에 숨어 있나요?

## 핵심 용어

| 용어 | 사람들이 말하는 표현 | 실제 의미 |
|------|----------------|------------------------|
| Production-stack | "그 참조 배포" | vLLM의 Kubernetes Helm 차트 + 오퍼레이터 |
| Connector API | "KV 백엔드 인터페이스" | vLLM 0.9.0+ 플러그형 KV 스토어 인터페이스 |
| 네이티브 CPU 오프로드 | "엔진 로컬 유출" | 같은 엔진의 호스트 RAM에 KV 저장 |
| LMCache | "클러스터 KV 캐시" | CPU DRAM + 디스크 위의 교차 엔진 KV 캐시 서버 |
| 0.11.0 비동기 | "논블로킹 오프로드" | 엔진 스트림 뒤로 숨겨진 오프로드 |
| 선점(Preemption) | "자리 만들려고 추방" | HBM이 찼을 때의 KV 캐시 재배치 |
| 프리픽스 재사용 | "같은 시스템 프롬프트" | 여러 쿼리가 시작부 공유; 캐시 적중 |
| Ceph 티어 | "디스크 티어" | 캐시 계층에서 DRAM 아래의 영구 저장소 |
