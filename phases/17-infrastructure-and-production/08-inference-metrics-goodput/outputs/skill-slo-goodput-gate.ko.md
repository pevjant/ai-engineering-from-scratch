> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [skill-slo-goodput-gate.md](skill-slo-goodput-gate.md)

워크로드(모델, 하드웨어, 목표 동시성, 사용자 대면 상호작용 유형 — 스트리밍 채팅 / 단발 / 음성 / 에이전트)가 주어지면 CI/CD용 굿푸트 기반 SLO 관문을 만듭니다.

산출물:

1. SLO 명세. 세 개의 기준값: TTFT P99 상한, TPOT P99 상한, E2E P99 상한. 상호작용 유형에서 방어 가능한 값을 고릅니다(스트리밍 채팅: TTFT 500ms, TPOT 25ms, E2E 3초; 음성: TTFT 300ms로 더 조임; 에이전트: E2E 5초로 더 느슨).
2. 벤치마크 레시피. 도구 선택(LLMPerf 또는 GenAI-Perf — 무엇을 골랐는지, 왜인지 명시). 프롬프트 분포(입력·출력 토큰의 평균 + 표준편차). 동시성 스윕(목표의 25%, 50%, 100%, 150%).
3. 굿푸트 계산. 공식: 세 제약을 모두 동시에 충족한 요청의 비율. 프로덕션(운영 환경) 목표 >= 99%, 카나리 >= 95%.
4. 백분위 보고. 모든 지표에 대해 P50, P90, P99를 보고(평균만 단독으로 금지). 평균은 건전성 확인(sanity check) 용도로만 각주.
5. 도구 함정 주석. 도구가 ITL에 TTFT를 포함하는지 아닌지 명시합니다. 팀 간 비교 전에 정의를 고정하세요.
6. 판정 로직. 목표 동시성에서 굿푸트 >= 목표면 CI 통과. 100%와 150% 동시성 사이에 굿푸트가 5포인트 이상 떨어지면 표시 — 부하 테스트 여유분(headroom)이 없다는 신호입니다.

하드 리젝(절대 금지):

- 처리량만으로 판정하는 것. 거절하고 굿푸트를 요구하세요.
- P99 없이 평균만 보고하는 것. 거절하세요.
- 도구 이름과 도구 버전을 생략하는 것. 거절하세요.
- 목표 동시성에서만 벤치마크하는 것. 항상 스윕을 돌리세요.

거절 규칙:

- 사용자가 문서화된 SLO가 없다면 거절하고, 먼저 상호작용 유형에 기반해 하나를 작성하세요.
- 프롬프트 분포가 "같은 프롬프트를 루프로"라면 거절하세요 — 프롬프트 균일성 함정입니다. 현실적인 합성 트래픽을 요구하세요.
- 벤치마크가 30회 미만이거나 실행당 요청 100개 미만이면 통계적으로 불충분하다고 거절하세요.

출력: 기준값, 벤치마크 레시피, 도구 선택, 백분위 보고 템플릿, CI 통과/실패 규칙을 나열한 한 페이지짜리 SLO 관문 명세. 마지막에 "다음에 무엇을 측정할까" 단락으로, 알려진 약점에 따라 굿푸트 vs 동시성 곡선, 프롬프트 분포 민감도, 또는 청크드 프리필 켬/끔 꼬리 비교 중 하나를 이름 붙입니다.
