> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [skill-quantization-picker.md](skill-quantization-picker.md)

하드웨어(CPU / H100 / H200 / B200 / GB200, 장수 포함), 엔진(llama.cpp / vLLM / TRT-LLM / SGLang), 모델(크기 + 태스크 유형 — 루틴 채팅 / 추론 / 코드 / 멀티-LoRA), 품질 허용치(HumanEval / MATH / MMLU에서 N포인트 하락을 감수 가능)가 주어지면 양자화 포맷을 골라 검증 계획을 만듭니다.

산출물:

1. 포맷 권고. 다음 중 하나: GGUF Q4_K_M, GGUF Q5_K_M, GPTQ-Int4 + Marlin, AWQ-Int4 + Marlin, FP8, NVFP4 + FP8 KV, 또는 겹친 조합. 결정 트리로 근거를 대세요: CPU → GGUF; 추론 → FP8; vLLM의 멀티-LoRA → GPTQ; 루틴 GPU 채팅 → AWQ; 검증된 Blackwell → NVFP4.
2. 메모리 예산. 가중치 + KV 캐시(보고된 동시성 × 컨텍스트 기준) + 활성값을 보고합니다. 목표 GPU에 들어가는지 확인하거나 멀티 GPU 요건을 명시합니다.
3. 캘리브레이션 계획. 데이터셋 출처(AWQ/GPTQ는 도메인 일치; 범용 C4/WikiText는 최후의 수단). 샘플 수(도메인 기준 500~2000). 검증 세트(캘리브레이션 풀에서 10% 홀드아웃).
4. 검증 계획. 태스크에 맞는 eval 세트: 코드는 HumanEval, 추론은 MATH/MMLU, 채팅은 MT-Bench. 베이스라인 BF16 vs 양자화 비교. 하락이 품질 허용치 이하면 출시.
5. KV 캐시 결정. 가중치 양자화와 분리합니다. 추론에는 FP8 KV를 권합니다. 어텐션 정확도가 한계점이라면 BF16 KV. INT8 KV는 검증 후에만.
6. 롤백 경로. BF16/FP8 가중치를 디스크에 유지하고, 프로덕션(운영 환경) 품질이 저하되면 되돌릴 수 있는 플래그를 만들어 둡니다.

하드 리젝(절대 금지):

- eval 세트 검증 없이 추론 사고형 워크로드에 NVFP4 가중치를 권하는 것.
- 도메인 모델을 범용 웹 데이터로 캘리브레이션하는 것. 반드시 도메인 내 데이터를 쓰세요.
- HBM 예산에서 KV 캐시를 잊는 것. 반드시 항목별로 적으세요.
- 커널 이름을 밝히지 않고 처리량 숫자를 주장하는 것(Marlin-AWQ vs 평범 AWQ는 10배 차이).

거절 규칙:

- 워크로드가 본질적으로 품질 한계점(자유로운 창작 생성, 경계 사례 추론)이라면 공격적 INT4를 거절하세요. FP8이나 BF16에 머무세요.
- 엔진이 llama.cpp라면 GGUF 이외의 어떤 포맷도 거절하세요. 엔진에 맞는 포맷 매칭은 기본 소양입니다.
- 사용자가 1,000샘플 eval을 돌릴 수 없다면 거절하세요. 프로덕션에서 눈 감고 하는 양자화는 없습니다.

출력: 선택한 포맷, HBM 예산, 캘리브레이션 계획, 검증 계획, KV 캐시 결정, 롤백 경로를 나열한 한 페이지짜리 양자화 선택. 마지막에 "다음에 무엇을 측정할까" 단락으로, 핵심 위험에 따라 eval 세트 델타, 피크 동시성에서의 KV 캐시 압박, 또는 실제 배치 크기에서의 처리량 중 하나를 이름 붙입니다.
