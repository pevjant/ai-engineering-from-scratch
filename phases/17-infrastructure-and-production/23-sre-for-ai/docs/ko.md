# AI를 위한 SRE — 멀티 에이전트 인시던트 대응, 런북, 예측형 감지

> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [en.md](en.md)

> AI SRE는 RAG를 통해 인프라 데이터(로그, 런북, 서비스 토폴로지)에 근거한 LLM으로 조사·문서화·조율 단계를 자동화합니다. 2026년의 아키텍처 패턴은 멀티 에이전트 오케스트레이션, 즉 슈퍼바이저가 전문 에이전트들(로그, 메트릭, 런북)을 조율하는 방식이며, AI는 가설과 쿼리를 제안하고 판단이 필요한 순간은 사람이 승인합니다. Datadog Bits AI와 Azure SRE Agent는 이를 매니지드(managed) 제품으로 제공합니다. 런북도 진화하고 있습니다. NeuBird Hawkeye는 적대적 평가(두 모델이 같은 인시던트를 분석하고, 의견이 일치하면 확신, 불일치하면 불확실)를 사용하고, 운영 지식(operational memory)은 팀원이 바뀌어도 남아 있습니다. 자동 복구(auto-remediation)는 여전히 신중합니다. AI가 제안하고 사람이 승인합니다. 완전 자율 실행은 아주 좁은 범위(파드 재시작, 특정 배포 롤백)에서만, 빡빡한 가드레일 안에서 이뤄집니다. "한 번 설정하면 끝"이라고 파는 곳이 있다면 과장된 광고입니다. 떠오르는 새 영역은 인시던트 사전 예측입니다. MIT 연구에 따르면 과거 로그 + GPU 온도 + API 오류 패턴으로 학습한 LLM이 장애의 89%를 10~15분 전에 예측했다고 합니다. 전망: 2026년 말까지 기업용 LLM의 95%가 자동 페일오버를 갖춥니다.

**유형:** Learn
**언어:** Python (표준 라이브러리, 장난감 수준의 멀티 에이전트 인시던트 트리아지 시뮬레이터)
**선수 지식:** 페이즈 17 · 13 (관측 가능성), 페이즈 17 · 24 (카오스 엔지니어링)
**시간:** 약 60분

## 학습 목표

- 멀티 에이전트 AI SRE 아키텍처를 그림으로 그릴 수 있습니다. 슈퍼바이저 + 전문 에이전트(로그, 메트릭, 런북) + 사람 승인 게이트.
- 자동 복구가 넓은 범위(서비스 재설계)가 아니라 좁은 범위(파드 재시작, 배포 되돌리기)로 제한되는 이유를 설명할 수 있습니다.
- 적대적 평가 패턴(NeuBird Hawkeye)의 이름을 말할 수 있습니다. 두 모델의 의견이 일치하면 확신, 불일치하면 사람에게 에스컬레이션.
- MIT의 89% 조기 감지 결과와 운영상 제약을 인용할 수 있습니다. 실행(action) 없는 예측은 그저 대시보드일 뿐입니다.

## 문제 상황

새벽 3시에 온콜 엔지니어의 호출기가 울립니다. "체크아웃에서 오류율 급증." Datadog을 확인하고, Loki를 확인하고, 런북 세 개를 넘기고, 배포 로그를 훑습니다. 30분 뒤에야 근본 원인이 KV 캐시 급증으로 인한 vLLM OOM(메모리 부족)임을 알아차립니다. 파드를 재시작하자 오류가 사라집니다.

2026년에는 이 조사의 처음 20분이 자동화 가능합니다. 서비스별로 로그를 묶고, 최근 배포와 연관 짓고, 런북과 대조하는 일 — 이 모든 것이 RAG + 도구 사용으로 처리됩니다. 감독(supervised) 방식의 에이전트라면 사람이 Datadog을 열기 전에 1차 트리아지를 끝내고 가설까지 제시할 수 있습니다.

완전 자율 복구는 다른 차원의 문제입니다. 파드 재시작: 안전합니다. GPU 풀 스케일 조정: 정책이 허용하면 안전합니다. 서비스 재설계: 절대 안 됩니다. 이 레슨의 핵심 규율은 바로 그 좁은 선을 긋는 것입니다.

## 개념

### 멀티 에이전트 아키텍처

```
          Incident
             │
             ▼
        Supervisor
        /    |    \
       ▼     ▼     ▼
  Log agent  Metric agent  Runbook agent
       │     │     │
       └─────┴─────┘
             │
             ▼
        Hypothesis + evidence
             │
             ▼
        Human approval
             │
             ▼
        Action (narrow set)
```

슈퍼바이저는 인시던트를 하위 쿼리로 쪼갭니다. 전문 에이전트들은 도구 접근 권한(로그 검색, PromQL, 문서 검색)을 갖습니다. 슈퍼바이저는 결과를 종합해 가설 + 근거를 사람에게 제시하고, 사람이 승인하거나 방향을 다시 잡아 줍니다.

### 자동 복구의 범위

**안전(좁은 범위)**: 파드 재시작, 특정 배포 되돌리기, 사전 승인된 한도 안에서의 풀 스케일 조정, 사전 승인된 기능 플래그 켜기.

**안전하지 않음(넓은 범위)**: 서비스 토폴로지 변경, 리소스 한도 수정, 새 코드 배포, IAM 변경, 데이터베이스 변경.

"한 번 설정하면 끝"이라고 파는 곳이 있다면 과장입니다. 안전한 작업 목록은 AI SRE가 성숙해지면서 점점 넓어지겠지만, 그 경계선은 분명히 존재합니다.

### 적대적 평가 (NeuBird Hawkeye)

두 모델이 같은 인시던트를 독립적으로 분석합니다. 근본 원인에 대한 의견이 일치하면 확신도가 높은 것이고, 불일치하면 두 가설을 모두 보여 주면서 사람에게 에스컬레이션합니다. 단순한 패턴이지만 환각으로 만들어진 근본 원인을 걸러 내는 효과적인 필터입니다.

### 운영 지식 (Operational memory)

전통적인 SRE의 잠복 살인자는 팀 인력 이동입니다. 노하우가 사람과 함께 사라지니까요. AI SRE는 런북 + 포스트모템(장애 회고)을 벡터 DB에 저장하고, 에이전트가 새 인시던트가 발생할 때마다 꺼내 봅니다. 새 엔지니어가 합류해도 AI는 전체 이력을 갖고 있습니다.

### 인시던트 사전 예측

MIT 2025년 연구: 과거 로그, GPU 온도, API 오류 패턴으로 학습한 LLM이 테스트셋에서 발생한 장애의 89%를 10~15분 전에 예측했습니다.

현실 점검: 실행이 따라오지 않는 예측은 그저 대시보드입니다. 운영 관점의 질문은 "예측했을 때, 우리가 뭘 할 것인가?"입니다. 미리 트래픽을 다른 곳으로 보낼까(pre-emptive drain)? 호출기를 울릴까? 오토스케일? 답은 정책에 따라 다릅니다.

### 2026년의 제품들

- **Datadog Bits AI** — Datadog 안에 들어 있는 매니지드 SRE 코파일럿.
- **Azure SRE Agent** — Azure 네이티브.
- **NeuBird Hawkeye** — 적대적 평가 + 운영 지식.
- **PagerDuty AIOps** — 트리아지 + 중복 제거.
- **Incident.io Autopilot** — 인시던트 커맨더 + 조율.

### 코드로서의 런북 (Runbooks as code)

런북은 Confluence 페이지에서 구조화된 섹션(증상, 가설, 검증, 조치)을 갖춘 버전 관리되는 마크다운으로 진화하고 있습니다. 구조화된 런북일수록 RAG 검색이 더 잘 됩니다. AI SRE 도입을 시작한다면, 제일 먼저 비구조화된 런북을 구조화된 것으로 바꾸세요.

### 기억해야 할 숫자들

- MIT 조기 감지: 장애의 89%, 10~15분의 선행 시간.
- 멀티 에이전트 트리아지: 슈퍼바이저 + (로그, 메트릭, 런북) + 사람.
- 안전한 자동 복구 목록: 파드 재시작, 배포 되돌리기, 한도 안에서의 스케일 조정.
- 적대적 평가: 두 모델이 독립적으로 분석, 의견 일치 = 확신.

## 연습 문제

1. `code/main.py`를 실행해 보세요. 로그 에이전트와 메트릭 에이전트의 의견이 갈리면 어떻게 될까요? 슈퍼바이저는 이걸 어떻게 조율할까요?
2. 여러분의 서비스를 위한 "안전한" 자동 복구 작업 세 가지를 정의하고, 각각의 근거를 제시하세요.
3. 구조화된 런북 템플릿을 작성해 보세요. 섹션, 필수 입력 항목, 검증 커맨드를 포함합니다.
4. 예측형 감지가 12분의 선행 시간을 확보하고 발동했습니다. 당신의 정책은? 호출기, 미리 트래픽 분산, 아니면 둘 다?
5. 3인 팀이 2026년에 AI SRE를 도입해야 하는지, 아니면 기다려야 하는지 논증해 보세요. 성숙도, 인시던트 발생량, 리스크를 고려하세요.
