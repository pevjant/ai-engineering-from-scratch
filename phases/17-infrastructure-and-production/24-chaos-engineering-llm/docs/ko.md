# LLM 프로덕션을 위한 카오스 엔지니어링

> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [en.md](en.md)

> LLM을 위한 카오스 엔지니어링은 2026년에 하나의 독립된 분야가 되었습니다. 프로덕션(운영 환경)에서 실험을 돌리기 전 필수 조건: 정의된 SLI/SLO, 트레이스+메트릭+로그 관측 가능성, 자동 롤백, 런북, 온콜 체계. 아키텍처는 네 개의 평면으로 이뤄집니다. 제어(실험 스케줄러), 대상(서비스, 인프라, 데이터 저장소), 안전(가드 + 중단 + 트래픽 필터), 관측 가능성(메트릭 + 트레이스 + 로그), 그리고 SLO 조정으로 이어지는 피드백. 가드레일은 필수입니다. 번 레이트(burn-rate) 알림은 일일 에러 예산 소진이 예상치의 2배를 넘으면 실험을 일시 중지합니다. 억제 윈도우(suppression window) + 트레이스-ID 상관관계로 알림 소음을 줄입니다. 주기: 주간 — 소규모 카나리 + SLO 리뷰, 월간 — 게임 데이 + 포스트모템, 분기 — 팀 간 복원력 감사 + 의존성 매핑. LLM 특화 실험: 메모리 과부하, 네트워크 장애, 공급자 장애, 비정상 프롬프트, KV 캐시 축출 폭풍. 도구: Harness Chaos Engineering (LLM 기반 실험 추천, 폭발 반경 축소, MCP 도구 통합), LitmusChaos (CNCF), Chaos Mesh (CNCF, Kubernetes 네이티브).

**유형:** Learn
**언어:** Python (표준 라이브러리, 장난감 수준의 카오스 실험 러너)
**선수 지식:** 페이즈 17 · 23 (AI를 위한 SRE), 페이즈 17 · 13 (관측 가능성)
**시간:** 약 60분

## 학습 목표

- 카오스 엔지니어링의 다섯 가지 필수 조건(SLI/SLO, 관측 가능성, 롤백, 런북, 온콜)을 말하고, 하나라도 빠지면 왜 이 실천이 무너지는지 설명할 수 있습니다.
- 네 개의 평면(제어, 대상, 안전, 관측 가능성)과 SLO로 이어지는 피드백 루프를 그림으로 그릴 수 있습니다.
- LLM 특화 실험 다섯 가지(메모리 과부하, 네트워크 장애, 공급자 장애, 비정상 프롬프트, KV 축출 폭풍)를 나열할 수 있습니다.
- 스택에 맞는 도구를 고를 수 있습니다 — Harness, LitmusChaos, Chaos Mesh.

## 문제 상황

전통적인 스택에서의 카오스 테스트는 이미 정착된 기술입니다. 하지만 LLM 스택은 새로운 고장 모드를 더합니다. 독성 문자 하나가 섞인 4K 토큰짜리 프롬프트가 토크나이저를 12초 동안 멈춰 세웁니다. 업스트림 공급자가 429를 뿜고, 게이트웨이가 재시도하고, 재시도가 몰린 동시성 때문에 서비스가 OOM(메모리 부족)으로 죽습니다. 순간적인 트래픽 폭주 상황에서 KV 캐시 축출 폭풍이 발생하면 재-프리필(re-prefill) 연쇄가 컴퓨팅을 잠식합니다.

이런 문제들은 단위 테스트에는 전혀 잡히지 않습니다. 카오스 엔지니어링은 사용자보다 먼저 이런 문제를 발견하는 방법입니다.

## 개념

### 필수 조건

다음이 갖춰지지 않으면 프로덕션에서 카오스를 돌리지 마세요:

1. **SLI/SLO** — 정의된 서비스 수준 지표와 목표.
2. **관측 가능성** — 트레이스, 메트릭, 로그가 대시보드에 연결되어 있어야 합니다.
3. **자동 롤백** — 페이즈 17 · 20의 정책 플래그 롤백.
4. **런북** — 구조화된 것. 페이즈 17 · 23.
5. **온콜** — 대응해 줄 사람.

하나라도 빠지면 카오스 실험이 실제 인시던트가 됩니다.

### 네 개의 평면 + 피드백

**제어 평면** — 실험 스케줄러(Litmus 워크플로, Chaos Mesh 스케줄, Harness UI).

**대상 평면** — 서비스, 파드, 노드, 로드 밸런서, 데이터 저장소.

**안전 평면** — 킬 스위치, 억제 윈도우, 폭발 반경(blast radius) 한도, 에러 예산 게이트.

**관측 가능성 평면** — 일반 메트릭 + 트레이스-ID 상관관계. 카오스로 인한 장애와 자연 발생 장애를 구분합니다.

**피드백 루프** — 실험 결과가 SLO 조정, 런북 업데이트, 코드 수정으로 이어집니다.

### 가드레일은 필수

- **번 레이트 알림**: 일일 에러 예산 소진이 예상치의 2배를 넘으면 실험을 일시 중지.
- **억제 윈도우**: 실험 중 폭발 반경 안에서 실험과 무관한 알림은 묵음 처리.
- **트레이스-ID 상관관계**: 실험으로 유발된 모든 오류에 태그를 달아 온콜 담당자가 중복 제거할 수 있게 합니다.

### LLM 특화 실험 다섯 가지

1. **메모리 과부하** — 높은 동시성으로 긴 컨텍스트 요청을 보내 KV 캐시 선점(preemption) 폭풍을 강제로 일으킵니다. 관찰할 것: 서비스가 우아하게 부하를 덜어내는지, 아니면 그냥 죽는지?

2. **네트워크 장애** — 추론 게이트웨이와 공급자 사이의 연결을 끊습니다. 관찰할 것: SLA 안에 폴백이 발동하는지? (페이즈 17 · 19)

3. **공급자 장애 시뮬레이션** — OpenAI가 100% 429를 반환하게 만듭니다. 관찰할 것: 라우팅이 Anthropic으로 페일오버하는지? (페이즈 17 · 16, 19)

4. **비정상 프롬프트** — 토크나이저를 멈추게 하는 페이로드(예: 깊게 중첩된 유니코드, 아주 큰 UTF-8 코드포인트)를 주입합니다. 관찰할 것: 요청 하나가 워커 전체를 잠가 버리는지?

5. **KV 축출 폭풍** — vLLM 블록 예산을 포화시켜 축출을 강제합니다. 관찰할 것: LMCache가 복구하는지, 아니면 서비스 성능이 떨어지는지?

### 실행 주기

- **주간** — 스테이징에서 소규모 카나리 실험. 상황에 따라 프로덕션의 5% 정도.
- **월간** — 특정 시나리오로 예약된 게임 데이. 팀 간 참여, 포스트모템 포함.
- **분기** — 팀 간 복원력 감사, 의존성 맵 업데이트.

### 도구

- **Harness Chaos Engineering** — 상용. AI 기반 실험 추천, 폭발 반경 축소, MCP 도구 통합.
- **LitmusChaos** — CNCF 졸업(graduated) 프로젝트. Kubernetes 워크플로 기반.
- **Chaos Mesh** — CNCF 샌드박스. Kubernetes 네이티브 CRD 스타일.
- **Gremlin** — 상용. 폭넓은 지원.
- **AWS FIS** / **Azure Chaos Studio** — 매니지드 클라우드 제품.

### 작게 시작하기

첫 실험: 안정적인 트래픽 상태에서 디코드 레플리카 하나를 pod-kill 합니다. 재라우팅과 복구를 관찰하세요. 이게 잘 되고 안전해 보이면, 네트워크 카오스로 넘어갑니다.

첫 LLM 특화 실험: 공급자 429를 5분 동안 하나 주입합니다. 폴백을 관찰하세요. 대부분의 팀은 이때 자신들의 폴백이 제대로 테스트된 적이 없다는 걸 깨닫습니다.

### 기억해야 할 숫자들

- 네 개의 평면: 제어, 대상, 안전, 관측 가능성.
- 번 레이트 일시 중지 기준: 예상 일일 예산 소진의 2배.
- 주기: 주간 카나리, 월간 게임 데이, 분기 감사.
- LLM 실험 다섯 가지: 메모리, 네트워크, 공급자, 비정상 프롬프트, KV 폭풍.
