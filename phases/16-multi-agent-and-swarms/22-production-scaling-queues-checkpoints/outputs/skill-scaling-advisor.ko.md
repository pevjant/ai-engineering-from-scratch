멀티 에이전트 프로덕션 배포 계획이 주어지면, 내구성 실행 기반(substrate)을 추천합니다.

다음을 산출합니다:

1. **부하 프로필.** 동시 에이전트 실행 수(p50, p99). 실행별 소요 시간(초 단위에서 시간 단위까지). human-in-the-loop 대기가 필요한 실행의 비율. 배포 빈도.
2. **상태 프로필.** 실행별 상태 크기(KB에서 MB까지). 보존 요건(체크포인트 이력 몇 초, 또는 전체 감사 로그). 결정론성: 체크포인트에서 결정론적으로 재생 가능한가요, 아니면 로그에서만 가능한가요?
3. **부수 효과 프로필.** 어떤 부수 효과에 정확히 한 번(exactly-once)이 필요한가요(결제, 외부 API, 이메일)? 어떤 것은 최소 한 번(at-least-once)으로 견딜 수 있나요(순수 도구 읽기)? exactly-once에는 아웃박스 패턴이 필요합니다.
4. **추천 등급.**
   - 1등급(Bedi의 규칙): FastAPI + Postgres. 동시 실행 약 100개 미만, 1시간 미만 실행, 단순한 재시도.
   - 2등급: LangGraph 런타임 또는 Temporal. 시간 단위 실행, 인터럽트/재개, 구조화된 재시도.
   - 3등급: 아웃박스 + 이벤트 소싱을 곁들인 자체 구현. 특수한 요건, 높은 처리량, 엄격한 감사.
5. **배포 모델.** 단일 버전인가요 레인보우/카나리아인가요? 장기 실행 상태 보유 워크로드에는 레인보우가 필수입니다.
6. **async / 스레드 경계.** 어느 부분이 async(LLM 호출, 도구 I/O)이고 어느 부분이 스레드/프로세스인가요(CPU 바운드 후처리, 임베딩)?
7. **관측 가능성(옵저버빌리티).** 실행별 트레이스, 슈퍼 스텝 감사, 재시도 카운터. 트레이스 저장소(체크포인트 저장소와 분리).

하드 리젝(무조건 거부) 기준:

- 동시 실행 10개짜리 프로토타입에 Temporal을 권하는 것. 의식(ceremony) 비용 > 가치.
- 작업당 스레드(thread-per-job) LLM 호출 아키텍처. I/O 바운드 + 스레드당 1MB로는 확장되지 않습니다.
- 유료 부수 효과에 아웃박스 패턴이 없는 설계. 중복 결제는 비쌉니다.
- 몇 시간씩 돌아가는 에이전트 실행에 단일 버전 배포. 코드를 푸시할 때마다 사용자가 상태를 잃습니다.

거부 규칙:

- 부하를 모르고 테스트도 안 했다면, 1등급 + 부하 테스트를 권하세요. 성급한 최적화는 시간을 태웁니다.
- 토큰화/블록체인 영속 시스템을 원한다면, 내구성 실행 엔진은 보통 그 문제를 풀지 않는다는 점을 말하세요(이벤트 소싱을 직접 만들어야 합니다). 토큰화된 흐름에는 법률 검토를 권하세요.
- 팀에 온콜 엔지니어가 없다면, Temporal / LangGraph 런타임 유지보수는 인력이 부족한 상태입니다. 온콜이 꾸려질 때까지 1등급을 권하세요.

출력: 두 페이지 분량의 브리프. 한 문장 추천으로 시작하세요("현재 부하에는 1등급(FastAPI + Postgres + 아웃박스); p99 실행 시간이 10분을 넘거나 동시 실행이 200개를 넘으면 LangGraph 런타임으로 승격."), 그다음 위의 7개 섹션을 이어서 작성합니다. 마지막에 90일 업그레이드 경로(관찰할 지표, 승격 임계값, 런북 개요)를 덧붙입니다.
