# 프로덕션 스케일링 — 큐, 체크포인트, 내구성

> 멀티 에이전트 시스템을 수천 개의 동시 실행 규모로 확장하려면 **내구성 있는 실행(durable execution)** 이 필요합니다 — 작업 큐에 체크포인트를 더하는 방식이죠. 그러면 어떤 워커도, 어떤 크래시 뒤에도 어떤 실행이든 이어받을 수 있습니다. 단, 임대(lease) 처리, 멱등(idempotent)한 부수 효과, 결정론적 재생이 갖춰져 있어야 합니다. LangGraph의 런타임이 대표적인 예입니다: `thread_id`를 키로 슈퍼 스텝(super-step)마다 체크포인트를 기록하고(Postgres 기본값), 워커가 죽으면 임대가 해제되어 다른 워커가 이어받습니다. 에이전트는 사람의 입력을 기다리며 무한히 잠들 수도 있습니다. **MegaAgent**(arXiv:2408.09955)는 에이전트별 생산자-소비자 큐에 세 가지 상태(Idle / Processing / Response)와 두 계층 조율(그룹 내 채팅 + 그룹 간 관리자 채팅)을 사용했습니다. LLM 스트리밍에서는 **파이버/async**가 작업당 스레드 방식을 이깁니다: 스레드는 토큰을 기다리며 99%의 시간을 놀고 있지만, 파이버는 I/O에서 협력적으로 양보합니다. 반론도 있습니다. Ashpreet Bedi의 "Scaling Agentic Software"는 부하가 증명할 때까지는 **FastAPI + Postgres, 그 이상 아무것도 없이** 가자고 주장합니다 — 단순한 아키텍처가 생각보다 훨씬 멀리 간다는 것이죠. 이 레슨에서는 내구성 있는 체크포인트 로그, 상태 전이가 있는 에이전트별 작업 큐, async vs 스레드 데모를 만들며 실용적인 "단순하게 시작하라" 규칙을 몸에 새깁니다.

**유형:** Learn + Build
**언어:** Python (표준 라이브러리, `asyncio`, `sqlite3`)
**선수 지식:** 페이즈 16 · 09 (Parallel Swarm Networks), 페이즈 16 · 13 (Shared Memory)
**시간:** 약 75분

## 문제

프로토타입 멀티 에이전트 시스템은 노트북 한 대에서 에이전트 셋이 인메모리 이벤트 루프로 돌아갑니다. 그런데 프로덕션(운영 환경)으로 넘어가면:

- 에이전트가 몇 시간씩 돌아가기도 합니다(긴 리서치, human-in-the-loop 대기).
- 워커 프로세스가 크래시합니다. 재시작하면 상태가 사라집니다.
- 피크 부하는 평균의 10배입니다. 수평 확장이 필요합니다.
- 사용자가 에이전트 실행 횟수만큼 지불합니다. 과금에는 정확히 한 번(exactly-once) 의미론이 필요합니다.

인메모리 이벤트 루프는 이중 어느 것도 해결하지 못합니다. 밑바닥에 내구성 있는 실행 계층이 필요합니다. 2026년의 대표적인 선택지는 다음과 같습니다:

1. 체크포인트가 있는 워크플로 엔진(Temporal, LangGraph 런타임).
2. 상태 저장소를 곁들인 메시지 큐(Postgres + SQS/RabbitMQ).
3. 액터 모델 프레임워크(MegaAgent의 에이전트별 생산자-소비자).
4. 손수 만드는 FastAPI + Postgres(Bedi의 주장).

이 레슨에서는 각각의 미니어처 버전을 만들어 봅니다.

## 개념

### 내구성 있는 실행, 그 패턴

내구성 실행 엔진은 각 "스텝"(LangGraph 용어로 슈퍼 스텝) 뒤에 프로그램 상태 전체를 저장합니다. 크래시가 나면:

```
worker crashes mid-step
  -> lease timeout
  -> another worker picks up the thread_id
  -> resumes from last checkpoint
  -> no duplicate side effects
```

이것이 작동하려면 다음이 필요합니다:

- **직렬화 가능한 상태.** 모든 에이전트 상태는 저장 가능해야 합니다. 살아 있는 데이터베이스 연결을 품은 함수 클로저는 살아남지 못합니다.
- **결정론적 재개.** 같은 상태와 같은 입력이 주어지면 에이전트는 같은 행동을 만들어야 합니다(또는 LLM 호출은 외부의 결정론적 오라클에 맡깁니다).
- **멱등한 부수 효과.** 외부 호출(도구 호출, 결제)은 멱등이거나 중복 제거 키를 사용해야 합니다.

LangGraph는 슈퍼 스텝마다 체크포인트를 기록하고, Temporal은 액티비티마다 기록하며, Restate는 이벤트 소싱 저널을 씁니다. 세 가지 모두 같은 패턴을 구현합니다.

### 스텝마다 체크포인트를 남기는 런타임

LangGraph의 런타임이 상세한 예입니다: 각 에이전트는 `thread_id`를 갖고, 상태는 타입이 지정된 딕셔너리이며, 슈퍼 스텝마다 체크포인트 테이블에 한 행을 기록합니다. 재개할 때 런타임은 처음부터가 아니라 마지막 체크포인트부터 재생합니다. 에이전트는 사람의 입력을 기다리며 `interrupt()`할 수 있고, 런타임은 상태를 저장하고 워커를 반납합니다. 입력이 도착하면 어떤 워커든 이어서 실행할 수 있습니다.

2026년 4월 기준의 참조용 프로덕션 설계가 바로 이것입니다.

### MegaAgent의 에이전트별 큐

arXiv:2408.09955는 규모 실험을 기술합니다: 하나의 클러스터에서 수천 개의 동시 에이전트. 아키텍처:

```
agent i:
  state ∈ {Idle, Processing, Response}
  in_queue   <- messages addressed to agent i
  out_queue  -> replies + side effects

coordinators:
  intra-group chat  (agents in the same group)
  inter-group admin chat  (high-level routing)
```

두 계층 조율 덕분에 그룹 내 대화는 촘촘하게 일어나고 그룹 간 통신은 성기게 유지됩니다 — 수천 개 에이전트에서 비용을 선형으로 유지하는 패턴입니다.

### Async vs 작업당 스레드

LLM 호출은 I/O 바운드입니다. 다음 토큰을 기다리는 스레드는 99%의 시간을 놀고 있습니다. 스레드는 개당 약 1MB의 RAM을 씁니다. 동시 호출 10,000개면 스택만으로 10GB입니다.

파이버(Python `asyncio`, Go 고루틴, Rust `tokio`)는 I/O에서 협력적으로 양보합니다. 같은 10,000개 호출이 프로세스 하나 안에 여유 있게 들어갑니다. LLM 에이전트 규모에서 async는 최적화 기법이 아니라 아키텍처 그 자체입니다.

예외: CPU 바운드 후처리(임베딩, 토크나이저 트릭)는 여전히 스레드나 프로세스를 원합니다. I/O 계층과 CPU 계층을 분리하세요.

### Bedi의 반론

"Scaling Agentic Software"(Ashpreet Bedi, 2026)는 대부분의 팀이 부하를 측정하기도 전에 과하게 설계한다고 주장합니다. 실용적인 기본값:

- FastAPI + Postgres.
- 각 에이전트 실행은 한 행(row); 상태는 낙관적 동시성 제어로 제자리에서 갱신.
- `pg_notify`나 간단한 Celery 워커로 백그라운드 작업 처리.
- 재시도 정책은 애플리케이션 코드에.

감당 가능한 태스크에서 동시 에이전트 실행이 약 100개 미만인 부하라면, 이것만으로 충분한 경우가 많습니다. 측정해서 실패하는 것이 확인되면 업그레이드하세요.

규칙: 단순한 아키텍처가 해결하지 못하는 구체적인 문제에 부딪혔을 때 내구성 실행 프레임워크를 도입하세요. 성급한 도입은 보상받지 못하는 의식(ceremony)에 시간을 태웁니다.

### 정확히 한 번(exactly-once) 의미론

유료 에이전트 실행에는 "정확히 한 번 실행되는 효과"(최소 한 번 전달 + 멱등 소비자)가 필요합니다. 엔지니어링 기법:

- **실행당 중복 제거 키.** 모든 부수 효과 호출에 포함시키세요.
- **아웃박스(outbox) 패턴.** 부수 효과는 먼저 테이블에 기록하고, 별도의 프로세스가 실행합니다. 두 단계 모두 멱등합니다.
- **보상 트랜잭션.** 부수 효과는 성공했는데 그 추적 기록이 실패하면, 보상(compensate)을 예약합니다.

이것들은 LLM 고유가 아니라 데이터베이스 엔지니어링 패턴입니다. LLM 세금이라는 건 LLM 호출이 느리다는 것뿐이고, 나머지는 표준 분산 시스템 이야기입니다.

### 레인보우 배포

Anthropic의 멀티 에이전트 리서치 시스템은 "레인보우 배포"를 씁니다: 에이전트 런타임의 여러 버전이 동시에 실행되어, 코드를 배포할 때마다 장기 실행 에이전트를 죽일 필요가 없습니다. 트래픽 일부에 새 버전을 카나리아로 띄우고, 오래된 버전은 그 에이전트들이 끝나면 은퇴시킵니다.

장기 실행 상태 보유 시스템에서는 표준적인 방식입니다. 2026년의 변형은 에이전트가 몇 시간씩 살아 있을 수 있으므로 배포 주기도 이를 수용해야 한다는 점입니다.

### 대표적인 프로덕션 체크리스트

- 내구성 있는 상태(체크포인트, 스냅샷, 또는 아웃박스 + 재생 가능한 로그).
- 멱등한 부수 효과.
- LLM 호출을 위한 비동기 I/O 계층.
- 중복 제거를 곁들인 최소 한 번 전달.
- 상태 보유 워크로드를 위한 레인보우/카나리아 배포.
- 관측 가능성(옵저버빌리티): 에이전트별 트레이스, 슈퍼 스텝 감사, 재시도 카운터.

## 직접 만들기

`code/main.py`는 다음을 구현합니다:

- `CheckpointStore` — thread-id 키를 쓰는 SQLite 기반 체크포인트 로그. 슈퍼 스텝마다 한 행을 추가합니다.
- `run_with_checkpoint(agent, thread_id)` — 실행 도중 크래시를 시뮬레이션합니다. 두 번째 워커가 마지막 체크포인트부터 재개합니다.
- `AgentQueue` — 작은 작업 큐를 곁들인 에이전트별 Idle / Processing / Response 상태 기계.
- `demo_async_vs_threads()` — asyncio 방식과 스레드 방식으로 동시 시뮬레이션 "LLM 호출" 500개를 실행합니다. 실제 걸린 시간과 (근사한) 피크 메모리를 보고합니다.

실행:

```
python3 code/main.py
```

예상 출력: 시뮬레이션된 크래시 후 체크포인트 재개가 성공합니다. async 버전은 1초 안에 500개 동시 호출을 처리하고, 스레드 버전은 몇 초가 걸리며 동시 실행 단위당 메모리를 몇 자릿수 더 씁니다.

## 출시하기

대표적인 프로덕션 강화 항목:

- **단순하게 시작하세요(Bedi의 규칙).** 측정상 실패가 확인될 때까지는 FastAPI + Postgres.
- **최적화하기 전에 모든 것을 계측하세요.** 실행별 지연 시간 히스토그램, 스텝별 시간, 재시도 횟수, 실패 분류.
- **부수 효과에는 아웃박스 패턴.** 특히 결제와 외부 API 호출.
- **레인보우 배포.** 배포 중에 실행 중인 에이전트를 절대 죽이지 마세요.
- **내구성 실행 엔진(Temporal / LangGraph / Restate)을 도입할 시점은** 구체적인 문제에 부딪혔을 때입니다: 몇 시간짜리 human-in-the-loop 대기, 지역 간 조율, 복잡한 재시도/보상 정책.
- **I/O 계층에는 async.** 스레드는 CPU 바운드 후처리에만.

## 연습 문제

1. `code/main.py`를 실행하세요. 체크포인트 재개가 작동하는지 확인하고, async와 스레드의 동시성 차이를 측정하세요.
2. **아웃박스** 테이블을 구현하세요: 모든 도구 호출은 먼저 아웃박스에 기록하고, 별도의 고루틴/태스크가 실행합니다. 도구 호출을 두 번 실행해서 멱등성을 검증하세요.
3. **레인보우 배포**를 시뮬레이션하세요: 두 개의 런타임 버전이 동시에 실행되고, 새 thread_id의 절반씩을 각각에 라우팅합니다. 구버전에서 실행 중인 스레드가 중단되지 않는지 확인하세요.
4. LangGraph 런타임 문서(아래 링크)를 읽으세요. 손수 만든 FastAPI + Postgres 버전에서 재현하는 데 가장 오래 걸릴 런타임 기능이 무엇인지 찾으세요. 그것이 도입할 이유가 되나요, 아니면 미룰 수 있나요?
5. MegaAgent(arXiv:2408.09955) 3절을 읽으세요. 두 계층 조율(그룹 내 + 그룹 간 관리자 채팅)이 명시적으로 드러납니다. 이것을 큐 패밀리 두 개를 가진 메시지 큐로 옮긴다면 어떻게 될지 스케치해 보세요.

| 레인보우 배포 | "겹치는 버전들" | 장기 실행 워크로드 동안 여러 런타임 버전이 동시에 존재. |
| 비동기 파이버 | "협력적 양보" | 사용자 모드 동시성; I/O 바운드 부하에서 스레드보다 저렴. |
| 체크포인트 | "상태 스냅샷" | 슈퍼 스텝 경계에서 직렬화된 상태; 재개의 열쇠. |
