# 슈퍼바이저 / 오케스트레이터-워커 패턴

> 리드 에이전트 하나가 계획하고 위임하고, 전문화된 워커들이 각자의 병렬 컨텍스트에서 실행한 뒤 결과를 보고합니다. Anthropic의 Research 시스템(Claude Opus 4가 리드, Sonnet 4가 서브에이전트) 뒤에 있는 패턴으로, 내부 리서치 평가에서 단일 에이전트 Opus 4 대비 +90.2%를 기록했습니다. Anthropic의 엔지니어링 글은 BrowseComp 변동의 80%가 토큰 사용량 하나만으로 설명된다고 보고합니다 — 멀티 에이전트가 이기는 건 대체로 각 서브에이전트가 새 컨텍스트 윈도우를 받기 때문입니다. 이 레슨에서는 프리미티브로부터 슈퍼바이저 패턴을 만들고, 프로덕션(운영 환경) 배포에서 나온 2026년 엔지니어링 교훈을 다룹니다.

**유형:** 학습 + 빌드
**언어:** Python (표준 라이브러리, `threading`)
**선수 지식:** 페이즈 16 · 04(프리미티브 모델)
**시간:** 약 75분

## 문제

리서치는 단일 에이전트 시스템이 실패하는 전형적인 작업입니다. "2023년과 2026년 사이에 멀티 에이전트 시스템에서 뭐가 바뀌었어?"라고 물어봅시다. 단일 에이전트는 논문 다섯 편을 순서대로 읽고, 그 텍스트로 컨텍스트 절반을 채운 다음, 이 모두를 한데 모아 추론해야 합니다. 다섯 번째 논문에 도달할 때쯤이면 첫 번째 논문을 잊어버렸죠. 병렬화도 못 합니다.

슈퍼바이저 패턴은 이걸 고칩니다: 리드 에이전트 하나가 검색을 계획하고, 서브 질문 하나하나를 워커에게 위임하고, 종합합니다. 각 워커는 좁은 질문 하나를 위해 자기만의 200k 토큰 윈도우를 받습니다. 리드는 원본 논문을 절대 보지 않습니다 — 워커 요약만 보죠.

Anthropic의 프로덕션 Research 시스템은 내부 리서치 평가에서 단일 Opus 4 대비 +90.2%를 보고했습니다. 같은 글은 BrowseComp 변동의 80%가 *토큰 사용량 하나만으로* 설명된다고 짚습니다. 서브에이전트마다 새 컨텍스트를 주는 것이 핵심 메커니즘입니다.

## 개념

### 패턴의 모습

```
                 ┌──────────────┐
                 │   Lead       │  plans, decomposes,
                 │  (Opus 4)    │  synthesizes
                 └──┬────┬───┬──┘
                    │    │   │
            ┌───────┘    │   └───────┐
            ▼            ▼           ▼
      ┌─────────┐  ┌─────────┐  ┌─────────┐
      │ Worker1 │  │ Worker2 │  │ Worker3 │
      │(Sonnet) │  │(Sonnet) │  │(Sonnet) │
      └─────────┘  └─────────┘  └─────────┘
         fresh       fresh        fresh
         context     context      context
```

리드는 원본 자료를 읽지 않습니다. 워커들은 리드가 종합하기 전까지 서로의 작업을 보지 못합니다. 각 화살표는 좁은 아티팩트 하나를 실은 핸드오프입니다.

### 왜 이기는가

세 가지 메커니즘입니다:

1. **서브에이전트마다 새 컨텍스트.** "FIPA-ACL 계보"를 탐색하는 워커는 리드가 계획하느라 쓴 40k 토큰을 짊어지지 않습니다. 질문 하나에 200k 윈도우를 통째로 받습니다.
2. **프롬프트를 통한 전문화.** 리드의 프롬프트는 "리서치해라"가 아니라 "분해하고 종합해라"입니다. 각 워커의 프롬프트는 좁습니다: "X에서 뭐가 바뀌었는지 찾아라." 좁은 프롬프트가 좁은(정확히 맞춰진) 출력을 만듭니다.
3. **병렬성.** 워커들이 동시에 돕니다. 실제 걸리는 시간은 대략 `max(worker_times) + plan + synthesis`이지, `sum(worker_times)`가 아닙니다.

### 엔지니어링 교훈 (Anthropic 2025)

Anthropic 글이 나열한 프로덕션 교훈 몇 가지는 2026년에도 유효합니다:

- **쿼리 복잡도에 맞춰 노력의 규모를 조정.** 단순 쿼리: 에이전트 하나, 도구 호출 3~10회. 복잡한 쿼리: 에이전트 10개 이상. 이걸 추정하는 건 호출자가 아니라 리드여야 합니다.
- **넓게 시작해 좁히기.** 먼저 넓은 서브 질문들로 분해하고, 답이 더 깊은 탐구를 요구하면 서브 질문당 워커를 더 띄웁니다.
- **레인보우 배포(rainbow deployment).** 에이전트는 오래 살아 있고 상태를 가집니다. 전통적인 블루-그린 배포는 안 됩니다. Anthropic은 레인보우 방식을 씁니다: 기존 버전이 물러나는 동안 새 버전을 점진적으로 롤아웃하는 거죠.
- **토큰 사용량이 지배한다.** 멀티 에이전트는 단일 에이전트의 약 15배 토큰을 씁니다. 작업 가치가 비용을 정당화할 때만 돌리세요.

### 그래프 네이티브로의 전환

LangGraph는 처음에 고수준 `create_supervisor` 헬퍼를 갖춘 `langgraph-supervisor` 라이브러리를 내놓았습니다. 2025년 LangChain은 권장안을 도구 호출(tool-calling)로 슈퍼바이저 패턴을 직접 구현하는 쪽으로 옮겼습니다. 도구 호출이 *슈퍼바이저가 무엇을 보는지*에 대한 더 많은 제어(컨텍스트 엔지니어링)를 주기 때문입니다. 라이브러리는 여전히 동작하며, 문서는 이제 도구 호출 방식을 권장합니다.

### 실패 양상

- **리드가 계획을 환각함.** 리드가 실제 질문을 분해하지 않는 서브 질문을 만들어 내면, 워커들은 잘못된 표적 위에서 정확한 리서치를 합니다.
- **워커가 과탐색함.** 명시적인 범위 경계가 없으면 워커들이 맡은 서브 질문을 넘어 표류하고 종합 단계를 오염시킵니다.
- **종합 충돌.** 두 워커가 상충하는 사실을 반환합니다. 리드는 다시 물어보거나(라운드 추가) 불일치를 명시적으로 표시해야 합니다. 한쪽을 조용히 고르는 게 최악의 실패입니다: 불일치가 있었다는 사실 자체를 사용자는 평생 모르게 되니까요.

### 슈퍼바이저가 틀린 선택일 때

- **순차 작업.** 2단계가 말 그대로 1단계의 출력을 필요로 한다면, 병렬화는 아무것도 사다 주지 못합니다. 파이프라인을 쓰세요(CrewAI Sequential, LangGraph 선형 그래프).
- **단순 쿼리.** 단일 에이전트가 더 빠르고 저렴하게 처리합니다. 워커를 띄우기 전에 리드의 "노력 규모 조정" 체크를 쓰세요.
- **엄격한 결정성.** 슈퍼바이저는 LLM 선택 위임을 씁니다. 감사/리플레이가 적응성보다 중요하다면 정적 그래프가 낫습니다.

## 만들기

`code/main.py`는 `threading`으로 병렬 워커 세 개짜리 슈퍼바이저를 구현합니다. 리드가 쿼리를 서브 질문으로 분해하고, 워커들이 각 서브 질문을 동시에 처리하고, 리드가 종합합니다. 진짜 LLM은 없습니다 — 워커들은 가져와서 요약하는 동작을 시뮬레이션하도록 스크립트로 짜여 있습니다.

핵심 구조:

- `Lead.plan(query)`가 쿼리를 서브 질문 3개로 쪼갭니다.
- `Worker.run(sub_q)`가 가짜 요약을 반환합니다(프로덕션에서는 도구를 쓰는 어떤 에이전트든 될 수 있습니다).
- `Lead.run(query)`가 워커를 스레드로 띄우고, 조인하고, 종합합니다.

실행:

```
python3 code/main.py
```

출력에는 계획, 시작/종료 타임스탬프가 찍힌 병렬 워커 트레이스, 최종 종합이 나타납니다. 실제 걸리는 시간의 이득을 눈으로 볼 수 있습니다: 0.3초짜리 워커 셋이 0.9초가 아니라 약 0.35초에 끝납니다.

## 사용하기

`outputs/skill-supervisor-designer.md`는 사용자 쿼리를 받아 슈퍼바이저 패턴 설계를 만들어 냅니다: 리드 시스템 프롬프트, 워커 역할, 서브 질문 분해 규칙, 종합 템플릿이죠. 새 리서치 스타일 에이전트 시스템을 만들기 전에 이걸 사용하세요.

## 출시하기

슈퍼바이저 패턴을 배포하기 전 체크리스트:

- **모델 페어링.** 리드는 추론 등급 모델(Opus급, `o3`급)에. 워커는 더 빠르고 싼 모델(Sonnet, `o4-mini`)에.
- **워커 타임아웃.** 중간값(median) 실행 시간의 2배를 넘긴 워커는 죽입니다; 리드는 더 좁은 범위로 다시 띄우거나 그 워커 없이 진행합니다.
- **워커당 토큰 한도.** 하드 리밋(예: 예상 종합 입력의 10배)이 폭주하는 워커가 예산을 태워 버리는 걸 막습니다.
- **관측 가능성(옵저버빌리티).** 리드의 계획, 각 워커의 도구 호출, 종합을 추적하세요. 사후 디버깅의 기반입니다.
- **레인보우 롤아웃.** 상태를 가진 오래 살아 있는 에이전트는 핫 스왑이 아니라 점진적 버전 전환이 필요합니다.

## 연습 문제

1. `code/main.py`를 실행한 다음, 리드가 워커 3개 대신 5개를 띄우도록 고쳐 보세요. 실제 걸리는 시간의 변화를 관찰하세요. 이 데모에서 워커 수가 몇 개일 때 띄우는 오버헤드가 병렬 이득을 넘어서나요?
2. 워커 타임아웃을 구현해 보세요: 0.5초보다 오래 도는 워커는 죽이고, 리드는 남은 결과로 종합합니다. 워커가 잘렸다는 걸 알려면 어떤 관측 가능성이 필요할까요?
3. 리드의 종합에 충돌 감지 단계를 추가해 보세요: 두 워커가 상충하는 답을 반환하면, 리드는 한쪽을 고르는 대신 불일치를 표시합니다. LLM을 호출하지 않고 모순을 어떻게 감지할 수 있을까요?
4. Anthropic의 Research 시스템 엔지니어링 글을 읽어 보세요. 이 장난감 데모가 프로덕션에서 돌아가려면 채택해야 할 실천 세 가지를 목록으로 만드세요.
5. LangGraph의 `create_supervisor`(레거시)와 새로운 도구 호출 권장안을 비교해 보세요. 슈퍼바이저가 무엇을 보는지에 대한 제어는 어느 쪽이 더 좋나요? Anthropic이 종합 단계에 워커의 원본 컨텍스트가 아니라 서브 답변만 명시적으로 넘기는 이유는 무엇일까요?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| Supervisor | "리드 에이전트" | 계획하고, 위임하고, 종합하는 오케스트레이터 에이전트. 자기가 직접 일을 하지는 않습니다. |
| Worker | "서브에이전트" | 슈퍼바이저가 좁은 범위와 자기만의 컨텍스트 윈도우를 주며 호출하는 집중된 에이전트. |
| Orchestrator-worker | "슈퍼바이저 패턴" | 같은 것, 다른 이름. 2026년 문헌은 둘 다 씁니다. |
| Fresh context | "깨끗한 윈도우" | 워커의 컨텍스트는 리드의 히스토리가 아니라 자기 시스템 프롬프트와 맡은 질문에서 시작합니다. |
| Rainbow deployment | "점진적 롤아웃" | 오래 살아 있는 상태 저장 에이전트는 블루-그린이 아니라 버저닝된 드레인 후 교체가 필요합니다. |
| Token dominance | "컨텍스트가 변수다" | Anthropic에 따르면 리서치 평가 변동의 80%는 모델 선택이 아니라 쓴 총 토큰에서 옵니다. |
| Scale effort | "복잡도에 맞춰 에이전트 수 조정" | 리드가 쿼리 난이도를 추정해서 워커 1개 vs 10개 이상을 골라 띄웁니다. |
| Synthesis conflict | "워커들이 의견이 다름" | 두 워커가 상충하는 사실을 반환; 리드는 조용히 한쪽을 고르는 게 아니라 불일치를 표면화해야 합니다. |
