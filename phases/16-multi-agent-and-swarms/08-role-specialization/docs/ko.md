# 역할 전문화 — 플래너, 크리틱, 실행자, 검증자

> 2026년 가장 흔한 멀티 에이전트 분해: 계획하는 에이전트 하나, 실행하는 에이전트 하나, 비판하거나 검증하는 에이전트 하나. MetaGPT(arXiv:2308.00352)는 이걸 역할 프롬프트에 인코딩된 SOP(표준 운영 절차)로 형식화합니다 — 제품 관리자, 아키텍트, 프로젝트 관리자, 엔지니어, QA 엔지니어 — `Code = SOP(Team)` 공식을 따르죠. ChatDev(arXiv:2307.07924)는 디자이너, 프로그래머, 리뷰어, 테스터를 "채팅 체인"과 "커뮤니케이티브 디할루시네이션(communicative dehallucination, 에이전트가 빠진 세부사항을 명시적으로 요청)"으로 연결합니다. 검증자가 하중을 지탱하는 기둥입니다: Cemri et al.(MAST, arXiv:2503.13657)은 모든 멀티 에이전트 실패가 빠졌거나 깨진 검증으로 추적된다는 걸 보였습니다. PwC는 CrewAI에서 구조화된 검증 루프로 정확도가 7배(10% → 70%) 올랐다고 보고했습니다.

**유형:** 학습 + 빌드
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 16 · 04(프리미티브 모델), 페이즈 16 · 05(슈퍼바이저)
**시간:** 약 60분

## 문제

범용적인 멀티 에이전트 시스템은 범용적인 출력을 만듭니다. 그룹 채팅의 코더 셋이 그럭저럭 같은 코드의 세 가지 맛을 씁니다. 에이전트를 더 붙이고, 라운드를 더 늘려도, 여전히 품질 문턱을 넘지 못합니다.

해법은 에이전트를 더 많이 두는 게 아니라 *다른* 에이전트를 두는 겁니다. 뚜렷이 구분되는 역할을 배정하세요. 크리틱에게는 플래너가 없는 도구를 주고, 검증자에게는 객관적인 테스트 스위트를 주세요. 이제 시스템은 나란히 찍기만 하는 게 아니라, 근거 있는 교정을 갖춘 내부 불일치를 갖게 됩니다.

## 개념

### 네 가지 정석 역할

**플래너(Planner).** 목표를 읽고 단계 목록이나 스펙을 만듭니다. 도구: 지식 검색, 문서. 출력: 구조화된 계획.

**실행자(Executor).** 계획 단계를 한 번에 하나씩 읽고 산출물을 만듭니다. 도구: 실제 작업 도구(코드 컴파일러, 셸, API 클라이언트). 출력: 산출물.

**크리틱(Critic).** 실행자의 출력을 플래너의 의도에 비추어 읽습니다. 도구: 산출물에 대한 읽기 전용 접근, 정적 분석. 출력: 사유와 함께 수용/거부.

**검증자(Verifier).** 산출물을 읽고 결정적인 검사를 돌립니다. 도구: 테스트 러너, 타입 체커, 스키마 검증기. 출력: 증거와 함께 통과/실패.

크리틱은 주관적이고, 소신이 뚜렷하고, 주로 LLM 기반입니다. 검증자는 객관적이고, 결정적이며, 주로 코드 기반입니다. 이 둘은 같은 역할이 아닙니다.

### MetaGPT의 SOP 패턴

MetaGPT(arXiv:2308.00352)는 소프트웨어 엔지니어링 SOP를 역할 프롬프트로 인코딩합니다:

- **제품 관리자(Product Manager)**가 PRD를 씁니다.
- **아키텍트(Architect)**가 시스템 설계를 만듭니다.
- **프로젝트 관리자(Project Manager)**가 태스크를 쪼갭니다.
- **엔지니어(Engineer)**가 구현합니다.
- **QA 엔지니어(QA Engineer)**가 테스트를 돌립니다.

각 역할에는 엄격한 입력/출력 스키마가 있습니다. 역할 프롬프트는 그 역할이 *무엇인지*와 *무엇을 반드시 만들어야 하는지*를 말합니다. `Code = SOP(Team)` 공식 — 결정적인 SOP가 LLM 팀을 예측 가능한 파이프라인으로 바꿉니다.

### ChatDev의 커뮤니티케이티브 디할루시네이션

ChatDev는 핵심 동작 하나를 더합니다: 실행자가 계획에 없던 구체적인 세부사항이 필요하면, 계속 진행하기 전에 디자이너에게 명시적으로 묻습니다. 그럴듯하게 세부사항을 지어내는 전형적인 LLM 실패를 막는 거죠.

구현: 역할 프롬프트에 "주어지지 않은 구체적인 정보가 필요하면, 출력을 만들기 전에 해당 역할의 이름을 부르며 물어라"를 포함합니다.

### 왜 검증자가 가장 중요한가

Cemri et al.(MAST)은 멀티 에이전트 실행 실패 1642건을 추적했습니다. 21.3%가 검증 공백이었습니다 — 아무도 확인하지 않은 답이 그대로 나간 거죠. 나머지 79%도 종종 "조용히 실패했거나 아예 안 돌린 검사가 있었다"로 거슬러 올라갑니다. 검증이 하중을 지탱하는 역할입니다.

PwC는 (CrewAI 배포, 2025) 구조화된 검증 루프를 더했더니 정확도가 10%에서 70%로 움직였다고 보고했습니다. 역할 하나로 7배의 이득입니다.

### 크리틱 vs 검증자

- 크리틱은 산출물의 품질을 검토하는 LLM입니다. 주관적입니다. 그럴듯한 문장에 속을 수 있습니다.
- 검증자는 산출물 위에서 돌아가는 결정적인 프로그램입니다. 객관적입니다. 증거와 함께 통과/실패를 알려 줍니다.

둘 다 쓰세요. 크리틱은 검증자가 말로 표현할 수 없는 취향 문제를 잡습니다. 검증자는 런타임에만 드러나서 크리틱 눈에 보이지 않는 버그를 잡습니다.

### 안티패턴

시스템의 모든 역할이 LLM이고 모든 역할의 출력이 "저는 괜찮아 보이는데요"일 때가 바로 그거입니다. 전형적인 MAST 실패 모드죠. 통과/실패를 LLM이 아니라 코드가 결정하는 검증자를 최소 하나는 두세요.

### 프레임워크 매핑

- **CrewAI** — `Agent(role, goal, backstory)`가 교과서적인 전문화 지점입니다.
- **LangGraph** — 노드마다 전문화된 프롬프트를 줄 수 있고, 엣지가 파이프라인을 강제합니다.
- **AutoGen** — GroupChat 안에서 한 단어 이름을 가진 역할별 ConversableAgent.
- **OpenAI Agents SDK** — 역할 전문화된 Agent들 사이의 핸드오프 도구.

## 만들기

`code/main.py`는 간단한 파이썬 함수를 만드는 4역할 파이프라인을 구현합니다:

- **플래너**가 스펙을 만듭니다.
- **실행자**가 코드 문자열을 생성합니다.
- **크리틱**(LLM 시뮬레이션)이 뻔한 문제를 표시합니다.
- **검증자**가 생성된 코드를 샌드박스(`exec`)에서 테스트 케이스로 돌립니다.

데모는 두 번 돕니다: 실행자가 올바른 코드를 만드는 경우(크리틱과 검증자 모두 통과), 실행자가 스펙에서 벗어난 코드를 만드는 경우(그럴듯해 보여서 크리틱이 버그를 놓치지만, 테스트가 실패해서 검증자가 잡습니다).

실행:

```
python3 code/main.py
```

## 사용하기

`outputs/skill-role-designer.md`는 과제를 받아 역할 명부(3~5개 역할), 역할별 입력/출력 스키마, 검증자 검사를 만들어 냅니다. 에이전트를 프레임워크에 연결하기 전에 이걸 사용하세요.

## 출시하기

체크리스트:

- **결정적인 검증자 최소 하나.** 전부 LLM인 건 절대 금물.
- **역할마다 명시적인 입출력 스키마.** 플래너는 산문이 아니라 스펙을 반환하고; 실행자는 그 스키마를 읽습니다.
- **커뮤니케이티브 디할루시네이션.** 정보가 빠졌으면 실행자는 플래너에게 물어야 합니다; 절대 지어내지 않습니다.
- **크리틱/검증자 순서.** 크리틱 먼저(싸고, 설계 문제를 잡음), 검증자 다음(느리고, 버그를 잡음).
- **루프 예산.** 사람에게 넘기기 전 크리틱-실행자 수정 라운드는 최대 2회.

## 연습 문제

1. `code/main.py`를 실행하고 검증자가 크리틱이 놓친 버그를 어떻게 잡는지 관찰하세요. 정적 분석 검사(`return` 개수 세기)를 추가 검증자로 붙여 보세요. 런타임 테스트가 놓치는 것 중 무엇을 잡나요?
2. 다섯 번째 역할을 추가해 보세요: 사용자의 소원을 플래너가 쓸 수 있는 스펙으로 번역하는 "요구사항 분석가". 어떤 커뮤니티케이티브 디할루시네이션 요청이 이 역할로 올라와야 할까요?
3. MetaGPT 3장("Agents")을 읽어 보세요. MetaGPT의 5개 역할 각각의 입력/출력 스키마를 목록으로 만드세요.
4. ChatDev의 채팅 체인 다이어그램(arXiv:2307.07924 Figure 3)을 읽어 보세요. 커뮤니티케이티브 디할루시네이션이 그렇지 않으면 무한히 계속됐을 루프를 끊는 지점을 찾으세요.
5. PwC의 7배 정확도 이득은 검증 루프에서 왔습니다. 검증자를 더해도 도움이 되지 않을 과제 세 가지를 가설로 세워 보세요 — 정확성의 결정적 검사가 불가능하거나 비용이 감당 못 할 만큼 비싼 경우입니다.

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| Role specialization | "에이전트마다 일이 다름" | 플래너/실행자/크리틱/검증자 역할에 맞춰 조율된 서로 다른 시스템 프롬프트. |
| SOP pattern | "인코딩된 표준 운영 절차" | MetaGPT의 틀: 역할마다 엄격한 입출력 스키마가 팀을 파이프라인으로 바꿈. |
| Communicative dehallucination | "지어내기 전에 물어라" | ChatDev 패턴: 세부사항이 빠졌으면 실행자가 만들어내는 대신 플래너에게 물음. |
| Critic | "LLM 리뷰어" | 주관적이고 소신 있는 리뷰어. 취향 문제를 잡습니다. 그럴듯한 문장에 속을 수 있음. |
| Verifier | "결정적 검사" | 코드 기반 통과/실패. 테스트 러너, 타입 체커, 스키마 검증기. 속일 수 없음. |
| Verification gap | "아무도 확인 안 함" | MAST 실패의 21.3%. 그 버그를 잡았을 검사 없이 답이 나감. |
| Revision loop | "크리틱이 되돌려 보냄" | 크리틱의 거부가 피드백과 함께 실행자 재실행을 촉발. 예산이 필요합니다. |
| All-LLM anti-pattern | "저는 괜찮아 보이는데요" | 모든 역할이 LLM이고 결정적 검사가 없음. 전형적인 MAST 실패. |
