# 계층형 아키텍처와 그 실패 양상

> 계층형(hierarchical)은 슈퍼바이저를 겹쳐 놓은 것입니다. 워커들 위에 서브 매니저, 그 위에 매니저 에이전트가 얹힙니다. CrewAI의 `Process.hierarchical`이 교과서 버전입니다: `manager_llm`이 태스크를 동적으로 위임하고 출력을 검증합니다. LangGraph식 동등물은 `create_supervisor(create_supervisor(...))`입니다. 과제가 실제 조직도 형태일 때 자연스러운 패턴이죠. 동시에 매니저 루핑으로 무너지기 가장 쉬운 패턴이기도 합니다 — 매니저 에이전트가 일을 엉뚱하게 배정하거나, 서브 출력을 잘못 해석하거나, 합의에 이르지 못합니다. 순차(sequential) 방식이 이걸 이기는 경우가 잦습니다.

**유형:** 학습 + 빌드
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 16 · 05(슈퍼바이저 패턴)
**시간:** 약 60분

## 문제

슈퍼바이저 패턴이 머리에 들어오면, 자연스러운 다음 질문은 "워커가 곧 슈퍼바이저라면 어떨까?"입니다. 팀 안에 서브팀이 있고, 회사 안에 부서들의 부서가 있죠. 계층형 아키텍처는 그걸 그대로 반영합니다.

문제는: LLM 매니저는 인간 매니저와 다릅니다. 인간 매니저는 자기 부하들이 무엇을 아는지에 대한 안정적인 선지식을 갖고 있습니다. LLM 매니저는 매 턴마다 컨텍스트에 담긴 것만으로 조직을 새로 추론합니다. 그 컨텍스트에 아주 작은 표류가 생기면, 트리 전체가 일을 잘못 배분합니다.

## 개념

### 모양새

```
                 Manager
                 ┌─────┐
                 └──┬──┘
           ┌────────┴────────┐
           ▼                 ▼
       Sub-Mgr A         Sub-Mgr B
       ┌─────┐           ┌─────┐
       └──┬──┘           └──┬──┘
         ┌┴──┬──┐          ┌┴──┐
         ▼   ▼  ▼          ▼   ▼
       W1  W2  W3         W4  W5
```

내부 노드는 전부 계획하고, 위임하고, 종합합니다. 실제 일을 하는 것은 잎(leaf) 노드뿐입니다.

### 빛나는 순간

- **명확한 조직 대응.** 실제 과제가 부서 단위라면("법무가 문서 검토, 재무가 문서 검토, 엔지니어링이 문서 검토, 그다음 경영진용으로 요약"), 계층이 그대로 드러납니다.
- **국소 요약.** 각 서브 매니저가 최상위 매니저가 보기 전에 자기 팀의 출력을 종합합니다. 최상위 매니저는 워커 출력 열다섯 개가 아니라 서브 매니저 요약 세 개를 보죠.

### 깨지는 순간

2026년 사후 분석(post-mortem)들이 계속 발견하는 세 가지 실패 양상:

1. **태스크 배정 오류.** 매니저가 목표를 읽고 분해를 환각해서 잘못된 서브 매니저에게 위임합니다. 서브 매니저는 시킨 일에 충실하게 매달리기 때문에, 이 오류는 최상위 종합에서만 표면화됩니다 — 인간이 잡았을 법한 지점보다 한 겹 위에서요.
2. **출력 오해.** 서브 매니저가 "주장 X를 검증할 수 없음"을 반환합니다. 최상위 매니저는 이를 "주장 X는 확인되지 않음"으로 요약합니다. 의미가 층마다 조금씩 흘러갑니다.
3. **합의 루프.** 두 서브 매니저가 의견이 다릅니다; 최상위 매니저가 조율을 지시합니다; 그들이 아래로 다시 위임합니다; 워커들이 다시 돌립니다; 서브 매니저들이 조금씩 다른 답을 돌려줍니다; 루프. CrewAI의 `Process.hierarchical`은 단계 한도로 이를 방어하지만, 그 한도 자체가 이제 하이퍼파라미터가 됩니다.

### 결정적 질문

순차(선형 파이프라인) vs 계층형: 당신의 과제가 정말 독립적인 서브팀을 갖고 있나요, 아니면 나무인 척하는 하나의 선형 흐름인가요? 후자라면 순차를 쓰세요. 전자라면 계층형을 쓰되, 명시적인 조율 규칙에 예산을 배정하세요.

### 역할 기반 프레임워크 구현

CrewAI의 `Process.hierarchical`은 전문 크루들 위에 매니저 LLM을 얹습니다. 매니저는:

- 최상위 태스크를 받고,
- 크루들에게 서브태스크를 배정하고,
- 크루 출력을 평가하고,
- 수용할지, 다시 위임할지, 반복할지 결정합니다.

문서: https://docs.crewai.com/en/introduction (Core Concepts 아래 "Hierarchical Process"를 찾으세요).

### 그래프 기반 프레임워크 구현

LangGraph는 중첩된 `create_supervisor` 호출을 씁니다. 안쪽 슈퍼바이저는 자기만의 그래프를 가지고, 바깥쪽 슈퍼바이저는 안쪽 그래프를 불투명한(opaque) 노드 하나로 취급합니다. 디버깅은 CrewAI보다 깔끔합니다(각 그래프를 따로 스텝별로 밟아볼 수 있음) 하지만 트리를 동적으로 재구성하는 걸 표현하기는 더 어렵습니다.

참고: https://reference.langchain.com/python/langgraph-supervisor.

## 만들기

`code/main.py`는 3단계 계층을 돌립니다:

- 최상위 매니저: 태스크를 "엔지니어링"과 "법무" 브랜치로 쪼갭니다,
- 엔지니어링 서브 매니저: "프론트엔드"와 "백엔드" 워커로 쪼갭니다,
- 법무 서브 매니저: 워커 하나.

데모는 해피 패스(모두가 의견 일치)를, 최상위 매니저의 분해가 "법무"를 "재무"로 잘못 라벨링하는 **교란된 경로(perturbed path)**와 대조합니다 — 그리고 오류가 어떻게 도미노처럼 연쇄되는지 보여 줍니다: 서브 매니저는 충실하게 재무 일을 하고, 최상위 종합자는 재무 발견을 보고하고, 원래 법무 질문은 끝내 답을 못 받습니다.

실행:

```
python3 code/main.py
```

출력에는 두 경로가 나란히 보여집니다: "무엇을 요청받았나" vs "무엇이 전달됐나".

## 사용하기

`outputs/skill-hierarchy-fitness.md`는 주어진 태스크가 계층형, 순차, 플랫 슈퍼바이저 중 무엇을 써야 하는지 평가합니다. 입력: 태스크 설명, 조직 구조, 조율 예산. 출력: 방어해야 할 구체적인 실패 양상이 붙은 패턴 추천.

## 출시하기

계층형을 출시한다면:

- **트리 깊이는 2로 제한.** 3단계만 되어도 대부분의 오류가 관측 가능성 밖으로 숨습니다.
- **명시적인 조율 예산.** 최상위 매니저가 결단해야 하는 최대 라운드 수를 정하세요. 보통은 2입니다.
- **모든 종합에 출처(provenance) 표기.** 각 노드의 요약은 자기를 만든 잎 출력들이 무엇인지 인용해야 합니다.
- **분해 표류 알림.** 매니저의 분해를 매 단계 기록하고; 사용자 쿼리와 diff하세요. 분해가 더 이상 쿼리를 커버하지 않으면 알림을 울리세요.

## 연습 문제

1. `code/main.py`를 실행해서 해피 패스와 교란된 경로를 비교해 보세요. 최상위 출력이 사용자의 질문과 완전히 갈라지기까지 매니저 핸드오프가 몇 단계 필요한가요?
2. 세 번째 단계를 추가해 보세요(최상위 → 서브 → 서브의 서브 → 워커). 깊이가 깊어질수록 교란된 경로가 스스로 교정되는 빈도와 완전히 갈라지는 빈도를 측정하세요.
3. 각 서브 매니저 아래에 "카나리아" 워커를 구현해 보세요. 이 워커는 언제나 원래 사용자 질문을 그대로 받습니다. 카나리아 답변으로 분해 표류를 감지하세요. 카나리아가 종합된 답과 다르다고 말할 때 매니저는 어떻게 반응해야 할까요?
4. CrewAI의 `Process.hierarchical` 문서를 읽어 보세요. CrewAI가 적용하는 구체적인 가드레일 하나(단계 한도, manager_llm 제약)를 찾고, 그게 겨냥하는 실패 양상을 기술하세요.
5. 중첩 LangGraph 슈퍼바이저와 CrewAI 계층형을 비교해 보세요. 조율 루프를 더 저렴하게 감지할 수 있는 쪽은 어디인가요?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| Hierarchical | "조직도 패턴" | 슈퍼바이저 위에 슈퍼바이저; 실제 일은 잎 노드만 합니다. |
| Manager LLM | "사장님" | 내부 노드에서 분해하고, 배정하고, 검증하는 LLM. |
| Decomposition drift | "사장님이 길을 잃음" | 최상위 매니저의 분해가 더 이상 원래 질문을 커버하지 않는 상태. |
| Reconciliation loop | "끝없는 회의" | 서브 매니저들이 의견이 다름; 최상위가 다시 위임; 워커들이 다시 실행; 예산이 닳을 때까지 루프. |
| Depth-2 ceiling | "2단계 이상 깊지 마라" | 경험적 가드레일: 3단계 이상이면 관측 가능성이 무너집니다. |
| Canary question | "매 층의 정답지" | 표류를 감지하기 위해 언제나 원래 쿼리를 그대로 받는 워커. |
| Provenance chain | "누가 뭘 말했나" | 각 종합으로부터 그것을 만든 잎 출력들까지의 추적 경로. |
