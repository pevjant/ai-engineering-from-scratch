# 멀티 에이전트 프리미티브 모델

> 프리미티브(기본 요소)는 단 네 가지입니다 — 에이전트, 핸드오프, 공유 상태, 오케스트레이터 — 이 네 축이 하나의 4차원 설계 공간을 이루고, 2026년에 출시되는 주요 멀티 에이전트 프레임워크들(AutoGen, LangGraph, CrewAI, OpenAI Agents SDK, Microsoft Agent Framework)은 그 공간 위의 점들일 뿐입니다. 이 레슨에서는 이들을 전부 제로부터 만들어 보고, 장난감 시스템을 네 가지 프리미티브 전부 위에서 돌려 본 다음, 모든 주요 프레임워크를 같은 축에 사상(mapping)해서 새 릴리스가 나와도 단락 하나로 읽어 내는 힘을 기릅니다.

**유형:** 학습
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 14(에이전트 엔지니어링), 페이즈 16 · 01(왜 멀티 에이전트인가)
**시간:** 약 60분

## 문제

반년에 한 번 새 멀티 에이전트 프레임워크가 나옵니다. 2023년 AutoGen. 2024년 CrewAI. 2024년 LangGraph와 OpenAI Swarm. 2025년 4월 Google ADK. 2026년 2월 Microsoft Agent Framework RC. 보도자료마다 자기들이 "올바른 추상화"라고 주장하죠.

이걸 하나씩 하나씩 배우려 하면 지쳐서 못 합니다. API는 전부 다르게 생겼고, 문서들은 "에이전트"가 뭔지에 대해 서로 의견이 다릅니다. 어떤 프레임워크는 공유 메모리를 "블랙보드"라 부르고, 다른 곳은 "메시지 풀", 또 다른 곳은 "StateGraph"라 부릅니다. 이 분야가 그냥 겉모습만 바꿔가며 우르르 쏟아내는 게 아닌가 의심이 들기 시작하죠.

아닙니다. 마케팅 아래에는 네 가지 프리미티브가 그대로 있습니다. 한 번만 배우면, 새 프레임워크를 단락 하나로 읽어 낼 수 있습니다.

## 개념

### 네 가지 프리미티브

1. **에이전트** — 시스템 프롬프트에 도구 목록을 얹은 것. 상태가 없습니다(stateless); 모든 실행은 자기 시스템 프롬프트와 현재 메시지 히스토리에서 시작합니다.
2. **핸드오프** — 한 에이전트에서 다른 에이전트로 제어권을 넘기는 구조화된 전달. 기계적으로는 새 에이전트를 반환하는 도구 호출이거나, 조건을 따라가는 그래프 엣지입니다.
3. **공유 상태** — 둘 이상의 에이전트가 읽을 수 있는(때로는 쓸 수 있는) 데이터 구조. 메시지 풀, 블랙보드, 키-값 저장소, 벡터 메모리 등이 여기 해당합니다.
4. **오케스트레이터** — 다음으로 누가 말할지 결정하는 주체. 선택지: 명시적인 그래프(결정적), LLM 스피커 선택기(소프트), 마지막 발화자의 핸드오프 호출(OpenAI Swarm), 큐 위에서 도는 스케줄러(스웜 아키텍처).

이게 설계 공간의 전부입니다. 모든 프레임워크는 각 축마다 기본값 하나씩 고를 뿐이고, 나머지는 표면 문법입니다.

### 2026년 모든 프레임워크가 이 모델에 대응되는 방식

| 프레임워크 | 에이전트 | 핸드오프 | 공유 상태 | 오케스트레이터 |
|-----------|-------|---------|--------------|--------------|
| OpenAI Swarm / Agents SDK | `Agent(instructions, tools)` | 도구가 Agent를 반환 | 호출자의 몫 | LLM의 다음 핸드오프 호출 |
| AutoGen v0.4 / AG2 | `ConversableAgent` | GroupChat의 스피커 선택기 | 메시지 풀 | 선택자 함수(LLM 또는 라운드 로빈) |
| CrewAI | `Agent(role, goal, backstory)` | `Process.Sequential / Hierarchical` | 태스크 출력을 체이닝 | 매니저 LLM 또는 고정 순서 |
| LangGraph | 노드 함수 | 그래프 엣지 + 조건 | `StateGraph` 리듀서 | 그래프 자체, 결정적 |
| Microsoft Agent Framework | 에이전트 + 오케스트레이션 패턴 | 패턴별 상이 | 스레드 / 컨텍스트 | 패턴별 상이 |
| Google ADK | 에이전트 + A2A 카드 | A2A 태스크 | A2A 아티팩트 | 호스트가 결정 |

표면 차이는 엄청나 보입니다. 그 아래에는 같은 네 개의 손잡이가 있을 뿐입니다.

### 왜 중요한가

프리미티브를 한 번 보고 나면, 프레임워크 비교는 짧은 체크리스트가 됩니다:

- 오케스트레이터가 라우팅을 LLM에게 맡기나요(Swarm), 아니면 코드에 박아 두나요(LangGraph)?
- 공유 상태가 전체 히스토리인가요(GroupChat), 아니면 투영된(projection) 뷰인가요(StateGraph 리듀서)?
- 에이전트가 서로의 프롬프트를 수정할 수 있나요(CrewAI 매니저), 아니면 핸드오프만 가능한가요(Swarm)?

이 세 질문이 주어진 문제에 어떤 프레임워크가 맞는지의 80%를 답해 줍니다. "최고의 멀티 에이전트 프레임워크"를 쇼핑하는 대신, 실제로 신경 쓰이는 축을 기준으로 설계하게 됩니다.

### 상태 없음(stateless)의 통찰

공유 상태를 빼면 모든 프리미티브는 상태가 없습니다. 에이전트는 (프롬프트, 도구)의 함수입니다. 핸드오프는 함수 호출입니다. 오케스트레이터는 스케줄러입니다. **시스템에서 유일하게 상태를 가진 것은 공유 상태입니다.** 재미있는 버그들이 전부 여기 삽니다: 메모리 오염(레슨 15), 메시지 순서, 버저닝, 쓰기 경쟁.

공유 상태를 숨기는 프레임워크(Swarm)는 문제를 호출자에게 떠넘깁니다. 공유 상태를 중앙화하는 프레임워크(LangGraph 체크포인트, AutoGen 풀)는 들여다보기 쉽게 만들지만 조율 비용을 공유 상태 구현에 떠넘깁니다.

### 프리미티브 하나의 해부학

#### 에이전트

```
Agent = (system_prompt, tools, model, optional_name)
```

메모리 없음. 상태 없음. 시스템 프롬프트와 도구가 같은 두 에이전트는 서로 바꿔 쓸 수 있습니다. 에이전트별 상태처럼 보이는 모든 것은 실제로는 공유 상태나 핸드오프 프로토콜 안에 있습니다.

#### 핸드오프

```
Handoff = (from_agent, to_agent, reason, payload)
```

세 가지 구현이 지배적입니다:

- **함수 반환** — 도구가 다음 에이전트를 반환합니다. OpenAI Swarm 패턴입니다. 에이전트가 자기 도구 스키마에 라우팅을 담고 있는 거죠.
- **그래프 엣지** — LangGraph. 엣지는 선언적입니다. LLM이 값을 만들면, 조건이 다음 노드를 고릅니다.
- **스피커 선택** — AutoGen GroupChat. 선택자 함수(가끔 그 자체가 LLM 호출)가 풀을 읽고 다음 발화자를 고릅니다.

#### 공유 상태

```
SharedState = { messages: [], artifacts: {}, context: {} }
```

최소한은 메시지 목록입니다. 종종 더 있습니다: 구조화된 아티팩트(CrewAI Task 출력), 타입이 지정된 컨텍스트(LangGraph 리듀서), 외부 메모리(MCP, 벡터 DB).

두 가지 토폴로지가 있습니다: **풀 풀(full pool)**(모든 에이전트가 모든 메시지를 봄)과 **투영(projected)**(에이전트가 역할에 맞게 좁혀진 뷰를 봄). 풀 풀은 단순하지만 확장에 취약합니다. 투영 풀은 확장에 유리하지만 사전 스키마 설계가 필요합니다.

#### 오케스트레이터

```
Orchestrator = ({state, last_speaker}) -> next_agent
```

네 가지 변형이 있습니다:

- **정적** — 그래프가 빌드 시점에 고정됩니다(LangGraph 결정적, CrewAI Sequential).
- **LLM 선택** — LLM이 풀을 읽고 다음 발화자를 고릅니다(AutoGen, CrewAI Hierarchical).
- **핸드오프 주도** — 현재 에이전트가 핸드오프 도구를 호출해서 결정합니다(Swarm).
- **큐 주도** — 워커들이 공유 큐에서 작업을 가져옵니다; 명시적인 다음 발화자가 없습니다(스웜 아키텍처, Matrix).

### 프레임워크 사이에서 달라지는 것

프리미티브가 고정되면, 남은 설계 결정은 다음과 같습니다:

- **메모리 전략** — 휘발성 vs 영속 체크포인팅(LangGraph checkpointer).
- **안전 경계** — 핸드오프를 승인할 수 있는 사람(사람 개입, human-in-the-loop).
- **비용 회계** — 에이전트별 토큰 예산.
- **관측 가능성(옵저버빌리티)** — 핸드오프 추적, 리플레이를 위한 상태 저장.

전부 프리미티브 위에 구현할 수 있는 것들입니다. 새로운 프리미티브는 하나도 없습니다.

## 만들기

`code/main.py`는 네 가지 프리미티브를 표준 라이브러리 파이썬 약 150줄로 구현합니다. 진짜 LLM은 없습니다 — 각 에이전트는 스크립트로 짜인 정책일 뿐이라서, 초점이 조율 구조에 그대로 유지됩니다.

이 파일이 내보내는 것:

- `Agent` — 이름, 시스템 프롬프트, 도구, 정책 함수를 담은 데이터클래스.
- `Handoff` — 새 에이전트를 반환하는 함수.
- `SharedState` — 스레드 세이프한 메시지 풀.
- `Orchestrator` — 세 가지 변형: `StaticOrchestrator`, `HandoffOrchestrator`, `LLMSelectorOrchestrator`(시뮬레이션).

데모는 같은 세 에이전트 파이프라인(리서치 → 작성 → 리뷰)을 세 가지 오케스트레이터 타입 전부로 돌리고, 마지막에 메시지 풀을 출력합니다. 출력 결과가 달라지는 지점은 오직 *다음을 고르는 주체*뿐이라는 걸 확인할 수 있습니다. 에이전트와 공유 상태는 실행마다 완전히 동일합니다.

실행 방법:

```
python3 code/main.py
```

기대 출력: 오케스트레이터 실행 3회, 패턴마다 하나씩. 각 실행이 최종 메시지 풀을 출력합니다. 리서처가 일찍 끝났다고 판단하면 핸드오프 주도 실행은 더 적은 수의 에이전트에 도달합니다 — 이게 축소판 LLM 라우팅 트레이드오프입니다.

## 사용하기

`outputs/skill-primitive-mapper.md`는 멀티 에이전트 코드베이스나 프레임워크 문서를 읽고 네 프리미티브 사상을 반환하는 스킬입니다. 새 프레임워크 릴리스가 나왔을 때 이걸 돌리면, 문서를 깊게 읽기 전에 단락 하나짜리 이해를 얻을 수 있습니다.

## 출시하기

새 프레임워크를 도입하기 전에, 그 프레임워크의 프리미티브 사상을 작성하세요. 작성할 수 없다면 문서가 불완전하거나, 그 프레임워크가 다섯 번째 프리미티브를 발명한 것입니다(드묾 — 여러분이 못 본 공유 상태 변형이 없는지 확인하세요).

사상 결과를 아키텍처 문서에 고정해 두세요. 새 팀원이 들어오면 API 문서보다 사상을 먼저 보내 주세요. 프레임워크 버전이 바뀌면 체인지로그가 아니라 사상을 diff하세요.

## 연습 문제

1. `code/main.py`를 다른 에이전트 정책으로 세 번 실행해 보세요. 오케스트레이터 선택이 어떤 에이전트가 실행되는지를 어떻게 바꾸는지 관찰하세요.
2. 네 번째 오케스트레이터 타입을 구현해 보세요: 에이전트들이 공유 상태를 폴링해서 작업을 가져가는 큐 주도 방식입니다. 어떤 교착 상태(deadlock)가 생길 수 있고, 어떻게 감지할 수 있을까요?
3. LangGraph 퀵스타트(https://docs.langchain.com/oss/python/langgraph/workflows-agents)를 가져다가 네 프리미티브로 다시 써 보세요. LangGraph의 추상화 중 무엇이 1:1로 대응되고, 무엇이 편의용 래퍼일까요?
4. OpenAI Swarm 쿡북(https://developers.openai.com/cookbook/examples/orchestrating_agents)을 읽어 보세요. Swarm이 네 프리미티브 중 무엇을 가장 쓰기 편하게 만들고, 무엇을 호출자에게 떠넘기는지 밝히세요.
5. 이 표에서 공유 상태를 완전히 숨기는 프레임워크를 하나 찾으세요. 핸드오프 사이를 오가는 에이전트들이 히스토리를 다시 읽지 않고 조율해야 할 때 무엇이 깨지는지 설명하세요.

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| Agent | "도구를 단 LLM" | `(system_prompt, tools, model)` 트리플렛. 상태 없음. |
| Handoff | "제어권 이전" | 다음 에이전트의 이름과 선택적 페이로드를 명시하는 구조화된 호출. 세 가지 구현: 함수 반환, 그래프 엣지, 스피커 선택. |
| Shared state | "메모리" / "컨텍스트" | 멀티 에이전트 시스템에서 유일하게 상태를 가진 부분. 메시지 풀 또는 블랙보드. |
| Orchestrator | "조율자" | 다음으로 누가 실행될지 결정하는 주체. 정적 그래프, LLM 선택자, 핸드오프 주도, 또는 큐 주도. |
| Primitive | "추상화" | 모든 프레임워크가 매개변수화하는 네 축 중 하나. 프레임워크 기능이 아닙니다. |
| Message pool | "공유 채팅 히스토리" | 전체 히스토리를 담는 공유 상태. 이해하기 쉽지만 확장에 취약. |
| Projected state | "범위가 좁혀진 뷰" | 공유 상태에서 역할별로 좁혀진 뷰. 확장에 유리하지만 스키마 설계가 필요. |
| Speaker selection | "다음에 누가 말할지" | 함수(주로 LLM)가 그룹에서 다음 에이전트를 고르는 오케스트레이터 패턴. |
