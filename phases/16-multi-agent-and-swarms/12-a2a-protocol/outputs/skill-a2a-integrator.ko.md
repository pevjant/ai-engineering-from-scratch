> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [skill-a2a-integrator.md](skill-a2a-integrator.md)

상호 운용이 필요한 두 에이전트 시스템이 주어지면, A2A 통합 계획을 만들어 냅니다: 에이전트 카드 내용, 태스크 스키마, 인증, 전송 방식.

산출물:

1. **에이전트 카드.** 이름, 버전, 스킬, 엔드포인트, 지원 모달리티(텍스트, 구조화, 이미지, 오디오, 비디오), protocol_version, 인증 선언.
2. **스킬별 태스크 스키마.** 입력 JSON 스키마 + 산출물 JSON 스키마. 명시적으로 적으세요 — 클라이언트가 이를 검증합니다.
3. **인증 선택.** 베어러 토큰(OAuth2 또는 불투명 토큰), mTLS, 또는 서명된 요청. 위협 모델(공개 인터넷, VPC, 혼합)을 고려해 근거를 제시합니다.
4. **전송 방식.** 폴링 vs SSE 스트리밍 vs 웹훅 콜백. 오래 걸리거나 진행 상황이 중요한 태스크는 스트리밍, 짧은 태스크는 폴링.
5. **속도 제한.** 클라이언트별 및 태스크별 제한. 남용 방지용입니다.
6. **멱등성.** 중복된 `POST /tasks` 요청에 대한 전략(클라이언트 측 태스크 키, 서버 측 중복 제거).
7. **실패 처리.** `failed` 너머의 태스크 상태(재시도 가능 vs 치명적), 데드레터 정책, 오류 산출물 스키마.
8. **MCP vs A2A 구분.** 원격 에이전트가 내부적으로 MCP를 쓴다면, 어떤 도구를 노출하고 어떤 도구를 내부에 두는지 적어 두세요.

하드 리젝(무조건 거부):

- 프로토콜 버전을 선언하지 않은 에이전트 카드.
- 사용 사례가 구조를 요구하는데도 자유 형식 텍스트로만 되어 있는 태스크 스키마.
- 공개 인터넷 배포에서 auth=none인 구성.

거부 규칙:

- 두 에이전트가 같은 프로세스에서 돈다면 A2A를 거부하고 직접 파이썬/JS 호출을 권하세요. A2A는 시스템 경계를 넘을 때 쓰는 것입니다.
- 지연 시간 요구가 왕복 100밀리초 미만이라면 A2A를 거부하고 공유 스키마를 쓰는 직접 RPC를 권하세요.
- 원격 에이전트가 에이전트 카드를 선언하지 않는다면 통합을 거부하고 먼저 카드 발행을 권하세요.

출력: 한 페이지짜리 통합 브리프. 마지막에 에이전트 카드 JSON을 그대로 붙여 넣어, 엔지니어링 팀이 `/.well-known/agent.json`에 바로 넣을 수 있게 하세요.
