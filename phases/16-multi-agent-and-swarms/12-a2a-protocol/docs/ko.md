# A2A — 에이전트 간(Agent-to-Agent) 프로토콜

> Google은 2025년 4월 A2A를 발표했고, 2026년 4월 현재 스펙은 https://a2a-protocol.org/latest/specification/ 에 있으며 150개 이상의 조직이 이를 지지합니다. A2A는 MCP(13레슨)의 수평 보완재입니다: MCP가 수직(에이전트 ↔ 도구)이라면 A2A는 피어 투 피어(에이전트 ↔ 에이전트)입니다. A2A는 에이전트 카드(디스커버리), 산출물(텍스트, 구조화 데이터, 비디오)을 동반하는 태스크, 불투명(opaque) 태스크 수명 주기, 인증을 정의합니다. 프로덕션(운영 환경) 시스템들은 점점 MCP와 A2A를 짝지어 씁니다. Google Cloud는 2025~2026년 동안 Vertex AI Agent Builder에 A2A 지원을 넣었습니다.

**유형:** 학습 + 빌드
**언어:** Python(표준 라이브러리, `http.server`, `json`)
**선수 지식:** 페이즈 16 · 04(프리미티브 모델)
**시간:** 약 75분

## 문제

여러분의 에이전트가 다른 시스템에 있는 또 다른 에이전트를 호출해야 합니다. 어떻게 할까요? HTTP 엔드포인트를 열고, 자체적인 JSON 스키마를 정의하고, 상대가 그걸 이해하길 바랄 수도 있겠죠. 그러면 에이전트 쌍마다 커스텀 통합이 하나씩 생겨납니다.

A2A는 바로 그 호출을 위한 범용 와이어 프로토콜입니다. 표준 디스커버리, 표준 태스크 모델, 표준 전송, 표준 산출물. HTTP+REST를 에이전트가 일급 시민이 되도록 바꿔 놓은 셈입니다.

## 개념

### 네 가지 요소

**에이전트 카드(Agent Card).** `/.well-known/agent.json`에 있는 JSON 문서로, 에이전트를 설명합니다: 이름, 스킬, 엔드포인트, 지원 모달리티, 인증 요구 사항. 디스커버리는 이 카드를 읽는 것으로 이뤄집니다.

```
GET https://agent.example.com/.well-known/agent.json
→ {
    "name": "code-review-agent",
    "skills": ["review-python", "review-typescript"],
    "endpoints": {
      "tasks": "https://agent.example.com/tasks"
    },
    "auth": {"type": "bearer"},
    "modalities": ["text", "structured"]
  }
```

**태스크(Task).** 작업의 단위. 수명 주기를 가진 비동기적이고 상태를 지닌 객체입니다: `submitted → working → completed / failed / canceled`. 클라이언트는 태스크를 보낸 뒤 업데이트를 폴링하거나 구독합니다.

**산출물(Artifact).** 태스크가 만들어내는 결과 타입. 텍스트, 구조화 JSON, 이미지, 비디오, 오디오. 산출물에는 타입이 붙어 있어 다양한 모달리티가 일급으로 다뤄집니다.

**불투명 수명 주기(opaque lifecycle).** A2A는 원격 에이전트가 태스크를 *어떻게* 푸는지 규정하지 않습니다. 클라이언트는 상태 전이와 산출물만 볼 뿐이고, 구현은 어떤 프레임워크든 자유롭게 쓸 수 있습니다.

### MCP/A2A 구분

- **MCP**(13레슨): 에이전트 ↔ 도구. 에이전트가 JSON-RPC로 도구 서버를 읽고 씁니다. 기본적으로 무상태입니다.
- **A2A**: 에이전트 ↔ 에이전트. 피어 프로토콜. 양쪽 모두 자기만의 추론 능력을 지닌 에이전트입니다.

프로덕션 멀티 에이전트 시스템은 둘 다 씁니다. A2A 피어는 자기 쪽에서 MCP 도구를 호출합니다. 이 구분 덕분에 두 관심사가 깔끔하게 분리됩니다.

### 디스커버리 흐름

```
클라이언트                     에이전트 서버
  ├──GET /.well-known/agent.json──>
  <──에이전트 카드 JSON───────────
  ├──POST /tasks {skill, input}──>
  <──201 task_id, state=submitted
  ├──GET /tasks/{id}──────────────>
  <──state=working, 42% 진행──────
  ├──GET /tasks/{id}──────────────>
  <──state=completed, 산출물─────
```

또는 스트리밍으로: `/tasks/{id}/events`를 SSE 구독해 푸시 업데이트를 받을 수도 있습니다.

### 인증

A2A는 흔한 세 가지 패턴을 지원합니다:

- **베어러 토큰(bearer token)** — OAuth2 또는 불투명 토큰.
- **mTLS** — 상호 TLS. 조직들이 서로 신원을 증명합니다.
- **서명된 요청** — 페이로드 위의 HMAC.

인증 방식은 에이전트 카드에 선언되고, 클라이언트가 이를 발견해 맞춰 줍니다.

### 2026년 4월까지 150개 이상의 조직

엔터프라이즈 도입이 A2A의 규모 확장을 이끌었습니다. 요점은 이것입니다: A2A는 엔터프라이즈 에이전트 시스템이 신뢰 경계를 넘을 때 쓰는 표준 방식이 되었습니다. Google Cloud는 Vertex AI Agent Builder에 A2A 지원을 출시했고, Microsoft Agent Framework가 이를 지원하며, 대부분의 주요 프레임워크(LangGraph, CrewAI, AutoGen)가 A2A 어댑터를 싣고 있습니다.

### A2A가 강한 곳

- **조직 간 호출.** A회사의 에이전트가 B회사의 에이전트를 호출합니다. A2A가 없다면 쌍마다 맞춤 계약이 필요합니다.
- **이기종 프레임워크.** LangGraph 에이전트가 CrewAI 에이전트를 호출하고, 그 에이전트가 커스텀 파이썬 에이전트를 호출하는 식. A2A가 이를 표준화합니다.
- **타입 있는 산출물.** 비디오 결과, 구조화 JSON, 오디오 — 모두 일급입니다.
- **장기 실행 태스크.** 불투명 수명 주기 + 폴링 덕분에 몇 시간짜리 태스크도 간단합니다.

### A2A가 애를 먹는 곳

- **지연 시간에 민감한 아주 짧은 호출.** A2A의 수명 주기는 비동기입니다. 밀리초 미만의 에이전트 간 호출에는 맞지 않습니다. 직접 RPC를 쓰세요.
- **강하게 결합된 프로세스 내 에이전트.** 두 에이전트가 같은 파이썬 프로세스에서 돈다면 A2A의 HTTP 왕복은 과합니다.
- **소규모 팀.** 스펙을 지키는 오버헤드는 실재합니다. 내부 전용 에이전트에는 이런 격식이 필요 없을 수 있습니다.

### A2A vs ACP, ANP, NLIP

2024~2026년 사이에 관련 스펙 여럿이 나왔습니다:

- **ACP**(IBM/Linux Foundation) — A2A의 전신. 범위가 더 좁습니다.
- **ANP**(Agent Network Protocol) — 피어 디스커버리 중심, 탈중앙화 우선.
- **NLIP**(Ecma Natural Language Interaction Protocol, 2025년 12월 표준화) — 자연어 콘텐츠 타입.

2026년 4월 기준 A2A가 가장 널리 채택된 피어 프로토콜입니다. 비교는 arXiv:2505.02279(Liu et al., "A Survey of Agent Interoperability Protocols")를 참고하세요.

## 만들어 보기

`code/main.py`는 `http.server`와 JSON으로 A2A 미니멀 서버와 클라이언트를 구현합니다. 서버는:

- `/.well-known/agent.json`을 노출하고,
- `POST /tasks`를 받아들이고,
- 태스크 상태를 관리하며,
- `GET /tasks/{id}`로 산출물을 반환합니다.

클라이언트는:

- 에이전트 카드를 가져오고,
- 태스크를 제출하고,
- 완료까지 폴링하고,
- 산출물을 읽습니다.

실행:

```
python3 code/main.py
```

스크립트는 서버를 백그라운드 스레드로 띄운 다음, 그 서버를 향해 클라이언트를 실행합니다. 디스커버리, 제출, 폴링, 산출물까지 전체 흐름이 보입니다.

## 활용하기

`outputs/skill-a2a-integrator.md`는 A2A 통합을 설계합니다: 에이전트 카드 내용, 태스크 스키마, 인증 선택, 스트리밍 vs 폴링.

## 출시하기

체크리스트:

- **스펙 버전 고정.** A2A는 아직 진화 중입니다. 에이전트 카드가 프로토콜 버전을 선언해야 합니다.
- **멱등한 태스크 생성.** 중복 제출(네트워크 재시도)은 하나의 태스크로 귀결되어야 합니다.
- **산출물 스키마.** 에이전트가 어떤 모양의 결과를 반환하는지 선언하세요. 소비자는 이를 검증해야 합니다.
- **속도 제한 + 인증.** A2A는 외부에 노출되는 인터페이스입니다. 표준 웹 보안을 적용하세요.
- **실패 태스크의 데드레터(dead-letter).** 반복되는 실패 유형을 시간이 지나며 파악할 수 있게 하세요.

## 연습 문제

1. `code/main.py`를 실행하세요. 클라이언트가 서버를 발견하고 올바른 산출물을 받는지 확인하세요.
2. 서버에 두 번째 스킬(예: "summarize")을 추가하세요. 에이전트 카드를 갱신하고, 태스크 유형에 따라 스킬을 고르는 클라이언트를 작성하세요.
3. 상태 변화를 내보내는 SSE 스트리밍 엔드포인트 `/tasks/{id}/events`를 구현해 보세요. 클라이언트 쪽은 뭐가 달라져야 할까요?
4. A2A 스펙(https://a2a-protocol.org/latest/specification/)을 읽고, 이 데모가 구현하지 않는 스펙의 필수 사항 세 가지를 찾아보세요.
5. A2A(에이전트 카드 디스커버리)와 MCP(`listTools`를 통한 서버 측 기능 나열)를 비교해 보세요. 자기 기술형(self-describing) 에이전트와 기능 탐방(probing) 사이의 트레이드오프는 무엇인가요?

## 핵심 용어

| 용어 | 사람들이 말하는 표현 | 실제 의미 |
|------|----------------|------------------------|
| A2A | "에이전트끼리의 통신" | 에이전트가 시스템을 넘어 다른 에이전트를 호출하기 위한 피어 프로토콜. Google, 2025. |
| 에이전트 카드(Agent Card) | "에이전트의 명함" | `/.well-known/agent.json`의 JSON. 스킬, 엔드포인트, 인증을 설명. |
| 태스크(Task) | "작업의 단위" | 수명 주기를 가진 비동기 상태 객체. 완료 시 산출물을 생산. |
| 산출물(Artifact) | "결과물" | 타입 있는 출력: 텍스트, 구조화 JSON, 이미지, 비디오, 오디오. 일급 미디어. |
| 불투명 수명 주기(opaque lifecycle) | "어떻게 푸는지는 에이전트 사정" | 클라이언트는 상태 전이만 보고, 서버는 프레임워크/도구를 자유롭게 선택. |
| 디스커버리(discovery) | "에이전트 찾기" | `GET /.well-known/agent.json`이 카드를 반환. |
| MCP vs A2A | "도구 vs 피어" | MCP: 수직 에이전트 ↔ 도구. A2A: 수평 에이전트 ↔ 에이전트. |
| ACP / ANP / NLIP | "자매 프로토콜" | 인접한 스펙들. 2026년 기준 A2A가 가장 널리 채택됨. |
