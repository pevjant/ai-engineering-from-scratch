멀티 에이전트 시스템과 표본으로 뽑은 실행 트레이스가 주어지면, 실패 양상 감사를 수행합니다.

다음을 산출합니다:

1. **표본 구성.** 프로덕션에서 나온 트레이스 200개 이상을, 태스크 유형과 시간 구간 전반에 걸쳐 균등하게 표본 추출합니다. 표본 추출 방법과 편향 위험을 문서화하세요.
2. **분류 패스.** 각 트레이스에 `success | failure` 표시를 합니다. 실패에는 MAST 범주 하나(spec / coord / verify)를, 해당되면 집단사고 계열 태그를 하나 이상(monoculture / conformity / tom / mixed-motive / cascade) 붙입니다.
3. **분포 표.** MAST 범주별 및 집단사고 태그별 건수와 백분율. Cemri 2025의 참조 분포(41.77 / 36.94 / 21.30)와 비교하세요. 참조 분포에서 크게 벗어나는 시스템은 보통 특정 약한 계층을 갖고 있습니다.
4. **상위 실패 패턴.** 가장 빈번한 구체적 패턴 3가지를 찾으세요(예: "두 에이전트가 둘 다 검토함"). 재현 절차를 문서화하세요.
5. **완화책 순위.** 각 상위 패턴에 대해 표준 라이브러리에서 완화책을 제안합니다: 명시적 역할 계약, 버전 관리되는 공유 상태, 독립 검증자, 서킷 브레이커, 탐지-진단-검증(STRATUS) 삼인조. 패턴 빈도를 반영해 기대 실패 감소분 순으로 순위를 매깁니다.
6. **조용한 실패의 위험.** 실패 중 몇 개가 시끄러운 오류 대신 그럴듯하지만 틀린 출력을 만들었나요? 조용한 실패 비율이 검증 계층 투자 규모를 결정합니다.
7. **느린 실패 대리 지표.** 큰 오류가 되기 전에 표류를 드러낼 실시간 지표 2~3개를 권하세요: 합의율, 재시도율, 출력 길이 분포, 에이전트 간 편집 거리.

하드 리젝(무조건 거부) 기준:

- 무작위 또는 층화 표본 없이 하는 감사. 손으로 골라 낸 실패는 극적인 사례를 과대 대표하고 느린 실패 표류를 놓칩니다.
- 기준선 측정 없이 내놓는 완화책 권고. 현재 실패율을 모르면 "검증자를 추가하라"는 아무 의미가 없습니다.
- MAST로 분류 안 되는 장애 무시하기. 어떤 트레이스가 범주에 맞지 않으면 분류 체계가 불완전한 것입니다. 범주를 억지로 맞추기보다 확장을 제안하세요.
- 실시간 느린 실패 모니터링 없이 분기별 감사만으로 충분하다고 주장하는 것. 분기 감사는 감사 사이의 표류를 놓칩니다.

거부 규칙:

- 트레이스에 에이전트별 귀속 정보(누가 무엇을 썼고 무엇을 읽었는지)가 없으면, 감사는 조율 실패와 역할 충돌을 구분할 수 없습니다. 재감사 전에 구조화된 에이전트별 로깅 추가를 권하세요.
- 전체 실패 트레이스가 50개 미만이면, 표본이 너무 작아 분포 추정을 만들 수 없습니다. 더 긴 관측 구간을 권하세요.
- 트레이스에 개인 식별 정보(PII)가 있으면 분석 전에 마스킹하세요.

출력: 세 페이지 분량의 보고서. 한 문장 요약으로 시작하세요("명세 실패 41%, 조율 12%, 검증 공백 39%, 미분류 8%; 최상위 패턴은 이중 검토자 충돌; 최고 ROI 완화책은 명시적 역할 계약."), 그다음 위의 7개 섹션을 이어서 작성합니다. 마지막에 우선순위가 매겨진 실행 목록(구현 비용 추정과 기대 실패율 감소를 곁들인 완화책 3가지)을 덧붙입니다.
