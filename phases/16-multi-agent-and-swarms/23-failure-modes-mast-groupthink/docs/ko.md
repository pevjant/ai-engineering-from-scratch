# 실패 양상 — MAST, 집단사고, 단일문화, 연쇄 오류

> 2026년의 참조용 분류 체계는 **MAST**(Cemri 등, NeurIPS 2025, arXiv:2503.13657)입니다. 최신 오픈소스 MAS 7종에서 수집한 1,642개 실행 트레이스로부터 도출되었고, **41~86.7%의 실패율**을 보여 줍니다. 세 가지 근본 범주: **명세(Specification) 문제**(41.77%) — 역할 모호성, 불명확한 태스크 정의; **조율(Coordination) 실패**(36.94%) — 통신 붕괴, 상태 불일치; **검증 공백**(21.30%) — 유효성 검사 누락, 품질 점검 부재. **집단사고(Groupthink)** 계열(arXiv:2508.05687)은 여기에 다음을 더합니다: 단일문화 붕괴(같은 베이스 모델 → 상관된 오류), 동조 편향(에이전트들이 서로의 오류를 강화), 결함 있는 마음 이론(theory of mind), 혼합 동기 역학, 연쇄 신뢰성 실패. 연쇄 실패의 예: 결제 실패가 주문 재시도를 부르고, 그것이 재고 재시도를 부르고, 재고 서비스가 압도당하는 재시도 폭풍(몇 초 만에 10배 부하 — 서킷 브레이커 필요). 메모리 오염: 한 에이전트의 환각이 공유 메모리에 들어가면, 하류 에이전트들이 그것을 사실로 받아들이고, 정확도가 서서히 떨어져 근본 원인 진단이 고통스러워집니다. **STRATUS**(NeurIPS 2025)는 특화된 탐지 / 진단 / 검증 에이전트를 통해 완화 성공률이 1.5배 개선됐다고 보고합니다. 이 레슨은 실패 양상을 일급 공학 대상으로 다룹니다.

**유형:** Learn
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 16 · 13 (Shared Memory), 페이즈 16 · 14 (Consensus and BFT), 페이즈 16 · 15 (Voting and Debate Topology)
**시간:** 약 75분

## 문제

멀티 에이전트 시스템은 실제 태스크에서 41~86.7%의 확률로 실패합니다(Cemri 등 2025가 오픈소스 MAS 7종에서 측정). "에이전트를 더 붙이면 되는" 문제가 아닙니다. 실패에는 구조적인 원인이 있습니다. MAST 분류 체계가 범주를 알려 줍니다. 이 레슨은 각 범주를 구체적인 탐지·진단·완화 패턴에 연결해서, 그 숫자들이 더 이상 임의적으로 보이지 않게 만듭니다.

2026년의 프로덕션 관행은 실패 양상을 설계 입력으로 다루는 것입니다. 각 MAST 범주를 가리키면서 자신이 배치한 완화책 이름을 말할 수 있을 때까지, 당신의 아키텍처는 "충분히 좋다"고 할 수 없습니다.

## 개념

### MAST 범주

**명세 문제(실패의 41.77%).** 에이전트의 태스크가 충분히 좁게 정의되지 않은 경우입니다. 예:

- 역할 모호성: 두 에이전트가 둘 다 자신이 검토자라고 생각합니다.
- 태스크 미정의: 사용자는 특정 관점을 원했는데 "이걸 요약해"라고만 전달됨.
- 성공 기준이 암묵적: 에이전트가 자신이 성공했는지 판단할 수 없음.

완화책:
- 명시적인 역할 계약서를 작성하세요. 각 에이전트의 프롬프트에 무엇을 하는지 *그리고 무엇을 하지 않는지* 적습니다.
- 태스크별 수용 테스트. 에이전트가 시작하기 전에 "완료는 X와 같다"를 정의합니다.
- 출발 전 명세 점검: 디스패치 전에 별도의 에이전트가 태스크 정의를 검토합니다.

**조율 실패(36.94%).** 통신이나 상태의 붕괴입니다.

예:
- 두 에이전트가 동기화 없이 공유 상태를 갱신합니다.
- 에이전트 사이에서 메시지가 유실됩니다(큐 실패, 타임아웃).
- 상태 드리프트: 에이전트 A는 태스크가 끝났다고 생각하는데, 에이전트 B는 아직 실행 중입니다.

완화책:
- 낙관적 동시성 제어가 적용된 버전 관리되는 공유 상태.
- 중요 메시지에 대한 명시적 확인 응답(ack가 올 때까지 재시도).
- 주기적인 상태 동기화 체크포인트; 드리프트를 조기에 탐지.

**검증 공백(21.30%).** 출력에 대한 독립적인 점검이 없는 경우입니다.

예:
- 한 에이전트가 성공을 주장하지만 아무도 검증하지 않습니다.
- 에이전트 사슬이 앞 에이전트의 출력을 무비판적으로 신뢰합니다.
- 창발적으로 합성된 동작에 대한 테스트 커버리지가 없습니다.

완화책:
- 독립적인 검증자 에이전트(레슨 13). 읽기 전용, 독립된 소스 접근.
- 명시적인 인수인계 계약: "B가 시작하기 전에 A의 출력은 검사기 C를 통과해야 한다."
- 사후 분석을 위한 결과 로깅.

### 집단사고 계열 (arXiv:2508.05687)

에이전트들이 서로 동질화되거나 흉내 낼 때 생기는 다섯 가지 관련 실패:

**단일문화 붕괴.** 같은 베이스 모델이나 학습 데이터 → 상관된 오류. 세 에이전트가 하나의 LLM을 공유하면, 그 LLM의 환각도 함께 공유합니다.

**동조 편향.** 에이전트들이 가장 시끄럽거나 가장 자신만만한 동료 쪽으로, 틀렸더라도 기웁니다.

**결함 있는 ToM(마음 이론).** 에이전트들이 서로의 신념을 모델링하지 못해 조율이 무너집니다(레슨 18).

**혼합 동기 역학.** 인센티브가 부분적으로만 정렬된 에이전트들이 타협의 중간 지점으로 표류하는데, 그 지점은 아무도 만족시키지 못합니다.

**연쇄 신뢰성 실패.** 한 컴포넌트의 오류 패턴이 의존하는 컴포넌트들의 오류 패턴을 촉발합니다.

### 연쇄 실패의 예 — 재시도 폭풍

2026년의 고전적인 사고 패턴:

```
payment service fails 10% of requests
   ↓
order agent retries payment (exponential backoff but naive)
   ↓
each retry is a new order-inventory check
   ↓
inventory service sees 2x normal load
   ↓
inventory service starts timing out
   ↓
every order retries inventory check
   ↓
inventory service sees 10x normal load
   ↓
cluster goes down
```

해법은 고전적입니다: **서킷 브레이커**. 하류의 오류율이 임계값을 넘으면 캐시된 결과나 기본값으로 단락시킵니다. 요청당 재시도 예산 상한도 함께 둡니다.

서킷 브레이커는 분산 시스템에서 수정 없이 그대로 빌려 올 수 있는 몇 안 되는 멀티 에이전트 실패 완화책입니다.

### 메모리 오염(재방문)

레슨 13에서 봤듯이: 한 에이전트의 환각이 공유 메모리의 사실이 되면, 하류 에이전트들은 오염된 사실 위에서 추론합니다. MAST 용어로는 공유 메모리 계층에서의 검증 공백입니다.

서서히 진행되는 정확도 하락이 증상입니다. 크래시가 나지 않습니다. 근본 원인을 찾기 어려운 느린 표류가 생길 뿐입니다.

완화책: 추가 전용(append-only) 로그, 출처(provenance) 기록, 쓰기 불가능한 검증자. 레슨 13에서 이미 다뤘습니다.

### STRATUS — 실패 탐지를 위한 특화 에이전트

STRATUS(NeurIPS 2025)는 다음을 배치했을 때 완화 성공률이 1.5배 개선된다고 보고합니다:

- **탐지 에이전트.** 증상 패턴을 감시합니다(높은 불일치율, 재시도 급증, 정확도 표류).
- **진단 에이전트.** 증상이 주어지면 MAST 분류 체계에서 가능성 높은 근본 원인을 추론합니다.
- **검증 에이전트.** 완화책이 적용된 뒤 증상이 사라졌는지 확인합니다.

이것은 SRE식 장애 대응을 에이전트 시스템에 적용한 것입니다. 세 역할 모두 특화된 프롬프트를 가진 LLM 에이전트로 구현할 수 있습니다.

### 실패 양상 감사

2026년의 모범 관행은 연 1회(또는 주요 릴리스마다) 실패 양상 감사입니다:

1. **트레이스 표본.** 실제 실행 트레이스 약 1,000개를 수집합니다.
2. **분류.** 각 트레이스의 실패를 MAST + 집단사고 범주에 매핑합니다.
3. **범주별 실패율 계산.** 당신 시스템을 지배하는 범주는 어디인가요?
4. **완화책 순위 매기기.** 어떤 수정이 가장 많은 실패를 없앨까요?
5. **완화책 2~3개 선정.** 구현하고, 다음 분기에 재감사합니다.

구체적인 선택보다 이 규율 자체가 더 중요합니다. 감사가 없으면 실패는 노이즈에 녹아들고 체계적으로 다뤄지지 않습니다.

### 조용히 실패하는 시스템

가장 위험한 실패 범주는 조용한 정확성 실패입니다. 시끄럽게 실패하는 시스템(크래시, 예외, 알림)은 모니터링할 수 있습니다. 그럴듯하지만 틀린 출력을 만드는 시스템은 예외 로그로 탐지할 수 없습니다. 이 때문에 검증 공백은 건수로는 21.30%에 불과하면서도 실패당 비용은 가장 비쌉니다.

여기에 투자하세요:
- 표본 기반 사람 검토.
- 골든 데이터셋 회귀 테스트.
- 중요한 출력에 대한 에이전트 간 교차 검증.

### 실패 vs 느린 실패

어떤 실패는 즉각적이고, 어떤 실패는 느립니다. 즉각적 실패(타임아웃, 스키마 불일치, 인증 오류)는 탐지가 쌉니다. 느린 실패(메모리 오염, 단일문화 표류, 역할 모호성)는 탐지와 예방이 둘 다 비쌉니다.

2026년의 엔지니어링 기법: 느린 실패의 대리 지표(proxy)를 계측해서, 표류가 눈에 보이는 오류가 되기 전에 잡아 내는 것입니다. 합의율, 재시도율, 출력 길이 분포, 연속된 에이전트 버전 간 편집 거리가 모두 유용한 대리 지표입니다.

## 직접 만들기

`code/main.py`는 다음을 구현합니다:

- `FailureTaxonomy` — 시뮬레이션된 장애를 MAST + 집단사고 범주로 분류합니다.
- `CircuitBreaker` — 고전 패턴; 오류율이 임계값을 넘으면 닫힙니다(차단 상태로 전환).
- `RetryStormSimulator` — 연쇄 실패를 보여 주고, 서킷 브레이커를 켜고 끕니다.
- `DetectionAgent` — 스크립트 기반 STRATUS식 증상 매처.

실행:

```
python3 code/main.py
```

예상 출력:
- 서킷 브레이커가 없는 재시도 폭풍: 재고 오류가 폭증합니다(시뮬레이션).
- 서킷 브레이커가 있는 경우: 임계값에서 차단하고, 저하 모드 응답을 제공합니다.
- 탐지 에이전트가 패턴을 표시하고 MAST 범주 이름을 붙입니다.

## 출시하기

프로덕션에서의 실패 양상 규율:

- **분기마다 MAST 감사.** 연 1회가 아닙니다. 시스템이 커지면 범주 분포도 바뀝니다.
- **서킷 브레이커를 모든 곳에.** 의존 서비스로 나가는 모든 호출마다. 기본 차단 임계값은 오류율 5~10%로 둡니다.
- **골든 데이터셋.** 작고, 고품질이고, 사람이 감사한 것. 매주 회귀 테스트를 돌리세요.
- **STRATUS 삼인조.** 탐지 + 진단 + 검증 에이전트가 프로덕션을 감시합니다. 처음에는 탐지 에이전트만으로 시작하고, 증상이 시끄러워지면 진단을 더하세요.
- **실패 예산.** 범주별 실패율에 대한 명시적 SLO. 예산을 초과하면 출시 중지 논의를 시작합니다.

## 연습 문제

1. `code/main.py`를 실행하세요. 서킷 브레이커가 재시도 폭풍을 잠그는지 확인하세요. 실패 임계값을 바꿔 가며 상충 관계를 관찰하세요.
2. **느린 실패 대리 지표**를 구현하세요: 3개 병렬 에이전트의 합의율. 급락하면 알림을 울립니다. 에이전트 출력을 서서히 상관시켜 단일문화 표류를 시뮬레이션해 보세요.
3. Cemri 등(arXiv:2503.13657)을 읽으세요. 그들의 MAS 7종 중 하나를 골라 상위 3개 실패 범주를 매핑하세요. MAST가 예측한 것과 어떻게 비교되나요?
4. 집단사고 논문(arXiv:2508.05687)을 읽으세요. 다섯 패턴 중 프로덕션에서 가장 탐지하기 어려운 것은 무엇인가요? 대리 지표를 하나 제안하세요.
5. 당신이 아는 특정 멀티 에이전트 시스템을 위한 STRATUS식 탐지-진단-검증 삼인조를 설계하세요. 탐지는 어떤 증상을 감시하나요? 진단은 어떤 완화책을 권하나요? 검증은 그것이 효과가 있음을 어떻게 확인하나요?

| 검증 공백 | "아무도 확인 안 함" | 독립적인 검증 없이 출력이 수용됨. |
| 집단사고 계열 | "동질화 실패" | 단일문화, 동조, 결함 있는 ToM, 혼합 동기, 연쇄 실패. |
| 단일문화 붕괴 | "같은 모델, 같은 환각" | 공유된 베이스 모델이나 학습 데이터에서 오는 상관된 오류. |
| 재시도 폭풍 | "연쇄 오류 증폭" | 한 실패가 재시도를 부르고, 재시도가 하류 부하를 증폭. |
| 서킷 브레이커 | "오류율에 빠르게 실패" | 오류율이 임계값을 넘으면 차단; 기본값으로 단락. |
| STRATUS | "장애 대응 삼인조" | 탐지 + 진단 + 검증 에이전트. 완화 성공률 1.5배. |
| 메모리 오염 | "환각의 전파" | 공유 메모리의 사실이 오염됨; 하류 에이전트가 오염 위에서 추론. |
