# 인계와 루틴 — 스테이트리스 오케스트레이션

> OpenAI의 Swarm(2024년 10월)은 멀티 에이전트 오케스트레이션을 두 프리미티브로 압축했습니다: **루틴**(시스템 프롬프트로서의 지침 + 도구)과 **인계(handoff, 다른 Agent를 반환하는 도구)**. 상태 머신도, 분기용 DSL도 없습니다 — LLM이 알맞은 인계 도구를 호출하며 라우팅합니다. OpenAI Agents SDK(2025년 3월)가 프로덕션(운영 환경) 후속격입니다. Swarm 자체는 여전히 가장 깔끔한 개념 참조 자료입니다 — 전체 소스가 몇백 줄 안에 들어가죠. 이 패턴이 퍼진 이유는 API 표면이 대략 "에이전트 = 프롬프트 + 도구, 인계 = 에이전트를 반환하는 함수"이기 때문입니다. 한계: 스테이트리스(무상태)라서 메모리는 호출자의 책임입니다.

**유형:** 학습 + 빌드
**언어:** Python(표준 라이브러리)
**선수 지식:** 페이즈 16 · 04(프리미티브 모델)
**시간:** 약 60분

## 문제

멀티 에이전트 프레임워크들은 모두 자기만의 DSL을 배우라고 합니다: LangGraph의 노드와 엣지, CrewAI의 크루와 태스크, AutoGen의 GroupChat과 매니저 같은 것들. 이 DSL들도 실제로는 쓸모 있는 추상화지만, 일을 필요 이상으로 무겁게 느끼게 만듭니다.

Swarm은 정반대 방향으로 밀어갑니다: 모델이 이미 갖고 있는 도구 호출 능력을 쓰자는 것입니다. 인계는 도구 호출이 됩니다. 오케스트레이터는 지금 대화를 쥐고 있는 에이전트 그 자체입니다. 상태 머신은 에이전트들의 시스템 프롬프트 안에 암묵적으로 존재합니다.

## 개념

### 두 프리미티브

**루틴(routine).** 에이전트의 역할과 사용 가능한 도구를 정의하는 시스템 프롬프트. 범위가 정해진 지침 묶음이라고 생각하세요: "너는 분류(triage) 에이전트다. 사용자가 환불을 묻으면 환불 에이전트에게 인계하라."

**인계(handoff).** 에이전트가 호출할 수 있고 새 Agent 객체를 반환하는 도구. Swarm 런타임은 Agent 반환값을 감지해 다음 턴의 활성 에이전트를 바꿔치기합니다.

이것이 추상화의 전부입니다.

```
def transfer_to_refunds():
    return refund_agent  # Swarm이 Agent 반환을 감지 → 활성 에이전트 전환

triage_agent = Agent(
    name="triage",
    instructions="Route the user to the right specialist.",
    functions=[transfer_to_refunds, transfer_to_sales, transfer_to_support],
)
```

트리아지 에이전트의 시스템 프롬프트가 사용자 메시지를 보고 알맞은 인계를 고르게 만듭니다. 실제 라우팅을 하는 것은 LLM의 도구 호출입니다.

### 왜 퍼졌나

- **작은 API.** 배울 개념이 두 개뿐입니다.
- **모델이 이미 하는 일을 활용.** 도구 호출은 이미 주요 프로바이더 전반에서 프로덕션 등급입니다.
- **상태 머신 부담 없음.** 그래프를 직접 기술하지 않습니다. 에이전트들의 프롬프트가 누구에게 인계하는지 설명합니다.

### 스테이트리스라는 거래

Swarm은 실행(run) 사이에서는 명시적으로 무상태입니다. 프레임워크는 한 실행 동안에만 메시지 기록을 유지하고, 아무것도 영속화하지 않습니다. 메모리, 연속성, 장기 실행 작업 — 전부 호출자의 몫입니다.

프로덕션 후속격인 OpenAI Agents SDK(2025년 3월)에서 바뀐 대표적인 것이 바로 이 부분입니다: SDK는 인계 프리미티브를 유지하면서 내장 세션 관리, 가드레일, 트레이싱을 더합니다.

### Swarm/인계가 어울리는 경우

- **트리아지 패턴.** 최전선 에이전트가 사용자를 전문 에이전트에게 연결합니다.
- **스킬 기반 인계.** "작업에 코드가 필요하면 코더를 호출하고, 조사가 필요하면 리서처를 호출한다."
- **짧고 한정된 대화.** 고객 지원, FAQ→티켓 전환, 단순 워크플로.

### Swarm이 애를 먹는 경우

- **공유 메모리가 있는 긴 세션.** 인계가 일어나면 대화 상태는 새 에이전트의 프롬프트 + 기록으로 리셋됩니다. 호출자가 직접 메모리를 관리하지 않는 한 에이전트 간 영속 상태는 없습니다.
- **병렬 실행.** 인계는 한 번에 하나 — 활성 에이전트가 교체되는 방식입니다. 병렬성이 필요하면 호출자가 여러 Swarm 실행을 직접 오케스트레이션해야 합니다.
- **감사와 재현.** 무상태 실행은 정확히 재현하기 어렵습니다. LLM의 인계 선택이 결정론적이지 않기 때문입니다.

### OpenAI Agents SDK(2025년 3월)

프로덕션 후속격이 추가한 것:

- **세션 상태.** 실행 간에 이어지는 영속 스레드.
- **가드레일.** 입력/출력 검증 훅.
- **트레이싱.** 모든 도구 호출과 인계가 기록됩니다.
- **인계 필터.** 인계 시 어떤 컨텍스트가 넘어가는지 제어합니다.

인계 프리미티브는 그대로 살아 있고, 그 주위에 프로덕션용 편의 기능이 얹힌 모양새입니다.

### Swarm vs GroupChat

둘 다 LLM 주도 라우팅을 쓰지만, **다음을 누가 고르는지**가 다릅니다:

- GroupChat: 셀렉터(함수 또는 LLM)가 바깥에서 다음 발언자를 고릅니다.
- Swarm: 현재 에이전트가 인계 도구를 호출해 자기 후계자를 고릅니다.

Swarm은 "에이전트가 다음을 결정"하고, GroupChat은 "매니저가 다음을 결정"합니다. Swarm의 결정은 활성 에이전트의 도구 호출 안에, GroupChat의 결정은 `GroupChatManager` 안에 있습니다.

## 만들어 보기

`code/main.py`는 Swarm을 처음부터 구현합니다: Agent 데이터클래스, 인계 메커니즘(도구가 Agent를 반환), 그리고 에이전트 교체를 감지하는 실행 루프.

데모: 트리아지 에이전트가 환불, 영업, 지원 전문 에이전트로 라우팅합니다. 각 전문 에이전트는 자기만의 도구를 갖습니다. 실행 루프는 인계가 일어날 때마다 출력합니다.

실행:

```
python3 code/main.py
```

## 활용하기

`outputs/skill-handoff-designer.md`는 주어진 작업에 대한 인계 토폴로지를 설계합니다: 어떤 에이전트들이 존재하는지, 누가 어떤 인계를 호출할 수 있는지, 어떤 컨텍스트가 넘어가는지.

## 출시하기

체크리스트:

- **인계 로깅.** 모든 인계는 from-에이전트, to-에이전트, 컨텍스트 스냅샷을 담은 추적 이벤트를 기록합니다.
- **컨텍스트 이전 규칙.** 인계 시 무엇을 넘길지 정하세요: 전체 기록(비쌈), 최근 N메시지, 또는 요약.
- **인계 가드레일.** 도구 권한이 다른 전문 에이전트로의 인계는 인증을 거쳐야 합니다 — 안 그러면 프롬프트 인젝션으로 원치 않는 인계를 강제당할 수 있습니다.
- **루프 감지.** 두 에이전트가 서로에게 계속 인계하는 것은 흔한 실패 양상입니다. 간단한 최근-K 링 검사로 감지하세요.
- **폴백 에이전트.** 인계 대상이 존재하지 않으면 안전한 기본값으로 폴백하세요.

## 연습 문제

1. `code/main.py`를 실행해 트리아지에서 환불 에이전트로 인계해 보세요. 두 번째 턴의 활성 에이전트가 refund인지 확인하세요.
2. 루프 감지 규칙을 추가해 보세요: 같은 두 에이전트가 3번 연속 인계하면 강제로 종료합니다. 폴백도 함께 설계해 보세요.
3. OpenAI Agents SDK 문서의 인계 필터를 읽어 보세요. "인계 시 요약" 버전을 구현해 보세요: 나가는 에이전트가 들어오는 에이전트에게 넘기기 전에 컨텍스트를 불릿 요약으로 압축합니다.
4. Swarm의 인계를 GroupChatManager 셀렉터와 비교해 보세요. 어느 패턴이 프롬프트 인젝션을 더 악화시키며, 왜 그런가요?
5. Swarm 쿡북(https://developers.openai.com/cookbook/examples/orchestrating_agents)을 읽고, OpenAI Agents SDK가 바꾸었거나 유지한 Swarm의 명시적 설계 결정을 하나 찾아보세요.

## 핵심 용어

| 용어 | 사람들이 말하는 표현 | 실제 의미 |
|------|----------------|------------------------|
| 루틴(Routine) | "에이전트 프롬프트" | 시스템 프롬프트 + 도구 목록. 역할과 사용 가능한 인계를 정의. |
| 인계(Handoff) | "다른 에이전트로 넘기기" | 활성 에이전트가 호출할 수 있고 새 Agent를 반환하는 도구. 런타임이 활성 에이전트를 교체. |
| 스테이트리스(Stateless) | "실행 사이에 메모리 없음" | Swarm은 아무것도 영속화하지 않음. 메모리는 호출자의 책임. |
| 활성 에이전트(active agent) | "지금 말하고 있는 사람" | 현재 대화를 쥐고 있는 에이전트. 인계가 이것을 바꿈. |
| 컨텍스트 이전(context transfer) | "인계 시 무엇이 넘어가나" | 들어오는 에이전트가 볼 기록에 대한 정책: 전체, 최근 N개, 또는 요약. |
| 인계 루프(handoff loop) | "에이전트들이 핑퐁" | 두 에이전트가 서로에게 계속 인계하는 실패 양상. |
| OpenAI Agents SDK | "프로덕션 Swarm" | 2025년 3월 후속격. 인계 프리미티브 위에 세션, 가드레일, 트레이싱 추가. |
| 인계 필터(handoff filter) | "이전 시 관문" | 인계 경계에서 컨텍스트를 검사·수정하는 SDK 기능. |
