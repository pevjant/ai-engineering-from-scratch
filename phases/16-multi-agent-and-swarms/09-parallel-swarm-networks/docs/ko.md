# 병렬 / 스웜 / 네트워크 아키텍처

> 슈퍼바이저와의 대비: 중앙 결정자가 없습니다. 에이전트들이 공유 이벤트 버스를 읽고, 작업을 비동기로 집어 가고, 결과를 되돌려 씁니다. LangGraph는 탈중앙화되고 동적인 환경을 위해 "스웜 아키텍처"를 명시적으로 지원합니다. Matrix(arXiv:2511.21686)는 제어 흐름과 데이터 흐름을 모두 분산 큐를 통해 전달되는 직렬화된 메시지로 표현해서 오케스트레이터 병목을 제거합니다. 트레이드오프는 명확합니다: 확장성을 위해 결정성과 추적성을 내놓는 것. 스웜은 독립적인 서브 문제가 많은 과제에 맞습니다; 하나의 일관된 계획이 필요한 과제에는 맞지 않습니다.

**유형:** 학습 + 빌드
**언어:** Python (표준 라이브러리, `threading`, `queue`)
**선수 지식:** 페이즈 16 · 05(슈퍼바이저 패턴), 페이즈 16 · 04(프리미티브 모델)
**시간:** 약 75분

## 문제

슈퍼바이저는 워커 몇 개까지 확장됩니다. 수백 개라면? 슈퍼바이저 자체가 병목이 됩니다: 누가 무엇을 할지에 대한 모든 결정이 하나의 에이전트로 관통합니다. 느린 계획 단계 하나가 시스템 전체를 멈추게 하죠.

스웜 아키텍처는 설계를 뒤집습니다. 중앙 플래너가 일을 배급하는 대신, 워커들이 공유 큐에서 작업을 집어 갑니다. "조율"은 이벤트 버스의 의미론에 구워져 있죠. 오케스트레이터가 없습니다; 시스템은 큐가 감당하는 한계까지 확장합니다.

## 개념

### 모양새

```
                ┌──── shared queue ────┐
                │                      │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     Worker  Worker  Worker   Worker
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            results pool
```

오케스트레이터가 없습니다. 각 워커는 이걸 반복합니다: 태스크를 꺼내고, 처리하고, 결과를 쓴다(그리고 선택적으로 후속 작업을 큐에 넣는다).

### 스웜이 맞을 때

- **독립적인 태스크가 많을 때.** 스크래핑, 변환, 분류. 태스크들이 서로 의존하지 않습니다.
- **소요 시간이 들쭉날쭉한 작업.** 어떤 태스크는 100ms, 어떤 태스크는 10초가 걸린다면, 스웜은 부하를 자동으로 균형 잡습니다 — 빠른 워커가 다음 작업을 집어 가니까요. 슈퍼바이저는 소요 시간을 미리 예측해야 합니다.
- **결정성보다 처리량.** 엄격한 순서가 아니라 총 완료 시간이 중요할 때입니다.

### 스웜이 실패할 때

- **순서가 있는 워크플로.** 3단계가 2단계의 출력을 필요로 한다면, 스웜은 2단계가 끝나기 전에 3단계가 발화하는 위험을 안고 있습니다.
- **전역 계획이 필요한 과제.** 복잡한 리서치 질문은 플래너의 이득을 봅니다. 리서처들의 스웜은 일관된 보고서가 아니라 산발적인 사실들을 만들어 냅니다.
- **디버깅.** 중앙 로그가 없고 작업이 비동기라서, 버그를 재현하는 데 비용이 큽니다.

### Matrix (arXiv:2511.21686)

Matrix는 스웜을 자연스러운 결론까지 밀어붙인 2025년 논문입니다: 제어 흐름과 데이터 흐름이 둘 다 분산 큐 위의 직렬화된 메시지입니다. 중앙 조율자가 없습니다. 내결함성은 메시지 내구성에서 옵니다. 확장성은 시스템의 문제가 아니라 메시지 브로커의 문제죠.

기여: 멀티 에이전트 조율을 "슈퍼바이저가 다음에 어떤 에이전트를 고르는가?"가 아니라 "이 에이전트는 어떤 메시지 토픽을 구독하는가?"로 바꾼 프로그래밍 모델입니다. 시스템이 pub/sub 이벤트 메시처럼 보이게 만들죠.

### 그래프 프레임워크 안의 스웜

LangGraph 2025 문서는 "스웜 아키텍처"를 멀티 에이전트 패턴 중 하나로 명시적으로 기술합니다: 에이전트들이 노드이되, 엣지가 사이클을 허용하는 방향 그래프를 이루고 어떤 노드든 풀에서 활성화될 수 있습니다. 워커는 슈퍼바이저 배정이 아니라 조건에 따라 가용한 작업을 고릅니다.

### 실패 양상: 기아(starvation)와 핫스팟

모든 워커가 가장 빨리 처리 가능한 태스크만 집어 가면, 오래 걸리는 태스크는 마지막 하나만 남을 때까지 영영 선택되지 않습니다. 전형적인 큐 기아입니다.

완화책:
- 명시적인 에이징(대기 시간에 따라 우선순위 상승)이 있는 우선순위 큐.
- 워커 전문화: 일부 워커는 "오래 걸리는" 태스크만 맡습니다.
- 백프레셔(back-pressure): 큐에 빠른 태스크가 들어오는 양을 제한합니다.

### 콘텐츠 기반 라우팅과의 연결

스웜은 콘텐츠 기반 라우팅(레슨 22)과 자연스럽게 짝이 됩니다. 범용 큐 하나 대신 메시지 타입마다 큐를 하나 두세요. 전문 워커들이 자기 타입만 구독합니다. 수천 개 에이전트로 확장되는 메시지 버스 아키텍처의 기반입니다.

## 만들기

`code/main.py`는 공유 `queue.Queue`에서 작업을 가져가는 4개 워커 스레드의 스웜을 구현합니다. 태스크는 소요 시간이 들쭉날쭉합니다(빠른 것과 느린 것). 데모는 이렇게 대조합니다:

- **순차 베이스라인:** 워커 하나가 모든 태스크를 직렬로 처리.
- **고정 배정:** 각 태스크가 특정 워커에 미리 배정됨(슈퍼바이저 스타일).
- **스웜:** 워커들이 공유 큐에서 작업을 가져감.

스웜은 부하를 자동으로 균형 잡습니다; 고정 배정은 배정된 태스크가 느릴 때 빠른 워커를 놀리게 둡니다.

실행:

```
python3 code/main.py
```

출력에는 워커별 태스크 수(스웜은 고르지 않지만 최적으로 분배함)와 실제 걸린 시간이 나타납니다.

## 사용하기

`outputs/skill-swarm-fit.md`는 과제가 스웜과 슈퍼바이저 중 무엇을 써야 하는지 평가합니다. 입력: 태스크 독립성, 소요 시간 분산, 순서 요구사항, 디버깅 용이성 요구.

## 출시하기

체크리스트:

- **에이징이 있는 우선순위 큐.** 오래 걸리는 태스크의 기아를 막습니다.
- **워커 멱등성.** 워커가 실행 도중 죽으면 태스크가 두 번 이상 꺼내질 수 있습니다. 워커는 멱등해야 합니다.
- **내구성 있는 큐.** 프로덕션에서는 Kafka, Redis Streams, 또는 데이터베이스 기반 큐를 쓰세요. `queue.Queue`는 인메모리일 뿐입니다.
- **태스크별 관측 가능성.** 모든 태스크에 트레이스 ID가 있고; 모든 워커가 시작/종료를 그 ID로 기록합니다.
- **백프레셔.** 큐가 워커가 비우는 속도보다 빠게 불어나면, 생산자를 늦추세요.

## 연습 문제

1. `code/main.py`를 실행해 보세요. 소요 시간이 들쭉날쭉한 워크로드에서 스웜이 순차보다 얼마나 빠른가요? 고정 배정보다는 얼마나 빠른가요?
2. 우선순위 큐 변형을 추가해 보세요(`queue.PriorityQueue` 사용). 태스크의 "중요도" 필드로 우선순위를 매기세요. 지속적인 부하에서 저우선순위 태스크가 기아에 빠지는지 관찰하세요.
3. 핫스팟 감지기를 구현해 보세요: 어떤 워커가 가장 느린 워커보다 3배 많은 태스크를 처리하면 기록합니다. 그게 태스크 소요 시간 분포에 대해 무엇을 말해 주나요?
4. Matrix 논문(arXiv:2511.21686)의 초록과 3장을 읽어 보세요. Matrix가 수용하는 구체적인 트레이드오프 하나(확장성 이득)와 포기하는 것 하나(추적성, 결정성)를 찾으세요.
5. 스웜 데모를 (task_type, payload) 튜플의 `queue.Queue`로 바꾸고, 워커들이 특정 타입만 구독하게 해 보세요. 태스크가 이질적일 때 어떤 라우팅 규칙이 타당할까요?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| Swarm architecture | "탈중앙화 에이전트" | 워커들이 공유 큐에서 가져옴; 중앙 오케스트레이터 없음. |
| Event bus | "에이전트들이 토픽을 구독" | 타입이나 내용에 따라 태스크를 워커에게 라우팅하는 메시지 브로커. |
| Starvation | "태스크가 영영 안 돎" | 더 높은 우선순위 작업이 계속 밀려와서 저우선순위 태스크가 영영 선택되지 않음. |
| Hot-spotting | "워커 하나가 익사함" | 한 워커에 태스크가 몰리는 부하 불균형. |
| Back-pressure | "생산자를 늦춰라" | 큐가 차면 상류에 생산을 멈추라고 신호하는 메커니즘. |
| Idempotent worker | "다시 돌려도 안전" | 태스크를 두 번 처리해도 같은 결과. 워커가 실행 도중 죽을 수 있으므로 필수. |
| Durable queue | "크래시에서 살아남음" | 디스크나 복제 저장소에 백업된 큐; 워커가 죽어도 태스크가 유실되지 않음. |
| Matrix framework | "풀 메시지 패싱 스웜" | 데이터 흐름과 제어 흐름이 둘 다 분산 큐 위의 직렬화된 메시지. |
