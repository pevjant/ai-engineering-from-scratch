제안된 멀티 에이전트 시스템 설계가 주어지면, 가장 가까운 대표 2026 케이스 스터디를 골라 적응시킵니다.

다음을 산출합니다:

1. **설계 지문(fingerprint).** 태스크 유형(리서치 / 엔지니어링 / 인구 규모 / 자동화), 에이전트 수, 검증 요건, 런타임 소요 시간, 역할 구별도, 사용자 대면 네트워크 노출도.
2. **가장 가까운 케이스 스터디.**
   - **Anthropic Research**: 리서치 또는 지식 검색 태스크, 검증이 필수, 몇 시간짜리 실행, 에이전트들이 주로 컨텍스트와 범위로 구별되는 경우(새 컨텍스트 서브에이전트가 유리).
   - **MetaGPT / ChatDev**: 엔지니어링 또는 구조화된 워크플로, 역할이 명확히 구별됨(기획자 / 코더 / 리뷰어 / 테스터), 인계 산출물의 타입이 잘 정의된 경우.
   - **OpenClaw / Moltbook**: 인구 규모, 사용자 대면 에이전트 네트워크, 프롬프트 인젝션이 실질적 위협, 창발 경제가 중요한 경우.
3. **베낄 패턴.** 선택된 케이스 스터디에서 적용 가능한 구체적 설계 결정: 새 컨텍스트 서브에이전트, 레인보우 배포, 커뮤니케이티브 탈환각, DAG 라우팅, 쓰기 불가능한 검증자, 기반(substrate) 수준 보안.
4. **프레임워크 추천.** LangGraph, CrewAI, AG2, Microsoft Agent Framework, OpenAI Agents SDK, Google ADK, Anthropic Claude Agent SDK, 또는 자체 구현. 기본값은 그 케이스 스터디가 흔히 쓰는 프레임워크; 특정 설계에 더 맞는 것이 있으면 밝히세요.
5. **그 사례의 안티패턴.** 참조 사례가 "통하지 않는다"고 확인한 것들. 새 설계에서 피하세요.
6. **비용 추정.** 예상 토큰 배수(Anthropic Research: 약 15배; MetaGPT: 약 5배; OpenClaw: 네트워크 효과에 좌우). 예상 실제 소요 시간과 달러 비용 범위.
7. **평가 접근.** 어느 벤치마크(MARBLE, SWE-bench Pro, 내부)가 관련 있는지; 케이스 스터디 베이스라인 대비 어느 정도의 차이를 목표로 하는 것이 합리적인지.

하드 리젝(무조건 거부) 기준:

- 태스크에 정확성 요건이 있는데 검증을 무시하는 설계. 모든 케이스 스터디는 검증 세금을 냅니다.
- 프롬프트 인젝션을 공격 표면으로 인정하지 않으면서 새로운 기반(substrate)을 주장하는 설계. OpenClaw/Moltbook 사례는 이것이 가설이 아니라 프로덕션 관심사임을 보여 줍니다.
- 어떤 케이스 스터디에도 매핑되지 않는 "혁명적" 주장. 멀티 에이전트는 2024년부터 프로덕션에 있었습니다; 새로운 주장에는 명시적인 비교가 필요합니다.
- 정당화 없이 MCP나 A2A 채택을 건너뛰는 설계. 프로토콜 지원은 기본 요양(table stakes)입니다.

거부 규칙:

- 설계에 명확한 태스크 유형이 없으면, 케이스 스터디를 고르기 전에 태스크 범위 잡기를 권하세요. "만능 멀티 에이전트"는 설계가 아닙니다.
- 설계가 프로덕션 준비를 주장하지만 실패 양상 감사가 없다면, 참조 매핑 전에 MAST식 감사(레슨 23)를 권하세요.
- 설계가 순수하게 실험적/연구용이라면, 어떤 케이스 스터디의 프로덕션 패턴을 채택하기 전에 어느 부분을 강화해야 하는지 밝히세요.

출력: 두 페이지 분량의 브리프. 한 문장 요약으로 시작하세요("가장 가까운 케이스 스터디: MetaGPT / ChatDev. 역할-SOP 분해, 커뮤니케이티브 탈환각, 구조화된 인계 산출물을 채택하고 CrewAI 또는 자체 구현을 사용."), 그다음 위의 7개 섹션을 이어서 작성합니다. 마지막에 90일 적응 계획(참조에서 베낄 것, 커스터마이즈할 것, 벤치마크로 검증할 것)을 덧붙입니다.
