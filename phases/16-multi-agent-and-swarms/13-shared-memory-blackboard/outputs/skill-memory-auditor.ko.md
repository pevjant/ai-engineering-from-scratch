멀티 에이전트 코드베이스나 아키텍처 문서가 주어지면, 공유 메모리 설계를 감사하고 메모리 오염(memory poisoning)에 대한 노출에 깃발을 꽂습니다.

산출물:

1. **토폴로지.** 전체 메시지 풀, 토픽 분할 블랙보드, 에이전트별 프로젝션 뷰, 아니면 하이브리드인가? 데이터 구조(리스트, 딕셔너리, pandas 프레임, 벡터 저장소, SQL 테이블)의 이름을 밝히세요. 안정 상태(steady state)에서의 쓰기·읽기 주체 수 대략 상한을 세어 보세요.
2. **출처(provenance) 필드.** 모든 쓰기에서 항목이 다음을 기록하는가: 작성자 id, 타임스탬프, 프롬프트 해시 또는 프롬프트 텍스트, 도구 호출 추적, 출처 URI 또는 도구 이름? 있는 필드와 빠진 필드를 나열하세요.
3. **갱신 모델.** 로그가 추가 전용(append-only)인가, 아니면 쓰기 주체가 제자리에서 수정하는가? 수정한다면 동시성 제어 메커니즘이 무엇인가(락, 낙관적 버저닝, 없음)? 정정은 제자리 편집이 아니라 대체(supersession) 항목이어야 합니다 — 그렇게 하지 않는 설계에는 깃발을 꽂으세요.
4. **검증자 분리.** 독자적인 출처 접근 권한을 가진 읽기 전용 에이전트가 있는가? 메인 풀에 쓸 수 있는가(쓸 수 없어야 함)? 검증자의 출력은 어디로 가는가?
5. **프로젝션 스키마.** 설계가 프로젝션(LangGraph 리듀서, 블랙보드 토픽, 역할 범위 뷰)을 쓴다면, 스키마가 문서화되어 있는가? 새 에이전트는 자신이 소비할 프로젝션을 어떻게 선언하는가?
6. **오염 위험 점수.** 각 축을 1~5점으로 평가합니다: [출처 완전성], [수정보다 대체], [검증자 독립성], [프로젝션 스키마 명확성]. 어떤 축에서든 3점 미만인 시스템에는 깃발을 꽂습니다.

하드 리젝(무조건 거부):

- 빠진 검증자에 깃발을 꽂지 않는 감사. 독자적인 출처 접근 권한을 가진 쓸 수 없는(unwritable) 검증자가 바로 버틸 수 있는 핵심 완화책입니다. 이것 없이는 나머지 완화책은 모두 장식입니다.
- "테스트를 더 추가하라"고 권하는 감사. 테스트는 메모리 오염을 잡지 못합니다. 오염은 테스트를 통과할 만큼 그럴듯한 출력을 만들어 내기 때문입니다.
- 콘텐츠 해싱을 유일한 출처 추적으로 권하는 감사. 해시는 *무엇이* 쓰였는지 알려 주지만, *누가*, *어디서부터* 썼는지는 알려 주지 않습니다.

거부 규칙:

- 코드베이스가 공유 상태를 외부 서비스(Redis, Postgres, 벡터 DB)에 숨기고 점검 도구가 없다면, 프로덕션 읽기 권한 없이는 감사를 완료할 수 없다고 명시하세요.
- 시스템의 에이전트가 셋보다 적다면, 메모리 오염 위험은 낮지만 출처 추적은 여전히 값싼 보험이라고 적어 두세요.
- 시스템이 내장 상태 관리를 갖춘 프레임워크(LangGraph 체크포인터, AutoGen 풀)를 쓴다면, 보장을 다시 유도해 내지 말고 프레임워크의 보장 자체를 감사하세요.

출력: 두 페이지짜리 보고서. 한 문장 요약으로 시작합니다("공유 상태는 출처 추적도 검증자도 없는 전체 메시지 풀 — 오염 위험 높음." 식으로). 그다음 위의 여섯 섹션을 담습니다. 마지막으로 우선순위가 매겨진 행동 목록으로 끝냅니다: 세 가지 변경, 각각 [critical] [should] 또는 [nice-to-have] 라벨과 예상 구현 시간을 붙입니다.
