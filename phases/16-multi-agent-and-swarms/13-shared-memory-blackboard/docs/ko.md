# 공유 메모리와 블랙보드 패턴

> 2026년 멀티 에이전트 시스템에는 두 가지 접근이 공존합니다: **메시지 풀**(모두가 모두의 메시지를 봅니다 — AutoGen GroupChat이나 MetaGPT처럼)과 **구독 기반 블랙보드**(에이전트가 관련 이벤트를 구독합니다 — Context-Aware MCP나 Matrix 프레임워크처럼). 이 둘은 멀티 에이전트 시스템에서 유일하게 상태를 지니는 부분이며, 그렇기 때문에 흥미로운 버그들이 모두 여기서 생겨납니다. 대표적인 실패 양상은 **메모리 오염(memory poisoning)**입니다. 한 에이전트가 "사실" 하나를 환각으로 만들면, 다른 에이전트들은 그것을 검증된 사실로 받아들이고, 정확도가 즉각적인 크래시보다 훨씬 디버깅하기 어려운 방식으로 서서히 무너집니다. 이 레슨은 두 구조를 표준 라이브러리만으로 만들어 보고, 오염 공격을 주입한 뒤, 프로덕션(운영 환경)에서 실제로 통하는 세 가지 완화책을 보여 줍니다.

**유형:** 학습 + 빌드
**언어:** Python(표준 라이브러리, `threading`)
**선수 지식:** 페이즈 16 · 04(프리미티브 모델), 페이즈 16 · 09(병렬 스웜 네트워크)
**시간:** 약 75분

## 문제

멀티 에이전트 시스템에는 에이전트들이 사실을 공유할 장소가 필요합니다. 문자 그대로의 선택지 하나는 "모든 것을 메시지로 전달한다"입니다 — 하지만 이건 공유 상태를 복사 비용을 추가하면서 다시 발명하는 셈입니다. 또 하나는 "모두에게 전역 로그를 준다"입니다 — 하지만 전역 로그는 무한히 커지고 쉽게 오염됩니다. 세 번째는 "에이전트마다 뷰를 투영한다"입니다 — 확장성은 좋지만 스키마 설계 부담이 큽니다.

에이전트 하나가 환각을 일으켜 그 환각을 공유 상태에 써 넣으면, 그 상태를 읽는 모든 다운스트림 에이전트가 그 환각을 사실로 받아들입니다. 사람이 문제를 알아차릴 때쯤이면 추론 사슬은 다섯 걸음이나 깊어져 있고, 근본 원인은 처음에 쓰인 세 번째 메시지입니다. 멀티 에이전트 정확도 저하의 디버깅은 크래시 디버깅보다 어렵습니다.

이것이 메모리 오염입니다. MAST 분류 체계(Cemri et al., arXiv:2503.13657)에서 두 번째로 많이 기록된 실패 계열이며, 구조적인 문제입니다. 출처(provenance) 추적과 쓸 수 없는 검증자가 없는 공유 메모리 설계는 결국 언젠가 이 문제를 겪습니다.

## 개념

### 두 가지 주요 토폴로지

**전체 메시지 풀.** 모든 에이전트가 모든 메시지를 읽습니다. AutoGen GroupChat과 MetaGPT가 이 방식입니다. 단순하고, 투명하고, 들여다보기 쉽지만, 에이전트 10개를 넘기면 확장되지 않습니다. 각 에이전트의 컨텍스트가 다른 에이전트의 작업물로 가득 차 버리기 때문입니다.

```
agent-A ──write──▶ ┌────────────────┐ ◀──read── agent-D
                   │ 메시지 풀      │
agent-B ──write──▶ │                │ ◀──read── agent-E
                   │ (전역 로그)    │
agent-C ──write──▶ └────────────────┘ ◀──read── agent-F
```

**구독 기반 블랙보드.** 에이전트가 관심 있는 토픽을 선언하면, 기반 판(base)이 관련 메시지만 라우팅해 줍니다. CA-MCP(arXiv:2601.11595)와 Matrix 탈중앙화 프레임워크(arXiv:2511.21686)가 이 방식입니다. 더 멀리 확장되지만, 구독이 의미 있으려면 미리 스키마 설계가 필요합니다.

```
                   ┌─ 토픽: prices ──┐
agent-A ──pub────▶ │                 │ ──▶ agent-D (구독 중)
                   ├─ 토픽: orders ──┤
agent-B ──pub────▶ │                 │ ──▶ agent-E (구독 중)
                   ├─ 토픽: alerts ──┤
agent-C ──pub────▶ │                 │ ──▶ agent-F (구독 중)
                   └─────────────────┘
```

### 어느 쪽이 이기는 경우

- **전체 풀**은 에이전트 수가 적고(10개 미만), 이기종이며, 대화가 짧은 기간일 때 유리합니다. 모두가 모든 것을 보면 누가 뭘 말했는지 따지는 것은 아주 쉽습니다.
- **블랙보드**는 에이전트가 많고, 역할은 같지만 인스턴스는 많으며(스웜), 대화가 오래 이어질 때 유리합니다. 라우팅이 토큰 비용과 컨텍스트 오염을 줄여 줍니다.

프로덕션 시스템은 흔히 섞어 씁니다: 위쪽에 작은 전체 풀(계획 계층), 아래에 블랙보드들(작업자 계층).

### 메모리 오염, 한 가지 시나리오

세 에이전트가 조사 작업을 합니다. 에이전트 A는 검색 에이전트, 에이전트 B는 요약 에이전트, 에이전트 C는 분석 에이전트입니다.

1. A가 페이지를 가져와 공유 상태에 메시지를 씁니다: "그 연구는 정확도가 42% 개선됐다고 보고한다."
2. 실제로 그 페이지는 "4.2% 개선"이라고 쓰고 있었습니다. A가 소수점을 환각으로 만든 것이죠.
3. B가 공유 상태를 읽고 씁니다: "큰 폭의 42% 정확도 향상이 보고됨(출처: A)."
4. C가 공유 상태를 읽고 씁니다: "도입을 권고 — 42% 상승은 혁신적이다."
5. 최종 보고서는 한 번도 존재하지 않은 42%라는 숫자를 인용합니다.

어떤 에이전트도 크래시하지 않았습니다. 어떤 테스트도 실패하지 않았습니다. 시스템은 "잘 동작"했습니다. 환각은 한 에이전트의 컨텍스트에서 공유 상태를 타고 모든 다운스트림 에이전트의 추론으로 스며들었습니다.

### 왜 구조적인 문제인가

공유 상태가 없다면, 에이전트 A의 환각은 A의 컨텍스트에 머뭅니다. 다운스트림 에이전트들은 다시 자료를 가져오거나 스스로 도출하다가 오류를 잡아낼 수도 있습니다. 순진한 공유 상태에서는 A의 컨텍스트가 모두의 컨텍스트가 되고, 환각은 사실로 세탁됩니다.

문제는 공유 상태 자체가 아닙니다 — 출처 추적과 독립적인 검증자 없이 공유하는 상태가 문제입니다. 이를 다루는 완화책 셋:

1. **모든 쓰기에 출처를 붙인다.** 공유 상태의 모든 항목은 누가 썼는지, 언제, 어떤 프롬프트로, 그리고 (해당하면) 에이전트가 어떤 출처를 인용했는지를 기록합니다. 다운스트림 에이전트는 출처에 맞춰 회의적인 태도로 읽습니다.
2. **쓰기에 버전을 매기고 추가 전용(append-only)으로 다룬다.** 정정은 기존 항목을 대체하는 새 항목이며, 제자리 수정이 아닙니다. 감사 추적이 보존됩니다.
3. **공유 상태에 쓸 수 없는 에이전트를 최소 하나 둔다.** 읽기 전용 검증자 에이전트가 항목을 샘플링하고, 출처를 다시 가져오고, 불일치에 깃발을 꽂습니다. 풀에 쓸 수 없기 때문에 풀에 의해 오염될 수도 없습니다.

### 블랙보드의 선례(Hayes-Roth, 1985)

블랙보드 패턴은 LLM 에이전트보다 40년 앞선 것입니다. Hayes-Roth(1985, "A Blackboard Architecture for Control")는 전역 블랙보드를 관찰하고 부분 해를 기여하며 다른 지식 원천을 트리거하는 전문가 지식 원천(Knowledge Source)들을 묘사했습니다. 2026년의 블랙보드(CA-MCP, Matrix)는 같은 패턴에, 지식 원천을 LLM 에이전트로, 부분 해를 JSON 덩어리로 바꾼 것입니다. 쓰기 경합, 기회주의적 제어, 일관성에 대한 해법은 옛 문헌에 이미 기록되어 있고, 현대 시스템들은 이를 다시 발견하고 있습니다.

### 프로젝션 vs 전체 뷰

순수한 블랙보드는 모든 구독자에게 같은 프로젝션(토픽 범위)을 줍니다. 더 공격적인 설계는 **에이전트별 프로젝션**입니다. 각 에이전트가 자기 역할에 맞춰 개인화된 뷰를 받습니다. LangGraph의 상태 리듀서(state reducer)가 2026년의 대표적인 구현입니다 — 리듀서 함수가 전역 상태를 역할별 슬라이스로 접어 줍니다.

에이전트별 프로젝션은 더 멀리 확장되지만 스키마가 필요합니다. 없다면 매 에이전트의 프롬프트 안에 임기응변식 프로젝션을 다시 만들게 됩니다.

### 쓰기 경합 패턴

여러 에이전트가 동시에 쓰는 것은 단순한 LLM 문제가 아니라 동시성 문제입니다. 통하는 패턴 셋:

- **순차 기록자(단일 생산자).** 모든 쓰기가 직렬화해 주는 하나의 코디네이터 에이전트를 거칩니다. 단순하지만 병목입니다.
- **버저닝이 있는 낙관적 동시성.** 각 항목에 버전이 있고, 쓰기는 버전 불일치 시 실패 후 재시도합니다. 고전적인 데이터베이스 기법입니다.
- **토픽 분할.** 서로 다른 에이전트가 서로 다른 토픽을 소유합니다. 토픽 간 경합이 없습니다. 설계된 분할 경계가 필요합니다.

2026년 대부분의 프레임워크는 순차 기록자를 기본값으로 둡니다. LLM 호출이 충분히 느려서 경합이 드물고 병목이 체감되지 않기 때문입니다.

### 쓸 수 없는 검증자

가장 중요한 완화책은 읽기 전용 검증자입니다. 구현 규칙:

- 검증자는 팀과 상태를 공유합니다(블랙보드나 풀을 읽음).
- 검증자는 공유 상태에 대한 쓰기 핸들이 없습니다 — 별도의 검증 채널에만 씁니다.
- 검증자는 쓰기에 인용된 출처를 독자적으로 다시 가져옵니다. 불일치에 깃발을 꽂습니다.
- 검증자 자신의 출력은 사람이나 별도의 의사 결정 에이전트로 라우팅되며, 절대 풀로 되먹이지 않습니다.

이 분리가 없으면 검증자의 출력이 풀의 새 항목이 되고, 오염된 풀은 검증자를 오염시키고, 오염된 검증자는 자기 검증 결과마저 오염시킵니다.

```figure
swarm-blackboard
```

## 만들어 보기

`code/main.py`는 두 토폴로지를 표준 라이브러리 파이썬으로 구현하고, 장난감 수준의 오염 공격과 세 가지 완화책을 함께 담습니다.

- `MessagePool` — 전체 읽기를 지원하는 스레드 안전한 추가 전용(append-only) 로그.
- `Blackboard` — 에이전트별 구독이 있는 토픽 키 방식 pub/sub.
- `ProvenanceEntry` — 모든 쓰기가 (writer, timestamp, prompt_hash, source_uri)를 기록.
- `PoisoningScenario` — 에이전트 A가 소수점을 환각으로 만드는 세 에이전트 조사 작업을 실행. 최종 보고서를 출력.
- `Verifier` — 출처를 다시 가져오고 불일치에 깃발을 꽂는 읽기 전용 에이전트. 검증자가 있는 상태로 같은 시나리오를 실행.

실행:

```
python3 code/main.py
```

예상 출력:
- 실행 1(검증자 없음): 환각된 42%가 최종 보고서까지 전파됩니다.
- 실행 2(검증자 있음): 검증자가 불일치에 깃발을 꽂고, 풀에 "flagged" 라벨이 붙으며, 최종 보고서에 정정이 포함됩니다.

## 출시하기

공유 메모리 설계라면 무엇이든:

- 모든 쓰기에 출처를 기록합니다: `(writer, timestamp, prompt_hash, tool_calls_cited, source_uri)`.
- 로그는 추가 전용으로 만듭니다. 정정은 대상 항목을 참조하는 새 항목입니다.
- 독자적인 출처 접근 권한을 가진 읽기 전용 검증자 에이전트를 최소 하나 배포합니다.
- 검증자의 출력은 별도 채널로 라우팅하고, 공유 풀로 되돌리지 않습니다.
- 쓰기 중 대체(supersession) 비율을 기록합니다 — 이 비율이 오르면 환각 패턴의 초기 신호입니다.

|------|----------------|------------------------|
| 메시지 풀(message pool) | "공유 채팅 기록" | 모든 에이전트가 읽는 추가 전용 로그. 완전한 투명성, 나쁜 확장성. |
| 블랙보드(blackboard) | "공유 작업 공간" | 토픽 키 방식 pub/sub. 에이전트가 관련 토픽을 구독. 더 멀리 확장됨. |
| 출처(provenance) | "누가 뭘 썼나" | 각 쓰기의 메타데이터: 작성자, 시각, 프롬프트, 출처. |
| 메모리 오염(memory poisoning) | "환각이 퍼짐" | 한 에이전트의 오류가 공유 상태에 들어가고, 다운스트림 에이전트가 이를 사실로 받아들임. |
| 추가 전용(append-only) | "제자리 수정 없음" | 정정은 기존 항목을 대체하는 새 항목. 감사 추적이 보존됨. |
| 쓸 수 없는 검증자(unwritable verifier) | "독립 감사관" | 출처를 다시 가져오고 불일치에 깃발을 꽂는 읽기 전용 에이전트. |
| 프로젝션(projection) | "범위를 좁힌 뷰" | 전역 상태에서 계산한 에이전트별 뷰. LangGraph 리듀서가 대표 사례. |
| 지식 원천(Knowledge Source) | "전문가 에이전트" | 블랙보드 참여자를 이르는 Hayes-Roth의 1985년 용어. |
