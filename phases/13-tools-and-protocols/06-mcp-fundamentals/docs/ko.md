# MCP 기초: 무상태 요청과 JSON-RPC

> 현대 MCP에는 핸드셰이크도 프로토콜 세션도 없습니다. 각 요청은 스스로 이해되고, 인가되고, 라우팅되고, 재시도될 만큼 충분한 메타데이터를 실어야 합니다.

**유형:** Learn(학습)
**언어:** Python
**선수 지식:** 페이즈 13, 레슨 01~05
**시간:** 약 55분

## 학습 목표

- MCP의 서버 원시 기능(primitive)과 클라이언트 쪽 기능을 구분할 수 있습니다.
- MCP `2026-07-28`용 유효한 JSON-RPC 2.0 요청과 응답을 만들 수 있습니다.
- 모든 요청에 프로토콜 버전, 클라이언트 기능, 클라이언트 신원을 붙일 수 있습니다.
- 핸드셰이크 없이 `server/discover`를 사용하고 `UnsupportedProtocolVersionError`를 처리할 수 있습니다.
- 하나의 독립적인 요청을 검증부터 완전한 결과까지 추적할 수 있습니다.

## 문제

MCP 서버는 서로 다른 클라이언트의 연속된 두 요청을, 서로 다른 기능을 실은 채, 같은 프로세스나 HTTP 워커에서 받을 수 있습니다. 서버가 이전 요청이 선언한 것을 기억하고 있다면 잘못된 권한을 적용하거나 잘못된 와이어 형태를 돌려줄 수 있습니다.

MCP `2026-07-28`은 이 모호함을 제거합니다. 프로토콜 코어는 무상태(stateless)입니다. 서버는 연결 이력이 아니라 현재 요청만 보고 현재 요청을 어떻게 처리할지 결정해야 합니다.

이것은 정신 모델을 바꿉니다. 낡은 순서는 연결 먼저, 핸드셰이크 둘째, 작업 셋째였습니다. 현대의 순서는 더 단순합니다.

1. 클라이언트가 자기 기술적(self-describing) 요청을 보냅니다.
2. 서버가 그 요청의 버전과 기능을 검증합니다.
3. 서버가 메서드를 처리합니다.
4. 서버가 타입화된 결과 또는 JSON-RPC 에러를 돌려줍니다.

다음 요청은 같은 과정을 처음부터 반복합니다.

## 개념

### 서버 원시 기능

MCP 서버는 세 가지 주요 원시 기능을 노출합니다.

1. **도구(Tools)**는 모델이 통제하는 행동입니다. `tools/list`로 찾아보고 `tools/call`로 호출합니다.
2. **리소스(Resources)**는 URI로 주소가 매겨진 데이터입니다. `resources/list`로 찾아보고 `resources/read`로 가져옵니다.
3. **프롬프트(Prompts)**는 재사용 가능한 템플릿입니다. `prompts/list`로 찾아보고 `prompts/get`으로 렌더링합니다.

루트(roots), 샘플링, 로깅은 호환성을 위해 `2026-07-28` 스키마에 남아 있지만 지원 중단(deprecated) 상태입니다. 새 구현은 루트에는 명시적인 도구 또는 리소스 입력을, 샘플링에는 모델 프로바이더 API를 직접, 로깅에는 stderr나 OpenTelemetry를 써야 합니다. 일라시테이션(elicitation)은 다중 왕복 요청(Multi Round-Trip Requests)으로 계속 사용할 수 있는데, 이 경우 서버가 입력 요청을 돌려주고 클라이언트가 원래 작업을 재시도합니다. 현대의 서버는 독립적인 JSON-RPC 요청을 절대 시작하지 않습니다.

### JSON-RPC 봉투

MCP는 JSON-RPC 2.0을 씁니다.

- 요청: `{jsonrpc, id, method, params}`
- 응답: `{jsonrpc, id, result}` 또는 `{jsonrpc, id, error}`
- 알림(notification): `id` 없는 `{jsonrpc, method, params}`

요청 `id`는 하나의 응답을 상관관계로 묶을 뿐입니다. 프로토콜 세션을 만들지 않습니다.

### 필수 요청 메타데이터

모든 현대 요청은 `params` 안에 `_meta` 객체를 실어 옵니다.

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {
        "name": "course-client",
        "version": "1.0.0"
      }
    }
  }
}
```

프로토콜 버전과 클라이언트 기능은 필수입니다. 클라이언트 신원은 권장입니다. 자기 보고형 표시 및 디버깅 데이터일 뿐, 보안 자격 증명이 아닙니다.

서버는 이 값들을 이전 요청, stdio 프로세스, HTTP 연결, 또는 전송 헤더만으로 추론해서는 안 됩니다.

### 완전한 결과와 서버 신원

성공하는 모든 현대 결과에는 `resultType`이 들어 있습니다. 정상적인 최종 결과는 `"complete"`를 씁니다. 서버는 결과 메타데이터에서 자기 신원도 밝혀야 합니다.

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "resultType": "complete",
    "tools": [],
    "ttlMs": 30000,
    "cacheScope": "public",
    "_meta": {
      "io.modelcontextprotocol/serverInfo": {
        "name": "notes-server",
        "version": "1.0.0"
      }
    }
  }
}
```

`tools/list`, `resources/list`, `prompts/list`, `resources/templates/list`, `resources/read`, `server/discover`는 캐시 가능한 결과입니다. `ttlMs`와 `cacheScope`를 포함합니다. 안전한 기본값은 `ttlMs: 0`과 `cacheScope: "private"`입니다. 목록 항목은 결정론적 순서를 가져야 합니다. 그래야 동등한 응답이 안정적인 캐시 키와 안정적인 모델 컨텍스트를 만들어 냅니다.

### 핸드셰이크 없는 디스커버리

모든 현대 서버는 `server/discover`를 구현해야 합니다. 클라이언트는 다른 메서드 전에 이것을 호출해 다음을 얻을 수 있습니다.

- `supportedVersions`
- 서버 `capabilities`
- 선택적 사용 `instructions`
- 결과 `_meta` 속의 서버 신원
- 캐시 힌트

디스커버리는 유용하지만 게이트는 아닙니다. 클라이언트는 `tools/list`를 먼저 보낼 수 있습니다. 그 요청이 이미 자기 프로토콜 버전과 기능을 실고 있기 때문입니다.

요청된 버전이 지원되지 않으면 서버는 JSON-RPC 코드 `-32022`와 함께 다음을 돌려줍니다.

```json
{
  "requested": "2027-01-01",
  "supported": ["2026-07-28"]
}
```

클라이언트는 상호 지원되는 현대 버전을 골라 새로운 JSON-RPC 요청 id로 재시도합니다.

### 하나의 요청 수명 주기

현대 요청을 이 순서로 추적하세요.

1. JSON-RPC 봉투 하나를 파싱합니다.
2. `jsonrpc`가 `"2.0"`인지, `id`가 있는지, `method`가 문자열인지, `params`가 객체인지 확인합니다.
3. `params._meta`의 버전 문자열과 기능 객체를 요구합니다. 잘못되었거나 빠진 메타데이터는 `-32602`입니다.
4. HTTP 경계에서 버전, 메서드, 적용 가능한 이름 헤더를 본문과 비교합니다. 불일치는 두 버전 값 중 하나가 지원되지 않더라도 `-32020`입니다.
5. 동등성이 확인된 후에, 짝은 맞지만 지원되지 않는 버전을 `-32022`로 거부합니다.
6. 필수 기능을 확인하고, `method`로 라우팅하고, 메서드별 인자를 검증합니다.
7. 핸들러가 실행되기 전에 구체적인 작업을 인증하고 인가합니다.
8. 서버 신원을 담은 완전한 결과를 돌려줍니다.
9. 요청 범위의 프로토콜 메타데이터를 잊습니다.

이 순서는 두 구성 요소가 서로 다른 호출을 해석하는 일을 막습니다. 게이트웨이가 `Mcp-Name: notes.read`를 인가하는 동안 오리진이 `params.name: notes.delete`를 실행하는 일이 없어야 합니다. 또한 잘못된 입력, 헤더 혼동, 버전 협상, 기능 실패, 인가 실패, 핸들러 실패가 서로 구분되는 증거로 남습니다.

stdin을 닫거나 HTTP 응답을 끝내는 것은 전송 활동을 끝낼 뿐입니다. 프로토콜 세션을 종료하지 않습니다. 현대 MCP에는 프로토콜 세션이 없으니까요.

### 명시적인 레거시 호환성

`2025-11-25` 이전 버전은 `initialize`, `notifications/initialized`, 연결 범위의 기능, 그리고 (초기 Streamable HTTP에서는) 선택적 프로토콜 세션을 씁니다. 이중 시대 클라이언트가 오래된 서버와 이야기할 때는 이 동작이 여전히 관련 있습니다.

시대를 분리해 두세요. 현대 요청은 필수 요청별 메타데이터로 식별합니다. 레거시 연결은 문서화된 폴백 경로로만 선택합니다. `2026-07-28` 서버에 `initialize`를 기본으로 보내지 마세요.

따라서 "무상태"에는 시대별 의미가 있습니다. `2026-07-28`에서는 프로토콜 불변 조건입니다. 모든 일반 요청이 독립적으로 해석 가능하고 MCP 세션이 존재하지 않는다는 것이죠. `2025-11-25` 이전 버전에서는 초기화와 협상된 기능이 연결에 속하므로, 호환성 어댑터가 그 레거시 연결 상태를 유지할 수 있습니다. 이중 시대 구현은 하나의 관대한 상태 머신이 아닙니다. 어느 파서도 돌기 전에 명시적인 선택 결정이 놓이고, 무상태 현대 코어 옆에 고립된 레거시 어댑터가 있는 구조입니다.

어느 의미도 내구성 있는 애플리케이션 상태를 금지하지 않습니다. 워크플로, 태스크, 초안은 공유 저장소의 불투명한 핸들 뒤에 살 수 있습니다. 클라이언트는 그 핸들을 평범한 입력으로 보내고, 모든 레플리카가 그 사용을 인증하고 인가합니다. 제거된 세션의 대체품으로 프로토콜 컨텍스트가 그 저장소로 새어 들어가서는 안 됩니다.

```figure
mcp-tool-call
```

## 활용하기

`code/main.py`는 프레임워크 없이 현대 MCP 메시지를 만들고, 검증하고, 추적하고, 디스패치합니다. 실행:

```bash
python3 code/main.py
python3 -m unittest discover code/tests -v
```

출력에서 세 가지 불변 조건을 확인하세요.

- 모든 요청이 자기 `_meta` 필드를 반복합니다.
- 성공하는 모든 결과는 `resultType: "complete"`이며 서버 신원을 포함합니다.
- 목록 결과는 결정론적 순서이며 명시적인 캐시 힌트를 가집니다.

## 연습 문제

1. 한 요청의 프로토콜 버전을 `2027-01-01`로 바꾸세요. 에러 코드가 `-32022`이고 데이터가 지원 버전을 알리는지 확인하세요.
2. 두 번째 요청에서 `io.modelcontextprotocol/clientCapabilities`를 제거하세요. 서버가 첫 번째 요청의 기능을 재사용하지 않는지 확인하세요.
3. 인메모리 도구 레지스트리의 순서를 뒤집으세요. `tools/list`가 여전히 같은 결정론적 순서를 돌려주는지 확인하세요.
4. `cacheScope`를 `public`에서 `private`으로 바꾸세요. 각 경우에 어떤 인가 컨텍스트가 응답을 재사용할 수 있는지 설명하세요.
5. 선택적 `clientInfo` 생략 테스트를 추가하세요. 클라이언트 신원은 권장이지 필수가 아니므로 요청은 여전히 유효해야 합니다.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 무상태 프로토콜 | 모든 요청이 자기 해석에 필요한 메타데이터를 공급함 |
| 요청 메타데이터 | `params._meta`의 버전, 클라이언트 기능, 권장 클라이언트 신원 |
| `server/discover` | 버전, 기능, 지침, 신원을 위한 필수 서버 메서드 |
| `resultType` | 성공하는 모든 현대 결과의 판별자 |
| 캐시 가능한 결과 | 필수 `ttlMs`와 `cacheScope` 힌트를 포함하는 결과 |
| 프로토콜 시대 | 현대의 요청별 메타데이터 또는 레거시의 연결 범위 초기화 |
| 전송 수명 | 프로세스, 연결, 또는 응답 스트림의 수명. 프로토콜 세션 상태가 아님 |
| `-32022` | 요청 버전과 지원 버전을 알려 주는 미지원 프로토콜 버전 에러 |
