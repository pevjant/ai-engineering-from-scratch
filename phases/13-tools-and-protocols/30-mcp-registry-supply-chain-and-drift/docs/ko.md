# MCP 레지스트리 공급망: 수용, 드리프트, 롤백

> 레지스트리 항목은 게시자가 무엇을 선언했는지 알려줍니다. 프로덕션 수용(admission)은 무엇을 가져왔는지, 무엇을 관찰했는지, 무엇을 승인했는지, 무엇을 안전하게 복원할 수 있는지 증명합니다.

**유형:** Build
**언어:** Python
**선수 지식:** 페이즈 13 · 17(게이트웨이와 레지스트리), 페이즈 13 · 18(프로덕션 인증)
**시간:** 약 90분

## 학습 목표

- 레지스트리 게시, 패키지 출처(provenance), 런타임 발견, 로컬 승인을 분리합니다.
- 자기 기록 안의 이름을 믿지 않고 MCP 서버 네임스페이스를 검증합니다.
- 불변인 게시, 실행 소스, 출처, 라이브 디스크립터 증거를 고정(pin)합니다.
- 수용 후 레지스트리 상태 변화와 런타임 드리프트(drift)를 탐지합니다.
- 역사를 다시 쓰지 않고 이전에 수용된 버전으로 라우팅을 롤백합니다.
- 모든 결정을 설명하는 변조 탐지 가능한 수용 원장(ledger)을 유지합니다.

## 문제 상황

레지스트리에서 `com.example/inventory`를 발견합니다. 설명은 그럴듯합니다. 패키지가 존재합니다. 서버는 `server/discover`에 답합니다.

그것은 하나의 사실이 아닙니다. 서로 다른 권위에서 오는 사실들의 체인입니다:

1. 네임스페이스에 대해 인증된 게시자가 기록을 제출했습니다.
2. 패키지 레지스트리가 특정 정체성과 다이제스트를 가진 아티팩트를 제공했습니다.
3. 실행 중인 엔드포인트가 프로토콜 버전, 기능, 도구, 진단 서버 정보를 보고했습니다.
4. 여러분의 조직이 이 정확한 조합을 허용하기로 결정했습니다.

이 사실들을 "레지스트리에 있으니 믿는다"로 뭉개면 공급망 사각지대가 생깁니다. 유효한 게시도 폐기(deprecated)될 수 있습니다. 다이제스트를 고정하지 않으면 패키지 태그가 뜻밖의 아티팩트를 가리킬 수 있습니다. 서버가 검토 후 파괴적인 도구를 추가할 수 있습니다. 롤백이 한 번도 수용되지 않은 버전을 조용히 고를 수 있습니다.

해결책은 모든 경계에 증거를 둔 수용 컨트롤러입니다.

## 레지스트리는 색인이지 여러분의 승인 시스템이 아니다

공식 MCP 레지스트리는 서버 메타데이터를 저장합니다. 그 `server.json` 기록은 서버 버전을 이름 짓고 하나 이상의 패키지나 원격 엔드포인트를 선언합니다. 게시 규칙은 네임스페이스 인증, 패키지 소유권 검사, 제한된 레지스트리 규칙, 좁은 게시자 메타데이터 위치를 추가합니다.

그 통제들은 게시 질문에 답합니다. 여러분의 프로덕션 정책은 여전히 배포 질문에 답합니다:

| 경계 | 질문 | 증거 소유자 |
|---|---|---|
| 네임스페이스 | 게시자가 이 이름을 쓰도록 허용되었는가? | 레지스트리 인증 + 여러분이 검증한 네임스페이스 입력 |
| 기록 | 게시자가 이 버전에 대해 무엇을 선언했는가? | 불변 `server.json` 다이제스트 |
| 실행 소스 | 어떤 패키지나 원격 엔드포인트가 실행되는가? | 선언된 소스 필드, 검증된 소유권 결과, 전송, 신뢰할 수 있는 다이제스트 |
| 런타임 | 엔드포인트가 지금 무엇을 노출하는가? | `server/discover`와 도구 디스크립터 |
| 수용 | 정책이 이 정확한 세트를 승인했는가? | 로컬 핀(pin)과 원장 항목 |
| 운영 | 여전히 안전한가, 무엇이 대체할 수 있는가? | 드리프트 검사, 상태 동기화, 헬스, 롤백 경로 |

레지스트리 스키마 버전과 MCP 프로토콜 버전은 독립입니다. 기록은 게시된 `2025-12-11` 서버 스키마를 쓰는 반면 라이브 서버는 MCP `2026-07-28`을 지원할 수 있습니다. 하나를 다른 것에서 추론하지 마세요.

```figure
mcp-registry-admission
```

## 하나의 수용 결정 안의 일곱 통제

### 1. 네임스페이스 검증

공식 레지스트리 이름은 인증된 네임스페이스를 사용합니다. 검증된 도메인은 뒤집힌 도메인 접두사로 매핑될 수 있습니다. 예를 들어 `example.com`의 소유는 `com.example/*`을 확립할 수 있습니다.

문자열 접두사 검사를 받아들이지 마세요:

```python
server_name.startswith("com.example")
```

그것은 `com.exampleevil/tool`도 받아들입니다. 이름을 `/`에서 나누고, 비어 있지 않은 슬러그(slug)를 요구하고, 네임스페이스 세그먼트를 정확히 비교하세요. 더 중요하게는, 인증 결과에서 검증된 네임스페이스를 수용으로 전달하세요. 신뢰할 수 없는 기록에서 신뢰를 도출하지 마세요.

GitHub 기반 네임스페이스와 도메인 기반 네임스페이스는 다른 인증 경로를 씁니다. 어느 쪽이든 하나의 수용 입력으로 정규화하세요: 정확한 검증된 네임스페이스 문자열.

### 2. 출처 조인(join)

패키지 기록에 대해 선언과 가져온 아티팩트는 명시적 필드로 조인되어야 합니다:

- 패키지 레지스트리 타입
- 패키지 식별자
- 패키지 버전
- 검증된 소유권 결과
- 다운로드한 아티팩트 다이제스트

선언된 패키지 전송도 검증하세요. 원격 엔드포인트만 있는 기록은 유효하며 패키지가 없다는 이유로 거부되어서는 안 됩니다. 원격 소스의 경우, 선언된 URL과 전송 타입을 독립적으로 검증된 엔드포인트 소유권과 신뢰할 수 있는 연결 또는 배포 증거의 다이제스트에 조인하세요.

레슨 코드는 두 소스 종류를 모두 지원하고, 선택된 소스를 레지스트리 소스, 서버 이름, 레지스트리 버전, 기록 다이제스트, 증거 다이제스트와 함께 해싱합니다. 결과 출처 다이제스트는 전체 증거 세트를 가리키는 압축된 포인터입니다. 증거를 보관하는 것을 대신하지 못합니다.

검증하려는 아티팩트 자체만이 공급하는 다이제스트를 받아들이지 마세요. 신뢰할 수 있는 가져오기 경계에서 계산하거나, 여러분이 검증 결과를 확인하는 패키지 서비스에서 받으세요.

### 3. 버전뿐 아니라 결정을 고정하기

레지스트리 버전은 고유한 게시 식별자입니다. 게시된 메타데이터는 불변입니다. 바뀐 기록은 새 버전을 필요로 합니다. 시맨틱 버저닝이 권장되지만 레지스트리는 그것을 요구하지 않고 버전 범위도 받아들이지 않습니다.

이것은 `^1.4`가 수용 핀이 아니라는 뜻입니다. "latest"도 아닙니다. 유용한 핀은 다음을 담습니다:

```json
{
  "server": "com.example/inventory",
  "version": "1.0.0",
  "recordDigest": "...",
  "source": {"kind": "package", "registryType": "pypi"},
  "sourceDigest": "...",
  "toolsetDigest": "...",
  "provenanceDigest": "...",
  "registryStatus": "active"
}
```

여러 층을 고정하면 어떤 경계가 바뀌었는지 식별할 수 있습니다. 같은 레지스트리 버전 아래 기록 다이제스트 변화는 레지스트리 무결성 실패입니다. 같은 패키지 좌표나 원격 배포 아래 소스 다이제스트 변화는 실행 소스 무결성 실패입니다. 도구 세트 다이제스트 변화는 런타임 드리프트입니다.

### 4. 라이브 드리프트 탐지

수용은 실제로 트래픽을 받을 서버를 관찰해야 합니다. `server/discover`를 호출하고, 노출된 도구 디스크립터를 여러분의 신뢰 경로를 통해 나열하거나 얻고, 다음을 검증하세요:

- `2026-07-28`이 `supportedVersions`에 있는가
- 로컬에서 요구하는 모든 기능이 있는가
- 모든 도구 디스크립터가 필요한 정체성과 스키마 표면을 갖추었는가
- 이후 검사에서 정규화된 디스크립터 다이제스트가 수용된 핀과 일치하는가

선택적 결과 `_meta["io.modelcontextprotocol/serverInfo"]` 값은 자기 보고식 표시, 로그, 디버깅 컨텍스트입니다. 진단 증거로 기록하되, 네임스페이스, 패키지 소유권, 엔드포인트 소유권, 수용 또는 그 외 어떤 보안 결정도 확립하는 데 절대 쓰지 마세요. `_meta` 밖의 직접 `serverInfo` 별칭은 계약 필드가 아니며 진단 증거로 승격되어서는 안 됩니다.

순서에 의미가 없는 필드만 정규화하세요. 예시는 해싱 전에 도구 목록을 안정적인 이름으로 정렬하므로, 무해한 목록 순서 변화가 드리프트를 만들지 않습니다. 디스크립터 필드를 버리지는 않습니다. 새 도구, 바뀐 스키마, 바뀐 설명, 새 애너테이션은 핀을 바꿉니다.

예시는 잘못된 형식의 디스크립터와 어떤 디스크립터 다이제스트 변화도 드리프트로 취급하고, 핀을 격리(quarantine)하고, 활성 경로를 제거하고, 그 버전을 롤백 대상으로 막습니다. 프로덕션 정책은 편집적 변화를 새 검토를 통해서만 허용할 수 있습니다. 설명이 모델의 도구 선택에 영향을 주기 때문입니다. "외견상" 메타데이터가 에이전트 동작을 바꿀 수 있습니다.

### 5. 레지스트리 상태는 살아 있는 상태다

레지스트리 API는 각 서버 기록 옆에 응답 수준 `_meta` 객체를 붙입니다. 레지스트리가 관리하는 필드는 `_meta["io.modelcontextprotocol.registry/official"]` 아래에 삽니다. 응답 `_meta` 객체를 수용에 전달하고 `_meta["io.modelcontextprotocol.registry/official"].status`를 읽으세요. 직접 `_meta.status` 값은 공식 회선 모양이 아닙니다. 응답 메타데이터를 게시 기록 자체의 `_meta`와 혼동하지 마세요. 상태는 다음이 될 수 있습니다:

- `active`: 기본으로 반환되며 로컬 수용 자격이 있음
- `deprecated`: 경고와 함께 여전히 발견되지만 더 이상 안전한 자동 선택이 아님
- `deleted`: 기본 나열에서 숨겨지지만 역사 기록은 삭제·증분 뷰를 통해 계속 이용 가능

수용 후 상태를 동기화하세요. 활성 버전이 deprecated나 deleted가 되면 핀을 격리하고 새 작업 라우팅을 멈추세요. 증거는 유지하세요. 기본 나열에서의 삭제는 감사 기록을 지울 허가가 아닙니다.

게시자가 제공한 커스텀 메타데이터는 게시 기록의 `_meta.io.modelcontextprotocol.registry/publisher-provided` 아래에만 속합니다. 레지스트리가 관리하는 응답 메타데이터는 별개입니다. 게시자가 자기 공식 상태를 설정하게 두지 마세요.

### 6. 롤백은 경로 복원이다

불변인 게시는 롤백 중 편집되지 않습니다. 롤백은 이전에 수용되었고 현재 자격이 있는 핀을 선택하고 활성 경로를 바꿉니다.

안전한 대상은 다음이어야 합니다:

1. 완료된 수용 기록을 가짐.
2. 정책 아래에서 여전히 활성 레지스트리 상태를 가짐.
3. 런타임이나 보안 증거로 격리되지 않음.
4. 여전히 고정된 패키지와 라이브 디스크립터 세트로 해석됨.
5. 현재 헬스 검사를 통과함.

예시는 처음 세 조건에 집중합니다. 실제 조정자(reconciler)는 활성화 전에 패키지를 다시 가져오고 라이브 엔드포인트를 다시 검사해야 합니다.

### 7. 수용 원장에 추가하기

수용 데이터베이스는 무엇이 활성인지 말합니다. 원장은 왜인지 설명합니다.

각 예시 항목은 시퀀스, 시간, 이벤트, 서버, 버전, 결과, 이유, 증거, 이전 항목 해시, 자기 해시를 담습니다. 오래된 결과를 바꾸면 그 항목과 이후 모든 링크의 검증이 깨집니다.

이것은 변조 탐지 가능(tamper-evident)할 뿐 마법처럼 변조 불가능(tamper-proof)한 것이 아닙니다. 주기적인 원장 헤드를 서명된 릴리스 메타데이터나 쓰기 한 번 저장소 같은 별도의 신뢰 도메인에 닻으세요. 추가할 수 있는 사람을 제한하세요. 인증 토큰, 패키지 자격 증명, 도구 인자, 비공개 엔드포인트 데이터는 증거에서 제외하세요.

## 직접 만들기

실행 가능한 컨트롤러는 `code/main.py`에 있습니다. 파이썬 표준 라이브러리만 사용합니다.

유한한 데모부터:

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift
python3 code/main.py
```

데모는 다섯 작업을 수행합니다:

1. 일치하는 네임스페이스, 패키지 출처, 프로토콜, 기능, 도구로 `1.0.0`을 수용합니다.
2. `1.1.0`을 수용하고 활성으로 만듭니다.
3. 런타임에서 뜻밖의 delete 도구를 관찰합니다.
4. `1.1.0`의 레지스트리 상태가 `deprecated`가 되는 것을 관찰합니다.
5. 여전히 수용된 `1.0.0` 핀으로 라우팅을 복원합니다.

기대 모양:

```json
{
  "admitted": [true, true],
  "driftAllowed": false,
  "rollbackAllowed": true,
  "activeVersion": "1.0.0",
  "ledgerValid": true
}
```

구현은 이 순서로 읽으세요:

1. `namespace_for_domain()`과 `namespace_matches()`가 정확한 이름 권위를 확립합니다.
2. `digest()`와 `normalized_tools()`가 결정론적 증거를 만듭니다.
3. `RegistryAdmissionController.admit()`이 게시, 출처, 런타임, 정책을 조인합니다.
4. `check_live()`가 새 관찰을 핀과 비교합니다.
5. `observe_registry_status()`가 레지스트리 상태가 바뀐 버전을 격리합니다.
6. `rollback()`은 이전에 수용된 자격 있는 대상만 활성화합니다.
7. `AdmissionLedger.verify()`가 기록된 역사의 변화를 탐지합니다.

## 사용하기

컨트롤러를 발견과 라우팅 사이에 두세요:

```text
레지스트리 동기화 -> 아티팩트 검증자 -> 라이브 발견 -> 수용 컨트롤러 -> 경로 테이블
                                          |                 |
                                          v                 v
                                     증거 저장소      수용 원장
```

이 작업들에는 별도의 정체성을 사용하세요. 레지스트리 동기화 작업자는 메타데이터 읽기 접근이 필요합니다. 아티팩트 검증자는 패키지 가져오기 접근이 필요합니다. 경로 조정자는 승인된 핀을 활성화할 권한이 필요합니다. 어느 것도 모든 자격 증명을 필요로 해서는 안 됩니다.

롤아웃 상태를 명시적으로 만드세요. "승인됨"은 증거가 정책을 통과했다는 뜻입니다. "활성"은 경로가 현재 그것을 선택한다는 뜻입니다. "격리됨"은 새 작업을 받을 수 없다는 뜻입니다. "대체됨"은 다른 수용된 버전이 활성이라는 뜻입니다. 네 의미를 하나의 불리언에 담지 마세요.

`tools/list`에 서버를 노출하기 전에 수용을 실행하세요. 그렇지 않으면 클라이언트가 게시와 정책 평가 사이의 공백 동안 도구를 발견할 수 있습니다.

## 대화형 실습

한 번에 하나의 경계가 실패하는 것을 지켜볼 것입니다.

### 실습 A: 네임스페이스 충돌

코드 디렉터리에서 파이썬 셸을 엽니다:

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift/code
python3 -q
```

그다음 실행합니다:

```python
from main import namespace_matches
namespace_matches("com.example/inventory", "com.example")
namespace_matches("com.exampleevil/inventory", "com.example")
```

첫 결과는 `True`, 두 번째는 `False`입니다. 로컬에서 정확한 비교를 `startswith`로 바꾸고 두 번째 이름이 왜 경계를 넘는지 관찰하세요. 계속하기 전에 정확한 비교를 복원하세요.

### 실습 B: 디스크립터 드리프트

```python
from main import *
times = iter(f"2026-08-21T12:00:{n:02d}+00:00" for n in range(10))
c = RegistryAdmissionController(clock=lambda: next(times))
meta = {OFFICIAL_META_KEY: {"status": "active"}}
c.admit(sample_record("1.0.0"), meta, "com.example", evidence_for("1.0.0"), sample_live("1.0.0"))
c.check_live("com.example/inventory", "1.0.0", sample_live("1.0.0", True))
```

이유와 경로 상태를 살펴보세요. 패키지와 레지스트리 기록은 바뀌지 않았습니다. 런타임 도구 표면이 바뀌었으므로 컨트롤러가 핀을 격리하고 비활성화했습니다. 공급망 통제가 설치 이후에도 계속되어야 하는 이유입니다.

### 실습 C: 상태와 롤백

`1.1.0`을 수용하고, deprecated로 표시하고, 두 롤백 대상을 모두 시도합니다:

```python
c.admit(sample_record("1.1.0"), meta, "com.example", evidence_for("1.1.0"), sample_live("1.1.0"))
c.observe_registry_status("com.example/inventory", "1.1.0", "deprecated")
c.rollback("com.example/inventory", "1.1.0", "unsafe retry")
c.rollback("com.example/inventory", "1.0.0", "restore known release")
c.ledger.verify()
```

격리된 대상은 거부됩니다. 이전 활성 핀은 수용됩니다. 원장은 유효하게 남습니다.

## 실습 과제

컨트롤러에 2인 승인 게이트를 추가하세요.

요구 사항:

- 승인을 핀 안의 가변 이름이 아니라 서명된 증거 참조로 저장합니다.
- `destructiveHint: true`인 도구를 포함하는 도구 세트에는 서로 다른 두 검토자 정체성을 요구합니다.
- 중복 검토자 정체성을 거부합니다.
- 승인이 불완전할 때 원래 수용 시도를 원장에 보존합니다.
- 0개, 1개, 중복, 2개의 구별된 승인에 대한 테스트를 추가합니다.
- 서명, 자격 증명, 전체 비공개 도구 인자를 로그하지 마세요.

성공은 두 정체성이 정확한 기록, 패키지, 도구 세트 다이제스트를 승인할 때까지 파괴적인 도구가 활성화될 수 없다는 뜻입니다.

## 배포되는 산출물

이 레슨은 `outputs/skill-mcp-registry-admission.md`를 배포합니다. 새 레지스트리 버전을 검토하거나 드리프트를 조사할 때 평면적이고 재사용 가능한 런북(runbook)으로 사용하세요. 샘플 클래스 이름에 의존하지 않고 입력, 거부 규칙, 증거 번들, 상태 대조, 롤백 증명을 정의합니다.

## 검증하기

데모와 결정론적 스위트를 실행하세요:

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

검증은 다음을 증명해야 합니다:

- 정확한 네임스페이스 경계가 유사 접두사를 거부함
- 공식 네임스페이스가 지정된 레지스트리 상태만이 버전에 자격을 부여함
- 검증되지 않았거나 일치하지 않는 패키지·원격 증거가 거부됨
- 게시자 메타데이터가 레지스트리 관리 메타데이터를 사칭할 수 없음
- 도구 순서가 디스크립터 변화를 숨기지 않고 정규화됨
- 잘못된 형식의 패키지와 도구 구조가 안전하게 거부됨
- `serverInfo`가 진단으로 남고 절대 수용 권한을 공급하지 않음
- 디스크립터 드리프트가 격리하고, 비활성화하고, 핀으로의 롤백을 막음
- 상태 변화가 활성 핀을 격리함
- 롤백이 격리되거나 모르는 버전을 선택할 수 없음
- 원장 변조가 탐지됨

## 프로덕션 실패 모드

| 실패 | 왜 일어나는가 | 요구되는 대응 |
|---|---|---|
| 이름은 유효해 보이지만 네임스페이스가 한 번도 인증되지 않음 | 정책이 기록 텍스트를 신뢰함 | 신뢰할 수 있는 네임스페이스 검증자가 정확한 접두사를 공급할 때까지 거부 |
| 같은 패키지 좌표가 새 바이트를 반환 | 가변 업스트림 또는 침해된 배포 | 활성화를 멈추고 두 다이제스트를 보존하며 가져오기 경계를 조사 |
| "latest"가 검토 없이 바뀜 | 부동 선택이 핀을 벗어남 | 정확히 수용된 버전과 다이제스트만 해석 |
| 승인 후 새 도구가 나타남 | 런타임 드리프트 또는 다른 배포 | 경로를 격리하고 새 디스크립터 관찰을 캡처 |
| deprecated 버전이 활성으로 남음 | 상태 동기화가 없거나 지연됨 | 일정에 따라, 그리고 활성화 전에 상태를 대조 |
| deleted 기록이 기본 동기화에서 사라짐 | 클라이언트가 active 기록만 요청함 | 증분 또는 삭제 인식 대조를 쓰고 로컬 역사를 보존 |
| 롤백 대상이 한 번도 수용되지 않음 | 경로 제어와 승인 상태가 분리됨 | 롤백을 거부하고 대상에 대한 새 수용을 실행 |
| 공격자가 모든 항목을 다시 쓴 뒤 원장이 로컬에서 검증됨 | 해시 체인에 외부 닻이 없음 | 서명된 원장 헤드를 별도의 신뢰 도메인에 게시 |
| 증거가 베어러 토큰이나 도구 인자를 담음 | 로깅이 요청 전체를 복사함 | 수집 시점에 편집(redact)하고 최소 증명만 저장 |

## 운영 규칙

게시는 "이 정체성이 이 이름을 게시할 수 있는가?"에 답합니다. 수용은 "이 정확한 아티팩트를 실행하고 이 정확한 동작을 노출할 것인가?"에 답합니다. 그 결정들을 분리해 두고, 모든 조인을 고정하고, 롤백이 기억이 아니라 증거를 고르게 하세요.
