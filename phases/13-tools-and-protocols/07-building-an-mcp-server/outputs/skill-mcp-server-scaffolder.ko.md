도메인이 주어지면 현대 MCP 서버 계획을 만들어 냅니다. 애플리케이션 상태는 명시적으로 유지하고, 프로토콜 동작은 무상태로 유지합니다.

산출물:

1. 원시 기능 분할. 원자적 도구, URI로 주소가 매겨진 리소스, 쓸모 있는 프롬프트를 정의합니다. 도메인이 정직하게 쓸 곳이 없는 원시 기능은 생략합니다.
2. 디스커버리 결과. `supportedVersions`, 서버 기능, 선택적 지침, `resultType: "complete"`, 캐시 힌트, 그리고 결과 `_meta` 속 서버 신원을 제공합니다.
3. 요청 검증기. 모든 `params._meta`에서 프로토콜 버전과 클라이언트 기능을 요구합니다. 권장 클라이언트 신원이 있으면 검증합니다. 불일치 시 `requested`와 `supported` 버전을 담은 `-32022`를 돌려줍니다.
4. 결과 래퍼. 모든 성공에 `resultType: "complete"`와 서버 신원을 추가합니다. 디스커버리, 목록, 템플릿, 리소스 읽기에는 `ttlMs`와 `cacheScope`를 추가합니다.
5. 순서 정책. 모든 목록 응답에 안정적인 정렬 키를 정의합니다.
6. 상태 정책. 내구성 있는 상태는 데이터베이스에 두거나, 명시적이고 불투명한 핸들을 평범한 도구 인자로 돌려줍니다. 상태를 프로토콜 세션에 숨기는 일은 절대 없습니다.
7. 호환성 경계. 레거시 지원이 필요하면 `2025-11-25` initialize 어댑터를 고립시킵니다. 레거시 트래픽에만 선택하고, 두 시대를 독립적으로 테스트합니다.

즉시 반려 사항:

- 첫 유효 메서드가 `initialize`여야 하는 현대 서버.
- 이전 요청의 기능, 신원, 버전 재사용.
- 현대 HTTP 트래픽에서 `Mcp-Session-Id` 돌려주기.
- 캐시 힌트 없는 목록 또는 리소스 읽기 결과.
- 주석을 인가 통제로 취급하는 것.
- 서버에서 독립적인 JSON-RPC 요청 보내기.

거절 규칙:

- 요청된 리소스가 인가 없이 시크릿을 노출할 것이라면 멈추고 접근 정책을 요구하세요.
- 도메인에 읽기 전용 데이터가 없으면 리소스를 발명하는 대신 생략하세요.
- 도메인에 재사용 가능한 템플릿이 없으면 채우기용 프롬프트를 만드는 대신 생략하세요.

출력: 한 페이지짜리 아키텍처, 메서드 표, 검증 의사코드, 결과 예제, 결정론적 순서 규칙, 최소 여섯 개의 적합성 테스트. 애플리케이션 상태와 프로토콜 상태의 경계로 마무리하세요.
