# MCP 신뢰성, 취소, 흐름 제어

> 요청 ID는 메시지를 연관 짓습니다. 부작용을 안전하게 만들거나, 작업자를 멈추거나, 느린 소비자로부터 스트림을 보호하지는 않습니다.

**유형:** Build
**언어:** Python
**선수 지식:** 페이즈 13, 레슨 09, 13
**시간:** 약 120분

## 학습 목표

- stdio와 Streamable HTTP에 맞는 올바른 취소 신호를 구현합니다.
- 취소 후 메시지를 보내지 않으면서 완료·취소 경쟁(race)을 해소합니다.
- 요청 취소와 영속적인 `tasks/cancel` 의미를 분리합니다.
- 부작용과 명시적 멱등성 키(idempotency key)로 재시도 결정을 만듭니다.
- 최종 응답을 지키면서 진행(progress) 큐에 경계를 둡니다.
- 재접속, 다시 가져오기(refetch), 지터가 있는 백오프로 스트림을 복구합니다.

## 문제 상황

행복 경로(happy path)는 가장 비싼 분산 시스템 버그를 숨깁니다.

클라이언트가 도구를 호출합니다. 서버가 작업을 시작합니다. 진행 상황이 도착합니다. 프록시가 스트림을 버퍼링합니다. 클라이언트가 타임아웃에 도달하고 연결을 끊습니다. 서버가 1밀리초 뒤에 끝냅니다. 클라이언트가 새 JSON-RPC id로 재시도합니다. 변경 작업이 두 번 실행됩니다.

모든 구성 요소는 로컬에서는 올바르게 행동했습니다. 시스템은 전역적으로 실패했습니다.

MCP는 메시지와 전송 동작을 정의하지만, 다음은 여전히 애플리케이션이 소유합니다:

- 시간 예산;
- 비즈니스 멱등성;
- 경계가 있는 큐;
- 재시도 분류;
- 영속적인 작업 상태;
- 재접속·다시 가져오기 정책.

이 레슨은 그 결정들을 결정론적 시뮬레이터로 만듭니다. sleep도, 소켓도, 무작위 실패도 없습니다. 취소 이벤트 순서를 직접 제어합니다. 하나의 동기화된 스레드 테스트가 두 개의 원장(ledger) 클라이언트가 같은 멱등성 키를 두고 경쟁하게 만듭니다.

## 요청 취소는 전송 계층별로 다르다

의도는 모든 전송 계층에서 같습니다: 클라이언트가 진행 중인 결과를 더 이상 필요로 하지 않는다. 회선 신호가 다를 뿐입니다.

### stdio

stdio는 하나의 공유 양방향 채널을 사용합니다. 클라이언트가 알림을 보냅니다:

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 41,
    "reason": "User closed the operation"
  }
}
```

이 알림은 fire-and-forget입니다. 서버는 그것에 대한 JSON-RPC 응답을 내보내지 않습니다.

서버는 작업을 멈추고, 리소스를 해제하고, 취소된 요청에 대한 응답을 보내지 않아야 합니다. 요청을 모르거나, 이미 끝났거나, 안전하게 멈출 수 없을 때는 취소를 무시할 수 있습니다.

형식이 틀린, 모르는, 이미 완료된 취소 알림은 무시됩니다. 그런 경쟁을 새 오류로 바꾸면 더 많은 경쟁만 생깁니다.

### Streamable HTTP

현대의 Streamable HTTP는 각 요청에 자체 HTTP 응답 또는 SSE 응답 스트림을 줍니다. 클라이언트는 그 요청의 응답 스트림을 닫아서 취소합니다.

평범한 HTTP 요청에 `notifications/cancelled`를 POST하지 마세요. 스트림 닫기가 곧 취소 신호입니다.

서버가 연결 끊김을 관찰하면 작업을 멈추고, 그 요청에 대한 더 많은 메시지를 보내서는 안 됩니다.

### 서버가 보내는 취소는 범위가 좁다

서버가 `notifications/cancelled`로 클라이언트 호출을 마음대로 취소하지 않습니다. stdio에서 서버가 보내는 취소는 `subscriptions/listen` 요청을 종료할 때만 쓰입니다. 그 경로를 평범한 클라이언트 요청 취소와 분리해 두세요.

## 취소는 경쟁 상태다

두 이벤트 순서가 모두 유효합니다.

### 취소가 이기는 경우

```text
요청 시작
클라이언트가 취소 신호 전송
서버가 요청을 취소로 표시
작업자가 완료에 도달
서버가 응답을 억제
```

### 완료가 이기는 경우

```text
요청 시작
작업자가 결과를 커밋
서버가 응답을 전송
취소가 늦게 도착
서버가 늦은 알림을 무시
```

클라이언트도 이미 포기한 요청의 늦은 응답을 무시해야 합니다. 네트워크 지연 때문에 어느 쪽도 상대가 어떤 이벤트를 먼저 관찰했는지 증명할 수 없습니다.

```figure
mcp-reliability-race
```

레슨의 `RequestCoordinator`는 터미널 상태를 하나만 저장합니다. 취소 후 `complete()`는 응답을 반환하지 않습니다. 늦은 취소는 완료된 기록을 바꿀 수 없습니다.

## 타임아웃에는 두 개의 시계가 필요하다

하나의 비활동 타이머로는 충분하지 않습니다.

두 개의 한도를 사용하세요:

1. **유휴 타임아웃(idle timeout).** 요청이 유용한 활동 없이 보낼 수 있는 시간.
2. **최대 타임아웃.** 요청 시작부터의 절대 실시간(wall-clock) 예산.

진행 상황이 유휴 시계를 초기화할 수 있습니다. 하지만 절대 최대 기한을 없애서는 안 됩니다.

```text
시작: 0 ms
진행: 400 ms
진행: 800 ms
진행: 1200 ms
유휴 타임아웃: 500 ms
최대 타임아웃: 2000 ms
```

1500 ms 시점에는 요청이 아직 활성입니다. 최신 진행이 겨우 300 ms 전이기 때문입니다. 2000 ms 시점에는 1999 ms에 또 다른 진행 이벤트가 도착했더라도 최대 기한이 취소합니다.

진행은 선택입니다. 서버는 진행 토큰을 받아들이고 아무 업데이트도 내보내지 않을 수 있습니다. 토큰의 존재를 무한 타임아웃으로 바꾸지 마세요.

MCP 진행 값은 반드시 증가해야 합니다. 알림은 완료나 취소 이후에는 멈춥니다. 빠른 작업자가 전송 계층을 범람하지 못하도록 진행에 속도 제한을 두세요.

## 요청 취소는 `tasks/cancel`이 아니다

이 메커니즘들은 서로 다른 수명을 다룹니다.

| 메커니즘 | 대상 | 신호 | 성공의 의미 |
|-----------|--------|--------------------|--------------------|
| stdio의 요청 취소 | 진행 중인 RPC 하나 | `notifications/cancelled` | 클라이언트가 요청을 포기함; 서버는 가능하면 멈춰야 함 |
| HTTP의 요청 취소 | 진행 중인 응답 스트림 하나 | 스트림 닫기 | 클라이언트가 요청을 포기함; 서버는 가능하면 멈춰야 함 |
| `tasks/cancel` | 영속적인 Task 하나 | 평범한 MCP 요청 | 서버가 취소 의도를 확인함 |

성공한 `tasks/cancel` 결과는 작업자가 멈췄음을 증명하지 않습니다. 작업자 체크포인트가 플래그를 관찰할 때까지 작업은 `working` 상태로 남을 수 있습니다. 그 체크포인트 전에 작업이 끝날 수도 있습니다.

HTTP 연결이 닫혔다고 해서 영속적인 작업 상태를 지우지 마세요. Task를 만드는 이유는 그 수명이 하나의 요청과 하나의 연결보다 오래가기 때문입니다.

## 새 JSON-RPC ID는 멱등성이 아니다

JSON-RPC id는 요청과 응답을 연관 짓습니다. 비즈니스 작업을 식별하지 않습니다.

클라이언트가 id `41`로 청구를 제출하고, 응답을 잃고, id `42`로 재시도한다고 해보세요. 서버는 두 개의 다른 메시지를 봅니다. 애플리케이션 키가 없다면 그것이 하나의 결제를 나타낸다는 것을 알 도리가 없습니다.

멱등성 키는 비즈니스 의도를 식별합니다:

```json
{
  "name": "charge_account",
  "arguments": {
    "account": "acct-7",
    "cents": 1200,
    "idempotencyKey": "checkout-7"
  }
}
```

서버는 다음을 저장합니다:

- 키;
- 작업 인자의 지문(fingerprint);
- 커밋된 결과.

같은 키와 같은 인자는 저장된 결과를 돌려줍니다. 같은 키에 다른 인자는 거부됩니다. 이것은 우연한 키 재사용이 다른 비즈니스 작업을 변경하는 사고를 막습니다.

### 원장 경계는 원자적이고 영속적이어야 한다

다음 순서는 안전하지 않습니다:

```text
키 검사
변경 실행
결과 저장
```

두 작업자가 모두 없는 키를 관찰하고 모두 변경 작업을 실행할 수 있습니다. 효과 이후, 저장 이전의 크래시는 재시도에서 같은 모호함을 만듭니다.

레슨은 파일 기반 SQLite 원장을 사용합니다. `BEGIN IMMEDIATE`가 키 검사, 시뮬레이션된 비즈니스 효과, 실행 카운터, 저장된 결과를 하나의 트랜잭션으로 직렬화합니다. 따라서 같은 키로 경쟁하는 두 개의 독립적인 원장 연결은 하나의 커밋된 결과와 하나의 실행을 관찰합니다. 원장을 닫았다가 다시 열어도 그 기록은 유지됩니다.

모든 반환 값은 저장된 JSON에서 재구성됩니다. 호출자는 원장이 쥔 가변 객체를 절대 받지 않으므로, 반환된 사전을 바꾼다고 이후 재생(replay) 결과가 오염되지 않습니다.

시뮬레이터의 비즈니스 효과는 같은 SQLite 트랜잭션 안의 영수증과 실행 카운터입니다. 실제 결제, 배포, 외부 API 호출은 로컬 테이블에 쓴다고 해서 원자적이 되지 않습니다. 프로덕션에는 영속적인 공유 데이터베이스 트랜잭션, 트랜잭셔널 아웃박스(outbox), 또는 같은 멱등성 키를 강제하는 업스트림 제공자가 필요합니다. 프로세스 잠금만으로는 여러 복제본을 보호하지 못하고 재시작을 견디지 못합니다.

### 재시도 매트릭스

구현하기 전에 재시도를 분류하세요.

| 분류 | 예시 | 재시도 규칙 |
|------|---------|------------|
| 안전 | 부작용 없는 결정론적 읽기 | 실패 경계를 파악한 뒤 새 JSON-RPC id로 재시도 |
| 조건부 | 영속적인 멱등성 키를 가진 변경 | 같은 키와 동일한 인자로 재시도 |
| 안전하지 않음 | 비즈니스 중복 제거 없는 변경 | 자동 재시도 금지; 먼저 대조(reconcile) |

`readOnlyHint`와 `idempotentHint` 같은 도구 애너테이션은 신뢰할 수 없는 힌트로 남습니다. 재시도 안전은 애플리케이션 계약과 서버 구현이 결정합니다.

## 백프레셔(backpressure)는 정확성의 일부다

SSE 생산자가 클라이언트, 프록시, 네트워크가 소비하는 것보다 빠르게 진행을 만들어 낼 수 있습니다. 경계 없는 큐는 느려짐을 메모리 고갈로 바꿉니다.

경계가 있는 큐를 사용하고 무엇을 잃을 수 있는지 정의하세요.

진행은 대체 가능합니다. 같은 토큰의 나중 진행 값은 이전 것을 대체합니다. 최종 JSON-RPC 응답은 대체 불가능합니다.

레슨 버퍼는 이 정책을 적용합니다:

1. 같은 토큰의 인접한 진행을 병합(coalesce).
2. 용량에 도달하면 가장 오래된 진행을 버림.
3. 스트림에 신뢰할 수 있는 소스에서 다시 가져와야 한다고 표시.
4. 최종 응답을 보존.
5. 최종 응답을 보존하는 것이 다른 최종 응답을 버리는 것을 요구하는 상태는 거부.

이것은 명시적 복구가 있는 경계 있는 손실입니다. 조용한 손실은 전략이 아닙니다.

### 프록시 버퍼링

서버는 올바르게 스트리밍하는데 역방향 프록시가 이벤트를 버퍼에 쥐고 있을 수 있습니다.

SSE 응답에는 다음을 보내세요:

```http
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
```

2026 Streamable HTTP 명세는 호환되는 프록시가 이벤트를 즉시 전달하도록 `X-Accel-Buffering: no`를 권장합니다.

조용한 장수명 스트림에는 주기적으로 SSE 주석을 내보내세요:

```text
:
```

클라이언트는 주석 줄을 무시합니다. 중개자는 트래픽을 보게 되고 유휴 연결을 닫을 가능성이 줄어듭니다.

킵얼라이브(keepalive)는 진행이 아닙니다. 전송 계층 주석이 도착했다는 이유만으로 작업의 의미적 유휴 타임아웃을 초기화하지 마세요.

## 재접속은 다시 가져오기를 의미한다

현대의 Streamable HTTP는 `Last-Event-ID`를 통한 재개 가능한 SSE를 지원하지 않습니다.

`subscriptions/listen` 스트림이 끊긴 후:

1. 새 JSON-RPC id로 새 listen 요청을 엽니다.
2. 원하는 구독 필터를 복원합니다.
3. 영향을 받은 도구, 리소스, 프롬프트, Task를 신뢰할 수 있는 메서드에서 다시 가져옵니다.
4. 안정적인 식별자로 애플리케이션 상태를 중복 제거합니다.
5. 응답을 잃었다는 이유만으로 안전하지 않은 변경을 재생하지 마세요.

예시 복구 계획은 `sendLastEventId`를 false로 명시하고 다시 가져올 리소스를 나열합니다.

### 재접속 무리(reconnect herd)를 막기

10,000개의 클라이언트가 정확히 1초에 재접속하면 복구 중인 서버는 다시 실패합니다.

상한과 지터가 있는 지수 백오프를 사용하세요. 레슨은 클라이언트 id와 시도 횟수에서 결정론적 지터를 계산해 테스트가 재현 가능하게 유지합니다:

```text
시도 0: 최대 250 ms
시도 1: 최대 500 ms
시도 2: 최대 1000 ms
...
상한: 8000 ms
```

프로덕션은 암호학적으로 안전한 무작위성이나 런타임 무작위성을 쓸 수 있습니다. 불변 조건은 분포이지 특정 공식이 아닙니다.

## 직접 만들기

`code/main.py`는 다섯 개의 작은 신뢰성 구성 요소를 만듭니다.

### `RequestCoordinator`

- 유휴·최대 기한과 함께 진행 중인 요청을 시작;
- 단조 증가하는 진행 알림을 내보냄;
- 올바른 stdio 또는 HTTP 취소 신호를 만들어 냄;
- 잘못된 취소 알림을 무시;
- 취소와 완료의 터미널 경쟁을 명시적으로 만듦;
- 서버가 보내는 취소를 stdio 구독에만 예약.

### `MutationLedger`

- 비즈니스 키 없이는 두 JSON-RPC id가 두 번 실행됨을 증명;
- 키 검사, 시뮬레이션된 효과, 실행 카운터, 결과 커밋에 파일 기반 SQLite 트랜잭션 사용;
- 독립적인 원장 연결을 가로질러 하나의 멱등성 키 아래 일치하는 인자를 중복 제거;
- 다른 인자로 재사용된 하나의 키를 거부;
- 방어적 사본을 반환하고, 파일을 닫았다 다시 열어도 커밋된 기록을 보존.

### `DurableTaskService`

- 취소 요청을 확인(acknowledge);
- 작업자 체크포인트까지 작업을 `working`으로 유지;
- 확인이 최종 상태가 아닌 이유를 보여줌.

### `BoundedSseBuffer`

- 압박 상황에서 진행을 병합하거나 버림;
- 신뢰할 수 있는 다시 가져오기가 필요하다고 기록;
- 최종 응답은 절대 버리지 않음.

### 복구 도우미

- 프록시에 안전한 SSE 헤더와 킵얼라이브 주석을 반환;
- 재접속·다시 가져오기 계획을 만듦;
- 결정론적 지수 백오프와 지터로 재시도를 시간에 걸쳐 흩뿌림.

## 대화형 실습

sleep을 추가하지 말고 네 가지 이벤트 순서를 실행하세요.

1. 요청 `A`를 시작하고, 취소한 다음, `complete()`를 호출합니다.
2. 요청 `B`를 시작하고, 완료한 다음, 취소를 전달합니다.
3. 요청 `C`를 시작하고, 모든 유휴 기한 전에 진행을 내보낸 다음, 최대 기한을 넘깁니다.
4. 요청 `D`를 Streamable HTTP로 시작하고 응답 스트림을 닫습니다.

각 시나리오를 기록하세요:

- 터미널 요청 상태;
- 최종 응답이 존재하는지;
- 회선에 놓인 취소 신호;
- 클라이언트가 무시해야 할 이벤트.

그다음 `D`를 stdio로 바꾸세요. 작업은 동일하지만 취소 신호는 바뀌어야 합니다.

## 실습 과제

`MutationLedger`에 `reserve_inventory` 변경을 추가하세요.

요구 사항:

1. 키는 SKU, 수량, 테넌트, 작업 이름을 묶습니다.
2. 같은 키와 같은 인자의 재시도는 첫 예약을 반환합니다.
3. 수량이 바뀐 재시도는 다른 예약 없이 실패합니다.
4. 커밋했지만 응답을 잃은 실행은 키로 대조(reconcile)할 수 있습니다.
5. 결과는 시크릿이나 결제 데이터를 기록하지 않습니다.
6. 클라이언트가 키를 제공하지 않으면 자동 재시도는 비활성입니다.
7. 시뮬레이션된 구독 끊김을 추가하고, 다음 행동을 결정하기 전에 재고 기록을 다시 가져옵니다.
8. 장벽(barrier)에서 두 개의 원장 연결을 시작하고 같은 키를 동시에 제출합니다. 하나의 예약만 커밋되었음을 단언(assert)합니다.
9. 첫 번째로 반환된 예약 객체를 변경합니다. 키를 재생하고 저장된 결과가 바뀌지 않았음을 증명합니다.
10. 원장 파일을 닫았다가 다시 열고, 키로 예약을 대조합니다.

실습을 정직하게 유지하세요: 재고가 다른 서비스에 있다면, 그 서비스가 같은 멱등성 키를 받는지, 아니면 트랜잭셔널 아웃박스가 로컬 커밋을 원격 효과에 연결하는지 설명하세요.

## 검증하기

다음 진술들이 참일 때 이 레슨은 완성입니다:

- stdio 취소는 `notifications/cancelled`를 보내고 응답을 받지 않습니다.
- Streamable HTTP 취소는 요청 스트림을 닫고 취소 POST를 보내지 않습니다.
- 완료 전 취소는 최종 응답을 억제합니다.
- 취소 전 완료는 응답을 보존하고 늦은 취소를 무시합니다.
- 진행은 유휴 타임아웃은 초기화할 수 있지만 최대 타임아웃은 절대 초기화할 수 없습니다.
- 새 JSON-RPC id만으로 변경이 다시 실행됩니다.
- 하나의 멱등성 키와 동일한 인자는 동시 2연결 경쟁 아래에서 한 번만 실행됩니다.
- 커밋된 기록은 다시 열기에서 살아남고 재생은 방어적 사본을 반환합니다.
- 반환된 결과 하나를 바꾸는 것은 저장된 결과를 바꿀 수 없습니다.
- 경계 있는 버퍼는 용량 안에 머물고 최종 응답을 보존합니다.
- 재접속은 새 요청을 사용하고, `Last-Event-ID`를 보내지 않고, 영향받은 상태를 다시 가져옵니다.
- `tasks/cancel` 확인은 작업자가 관찰할 때까지 작업을 터미널이 아닌 상태로 둡니다.

## 프로덕션 실패 모드

| 실패 | 관찰되는 증상 | 올바른 대응 |
|---------|--------------------|------------------|
| HTTP 클라이언트가 취소 알림을 POST | 서버와 클라이언트가 요청 수명에 대해 불일치 | 요청의 SSE 응답 스트림을 닫음 |
| 수용된 취소 후에 서버가 응답 | 클라이언트가 쓸 수 없는 늦은 결과를 받음 | 취소가 이기면 작업을 멈추고 이후 메시지를 억제 |
| 진행이 모든 기한을 초기화 | 멈춘 작업이 영원히 생존 | 별도의 절대 최대 타임아웃 유지 |
| 새 RPC id를 중복 제거로 취급 | 청구, 배포, 삭제가 두 번 실행 | 영속적인 애플리케이션 멱등성 키 추가 |
| 키 검사와 효과가 분리됨 | 동시 작업자가 모두 없는 키를 관찰 | 키 점유, 효과 기록, 결과를 원자적으로 커밋 |
| 복제본 사이에서 메모리 원장 사용 | 재시작이나 다른 작업자가 이전 커밋을 잊음 | 공유 영속 저장소 또는 업스트림 멱등성 사용 |
| 저장된 가변 결과를 직접 반환 | 호출자의 변경이 이후 재생을 오염 | 커밋된 결과를 직렬화하고 방어적 사본 반환 |
| 바뀐 인자로 키 재사용 | 하나의 키가 두 비즈니스 의도를 가리킴 | 인자 지문을 저장하고 비교 |
| 경계 없는 진행 큐 | 느린 소비자와 함께 메모리 상승 | 경계 안에서 대체 가능한 진행을 병합·버림 |
| 압박 상황에서 최종 응답 버려짐 | 클라이언트가 요청 결과를 알 수 없음 | 용량을 예약하거나 진행을 내보내고, 최종 응답은 절대 버리지 않음 |
| 프록시가 SSE 버퍼링 | 진행이 몰아서 도착하거나 타임아웃 이후 도착 | 버퍼링을 비활성화하고 호환되는 프록시 타임아웃 구성 |
| `Last-Event-ID` 가정 | 클라이언트가 서버가 지원하지 않는 상태에서 재개 | 새 요청으로 재접속하고 다시 가져옴 |
| 모든 클라이언트가 즉시 재접속 | 복구가 또 다른 장애를 만듦 | 상한과 지터가 있는 지수 백오프 사용 |
| 작업 확인을 최종 취소로 취급 | UI가 멈췄다고 한 뒤에도 작업자가 계속 실행 | 터미널 상태까지 Task를 폴링 |

## 캡스톤 연결

도구 생태계 캡스톤은 신뢰성을 아키텍처 다이어그램의 한 문단이 아니라 실행 가능한 증거로 다뤄야 합니다.

다음 산출물을 요구하세요:

- 전송 계층별 취소 경쟁 트랜스크립트 하나씩;
- 노출된 모든 변경을 위한 재시도 표;
- 멱등성 키 기록과 불일치 픽스처;
- 동시 같은-키 트랜스크립트, 다시 열기 검사, 변경-별칭 검사;
- 경계 있는 버퍼 과부하 결과;
- 역방향 프록시 SSE 헤더와 유휴 정책;
- 신뢰할 수 있는 다시 가져오기 메서드의 이름을 밝히는 재접속 계획;
- 캡스톤이 Task를 쓴다면 영속적인 Task 취소 트레이스.

로컬 프로세스의 녹색 요청은 행복 경로만 증명합니다. 잃어버린 응답, 늦은 취소, 느린 소비자, 재접속 무리가 결정론적 결과를 가질 때 캡스톤은 프로덕션 준비가 된 것입니다.
