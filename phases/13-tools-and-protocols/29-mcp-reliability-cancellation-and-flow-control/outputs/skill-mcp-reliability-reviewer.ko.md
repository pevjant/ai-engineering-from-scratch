요청 시작부터 실패 복구까지 하나의 MCP 작업을 검토하세요.

없으면 다음 입력을 요청하세요:

1. 전송 계층: stdio 또는 Streamable HTTP.
2. 작업 의미와 부작용.
3. 유휴 및 절대 최대 타임아웃.
4. 진행 토큰 동작과 속도 제한.
5. 재시도 정책과 비즈니스 멱등성 저장소.
6. SSE 버퍼, 프록시, 킵얼라이브, 재접속 설정.
7. 작업이 Tasks 확장을 사용한다면 영속적인 Task 동작.

다음 섹션들을 만드세요.

## 취소 회선

- stdio라면, 활성 요청 id를 참조하는 클라이언트가 보낸 `notifications/cancelled` 알림을 요구.
- Streamable HTTP라면, 그 요청의 응답 스트림 닫기를 요구. 평범한 취소 POST는 거부.
- 취소 알림에 대한 JSON-RPC 응답이 없음을 요구.
- 서버가 보내는 `notifications/cancelled`는 stdio `subscriptions/listen` 종료에만 예약.
- 취소를 모르거나, 형식이 틀리거나, 늦었거나, 불가능할 때 무슨 일이 일어나는지 명시.

## 경쟁 표

다음에 대한 결정론적 결과를 제시하세요:

| 이벤트 순서 | 서버 터미널 상태 | 최종 응답 | 클라이언트 동작 |
|------------|-----------------------|----------------|-----------------|
| 취소 후 완료 | 취소됨 | 억제됨 | 복구 계속 |
| 완료 후 취소 | 완료됨 | 보존됨 | 늦은 취소 무시 |
| 타임아웃 후 늦은 응답 | 전송 계층에 따른 취소 | 관찰된 순서에 따라 무시 또는 억제 | 안전하지 않은 재시도 전에 대조 |
| 진행 중 연결 끊김 | 취소된 진행 중 요청 | 재개 가능한 스트림 없음 | 재접속하고 다시 가져옴 |

## 기한 정책

유휴 타임아웃과 절대 최대 타임아웃을 모두 요구하세요. 진행은 유효하고, 단조 증가하고, 속도 제한이 있을 때만 유휴 시간을 초기화할 수 있습니다. 킵얼라이브 주석은 의미적 진행으로 세지 않습니다. 최대 타임아웃은 절대 초기화되지 않습니다.

## 재시도 분류

작업마다 분류 하나를 반환하세요:

- `SAFE`: 애플리케이션 계약이 부작용 없음을 증명.
- `CONDITIONAL`: 변경 작업이 동일한 인자로 재사용되는 하나의 영속적인 멱등성 키를 가짐.
- `UNSAFE`: 변경 작업에 신뢰할 수 있는 중복 제거가 없음.

새 JSON-RPC id, 도구 애너테이션, 전송 계층 재접속을 비즈니스 멱등성으로 취급하지 마세요.

조건부 재시도에는 저장된 인자 지문과 커밋된 결과를 요구하세요. 바뀐 인자로 재사용된 하나의 키를 거부하세요.

키 점유, 인자 지문, 비즈니스 효과 기록, 커밋된 결과에 대해 하나의 원자적이고 영속적인 원장 경계를 요구하세요. 프로세스 로컬 사전이나 잠금은 영속적이지 않고 복제본을 조율하지 못합니다. 공유 데이터베이스 트랜잭션, 트랜잭셔널 아웃박스, 또는 같은 키를 강제하는 업스트림 제공자를 받아들이세요. 어떤 효과가 실제로 그 경계 안에 들어가는지 명시하세요.

커밋된 결과의 방어적 사본을 반환하세요. 원장이 쥔 가변 객체를 절대 노출하지 마세요. 동시 같은-키 픽스처, 다시 열기 픽스처, 변경-별칭 픽스처로 두 성질을 모두 증명하세요.

## 흐름 제어

- 스트림별 또는 클라이언트별 명시적 용량을 설정.
- 대체 가능한 진행을 병합.
- 버려진 진행에 신뢰할 수 있는 다시 가져오기 필요 표시.
- 최종 JSON-RPC 응답을 보존.
- SSE에 `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no` 설정.
- 킵얼라이브 주기를 작업 진행과 별도로 정의.
- 경계 없는 큐를 거부.

## 재접속 계획

- 새 id로 새 요청을 엶.
- 구독 필터를 복원함.
- MCP 2026-07-28에서는 `Last-Event-ID`를 사용하지 않음.
- 영향받은 리소스, 목록, 프롬프트, Task를 다시 가져옴.
- 안전하지 않은 변경을 자동으로 재생하지 않음.
- 상한과 지터가 있는 지수 백오프를 사용함.

## 영속적인 Task

Task가 존재하면 `tasks/cancel`을 요청 취소와 분리해 두세요. 완전한 확인은 취소 의도가 수용되었음만 증명합니다. 영속적인 작업이 터미널 상태에 도달할 때까지 폴링하거나 청취(listen)하세요.

## 필수 픽스처

최소 다음 실행 가능한 시나리오들을 반환하세요:

1. 완료 전 stdio 취소;
2. 늦은 취소 전 stdio 완료;
3. 완료 전 HTTP 스트림 닫기;
4. 최대 타임아웃이 여전히 발화하는 동안 유휴 타임아웃을 초기화하는 진행;
5. 두 JSON-RPC id와 멱등성 키 없는 중복 변경;
6. 하나의 키와 동일한 인자를 가진 중복 변경;
7. 바뀐 인자로 재사용된 키;
8. 진행 버퍼를 초과하는 느린 소비자;
9. 스트림 끊김, 새 구독, 신뢰할 수 있는 다시 가져오기;
10. `tasks/cancel` 확인 후 지연된 작업자 취소.
11. 하나의 키와 동일한 인자로 경쟁하는 두 개의 독립 원장 연결;
12. 반환된 결과의 호출자 변경 후 영속적인 기록에서의 깨끗한 재생.

재시도 정책이 "타임아웃 시 재시도"로만 설명되거나, 원장이 프로세스 로컬이거나, 외부 효과가 아웃박스나 업스트림 키 없이 주장된 원자적 경계 밖에 있거나, 반환된 기록이 가변 저장소와 별칭을 공유하거나, 큐 용량이 명시되지 않으면 프로덕션 준비 판정을 거부하세요.
