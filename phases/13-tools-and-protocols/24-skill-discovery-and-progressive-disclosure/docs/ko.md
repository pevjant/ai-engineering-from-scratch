# 스킬 발견과 점진적 공개

> 스킬은 본문이 로드되기 전부터 쓸모를 갖춥니다. 이름과 description이 카탈로그의 자리를 얻고, 더 깊은 파일들은 작업이 그곳에 도달했을 때에만 컨텍스트 자리를 얻습니다.

**유형:** 빌드(Build)
**언어:** Python(표준 라이브러리)
**선수 지식:** 페이즈 13 · 22(에이전트 스킬: 이식 가능한 계약과 런타임 경계)
**시간:** 약 105분

## 학습 목표

- 스코프, 검증, 충돌 정책, 카탈로그 출판을 분리한 파일시스템 발견 파이프라인을 만듭니다.
- 세 가지 공개 수준(카탈로그 메타데이터, 활성 지침, 작업 전용 리소스)을 설명합니다.
- 에이전트가 패키지 전체를 로드하지 않고도 필요한 세부 정보에 바로 도달할 수 있게 references를 설계합니다.
- 카탈로그 공간 예산을 활성 스킬 컨텍스트 예산과 별개로 관리합니다.
- 스킬이 자기 리소스를 읽을 때 경로 탐색(path traversal)과 심볼릭 링크 탈출을 거부합니다.

## 문제 상황

에이전트에 스킬 200개가 설치돼 있다고 합시다. 세션 시작 때 모든 `SKILL.md`, 참조 파일, 스크립트, 템플릿을 로드하면 현재 작업이 무관한 절차에 파묻힙니다. 아무것도 로드하지 않으면 사용자가 정확한 파일시스템 경로를 외워야 합니다.

흔히 쓰는 타협이 카탈로그입니다. 자격이 된 스킬마다 요약된 정체성과 라우팅용 description만 모델에게 보여주고, 선택된 후에야 전체 본문을 로드합니다. 그러면 새로운 엔지니어링 문제가 두 개 생깁니다.

첫째, 발견(discovery)은 단순한 재귀 파일 탐색이 아닙니다. 스킬은 프로젝트, 사용자, 관리자, 플러그인, 내장 스코프 어디에나 있을 수 있습니다. 두 패키지가 같은 이름을 쓸 수도 있습니다. 심볼릭 링크가 신뢰 루트 밖을 가리킬 수도 있습니다. 형식이 잘못된 패키지가 카탈로그 공간을 잡아먹거나 아예 호출 불가능해질 수도 있습니다.

둘째, 점진적 공개가 점진적 혼란이 될 수 있습니다. `SKILL.md`가 "관련 가이드를 읽으세요"라고 말하는데 패키지에 가이드가 열두 개 들어 있다면, 모델은 추측할 수밖에 없습니다. 모든 가이드가 또 세 개씩 파일을 가리키면 로딩은 끝없는 그래프 탐색이 됩니다.

좋은 런타임은 발견을 결정론적으로, 공개를 의도적으로 만듭니다.

## 개념

### 발견은 컴파일러 파이프라인이다

파일시스템을 소스 입력으로 취급하세요. 날경로(raw path)를 모델에게 바로 출판하지 않습니다.

```figure
skill-discovery-pipeline
```

각 단계는 구조화된 데이터와 구조화된 실패를 산출해야 합니다. 발견 로그는 다음 질문에 답할 수 있어야 합니다:

- 어떤 루트를 검색했는가?
- 어떤 후보를 찾았는가?
- 어떤 후보가 거부됐고, 왜 그런가?
- 충돌에서 어떤 패키지가 이겼는가?
- 예산 때문에 어떤 카탈로그 항목이 줄여지거나 빠졌는가?

이 증거가 없으면 "모델이 내 스킬을 쓰지 않았다"는 문제를 거의 진단할 수 없습니다.

### 스코프는 런타임 정책이다

이식 가능한 규격은 스킬 패키지를 정의할 뿐, 만능 설치 경로나 우선순위 규칙을 정의하지 않습니다. 어디를 검색할지는 호스트가 결정합니다.

일반적인 런타임이라면 다음 스코프를 쓸 수 있습니다:

| 스코프 | 루트 예시 | 의도된 소유자 |
|---|---|---|
| 작업 공간(Workspace) | `<repo>/.agents/skills/` | 프로젝트 유지 보수자 |
| 사용자(User) | `<user-data>/skills/` | 한 명의 개발자 |
| 관리자(Administrator) | `<system>/skills/` | 머신 또는 조직 정책 |
| 플러그인(Plugin) | 서명된 플러그인 번들 | 플러그인 배포자와 설치 프로그램 |
| 내장(Built-in) | 런타임 패키지 | 런타임 벤더 |

2026년 8월 기준으로 Codex는 `$CWD/.agents/skills`에서 저장소 루트까지 조상 디렉터리를 따라 올라가는 프로젝트 발견과, 사용자·관리자·내장 위치를 문서화하고 있습니다. 심볼릭 링크된 스킬 디렉터리도 지원합니다. 이름이 겹치면 병합하지 않고 둘 다 표시할 수 있습니다. 이것들은 `SKILL.md`의 요구 사항이 아니라 Codex의 동작이므로, 어댑터를 쓸 때는 최신 [Codex 스킬 문서](https://learn.chatgpt.com/docs/build-skills)에서 확인하세요.

디렉터리 이름만 보고 우선순위를 만들어 내지 마세요. 정책으로 선언하고 테스트하세요. 이 레슨 실습은 각 `Scope`에 명시적인 정수 순위를 두어, 같은 후보 집합이면 항상 같은 방식으로 해결되게 만듭니다.

### 충돌에는 `name` 너머의 정체성이 필요하다

`release-readiness`라는 이름을 가진 패키지 둘이 동시에 정당할 수 있습니다. 하나는 작업 공간 재정의(override), 다른 하나는 사용자 기본값일 수 있죠. 따라서 카탈로그 항목에는 최소한 다음이 필요합니다:

```json
{
  "name": "release-readiness",
  "description": "Inspect a release candidate for this repository.",
  "scope": "workspace",
  "source": "/repo/.agents/skills/release-readiness",
  "selected": true
}
```

흔한 충돌 정책은 다음과 같습니다:

| 정책 | 장점 | 위험 |
|---|---|---|
| 모든 후보를 유지 | 아무것도 숨겨지지 않음 | 모델이 모호한 이름을 보게 됨 |
| 가장 높은 우선순위 스코프가 승리 | 호출이 단순함 | 로컬 패키지가 신뢰되는 패키지를 가릴 수 있음 |
| 중복 거부 | 조용한 덮어쓰기 없음 | 정당한 재정의가 동작을 멈춤 |
| 출처로 이름 한정 | 명확한 정체성 | 사용자가 보는 이름이 길어짐 |

호스트에는 정책 하나를 고르세요. 거부되거나 가려진 후보는 모델 카탈로그에 없더라도 진단 정보에는 남겨 두세요.

### 세 가지 공개 수준

Agent Skills 규격은 단계적 로딩을 묘사합니다. 핵심은 각 수준이 서로 다른 목적을 가진다는 점입니다.

```figure
skill-disclosure-levels
```

#### 수준 1: 카탈로그 메타데이터

모델은 이웃 스킬과 이 스킬을 구별할 만큼의 정보가 필요합니다. 규격은 카탈로그 항목 하나를 대략 100토큰으로 추정하지만, 실제 직렬화와 토큰화는 호스트의 몫입니다.

쓸모 있는 description은 두 절로 이루어집니다:

```yaml
description: Validate a release candidate and produce a readiness report. Use when the user asks whether a version, tag, or package is ready to publish.
```

첫 번째 절은 능력을 밝힙니다. 두 번째 절은 트리거 경계를 밝힙니다. 레슨 25가 긍정 프롬프트와 근접 실패(near-miss) 프롬프트로 이 경계를 평가합니다.

#### 수준 2: 활성 지침

활성화 후 본문은 지도이자 절차로 기능해야 합니다. 규격은 `SKILL.md`를 500줄 아래로 유지할 것을 권하지만, 이는 채워야 할 목표가 아니라 설계 신호입니다.

본문에는 다음이 들어가야 합니다:

- 작업 경계
- 기본 워크플로
- 분기 조건
- 더 깊은 파일에 대한 직접 참조
- 도구와 스크립트 계약
- 실패와 중단 동작
- 기대 출력과 그 검증 방법

진입 파일을 짧게 만들겠다고 핵심 워크플로를 참조 파일로 옮기지 마세요. 활성화는 모델이 올바르게 시작할 만큼의 컨텍스트를 반드시 제공해야 합니다.

#### 수준 3: 보조 리소스

References는 문장이나 데이터를 공급합니다. Scripts는 결정론적 계산을 제공합니다. Assets는 지침으로 취급되는 것이 아니라 복사되거나, 채워지거나, 변형되어 최종 산출물이 됩니다.

| 디렉터리 | 모델이 읽나? | 모델이 실행하나? | 전형적인 내용 |
|---|:---:|:---:|---|
| `references/` | 필요할 때 읽음 | 아니요 | 스키마, 정책, 도메인 가이드 |
| `scripts/` | 들여다볼 수는 있음 | 허용된 도구를 통해서만 | 검증기, 변환기, 수집기 |
| `assets/` | 유용할 때만 | 아니요 | 템플릿, 픽스처, 이미지, 시작 파일 |

이 이름들은 관례일 뿐 마법 같은 능력이 아닙니다. 여전히 호스트의 파일 접근과 실행 도구가 필요합니다.

### 분기별 참조가 주제 덤프보다 낫다

진입 파일을 의사 결정 지도로 쓰세요:

```markdown
## Choose the path

- For a Python package, read `references/python-release.md`.
- For a container image, read `references/container-release.md`.
- For a documentation-only release, read `references/docs-release.md`.
- If the release combines artifact types, read only the guides for those artifacts.
```

이렇게 하면 모든 참조에 관찰 가능한 로드 조건이 생깁니다. "더 보려면 `references/`를 읽으세요" 같은 말로는 안 됩니다.

참조 그래프는 얕게 유지하세요. 공식 가이드는 `SKILL.md`에서 직접 링크를 걸고 깊은 사슬을 피하라고 권합니다. 홉 한 번이면 도달 가능성을 테스트할 수 있고, 필요한 제약 조건이 컨텍스트에 들어오지 못하는 일도 줄어듭니다.

```figure
skill-reference-map
```

### 카탈로그 예산과 활성 컨텍스트는 별개의 예산이다

스킬 `i`의 직렬화된 카탈로그 비용을 `c_i`, 카탈로그 예산을 `B_c`, 활성 본문 비용을 `b_j`, 실제 로드된 리소스를 `r_k`라고 합시다.

```text
catalog_cost = sum(c_i for every published skill)
active_cost = sum(b_j for every activated skill) + sum(r_k for every disclosed resource)
```

한쪽 예산을 줄인다고 다른 쪽이 자동으로 줄지 않습니다. description을 짧게 줄여 카탈로그 공간은 아끼더라도, 활성화된 900줄짜리 본문이 여전히 작업을 질식시킬 수 있습니다. 본문을 참조로 나눠도, 런타임과 지침이 실제로 무관한 분기 로딩을 피할 때만 활성 비용이 줄어듭니다.

Codex는 현재 컨텍스트 윈도우 크기를 알 때 초기 스킬 목록에 컨텍스트 윈도우의 2퍼센트를 배정합니다. 8,000자 값은 크기를 알 수 없을 때만 쓰는 폴백이며, 2퍼센트 규칙과 합쳐진 두 번째 상한이 아닙니다. 카탈로그가 해당 예산을 넘으면 description이 줄여지거나 빠질 수 있습니다. 이 수치들은 Agent Skills 표준의 속성이 아니라 현재 Codex 정책으로 취급하세요.

### 리소스 경로는 신뢰 경계다

스킬은 자기 패키지 안의 파일만 읽어야 합니다. 문자열 접두사 비교만으로는 부족합니다:

```text
references/../../../../.ssh/config
references/external-link -> /private/company-secrets
```

파일시스템 의미론으로 패키지 루트와 후보 경로를 해석(resolve)하고, 절대 경로 입력을 거부하고, 해석된 후보가 해석된 루트 안에 남는지 확인하세요. 심볼릭 링크를 허용할지는 발견 단계 전에 결정합니다. 허용한다면 매번 해석된 대상을 검사하세요.

```figure
skill-resource-containment
```

경로 봉쇄가 내용 신뢰를 보장하지는 않습니다. 패키지 안의 유효한 참조도 악성 지침을 담고 있을 수 있습니다. 그 위협은 레슨 26이 다룹니다.

### 로딩은 관찰 가능해야 한다

시크릿을 로그에 남기지 않으면서 공개 이벤트를 기록하세요:

```json
{
  "event": "skill.resource.loaded",
  "skill": "release-readiness",
  "resource": "references/python-release.md",
  "reason": "candidate contains pyproject.toml",
  "bytes": 2840
}
```

reason 필드가 있으면 컨텍스트 선택이 검토 가능한 증거가 됩니다. "만약을 대비해" 모든 파일을 로드하게 만드는 지침을 찾아내는 데도 도움이 됩니다.

## 만들어 보기

`code/main.py`는 결정론적인 발견·공개 엔진을 만듭니다.

발견 표면에는 다음이 있습니다:

- 출처와 우선순위 메타데이터를 위한 `Scope`
- 검증 전 파일시스템 후보를 위한 `SkillCandidate`
- 바로 아래 단계의 스킬 디렉터리를 나열하는 `discover_scope(scope)`
- 선언된 정책 하나를 적용하는 `resolve_collisions(candidates, precedence)`
- 한도가 있는 메타데이터를 출판하는 `CatalogEntry`와 `build_catalog(...)`
- 문자를 만능 토큰인 것처럼 가정하지 않고 직렬화된 항목을 회계 처리하는 `CatalogBudget`

공개 표면에는 다음이 있습니다:

- 수준 2 활성화를 위한 `load_skill_body(entry, ...)`
- 경로 봉쇄를 위한 `validate_reference(skill_dir, reference)`
- 한도가 있는 수준 3 읽기를 위한 `load_reference(...)`

실습을 실행해 보세요:

```bash
cd "$(git rev-parse --show-toplevel)"
cd phases/13-tools-and-protocols/24-skill-discovery-and-progressive-disclosure
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

이 블록은 로컬 클론이 필요하며, 클론 내부의 어떤 작업 디렉터리에서든 저장소 루트를 찾아냅니다.

데모는 임시 프로젝트·사용자 스코프를 만들고, 충돌을 하나 끼워 넣고, 의도적으로 작게 잡은 예산 아래에서 카탈로그를 만들고, 스킬 하나를 활성화한 뒤, 유효한 참조 읽기와 탐색 탈출 시도를 둘 다 수행합니다. 영구 파일은 설치되지 않습니다.

### 발견이 얕은 이유

`discover_scope`는 바로 아래 자식 디렉터리에서 `SKILL.md`를 확인합니다. 중첩된 모든 `SKILL.md`를 별도 패키지로 재귀적으로 취급하지는 않습니다. 이렇게 해야 패키지 경계가 지켜지고, 설치된 스킬 안의 예제나 픽스처가 실수로 출판되는 일을 막을 수 있습니다.

### 실습이 임의의 YAML을 파싱하지 않는 이유

실습은 카탈로그에 필요한 스칼라 프론트매터만 지원합니다. 프로덕션 런타임은 명시적인 스키마, 크기 한도, 커스텀 객체 생성 비활성화를 갖춘 안전한 YAML 파서를 써야 합니다. "표준 라이브러리만 사용"은 교육용 제약일 뿐, 부분적인 YAML 방언을 몰래 만들어도 된다는 허가가 아닙니다.

## 사용해 보기

어떤 발견 어댑터에든 이 체크리스트를 적용하세요:

1. 설정된 모든 루트와 쓰기 권한자를 나열합니다.
2. 심볼릭 링크된 패키지를 허용하는지 밝힙니다.
3. 패키지 이름, 디렉터리 이름, 필수 메타데이터, 진입 본문 크기를 검증합니다.
4. 내부 정체성에 출처와 스코프를 남겨 둡니다.
5. 이름 중복 동작을 선언하고 테스트합니다.
6. 모델에 보내는 직렬화된 카탈로그의 정확한 크기를 측정합니다.
7. 본문이나 리소스를 로드한 이유를 기록합니다.
8. 리소스 읽기를 해석된 패키지 루트 안에 가둡니다.
9. 참조된 파일이 없으면 명확하게 실패합니다.
10. 설치나 정책이 바뀌면 카탈로그를 다시 만듭니다.

## 출시하기

이 레슨은 `skill-catalog-builder` 번들을 만듭니다. 명시적으로 순서가 정해진 루트를 검색하고, 심볼릭 링크된 진입 파일과 이름-디렉터리 불일치를 거부하고, 스코프를 넘는 충돌을 해결하고, 같은 우선순위의 중복을 거부하고, 선택된 메타데이터를 선언된 항목·description·직렬화 문자 예산 안에 맞춥니다.

JSON 보고서에는 선택된 항목, 가려진 후보, 빠진 항목, 검증 오류, 우선순위, 예산 사용량이 담깁니다. 본문과 참조 로딩은 별도의 런타임 작업으로 남아 있으므로, 카탈로그 빌더는 스크립트를 실행하지도 패키지 전체를 컨텍스트에 넣지도 않습니다.

## 연습 문제

1. 플러그인 스코프를 추가하고 사용자 스코프와 내장 스코프 사이 우선순위에 놓으세요. 충돌 결과를 테스트로 증명하세요.
2. 충돌 정책을 '최고 우선순위 승리'에서 '이름 한정'으로 바꾸세요. 두 항목 모두 카탈로그에 남겨 두세요.
3. `load_reference`에 바이트 크기 한도를 추가하세요. 한도에 정확히 맞는 파일과 한도보다 한 바이트 큰 파일을 테스트하세요.
4. 거의 똑같이 들리는 description 두 개를 만들어 보세요. 트리거 경계가 겹치지 않도록 다시 쓰세요.
5. 모든 참조와 스크립트의 해시를 담은 매니페스트를 추가하세요. 로드하기 전에 변경된 리소스를 탐지하세요.
6. 데모에 계측을 넣어 수준 1, 수준 2, 수준 3의 바이트 수를 따로 보고하게 하세요.

## 핵심 용어

| 용어 | 사람들이 말하는 표현 | 실제 의미 |
|---|---|---|
| 스킬 발견 | "SKILL.md를 다 찾는 것" | 설정된 스코프를 검색하고, 패키지를 검증하고, 출처를 붙이고, 정책을 적용하는 것 |
| 스킬 카탈로그 | "설치된 스킬 목록" | 자격이 된 패키지를 위한, 요약된 모델용 라우팅 메타데이터 |
| 충돌 정책 | "중복 중 누가 이기나" | 다른 출처의 같은 이름 후보에 대한 선언된 규칙 |
| 점진적 공개 | "지연 로딩(lazy loading)" | 카탈로그 → 본문 → 분기별 리소스로 이어지는 단계적 컨텍스트 수용 |
| 참조 그래프 | "스킬이 링크한 파일들" | 도달 가능한 리소스 구조와 그 로드 조건 |
| 경로 봉쇄 | "폴더 안에만 있기" | 해석된 리소스 대상이 해석된 패키지 루트 안에 남는지 확인 |
