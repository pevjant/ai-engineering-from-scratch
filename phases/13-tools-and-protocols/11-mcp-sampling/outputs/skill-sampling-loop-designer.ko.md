> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [skill-sampling-loop-designer.md](skill-sampling-loop-designer.md)

프로토콜 리비전 `2026-07-28`을 대상으로 하는 MCP 서버의 모델 보조 동작을 설계하세요.

하나의 결정에서 시작합니다: 서버가 모델 제공자와 직접 연동할 수 있는가? 새 설계에서 샘플링은 폐기되었습니다. "클라이언트의 모델과 자격 증명을 쓰는 것"이 명시적인 제품 요구사항이 아니라면 직접 연동을 선호하세요.

다음을 산출합니다:

1. 아키텍처 결정. 직접 추론 또는 호환 샘플링을 고르고 이유를 명시합니다.
2. 디스커버리 계약. 정확한 `supportedVersions`, 광고된 역량, `ttlMs`, `cacheScope`를 갖춘 `server/discover`를 보여 줍니다. 도구를 광고한다면 유효한 객체형 `inputSchema`, `resultType: "complete"`, 서버 식별 메타데이터, 캐시 힌트를 갖춘 필수·결정론적 `tools/list` 디스크립터를 포함합니다.
3. 요청 봉투. 모든 요청의 `_meta`에 프로토콜 버전과 클라이언트 역량을 넣습니다. 버전이 없거나 문자열이 아니면 `-32602`, 미지원 버전이면 정확한 `supported`·`requested` 데이터와 함께 `-32022`, 샘플링이 없으면 `requiredCapabilities` 객체와 함께 `-32021`을 사용합니다. 클라이언트 식별 메타데이터는 참고용으로만 다룹니다. id 없는 알림에는 절대 JSON-RPC 응답을 내보내지 않습니다. 수락된 HTTP 알림은 본문 없는 `202`를 받습니다.
4. 라운드 표. 각 MRTR 라운드마다 `inputRequests` 키, 포함된 요청 메서드, 기대 응답 스키마, 검증, 예산을 명시합니다.
5. 재시도 계약. 원래 메서드와 인자, 새로운 JSON-RPC id, 이번 라운드의 `inputResponses`, 바이트 단위로 동일한 `requestState`를 요구합니다.
6. 상태 보호. HMAC 또는 인증된 암호화를 인증된 주체, 메서드, 인자 다이제스트, 페이즈, 짧은 만료에 묶습니다.
7. 안전 정책. 승인, 최대 라운드 수, 토큰·바이트 한도, 응답 검증, 로깅, 거부 동작을 정의합니다.
8. 제거 계획. 샘플링이 남는다면 직접 연동으로 교체할 조건과 시점을 명시합니다.

하드 리젝(필수 반려 사항):

- 문서화된 요구사항 없이 폐기된 샘플링을 채택하는 새 설계.
- 살아있는 서버→클라이언트 요청으로 `sampling/createMessage`를 보내는 2026-07-28 서버.
- `initialize`, `notifications/initialized`, `Mcp-Session-Id`, 숨겨진 프로토콜 세션 상태의 모든 사용.
- 권한 부여, 리소스 접근, 비즈니스 로직에 영향을 주는 서명되지 않은 `requestState`.
- 원래 JSON-RPC id를 재사용하거나 원래 인자를 바꾸는 재시도.
- 역량 검사, 승인 정책, 검증, 하드 라운드 한도 없이 도는 클라이언트 모델 루프.
- `includeContext: "allServers"` 또는 암묵적인 서버 간 컨텍스트.

거부 규칙:

- 은밀한 모델 호출, 또는 사용자에게 서버의 의도를 숨기는 설계는 거부합니다.
- 신원, 권한, 사용자 동의의 증거로 쓰이는 모델 출력은 거부합니다.
- 하나의 결정론적 도구 호출로 충분한데 다중 라운드 설계를 하는 것은 거부합니다.
- 클라이언트·서버 메타데이터를 인증된 신원이라 부르는 것은 거부합니다.

결정, 와이어 흐름, 라운드 표, 서명된 상태 내용, 안전 예산, 실패 사례, 마이그레이션 계획이 담긴 한 페이지 아키텍처를 출력하세요. 마지막에 판정을 남깁니다: `direct inference`(직접 추론), `temporary MRTR compatibility`(임시 MRTR 호환), 또는 `no model required`(모델 불필요).
