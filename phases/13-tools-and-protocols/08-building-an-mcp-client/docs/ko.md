# MCP 클라이언트 만들기: 디스커버리, 라우팅, 이중 시대 폴백

> 현대 MCP 클라이언트는 모든 요청에서 자기 계약을 반복합니다. 가장 어려운 호환성 결정은 오래된 서버가 진짜 오래된 것인지, 현대 서버가 교정 가능한 에러를 보고하는 것인지 아는 일입니다.

**유형:** Build(빌드)
**언어:** Python
**선수 지식:** 페이즈 13, 레슨 07
**시간:** 약 85분

## 학습 목표

- 현재 메타데이터로 모든 MCP `2026-07-28` 요청을 만들 수 있습니다.
- `server/discover`로 stdio 서버를 탐침하고 상호 지원되는 버전을 선택할 수 있습니다.
- 명시적으로 허용 목록에 오른 피어에만 한정된 레거시 탐침을 인가할 수 있습니다.
- 지원되는 리비전에 대한 긍정적 `initialize` 결과를 검증한 후에만 레거시 시대를 받아들일 수 있습니다.
- 충돌을 조용히 덮어쓰지 않고 결정론적 도구 목록을 병합할 수 있습니다.
- 프로토콜 세션을 발명하지 않고 각 도구를 소유한 피어로 호출을 라우팅할 수 있습니다.

## 문제

에이전트 호스트는 보통 둘 이상의 MCP 서버와 이야기합니다. 각 서버를 디스커버리하고, 도구 카탈로그를 병합하고, 중복 이름을 해소하고, 호출을 라우팅하고, 전송 실패에서 복구해야 합니다.

`2026-07-28` 리비전은 각 요청이 자기 완결적이기 때문에 정상 상태를 단순하게 만듭니다. 호환성이 시작을 더 미묘하게 만듭니다. 클라이언트는 다음을 만날 수 있습니다.

- 선호 버전을 지원하는 현대 서버;
- 인식된 버전 또는 헤더 에러를 돌려주는 현대 서버;
- `server/discover`를 한 번도 들어본 적 없는 레거시 서버;
- `initialize`를 받기 전까지 침묵하는 레거시 서버.

모든 탐침 에러를 레거시로 취급하는 것은 위험합니다. 잘못된 현대 요청, 과부하 서버, 죽은 프로세스, 오래된 서버가 모두 같은 타임아웃이나 연결 종료를 만들 수 있습니다. 그 신호들은 모호합니다. 클라이언트는 레거시 시대를 선택하기 전에 명시적인 운영자 의도와 긍정적인 프로토콜 증거를 결합해야 합니다.

## 개념

### 프로토콜 세션이 아니라 피어

서버 프로세스나 엔드포인트마다 하나의 전송 피어 기록을 유지하세요:

- 전송 핸들 또는 전송 함수;
- 선택된 프로토콜 시대와 버전;
- 마지막으로 디스커버리한 서버 기능;
- 마지막 결정론적 도구 목록;
- 상관관계를 위한 대기 중인 요청 id들;
- 전송 건강 상태.

이것은 클라이언트 장부 기록입니다. 프로토콜 세션 상태가 아닙니다. 현대 MCP에서 서버는 여전히 모든 요청에서 현재 버전과 기능을 받습니다.

### 모든 현대 요청을 처음부터 만들기

```python
def modern_request(request_id, method, params, version, capabilities):
    return {
        "jsonrpc": "2.0",
        "id": request_id,
        "method": method,
        "params": {
            **params,
            "_meta": {
                "io.modelcontextprotocol/protocolVersion": version,
                "io.modelcontextprotocol/clientCapabilities": capabilities,
                "io.modelcontextprotocol/clientInfo": CLIENT_INFO,
            },
        },
    }
```

메타데이터를 연결 객체에 한 번 붙이고 와이어에 도달했다고 가정하지 마세요. 최종 직렬화된 요청에 도장을 찍고 검사하세요.

### 현대 디스커버리

`server/discover`는 지원 버전, 서버 기능, 지침, 캐시 힌트, 권장 서버 신원을 돌려줍니다. 클라이언트는 상호 지원되는 현대 버전 중 가장 높은 것을 고릅니다.

현대 전용 클라이언트에게 디스커버리는 선택 사항이지만 stdio에서는 권장됩니다. 일부 레거시 서버는 초기화 전에 작업을 받아들이므로, `tools/list`를 먼저 보내면 모호한 성공이 나올 수 있습니다. `server/discover`가 깨끗한 시대 경계를 만들어 줍니다.

### stdio 호환성 탐침

이중 시대 stdio 클라이언트는 다른 어떤 요청보다 먼저 선호하는 현대 메타데이터와 함께 `server/discover`를 보냅니다. 결과는 세 부류로 나옵니다.

1. **DiscoverResult.** 서버는 현대입니다. 상호 지원되는 버전을 선택하고 요청별 메타데이터로 계속합니다.
2. **인식된 현대 에러.** 서버는 현대입니다. `-32022`라면 `data.supported`에서 고르고 새 요청 id로 재시도합니다. 헤더나 기능 에러라면 요청을 교정합니다. `initialize`를 보내지 마세요.
3. **모호한 신호.** 인식되지 않은 JSON-RPC 에러, 타임아웃, 연결 종료, 빈 응답은 시대를 특정하지 않습니다. 그 정확한 피어가 레거시 호환성으로 설정되지 않았다면 실패로 닫습니다(fail closed).

인식되는 현대 프로토콜 에러는 다음과 같습니다.

- `-32020` HeaderMismatch
- `-32021` MissingRequiredClientCapability
- `-32022` UnsupportedProtocolVersion

인식된 현대 에러는 피어가 레거시 허용 목록에 있어도 현대로 유지됩니다. 서버가 현대 에러 어휘를 이해함을 한번 증명했다면, `initialize`를 보내는 것은 다운그레이드입니다.

`-32601`을 긍정적 레거시 증거로 취급하지 마세요. 명시적으로 허용 목록에 오른 피어에게 한 번의 레거시 탐침 자격을 줄 뿐입니다. 같은 규칙이 타임아웃, 연결 종료, 빈 응답에도 적용됩니다.

### 허용 목록은 증거가 아니라 운영자 의도

레거시 호환성은 고정된 하나의 피어 설정에 대한 명시적 속성이어야 합니다:

```python
client.add_server("archive", archive_transport, allow_legacy=True)
```

그 선택을 설정된 명령이나 엔드포인트에 묶으세요. 임의의 서버가 스스로 더 약한 의미론에 자진 들어올 수 있는 와일드카드를 쓰지 마세요. `allow_legacy=True`가 없는 피어는 모호한 디스커버리 결과 뒤에 실패로 닫히고 `initialize`를 절대 받지 못합니다.

허용 목록은 탐침 권한을 부여할 뿐입니다. 시대를 선택하지 않습니다. 클라이언트는 전송이 강제하는 마감 시한 아래에서 `initialize` 하나를 보내고, 그다음 다음 전부를 요구합니다:

- 요청 id가 맞는 JSON-RPC `2.0` 응답;
- 정확히 하나의 `result`와 `error` 없음;
- 클라이언트의 설정된 레거시 리비전 집합에 있는 `protocolVersion`;
- 객체 값의 `capabilities` 필드;
- 비어 있지 않은 `name`과 `version` 문자열 필드를 가진 `serverInfo` 객체.

타임아웃, 연결 종료, 에러 응답, 잘못된 결과, 어긋난 id, 미지원 리비전은 실패로 닫힙니다. 구조적으로 유효한 긍정 결과만이 레거시 시대를 선택합니다. 코드는 `legacy_probe_timeout_ms`를 전송 어댑터에 넘깁니다. 실제 stdio나 HTTP 어댑터는 그 마감을 기록만 하는 게 아니라 강제해야 합니다.

선택된 시대를 전송 피어에 캐시하세요. 호출마다 다시 탐침하지 마세요.

### 레거시는 호환성 분기다

한정된 탐침이 유효한 긍정적 레거시 증거를 돌려주면, 클라이언트는 선택된 레거시 버전을 그 리비전이 정의한 대로 정확히 씁니다:

1. 응답 봉투와 상관관계 id를 검증합니다.
2. 협상된 리비전이 설정된 레거시 집합에 있는지 검증합니다.
3. 검증된 기능과 서버 신원을 기록합니다.
4. 모든 검사가 통과한 후에만 `notifications/initialized`를 보냅니다.
5. 그 전송 수명 동안 레거시 요청 형태를 씁니다.

이 분기는 알려진 피어와의 상호 운용을 위해 존재합니다. 새 서버나 새 요청의 기본 설계가 아닙니다. 전송이 재시작하거나 엔드포인트가 바뀌면 피어-시대 캐시를 버리고 다시 협상하세요.

### 도구 디스커버리와 캐싱

활성 피어마다 `tools/list`를 호출하세요. 현대 결과에는 `resultType`, `ttlMs`, `cacheScope`가 포함됩니다. 올바른 인가 컨텍스트 안에서 신선도 힌트를 존중하세요. 만료 후 또는 구독된 목록 변경 이벤트 후에 다시 가져옵니다.

클라이언트는 레거시 서버의 빠진 `resultType`을 `"complete"`로 취급해야 합니다. 이전에 협상된 시대의 응답에는 현대 캐시 필드를 요구하지 마세요.

서버는 결정론적 순서를 돌려줘야 합니다. 클라이언트도 병합 전에 정렬해야 합니다. 그래야 로컬 레지스트리 순서가 프로세스 시작 타이밍에 의존하지 않습니다.

### 충돌 안전 네임스페이스 병합

두 서버가 모두 `search`를 노출할 수 있습니다. 선언된 정책을 고르세요:

1. **충돌 시 접두사.** 첫 정규 이름을 유지하고 이후 충돌은 `<server>/<tool>`로 노출합니다.
2. **충돌 시 거부.** 중복은 로드하지 않고 명확한 설정 에러를 표면화합니다.
3. **조용한 덮어쓰기.** 절대 쓰지 마세요. 어떤 서버가 모델이 선택한 행동을 받는지 숨겨 버립니다.

정규 이름과 로컬 이름을 둘 다 저장하세요. 모델은 정규 이름을 봅니다. 나가는 `tools/call`은 소유 서버가 선언한 로컬 이름을 씁니다.

### 호출 라우팅

라우팅은 순수한 조회입니다:

```text
canonical tool name
  -> peer name + local tool name
  -> new JSON-RPC request id
  -> modern request metadata or explicit legacy shape
  -> matching response id
```

소유 전송이 사용 불가하면 호출을 보내지 마세요. 전송을 재연결하거나 재시작한 다음, 디스커버리와 `tools/list`를 다시 실행하세요. 깨진 전송에서 잃은 현대 진행 중 요청은 작업의 안전 정책이 허용하면 새 JSON-RPC id로 재시도할 수 있습니다.

### 알림과 구독

현대 목록과 리소스 변경은 클라이언트가 연 `subscriptions/listen` 스트림으로만 도착합니다. 클라이언트는 알림 필터를 보내고, `notifications/subscriptions/acknowledged`를 기다리고, 알림 메타데이터의 listen 요청 id로 이벤트를 상관관계로 묶습니다.

연결이 끊기면 새 listen 요청을 열고 관련 목록이나 리소스를 다시 가져옵니다. 현대 스트림은 `Last-Event-ID`로 재개하지 않습니다.

### 서버가 시작하는 요청 없음

현대 서버는 샘플링, 일라시테이션(elicitation), 루트를 위해 클라이언트를 독립적인 JSON-RPC 요청으로 호출하지 않습니다. `input_required`를 돌려주고, 클라이언트가 내장된 입력 요청을 이행한 후 원래 요청을 재시도합니다.

입력을 이행하는 동안 피어의 응답 판독기를 막지 마세요. 상관관계를 보존하고 재시도를 위해 새 JSON-RPC id를 만드세요.

```figure
tp-client-merge
```

## 활용하기

`code/main.py`는 인프로세스 피어 함수를 써서 프로토콜 결정이 잘 보이게 합니다. 두 현대 피어와 하나의 의도적으로 허용 목록에 오른 레거시 피어에 연결한 다음, 그들의 도구를 병합하고 라우팅합니다. 전송 호출 가능 객체는 타임아웃 예산을 받으므로 호환성 분기가 무한 탐침을 숨길 수 없습니다.

```bash
cd code
python3 main.py
python3 -m unittest discover tests -v
```

테스트는 보통 데모가 놓치는 경계를 증명합니다:

- 현대 요청은 메타데이터를 반복합니다;
- `-32022`는 초기화 없이 현대 디스커버리를 재시도합니다;
- 인식된 현대 에러는 허용 목록 피어에게도 절대 다운그레이드하지 않습니다;
- 타임아웃, 연결 종료, 빈 응답, 인식되지 않은 에러는 허용 목록 없이는 `initialize`를 유발하지 않습니다;
- 허용 목록 피어는 유효하고 지원되는 `initialize` 결과 뒤에만 레거시가 됩니다;
- 잘못된 및 미지원 레거시 결과는 피어를 사용 불가 상태로 남겨 둡니다;
- 성공적으로 선택된 시대는 전송 수명 동안 캐시됩니다.

## 연습 문제

1. 가짜 서버가 상호 지원 버전 없이 `-32022`를 돌려주게 하세요. 클라이언트가 `initialize`를 보내는 대신 실패하는지 확인하세요.
2. 가짜 레거시 서버를 허용 목록에 넣고, 한정된 `initialize` 탐침이 시간 초과되게 하고, 피어가 `unknown`과 사용 불가로 남는지 증명하세요.
3. 두 인가 컨텍스트에 `cacheScope: "private"` 도구 목록을 추가하세요. 클라이언트가 한 컨텍스트의 캐시 결과를 다른 컨텍스트와 절대 공유하지 않는지 확인하세요.
4. 충돌 정책을 거부로 바꾸고, 시작이 두 피어 이름을 에러에 담아 실패하게 하세요.
5. 유한한 `subscriptions/listen` 시뮬레이터를 추가하세요. 스트림 손실 시 새 요청 id로 다시 listen하고 도구를 다시 가져오세요.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 피어(Peer) | 하나의 서버 전송과 그 디스커버리 데이터를 위한 클라이언트 쪽 기록 |
| 프로토콜 시대 | 현대의 요청별 메타데이터 또는 레거시 초기화 의미론 |
| 디스커버리 탐침 | stdio 시대를 식별하는 데 쓰는 초기 `server/discover` |
| 인식된 현대 에러 | 현대 동작을 증명하고 레거시 폴백을 금지하는 에러 |
| 레거시 허용 목록 | 고정된 피어에 대한 한정된 호환성 탐침 하나를 허용하는 운영자 설정 |
| 긍정적 레거시 증거 | 명시적으로 지원되는 레거시 리비전에 대한 유효하고 상관관계가 맞는 `initialize` 결과 |
| 병합된 네임스페이스 | 모든 활성 피어에 걸친 정규 도구 이름 |
| 충돌 정책 | 중복 도구 이름에 대한 접두사 또는 거부 규칙 |
| 시대 캐시 | 하나의 전송 피어에 저장된, 선택된 현대 또는 레거시 동작 |
| 전송 복구 | 재시작 또는 재연결, 재디스커버리, 재나열, 새 id로 안전한 재시도 |
