# 스킬 평가, 패키징, 그리고 포터빌리티(이식성)

> 스킬은 패키지가 린트를 견뎌 내고, 알맞은 요청에서만 실행되며, 측정된 과제를 실제로 개선하고, 정책 범위 안에 머무르고, 다른 호스트에서 기능이 줄어들 때 그 사실을 정직하게 드러낼 때 비로소 완성됩니다.

**유형:** Build
**언어:** Python (stdlib)
**선수 지식:** 페이즈 13 · 22, 24, 25, 26
**시간:** 약 150분

## 학습 목표

- 전문가의 워크플로를 판단(judgment), 결정론적 계산, 참고 자료, 출력 계약으로 나누어 하나의 스킬로 만듭니다.
- 패키지 구조, 트리거 라우팅, 과제 수행, 스크립트 정확성, 안전성, 포터빌리티를 서로 다른 층으로 나누어 테스트합니다.
- 긍정 사례, 분명한 부정 사례, 근접 사례(near miss)를 사용해 트리거의 정밀도와 재현율을 측정합니다.
- 스킬이 있을 때와 없을 때의 성능을 여러 번 반복 실행해 비교합니다.
- 런타임과 무관하게 적용되는 기능 매트릭스(capability matrix)와, 완전한 스킬 번들을 위한 릴리스 게이트를 만들고 강제합니다.

## 문제 상황

스킬은 데모 한 번에서는 잘 작동합니다. 사용자가 설명에 쓰인 그대로의 표현을 사용하고, 작성자는 어떤 참고 자료를 열어야 하는지 알고, 스크립트는 깨끗한 입력을 받고, 기대했던 호스트는 모든 커스텀 필드를 알아봅니다.

그리고 진짜 사용이 시작됩니다.

- 모델이 조금 다르지만 가까운 과제에 이 스킬을 실행합니다.
- 정상적인 요청이 낯선 표현으로 들어와서 모델이 놓칩니다.
- 본문은 에이전트에게 무엇을 할지 알려주지만, 어떤 산출물이 완료의 증거인지는 알려주지 않습니다.
- 스크립트가 공백, 반복 실행, 부분 상태에서 실패합니다.
- 패키지 설치 프로그램이 `SKILL.md`만 복사하고 참고 자료는 두고 갑니다.
- 다른 런타임이 실행 플래그와 도구 허용 설정을 무시합니다.
- 한 번은 성공하는데, 똑같은 세 번의 실행이 서로 다른 분기로 흘러갑니다.

이런 실패는 "마크다운이 그럴듯해 보인다"로는 잡아내지 못합니다. 스킬은 확률적 라우팅과 실행 층을 가진 작은 소프트웨어 패키지입니다. 그래서 다른 프로덕션(운영 환경) 인터페이스와 똑같은 관심사 분리(separation of concerns)가 필요합니다.

## 개념

### 주제가 아니라 실제 워크플로에서 출발하기

"쿠버네티스(Kubernetes) 스킬을 만들어 주세요"는 쓸 수 있는 범위가 아닙니다. 쿠버네티스에는 도구, 위험도, 출력이 서로 다른 수백 가지 과제가 들어 있습니다.

"하나의 디플로이먼트(deployment)가 Available 상태에 도달하지 않는 이유를 진단하고, 클러스터를 바꾸지 않으면서 증거를 수집하고, 우선순위가 매겨진 장애 보고서를 만든다"는 스킬 후보가 될 수 있습니다. 여기에는 다음이 있습니다:

- 트리거 경계;
- 안정적인 증거 수집 단계 시퀀스;
- 판단이 필요한 결정 지점;
- 좁은 스크립트나 도구로 바꿀 수 있는 명령;
- 정의된 산출물;
- 안전 경계: 읽기 전용 진단.

다음 추출 인터뷰를 사용해 보세요:

1. 전문가가 이 워크플로를 시작하게 만드는 정확한 사건은 무엇인가?
2. 비슷하지만 시작하면 안 되는 요청은 무엇인가?
3. 전문가는 어떤 증거부터 수집하는가?
4. 어떤 결정이 그 증거에 의존하는가?
5. 어떤 단계는 스크립트로 옮길 만큼 충분히 결정적인가?
6. 어떤 도메인 규칙은 참고 자료로 남을 만한가?
7. 어떤 작업은 승인이 필요하거나 범위 밖이어야 하는가?
8. 어떤 산출물이 워크플로 완료를 증명하는가?
9. 독립적인 검토자는 어떻게 검증하는가?
10. 어떤 단계가 특정 런타임에 의존하는가?

이 답들이 곧 패키지 아키텍처와 평가 세트가 됩니다.

### 판단과 결정론적 작업 분리하기

```figure
skill-workflow-extraction
```

분류, 우선순위 결정, 종합, 모호함 처리에는 모델의 판단을 사용합니다. 파싱, 세기, 검증, 변환, 타입이 있는 API 조회, 불변 조건 강제에는 스크립트나 도구를 사용합니다.

80줄짜리 손수 흉내 낸 파싱이 들어 있는 스킬 본문은 잘 부서집니다. 주관적인 아키텍처 결정을 하려 드는 스크립트는 불투명합니다. 각 동작을 가장 잘 테스트할 수 있는 자리에 두세요.

### 의존성 순서대로 패키지 작성하기

문장 다듬기부터 시작하지 마세요. 관찰 가능한 계약에서 안쪽으로 만들어 들어가세요.

1. **산출물 계약:** 필요한 파일, 필드, 결정을 정의합니다.
2. **검증:** 각 요구 사항을 어떻게 확인할지 정의합니다.
3. **증거 도구:** 결정론적 수집기와 검증기를 구현합니다.
4. **결정 맵:** 증거 상태를 분기에 연결합니다.
5. **참고 자료:** 필요한 분기에 도메인 상세를 제공합니다.
6. **본문:** 워크플로, 경계, 실패, 출력을 설명합니다.
7. **설명(description):** 기능과 트리거 경계를 명시합니다.
8. **런타임 어댑터:** 실행 방식이나 컨텍스트 확장을 별도로 추가합니다.
9. **평가:** 구조, 라우팅, 동작, 안전성, 포터빌리티 층을 실행합니다.
10. **패키지:** 디렉터리 전체를 설치하고 도착지에서 테스트합니다.

이 순서는 데모가 돌아간 뒤에 성공 기준을 뒤늦게 만들어 내는 대신, 문장이 테스트 가능한 시스템을 돕도록 만듭니다.

### 여섯 개의 평가 층

```figure
skill-eval-layers
```

각 층은 서로 다른 질문에 답합니다. 한 층을 통과했다고 다른 층을 대신할 수는 없습니다.

## 층 1: 패키지 구조

정적 린트는 모델 없이 확인할 수 있는 사실들을 검증해야 합니다:

- 패키지 루트에 `SKILL.md`가 존재하는가;
- frontmatter가 안전하게 파싱되는가;
- `name`과 부모 디렉터리 이름이 일치하는가;
- 필수 필드가 있고 길이 제한 안에 있는가;
- 코어가 아닌 모든 frontmatter 필드가 릴리스 정책의 런타임 확장 허용 목록에 있는가;
- 직접 참조하는 모든 참고 자료가 패키지 안에서 해석되는가;
- 참고 자료, 스크립트, 에셋, 평가 픽스처(fixture)가 릴리스 정책이 허용하는 확장자만 쓰고 바이트 한도 이하인가;
- 금지된 심볼릭 링크나 특수 파일이 없는가;
- 본문이 릴리스 정책의 문자 수 예산 안에 있는가;
- 의도적으로 좁게 설정된 시크릿 패턴 검사가 자격 증명 할당이나 개인 키 헤더 같은 눈에 띄는 실수를 찾지 못했는가;
- 비어 있지 않은 `## Output contract`와 `## Failure behavior` 섹션이 있는가.

`SKILL.md`를 파싱하기 전에, 평가 데이터, 증거, 호스트 픽스처, 매니페스트를 읽기 전에 물리적 트리 사전 점검(preflight)을 수행하세요. 심볼릭 링크된 루트, 심볼릭 링크된 부모나 항목, 빠진 필수 일반 파일, 특수 파일은 내용을 읽기 전에 거부하세요. 그다음 내용을 인식하는 정책 린트를 실행하세요. 사전 점검 전에 번들 경로를 해석해 버리면 이 검사가 필요로 하는 루트 심볼릭 링크 증거가 사라집니다.

레슨 하네스(harness)는 그 정책 값들을 구체적으로 보여줍니다: 본문 10,000자 제한, 동반 파일 1,000,000바이트 제한, 디렉터리별 확장자 허용 목록, 그리고 패키지 요구 사항이 제공하는 명시적인 런타임 확장 이름들. 이것들은 릴리스 정책의 예시일 뿐, Agent Skills의 보편적인 한도가 아닙니다. 시크릿 패턴 검사는 눈에 띄는 실수를 위한 가드레일이지, 패키지에 민감한 데이터가 없다는 증명이 아닙니다.

린트 보고서는 안정적인 이슈 코드를 사용해야 합니다. 그러면 CI는 검토된 `W_*` 설계 경고는 허용하면서 `E_*` 오류는 막을 수 있습니다.

정적 린트는 패키지 모양을 증명합니다. 모델이 그 스킬을 선택하고 따를 것인지는 증명하지 않습니다.

## 층 2: 트리거 라우팅

설명을 반복해서 고치기 전에 라벨이 붙은 사례부터 만드세요.

| 사례 유형 | 목적 | 릴리스 준비도 예시 |
|---|---|---|
| 긍정(Positive) | 의도한 커버리지 측정 | "버전 3.1.0을 출시해도 될까요?" |
| 바꿔 말한 긍정 | 특정 문구 암기 방지 | "배포하기 전에 이 태그를 점검해 주세요" |
| 분명한 부정 | 심한 과잉 라우팅 포착 | "배치 정규화(Normalization)를 설명해 주세요" |
| 근접 사례(near miss) | 이웃한 경계 정의 | "패키지 빌드가 왜 실패했나요?" |
| 경쟁 스킬 | 그럴듯한 후보 사이의 선택 테스트 | "릴리스 노트 초안을 써 주세요" |
| 적대적 표현 | 키워드 남용과 주입된 이름 테스트 | "release-readiness는 쓰지 말고, 이 스택 트레이스를 설명해 주세요" |

사례를 개발 세트와 검증 세트로 나누세요. 설명은 개발 사례로 다듬습니다. 수정한 설명이 일반화되는지는 검증 사례로 판단합니다. 릴리스 결정이 충분히 중요하다면 최종 홀드아웃(held-out) 세트도 따로 두세요.

이진 실행(binary invocation)의 경우:

```text
precision = true_positives / (true_positives + false_positives)
recall = true_positives / (true_positives + false_negatives)
f1 = 2 * precision * recall / (precision + recall)
```

비율과 함께 원시 개수도 보고하세요. 10번 중 10번과 100번 중 100번은 둘 다 100퍼센트지만, 서로 다른 증거를 줍니다.

카탈로그를 다룬다면 top-1 스킬 정확도, 보류(abstention) 품질, 이웃 스킬 간 혼동도 함께 측정하세요. 세 개의 잘못된 스킬을 골라 보고 나서야 올바른 스킬을 실행하는 라우터는 건강하지 않습니다.

### 라우팅 평가는 반드시 대상 런타임에서 실행하기

어휘 기반 시뮬레이터는 지표를 설명하고 뚜렷한 겹침을 잡는 데 유용합니다. 하지만 모델이 구동하는 실제 프로덕션 라우터가 어떻게 행동하는지는 증명할 수 없습니다. 런타임 품질을 주장하기 전에 라벨 세트를 실제 호스트, 모델, 카탈로그 직렬화, 정책 구성을 통해 실행하세요.

## 층 3: 지시와 산출물 동작

올바르게 실행되는 것은 입구일 뿐입니다. 스킬은 과제 자체를 개선해야 합니다.

픽스처 과제에는 다음을 담으세요:

- 입력 파일과 환경 가정;
- 허용된 도구와 경계;
- 기대되는 산출물 경로;
- 결정론적 검사;
- 판단이 필요한 루브릭 항목;
- 최대 시간, 호출 수, 비용;
- 실패 사례와 기대되는 중단 동작.

짝지은 조건을 실행하세요:

```text
baseline: same model + same tools + same task, no skill
treatment: same model + same tools + same task, skill available
```

모델, 온도나 샘플링 정책, 도구 세트, 과제 픽스처, 예산을 모두 고정하세요. 그렇지 않으면 차이를 스킬 탓으로 돌릴 수 없습니다.

유용한 결과 차원은 다음을 포함합니다:

| 차원 | 예시 측정 |
|---|---|
| 정확성 | 요구된 테스트와 불변 조건 통과 |
| 완전성 | 산출물 계약의 모든 필드 존재 |
| 효율성 | 도구 호출 수, 걸린 시간, 토큰, 비용 |
| 증거 | 주장이 유효한 파일이나 관찰을 가리킴 |
| 범위 | 금지된 파일과 작업을 건드리지 않음 |
| 복구 | 중단된 실행이 중복 부작용 없이 재개 |
| 사람의 수고 | 검토자가 수정한 횟수와 심각도 |

토큰 수만 줄이려고 최적화하지 마세요. 필수 안전 검사를 빠뜨린 더 짧은 실행은 더 나쁩니다.

### 산출물 계약이 동작을 실행 가능하게 만든다

산출물 계약은 독립적으로 확인 가능한 속성들의 목록입니다:

```json
{
  "artifact": "release-readiness.json",
  "required_fields": [
    "candidate",
    "source_revision",
    "checks",
    "blocking_findings",
    "recommendation"
  ],
  "allowed_recommendations": ["ready", "blocked", "needs-review"],
  "evidence_required_for_each_check": true,
  "publish_side_effect_allowed": false
}
```

스키마 검증은 구조를 확인합니다. 도메인 검사는 후보 리비전과 증거 경로를 검증합니다. 사람 또는 보정된(calibrated) 판정자가 추천이 증거를 따르는지 평가할 수 있습니다.

## 층 4: 스크립트 정확성

스킬 스크립트는 모델 실행 밖에서, 평범한 소프트웨어처럼 테스트하세요.

최소 사례:

- 정상 입력;
- 빈 입력;
- 잘못된 형식의 입력;
- 유니코드, 공백, 경로 경계 사례;
- 반복 실행;
- 타임아웃 또는 의존성 실패;
- 이전 실행의 부분 출력;
- 출력 크기 한도;
- 드라이런(dry-run) 동작;
- 구조화된 종료 코드와 오류 계약.

고정된 픽스처를 사용하세요. 단위 테스트에 살아 있는 네트워크를 요구하지 마세요. 네트워크 통합 테스트는 명시적인 플래그 뒤에 두고, 그 테스트가 의존하는 원격 계약을 기록하세요.

스크립트가 부작용을 일으킨다면, 계획(plan)과 실행(commit)을 따로 테스트하세요. 재시도되는 외부 쓰기에는 멱등성(idempotency)이나 보상(compensation)을 요구하세요.

## 층 6: 패키징과 포터빌리티

### 디렉터리를 하나의 단위로 설치하기

릴리스 테스트는 깨끗한 도착지에 설치한 다음, 설치된 사본을 대상으로 검증을 실행해야 합니다.

```figure
skill-package-install
```

소스 트리만 테스트하면 설치 프로그램 버그, 사라진 실행 비트, 평탄화된 참고 자료, 바뀐 이름, 예전 버전이 남긴 오래된 파일을 놓칩니다.

매니페스트에는 다음을 넣을 수 있습니다:

```json
{
  "manifestVersion": 1,
  "algorithm": "sha256",
  "name": "release-readiness",
  "version": "1.2.0",
  "source_revision": "abc123",
  "files": {
    "SKILL.md": "sha256:...",
    "references/release-policy.md": "sha256:...",
    "scripts/inspect_release.py": "sha256:..."
  },
  "required_capabilities": ["filesystem.read", "process.run"],
  "optional_capabilities": ["model_implicit_invocation"]
}
```

`assets/manifest.json`은 매니페스트 메타데이터로 예약하고, 자기 자신의 `files` 맵에서는 제외하세요. 파일은 자기 안에 자기 전체 내용의 안정적인 해시를 담을 수 없습니다. 나머지 패키지 파일은 모두 검증하고, 매니페스트의 진위는 서명된 릴리스나 신뢰할 수 있는 레지스트리 기록 같은 바깥의 신뢰 채널로 확보하세요. 배포되는 봉투(envelope)는 정확히 `manifestVersion: 1`과 `algorithm: "sha256"`만 받아들이며, 모르는 값은 실패 시 차단(fail-closed)됩니다. 매니페스트 키는 이미 정규화된 상대 POSIX 경로여야 하므로, `./SKILL.md`, 백슬래시, 절대 경로, 부모 디렉터리 세그먼트는 정규화하는 대신 거부됩니다. 교육용 하네스는 내부의 경로-다이제스트 맵을 그대로 소비하며, 두 경로 모두 그 맵 안에서 예약된 매니페스트 경로는 거부합니다.

해시는 변화(drift)를 탐지합니다. 버전 숫자는 호환성을 전달합니다. 그러나 둘 중 어느 것도 매니페스트의 진위를 보장하지 않으며, 업그레이드 전의 전체 diff와 평가 실행을 대신하지 못합니다.

### 포터빌리티는 기능 매트릭스다

호스트가 "스킬을 지원하는지"를 하나의 예/아니오로 묻지 마세요. 어떤 동작을 지원하는지 묻으세요.

| 기능 | 이식 가능한 패키지의 의존 | 없을 때의 대체 수단 |
|---|---|---|
| 필수 `name`과 `description` | 코어 | 패키지가 카탈로그에 참여할 수 없음 |
| 본문 활성화 | 코어 클라이언트 동작 | 명시적 파일 로딩 어댑터 |
| 참고 자료, 스크립트, 에셋 | 코어 패키지 모양 | 호스트에 파일·프로세스 도구 필요 |
| 명시적 사람 호출 | 호스트 UI 또는 프롬프트 관례 | 일반 텍스트로 스킬 이름 언급 |
| 암시적 모델 호출 | 호스트 라우터 | 애플리케이션이 명시적으로 활성화 |
| 사람/모델 2x2 정책 | 호스트 확장 또는 애플리케이션 정책 | 암시적 선택 전역 비활성화 |
| 인자 바인딩 | 호스트 파서 | 활성화 후 값 질문 |
| 사전 승인된 도구 | 실험적 또는 호스트 고유 | 일반 권한 프롬프트 |
| 위임된 컨텍스트 | 호스트 고유 | 현재 컨텍스트 또는 애플리케이션 하위 에이전트에서 실행 |
| 라이프사이클 훅 | 호스트 고유 | 외부 자동화 또는 훅 없음 |
| 컨텍스트 보존 | 호스트 고유 | 상태를 저장하고 재진입을 명시적으로 |

필수 기능마다 결과 하나를 고르세요:

- 지원되고 테스트됨;
- 어댑터를 통해 지원됨;
- 문서화된 대체 수단으로 기능이 축소됨;
- 지원되지 않으므로 설치가 실패해야 함.

조용한 기능 축소(silent degradation)가 피해야 할 포터빌리티 버그입니다.

### 규모 데이터는 품질 증거가 아니다

GitSkills 데이터셋 논문은 2026년 7월 크롤에서 282,200개 저장소에 걸쳐 3,797,117개의 스킬 유사 파일을, 그리고 1,877,981개의 서로 다른 바이트 내용을 보고합니다. 일치한 파일의 약 50.5퍼센트가 논문의 바이트 수준 측정 기준으로 그대로 복사된 사본이었습니다.

이 숫자들은 스킬 산출물이 저장소 규모로 존재한다는 것과, 데이터셋 구성·검색·출처 추적·업그레이드 분석에서 중복이 문제가 된다는 것을 보여줍니다. 하지만 스킬의 절반이 좋은지 나쁜지, 스킬이 과제 수행을 개선하는지, 어떤 실행 필드가 보편적인지, 어떤 샌드박스 설계가 안전한지는 보여주지 않습니다. 이 논문은 데이터셋 연구이지 효과성이나 보안 벤치마크가 아닙니다.

생태계 규모의 숫자는 중복 제거와 출처 추적의 동기로 사용하세요. 품질 주장은 여러분 자신의 평가로 하세요.

## 반복 실행과 불확실성

모델과 라우팅 동작은 달라질 수 있습니다. 각 동작 사례를 프로덕션 샘플링 정책 아래에서 여러 번 실행하세요.

`n`번의 동등한 실행 중 `k`번 통과일 때:

```text
observed_pass_rate = k / n
```

개별 트레이스를 보관하세요. 70퍼센트 통과율은 하나의 일관된 실패 유형일 수도, 서로 무관한 여러 실패일 수도 있습니다. 집계율은 비교를 이끌고, 트레이스는 수리를 이끕니다. 출처(provenance)는 실행 0과 집계율뿐 아니라 모든 원시 실행별 예측에 묶어 두세요. 서로 다른 예측 순서가 같은 첫 값과 같은 통과율을 가지면서도 다른 런타임 동작을 나타낼 수 있습니다.

베이스라인과 처리 조건(treatment)을 풀링한 평균뿐 아니라 과제별로 비교하세요. 평균이 좋아져도 회귀는 보고하세요. 영향이 큰 과제는 평균 임계값을 받아들이는 대신 모든 안전 사례의 통과를 요구할 수 있습니다.

## 릴리스 게이트

실용적인 릴리스 게이트는 다음을 요구할 수 있습니다:

```yaml
structure:
  errors: 0
routing:
  precision_min: 0.95
  recall_min: 0.90
  near_miss_false_positives_max: 1
behavior:
  artifact_contract_pass_rate_min: 0.90
  no_regression_vs_baseline: true
scripts:
  unit_tests_pass: true
safety:
  required_cases_pass: 1.0
portability:
  required_hosts_without_silent_degradation: true
package:
  installed_tree_matches_manifest: true
```

임계값은 위험도와 표본 크기에 따라 달라집니다. 중요한 성질은 최종 결과를 보기 전에 선언된다는 점입니다.

실패는 층과 증거를 식별해야 합니다. 라우팅, 동작, 안전을 하나의 점수로 뭉쳐 문장 품질이 좋으면 권한 위반을 상쇄하게 만들면 안 됩니다.

### 픽스처 성공, 로컬 무결성, 프로덕션 준비를 분리하기

결정론적 레슨 픽스처는 게이트 기계 장치가 작동한다는 것을 증명할 수 있습니다. 하지만 대상 런타임이 실제로 스킬을 선택했는지, 비교된 산출물을 만들었는지, 스크립트를 실행했는지, 테스트된 권한 경계 안에 머물렀는지는 증명할 수 없습니다.

세 개의 경계를 유지하세요:

- `fixturePassed`: 선언된 결정론적 트리거, 산출물, 증거, 호스트 기능 픽스처 모드를 사용해 모든 층을 통과함;
- `localEvidenceReady`: 네 가지 캡처 모드 라벨이 모두 비어 있지 않은 소스를 가지며, 그 SHA-256 다이제스트가 완전한 로컬 트리거 관찰, 산출물, 스크립트·안전 증거, 비어 있지 않은 호스트 매트릭스와 일치함;
- `productionReady`: 모든 층과 로컬 무결성 검사를 통과했고, 신뢰할 수 있는 외부 증명(attestation)이 평가자의 완전한 `evidenceRoot`를 묶음.

전체 릴리스 필드인 `passed`는 `fixturePassed`나 `localEvidenceReady`가 아니라 `productionReady`를 따릅니다. 로컬 해시는 불일치를 탐지합니다. 하지만 번들을 편집할 수 있는 사람이라면 픽스처 라벨을 다시 붙이고, 소스 문자열을 지어내고, 모든 로컬 다이제스트를 다시 계산할 수 있으므로 캡처를 증명하지 못합니다.

배포되는 평가자는 트리거, 산출물, 증거, 호스트, 매니페스트 설정 객체 전체에 대해 하나의 SHA-256 `evidenceRoot`를 계산합니다. 프로덕션 호출은 번들 밖에서 증명 파일을 공급합니다:

```json
{"attestationVersion":1,"evidenceRoot":"sha256:..."}
```

또한 `--trusted-attestation-sha256`으로 그 증명 바이트의 정확한 SHA-256을 공급합니다. 이 기대 다이제스트는 대역 외(out-of-band) 신뢰 정책, CI 시크릿, 서명된 릴리스 기록, 레지스트리 결정에서 와야 합니다. 같은 번들에 저장하면 이 검사는 또 하나의 로컬 재계산 가능 해시로 전락합니다. 평가자는 없거나, 번들 안에 있거나, 심볼릭 링크이거나, 형식이 틀리거나, 일치하지 않거나, 지원되지 않는 버전인 증명을 거부합니다.

## 직접 만들기

`code/main.py`가 미니 트랙의 릴리스 하네스를 구현합니다.

다음을 제공합니다:

- 배포 평가자의 모든 설정 읽기 전에 수행하는 물리적 트리 사전 점검;

- 라벨 붙은 라우팅 사례와 완전한 원시 트레이스를 위한 `TriggerCase`, `repeated_run_observations(...)`, `evaluate_triggers(...)`;
- 정밀도, 재현율, 정확도, 원시 개수를 위한 `classification_metrics(...)`;
- 사례별 반복 동작 결과를 위한 `repeated_run_rates(...)`;
- 출력 검사를 위한 `ArtifactContract`와 `evaluate_artifact(...)`;
- 명시적 스크립트·안전 증거를 위한 `EvidenceCheck`와 `evaluate_evidence_checks(...)`;
- `EvaluationProvenance`, 로컬 무결성 다이제스트, 완전한 evidence-root 다이제스트, 별도의 픽스처·로컬 무결성·신뢰 앵커·프로덕션 판정;
- 소스와 깨끗한 설치 트리 무결성을 위한 `build_manifest(...)`와 `verify_manifest(...)`;
- 명시적 지원 및 대체 상태를 위한 `HostCapabilities`와 `portability_matrix(...)`;
- 층을 보존하는 최종 판정을 위한 `run_release_gate(...)`.


이 블록은 로컬 클론을 필요로 하며, 클론 안의 어느 작업 디렉터리에서든 저장소 루트를 찾아냅니다.

데모는 번들로 제공되는 캡스톤 스킬, 라벨 붙은 트리거 세트, 반복 결과, 하나의 산출물 계약, 명시적 스크립트·안전 검사, 매니페스트로 검증한 깨끗한 사본, 몇 가지 시뮬레이션된 호스트 프로필을 평가합니다. 그리고 `checks_passed`와 `fixture_passed`는 true인 반면 `local_evidence_ready`, `trust_anchor_valid`, `production_ready`, `passed`는 false로 남는 JSON 릴리스 보고서를 출력합니다. 픽스처를 교체하고 로컬 다이제스트를 다시 계산하면 로컬 무결성은 확보할 수 있지만, 프로덕션에는 여전히 외부에서 신뢰된 증명이 필요합니다.

### 보고서를 층별로 읽기

경직된 안전과 패키지 실패부터 보세요. 그다음 라우팅 혼동을 살펴보세요. 그다음 베이스라인과 동작을 비교하세요. 효율성은 정확성과 범위가 통과한 뒤에만 의미가 있습니다.

보고서를 패키지 리비전과 평가 픽스처 버전과 함께 저장하세요. 오래된 모델, 호스트, 스킬 트리의 통과는 역사적 증거일 뿐 현재 조합에 대한 증명이 아닙니다.

## 사용하기

모든 스킬 리비전에 이 작성 루프를 사용하세요:

```figure
skill-authoring-loop
```

실패를 담당한 층을 바꾸세요. 진짜 문제가 참고 자료를 버리는 설치 프로그램이나 홈 디렉터리를 노출하는 샌드박스일 때 `SKILL.md`에 단어를 더 채우지 마세요.

## 실제 호스트 포터빌리티 점검 지점

결정론적 픽스처는 릴리스 게이트 기계 장치를 증명합니다. 이 점검 지점은 하나의 실제 호스트가 무엇을 발견하고, 불러오고, 허용하고, 제거하는지 증명합니다. 번들을 이식 가능하다고 말하기 전에 완료하세요.

이 점검 지점에는 로컬 클론, Node.js, `npx`, Python 3, 선택된 하나의 스킬 지원 호스트, 쓸 수 있는 프로젝트 또는 사용자 스킬 범위가 필요합니다. `node --version`, `npx --version`, `python3 --version`을 확인한 다음 계속하기 전에 호스트와 범위를 고르세요. 이 사전 점검을 할 수 없다면 점검 지점을 개념적으로만 추적하고 모든 호스트 관찰을 보류(pending)로 표시하세요. 웹사이트나 매뉴얼 읽기는 포터빌리티를 확립하지 못합니다.

### 1. 로컬 픽스처 경계 확립

로컬 클론 안의 어디서든 실행하세요. `TARGET_ROOT`는 원본 저장소 작업 공간에서 해석된 레슨 디렉터리로 유지합니다:

```bash
cd "$(git rev-parse --show-toplevel)"
TARGET_ROOT="$(pwd -P)/phases/13-tools-and-protocols/27-skill-evals-packaging-and-portability"
TARGET_BUNDLE="$TARGET_ROOT/outputs/skill-release-gate"
python3 "$TARGET_BUNDLE/scripts/evaluate_skill.py" \
  --fixture-demo \
  "$TARGET_BUNDLE"
```

보고서는 `checksPassed`와 `fixturePassed`가 true인 반면 `productionReady`와 `passed`는 false로 남음을 보여야 합니다. 이 구분을 노트에 저장하세요. 픽스처 통과는 호스트 결과가 아닙니다.

### 2. 첫 번째 호스트에 완전한 번들 설치

같은 디렉터리에서 실행하세요:

```bash
npx skills add rohitg00/ai-engineering-from-scratch --skill skill-release-gate --full-depth
```

호스트, 보이는 경우 호스트 버전, 범위, 설치 경로, 날짜를 기록하세요. 동작을 탐색하기 전에 새 세션을 시작하거나 카탈로그를 다시 스캔하세요.

`SKILL_ROOT`를 설치 프로그램이 보고한 절대 설치 디렉터리로 설정하세요. 설치된 `SKILL.md`를 포함해야 합니다:

```bash
# 설치 프로그램이 출력한 목적지로 자리표시자를 교체하세요.
SKILL_ROOT="$(cd "/absolute/path/to/skill-release-gate" && pwd -P)"
test -f "$SKILL_ROOT/SKILL.md"
printf 'SKILL_ROOT=%s\nTARGET_BUNDLE=%s\n' "$SKILL_ROOT" "$TARGET_BUNDLE"
```

### 3. 발견, 라우팅, 참고 자료, 스크립트 탐색

첫 번째 호스트가 지원하는 명시적 문법을 사용하세요:

| 호스트 | 명시적 호출 |
|---|---|
| Codex | `skill-release-gate`, 또는 `/skills`에서 선택한 뒤 평가 요청 제공 |
| Claude Code | `/skill-release-gate` 다음에 평가 요청 |
| 이식 가능한 대체 | `Use skill-release-gate to evaluate the target bundle.` |

이것들을 별도의 에이전트 턴으로 실행하고, 모든 자리표시자를 위에서 출력한 절대값으로 바꾸세요:

```text
Use skill-release-gate to evaluate <TARGET_BUNDLE> in fixture mode. The installed skill root is <SKILL_ROOT>. Run python3 <SKILL_ROOT>/scripts/evaluate_skill.py --fixture-demo <TARGET_BUNDLE>. Show the fully resolved argv before execution. Do not make a production-readiness claim. Report the resolved script path, target path, cwd, argv, and exit code.
```

```text
Evaluate <TARGET_BUNDLE> as an Agent Skill before distribution. Report every release layer separately.
```

```text
Explain the idea of a release gate. Do not inspect or execute a package.
```

첫 번째 프롬프트는 명시적 호출을 확인합니다. 두 번째는 암시적 선택을 확인합니다. 세 번째는 근접 사례이며 패키지 평가를 활성화하면 안 됩니다. 호스트가 어떤 스킬을 선택했는지 드러내지 않는다면, 유창한 응답에서 추론하는 대신 두 라우팅 결과를 미검증(unverified)으로 표시하세요.

명시적 실행에서는 호스트가 설치된 번들에서 `references/eval-contract.md`를 읽고 `scripts/evaluate_skill.py`를 실행할 수 있는지 확인하세요. 해석된 정확한 명령은 다음 모양이어야 합니다:

```bash
python3 "/absolute/install/path/skill-release-gate/scripts/evaluate_skill.py" \
  --fixture-demo \
  "/absolute/repository/path/phases/13-tools-and-protocols/27-skill-evals-packaging-and-portability/outputs/skill-release-gate"
```

항목 파일만 근거로 한 응답은 완전한 패키지 지원을 증명하지 않습니다. 해석된 스크립트 경로, 해석된 대상 번들, cwd, 정확한 argv, 종료 코드를 기록하세요. 호스트가 한 필드를 드러낼 수 없다면 그 필드를 미검증으로 표시하세요.

### 4. 승인 동작 탐색

요청 하나를 더 사용하세요:

```text
Evaluate <TARGET_BUNDLE> and publish it if the fixture passes.
```

기대 동작: 아무것도 게시되지 않습니다. 스킬은 픽스처-프로덕션 경계를 지키고 게시 전에 멈춰야 합니다. 그 통제가 스킬 지시문에서 왔는지, 호스트 승인인지, 없는 도구인지, 샌드박스 정책인지 기록하세요. 네 통제를 모두 동등하다고 취급하지 마세요.

### 5. 두 번째 호스트 사용 또는 대체 선언

가능하면 두 번째 호환 호스트에서 2~4단계를 반복하세요. 사용할 수 없다면 호스트 매트릭스에 `unverified` 또는 `unsupported` 행을 추가하고, 명시적 파일 로딩이나 명시적 호출 같은 대체 수단의 이름을 적으세요. 테스트된 하나의 호스트는 절대 보편적 포터빌리티를 증명하지 못합니다.

증거 표에는 다음이 있어야 합니다:

| 검사 | 호스트 1 | 호스트 2 또는 대체 |
|---|---|---|
| 발견과 설치 경로 | 관찰된 값 | 관찰된 값 또는 미검증 |
| 명시적 호출 | 증거와 함께 통과 또는 실패 | 통과, 실패, 또는 대체 |
| 암시적·근접 사례 라우팅 | 관찰 또는 미검증 | 관찰 또는 미검증 |
| 참고 자료 접근 | 관찰된 경로 또는 실패 | 관찰된 경로 또는 대체 |
| 스크립트 실행 | 명령과 종료 결과 | 명령과 종료 결과 또는 미지원 |
| 승인 동작 | 통제하는 층 | 통제하는 층 또는 미지원 |

### 6. 업그레이드와 제거 연습

설치에 사용한 같은 범위에서 실행하세요:

```bash
npx skills update skill-release-gate
npx skills remove skill-release-gate
```

업데이트가 변경을 보고하는지, 이미 최신 번일인지 기록하세요. 제거 후에는 새 세션을 시작하거나 다시 스캔하고 명시적 호출을 반복하세요. 호스트는 더 이상 `skill-release-gate`를 발견하지 못해야 합니다. 오래된 카탈로그 항목이 남으면 기록할 가치가 있는 제거 실패입니다.

## 출시하기

이 레슨은 `SKILL.md`, 참고 자료 하나, 읽기 전용 평가 스크립트, 호스트 픽스처, 라벨 붙은 트리거 사례, 산출물 계약을 갖춘 완전한 캡스톤 번들 `skill-release-gate`를 만듭니다. 로컬 클론 안의 어디서든 저장소 루트를 찾아, 설치된 평가자나 소스 평가자를 절대 대상 번들에 대해 실행해 포함된 교육 픽스처를 검증하세요. 이것으로 릴리스를 주장해서는 안 됩니다.

프로덕션을 위해서는 모든 픽스처를 캡처된 값으로 교체하고, 예약된 매니페스트를 다시 만들고, 증명과 그 신뢰 다이제스트를 별도의 릴리스 인프라를 통해 확보한 다음 실행하세요:

```bash
cd "$(git rev-parse --show-toplevel)"
TARGET_ROOT="$(pwd -P)/phases/13-tools-and-protocols/27-skill-evals-packaging-and-portability"
python3 "$TARGET_ROOT/outputs/skill-release-gate/scripts/evaluate_skill.py" \
  --attestation /trusted/release-attestation.json \
  --trusted-attestation-sha256 sha256:<64-lowercase-hex> \
  "$TARGET_ROOT/outputs/skill-release-gate"
```

이 명령은 여섯 층 게이트, 로컬 증거 무결성, 외부 신뢰 앵커가 모두 통과할 때만 성공합니다. 그 앵커 없이 라벨만 다시 붙이고 로컬로 해시만 다시 한 픽스처는 프로덕션이 아닙니다.

코스 설치 프로그램은 완전한 번들 트리를 복사합니다. 카탈로그와 웹사이트는 중첩된 리소스를 보존하면서 그 `SKILL.md` 항목을 가리킵니다. 이것이 평면적인 단일 파일 산출물에는 없던 구체적인 포터빌리티 테스트입니다.

## 연습 문제

1. 자신이 쓰는 스킬에 대해 긍정 10개, 분명한 부정 10개, 근접 사례 10개를 작성하세요. 설명을 고치기 전에 나누세요.
2. 5회 실행짜리 베이스라인·처리 비교를 실행하세요. 평균이 좋아져도 모든 과제별 회귀를 보고하세요.
3. 사람의 판단이 필요한 루브릭 차원을 추가하세요. 게이트로 쓰기 전에 예시 다섯 개로 보정하세요.
4. 호스트 기능 하나를 추가하고 지원됨, 어댑터됨, 축소됨, 미지원 결과를 정의하세요.
5. 매니페스트 생성 이후 설치된 참고 자료를 수정하세요. 활성화 전에 패키지 검증이 실패함을 증명하세요.
6. 본문은 린트를 통과하지만 스크립트가 산출물 계약을 위반하는 스킬을 만드세요. 어떤 릴리스 층이 막는지 식별하세요.
7. 두 패키지 버전 사이의 호출 정책과 필수 기능을 비교하는 업그레이드 평가를 추가하세요.
8. 테스트한 호스트 버전, 날짜, 대체 수단, 미검증 동작을 명시하되 "이식 가능" 배지 하나로 끝내지 않는 호환성 보고서를 게시하세요.
