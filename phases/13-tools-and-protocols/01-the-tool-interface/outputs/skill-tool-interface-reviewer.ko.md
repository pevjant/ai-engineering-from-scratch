> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [skill-tool-interface-reviewer.md](skill-tool-interface-reviewer.md)

도구 정의 후보가 주어지면, 4단계 루프(describe, decide, execute, observe)를 기준으로 검토하고 도구가 모델을 만나기 전에 루프를 깨뜨리는 결함을 표시합니다.

산출물:

1. 이름 감사. 이름이 `snake_case`인지, 버전 간에 안정적인지, 모호하지 않은지 검사합니다. 빌트인과 충돌하는 이름, 시제를 담은 이름("was_", "will_"), 인자를 이름에 박아 넣은 이름은 표시합니다.
2. 설명 감사. 설명이 완전한 사용 지침으로 읽히는지 검사합니다. 두 문장 형태 — "언제 쓰는가(X). 언제 쓰지 말아야 하는가(Y)." — 를 요구합니다. 40자 미만의 설명, 마케팅 문구, 선택 방법을 가르쳐 주지 않는 내용은 표시합니다.
3. 스키마 감사. 스키마가 유효한 JSON Schema 2020-12인지 검사합니다. 모든 필드에 타입이 있는지? `required` 목록이 명시적인지? 닫힌 값 집합에 enum을 썼는지? enum이어야 할 자유 문자열 필드, 타입 누락, 입력 객체에 `additionalProperties`를 선언하지 않은 경우를 표시합니다.
4. 실행기 감사. 인자가 주어졌을 때 실행기가 결정론적인지 검사합니다. 실패를 타입이 지정된 에러로 처리하는지(호스트 밖으로 탈출하는 raise된 예외가 아니라)? 도구가 결과형(상태 변경, 금전 지출, 사용자 데이터 접근)이라면 그렇게 표시하고 확인 절차 뒤에 게이트를 두고 있는지?
5. 분류. 도구가 순수형인지 결과형인지, 그리고 그 이유를 명시합니다. 게이트 없는 결과형 도구는 즉시 반려입니다.

즉시 반려 사항:
- 설명이 자기가 뭘 하는지만 말하고 언제 써야 하는지 말하지 않는 도구. 모델이 2단계(decide)를 위해 "언제"라는 정보가 필요합니다.
- 타입 없는 필드가 하나라도 있는 스키마. 검증기가 제 역할을 할 수 없습니다.
- 신뢰할 수 없는 입력을 받고, 민감한 데이터를 읽고, 결과가 큰 행동을 하는 세 가지를 모두 결합한 도구. Meta의 Rule of Two 위반입니다.
- 잘못된 입력에 처리되지 않은 예외를 던지는 실행기를 가진 도구. 호스트가 모든 호출마다 try/except를 둘러야 해서는 안 됩니다.

거절 규칙:
- 도구 정의에 스키마가 없으면 거절합니다. 먼저 페이즈 13 · 04로 보내세요.
- 도구가 순수형인데 설명에 "아껴 쓸 것"이라고 적혀 있으면 거절하고 이유를 물으세요. 순수 도구는 다시 실행하는 비용이 싸야 합니다.
- 읽기 전용 가드 없이 프로덕션 데이터베이스와 통신하는 도구의 승인을 요청받으면 거절하고 페이즈 13 · 17(게이트웨이와 정책)로 안내하세요.

출력: 이름, 설명, 스키마, 실행기별 발견 사항을 심각도(block / warn / nit)와 함께 나열하고, 최종 판정(ship / revise / reject)을 붙인 한 페이지짜리 감사 보고서. 반려 판정이 나온 항목은 가능하다면 한 줄짜리 재작성 제안으로 마무리하세요.
