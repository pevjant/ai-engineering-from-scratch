# MCP 적합성(Conformance) 엔지니어링: 버전 관리, 증거, 운영

> SDK 하나로 정상 경로가 동작했다고 해서 서버가 적합한 것은 아닙니다. 적합성은 와이어(전송되는 실제 바이트) 위에서, 버전 경계에서, 중개자를 거치는 구간에서, 롤백하는 시점에 존재합니다.

**유형:** Build
**언어:** Python
**선수 지식:** 페이즈 13 · 09 (트랜스포트), 페이즈 13 · 17 (게이트웨이), 페이즈 13 · 30 (레지스트리 입장 심사)
**시간:** ~100분

## 학습 목표

- MCP의 규범적(normative) 규칙을 골든 트랜스크립트와 네거티브 트랜스크립트라는 실제 전송 기록으로 바꿔 봅니다.
- 엄격한 `2026-07-28` 동작과 범위가 제한된 레거시 폴백(fallback)을 확실히 분리합니다.
- (미래를 위해) 추가된 알 수 없는 필드와 잘못된 알 수 없는 `resultType`을 구분합니다.
- raw JSON-RPC 증거와 SDK가 정규화한 뷰를 비교합니다.
- 실제 프록시 경계를 통과한 뒤에도 헤더와 본문의 무결성이 지켜지는지 증명합니다.
- 레닥션(민감 정보 삭제)을 마친 트랜스크립트, 헬스, 롤백 증거로 릴리스를 통제합니다.

## 문제 상황

클라이언트가 SDK를 통해 `tools/list`를 호출하고 도구 목록을 받습니다. 통합 테스트도 통과합니다.

하지만 그 결과만으로는 중요한 질문들에 답이 남아 있습니다:

- 요청이 최신 방식의 요청별 프로토콜 메타데이터를 실어 보냈을까요?
- `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` 헤더가 JSON-RPC 본문과 일치했을까요?
- 응답이 와이어 상에서 유효한 `resultType`을 담고 있었을까요, 아니면 SDK가 없는 값을 만들어 낸 걸까요?
- 클라이언트는 미래에 추가될 필드를 그대로 보존할 수 있을까요?
- 알려진 최신 오류가 실수로 레거시 핸드셰이크를 촉발하지는 않을까요?
- 프록시는 오리진(origin, 원본 서버)의 상태 코드와 JSON-RPC 오류를 그대로 전달했을까요?
- 알림(notification) 직렬화기가 금지된 응답을 내보내지는 않았을까요?
- 운영팀은 시크릿을 저장하지 않고도 릴리스가 승격되거나 롤백된 이유를 증명할 수 있을까요?

적합성(conformance)은 관측 가능한 불변식(invariant, 언제나 참이어야 하는 규칙)의 모음입니다. 프로덕션(운영 환경) 트래픽이 이를 뼈저리게 발견하기 전에, 그 불변식들을 잡아 내는 테스트 하네스를 만드세요.

```figure
mcp-conformance-operations
```

## 버전 시대(era)부터 이해하기

MCP `2026-07-28`은 요청 하나하나에 온전히 담기는(self-contained) 메타데이터를 사용합니다. 최신 방식의 요청은 `params._meta.io.modelcontextprotocol/protocolVersion`과 `params._meta.io.modelcontextprotocol/clientCapabilities`을 실어 보냅니다. 네임스페이스가 붙은 정확한 키 이름이 중요합니다. `protocolVersion`이나 `clientCapabilities`라는 별칭만 달랑 있는 요청은 잘못된 형식입니다. HTTP 경계에서 미러링된 라우팅 헤더가 존재한다면, 그 값은 JSON-RPC 본문과 일치해야 합니다. 최신 방식의 성공 결과에는 `resultType`이 들어 있습니다.

`2025-11-25`까지의 버전은 그 이전의 초기화(initialization) 시대를 사용합니다. `resultType`이 없는 레거시 결과는 클라이언트가 그 이전 시대를 선택한 후에야 완료로 해석됩니다.

두 형식을 한꺼번에 받아 주는 관대한 검증기 하나를 만들지 마세요. 두 갈래로 나누세요:

| 분기 | 진입 증거 | `resultType` 누락 | 초기화 |
|---|---|---|---|
| 최신 | 성공한 `server/discover` 또는 알려진 최신 응답 | 잘못됨 | 기본 경로가 아님 |
| 레거시 | 설정된 허용 목록 + 최신 프로브가 판단 불가로 끝난 뒤의 유효한 레거시 `initialize` 결과 | 완료로 해석 | 그 시대에서는 필수 |

이 분리 덕분에 잘못된 형식의 최신 피어가 "더 느슨한 검증"이라는 보상을 받는 일을 막을 수 있습니다.

### 엄격 모드

엄격 모드는 최신 동작의 증거를 요구합니다. 성공한 `server/discover`는 최신 분기의 증거입니다. 알려진 최신 JSON-RPC 오류 역시 증거가 됩니다. 요청을 고치거나 중단하세요. 서버가 `-32020`, `-32021`, `-32022`를 반환했다는 이유로 다운그레이드해서는 절대 안 됩니다.

### 폴백 모드

폴백 모드는 범위가 제한된 최신 프로브를 한 번 수행합니다. 타임아웃, 빈 응답, 끊긴 연결, 알 수 없는 응답은 "판단 불가"일 뿐입니다. 피어가 레거시라는 증거가 아닙니다. 호환성을 위해 명시적으로 설정되었거나 허용 목록에 오른 엔드포인트만 그다음 단계로 범위가 제한된 레거시 프로브를 받을 수 있고, 클라이언트는 그 프로브의 `initialize` 결과와 협상된 레거시 리비전을 검증한 뒤에야 레거시 분기를 선택합니다.

폴백은 "아무 오류나 나면 레거시를 시도"가 아닙니다. 알려진 최신 오류에는 유용한 수정 정보가 담겨 있습니다. 그 뒤에 다운그레이드하면 헤더 불일치, 누락된 기능 선언, 지원하지 않는 버전 같은 문제를 덮어버릴 수 있습니다.

이렇게 하면 공격자, 장애, 필터링 프록시가 최신 응답을 가로채서 다운그레이드를 강요하는 일을 막을 수 있습니다. 엔드포인트 정책, 판단 불가였던 최신 관측 결과, 명확한 레거시 긍정 증거, 선택된 시대를 함께 기록하세요.

모든 트랜스크립트 옆에는 선택된 시대를 함께 기록하세요. 이 정보가 없으면 같은 누락된 필드가 어떤 테스트 실행에서는 괜찮아 보이고 다른 실행에서는 잘못되어 보일 수 있습니다.

## 트랜스크립트 코퍼스 만들기

트랜스크립트 픽스처(fixture, 고정된 테스트 입력)는 SDK 호출만이 아니라 경계를 실제로 오간 것이 무엇인지 기록합니다:

```json
{
  "name": "golden-modern-list",
  "era": "modern",
  "headers": {
    "MCP-Protocol-Version": "2026-07-28",
    "Mcp-Method": "tools/list"
  },
  "request": {
    "jsonrpc": "2.0",
    "id": 1,
    "method": "tools/list",
    "params": {
      "_meta": {
        "io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {}
      }
    }
  },
  "responseStatus": 200,
  "responseBody": {
    "jsonrpc": "2.0",
    "id": 1,
    "result": {
      "resultType": "complete",
      "tools": []
    }
  }
}
```

픽스처는 두 부류로 관리하세요.

### 골든 트랜스크립트

골든 트랜스크립트는 받아들여져야 하는 동작을 증명합니다:

- 메타데이터와 헤더가 일치하는 최신 discovery 또는 메서드 요청
- 필수 필드를 갖춘 완료 결과
- 메서드가 입력을 더 요구할 수 있을 때의 `input_required` 결과
- 해당 기능(capability)이 광고된 경우에만 나오는 확장 결과
- `resultType`이 없는 레거시 결과 — 단, 선택된 레거시 시대에서만
- JSON-RPC 응답 없이 처리되는 알림(notification)

골든 트랜스크립트는 커다란 것이 아니라 정밀한 것이어야 합니다. 매번 달라지는 ID와 타임스탬프는 결정적으로 고정하거나 비교 전에 정규화하세요.

### 네거티브 트랜스크립트

네거티브 트랜스크립트는 거부 동작을 증명합니다:

- 헤더와 본문의 불일치
- 요청별 기능(capabilities) 누락
- 매칭됐지만 지원하지 않는 프로토콜 버전
- 최신 응답에 `resultType` 누락
- 알 수 없거나 광고되지 않은 `resultType`
- `2.0`이 아닌 응답 `jsonrpc`, 또는 값이나 JSON 타입이 다른 ID
- `result`와 `error`를 둘 다 담거나 둘 다 없는 응답
- 정수 `code`와 문자열 `message`가 없는 오류
- 알려진 프로토콜 오류가 잘못된 HTTP 상태로 매핑된 경우
- 알림에 대해 내보낸 응답
- 잘못된 형식의 JSON-RPC 봉투(envelope)
- 프록시가 프로토콜 오류를 뭉개버린 경우

각 네거티브 케이스마다 거부 경계와 안정적인 오류 코드를 단언(assert)하세요. "호출이 실패했다"로는 너무 약합니다. 프록시가 만들어 낸 500과 오리진의 `-32020`은 둘 다 실패처럼 보이지만, 운영자에게는 완전히 다른 이야기를 들려줍니다.

헤더 불일치 픽스처에는 요청 ID가 일치하고 오류 코드가 `-32020`인 서버의 실제 HTTP 400 JSON-RPC 응답이 반드시 포함되어야 합니다. 로컬 검증기가 `HeaderMismatch`를 관측할 때마다 이를 자동으로 강제하세요. 응답 검증을 선택적 픽스처 플래그로 만들면 안 됩니다. 로컬 거부 코드가 올바랐더라도 HTTP 500에 빈 본문인 케이스는 실패입니다. 자기 요청 검증기가 예외를 던지는 것으로 끝나는 하네스는 서버가 아니라 자기 자신만 테스트한 것입니다.

공식 MCP 적합성 프로젝트는 외부 스위트이자 버전별 참고 자료로 유용합니다. 하지만 로컬 트랜스크립트도 함께 유지하세요. 여러분의 프록시, SDK, 인증, 확장, 릴리스 경로는 범용 스위트가 알 수 없는 부분이고, 로컬 트랜스크립트가 바로 그것을 잡아 줍니다.

## 헤더 값은 RPC 본문과 일치해야 합니다

최신 Streamable HTTP에서 중개자는 미러링된 헤더로 라우팅하거나 정책을 적용할 수 있습니다. 하지만 프로토콜의 진실의 원천(source of truth)은 JSON-RPC 본문입니다. 불일치는 "둘 중 하나를 고르라"는 힌트가 아니라 무결성 실패입니다.

이 순서로 검증하세요:

1. JSON-RPC 봉투와 메타데이터 타입을 파싱하고 검증합니다.
2. `MCP-Protocol-Version`과 `params._meta.io.modelcontextprotocol/protocolVersion`을 비교합니다.
3. `Mcp-Method`와 `method`를 비교합니다.
4. 메서드에 라우팅 이름이 있으면 `Mcp-Name`과 본문의 해당 값을 비교합니다.
5. 일치가 확인된 후에야 매칭된 버전과 기능 집합이 지원되는지 판단합니다.

이 순서 덕분에 불일치 `-32020`과 미지원 버전 `-32022`를 구별할 수 있습니다. 게이트웨이가 헤더 이름을 승인해 주는데 오리진은 본문의 다른 이름을 실행하는 상황도 막아 줍니다.

HTTP 필드 이름은 대소문자를 구별하지 않지만, 값은 대소문자를 구별합니다. 조회 전에 헤더 이름을 정규화하고 서로 충돌하는 중복은 거부하세요. 안전하지 않거나, 비 ASCII이거나, 앞뒤 공백이 있는 `Mcp-Name`은 본문과 비교하기 전에 정확히 `=?base64?{Base64EncodedValue}?=` UTF-8 센티널(sentinel, 표시용 인코딩 마커)로 디코딩해야 합니다. 불완전한 센티널, 잘못된 Base64, 잘못된 UTF-8, raw 상태의 안전하지 않은 값은 `-32020`으로 거부합니다. 본문에 같은 문자가 있더라도 raw 상태의 앞뒤 공백은 잘못된 값입니다. 그런 값은 전송 전에 센티널 인코딩이 필요했어야 하기 때문입니다.

중개자는 요청이 MCP 서버에 도달하기 전에 잘못된 형식의 HTTP를 거부할 수 있습니다. 그래서 그 실패는 JSON-RPC 없이 HTTP 오류일 수 있습니다. 거부가 중개자에서 왔는지 오리진에서 왔는지 구분해서 기록하세요. 오리진 MCP 서버는 유효한 JSON-RPC 요청을 처리했을 때 프로토콜 오류 계약을 사용해야 합니다.

## 알 수 없는 필드는 알 수 없는 결과가 아닙니다

포워드 호환성(미래 버전을 미리 수용하는 호환성)에는 두 가지 서로 다른 규칙이 필요합니다.

### 추가된 알 수 없는 필드

결과 객체와 `_meta` 맵에는 필드가 추가될 수 있습니다. 검증기는 자신의 역할에 따라 추가된 필드를 보존하거나 무시해야 합니다. 단, 그 필드가 예약된 계약을 위반하는 경우는 예외입니다. 샘플은 raw 결과 전체를 증거로 보관하고, 알려진 결과 옆의 `futureHint`는 받아들입니다.

투명 프록시라면 알 수 없는 필드를 벗겨내기보다 보존하는 편이 보통 더 안전합니다. 애플리케이션 클라이언트라면 무시하는 것이 유효할 수 있습니다. 다만 차이 비교 테스트가 "SDK가 이 필드를 빼먹었다"는 사실을 드러내 줘야, 그 동작이 의도된 것인지 판단할 수 있습니다.

### 알 수 없는 `resultType`

`resultType`은 판별자(discriminator, 결과의 종류를 가려 내는 표지)입니다. 핵심 최신 결과는 `complete` 또는 `input_required`를 사용합니다. 확장은 자신의 기능이 광고된 경우에만 다른 값을 추가할 수 있습니다. 예컨대 Tasks 확장은 협상된 기능 컨텍스트 안에서 `task`를 추가할 수 있습니다.

알 수 없거나 광고되지 않은 판별자를 완료로 안전하게 취급할 수는 없습니다. 클라이언트는 자신이 어떤 라이프사이클을 버리는지 알지 못합니다. 거부하세요.

그래서 하나의 raw 응답이 "괜찮은 알 수 없는 필드"와 "괜찮지 않은 알 수 없는 결과 타입"을 동시에 담을 수 있습니다. 두 케이스를 모두 테스트하세요.

판별자는 첫 번째 층일 뿐입니다. 그다음에 메서드별 페이로드를 검증해야 합니다. 완료된 `tools/list` 결과에는 `tools` 배열이 필요하고, 그 설명자(descriptor)들은 서로 겹치지 않는 비어 있지 않은 이름, 유용한 설명, 객체 루트의 `inputSchema` 값을 가져야 합니다. `task` 결과는 Tasks 기능이 있는 적격한 `tools/call`에 대해서만 유효하며, `taskId`, 알려진 상태, 생성·수정 타임스탬프, `ttlMs`가 필요하고 선택적인 폴링 간격도 유효해야 합니다. 완료된 `completion/complete` 결과에는 문자열 값을 100개 이하로 담는 `completion` 객체와, 반환된 값보다 작지 않은 선택적 음수 아닌 정수 `total`, 선택적 불리언 `hasMore`가 필요합니다. `resultType`의 철자가 완벽하다고 해서 잘못된 형식의 페이로드가 적합해지지는 않습니다.

## 알림 불변식

JSON-RPC 알림(notification)에는 `id`가 없습니다. 수신자는 JSON-RPC 성공 응답이나 오류 응답을 보내서는 안 됩니다.

받아들여지는 HTTP 알림 형태에 대해 하네스는 빈 본문을 가진 HTTP `202`를 기대합니다. MCP `2026-07-28`은 Streamable HTTP 위의 핵심 클라이언트→서버 알림을 정의하지 않습니다. 샘플은 일방향 직렬화기 불변식을 테스트하기 위해서만 네임스페이스가 붙은 코스 확장 알림을 사용합니다. 이를 새로운 핵심 메서드로 소개해서는 안 됩니다.

핸들러만이 아니라 직렬화기를 테스트하세요. 핸들러는 `None`을 반환했는데 미들웨어가 그것을 JSON 성공 객체로 감쌀 수 있습니다. 최종 이그레스(egress, 외부로 나가는) 바이트를 캡처하세요.

## SDK 차이 비교(SDK differential) 추가하기

SDK는 와이어 객체를 편리한 언어 타입으로 바꾸는 경우가 많습니다. 편리하지만, 정규화된 객체만으로는 실제로 무엇을 받았는지 증명할 수 없습니다.

위험도가 높은 모든 픽스처에 대해 다음을 캡처하세요:

1. SDK 디코딩 전의 raw 상태 코드, 헤더, 응답 본문
2. SDK가 정규화한 반환값 또는 예외
3. 선택된 시대에서 기대되는 의미적 투영(projection)
4. SDK가 옮겨 담거나, 만들어 내거나, 벗겨 내거나, 바꾼 필드

샘플은 애플리케이션 페이로드를 비교할 때 `resultType`, `_meta`, `ttlMs`, `cacheScope` 같은 알려진 와이어 부기(bookkeeping) 필드가 SDK 쪽에서만 제거되는 것은 허용합니다. 하지만 `futureHint`가 사라지면 보고합니다. 알 수 없는 의미 필드가 사라진 것이기 때문입니다.

모든 차이를 SDK 버그로 단정하지 마세요. 요점은 변환을 눈에 보이게 하는 것입니다. 내 컴포넌트가 (추가 필드를 무시해도 되는) 애플리케이션 엔드포인트인지, (보존해야 하는) 투명 중개자인지 판단하세요.

출시하는 모든 SDK와 버전에 대해 차이 비교를 실행하세요. 두 SDK가 같은 트랜스크립트를 다르게 정규화한다면, 릴리스 정책이 어느 동작이 허용되는지 정해야 합니다. 나중에 편한 쪽을 골라서는 안 됩니다.

## 프록시 증거 수집하기

프로덕션 MCP 장애는 대부분 둘 이상의 프로세스를 거치는 동안 발생합니다. 세 가지 뷰를 기록하세요:

| 뷰 | 최소 증거 |
|---|---|
| 인그레스(ingress, 들어오는 쪽) | 요청 헤더, JSON-RPC 본문, 콘텐츠 타입, 인증된 라우트, 수신 시각 |
| 오리진(origin, 원본 서버) | 전달된 헤더와 본문 다이제스트, 오리진 상태 코드, 응답 헤더와 본문 |
| 이그레스(egress, 나가는 쪽) | 클라이언트가 보는 상태 코드, 헤더, 본문, 전송 시각 |

샘플은 두 가지 흔한 변환을 탐지합니다:

- 오리진의 HTTP 400 또는 404 JSON-RPC 오류가 프록시의 만능 500으로 바뀜
- 이그레스 JSON-RPC 본문이 오리진 본문과 다름

콘텐츠 타입, `Accept`, 압축, 요청 범위 SSE, 캐시 헤더, 트레이스 상관관계에 대해서는 배포 환경에 맞는 단언을 추가하세요. 정책이 허용하면 TLS 종단 양쪽을 캡처하세요. 경로를 증명한다는 이유로 자격 증명을 로그에 남기는 일은 절대 없어야 합니다.

## 증거가 메모리를 떠나기 전에 레닥션(redaction)하기

레닥션(민감 정보 삭제)은 나중에 하면 되는 청소 작업이 아니라 적합성 운영의 일부입니다. 직렬화, 해싱, 로그, 테스트 산출물, 장애 업로드보다 먼저 적용하세요.

샘플은 매칭 전에 키 이름의 대소문자를 통일하고 구분 기호를 제거한 뒤, `Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key`, `accessToken`, `clientSecret`, `registrationAccessToken`, `token`, `password`, `secret`, `api_key` 같은 키 아래의 값을 재귀적으로 다른 값으로 바꿉니다. 정규화(canonicalization)와 거부 목록이 같은 형태를 사용해야 camelCase, 하이픈, 밑줄, 점 변형이 서로의 정책을 우회할 수 없습니다. 프로덕션 수집기라면 메서드별 인자 정책을 추가해야 합니다. `query` 같은 무해해 보이는 키에도 개인정보나 규제 대상 데이터가 들어 있을 수 있기 때문입니다.

레닥션을 마친 증거 번들은 해시하세요. raw 캡처는 구체적인 조사에서 필요할 때 승인된 단기 보관 시스템에만 두세요. 다이제스트는 "어떤 레닥션된 번들이 그 결정을 만들었는지"를 증명할 뿐, 삭제된 값을 드러내지는 않습니다.

## 헬스와 롤백을 게이트의 일부로 만들기

프로토콜 적합성은 릴리스에 필요하지만 충분하지는 않습니다. 적합한 후보도 타임아웃이 나거나, 메모리를 샜거나, 의존성에 과부하를 줄 수 있습니다.

배포 전에 헬스 윈도우(관측 구간)를 정의하세요:

- 최소 샘플 수
- 최대 오류율
- 최대 지연 시간 백분위
- 포화도 또는 자원 한도
- 관측 기간
- 승인된 베이스라인과의 비교

롤백 증거도 배포 전에 정의하세요:

- 정확한 이전 버전
- 입장 심사 증거 다이제스트
- SHA-256 아티팩트·설명자 핀(pin)
- 현재 레지스트리 상태
- 현재 헬스 결과
- 라우트 복원 절차
- 신뢰할 수 있는 릴리스 컨트롤러 신원이 그 정확한 필드들에 대해 발행한 증명서(attestation)

롤백 대상이 후보가 실패한 뒤가 아니라 승격(promotion) 전에부터 검증되고 건강한 상태여야 한다고 요구하세요. 쓸 수 있는 복구 경로가 없는 성공적인 릴리스는 프로덕션 준비가 된 것이 아닙니다.

후보가 실패했는데 롤백 대상에 그 증거가 없다면, 추측 대신 트래픽을 멈춰 두세요. "그 자리에 있던 뭐든 롤백"은 운영 통제가 아닙니다.

준비 상태를 "버전이 비어 있지 않다", `healthy: "yes"`, 아무 문자열 증거 같은 참 같은 값(truthiness) 검사로 축소하지 마세요. 샘플은 정확한 타입, 활성 상태, SHA-256 다이제스트 세 개, 신뢰할 수 있는 서명자, 롤백 페이로드 전체에 대한 유효한 HMAC-SHA-256 증명서를 요구합니다. 샘플의 결정적 데모 키는 비밀이 아닌 픽스처입니다. 프로덕션에서는 릴리스 경계에 보호된 키, KMS 검증 결과, 공개키 증명서 검증기를 주입하세요.

릴리스 게이트는 비어 있는 트랜스크립트, SDK 차이 비교, 프록시 증거도 거부합니다. 각 소스는 유효한 증거 다이제스트를 가져야 합니다. 초록불 헬스 윈도우로는 한 번도 관측되지 않은 경계를 메울 수 없습니다.

## 만들어 보기

표준 라이브러리 하네스를 실행해 보세요:

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations
python3 code/main.py
```

데모는 정확히 열다섯 개의 골든·네거티브 트랜스크립트(유효한 completion 결과와 잘못된 completion 결과 포함)를 실행하고, raw 결과를 SDK 뷰와 비교하고, 오리진 오류를 뭉개버린 프록시를 검사하고, 헬스를 평가하고, 롤백 증거를 인증하고, 그 대상을 선택합니다.

기대되는 형태:

```json
{
  "transcriptsPassed": 15,
  "transcriptsTotal": 15,
  "sdkDroppedFields": ["futureHint"],
  "proxyIssues": [
    "proxy collapsed a protocol error into HTTP 500",
    "proxy changed the origin JSON-RPC body"
  ],
  "releaseAction": "rollback",
  "evidenceDigest": "..."
}
```

`code/main.py`를 이 순서로 읽어 보세요:

1. `validate_request()`는 시대별 요청·헤더 규칙을 강제합니다.
2. `validate_result()`는 누락된 레거시 판별자, 유효한 최신 값, 확장, 알 수 없는 값을 구분합니다.
3. `select_era()`는 엄격 모드와 범위가 제한된 폴백 정책을 구현합니다.
4. `run_transcript()`는 골든·네거티브 픽스처를 평가합니다.
5. `compare_sdk_view()`는 정규화 차이를 드러냅니다.
6. `inspect_proxy()`는 인그레스·오리진·이그레스 증거를 비교합니다.
7. `redact()`는 증거 해싱 전에 뻔한 시크릿을 제거합니다.
8. `rollback_evidence_ready()`는 정확한 핀 필드와 신뢰할 수 있는 릴리스 증명서를 검증합니다.
9. `ReleaseGate.evaluate()`는 비어 있지 않은 적합성·SDK·프록시·헬스·롤백 증거를 하나로 합칩니다.

## 인터랙티브 랩

### 랩 A: 시대 경계 증명하기

`code` 디렉터리에서 파이썬을 열어 보세요:

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations/code
python3 -q
```

실행:

```python
from main import *
validate_result({"tools": []}, "legacy")
validate_result({"tools": []}, "modern")
```

레거시 호출은 `complete`로 추론합니다. 최신 호출은 `ProtocolViolation`을 일으킵니다. 이제 폴백을 테스트해 보세요:

```python
select_era({"kind": "timeout"}, "fallback")
select_era(
    {"kind": "timeout"},
    "fallback",
    legacy_allowed=True,
    legacy_evidence={"kind": "initialize_success", "protocolVersion": LEGACY_VERSION},
)
select_era({"kind": "jsonrpc_error", "code": -32021}, "fallback")
```

첫 번째 타임아웃은 실패(fail closed)로 끝납니다. 침묵은 레거시 증거가 아니기 때문입니다. 두 번째 호출은 설정이 허용하고 유효한 레거시 초기화 결과가 관측되었기 때문에만 레거시를 선택합니다. 알려진 누락 기능 오류는 최신 분기의 증거입니다.

### 랩 B: 추가 필드 vs 판별자

```python
validate_result({"resultType": "complete", "tools": [], "futureHint": True}, "modern")
validate_result({"resultType": "future_mode", "tools": []}, "modern")
```

첫 번째 결과는 `futureHint`를 보존합니다. 두 번째는 라이프사이클 판별자를 알 수 없어 거부됩니다.

### 랩 C: SDK 변환 들여다보기

```python
compare_sdk_view(
    {"resultType": "complete", "tools": [], "futureHint": {"mode": "new"}},
    {"tools": []},
)
```

내 컴포넌트가 `futureHint`를 무시해도 되는지, 반드시 전달해야 하는지 판단하세요. 그 선택을 릴리스 정책에 적어 두세요. 차이 비교를 조용히 지워 버리면 안 됩니다.

### 랩 D: 프록시 고치기

데모 교환을 수정해서 이그레스가 오리진의 상태와 본문을 보존하게 만들어 보세요. `python3 main.py`를 다시 실행하면 프록시 문제는 사라지지만, SDK 차이 비교가 여전히 승격을 막습니다. 그다음 SDK 뷰에 `futureHint`를 포함하면 모든 증거 소스가 통과했을 때 동작이 `promote`로 바뀌는 것을 볼 수 있습니다.

- 응답 상태, 콘텐츠 타입, 순서가 보존된 SSE 이벤트, 스트림 종료를 캡처합니다.
- 각 JSON-RPC 이벤트가 해당 시대에 유효한 결과나 오류를 갖는지 증명합니다.
- 전달 전에 스트림 전체를 버퍼링하는 프록시에 대한 네거티브 케이스를 추가합니다.
- JSON-RPC id가 요청과 다른 SSE 이벤트에 대한 네거티브 케이스를 추가합니다.
- 증거를 기록하기 전에 이벤트 데이터를 레닥션합니다.
- 헬스 윈도우에 스트림 지속 시간, 첫 이벤트 지연 시간, 이벤트 수를 포함합니다.
- 스트림이 실패했을 때 릴리스 게이트가 증거가 있는 롤백 대상만 선택하게 만듭니다.

성공 기준은 같은 케이스를 직접 실행과 프록시 경유 실행 양쪽으로 돌리고, 어떤 경계가 동작을 바꿨는지 정확히 짚어 주는 보고서를 얻는 것입니다.

이 레슨은 `outputs/skill-mcp-conformance-release-gate.md` 산출물을 제공합니다. 이것을 사용해 서버, 클라이언트, 게이트웨이, SDK 변경을 버전이 매겨진 적합성 매트릭스와 릴리스 결정으로 바꾸세요. 이 산출물은 raw 와이어 증거, 네거티브 케이스, 명시적인 시대 선택, SDK 차이 비교, 프록시 증명, 레닥션, 헬스 임계값, 롤백 증거를 요구합니다.

## 검증하기

데모와 결정적(deterministic) 스위트를 실행하세요:

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

검증은 다음을 증명해야 합니다:

- 포함된 모든 골든·네거티브 트랜스크립트가 기대한 결과에 도달한다
- 최신 요청은 정확한 네임스페이스 메타데이터 키를 요구한다
- HTTP 헤더 이름은 대소문자 구별 없이 매칭되고, 인코딩된 `Mcp-Name` 값은 정확히 디코딩된다
- 헤더·본문 불일치는 최신 불일치 코드를 반환한다
- 응답 버전, ID, result·error 상호 배타성, 오류 형태, HTTP 매핑이 검증된다
- 메서드별 tool-list, task, completion 페이로드 요구 사항이 강제된다
- 관측된 모든 `HeaderMismatch`에는 실제 HTTP 400 JSON-RPC `-32020` 응답이 필요하다
- raw `Mcp-Name`의 공백은 거부되지만, 정확히 센티널 인코딩된 공백은 왕복(round-trip)에 성공한다
- `resultType` 누락은 선택된 레거시 시대에서만 유효하다
- 추가된 필드는 raw 검증을 통과하고, 알 수 없는 결과 타입은 실패한다
- 확장 결과 타입은 광고된 기능을 요구한다
- 알려진 최신 오류는 결코 레거시 폴백을 일으키지 않는다
- 알림은 JSON-RPC 응답을 만들어 내지 않는다
- SDK 부기 필드 제거와 의미 필드 손실은 구분된다
- 프록시의 오류 뭉개기가 탐지되고, 자격 증명이 camelCase·구분 기호 변형 전반에 걸쳐 재귀적으로 레닥션된다
- 승격에는 비어 있지 않은 트랜스크립트·SDK·프록시 증거와 건강한 운영 증거가 필요하다
- 승격과 롤백 모두 인증되고 핀되고 활성화되고 건강한 롤백 대상을 요구한다

## 프로덕션 장애 양상

| 장애 | 약한 테스트가 보고하는 것 | 하네스가 증명해야 하는 것 |
|---|---|---|
| SDK가 누락된 판별자를 만들어 냄 | "tools/list 통과" | raw 최신 결과에는 `resultType`이 없었고 잘못됨 |
| 클라이언트가 `-32021` 뒤에 다운그레이드함 | "레거시 재시도 성공" | 알려진 최신 오류는 폴백을 금지함 |
| 알 수 없는 결과 타입을 완료로 취급 | "응답 파싱됨" | 광고되지 않은 라이프사이클 판별자는 거부됨 |
| 프록시가 한 도구를 승인하고 오리진이 다른 도구를 실행 | "서버에 요청 도달" | 모든 홉에서 `Mcp-Name`이 본문 라우팅 이름과 같음 |
| 하네스가 서버 응답을 읽기 전에 예외로 종료 | "헤더 불일치 테스트 통과" | HTTP 400과 JSON-RPC `-32020` 응답이 캡처·검증됨 |
| 프록시가 오리진 400을 만능 500으로 바꿈 | "업스트림 오류" | 오리진·이그레스 상태와 JSON-RPC 본문이 보존됨 |
| 알림 미들웨어가 `{result: null}`을 내보냄 | "핸들러가 none 반환" | 최종 이그레스 본문은 비어 있고 JSON-RPC 응답이 존재하지 않음 |
| SDK가 추가 필드를 제거함 | "타입 객체 일치" | raw 뷰와 정규화 뷰가 빠진 필드를 정확히 보여 줌 |
| 장애 산출물이 베어러 토큰을 유출함 | "디버그 번들 업로드됨" | 해싱·로깅·업로드 전에 레닥션이 일어남 |
| 자격 증명 키 스타일이 레닥션을 우회함 | "거부 목록에 api_key 있음" | camelCase와 구분 기호 변형이 하나의 정규 거부 목록 형태를 공유함 |
| 카나리에 샘플이 없는데 건강해 보임 | "오류 0건" | 최소 샘플 수가 강제됨 |
| 롤백이 알 수 없는 빌드를 선택함 | "이전 배포 복원됨" | 대상 버전, 입장 심사 다이제스트, 핀, 상태, 헬스가 존재함 |

## 운영 규칙

내가 보내는 바이트, 모든 중개자가 전달하는 바이트, 각 SDK가 드러내는 의미, 그리고 운영팀이 압박 속에서 사용할 증거를 테스트하세요. 호환성은 명시적인 분기입니다. 롤백은 증거에 기반한 릴리스 동작입니다. 어느 쪽도 관대한 파서의 우연한 부작용이 되어서는 안 됩니다.
