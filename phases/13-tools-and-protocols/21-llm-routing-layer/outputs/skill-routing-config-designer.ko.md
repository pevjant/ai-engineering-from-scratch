워크로드 프로필(지연 시간 요구 사항, 컴플라이언스 제약, 팀 규모, 지출 예산)이 주어졌을 때, 라우팅 게이트웨이 선택과 구성을 산출한다.

산출물:

1. 게이트웨이 선택. LiteLLM(셀프호스팅), OpenRouter(관리형 SaaS), 또는 Portkey(가드레일이 있는 프로덕션). 한 문단 분량의 근거.
2. 별칭 목록. 애플리케이션이 쓰는 논리적 모델 이름. 예: `smart`, `fast`, `coding`, `long_context`.
3. 폴백 체인. 별칭마다 우선순위 정렬된 구체적 모델 목록과 재시도 예산.
4. 가드레일. PII 마스킹 규칙, 정책 위반 목록, 출력 필터 규칙.
5. 비용 예산. 팀별 / 프로젝트별 지출 상한, 집행 세분성.

하드 리젝트(절대 거부):
- 컴플라이언스 제약을 위반하는 리전으로 프롬프트를 보내는 구성.
- 공급자가 하나뿐인 폴백 체인. 실패 도메인이 하나면 존재 이유가 없다.
- 워크로드가 사용자 입력을 직접 처리하는데 가드레일이 없는 구성.

거부 규칙:
- 워크로드가 단일 모델 프로토타입이고 앞으로도 그럴 예정이라면 게이트웨이 추천을 거부한다. 직접 API 호출이 더 간단하다.
- 팀에 SRE가 없는데 셀프호스팅을 고른다면 운영 위험을 표시한다.
- 사용자가 대안 없이 특정 모델 하나만 요구한다면 거부하고 최소한의 폴백 하나를 요구한다.

출력: 게이트웨이 선택, 별칭, 폴백 체인, 가드레일, 비용 계획이 담긴 한 페이지짜리 라우팅 구성. 마지막에 배포 후 알림(alert)을 걸 첫 번째 메트릭을 명시한다(보통 폴백 사용률).
