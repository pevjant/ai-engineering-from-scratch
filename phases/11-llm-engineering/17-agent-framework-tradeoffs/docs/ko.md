# 에이전트 프레임워크 트레이드오프 — 그래프, 역할, 액터 오케스트레이션

> 모든 프레임워크는 똑같은 데모(리서치 에이전트가 보고서를 만든다)를 내세우고 똑같은 버그(상태 스키마가 오케스트레이션 계층과 부딪힌다)를 숨깁니다. 자신의 문제 모양과 추상화가 맞는 프레임워크를 고르세요. 나머지는 두 번씩 쓰게 되는 접착제 코드일 뿐입니다.

**유형:** Learn
**언어:** Python
**선수 지식:** 페이즈 11 · 09(함수 호출), 페이즈 11 · 16(LangGraph)
**소요 시간:** 약 45분

## 문제 상황

LLM 호출을 한 번 넘게 해야 하는 작업이 있습니다. 리서치 워크플로일 수도 있고(계획, 검색, 요약, 인용), 코드 리뷰 파이프라인일 수도 있고(diff 파싱, 비평, 패치, 검증), 항공권을 예약하고 이메일을 쓰고 경비 보고서를 제출하는 여러 턴짜리 어시스턴트일 수도 있습니다. 여러분은 프레임워크를 고릅니다.

사흘 뒤, 프레임워크의 추상화가 새는 것을 발견합니다. CrewAI는 역할을 주지만 "researcher"가 "writer"에게 구조화된 계획을 넘겨야 할 때 발목을 잡습니다. AutoGen은 에이전트 사이 채팅을 주지만 일급 상태가 없어서 체크포인트가 대화 로그의 피클(pickle) 덩어리가 됩니다. LangGraph는 상태 그래프를 주지만 에이전트가 뭘 할지 알기도 전에 모든 전이에 이름을 붙이라 강요합니다. Agno는 단일 에이전트 추상화를 주는데, 동시 워커 셋으로 확산하려 하자 비명을 지릅니다.

해법은 "가장 좋은 프레임워크 고르기"가 아닙니다. 프레임워크의 핵심 추상화를 문제의 모양에 맞추는 것입니다. 이 레슨이 그 지도를 그려 줍니다.

## 개념

![에이전트 프레임워크 매트릭스: 핵심 추상화 대 문제 모양](../assets/framework-matrix.svg)

2026년의 생태계를 지배하는 프레임워크는 넷입니다. 핵심 추상화는 서로 다릅니다.

| 프레임워크 | 핵심 추상화 | 가장 잘 맞는 경우 | 가장 안 맞는 경우 |
|-----------|------------------|----------|-----------|
| **LangGraph** | `StateGraph` — 타입 있는 상태, 노드, 조건부 엣지, 체크포인터. | 명시적 상태와 human-in-the-loop 인터럽트가 있는 워크플로. 타임 트래블 디버깅이 필요한 프로덕션(운영 환경) 에이전트. | 토폴로지를 알 수 없는 느슨한 역할 기반 브레인스토밍. |
| **CrewAI** | `Crew` — 역할(목표, 배경 스토리), 작업, 프로세스(순차 또는 계층). | 짧은 선형/계층 계획을 가진 역할극이나 페르소나 기반 워크플로. | 크루의 턴 기록을 넘어서는 상태가 필요한 모든 것. 복잡한 분기. |
| **AutoGen** | `ConversableAgent` 쌍 — 종료 조건이 나올 때까지 번갈아 대화하는 둘 이상의 에이전트. | 사고가 대화 속에서 자연스럽게 나오는 다중 에이전트 *대화*(교사-학생, 제안자-비평가, 배우-리뷰어). | DAG가 미리 알려진 결정론적 워크플로. 재시작을 넘어 지속되는 상태가 필요한 모든 것. |
| **Agno** | `Agent` — LLM 하나 + 도구 + 메모리, 팀으로 조립 가능. | 빠르게 만드는 단일 에이전트와 가벼운 팀. 강력한 멀티모달과 내장 스토리지 드라이버. | 커스텀 리듀서를 쓰는 깊고 명시적으로 분기하는 그래프. |

### "추상화"가 실제로 의미하는 것

프레임워크의 핵심 추상화란 아키텍처를 설명할 때 화이트보드에 그리는 바로 그것입니다.

- **LangGraph** → 그래프를 그립니다. 노드는 단계, 엣지는 전이이고, 모든 지점의 상태 객체는 타입이 있습니다. 멘탈 모델은 상태 머신입니다.
- **CrewAI** → 조직도를 그립니다. 각 역할은 직무 기술서를 갖고 매니저가 작업을 배분합니다. 멘탈 모델은 소규모 전문가 팀입니다.
- **AutoGen** → Slack DM을 그립니다. 두 에이전트가 메시지를 주고받고, 조정자가 필요하면 셋째가 끼어듭니다. 멘탈 모델은 채팅입니다.
- **Agno** → 도구가 달린 상자 하나를 그립니다. 팀이 필요하면 상자를 나란히 놓습니다. 멘탈 모델은 "기본 탑재형(batteries included) 에이전트"입니다.

### 상태라는 질문

대부분의 프레임워크 선택이 프로덕션에서 무너지는 지점이 상태입니다.

- **LangGraph.** 타입 있는 상태(`TypedDict` 또는 Pydantic 모델), 필드별 리듀서, 일급 체크포인터(SQLite/Postgres/Redis). 재개, 인터럽트, 타임 트래블이 공짜로 따라옵니다. *(페이즈 11 · 16 참고.)*
- **CrewAI.** 상태는 `context` 필드를 통해 작업 사이를 문자열로 흐르거나 `output_pydantic`으로 구조화됩니다. 크루별 영구 저장소는 기본 제공이 아니며, 크루가 재시작을 넘어 살아남아야 한다면 직접 붙여야 합니다.
- **AutoGen.** 상태란 채팅 기록과 사용자가 정의한 `context`입니다. 대화 전사(transcript)는 유지되지만, 임의의 워크플로 상태는 어댑터를 직접 쓰지 않는 한 유지되지 않습니다.
- **Agno.** 내장 스토리지 드라이버(SQLite, Postgres, Mongo, Redis, DynamoDB)를 `storage=`로 `Agent`에 붙입니다. 대화 세션과 사용자 메모리가 자동으로 유지됩니다. 완전한 그래프 체크포인터가 아니라 세션 저장소입니다.

### 분기라는 질문

간단하지 않은 에이전트는 모두 분기합니다. 누가 분기를 결정하느냐가 중요합니다.

- **LangGraph** — 여러분이 조건부 엣지로 결정합니다. 라우팅은 이름 있는 분기를 가진 Python 함수입니다. 분기는 컴파일된 그래프에서 일급이고, 체크포인터가 어느 분기를 갔는지 기록합니다.
- **CrewAI** — 계층 모드에서는 매니저가 결정하고, 순차 모드에서는 빌드할 때 여러분이 결정합니다. 라우팅은 작업 목록에 암묵적으로 녹아 있으며, 매니저 프롬프트 밖에는 일급 "if"가 없습니다.
- **AutoGen** — 에이전트들이 채팅으로 결정합니다. 분기는 다음 발화자가 누구냐에서 자연스럽게 생겨납니다. `GroupChatManager`가 다음 발화자를 고르며, `speaker_selection_method`를 직접 쓸 수도 있지만 기본값은 LLM 주도입니다.
- **Agno** — 에이전트가 다음에 어떤 도구를 호출할지로 결정합니다. 팀에는 coordinator/router/collaborator 모드가 있고, 그 이상의 분기는 개발자의 책임입니다.

### 관측 가능성(옵저버빌리티)이라는 질문

- **LangGraph** — LangSmith 또는 아무 OTel 익스포터를 통한 OpenTelemetry. 노드 전이마다 트레이스 스팬이 생기고, 체크포인트가 재생 가능한 트레이스를 겸합니다. LangSmith가 자사 옵션이고 Langfuse/Phoenix용 어댑터도 있습니다.
- **CrewAI** — 2025년 말부터 일급 OpenTelemetry 지원. Langfuse, Phoenix, Opik, AgentOps와 통합.
- **AutoGen** — `autogen-core`를 통한 OpenTelemetry 통합. AgentOps와 Opik에 커넥터가 있음. 트레이싱 단위는 노드가 아니라 에이전트 메시지입니다.
- **Agno** — 내장 `monitoring=True` 플래그와 OpenTelemetry 익스포터 제공. 세션 트레이스는 Langfuse와 긴밀히 통합.

### 비용과 지연 시간

네 프레임워크 모두 호출당 오버헤드(프레임워크 로직, 검증, 직렬화)를 더합니다. 오버헤드가 커지는 대략적인 순서는 Agno ≈ LangGraph < CrewAI ≈ AutoGen입니다. 이 차이는 프레임워크가 LLM 라우팅을 얼마나 더 하는지에 좌우됩니다. CrewAI의 계층형 매니저는 다음 차례를 정하느라 토큰을 쓰고, AutoGen의 `GroupChatManager`도 마찬가지입니다. LangGraph는 여러분이 `llm.invoke`를 쓴 곳에서만 토큰을 씁니다. Agno의 단일 에이전트 경로는 얇습니다.

실행당 비용이 중요하다면 LLM이 고르는 라우팅 대신 명시적 라우팅(LangGraph 엣지, AutoGen `speaker_selection_method`)을 선호하세요.

### 상호 운용성

- **LangGraph** ↔ **LangChain** 도구, 검색기, LLM. 일급 MCP 어댑터(도구를 MCP 서버로 가져옴).
- **CrewAI** ↔ 도구는 `BaseTool`을 상속합니다. LangChain 도구, LlamaIndex 도구, MCP 도구 모두 어댑터로 들어옵니다. `allow_delegation=True`로 크루 간 위임.
- **AutoGen** → `FunctionTool`이 모든 Python 콜러블을 감쌉니다. MCP 어댑터도 있습니다. 에이전트 간 패턴은 AG2 생태계와 강하게 결합됩니다.
- **Agno** → `@tool` 데코레이터 또는 BaseTool 서브클래스. MCP 어댑터. 도구는 에이전트와 팀 사이에서 공유할 수 있습니다.

## 스킬

> 주어진 에이전트 문제에 주어진 프레임워크가 왜 맞는지 한 문장으로 설명할 수 있습니다.

설계 전 체크리스트:

1. **모양 그리기.** 이것은 그래프인가(타입 있는 상태, 이름 있는 전이)? 역할극인가(전문가들이 작업을 넘겨줌)? 채팅인가(에이전트들이 끝날 때까지 대화)? 도구를 달은 단일 에이전트인가?
2. **누가 분기할지 정하기.** 개발자가 결정하는 분기 → LangGraph. 매니저 에이전트가 결정 → CrewAI 계층. 채팅에서 자연 발생 → AutoGen. 도구 호출이 결정 → Agno.
3. **상태 예산 확인하기.** 체크포인트에서 재개해야 하나요? 타임 트래블? 실행 도중 human 인터럽트? 그렇다면 기본값은 LangGraph입니다. 대화 범위의 상태라면 Agno 세션으로도 충분합니다.
4. **비용 예산 확인하기.** LLM 선택 라우팅은 매 턴 토큰을 추가로 씁니다. 에이전트가 하루 수천 번 돈다면 명시적 라우팅을 선호하세요.
5. **프레임워크 오버헤드도 예산에 넣기.** 프레임워크는 또 하나의 의존성입니다. 작업이 LLM 호출 두 번과 도구 하나뿐이라면 평범한 Python 30줄로 해결하세요. 프레임워크 없음보다 싼 프레임워크는 없습니다.

그래프, 조직도, 채팅, 에이전트 상자를 그릴 수 없는 상태에서 프레임워크에 손대는 것은 거부합니다. 정말 필요한 것을 위해 그 상태 모델과 계속 싸우게 만드는 프레임워크를 고르는 것도 거부합니다.

## 의사 결정 매트릭스

| 문제 모양 | 선호 프레임워크 | 이유 |
|---------------|---------------------|-----|
| 타입 있는 상태, human 승인, 장기 실행을 갖춘 워크플로 DAG | LangGraph | 일급 상태, 체크포인터, 인터럽트, 타임 트래블. |
| 뚜렷한 역할이 있는 리서치/작성 파이프라인 | CrewAI(순차) 또는 LangGraph 서브그래프 | 작업당 역할은 CrewAI에서 표현 비용이 싸다. 분기가 복잡해지면 LangGraph로 확장. |
| 제안자-비평가 또는 교사-학생 대화 | AutoGen | 두 에이전트 채팅이 그 고유 형태. |
| 도구·세션·메모리를 갖춘 단일 에이전트 | Agno | 가장 얇은 설정, 내장 스토리지와 메모리. |
| 리듀서와 함께 수천 개의 병렬 팬아웃 | LangGraph + `Send` | 일급 병렬 발송 API를 갖춘 유일한 선택지. |
| 빠른 프로토타입, 프레임워크 미사용 | 평범한 Python + 제공사 SDK | 프레임워크 없음이 가장 빠른 프레임워크. |

## 연습 문제

1. **쉬움.** 같은 작업("Anthropic 본사 조사, 200단어 브리프 작성, 출처 인용")을 LangGraph(노드 넷: plan, search, write, cite)와 CrewAI(역할 셋: researcher, writer, editor)로 구현합니다. 실행당 토큰 비용과 코드 줄 수를 보고합니다.
2. **보통.** 같은 작업을 AutoGen(researcher ↔ writer 채팅, `GroupChat`으로 editor 합류)과 Agno(`search_tools`와 `write_tools`를 달은 단일 에이전트 + 세션 저장소)로 만듭니다. 네 구현을 (a) 실행당 비용, (b) 크래시 후 재개 능력, (c) 쓰기 단계 전 human 승인 주입 능력 기준으로 순위를 매깁니다.
3. **어려움.** 짧은 문제 설명(JSON: `{has_typed_state, has_roles, has_dialogue, has_parallel_fanout, needs_resume}`)을 받아 한 문장 근거와 함께 추천을 돌려주는 의사결정 트리 스크립트 `pick_framework.py`를 만듭니다. 직접 설계한 여섯 사례로 검증합니다.

## 핵심 용어

| 용어 | 흔히 하는 말 | 실제 의미 |
|------|-----------------|-----------------------|
| 오케스트레이션 | "에이전트들이 어떻게 협조하나" | 어떤 노드/역할/에이전트가 다음에 실행될지 결정하는 계층. |
| 내구성 있는 상태 | "재시작 뒤에도 재개" | 프로세스가 죽어도 살아남아 체크포인트나 세션 저장소에 붙어 있는 상태. |
| LLM 선택 라우팅 | "모델이 정하게 두자" | 플래너 LLM이 매 턴 다음 단계를 고름. 유연하지만 모든 결정에 토큰을 지불. |
| 명시적 라우팅 | "개발자가 결정" | Python 함수나 정적 엣지가 다음 단계를 고름. 싸고 감사 가능. |
| 크루(Crew) | "CrewAI 팀" | 역할 + 작업 + 프로세스(순차 또는 계층)를 하나의 실행체로 묶은 것. |
| GroupChat | "AutoGen의 다중 에이전트 채팅" | 발화자 선택자를 둔 N개 에이전트의 관리되는 대화. |
| 팀(Team, Agno) | "다중 에이전트 Agno" | 에이전트 집합 위의 route/coordinate/collaborate 모드. |
| StateGraph | "LangGraph의 그래프" | 타입 있는 상태, 노드, 조건부 엣지, 체크포인터 추상화. |
