# 고급 RAG 패턴

기본 RAG: 쿼리 임베딩 -> 벡터 검색 -> top-k -> 생성.
고급 RAG: 쿼리 임베딩 + BM25 -> 순위 융합 -> 리랭킹 -> top-k -> 생성.

```
query -> [vector search (top-50)] -+-> RRF fusion -> reranker (top-5) -> prompt -> LLM
                                   |
query -> [BM25 search (top-50)]  --+
```

## 기본 RAG에서 업그레이드해야 할 때

- 검색 품질이 Recall@5 70% 미만으로 떨어짐
- 사용자들이 틀렸거나 관련 없는 답변을 신고함
- 코퍼스가 10만 청크를 넘어섬
- 쿼리가 문서와 다른 어휘를 사용함
- 멀티홉 질문이 계속 실패함

## 구현 체크리스트

1. 벡터 인덱스와 함께 BM25 인덱스 추가
2. 두 검색을 병렬로 실행(각각 top-50)
3. RRF(Reciprocal Rank Fusion, k=60)로 병합
4. 크로스 인코더로 상위 후보 리랭킹
5. 최종 프롬프트에는 top-5 사용
6. 테스트 세트에 충실성 평가 추가

## 기법 선택 가이드

- **하이브리드 검색**: 프로덕션에서는 항상 사용하세요. 쿼리 시점에 추가 비용이 없습니다.
- **리랭킹**: Recall@50은 좋은데 Recall@5가 나쁠 때 사용하세요. 지연 시간이 50~200ms 추가됩니다.
- **HyDE**: 쿼리가 모호하거나 문서와 어휘가 다를 때 사용하세요. LLM 호출이 한 번 추가됩니다.
- **부모-자식 청크**: 작은 청크는 컨텍스트가 부족하고 큰 청크는 관련성이 묽어질 때 사용하세요.
- **메타데이터 필터링**: 코퍼스에 뚜렷한 카테고리(날짜, 출처 유형, 부서)가 있을 때 사용하세요.
- **쿼리 분해**: 여러 문서의 정보가 필요한 멀티홉 질문에 사용하세요.

## 흔한 실수

- BM25와 벡터 검색을 서로 다른 청크 집합으로 돌리기(같은 코퍼스를 검색해야 합니다)
- 리랭킹 후보 풀이 너무 작음(top-10은 너무 적습니다. top-50을 사용하세요)
- 모든 쿼리에 HyDE 붙이기(어휘 불일치가 병목일 때만 도움이 됩니다)
- 변경 사항을 평가하지 않기(기법을 하나 추가할 때마다 Recall@k를 전후로 측정하세요)
- 어디서 실패하는지 측정하기도 전에 파이프라인을 과하게 설계하기

## 평가 워크플로

1. 정답 청크를 알고 있는 테스트 질문 50개 이상 만들기
2. 검색 방식별로 Recall@5와 Recall@10 측정하기
3. 검색이 성공한 쿼리에 대해서는 생성된 답변의 충실성 측정하기
4. 코퍼스가 커짐에 따라 지표를 매주 추적하기
5. 기법을 더 추가하기 전에 개별 실패 사례부터 조사하기
