# RAG 파이프라인 패턴

모든 RAG 시스템은 이 패턴을 따릅니다:

```
documents -> chunk -> embed -> store
query -> embed -> search(top_k) -> build_prompt -> generate
```

인덱싱은 문서당 한 번 일어납니다. 쿼리는 모든 사용자 요청마다 일어납니다.

## RAG를 사용해야 할 때

- LLM이 비공개 문서나 최신 문서에 접근해야 할 때
- 파인튜닝이 업데이트하기에 너무 비싸거나 너무 느릴 때
- 답변에 출처를 인용해야 할 때
- 지식 베이스가 자주 바뀔 때

## RAG를 사용하면 안 될 때

- 답이 LLM이 이미 갖고 있는 일반 지식일 때
- 작업이 창작(글쓰기, 브레인스토밍)이고 사실 기반이 아닐 때
- 모델에 특정 추론 스타일을 갖게 해야 할 때(파인튜닝을 사용)

## 구현 체크리스트

1. 문서를 50토큰 겹침을 둔 256-512토큰 조각으로 나눕니다
2. 일관된 임베딩 모델로 각 청크를 임베딩합니다
3. 임베딩을 원본 텍스트와 함께 벡터 데이터베이스에 저장합니다
4. 쿼리 시점에는 같은 모델로 사용자 질문을 임베딩합니다
5. 코사인 유사도로 가장 비슷한 top-k(5-10) 청크를 검색합니다
6. 프롬프트를 구성합니다: 시스템 지시문 + 검색된 컨텍스트 + 사용자 질문
7. 검색된 컨텍스트에 근거해 답변을 생성합니다
8. 출처 참조와 함께 답변을 반환합니다

## 흔한 실수

- 인덱싱과 쿼리에 서로 다른 임베딩 모델 사용(벡터가 호환되지 않습니다)
- 청크가 너무 작으면(문맥 상실) 너무 크면(관련성 희석)
- 청크 사이에 겹침을 두지 않음(경계에서 문장이 잘립니다)
- 문서가 바뀌었을 때 재인덱싱을 잊음
- 일관된 답변을 만들지 않은 채 검색된 청크를 그대로 사용자에게 반환
- 사실 기반 RAG 쿼리에 temperature=0을 설정하지 않음(온도가 높을수록 환각이 늘어납니다)

## 검색 디버깅

올바른 청크가 검색되지 않는다면:
1. 쿼리 임베딩을 출력해 0이 아닌지 확인합니다
2. 관련성이 확실한 청크의 코사인 유사도를 직접 확인합니다
3. 문서 어휘에 맞게 쿼리를 다시 표현해 봅니다
4. 인덱싱 때와 쿼리 때의 임베딩 모델이 같은지 확인합니다
5. 관련 내용이 청킹 과정에서 사라지지 않았는지 확인합니다

## 프로덕션 파라미터

- 청크 크기: 256-512토큰
- 겹침: 50토큰(청크 크기의 10-20%)
- Top-k: 대부분의 사용 사례에서 5-10
- Temperature: 사실 기반 답변은 0
- 임베딩 모델: text-embedding-3-small(가성비) 또는 text-embedding-3-large(더 높은 정확도)
