# 임베딩 패턴

모든 임베딩 워크플로는 이 계약을 따릅니다:

```
text -> embed(text) -> vector (float array)
similarity(vector_a, vector_b) -> score (float)
```

임베딩 모델과 유사도 지표가 실제로 중요한 두 가지 결정입니다. 나머지는 전부 배관 작업입니다.

## 임베딩을 사용해야 할 때

- 문서 전반의 시맨틱 검색(키워드가 아니라 의미를 찾기)
- 비슷한 항목 클러스터링(고객 지원 티켓, 상품 리뷰, 버그 리포트)
- 최근접 이웃으로 분류(레이블이 달린 예시와의 유사도로 새 항목에 레이블 붙이기)
- 추천 시스템(사용자가 좋아한 것과 비슷한 항목 찾기)
- 중복 제거(유사도 임계값으로 거의 같은 내용 찾기)

## 임베딩을 사용하면 안 될 때

- 정확한 키워드 매칭(전문 검색(full-text search)을 사용)
- 구조화된 쿼리(SQL, 필터를 사용)
- 수작업 레이블링이 더 빠른 작은 데이터셋(100개 미만 항목)
- 정확도보다 설명 가능성이 중요한 작업(임베딩은 불투명합니다)

## 모델 선택

제약 조건에 따라 고르세요:

- **API를 쓰고 가성비가 중요할 때**: OpenAI text-embedding-3-small (1536d, 백만 토큰당 $0.02)
- **최대 정확도가 필요할 때**: Voyage-3 (1024d, 백만 토큰당 $0.06, 최고 MTEB)
- **로컬/비공개 실행이 필요할 때**: BGE-M3 (1024d, 무료, 다국어, GPU 권장)
- **빠른 로컬 프로토타이핑이 필요할 때**: all-MiniLM-L6-v2 (384d, 무료, CPU에서 실행)
- **다국어가 필요할 때**: Cohere embed-v3 (1024d) 또는 BGE-M3 (둘 다 다국어에 강함)

규칙: 인덱싱과 쿼리 사이에 임베딩 모델을 절대 섞지 마세요. 서로 다른 모델의 벡터는 호환되지 않는 공간에 존재합니다.

## 청킹 규칙

1. 청크당 256-512토큰, 50토큰 겹침을 목표로 합니다
2. 피할 수 있다면 문장 중간에서 절대 자르지 않습니다
3. 모든 청크에 메타데이터(출처 파일, 섹션 제목, 위치)를 함께 담습니다
4. 구조화된 문서(Markdown, HTML)는 먼저 헤딩 경계에서 자릅니다
5. 답을 알고 있는 질문으로 검색해 보고 검색 결과를 확인하며 청크 품질을 테스트합니다

## 유사도 지표 선택

- **코사인 유사도**: 기본 선택, 가변 길이 텍스트 처리, 정규화됨
- **내적**: 벡터가 이미 단위 정규화되어 있을 때 사용(OpenAI 모델은 정규화되어 있음), 약간 더 빠름
- **유클리드 거리**: 클러스터링, 절대적 위치가 중요할 때 사용

벡터가 정규화되어 있으면 세 지표 모두 같은 순위를 줍니다. 선택이 중요해지는 경우는 정규화되지 않은 벡터뿐입니다.

## 저장 최적화

세 가지 압축 단계가 있고, 조합할 수 있습니다:

1. **마트료시카 절단**: 차원 축소 (1536 -> 256 = 6배 절감, 정확도 3-5% 손실)
2. **Float16 양자화**: 차원당 저장 공간 절반 (2배 절감, 정확도 1% 미만 손실)
3. **이진 양자화**: 차원당 1비트 (32배 절감, 정확도 5-10% 손실, 리스코어링과 함께 사용)

프로덕션 패턴: 전체 코퍼스를 이진 양자화 벡터로 검색하고, 상위 1,000개는 float32 벡터로 다시 점수를 매깁니다.

## 검색 후 리랭킹(Retrieve-then-rerank)

최고 정확도를 위한 2단계 파이프라인입니다:

1. 바이 인코더가 상위 100개 후보를 검색합니다 (빠름, 사전 계산된 임베딩 사용)
2. 크로스 인코더가 상위 10개로 리랭킹합니다 (느림, 각 쿼리-문서 쌍을 개별 처리)

이 방식은 단일 단계 검색보다 정밀도(precision) 지표에서 10-15% 더 좋습니다. 지연 시간보다 정확도가 중요할 때 사용하세요.

## 흔한 실수

- 인덱싱과 쿼리에 서로 다른 임베딩 모델 사용
- 청크가 아니라 문서 전체를 임베딩(임베딩이 모든 것의 평균이 되어버림)
- 코사인 유사도 계산 전 벡터를 정규화하지 않음(대부분의 모델은 미리 정규화하지만 확인 필요)
- 청크 겹침 무시(경계에서 잘린 문장은 문맥을 잃습니다)
- 원본 텍스트 없이 벡터만 저장(검색에는 둘 다 필요합니다)
- 모델이 바뀌었을 때 재임베딩하지 않음(기존 벡터는 호환되지 않습니다)
- 정확도만 보고 차원 선택(저장 공간과 지연 시간은 차원에 선형 비례해서 늘어납니다)

## 임베딩 디버깅

검색 결과가 좋지 않다면:

1. 쿼리 임베딩이 0이 아닌지 확인합니다(빈 입력이나 공백 입력은 영벡터를 만듭니다)
2. 관련성이 확실한 문서의 유사도 점수를 직접 확인합니다
3. 문서 어휘에 맞게 쿼리를 다시 표현해 봅니다
4. 청크 경계를 점검해 관련 내용이 청크 사이에 쪼개지지 않았는지 확인합니다
5. 지표별(cosine, dot, euclidean) top-k 결과를 비교해 정규화 문제를 찾아냅니다
6. 확실히 매칭되는 쿼리(문서에서 문장을 그대로 복사)로 파이프라인이 동작하는지 확인합니다

## 프로덕션 파라미터

- 청크 크기: 256-512토큰
- 청크 겹침: 50토큰(청크 크기의 10-20%)
- Top-k 검색: 직접 사용 시 5-10, 리랭킹용이면 50-100
- 유사도 임계값: 코사인 기준 0.7 이상(이보다 낮으면 보통 무관한 결과입니다)
- 배치 임베딩: 처리량을 위해 API 호출당 텍스트 100-500개 처리
- 인덱스 재구축: 모델이 바뀌거나 문서가 크게 업데이트되면 재임베딩
