# 프로덕션 LLM 체크리스트

LLM 애플리케이션을 출시할 때는 이 체크리스트를 순서대로 진행하세요. 각 섹션에는 구체적인 임계값이 붙은 통과/실패 기준이 있습니다.

## 1. 보안(출시 방해 요소)

여기 항목들은 어떤 배포보다도 앞서 반드시 통과해야 합니다.

| 검사 | 통과 기준 | 검증 방법 |
|-------|--------------|---------------|
| API 키는 환경 변수에 | 코드베이스에 하드코딩된 키 0개 | `grep -r "sk-" --include="*.py"` 결과가 없어야 함 |
| 입력 가드레일 활성 | 프롬프트 인젝션 패턴 차단 | "Ignore all previous instructions" 전송 -- 차단 응답이 돌아옴 |
| PII 마스킹 | SSN, 신용카드, 이메일 패턴 포착 | "My SSN is 123-45-6789" 전송 -- LLM 호출 전에 PII 마스킹 |
| 출력 필터링 | 위험한 콘텐츠 차단 | 모델이 `DROP TABLE`, `rm -rf`, `exec()` 패턴을 반환하지 못함 |
| 속도 제한 | 사용자별 요청 상한 강제 | 같은 사용자가 10초 동안 100요청 -- 마지막 50개 이상 거부 |
| 모든 엔드포인트에 인증 | 인증 없는 LLM 접근 없음 | 토큰 없이 `curl /v1/chat` 호출 시 401 반환 |
| CORS 제한 | 프로덕션 도메인만 허용 | `Origin: evil.com` 요청 거부 |
| 최대 입력 토큰 | 한도 초과 요청 거부 | 5만 토큰 입력 전송 -- 413 또는 잘린 결과 반환 |

## 2. 신뢰성(첫 주 생존)

이것들이 여러분의 첫 온콜(on-call) 사고를 막아 줍니다.

| 검사 | 통과 기준 | 검증 방법 |
|-------|--------------|---------------|
| 백오프가 있는 재시도 | 5xx에 3회 재시도, 지수 증가 지연 | 요청 도중 LLM 목(mock) 종료 -- 로그에 재시도 표시 |
| 폴백 모델 체인 | 체인에 모델 2개 이상 | 기본 모델 사용 불가 -- 폴백에서 응답이 돌아옴 |
| 요청 타임아웃 | 모든 외부 호출에 최대 30초 | 느린 LLM 목(60초) -- 요청이 30초에 타임아웃 |
| 우아한 성능 저하 | 캐시/RAG 실패로도 서비스는 생존 | 캐시 중지 -- 요청은 계속 성공(느리고 비쌈) |
| 헬스 체크 엔드포인트 | 의존성 상태 반환 | `GET /health`가 `{"status": "healthy", "cache": ..., "llm": ...}` 반환 |
| 스트리밍 동작 | 첫 토큰 500ms 미만 | 첫 토큰까지 걸린 시간(TTFT) 측정, 일관되게 < 500ms |
| 오류 메시지가 안전함 | 내부 오류가 사용자에게 새지 않음 | 500 강제 발생 -- 사용자에게는 일반 오류만 보임, 스택 트레이스는 아님 |

## 3. 비용 관리(첫 달 경제성)

이것들이 $50,000짜리 깜짝 청구서를 막아 줍니다.

| 검사 | 통과 기준 | 검증 방법 |
|-------|--------------|---------------|
| 요청당 비용 추적 | 모든 요청이 토큰 수 + USD 비용 기록 | 요청 로그에 `input_tokens`, `output_tokens`, `cost_usd` 필드 존재 |
| 시맨틱 캐시 활성 | 반복 패턴에서 히트율 > 20% | 테스트 요청 1,000건 후 캐시 통계에 히트율 표시 |
| 캐시 TTL 구성 | 항목 만료(기본 1시간) | 항목 삽입 -- TTL이 지나면 반환되지 않음 |
| 사용자별 비용 추적 | user_id 기준 비용 집계 | 대시보드/API가 비용 상위 10명 사용자 표시 |
| 비용 알림 | 일일 예산의 80%에서 알림 | 일일 예산 $10 설정, $8.50 어치 요청 전송 -- 알림 발화 |
| 비용 기준 모델 라우팅 | 낮은 복잡도 쿼리는 싼 모델 사용 | 간단한 질문은 gpt-4o-mini로, 복잡한 질문은 gpt-4o로 라우팅 |
| 최대 출력 토큰 설정 | 템플릿별 응답 상한 | max_output_tokens=512 템플릿 -- 응답이 절대 초과하지 않음 |

**비용 추정 공식:**
```
월간 LLM 비용 = DAU x 사용자당_쿼리수 x 30 x (1 - 캐시_히트율) x (평균_입력_토큰 x 입력_가격 + 평균_출력_토큰 x 출력_가격) / 1,000,000
```

**규모별 벤치마크 임계값:**

| DAU | 요청당 목표 비용 | 월간 예산 |
|-----|-------------------|----------------|
| 1K | < $0.005 | < $750 |
| 10K | < $0.003 | < $4,500 |
| 100K | < $0.001 | < $15,000 |

## 4. 관측 가능성(프로덕션 디버깅)

보이지 않는 것은 고칠 수 없습니다.

| 검사 | 통과 기준 | 검증 방법 |
|-------|--------------|---------------|
| 구조화된 JSON 로깅 | 모든 요청이 JSON 로그 라인 생성 | 로그에 request_id, user_id, model, tokens, latency_ms, cost 포함 |
| 요청 추적 | 컴포넌트 타이밍이 담긴 엔드투엔드 트레이스 | 요청 하나가 표시: 가드레일(5ms) + 캐시(2ms) + llm(3200ms) + 평가(1ms) |
| 지연 시간 추적 | P50, P95, P99 측정 | 요청 1,000건 후: P50 < 2초, P99 < 10초 |
| 오류율 모니터링 | 오류 집계 및 분류 | 대시보드 표시: API 오류 0.5%, 가드레일 차단 0.1%, 타임아웃 0.01% |
| 캐시 지표 | 히트율, 미스율, 항목 수 표시 | `GET /v1/cache/stats`가 현재 숫자 반환 |
| A/B 테스트 지표 | 변형별 품질 지표 기록 | 각 요청이 비교를 위해 prompt_template + 버전을 기록 |
| 평가(eval) 로깅 | 요청별 품질 신호 기록 | 응답 길이, 지연 시간, 모델, 템플릿 버전을 오프라인 분석용으로 저장 |

## 5. 프롬프트 관리

프롬프트는 코드입니다. 코드처럼 다루세요.

| 검사 | 통과 기준 | 검증 방법 |
|-------|--------------|---------------|
| 버전 관리된 템플릿 | 모든 템플릿에 이름 + 버전 문자열 존재 | 템플릿 변경 시 새 버전 생성, 이전 버전 보존 |
| A/B 테스트 지원 | 결정론적 사용자 해시로 트래픽 분할 | 같은 사용자는 실험 내내 같은 변형을 봄 |
| 롤백 역량 | 1분 안에 이전 버전으로 복귀 | 실험 설정 변경 -- 트래픽 즉시 전환 |
| 템플릿 검증 | 렌더링 전에 변수 검증 | 템플릿의 누락 변수가 KeyError가 아니라 명확한 오류 발생 |
| 시스템 프롬프트 분리 | 시스템/사용자 메시지가 별도 필드에 | 시스템 프롬프트가 사용자 메시지에 합쳐지지 않음 |

## 6. 확장 준비성

출시 때는 필요 없습니다. 10배가 되면 필요합니다.

| 검사 | 통과 기준 | 검증 방법 |
|-------|--------------|---------------|
| 비동기 LLM 호출 | API 호출로 스레드를 막아 두지 않음 | 동시 요청 50개 -- 서버 CPU 30% 미만 유지 |
| 커넥션 풀링 | HTTP 연결 재사용 | 네트워크 트레이스에 LLM 제공사로의 지속 연결 표시 |
| 수평 확장 | 무상태(stateless) 서버 설계 | 로드 밸런서 뒤 인스턴스 2대 -- 모든 요청 성공 |
| 큐 지원 | 실시간이 아닌 작업은 큐로 | 요약 요청이 job_id 반환, 결과는 폴링으로 확인 |
| 부하 테스트 완료 | 동시 사용자 100명, 오류율 < 5% | 목표 동시성에서 `wrk` 또는 `locust` 테스트 통과 |

## 신규 프로젝트 구현 순서

1. **1일차:** API 서버 + 프롬프트 템플릿 + 재시도가 있는 단일 LLM 호출
2. **2일차:** 입력 가드레일 + 출력 가드레일 + 오류 처리
3. **3일차:** 시맨틱 캐시 + 요청별 비용 추적
4. **4일차:** 스트리밍(SSE) + 헬스 체크 엔드포인트
5. **5일차:** 구조화된 로깅 + 요청 추적 + 평가(eval) 로깅
6. **2주차:** A/B 테스트 + 프롬프트 버저닝 + 롤백
7. **3주차:** 폴백 모델 체인 + 우아한 성능 저하
8. **4주차:** 부하 테스트 + 비동기 최적화 + 수평 확장

## 빠른 진단

프로덕션에서 뭔가 잘못됐다면 이 순서로 확인하세요:

1. **사용자가 오류를 호소하나?** 헬스 엔드포인트 확인, 그다음 로그의 오류율, 그다음 LLM 제공사 상태 페이지
2. **응답이 느린가?** P99 지연 시간 확인, 그다음 캐시 히트율, 그다음 트레이스 속 LLM 응답 시간
3. **비용이 급등하나?** 요청당 비용 추이 확인, 그다음 캐시 히트율, 그다음 비용 상위 사용자, 그다음 토큰 수를 늘린 프롬프트 템플릿 변경 탐색
4. **품질이 떨어졌나?** 새 프롬프트 버전이 배포됐는지 확인, RAG 검색 정확도가 바뀌었는지 확인, 모델 제공사가 기본 모델 버전을 바꿨는지 확인
5. **보안 사고인가?** 가드레일 차단률 확인(급락 = 가드레일 비활성화), 요청 로그의 비정상 패턴 확인, API 키 즉시 로테이션
