# 프롬프트 패턴 선택 가이드

LLM 기반 기능을 만들 때는 프롬프트를 쓰기 전에 먼저 프롬프트 패턴을 고르세요. 패턴이 구조를 결정하고, 내용이 그 구조를 채웁니다.

## 패턴 의사 결정 매트릭스

| 작업 유형 | 1순위 패턴 | 2순위 패턴 | 온도 | Few-Shot 필요? |
|-----------|----------------|-------------------|-------------|-----------------|
| 데이터 추출 | Template Fill | Few-Shot | 0.0 | 예 (2-3개 예시) |
| 분류 | Few-Shot | Guardrail | 0.0 | 예 (3-5개 예시) |
| 요약 | Persona + Template | Audience Adapt | 0.3 | 아니오 |
| 코드 생성 | Persona | Chain-of-Thought | 0.0 | 선택 |
| 창작 | Persona | Critique | 0.7-1.0 | 아니오 |
| 다단계 추론 | Chain-of-Thought | Decomposition | 0.3 | 선택 |
| 질의응답 | Persona + Guardrail | Boundary | 0.3 | 아니오 |
| 프롬프트 생성 | Meta-Prompt | Critique | 0.7 | 예 (1-2개 예시) |
| 콘텐츠 검토 | Guardrail + Boundary | Few-Shot | 0.0 | 예 (5개 이상 예시) |
| 번역/변환 | Audience Adapt | Few-Shot | 0.3 | 예 (2-3개 예시) |

## 각 패턴을 언제 쓰나

**Persona 패턴**: 모든 프롬프트의 기본값으로 사용하세요. 고민할 것은 역할을 얼마나 구체적으로 만들지뿐입니다. 범용 작업이라면 넓은 역할로 충분합니다. 도메인 특화 작업이라면 역할에 도메인, 연차(시니어 정도), 맥락을 명시해야 합니다.

**Few-Shot 패턴**: 내용보다 출력 형식이 중요할 때 사용하세요. 모델이 특정 JSON 구조, CSV 형식, 분류 레이블을 만들어야 한다면, 지시문보다 예시가 더 효과적입니다. 경험 법칙: 간단한 형식은 예시 2-3개, 복잡하거나 모호한 형식은 5개 이상.

**Chain-of-Thought 패턴**: 수학, 논리, 다단계 분석, 그리고 모델이 "풀이 과정을 보여 줘야 하는" 모든 작업에 사용하세요. 추론 과제에서 정확도가 10-40% 향상됩니다(Wei et al., 2022). 단순 사실 조회나 추출에는 쓰지 마세요 — 토큰만 낭비합니다.

**Template Fill 패턴**: 모든 출력이 똑같은 모양을 가져야 하는 구조화된 추출에 사용하세요. temperature=0.0과 함께, 빠진 필드에 대한 명시적인 "N/A" 처리를 하면 가장 잘 작동합니다.

**Critique 패턴**: 속도보다 품질이 중요할 때 사용하세요. 모델이 생성하고, 비평하고, 개선합니다. 토큰 비용은 대략 두 배가 되지만 정확성과 완성도가 크게 향상됩니다. 결과가 큰 작업(보고서, 추천안, 외부 공개 콘텐츠)에 가장 적합합니다.

**Guardrail 패턴**: 사용자를 향하는 모든 시스템에 사용하세요. 항상 포함할 것: 범위 경계, 범위 밖 요청에 대한 거절 동작, 명시적인 "모르겠습니다" 처리. 애플리케이션 쪽 입력 검증과 함께 쓰세요.

**Meta-Prompt 패턴**: 새로운 작업을 위한 프롬프트를 만들 때 사용하세요. 프롬프트를 처음부터 직접 쓰는 대신, 작업을 설명하고 모델에게 프롬프트를 쓰게 하세요. 그다음 테스트하고 반복하면 됩니다. 초기 프롬프트 개발 시간을 아껴 줍니다.

**Decomposition 패턴**: 분할 정복이 도움이 되는 복잡한 문제에 사용하세요. 모델이 문제를 조각내고, 각각 풀고, 합칩니다. 하위 문제가 3-7개인 작업에서 가장 효과적입니다.

**Audience Adaptation 패턴**: 같은 콘텐츠로 여러 독자를 만족시켜야 할 때 사용하세요. 대상 독자를 명시적으로 지정하세요 — 모델이 맥락에서 추측하게 두지 마세요.

**Boundary 패턴**: 특정 유형의 질문에는 절대 답하면 안 되는 프로덕션(운영 환경) 시스템에 사용하세요. 정확한 거절 메시지와 함께 딱딱한 경계를 정의하기 때문에 가드레일보다 강합니다. 규정 준수가 중요한 도메인에는 필수입니다.

## 크로스 모델 호환성

GPT-4o, Claude 3.5 Sonnet, Gemini 1.5 Pro, Llama 3에서 얼마나 일관되게 작동하는지 순위를 매긴 패턴 목록입니다:

| 패턴 | 크로스 모델 일관성 | 비고 |
|---------|------------------------|-------|
| Few-Shot | 매우 높음 | 예시는 모든 모델에서 잘 전달된다 |
| Template Fill | 매우 높음 | 구조를 명시하면 빗나갈 여지가 거의 없다 |
| Chain-of-Thought | 높음 | 주요 모델 모두 "think step by step"를 지원한다 |
| Persona | 높음 | 어디서든 작동하지만, 모델마다 잘 반응하는 역할 구체성 수준이 다르다 |
| Guardrail | 보통 | Claude가 가드레일을 가장 엄격하게 따른다. GPT-4o는 긴 대화에서 가끔 흐트러진다 |
| Critique | 보통 | 자기 비평의 품질은 모델에 따라 크게 갈린다 |
| Meta-Prompt | 보통 | GPT-4o와 Claude는 서로 다른 스타일의 프롬프트를 만든다 |
| Boundary | 낮음~보통 | 거절 동작이 모델마다 다르다. 모델별로 테스트할 것 |

## 흔한 실수

1. **모든 것에 Chain-of-Thought 사용**: CoT는 토큰과 지연 시간을 더합니다. 추론 단계가 필요할 때만 쓰세요.
2. **제약 조건 과다**: 제약이 5-7개를 넘으면 모델이 일부를 누락하기 시작합니다. 가장 중요한 3개에 우선순위를 두세요.
3. **모순되는 페르소나 + 제약**: "You are a creative writer" + "Never use metaphors"는 모델을 혼란스럽게 합니다.
4. **온도 미지정**: 결정론적 출력이 필요한데 온도를 기본값(보통 1.0)으로 그대로 두는 것.
5. **모델 간 프롬프트 복사-붙여넣기**: 반드시 테스트하세요. GPT-4o에 맞춘 프롬프트는 Claude에서 성능이 떨어질 수 있고, 그 반대도 마찬가지입니다.
6. **시스템 메시지 무시**: 지속적으로 유지되어야 할 규칙을 시스템 메시지에 넣지 않고 전부 사용자 메시지에 몰아넣는 것.
7. **부정 제약 과잉 의존**: "Do NOT do X, Y, Z, A, B, C"는 "ONLY do W"보다 효과가 떨어집니다. 긍정으로 표현하면 모델에게 명확한 목표가 주어집니다.

## 신뢰성 목표

| 사용 사례 | 패턴 조합 | 기대 정확도 | 토큰 비용 |
|----------|-------------------|-------------------|------------|
| 프로덕션(운영 환경) 추출 | Template + Few-Shot | 95% 이상 | 낮음 (500-1K) |
| 사용자 대상 Q&A | Persona + Guardrail + Boundary | 90% 이상 | 중간 (1-2K) |
| 코드 생성 | Persona + Chain-of-Thought | 85% 이상 | 중간 (1-3K) |
| 콘텐츠 생성 | Persona + Critique | 90% 이상 품질 | 높음 (2-4K, 2회 통과) |
| 분류 | Few-Shot + Guardrail | 95% 이상 | 낮음 (300-800) |
| 복잡한 분석 | Decomposition + Chain-of-Thought | 85% 이상 | 높음 (3-5K) |
