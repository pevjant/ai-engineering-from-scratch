# 구조화 출력 전략

구조화된 데이터가 필요한 LLM 애플리케이션을 만들 때는 이 의사 결정 프레임워크를 적용하세요.

## 각 접근법을 언제 쓰나

**프롬프트 기반 ("JSON으로 반환"):** 프로토타이핑 전용입니다. 가끔 파싱이 실패해도 괜찮은 내부 도구라면 허용할 만합니다. 재시도가 들어간 try/except를 추가하세요. 프로덕션(운영 환경) 파이프라인에는 절대 쓰지 마세요.

**JSON 모드 (API 플래그):** 유효한 JSON이 보장되길 원하지만 스키마가 단순하거나 유연해도 될 때입니다. 애플리케이션 쪽에서 모양을 검증할 때 쓸 만합니다. 지원: OpenAI, Anthropic (도구 사용 경유), Google.

**스키마 모드 (제약 디코딩):** 모든 출력이 특정 스키마와 일치해야 하는 프로덕션(운영 환경) 시스템용입니다. 파싱 실패 0건. 스키마 위반 0건. 프로덕션 추출이나 분류 작업이라면 기본값으로 이것을 쓰세요. 지원: OpenAI 구조화된 출력, Outlines, Guidance.

**함수 호출 / 도구 사용:** 모델이 파라미터만 채우는 게 아니라 어떤 함수를 호출할지 골라야 할 때입니다. 스키마가 여러 개 있고 모델이 알맞은 것을 선택하는 방식이죠. 기존 도구/함수 인프라와 연동할 때도 씁니다.

**Instructor 라이브러리:** 어떤 제공사든 자동 재시도가 붙은 Pydantic 검증을 원할 때입니다. Python 프로젝트에서 개발자 경험이 가장 좋습니다. OpenAI, Anthropic, Google, 오픈소스 모델을 모두 감쌉니다.

## 제공사별 가이드

**OpenAI:** `json_schema` 타입의 `response_format`을 사용하세요. 제약 디코딩이 내장되어 있습니다. Pydantic 모델을 바로 쓸 수 있습니다. 가장 신뢰할 수 있는 구조화 출력 구현입니다.

**Anthropic:** 구조화 출력에 도구 사용을 쓰세요. 원하는 스키마를 가진 도구 하나를 정의하면, 모델이 스키마와 일치하는 도구 호출 인자를 반환합니다. 신뢰할 수 있지만 도구 사용 API 패턴을 따라야 합니다.

**오픈소스 모델 (vLLM, Ollama):** 제약 디코딩에 Outlines나 Guidance를 사용하세요. 이 라이브러리들은 JSON Schema를 유한 상태 머신으로 컴파일해 생성 중에 잘못된 토큰을 가립니다. 로컬에서 추론을 실행해야 합니다.

## 스키마 설계 가이드라인

1. 가능하면 스키마를 평평하게 유지하세요. 2단계를 넘는 중첩 객체는 추출 오류를 늘립니다.
2. 범주형 필드에는 enum을 쓰세요. 모델이 알맞은 문자열을 지어내길 기대하지 마세요.
3. 모호한 필드는 선택 사항으로 두지 말고, 명시적인 null 지원과 함께 필수로 만드세요. 모델이 결정을 내리도록 강제하는 것입니다.
4. 스키마 속성에 description을 붙이세요. 모델은 이것을 지시문처럼 읽습니다.
5. 필요 없다면 유니언 타입(oneOf/anyOf)을 피하세요. 디코딩 복잡도를 높입니다.
6. 숫자에는 최솟값/최댓값을 설정하세요. 환각된 이상한 값을 잡아 줍니다.
7. 배열에는 minItems/maxItems를 설정해 빈 배열이나 무한정 늘어나는 출력을 막으세요.

## 흔한 실패 패턴과 해결책

- **모델이 JSON을 마크다운 펜스로 감쌈**: 프롬프트 기반에서 JSON 모드나 스키마 모드로 전환
- **스키마는 맞는데 사실이 틀림**: 추출 후에 LLM-as-judge 검증 단계를 추가
- **일관성 없는 enum 값**: 제약 디코딩으로 전환하거나 후처리 정규화를 추가
- **선택 필드가 빠짐**: 필수로 바꾸거나 애플리케이션 코드에서 기본값을 추가
- **추출이 너무 느림**: 제약 디코딩은 지연 시간을 5-15% 더합니다. 지연 시간에 민감하다면 스키마 복잡도를 줄이세요
- **항목이 다양한 큰 배열**: 입력을 청크로 나눠 청크별로 추출한 뒤 결과를 병합
