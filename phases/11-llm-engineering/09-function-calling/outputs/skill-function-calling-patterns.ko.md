# 함수 호출 패턴

도구를 쓰는 LLM 애플리케이션을 만들 때 이 의사결정 프레임워크를 적용하세요.

## 함수 호출을 쓸 때

**함수 호출을 쓸 때:**
- 모델에 실시간 데이터가 필요할 때(날씨, 주가, 데이터베이스 조회)
- 작업에 부작용이 필요할 때(이메일 발송, 레코드 생성, 코드 배포)
- 사용자 의도에 따라 모델이 여러 동작 중 하나를 골라야 할 때
- 외부 시스템과 상호작용하는 에이전트를 만들 때

**대신 구조화 출력을 쓸 때:**
- 텍스트에서 데이터 추출이 필요할 때(외부 호출 불필요)
- 출력이 중간 단계가 아니라 최종 산출물일 때
- 선택할 도구 여러 개가 아니라 스키마 하나만 있을 때

**둘 다 쓸 때:**
- 모델이 도구를 호출한 뒤 도구 결과를 특정 출력 형식으로 구조화할 때

## 도구 설계 가이드라인

1. **도구 하나에 동작 하나.** 쿼리, 삽입, 업데이트, 삭제를 다 처리하는 `manage_database` 같은 도구는 너무 광범위합니다. `query_records`, `insert_record`, `update_record`로 쪼개세요. 도구가 구체적일수록 모델의 선택이 좋아집니다.

2. **설명은 곧 프롬프트.** 모델은 도구 설명을 읽고 선택을 합니다. 신입 개발자에게 일을 시키듯 쓰세요. 도구가 뭘 하는지뿐 아니라 무엇을 반환하는지도 적습니다.

3. **enum으로 묶어 두기.** 파라미터에 유효한 값이 3~10개면 enum을 쓰세요. 묶어 두지 않으면 모델이 "celsius", "Celsius", "C", "metric" 같은 문자열을 지어냅니다.

4. **도구는 적을수록 좋다.** GPT-4o는 도구 5~10개를 잘 다룹니다. 20개가 넘으면 선택 정확도가 떨어지고, 50개가 넘으면 잘못된 도구 선택이 10~15% 생길 수 있습니다. 관련 기능을 묶거나 라우팅 레이어를 쓰세요.

5. **required는 정말 필수일 때만.** 도구가 그 파라미터 없이는 문자 그대로 동작할 수 없을 때만 required로 표시하세요. 좋은 기본값을 가진 선택 파라미터가 도구 호출 실패를 줄여 줍니다.

## 공급자별 패턴

### OpenAI (GPT-4o, o3, GPT-4o-mini)

```python
tools=[{"type": "function", "function": {"name": ..., "parameters": ...}}]
tool_choice="auto"       # 모델이 판단
tool_choice="required"   # 최소 한 개 도구는 반드시 호출
tool_choice={"type": "function", "function": {"name": "specific_tool"}}
```

- 병렬 도구 호출 지원(한 응답에 `tool_calls` 여러 개)
- 도구 호출 ID는 결과와 함께 돌려보내야 함
- `gpt-4o-mini`는 10배 싸고 간단한 도구 라우팅은 잘 해냄
- 구조화 출력 모드는 도구 파라미터와 함께 쓸 수 있어 스키마 준수를 보장

### Anthropic (Claude 3.5 Sonnet, Claude 4 Opus)

```python
tools=[{"name": ..., "description": ..., "input_schema": ...}]
tool_choice={"type": "auto"}     # 모델이 판단
tool_choice={"type": "any"}      # 최소 한 개 도구는 반드시 호출
tool_choice={"type": "tool", "name": "specific_tool"}
```

- 도구 호출은 `type: "tool_use"` 콘텐츠 블록으로 나타남
- 결과는 `type: "tool_result"` 사용자 메시지로 전달
- 필드 이름은 `parameters`가 아니라 `input_schema`(흔한 이주 버그)
- 응답당 도구 호출 여러 개 지원

### Google (Gemini 2.0 Flash, Gemini 2.0 Pro)

```python
function_declarations=[{"name": ..., "description": ..., "parameters": ...}]
function_calling_config={"mode": "AUTO"}   # 또는 "ANY", "NONE"
```

- 최상위에 `function_declarations`를 사용
- 결과는 `function_response` 파트로 반환
- 병렬 함수 호출 지원

### 오픈소스 모델 (Llama 3, Hermes, Qwen)

- 표준화된 형식이 없음 -- 모델과 서빙 프레임워크마다 다름
- Hermes 형식(NousResearch)이 파인튜닝 커뮤니티의 가장 흔한 관례
- vLLM은 지원 모델에 대해 OpenAI 호환 도구 호출을 제공
- Ollama는 호환 모델로 기본 도구 호출을 지원
- 프로덕션 전에 도구 선택 정확도를 테스트할 것 -- Berkeley Function Calling Leaderboard에서 오픈 모델은 GPT-4o보다 15~30% 정확도가 낮습니다

## 오류 처리 패턴

### 구조화된 오류 반환

```json
{"error": true, "message": "City 'Toky' not found. Did you mean 'Tokyo'?", "code": "NOT_FOUND", "suggestions": ["Tokyo"]}
```

실행 가능한 정보를 담으세요. "못 찾음"은 나쁘고, "못 찾음. ~을(를) 찾으신가요?"은 좋습니다. 모델은 오류 메시지로 스스로 교정합니다.

### 재시도 전략

1. 도구 호출이 고칠 수 있는 오류로 실패(오타, 잘못된 enum 값)
2. 오류를 도구 결과 형태로 모델에 돌려보내기
3. 모델이 고쳐서 재시도
4. 도구 호출당 최대 재시도 3회
5. 3번 실패하면 오류를 사용자에게 반환

### 타임아웃 처리

모든 도구 실행에 타임아웃을 걸어 두세요. 30초가 무난한 기본값입니다. 도구가 시간 초과되면 구조화된 타임아웃 오류를 돌려줘서, 모델이 멈춰 있는 대신 사용자에게 알릴 수 있게 하세요.

## 보안 체크리스트

| 점검 항목 | 이유 | 방법 |
|-------|-----|-----|
| 함수 allowlist | 임의 코드 실행 방지 | 사용자가 필요로 하는 도구만 등록 |
| 인자 타입 검증 | 타입 혼동 공격 방지 | 실행 전에 타입 검사 |
| 문자열 인자 정제 | 인젝션 방지 | 특수 문자 거부 또는 이스케이프 |
| 데이터베이스 쿼리 파라미터화 | SQL 인젝션 방지 | 모델이 만든 SQL을 절대 직접 전달하지 않음 |
| 도구 결과 필터링 | 데이터 유출 방지 | API 키, 개인정보(PII), 내부 오류 제거 |
| 도구 호출 속도 제한 | 폭주 루프 방지 | 대화당 최대 10~20회 |
| 모든 도구 호출 기록 | 감사 추적 | 도구 이름, 인자, 결과, 타임스탬프 저장 |
| 경로 탐색 차단 | 파일 시스템 접근 방지 | 파일 도구에서 `..`와 절대 경로 거부 |
| 코드 실행 샌드박스 | 시스템 접근 방지 | 컨테이너 또는 제한된 빌트인 사용 |
| 반환 크기 검증 | 컨텍스트 과다 채움 방지 | 10KB 넘는 결과 잘라내기 |

## 성능 최적화

- **병렬 호출:** 모델이 독립적인 도구 여러 개를 요청하면 `asyncio.gather()`나 `concurrent.futures`로 동시에 실행
- **캐싱:** 같은 세션에서 동일한 인자의 도구 결과는 캐싱(날씨는 60초 안에 안 바뀝니다)
- **스트리밍:** 도구 결과를 가져오는 동안 모델의 최종 응답을 스트리밍
- **도구 정리(pruning):** 컨텍스트가 빠듯하면 현재 쿼리와 관련된 도구 정의만 포함(분류기로 걸러내기)
- **라우팅용 소형 모델:** 도구 선택은 `gpt-4o-mini`나 `claude-haiku-4-5`로 하고, 결과는 더 강한 모델에 넘겨 종합

## 흔한 실패 패턴

| 실패 | 원인 | 해결 |
|---------|-------|-----|
| 잘못된 도구 선택 | 모호한 설명 | 구체적인 트리거 단어로 설명 재작성 |
| 필수 인자 누락 | 모델이 파라미터를 잊음 | 파라미터 설명에 명확한 예시 추가 |
| 무한 도구 루프 | 모델이 같은 도구를 계속 호출 | 최대 반복 횟수 설정(5~10)과 반복 호출 감지 |
| 지어낸 인자 | 모델이 그럴듯하지만 틀린 값을 만듦 | enum 사용, 알려진 값으로 검증 |
| 도구 결과가 너무 큼 | API가 100KB 데이터를 반환 | 다시 먹여 주기 전에 잘라내기 또는 요약 |
| 모델이 도구 결과를 무시 | 결과 형식이 혼란스러움 | 필드 이름이 명확한 깔끔한 JSON 반환 |
