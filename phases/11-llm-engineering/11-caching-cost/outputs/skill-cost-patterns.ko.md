# LLM 비용 최적화 패턴

비용을 통제해야 하는 LLM 애플리케이션을 만들 때는 이 의사 결정 프레임워크를 적용하세요.

## 언제 최적화하나

**즉시 최적화해야 하는 경우:**
- 월간 LLM 지출이 $500 또는 인프라 예산의 10%를 넘을 때
- 소비자용 제품에서 질의당 비용이 $0.01을 넘을 때
- 시스템 프롬프트가 1,000토큰을 넘고 모든 요청마다 전송될 때
- 질의의 30% 이상이 중복 또는 거의 중복일 때
- 일일 사용자를 100명에서 10,000명 이상으로 확장하는 중일 때

**아직 최적화하면 안 되는 경우:**
- DAU가 100명 미만이고 제품-시장 적합성을 검증하는 중일 때
- 월간 지출이 $100 미만이고 천천히 늘어나는 중일 때
- 아직 프롬프트 설계를 반복하는 중일 때 (캐싱은 특정 프롬프트에 고정됨)

## 캐싱 전략 선택

### 정확 캐싱

**쓰는 경우:** temperature=0, 동일한 프롬프트 반복, 결정론적 출력이 필요할 때.

```python
key = sha256(json.dumps({"model": m, "messages": msgs, "temp": 0}))
```

- 구현: 30분
- 히트율: 대부분의 앱에서 10-25%, FAQ 봇에서 40-60%
- 지연 시간: 1ms 미만 (딕셔너리 조회)
- 위험: 기반 데이터가 바뀌면 오래된(stale) 응답

**건너뛰는 경우:** temperature > 0, 모든 질의가 고유, 실시간 데이터 필요.

### 시맨틱 캐싱

**쓰는 경우:** 사용자가 같은 질문을 다른 표현으로 하는 경우, FAQ 위주 제품, 고객 지원.

- 구현: 2-4시간 (임베딩 + 유사도 + 저장소)
- 히트율: 정확 캐시 위에 15-35% 추가
- 지연 시간: 10-50ms (임베딩 + ANN 검색)
- 위험: 오탐(비슷하지만 다른 질문에 잘못된 캐시 답변을 돌려주는 것)

**임계값 가이드:**
- 0.98 이상: 매우 보수적, 오탐이 거의 없음, 히트율 낮음
- 0.95: 사실 기반 Q&A에 적합한 균형점
- 0.90: 공격적, 히트율 높지만 오답 위험
- 0.85: 저위험 애플리케이션 전용 (추천, 자동 완성)

**건너뛰는 경우:** 모든 질의의 컨텍스트가 고유(코드 생성), 응답이 최신 데이터를 반영해야 함, 질의 공간이 무한.

### 프로바이더 프롬프트 캐싱

**쓰는 경우:** 시스템 프롬프트가 1,024토큰(OpenAI) 또는 모델별 최소치를 넘고, 같은 프리픽스가 반복 전송될 때.

| 프로바이더 | 조치 | 절감 |
|----------|--------|---------|
| Anthropic | 시스템 메시지에 `cache_control: {"type": "ephemeral"}` 추가 | 캐시된 프리픽스의 90% (25% 쓰기 프리미엄 이후) |
| OpenAI | 아무것도 안 함 (자동) | 캐시된 프리픽스의 50% |
| Google | 명시적 TTL과 함께 Context Caching API 사용 | 캐시된 컨텍스트의 약 75% |

**건너뛰는 경우:** 요청마다 시스템 프롬프트가 바뀜, 프롬프트가 최소 길이 미달.

## 모델 라우팅 규칙

### 키워드 기반 (단순, 빠름)

```
simple:  <= 5 단어 OR FAQ 키워드 일치 -> gpt-4o-mini ($0.15/$0.60)
medium:  일반 질의, 요약              -> claude-sonnet ($3/$15)
complex: "analyze", "compare", "debug" -> gpt-4o ($2.50/$10)
```

- 구현: 1시간
- 정확도: 70-80%
- 절감: 모델 비용의 40-60%

### 임베딩 기반 (더 정확)

카테고리당 레이블된 질의 50-100개를 임베딩합니다. 새 질의는 최근접 이웃으로 분류합니다.

- 구현: 4-8시간
- 정확도: 85-92%
- 절감: 모델 비용의 50-70%
- 추가 비용: 분류용 임베딩으로 백만 토큰당 약 $0.02 (무시 가능)

### ML 기반 (프로덕션 등급)

과거 질의/모델 쌍 데이터로 작은 분류기(로지스틱 회귀 또는 소형 BERT)를 학습시킵니다.

- 구현: 1-2주
- 정확도: 90-95%
- 절감: 모델 비용의 60-75%
- 필요한 것: 프로덕션 트래픽에서 수집한 레이블된 학습 데이터

## 속도 제한 설정

### 티어별 토큰 버킷 파라미터

| 티어 | 버킷 크기 | 재충전 속도 | 최대 RPM | 일일 한도 |
|------|-------------|-------------|---------|-----------|
| Free | 5만 토큰 | 초당 500 | 10 | 5만 |
| Pro | 50만 토큰 | 초당 5천 | 60 | 50만 |
| Enterprise | 5백만 토큰 | 초당 5만 | 300 | 5백만 |

### 구현 체크리스트

1. 멀티 인스턴스 앱을 위해 버킷을 Redis에 저장한다 (인메모리 X)
2. 원자적 연산(MULTI/EXEC)으로 경쟁 상태(race condition)를 막는다
3. 거부 응답에 `Retry-After` 헤더를 반환한다
4. 거부된 요청을 지표로 추적한다 (거부율 5% 초과 = 티어 한도가 너무 빡빡함)
5. 단계적 성능 저하를 구현한다: 비싼 모델 요청부터 거부하고, 싼 모델 접근은 유지한다

## 예산 통제

### 3단계 서킷 브레이커

| 임계값 | 조치 | 되돌릴 수 있는가 |
|-----------|--------|------------|
| 월간 예산의 70% | 경고 기록, Slack/PagerDuty로 팀 알림 | 예 (자동) |
| 월간 예산의 85% | 모든 트래픽을 가장 싼 모델로 라우팅 | 예 (자동, 다음 청구 주기) |
| 월간 예산의 95% | 캐시된 응답만 제공, 새 LLM 호출 거부 | 예 (수동 초기화 또는 다음 주기) |

### 사용자별 비용 추적

사용자별 누적 비용을 추적합니다. 중앙값의 10배를 넘는 사용자를 표시하세요. 흔한 원인:
- 합법적인 파워 유저 (티어 업그레이드 제안)
- 프롬프트 인젝션 루프 (봇이 자동 요청을 보내는 중)
- 비효율적인 통합 (클라이언트가 에러마다 재시도하는 중)

## 비용 추적 필드

모든 API 호출을 다음 필드와 함께 기록합니다:

```json
{
  "timestamp": "2026-04-02T10:30:00Z",
  "model": "gpt-4o",
  "input_tokens": 1523,
  "output_tokens": 487,
  "cached_input_tokens": 1024,
  "latency_ms": 1847,
  "cost_usd": 0.006142,
  "user_id": "user_abc123",
  "cache_status": "partial_hit",
  "request_category": "customer_support",
  "complexity_class": "medium",
  "routed_from": "gpt-4o"
}
```

### 대시보드에 올릴 핵심 지표

- **질의당 비용** (P50, P95, P99) -- 모델별, 기능별, 사용자 티어별
- **캐시 히트율** -- 정확 vs 시맨틱, 시간에 따른 추이
- **모델 분포** -- 모델별 트래픽 비율, 모델별 비용
- **예산 소진 속도** -- 현재 지출 vs 현재 속도 기준 월말 예상치
- **거부율** -- 속도 제한에 걸린 요청 비율, 티어별

## 흔한 실수

| 실수 | 해가 되는 이유 | 해결책 |
|---------|-------------|-----|
| temperature > 0에서 캐싱 | 출력이 비결정론적, 오래된 캐시가 잘못된 다양성을 제공 | temp=0 호출만 캐시하거나, 캐시된 응답이 무작위성을 잃는다는 점을 감수 |
| 시맨틱 캐시 임계값이 너무 낮음 | 표면적으로만 비슷한 질의에 오답을 반환 | 0.95에서 시작하고, 오탐률을 측정한 후에만 낮춘다 |
| 캐시 무효화 없음 | 기반 데이터가 바뀌면 응답이 낡음 | TTL 설정(동적 데이터 1시간, 정적 데이터 24시간), 데이터 업데이트 시 무효화 |
| 모든 트래픽을 가장 싼 모델로 라우팅 | 품질이 떨어지고 사용자가 알아차림 | 복잡도로 라우팅하고, 티어별 품질을 측정하고, 최소 품질 임계값을 설정 |
| 사용자별 한도 없음 | 어뷰징 사용자 한 명이 예산 전부를 태움 | 아무리 넉넉하더라도 항상 사용자별 할당량 구현 |
| 출력 토큰 무시 | 출력은 토큰당 입력보다 2-5배 비쌈 | max_tokens를 적절히 설정, stop 시퀀스 사용, 출력 압축 |
| 프롬프트가 안정되기 전에 캐싱 | 캐시가 옛 프롬프트의 응답으로 채워짐 | 프롬프트 확정 후에만 캐싱 활성화, 프롬프트 변경 시 캐시 플러시 |
