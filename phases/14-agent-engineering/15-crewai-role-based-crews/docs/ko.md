# 역할 기반 에이전트 팀 — 역할, 태스크, 프로세스

> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [en.md](en.md)

> 네 가지 기본 요소: Agent, Task, Crew, Process. 두 가지 최상위 형태: 크루(자율적, 역할 기반 협업)와 플로(이벤트 주도, 결정론적). CrewAI는 2026년의 기준 구현이며, 문서는 돌직구를 던집니다: "프로덕션 수준 애플리케이션은 Flow로 시작하라."

**유형:** 학습 + 빌드
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 14 · 12 (워크플로 패턴), 페이즈 14 · 14 (액터 모델)
**시간:** 약 75분

## 학습 목표

- CrewAI의 네 기본 요소(Agent, Task, Crew, Process)와 각각이 소유한 것을 말할 수 있습니다.
- Sequential, Hierarchical, 그리고 계획 중인 Consensus 프로세스를 구분하고, 워크로드마다 하나를 고릅니다.
- 크루(자율적 역할 기반)와 플로(이벤트 주도 결정론적)를 구분하고, 문서의 프로덕션 권고를 설명할 수 있습니다.
- `@tool` 데코레이터와 `BaseTool` 서브클래스로 도구를 연결하고, 구조화 출력과 자유 텍스트를 저울질합니다.
- CrewAI의 네 가지 메모리 유형과 각각이 빛을 보는 때를 말할 수 있습니다.
- 브리프를 만들어 내는 표준 라이브러리 기반 3에이전트 크루(리서처, 라이터, 에디터)를 구현합니다.
- CrewAI의 세 가지 실패 양상 — 프롬프트 비대, 매니저 LLM 세금, 깨지기 쉬운 인계 — 을 알아봅니다.

## 문제

멀티 에이전트 프레임워크를 도입한 팀들은 같은 벽에 부딪힙니다. "자율적 협업"은 데모에서는 그럴듯합니다. 그런데 고객이 버그를 접수하면 결정론적 재현이 필요해집니다. 재무 부서가 LLM 라우팅 크루가 실행당 얼마인지 묻습니다. 온콜 엔지니어는 새벽 3시에 어떤 에이전트가 멈췄는지 알아야 합니다.

자유 형식의 LLM 라우팅 크루는 이 질문 중 하나도 깔끔하게 답하지 못합니다. 순수 DAG는 전부 답하지만 브레인스토밍 에이전트에 필요한 탐색적 모양을 잃습니다.

CrewAI의 이분법은 이 트레이드오프에 솔직합니다. 협업적·역할 기반·탐색적 작업에는 크루. 이벤트 주도·코드 소유·감사 가능한 프로덕션에는 플로. 같은 프레임워크, 두 가지 모양, 표면마다 고르는 겁니다.

## 개념

### 네 가지 기본 요소

CrewAI의 표면은 작습니다. 이것만 외우면 나머지는 설정입니다.

- **Agent.** `role + goal + backstory + tools + (선택) llm`. 백스토리가 구조를 떠받칩니다. 말투와 판단, 에이전트가 언제 멈추는지를 만듭니다. 도구는 에이전트가 호출할 수 있는 함수입니다(뒤에서 더 다룹니다).
- **Task.** `description + expected_output + agent + (선택) context + (선택) output_pydantic`. 재사용 가능한 작업 단위입니다. `expected_output`이 계약입니다. `context`는 출력이 전달되는 상류 태스크의 목록입니다. `output_pydantic`은 구조화된 모양을 강제합니다.
- **Crew.** 컨테이너입니다. `agents` 목록, `tasks` 목록, `process`, 그리고 선택적 `memory` + `verbose` + `manager_llm` 설정을 소유합니다.
- **Process.** 실행 전략입니다. Sequential, Hierarchical, Consensus(계획 중). 실행의 모양을 정합니다.

에이전트들은 서로를 직접 보지 못합니다. 태스크가 에이전트를 참조하고, 크루가 태스크를 순서대로 배열하고, 프로세스가 다음 태스크를 누가 고르는지 정합니다. 이게 사고 모델의 전부입니다.

> **CrewAI 0.86 기준 검증**(2026-05). 더 최신 버전은 프로세스 타입의 이름을 바꾸거나 합칠 수 있습니다. 특정 모양에 의존하기 전에 [CrewAI Processes 문서](https://docs.crewai.com/concepts/processes)를 확인하세요.

### Sequential vs Hierarchical vs Consensus

- **Sequential.** 태스크가 선언 순서대로 돕니다. 태스크 N의 출력이 `context`로 태스크 N+1에 전달됩니다. 비용이 가장 낮고 가장 예측 가능합니다. 순서가 고정일 때 쓰세요.
- **Hierarchical.** 매니저 에이전트(별도 LLM 호출)가 전문가들 사이를 배차합니다. CrewAI는 `manager_llm` 설정이나 기본값으로 매니저를 만듭니다. 매니저는 매 라운드 다음 태스크를 고르고 거절하거나 재배차할 수 있습니다. 전문가가 넷 이상이고 순서가 진짜로 이전 출력에 달려 있을 때 쓰세요.
- **Consensus.** 계획 중이며, 현재 공개 API에는 구현되지 않았습니다. 문서는 이 이름을 투표 기반 프로세스의 미래를 위해 남겨 둡니다. 지금 의존하지 마세요.

Hierarchical은 모든 전문가 호출 위에 라운드마다 LLM 호출(매니저)을 얹습니다. 5단계 실행에서 토큰 비용이 세 배가 될 수 있습니다. 라우팅이 정말 필요할 때만 값을 지불하세요.

### 크루 vs 플로

2026년 문서가 첫머리에 내세우는 프레이밍입니다.

- **크루.** LLM 주도의 자율성. 프레임워크가 실행 시점에 모양을 고릅니다. 좋은 용도: 리서치, 브레인스토밍, 초고, 경로 자체가 답의 일부인 모든 곳. 재현은 어렵고, 테스트는 어렵고, 프로토타이핑은 쌉니다.
- **플로.** 여러분이 소유하는 이벤트 주도 그래프. `@start`가 진입점을 표시합니다. `@listen(topic)`은 다른 단계가 그 토픽을 발행할 때 발동하는 단계를 표시합니다. 각 단계는 일반 Python입니다(내부에서 크루를 호출할 수 있음). 좋은 용도: 프로덕션. 관측 가능하고, 테스트 가능하고, 결정론적입니다.

문서의 2026년 프로덕션 권고: Flow로 시작하라. 자율성이 비용을 정당할 때는 Flow 단계 안에서 `Crew.kickoff()` 호출로 크루를 접어 넣습니다. 플로가 감사 기록을 주고, 크루가 탐색을 줍니다. 고르지 말고 조합하세요.

### 도구 통합

에이전트에게 도구를 주는 세 가지 방법. 맞는 가장 단순한 것을 고르세요.

1. **`@tool` 데코레이터.** 순수 함수가 도구가 됩니다. 시그니처가 스키마이고, docstring은 LLM이 보는 설명입니다. 일회성 헬퍼에 가장 좋습니다.

   ```python
   from crewai.tools import tool

   @tool("Search the web")
   def search(query: str) -> str:
       """Return top results for the query."""
       return run_search(query)
   ```

2. **`BaseTool` 서브클래스.** 명시적 args 스키마, 비동기 지원, 재시도를 갖춘 클래스 기반 도구. 도구가 상태를 가지거나(클라이언트, 캐시) 구조화된 인자가 필요할 때 쓰세요.

   ```python
   from crewai.tools import BaseTool
   from pydantic import BaseModel

   class SearchArgs(BaseModel):
       query: str
       limit: int = 10

   class SearchTool(BaseTool):
       name = "web_search"
       description = "Search the web and return top results."
       args_schema = SearchArgs

       def _run(self, query: str, limit: int = 10) -> str:
           return self.client.search(query, limit=limit)
   ```

3. **내장 툴킷.** CrewAI는 자사 어댑터를 실어 나옵니다: `SerperDevTool`, `FileReadTool`, `DirectoryReadTool`, `CodeInterpreterTool`, `RagTool`, `WebsiteSearchTool`. 임포트 한 줄로 연결됩니다.

구조화 출력은 Pydantic을 씁니다. 태스크에 `output_pydantic=MyModel`을 넘기세요. CrewAI는 LLM 응답을 모델로 검증해 형을 맞추거나 재시도합니다. 여기에 빡빡한 `expected_output` 문자열을 짝지으세요. 자유 텍스트 출력은 초고엔 충분하지만, 하류 플로가 소비할 수 있는 것은 구조화 출력입니다.

### 메모리 훅

CrewAI는 네 가지 메모리 유형을 기본으로 실어 나옵니다. 조합도 됩니다: 크루는 넷을 동시에 켤 수 있습니다.

> **CrewAI 0.86 기준 검증**(2026-05). 최근 릴리스는 이 네 저장소를 감싸는 통합 `Memory` 시스템으로 모든 것을 보냅니다. 아래의 개념 모델은 여전히 유효하지만, 더 새 버전에서는 공개 클래스 표면이 단일 `Memory` 진입점으로 합쳐질 수 있습니다. 현재 API는 [CrewAI memory 문서](https://docs.crewai.com/concepts/memory)를 확인하세요.

- **단기.** 한 번의 실행 안에서의 대화 버퍼. 끝나면 지워집니다.
- **장기.** 실행을 넘어 영속화됩니다. 벡터 DB에 저장되고(기본은 Chroma, 교체 가능), 현재 태스크와의 유사도로 꺼냅니다.
- **엔티티.** 엔티티별 사실입니다. "X 고객은 엔터프라이즈 플랜이다." 유사도가 아니라 엔티티로 키가 잡힙니다. 실행을 넘어 살아남습니다.
- **문맥적.** 조립 시점 검색입니다. 미리 싣지 않고, 에이전트가 필요한 순간에 관련 메모리를 끌어 옵니다.

크루에 `memory=True` 또는 유형별 설정으로 켭니다. 설정한 임베딩 제공자가 뒷받침합니다(기본은 OpenAI, 로컬로 교체 가능). 메모리는 얇은 프레임워크와 비교해 CrewAI가 값을 증명하는 지점 중 하나입니다. 순수 LangGraph라면 이 각각을 직접 연결해야 합니다.

### 역할 기반 팀이 맞는 때

- 이름 있는 역할과 협업 워크플로를 갖춘 3~6개 에이전트. 초고 쓰기, 리뷰, 계획, 브레인스토밍.
- 다음 단계에 대한 LLM의 판단 자체가 가치의 일부인 라우팅(Hierarchical).
- 팀이 그래프 정의를 읽는 것보다 `role + goal + backstory`를 읽는 쪽이 편한 모든 곳.

### 맞지 않는 때

- 엄격한 순서를 가진 결정론적 DAG. LangGraph(레슨 13)를 쓰세요. 그래프 모양이 맞는 추상화이고, CrewAI의 역할 프레이밍은 마찰입니다.
- 1초 미만 지연 시간 예산. Hierarchical은 왕복을 더합니다. Sequential조차 백스토리와 이전 출력이 들어간 프롬프트를 직렬화합니다.
- 단일 에이전트 루프. 프레임워크를 건너뛰세요. 에이전트 루프(레슨 1) + 도구 레지스트리가 더 짧습니다.

레슨 17(Agent Framework Tradeoffs)이 이걸 표로 정리합니다. 요약하면: CrewAI는 "협업적 역할 기반" 구석에 앉아 있습니다.

### 의존성 모양

LangChain과 독립적입니다. Python 3.10~3.13. `uv`를 씁니다. 스타 수: [crewAIInc/crewAI](https://github.com/crewAIInc/crewAI) 참고(2026-05 기준 스냅샷). AWS Bedrock 연동은 문서화되어 있습니다. 벤더 벤치마크는 QA 워크로드에서 LangGraph 대비 상당한 가속을 보고하지만, 방법론(데이터셋, 하드웨어, 평가 지표)이 공개되지 않았으므로 프레임워크 벤더 수치는 참고용으로만 받아들이세요.

### 이 패턴이 잘못되는 지점

- **백스토리가 부르는 프롬프트 비대.** 에이전트당 2000단어 백스토리에 다섯 에이전트 크루라면 첫 도구 호출 전에 컨텍스트 예산이 타 없어집니다. 백스토리는 200단어 아래로. 문구는 에이전트들끼리 재활용하세요. 하우스 스타일을 다섯 번 반복하지 마세요.
- **매니저 LLM 토큰 세금.** Hierarchical 프로세스는 모든 전문가 호출 전에 매니저 LLM 호출을 더합니다. 태스크 다섯 개짜리 크루에서는 LLM 호출이 다섯 번이 아니라 여섯 번이고, 매니저 호출은 전체 태스크 목록과 이전 출력까지 실어 나릅니다. 라우팅이 출력에 달려 있지 않다면 Sequential로 바꾸세요.
- **깨지기 쉬운 인계.** 태스크 N의 `expected_output`이 "개요 하나"입니다. 태스크 N+1이 그걸 `context`로 읽고 섹션 3개를 파싱하려 합니다. LLM은 네 개를 만들었죠. 하류 에이전트는 즉흥으로 때웁니다. 태스크 N에 `output_pydantic`을 붙여 태스크 N+1이 자유 텍스트가 아니라 타입 객체를 읽게 고치세요.
- **크루를 프로덕션에.** Flow 포장 없이 자유 형식 크루를 프로덕션에 출시하는 것. 출력 변동성이 높고, 재현은 불가능하고, 온콜은 나쁜 실행과 좋은 실행을 비교할 수 없습니다. Flow로 감싸세요.

## 직접 만들기

`code/main.py`는 두 모양의 표준 라이브러리 버전과 3에이전트 크루를 구현합니다.

구성:

- CrewAI의 표면에 맞춘 `Agent`, `Task` 데이터클래스.
- `SequentialCrew.kickoff(inputs)`는 선언 순서대로 태스크를 돌리고 출력을 `context`로 흘려 보냅니다.
- `HierarchicalCrew.kickoff(topic)`는 매 라운드 다음 전문가를 고르는 매니저 에이전트를 더하고, "done"에서 멈춥니다.
- `@start`와 `@listen(topic)` 데코레이터, 작은 이벤트 루프, 추적을 갖춘 `Flow`.
- CrewAI의 `@tool` 모양을 본뜬 `tool(name)` 데코레이터.
- `short_term`, `long_term`, `entity` 저장소를 가진 `Memory`. 모의 유사도 계산은 numpy를 씁니다.
- 모의 LLM 응답은 역할 + 입력 접두사를 키로 삼은 하드코딩 문자열입니다. 네트워크 없음. 결정론적.

구체적 데모: "agent engineering 2026"에 관한 브리프를 만드는 리서처·라이터·에디터 크루. 리서처가 (모의) 소스를 끌어 오고, 라이터가 초고를 쓰고, 에디터가 다듬습니다. 같은 크루가 Flow를 통해 돌며 결정론적 모양을 보여 줍니다.

실행 방법:

```bash
python3 code/main.py
```

추적 내용: 출력을 `context`로 흘려 보내는 순차 크루, 매니저가 고르는 계층형 크루(리서처, 라이터, 에디터, 그다음 "done"), 명시적 토픽(`researched`, `drafted`, `edited`)으로 같은 세 단계를 도는 플로, `@tool`로 배차되는 도구 호출, 두 번의 킥오프에 걸쳐 살아남는 장기 메모리.

크루 추적은 유동적입니다. 매니저가 원칙적으로 순서를 바꿀 수 있죠. 플로 추적은 고정입니다. 그 선택 자체가 이 레슨입니다.

## 활용하기

- 프로덕션에는 **CrewAI Flow**. 그 Flow가 `Crew.kickoff()`를 부르는 한 단계일 때도 마찬가지입니다. Flow가 감사 경계를 줍니다.
- 순서가 명확한 협업 작업, 특히 초고와 리뷰 루프에는 **CrewAI Crew (Sequential)**.
- 라우팅이 출력에 달려 있고 전문가가 넷 이상일 때는 **CrewAI Crew (Hierarchical)**.
- 명시적 상태 기계, 내구 재개, 엄격한 순서에는 **LangGraph**(레슨 13).
- 액터 모델 동시성과 결함 격리에는 **AutoGen v0.4**(레슨 14).
- 핸드오프와 가드레일이 있는 OpenAI 우선 제품에는 **OpenAI Agents SDK**(레슨 16).
- 서브에이전트와 세션 저장소가 있는 Claude 우선 제품에는 **Claude Agent SDK**(레슨 17).

## 산출물 내보내기

`outputs/skill-crew-or-flow.md`는 태스크에 대해 크루냐 플로냐를 골라 최소 구현의 뼈대를 만들어 줍니다. 백스토리 없는 크루, 명시적 토픽 없는 플로, 전문가 셋 미만인 Hierarchical은 무조건 반려합니다.

## 함정

- **맛보기용 백스토리.** 백스토리는 출력을 만듭니다. 에이전트당 변형 세 개를 테스트하세요. 편차는 실제입니다. 하나를 골라 얼리세요.
- **`expected_output` 건너뛰기.** 태스크마다 계약이 없으면 하류 태스크는 LLM이 만든 뭐든 그냥 받아 씁니다. 크루는 돌지만 감사는 실패합니다.
- **항상 켜진 메모리.** 장기 메모리는 매 실행마다 씁니다. 벡터 DB는 불어나고 검색은 시끄러워집니다. 사실이 지속되는 태스크에만 쓰기 범위를 제한하세요.
- **매니저 프롬프트 드리프트.** Hierarchical의 매니저 프롬프트는 암묵적입니다. 라우팅이 이상해지면 verbose 모드로 덤프해서 읽어 보세요.
- **크루 안의 부수 효과 도구.** 크루는 예상보다 도구를 더 많이 호출할 수 있습니다. POST, DELETE, 결제는 Flow 단계에 넣으세요. 크루 도구에는 절대 넣지 마세요.

## 연습 문제

1. 순차 크루를 Flow로 바꾸세요. 변동성이 떨어지는 접점을 세어 보고, 가독성이 떨어진 지점도 적어 둡니다.
2. 크루에 엔티티 메모리를 추가하세요: 고객에 관한 사실이 킥오프를 넘어 유지됩니다. 검색이 올바른 엔티티를 꺼내 오는지 확인합니다.
3. 라이터의 출력이 최소 세 문단이 될 때까지 매니저가 에디터로 배차를 거부하는 Hierarchical 프로세스를 구현하세요. 재시도를 추적합니다.
4. (모의) 웹 검색용 `BaseTool` 서브클래스를 연결하세요. `@tool` 데코레이터 버전과 추적 모양을 비교합니다.
5. 에디터 태스크에 `output_pydantic=Brief`를 추가하세요. `Brief`는 `title`, `summary`, `sections`를 가집니다. 라이터 태스크가 한 번은 깨진 JSON을 내뱉게 만들고, 추적에서 CrewAI의 재시도 동작을 확인합니다.
6. CrewAI 문서 입문을 읽어 보세요. 연습용 구현을 진짜 `crewai` API로 옮깁니다. 표준 라이브러리 버전은 어떤 보장을 건너뛰었나요?
7. 실제 실행에 AgentOps나 Langfuse(레슨 24)를 연결하세요. 표준 라이브러리 버전에서 빠뜨린 추적은 무엇이었나요?

## 핵심 용어

| 용어 | 사람들이 말하는 표현 | 실제 의미 |
|------|----------------|------------------------|
| Agent | "페르소나" | 역할 + 목표 + 백스토리 + 도구 |
| Task | "작업 단위" | 설명 + 기대 출력 + 담당자 + 선택적 구조화 출력 |
| Crew | "에이전트 팀" | Agent + Task + Process의 컨테이너 |
| Process | "실행 전략" | Sequential / Hierarchical / Consensus(계획 중) |
| Flow | "결정론적 워크플로" | 이벤트 주도, 코드 소유, 테스트 가능 |
| Backstory | "페르소나 프롬프트" | 에이전트의 말투와 판단을 빚는 요소 |
| `@tool` | "함수 도구" | 함수를 에이전트가 호출할 수 있는 도구로 바꾸는 데코레이터 |
| `BaseTool` | "클래스 도구" | args 스키마, 재시도, 비동기 지원을 갖춘 클래스 기반 도구 |
| 엔티티 메모리 | "엔티티별 사실" | 고객/계정/이슈로 범위가 잡힌 메모리 |
| 장기 메모리 | "실행 간 메모리" | 킥오프 사이에서 살아남는 벡터 기반 메모리 |
| 문맥 메모리 | "적시 검색" | 에이전트가 필요한 순간에 끌어 오는 메모리 |
| 매니저 LLM | "라우터 에이전트" | Hierarchical 프로세스에서 다음 태스크를 고르는 추가 LLM |
| `expected_output` | "태스크 계약" | 에이전트(그리고 감사)에게 어떤 모양을 돌려줄지 알려 주는 문자열 |
