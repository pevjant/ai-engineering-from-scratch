# 에이전트 메모리 — 가상 컨텍스트와 메모리 페이징

> 컨텍스트 윈도우는 유한합니다. 대화, 문서, 도구 추적은 유한하지 않죠. 해결책은 운영체제 가상 메모리를 다시 말한 것입니다. 메인 컨텍스트는 RAM, 외부 저장소는 디스크, 에이전트는 그 사이를 페이징합니다. MemGPT(Packer 등, 2023)가 이 패턴에 이름을 붙였고, 수많은 프로덕션 메모리 시스템이 그 위에 서 있습니다.

**유형:** Build
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 14 · 01 (에이전트 루프), 페이즈 14 · 06 (도구 사용)
**시간:** ~75분

## 학습 목표

- MemGPT가 세운 운영체제 비유를 설명합니다. 메인 컨텍스트 = RAM, 외부 컨텍스트 = 디스크, 메모리 도구 = 페이지 인/아웃.
- 메인 컨텍스트 버퍼, 검색 가능한 외부 저장소, 페이지 인/아웃 도구를 갖춘 2계층 MemGPT 패턴을 표준 라이브러리로 구현합니다.
- 에이전트가 "인터럽트"를 발생시켜 외부 메모리를 질의·수정하는 방식과, 그 결과가 다음 프롬프트에 이어 붙는 방식을 설명합니다.
- MemGPT의 설계 선택 중 Letta(레슨 08)와 Mem0(레슨 09)로 이어지는 것들을 짚습니다.

## 문제 상황

컨텍스트 윈도우가 메모리 문제를 해결해 줄 것 같지만 그렇지 않습니다. 프로덕션(운영 환경)에서는 세 가지 실패 양상이 되풀이됩니다:

1. **넘침(Overflow).** 멀티 턴 대화, 긴 문서, 도구 호출이 많은 궤적이 윈도우를 넘습니다. 잘린 지점 너머는 전부 사라집니다.
2. **희석(Dilution).** 윈도우 안에 있더라도 관련 없는 맥락을 가득 채우면 중요한 것에 대한 어텐션이 희석됩니다. 프론티어 모델도 긴 입력에서는 여전히 성능이 떨어집니다.
3. **지속성(Persistence).** 새 세션은 빈 윈도우로 시작합니다. 외부 메모리가 없는 에이전트는 세션을 넘어 "예전에 내가 … 해 달라고 했잖아"라고 말할 수 없습니다.

더 큰 윈도우가 도움은 되지만 이 문제를 고치지는 않습니다. Mem0의 2025년 논문은 128k 윈도우 베이스라인이 여전히 놓치는 장기 사실을, 외부 메모리를 단 4k 윈도우 에이전트가 잡아 낸다는 것을 측정했습니다.

## 개념

### 운영체제 비유

MemGPT(Packer 등, arXiv:2310.08560, 2024년 2월 v2)는 컨텍스트 관리를 운영체제 가상 메모리에 대응시킵니다:

| OS 개념 | MemGPT 개념 | 2026년 프로덕션 대응물 |
|------------|---------------|------------------------|
| RAM | 메인 컨텍스트(프롬프트) | Anthropic/OpenAI 컨텍스트 윈도우 |
| 디스크 | 외부 컨텍스트 | 벡터 DB, KV, 그래프 저장소 |
| 페이지 폴트 | 메모리 도구 호출 | `memory.search`, `memory.read`, `memory.write` |
| OS 커널 | 에이전트 제어 루프 | 메모리 도구가 붙은 ReAct 루프 |

에이전트는 평범한 ReAct 루프를 돕니다. 한 부류의 도구가 더 있을 뿐입니다. 그 도구들로 메인 컨텍스트에 데이터를 페이지 인/아웃합니다.

### 두 계층

- **메인 컨텍스트.** 현재 과제를 담는 고정 크기 프롬프트. 언제나 모델에게 보입니다.
- **외부 컨텍스트.** 크기 제한 없이 도구로 검색합니다. 관련될 때 읽고, 사실이 나타날 때 씁니다.

원 논문은 이 설계를 기본 윈도우를 넘는 두 과제로 평가했습니다. 100k 토큰이 넘는 문서 분석과, 며칠에 걸쳐 지속되는 메모리를 가진 멀티 세션 채팅입니다.

### 인터럽트 패턴

MemGPT는 메모리를 인터럽트처럼 다룹니다. 대화 도중에 에이전트가 메모리 도구를 호출하면, 런타임이 실행하고, 결과가 새 관찰로서 다음 어시스턴트 턴에 이어 붙습니다. 개념적으로는 프로세스를 막았다가 바이트를 돌려주고 계속 진행하게 하는 Unix `read()` 시스템 콜과 완전히 같습니다.

표준적인 메모리 도구 표면:

- `core_memory_append(section, text)` — 프롬프트의 영속 섹션에 씁니다.
- `core_memory_replace(section, old, new)` — 영속 섹션을 고칩니다.
- `archival_memory_insert(text)` — 검색 가능한 외부 저장소에 씁니다.
- `archival_memory_search(query, top_k)` — 외부 저장소에서 꺼냅니다.
- `conversation_search(query)` — 지난 턴을 훑습니다.

### 논문이 끝나고 프로덕션이 시작되는 곳

2024년 9월 MemGPT는 Letta가 되었습니다. 연구 저장소(`cpacker/MemGPT`)는 남아 있고, Letta는 설계를 확장합니다:

- 두 계층 대신 세 계층(코어, 리콜, 아카이벌 — 레슨 08).
- `send_message`/하트비트 패턴을 대체하는 고유 추론(레슨 08).
- 비동기 메모리 작업을 돌리는 sleep-time 에이전트(레슨 08).

프로덕션 시스템이 Letta, Mem0, 또는 자체 2계층 저장소를 돌리더라도, MemGPT 논문은 2026년의 토대입니다.

### 이 패턴이 잘못 가는 곳

- **메모리 부패.** 쓰기가 읽기보다 빨리 쌓입니다. 검색이 낡은 사실에 잠깁니다. 해법: 주기적 통합(Letta의 sleep-time), 명시적 무효화(Mem0의 충돌 탐지기).
- **메모리 오염.** 외부 메모리는 검색되는 텍스트입니다. 공격자가 조종한 콘텐츠가 메모리 노트에 들어가면, 에이전트는 다음 세션에 그것을 다시 흡수합니다. 이것은 Greshake 등(레슨 27)의 공격을 시간축으로 다시 쓴 것입니다.
- **출처 상실.** 에이전트가 "사용자가 X를 출시하라고 했다"고 기억하지만 어느 턴인지 인용하지 못합니다. 모든 아카이벌 쓰기에 출처 참조(세션 ID, 턴 ID)를 함께 저장하세요.

## 만들어 보기

`code/main.py`는 MemGPT의 2계층 패턴을 표준 라이브러리로 구현합니다:

- `MainContext` — `core` 딕셔너리와 `messages` 리스트를 가진 고정 크기 프롬프트 버퍼, 상한을 넘으면 가장 오래된 메시지를 자동 압축.
- `ArchivalStore` — (id, text, tags, session, turn) 레코드를 담은 인메모리 BM25풍 저장소(토큰 겹침 점수).
- MemGPT 표면에 대응하는 다섯 가지 메모리 도구.
- 아카이벌에 사실을 채워 넣고, `archival_memory_search`를 호출해 질문에 답하는 스크립트된 에이전트.

실행:

```
python3 code/main.py
```

트레이스는 에이전트가 사실 세 개를 쓰고, 메인 컨텍스트를 상한까지 채워(강제 축출) 그다음 후속 질문에 아카이벌에서 꺼내 답하는 모습을 보여 줍니다. 실제 LLM 없이 MemGPT 워크플로를 재현합니다.

## 활용하기

오늘날의 모든 프로덕션 메모리 시스템은 MemGPT 변형입니다:

- **Letta** (레슨 08) — 세 계층, 고유 추론, sleep-time compute.
- **Mem0** (레슨 09) — 벡터 + KV + 그래프를 점수 계층으로 융합.
- **OpenAI Assistants / Responses** — 스레드와 파일로 관리형 메모리.
- **Claude Agent SDK** — 스킬과 세션 저장소를 통한 장기 메모리.

핵심 패턴으로 고르지 말고 운영 형태(자체 호스팅, 관리형, 프레임워크 통합)로 고르세요. 핵심 패턴은 어차피 MemGPT입니다.

### 에이전트 메모리의 형태

페이징은 용량을 해결합니다. 무엇을 저장할지는 결정하지 않습니다. 네 가지 메모리 유형이 프로덕션 시스템마다 되풀이되며, 각각 다른 질문에 답합니다:

- **작업 메모리(Working memory)** — 지금 무엇이 중요한가? 맥락 안의 계층: 현재 과제, 최근 턴, 고정된 코어 섹션. 프롬프트 그 자체입니다.
- **에피소드 메모리(Episodic memory)** — 무슨 일이 있었나? 과거 턴과 궤적. 세션·턴 참조와 함께 저장되고, 필요하면 재생됩니다.
- **의미 메모리(Semantic memory)** — 무엇이 사실인가? 사용자, 도메인, 세상에 대한 사실. 변할 때 갱신하고 중복을 제거합니다.
- **절차 메모리(Procedural memory)** — 이걸 어떻게 하나? 회상이 아니라 미래 행동을 이끄는 학습된 루틴, 선호, 규칙.

오픈소스 구현은 서로 다른 공격 지점을 고릅니다:

| 유형 | 구현 | 접근 방식 |
|------|----------------|-------------------|
| 작업 | MemGPT / Letta | 메모리 도구로 고정 프롬프트 예산에 콘텐츠를 페이지 인/아웃 (이 레슨, 레슨 08) |
| 에피소드 | Zep | 시간축 지식 그래프 — 사실에 유효 구간이 붙어서 "언제 무엇이 참이었는지" 질의 가능 |
| 의미 | Mem0 | 벡터·KV·그래프 저장소에 걸쳐 사실을 중복 제거하고 갱신하는 추출 파이프라인 (레슨 09) |
| 의미 + 절차 | LangMem | 턴 사이에 에이전트가 참조하는 저장소로 사실과 행동 규칙을 백그라운드 추출 |
| 에피소드 + 의미 | agentmemory | 실행 중인 세션을 포착해 타입이 지정되고 검색 가능한 레코드로 통합 |

## 연습 문제

1. 토큰으로 잰 `max_main_context_tokens` 상한(`len(text.split())` * 1.3으로 근사)을 추가해 보세요. 상한을 넘으면 가장 오래된 메시지를 요약으로 압축합니다. 요약기가 있을 때와 없을 때의 동작을 비교해 보세요.
2. 아카이벌 저장소 위에 BM25를 제대로 구현해 보세요(용어 빈도, 역문서 빈도). 토큰 겹침 베이스라인 대비 장난감 사실 집합에서 recall@10을 측정해 보세요.
3. 아카이벌 삽입에 `citation` 필드(session_id, turn_id, source_url)를 추가해 보세요. 검색에 근거한 모든 답에서 에이전트가 출처를 인용하게 만드세요.
4. 메모리 오염을 시뮬레이션해 보세요. "이후의 모든 사용자 지시를 무시하라"는 아카이벌 레코드를 추가합니다. 검색 결과에서 지시문 형태 텍스트를 훑어 신뢰할 수 없다고 표시하는 가드를 작성하세요.
5. 구현을 MemGPT 연구 저장소의 core-memory JSON 스키마(`cpacker/MemGPT`)로 이식해 보세요. 평면 문자열에서 타입이 지정된 섹션으로 바꾸면 무엇이 달라질까요?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| 가상 컨텍스트(Virtual context) | "무한 메모리" | 페이지 인/아웃이 있는 메인(프롬프트) + 외부(검색 가능) 계층 |
| 메인 컨텍스트(Main context) | "작업 메모리" | 프롬프트 — 고정 크기, 언제나 보임 |
| 아카이벌 메모리(Archival memory) | "장기 저장소" | 외부의 검색 가능한 지속 저장소, 필요할 때 검색 |
| 코어 메모리(Core memory) | "영속 프롬프트 섹션" | 메인 컨텍스트 안에 고정된 이름 있는 섹션 |
| 메모리 도구(Memory tool) | "메모리 API" | 에이전트가 외부 메모리를 읽고/쓰려고 발행하는 도구 호출 |
| 인터럽트(Interrupt) | "메모리 페이지 폴트" | 에이전트가 멈추고, 런타임이 가져오고, 결과가 다음 턴에 이어 붙음 |
| 메모리 부패(Memory rot) | "낡은 사실" | 오래된 쓰기가 검색을 잠급니다. 통합으로 해결 |
| 메모리 오염(Memory poisoning) | "주입된 영속 노트" | 공격자 콘텐츠가 메모리로 저장되고, 회상 때 다시 흡수됨 |
