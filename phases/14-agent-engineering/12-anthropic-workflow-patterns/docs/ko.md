# Anthropic의 워크플로 패턴: 복잡한 것보다 단순한 것

> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [en.md](en.md)

> Schluntz와 Zhang(Anthropic, 2024년 12월)은 워크플로(미리 정의된 경로)와 에이전트(동적 도구 사용)를 구분합니다. 다섯 가지 워크플로 패턴이 대부분의 경우를 커버합니다. 직접 API 호출로 시작하세요. 단계를 예측할 수 없을 때만 에이전트를 더하세요.

**유형:** 학습 + 빌드
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 14 · 01 (에이전트 루프)
**시간:** 약 60분

## 학습 목표

- Anthropic의 다섯 가지 워크플로 패턴 — 프롬프트 체이닝, 라우팅, 병렬화, 오케스트레이터-워커, 평가자-최적화자 — 를 말할 수 있습니다.
- 에이전트와 워크플로의 구분과 각각의 공학적 비용을 설명할 수 있습니다.
- 에이전트 대신 워크플로를 고를 때(그 반대일 때)를 가려낼 수 있습니다.
- 스크립트형 LLM을 상대로 다섯 패턴을 모두 표준 라이브러리로 구현합니다.

## 문제

함수 호출 하나면 되는 문제에 팀들이 멀티 에이전트 프레임워크를 꺼내 듭니다. 대가는 실제입니다. 프레임워크는 프롬프트를 가리고, 제어 흐름을 숨기고, 성급한 복잡성을 초대하는 레이어를 얹습니다. Schluntz와 Zhang의 2024년 12월 글은 가장 많이 인용되는 업계의 반성책입니다: 단순하게 시작하고, 대가를 정당할 때만 복잡성을 더하라.

## 개념

### 워크플로 vs 에이전트

- **워크플로.** 미리 정의된 코드 경로로 LLM과 도구를 엮어 내는 것. 그래프의 주인은 엔지니어입니다.
- **에이전트.** LLM이 스스로 도구를 지정하고 스스로 다음 단계를 밟는 것. 그래프의 주인은 모델입니다.

둘 다 제 자리가 있습니다. 워크플로는 더 싸고, 빠르고, 디버깅이 쉽습니다. 에이전트는 열린 문제를 풀지만 실패 양상을 추론하기 어렵게 만듭니다.

### 증강된 LLM

다섯 패턴 모두의 기초: 검색(검색 증강), 도구(행동), 메모리(영속화)라는 세 능력이 연결된 LLM 하나. 어떤 API 호출이든 이 능력들을 쓸 수 있습니다.

### 다섯 가지 패턴

1. **프롬프트 체이닝.** 첫 번째 호출의 출력이 두 번째 호출의 입력이 됩니다. 태스크가 깔끔한 선형 분해를 가질 때 씁니다. 단계 사이에 선택적인 프로그램 방식 게이트를 둘 수 있습니다.

2. **라우팅.** 분류기 LLM이 어느 하류 LLM이나 도구를 호출할지 고릅니다. 범주가 다른 입력에 다른 처리가 필요할 때 씁니다(1티어 지원 vs 환불 vs 버그 vs 영업).

3. **병렬화.** N개의 LLM 호출을 동시에 돌리고 결과를 모읍니다. 두 가지 모양이 있습니다: 구획 나누기(서로 다른 조각)와 투표(같은 프롬프트, N회 실행, 다수결/종합).

4. **오케스트레이터-워커.** 오케스트레이터 LLM이 어떤 워커(이것도 LLM)를 돌릴지 동적으로 정하고 그 출력을 종합합니다. 에이전트 루프와 비슷하지만 오케스트레이터는 무한히 반복하지 않습니다.

5. **평가자-최적화자.** 한 LLM이 답을 제안하면 다른 LLM이 평가합니다. 평가자가 통과할 때까지 반복합니다. Self-Refine(레슨 05)을 일반화한 것입니다.

### 워크플로가 에이전트를 이기는 곳

- **예측 가능한 태스크.** 단계를 나열할 수 있다면, 나열해야 합니다.
- **비용이 묶인 태스크.** 워크플로는 단계 수에 상한이 있습니다. 에이전트는 나뭇가지처럼 불어날 수 있습니다.
- **컴플라이언스가 묶인 태스크.** 감사자는 그래프를 읽길 원하지, 실행 기록으로부터 추론해 내길 원하지 않습니다.

### 에이전트가 워크플로를 이기는 곳

- **열린 연구.** 다음 단계가 이전 단계의 결과에 달려 있을 때.
- **길이가 변하는 태스크.** 단계 수를 알 수 없는 몇 분에서 몇 시간짜리 작업.
- **새로운 도메인.** 올바른 워크플로를 아직 모를 때 — 먼저 탐색하고, 나중에 코드로 굳히세요.

## 직접 만들기

`code/main.py`는 다섯 워크플로 패턴을 모두 `ScriptedLLM`을 상대로 구현합니다:

- `prompt_chain(input, steps)` — 순차 실행.
- `route(input, classifier, handlers)` — 분류 + 디스패치.
- `parallel_vote(prompt, n, aggregator)` — N회 실행, 결과 집계.
- `orchestrator_workers(task, workers)` — 오케스트레이터가 워커를 고름.
- `evaluator_optimizer(task, proposer, evaluator, max_iter)` — 통과할 때까지 반복.

실행 방법:

```
python3 code/main.py
```

각 패턴이 자기 추적을 출력합니다. 패턴당 코드 줄수는 10~15줄 정도입니다. 프레임워크의 비용은 수천 줄 단위로 잽니다.

## 활용하기

- 대부분의 태스크는 직접 API 호출로 충분합니다.
- 프레임워크는 패턴이 진짜로 영속 상태(LangGraph), 액터 모델 동시성(AutoGen v0.4), 역할 템플릿(CrewAI)을 필요로 할 때만 씁니다.
- Claude Code 하네스스의 모양을 새로 만들고 싶지 않다면 Claude Agent SDK를 꺼내세요.

## 연습 문제

1. 신뢰도 임계값이 있는 라우팅을 구현하세요. 임계값 아래면 -> 사람에게 에스컬레이션합니다. 1티어 지원 유스케이스에서 임계값은 어디에 잡히나요?
2. `parallel_vote`에 타임아웃을 추가하세요. 한 호출이 멈추면 어떻게 되나요? 표가 하나 빠졌을 때 어떻게 집계할까요?
3. `evaluator_optimizer`를 밴디트로 바꾸세요: 반복에 걸쳐 상위 2개 출력을 계속 간직해, 늦게 온 나쁜 결과가 늦게 온 좋은 결과를 덮어쓰지 않게 합니다.
4. 프롬프트 체이닝과 라우팅을 결합하세요: 라우터가 세 체인 중 하나를 고릅니다. 큰 프롬프트 하나로 버티는 대안과 토큰 비용을 비교해 보세요.
5. 여러분의 프로덕션 기능 하나를 고르세요. 워크플로 그래프를 그리고 단계를 세어 봅니다. 여기서 에이전트가 정말 나을까요?

| 워크플로 | "미리 정의된 흐름" | 엔지니어가 소유하는, LLM·도구 호출의 그래프 |
