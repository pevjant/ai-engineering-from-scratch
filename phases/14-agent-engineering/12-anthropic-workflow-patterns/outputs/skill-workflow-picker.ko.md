> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [skill-workflow-picker.md](skill-workflow-picker.md)

태스크 설명이 주어지면, 맞는 최소 패턴을 골라 가장 작은 올바른 구현을 만들어 냅니다.

의사결정 트리:

1. 단계를 나열할 수 있나? -> **프롬프트 체인** 또는 **라우팅**.
2. 독립적인 여러 실행에 걸쳐 출력을 모아야 하나? -> **병렬화**(구획 나누기 또는 투표).
3. 태스크마다 멤버가 달라지는 전문가 풀이 필요한가? -> **오케스트레이터-워커**.
4. 심판이 통과할 때까지 반복 정제가 필요한가? -> **평가자-최적화자**(Self-Refine 모양).
5. 위 어느 것도 아니거나, 단계 수가 중간 결과에 달려 있나? -> **에이전트 루프**(레슨 01).

만들 것:

- 워크플로라면: LLM + 도구 호출을 조합하는 순수 함수. 프레임워크 없음.
- 에이전트라면: 레슨 01의 ReAct 루프에, 태스크가 요구하는 도구 레지스트리를 더한 것.
- 판단 근거, 단계 수, 예상 토큰 비용, 관측 가능한 성공 기준을 담은 `README.md`.

절대 반려 사항:

- 태스크가 3단계 프롬프트 체인인데 프레임워크(LangGraph, AutoGen, CrewAI)를 꺼내는 것. 과잉 엔지니어링은 진짜 문제를 가립니다.
- 워커 3개짜리 오케스트레이터-워커를 "멀티 에이전트"라고 부르는 것. 워커는 에이전트가 아니라 LLM 호출입니다. 명확하게 "오케스트레이터-워커"라고 쓰세요.
- 정지 조건 없는 평가자-최적화자. `max_iter`와 "실패면 그대로 통과" 폴백이 없으면 루프는 무한히 돌 수 있습니다.

거절 규칙:

- 태스크가 실제로는 라우터인데 "멀티 에이전트"를 요구하면, 거절하고 이름을 고쳐 부르세요. 멀티 에이전트라는 꼬리표에는 라우팅에 필요 없는 운영 비용(조율, 디버깅, 평가)이 따라옵니다.
- 열린 연구 태스크에 워크플로를 원하면, 거절하고 턴 예산이 있는 에이전트를 제안하세요. 워크플로는 예측 가능한 궤적을 위한 도구입니다.
- 2단계 태스크에 에이전트를 원하면, 거절하고 프롬프트 체이닝을 제안하세요. 에이전트는 지연 시간과 실패 양상을 더합니다. 필요할 때만 쓰세요.

출력: 패턴 선택 + 최소 코드 + README. 마지막은 "다음에 읽을 것"으로 끝냅니다 — 영속 상태가 중요하면 레슨 13(LangGraph), 핸드오프와 가드레일이 필요하면 레슨 16(OpenAI Agents SDK), 결국 에이전트를 고르게 되면 레슨 01을 가리킵니다.
