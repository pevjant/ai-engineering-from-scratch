# 평가 기반 에이전트 개발

> Anthropic의 조언: "간단한 프롬프트로 시작하고, 포괄적인 평가로 최적화하며, 필요할 때만 다단계 에이전트 시스템을 추가하라." 평가는 마지막 단계가 아닙니다. 페이즈 14의 모든 다른 선택을 이끄는 바깥 루프입니다.

**유형:** Learn + Build(학습 + 구축)
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 14 전체.
**시간:** 약 60분

## 학습 목표

- 세 가지 평가 계층(정적 벤치마크, 커스텀 오프라인, 온라인 프로덕션)과 각각의 용도를 말할 수 있습니다.
- 평가자-최적화자 타이트 루프를 설명할 수 있습니다.
- 2026년 모범 사례를 설명할 수 있습니다. 평가는 코드 옆에 살고, CI에서 돌고, PR을 가둡니다(gate).
- 페이즈 14의 모든 레슨을 그것이 만들어 내는 평가 케이스와 연결할 수 있습니다.

## 문제 상황

에이전트는 데모를 통과합니다. 그리고 데모가 예측할 수 없는 방식으로 프로덕션에서 실패합니다. 벤치마크는 "이 모델이 폭넓게 유능한가?"에는 답하지만 "이 에이전트가 내 제품에 올바른 패치를 내고 있는가?"에는 답하지 않습니다. 해답: 세 계층의 평가가 끊임없이 돌고, 모든 가드레일과 학습된 규칙이 평가 케이스에 매핑되는 것입니다.

## 핵심 개념

### 세 가지 평가 계층

1. **정적 벤치마크** — 코드용 SWE-bench Verified(레슨 19), 브라우징/데스크톱용 WebArena/OSWorld(레슨 20), 범용 GAIA(레슨 19), 도구 사용 BFCL V4(레슨 06). 모델 간 비교과 레그레션 게이팅에 사용합니다. 오염(contamination)은 실재합니다. SWE-bench+는 32.67%의 풀이 유출을 발견했습니다. 항상 Verified / +-감사 점수를 함께 보고하세요.

2. **커스텀 오프라인 평가** — 여러분 제품의 형태에 맞춘 평가:
   - LLM-as-judge (Langfuse, Phoenix, Opik — 레슨 24).
   - 실행 기반(패치를 실행하고 테스트를 확인).
   - 궤적 기반(행동 시퀀스를 정답(gold)과 비교. OSWorld-Human은 최상위 에이전트가 정답보다 1.4~2.7배 많은 단계를 사용함을 보여 줍니다).

3. **온라인 평가** — 프로덕션:
   - 세션 리플레이(Langfuse).
   - 가드레일 트리거 알림(레슨 16, 21).
   - 단계별 비용/지연 시간 추적(레슨 23 OTel 스팬).

### 평가자-최적화자 (Anthropic)

타이트 루프:

1. 제안자가 출력을 생성합니다.
2. 평가자가 판정합니다.
3. 평가자가 통과할 때까지 다듬습니다.

이것은 셀프 리파인(레슨 05)을 일반화한 것입니다. 신뢰성이 필요한 어떤 에이전트 흐름이든 평가자-최적화자로 감쌀 수 있습니다.

### 2026년 모범 사례

- 평가는 코드 옆에 삽니다.
- 모든 PR에서 CI로 돌립니다.
- 평가 점수로 병합을 가둡니다(예: "main 대비 레그레션 5% 초과 금지").
- 모든 가드레일이 평가 케이스 하나에 매핑됩니다.
- 모든 학습된 규칙(Reflexion, pro-workflow learn-rule)이 실패 케이스 하나에 매핑됩니다.

### 페이즈 14 엮기

페이즈 14의 모든 레슨은 평가 케이스를 만들어 냅니다.

| 레슨 | 그것이 만들어 내는 평가 케이스 |
|--------|------------------------|
| 01 에이전트 루프 | 예산 소진, 무한 루프 가드 |
| 02 ReWOO | 도구 실패 시 플래너가 올바르게 재계획 |
| 03 Reflexion | 학습된 성찰이 재시도에서 적용 |
| 05 셀프 리파인/CRITIC | 판정자가 다듬어진 출력을 통과 판정 |
| 06 도구 사용 | 인수 강제 변환이 동작. 알 수 없는 도구는 거부 |
| 07-10 메모리 | 검색 인용이 출처와 일치. 오래된 사실은 무효화 |
| 12 워크플로 패턴 | 각 패턴이 올바른 출력을 산출 |
| 13 LangGraph | 재개 시 상태를 정확히 재현 |
| 14 AutoGen 액터 | DLQ가 죽은 핸들러를 잡아냄 |
| 16 OpenAI Agents SDK | 가드레일이 올바른 입력에서 발동 |
| 17 Claude Agent SDK | 서브에이전트 결과가 오케스트레이터로 반환 |
| 19-20 벤치마크 | SWE-bench Verified 점수, WebArena 성공률, OSWorld 효율성 |
| 21 컴퓨터 사용 | 단계별 안전 점검이 주입된 DOM을 잡아냄 |
| 23 OTel | 스팬이 필수 속성을 발행 |
| 26 실패 모드 | 감지기가 알려진 실패에 태그 |
| 27 프롬프트 인젝션 | PVE가 오염된 검색 결과를 거절 |
| 28 오케스트레이션 | 슈퍼바이저가 올바른 전문가에게 라우팅 |
| 29 런타임 형태 | DLQ가 N% 실패를 처리 |

평가 스위트에 각각의 케이스가 있다면 페이즈 14를 커버한 것입니다.

### 평가 기반 개발이 실패하는 지점

- **베이스라인 부재.** 마지막 정상 상태가 없는 평가는 읽을 수 없습니다. 베이스라인을 저장하세요.
- **근거 없는 LLM 판정.** 판정자도 환각합니다. CRITIC 패턴(레슨 05) — 판정자는 외부 도구에 근거를 둡니다.
- **평가에 과적합.** 평가만 노리는 최적화는 프로덕션 유용성과 어긋납니다. 케이스를 순환시키세요.
- **불안정한(flaky) 평가.** 비결정론적 케이스는 오탐을 냅니다. 시드를 고정하고 상태를 스냅샷하세요.

## 만들어 보기

`code/main.py`는 표준 라이브러리 기반 평가 하네스입니다.

- 카테고리별(벤치마크, 커스텀, 온라인) 케이스 레지스트리.
- 테스트 대상 스크립트화 에이전트.
- 평가자-최적화자 루프: 제안, 판정, 통과 또는 최대 라운드까지 다듬기.
- CI 게이트: 집계 통과율 + 베이스라인 대비 레그레션.

실행 방법:

```
python3 code/main.py
```

출력: 케이스별 통과/실패, 레그레션 플래그, CI 게이트 판정.

## 활용하기

- 평가 케이스를 에이전트 코드와 같은 저장소에 둡니다.
- 모든 PR에서 CI로 돌립니다.
- 레그레션이면 빌드를 실패시킵니다.
- 시간에 따른 통과율을 추적합니다.
- 모든 프로덕션 실패를 새 케이스에 묶습니다.

## 출시하기

`outputs/skill-eval-suite.md`는 CI 게이트와 레그레션 추적이 붙은 세 계층 평가 스위트를 에이전트 제품에 구축합니다.

## 연습 문제

1. 여러분의 프로덕션 실패 하나를 골라, 그것을 재현하는 평가 케이스를 작성해 보세요. 지금 에이전트가 그 케이스를 통과하나요?
2. 여러분의 도메인에 맞는 LLM 판정 루브릭을 세 차원(사실성, 어조, 범위)으로 작성해 보세요. 50개 세션을 채점해 보세요.
3. 평가 스위트를 CI에 연결해 보세요. 5% 이상 레그레션 시 빌드를 실패시킵니다.
4. 궤적 효율성 메트릭을 추가해 보세요. 에이전트가 정답 궤적 대비 몇 단계를 사용했나요?
5. 페이즈 14의 모든 레슨을 여러분의 스위트 평가 케이스에 매핑해 보세요. 빠진 것이 있나요? 그것이 메워야 할 구멍입니다.

## 핵심 용어

| 용어 | 사람들이 말하는 표현 | 실제 의미 |
|------|----------------|------------------------|
| 정적 벤치마크 | "기성품 평가" | SWE-bench, GAIA, AgentBench, WebArena, OSWorld |
| 커스텀 오프라인 평가 | "도메인 평가" | 제품 형태에 맞춘 LLM-as-judge / 실행 / 궤적 평가 |
| 온라인 평가 | "프로덕션 평가" | 세션 리플레이, 가드레일 알림, 비용/지연 시간 추적 |
| 평가자-최적화자 | "제안-판정-다듬기" | 판정자가 통과할 때까지 반복 |
| CI 게이트 | "병합 차단기" | 평가 레그레션 시 빌드 실패 |
| 베이스라인 | "마지막 정상 상태" | 레그레션 감지를 위한 기준 점수 |
| 궤적 효율성 | "정답 대비 단계 수" | 에이전트 단계 수를 인간 전문가 최소치로 나눈 값 |
