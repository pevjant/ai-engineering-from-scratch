# ReWOO와 Plan-and-Execute: 분리된 계획

> ReAct는 생각과 행동을 한 스트림에서 번갈아 배치합니다. ReWOO는 둘을 분리합니다. 큰 계획을 한 번에 다 세운 뒤 실행합니다. 토큰은 5배 줄고, HotpotQA 정확도는 +4% 올라가며, 플래너를 7B 모델로 증류할 수도 있습니다. Plan-and-Execute가 이 패턴을 일반화했고, Plan-and-Act가 웹 내비게이션으로 확장했습니다.

**유형:** Build
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 14 · 01 (에이전트 루프)
**시간:** ~60분

## 학습 목표

- ReWOO의 플래너/워커/솔버 분리가 ReAct의 엮인 루프보다 토큰을 아끼고 견고함을 높이는 이유를 설명합니다.
- 계획 DAG, 의존성 순서대로 도는 실행기, 워커 산출물을 합치는 솔버를 구현합니다 — 모두 표준 라이브러리로.
- 2026년 "다섯 가지 워크플로 패턴" 프레임(Anthropic)을 이용해 과제를 plan-then-execute로 돌릴지 엮인 ReAct로 돌릴지 결정합니다.
- 장기 지속형 웹·모바일 과제에 Plan-and-Act의 합성 계획 데이터가 필요한 때를 알아봅니다.

## 문제 상황

ReAct의 생각-행동-관찰 엮인 루프는 단순하고 유연하지만, 도구 호출 하나하나가 이전의 모든 맥락 — 모든 이전 생각을 포함해 — 을 실어 다녀야 합니다. 토큰 사용량은 깊이에 따라 제곱으로 불어납니다. 더 심한 것은: 루프 중간에 도구가 실패하면, 모델이 오류 관찰만으로 계획 전체를 다시 세워야 합니다.

ReWOO(Xu 등, arXiv:2305.18323, 2023년 5월)는 이 점을 짚고 한 가지 내기를 했습니다. 전체를 미리 계획하고, 증거는 병렬로 모으고, 답은 마지막에 조립합니다. 계획에 LLM 호출 한 번, 증거 수집에 도구 호출 N번(병렬 가능), 풀이에 LLM 호출 한 번. 유연함(계획이 정적임)을 내주고 토큰 효율과 명확한 실패 양상을 얻는 거래입니다.

## 개념

### 세 가지 역할

```
Planner:  user_question -> [plan_dag]
Workers:  [plan_dag]     -> [evidence]        (도구 호출, 병렬 가능)
Solver:   user_question, plan_dag, evidence -> final_answer
```

플래너는 DAG를 만들어 냅니다. 각 노드는 도구 이름, 인자, 그리고 어떤 이전 노드에 의존하는지(`#E1`, `#E2` 같은 참조)를 적습니다. 워커는 위상 정렬 순서대로 노드를 실행합니다. 솔버는 모든 것을 하나로 이어 붙입니다.

### 토큰이 5배 줄어드는 이유

ReAct는 프롬프트 길이가 단계 수에 따라 선형으로 자랍니다. 10번째 단계에서 프롬프트는 생각 1 + 행동 1 + 관찰 1 + 생각 2 + 행동 2 + 관찰 2, … 을 전부 담고 있습니다. 중간 단계마다 원래 프롬프트도 다시 중복해서 포함됩니다.

ReWOO는 플래너 프롬프트 한 번(큼), 작은 워커 프롬프트 N번(각각 도구 호출만, 체인 없음), 솔버 프롬프트 한 번을 지불합니다. 논문은 HotpotQA에서 토큰이 약 5배 줄면서 절대 정확도는 +4점 올랐다고 측정했습니다.

### 더 견고한 이유

ReAct에서 워커 3이 실패하면 루프가 도중에 오류만으로 추론을 이어가야 합니다. ReWOO에서는 워커 3이 오류 문자열을 반환하고, 솔버는 그것을 원래 계획과 함께 맥락에서 보며 우아하게 성능을 낮춰 갈 수 있습니다. 실패 지역화가 단계별이 아니라 노드별입니다.

### 플래너 증류

논문의 두 번째 결과: 플래너는 관찰을 보지 않기 때문에, 175B 교사의 플래너 출력으로 7B 모델을 파인튜닝할 수 있습니다. 작은 모델이 계획을 맡고, 추론에는 큰 모델이 필요 없습니다. 이제는 표준입니다 — 2026년 많은 프로덕션(운영 환경) 에이전트가 작은 플래너 + 큰 실행자(또는 그 반대)를 씁니다.

### Plan-and-Execute (2023)

LangChain 팀의 2023년 8월 글이 ReWOO를 패턴 이름으로 일반화했습니다: Plan-and-Execute. 미리 준비한 플래너가 단계 목록을 내놓고, 실행자가 각 단계를 돌리고, 선택적인 재계획기(replanner)가 결과를 관찰한 뒤 수정할 수 있습니다. 재계획기가 관찰을 계획에 다시 들이기 때문에 ReWOO보다는 ReAct에 가깝지만, 토큰 절약은 지킵니다.

### Plan-and-Act (Erdogan 등, arXiv:2503.09572, ICML 2025)

Plan-and-Act는 이 패턴을 장기 지속형 웹·모바일 에이전트로 확장합니다. 핵심 기여는 합성 계획 데이터입니다. 레이블이 붙은 궤적 생성기가 계획이 명시적으로 드러난 학습 데이터를 만들어 냅니다. 이걸로 플래너 모델을 파인튜닝하면, ReAct 궤적 하나는 결속력을 잃는 WebArena류 과제에서도 30~50단계를 넘어 계속 동작합니다.

### 언제 무엇을 고를까

| 패턴 | 언제 |
|---------|------|
| ReAct | 짧은 과제, 낯선 환경, 반응형 예외 처리 필요 |
| ReWOO | 도구가 알려진 구조적 과제, 토큰에 민감, 증거 병렬화 가능 |
| Plan-and-Execute | ReWOO 같지만 부분 실행 뒤 재계획 가능 |
| Plan-and-Act | 장기 지속형(30단계 초과), 웹/모바일/computer-use |
| Tree of Thoughts | 탐색 비용을 치를 가치가 있을 때 (레슨 04) |

Anthropic의 2024년 12월 가이드: 가장 단순한 것부터 시작하세요. 과제가 도구 호출 한 번에 요약 하나라면 ReWOO를 만들지 마세요. 과제가 40단계짜리 리서치라면 ReAct만으로 버티지 마세요.

## 만들어 보기

`code/main.py`는 장난감 ReWOO를 구현합니다:

- `Planner` — 프롬프트에서 계획 DAG를 내놓는 스크립트된 정책.
- `Worker` — 각 노드의 도구 호출을 레지스트리로 보내는 실행자.
- `Solver` — 증거를 읽고 최종 답을 만들어 내는 스크립트된 조립.
- 의존성 해석 — `#E1` 같은 참조가 이전 워커 출력으로 치환됩니다.

데모는 "프랑스 수도의 인구는 백만 단위로 반올림하면 얼마인가요?"라는 질문에 2단계 계획으로 답합니다: (1) 수도를 찾고, (2) 인구를 찾은 뒤 풉니다.

실행:

```
python3 code/main.py
```

트레이스는 전체 계획을 먼저 보여 주고, 그다음 워커 결과, 그다음 솔버 조립을 보여 줍니다. 토큰 수(대략의 문자 수를 출력합니다)를 ReAct식 엮인 실행과 비교해 보세요 — 이런 구조적 과제에서는 ReWOO가 이깁니다.

## 활용하기

LangGraph는 Plan-and-Execute를 레시피로 제공합니다(ReAct는 `create_react_agent`, plan-execute는 커스텀 그래프). CrewAI의 Flows는 이 패턴을 그대로 담습니다. 과제를 미리 정의하면 Flow DAG가 실행합니다. Plan-and-Act의 합성 데이터 접근은 아직 대부분 연구 단계이고, 런타임 패턴(명시적 계획 DAG)은 LangGraph와 CrewAI Flows를 통해 프로덕션에 들어가 있습니다.

## 출시하기

`outputs/skill-rewoo-planner.md`는 도구 카탈로그가 주어지면 사용자 요청에서 ReWOO 계획 DAG를 생성합니다. 실행자에 넘기기 전에 계획을 검증합니다(비순환, 모든 참조 해석됨, 모든 도구 존재).

## 연습 문제

1. 독립적인 계획 노드의 워커 실행을 병렬화해 보세요. 병렬 그룹 2개짜리 6노드 DAG에서 무엇을 얻나요?
2. 워커가 오류를 반환하면 발동하는 재계획 노드를 추가해 보세요. ReWOO를 Plan-and-Execute로 바꾸는 가장 작은 변화는 무엇일까요?
3. `Planner`를 작은 모델(7B급)로 바꾸고 `Solver`는 프론티어 모델에 두어 보세요. 엔드투엔드 품질을 비교해 보세요 — 이 분리는 어디에서 무너질까요?
4. ReWOO 논문 4절의 플래너 증류를 읽어 보세요. 175B → 7B 결과를 개념적으로 재현해 보세요. 어떤 학습 데이터가 필요하고, 계획 품질은 어떻게 채점할까요?
5. 장난감을 Plan-and-Act의 궤적 형태로 이식해 보세요. 계획이 DAG가 아니라 수열입니다. 어떤 트레이드오프가 바뀔까요?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| ReWOO | "Reasoning without observations" | 계획 세우고, 증거를 병렬로 모으고, 풀이 — 계획 프롬프트에는 관찰이 없음 |
| Plan-and-Execute | "LangChain의 plan-execute 패턴" | 실행 뒤 선택적 재계획 노드가 붙은 ReWOO |
| Plan-and-Act | "확장된 plan-execute" | 장기 지속형 과제를 위한 합성 계획 학습 데이터를 갖춘 명시적 플래너/실행자 분리 |
| 증거 참조(Evidence reference) | "#E1, #E2, ..." | 디스패치 시점에 이전 워커 출력으로 치환되는 계획 노드 자리표시자 |
| 플래너 증류(Planner distillation) | "작은 플래너, 큰 실행자" | 큰 교사의 플래너 트레이스로 작은 모델을 파인튜닝 |
| 토큰 효율(Token efficiency) | "왕복 횟수 절감" | 논문에서 HotpotQA 기준 ReAct 대비 토큰 5배 절감 |
| DAG 실행자(DAG executor) | "위상 정렬 디스패처" | 계획 노드를 의존성 순서로 실행, 각 층에서는 병렬 |
