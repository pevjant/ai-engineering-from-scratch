# 실패 모드: 에이전트가 왜 망가지는가

> MASFT(버클리, 2025)는 멀티 에이전트 실패 모드 14가지를 3개 카테고리로 분류했습니다. 마이크로소프트의 Taxonomy는 기존 AI 실패가 에이전트 환경에서 어떻게 증폭되는지 문서화합니다. 업계 현장 데이터는 다섯 가지 반복되는 모드로 수렴합니다. 환각된 행동, 범위 확장(scope creep), 연쇄 오류, 컨텍스트 손실, 도구 오용.

**유형:** Learn + Build(학습 + 구축)
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 14 · 05(셀프 리파인과 CRITIC), 페이즈 14 · 24(관측 가능성)
**시간:** 약 60분

## 학습 목표

- MASFT의 세 실패 카테고리와 각 카테고리의 구체적 모드 4가지 이상을 말할 수 있습니다.
- 에이전트 환경에서 기존 AI 실패 모드(편향, 환각)가 왜 증폭되는지 설명할 수 있습니다.
- 업계에서 반복되는 다섯 가지 모드와 그 완화 방법을 설명할 수 있습니다.
- 에이전트 트레이스에 실패 모드 레이블을 붙이는 표준 라이브러리 기반 감지기를 구현할 수 있습니다.

## 문제 상황

팀들은 트레이스의 90%에서 동작하는 에이전트를 출시합니다. 남은 10%의 실패는 무작위 잡음이 아닙니다. 몇 가지 반복되는 범주로 뭉쳐 있습니다. 이름을 붙일 수 있게 되면, 모니터링하고 고칠 수도 있습니다.

## 핵심 개념

### MASFT (버클리, arXiv:2503.13657)

멀티 에이전트 시스템 실패 분류 체계입니다. 14가지 실패 모드를 3개 카테고리로 묶었습니다. 평가자 간 코헨 카파(Cohen's Kappa)가 0.88로, 카테고리들이 신뢰할 수 있게 구분됩니다.

핵심 주장: 실패는 더 나은 베이스 모델로 고칠 수 있는 LLM 한계가 아니라, 멀티 에이전트 시스템의 근본적인 설계 결함이라는 것입니다.

### Microsoft Taxonomy of Failure Mode in Agentic AI Systems

- 기존 AI 실패(편향, 환각, 데이터 유출)는 에이전트 환경에서 증폭됩니다.
- 자율성에서 새로운 실패가 생겨납니다. 대규모 의도치 않은 행동, 도구 오용, 임무 이탈.
- 이 백서는 에이전트 제품의 위험 등록부입니다.

### Characterizing Faults in Agentic AI (arXiv:2603.06847)

- 실패는 오케스트레이션, 내부 상태 변화, 환경 상호작용에서 발생합니다.
- 단순히 "나쁜 코드"나 "나쁜 모델 출력"만이 아닙니다.

### LLM 에이전트 환각 조사 (arXiv:2509.18970)

두 가지 주요 양상:

1. **지시 이탈(Instruction-following Deviation)** — 에이전트가 시스템 프롬프트를 따르지 않음.
2. **장거리 컨텍스트 오용(Long-range Contextual Misuse)** — 에이전트가 이전 턴의 컨텍스트를 잊거나 잘못 적용함.

하위 의도(sub-intention) 오류: 생략(단계 누락), 중복(단계 반복), 순서 뒤바뀜(단계 순서 오류).

### 업계에서 반복되는 다섯 가지 모드

Arize, Galileo, NimbleBrain의 2024-2026 현장 분석이 수렴한 결론:

1. **환각된 행동.** 존재하지 않는 도구를 호출하거나 인수를 지어냅니다.
2. **범위 확장(scope creep).** 사용자가 요청한 것 이상으로 과제를 키웁니다(없는 PR을 만들고, 없는 이메일을 보냄).
3. **연쇄 오류.** 잘못된 호출 하나가 하류 효과를 촉발합니다. 존재하지 않는 SKU 환각이 네 번의 API 호출을 일으켜 다중 시스템 장애로 번집니다.
4. **컨텍스트 손실.** 장기 과제에서 초반 턴의 제약을 잊어버립니다.
5. **도구 오용.** 올바른 도구를 잘못된 인수로 호출하거나, 아예 잘못된 도구를 호출합니다.

연쇄 오류가 가장 위험합니다. 에이전트는 "내가 실패했다"와 "과제가 불가능하다"를 구분하지 못하고, 루프를 닫으려고 400 오류 위에서 성공 메시지를 환각으로 만들어 내곤 합니다.

### 완화: 매 단계의 게이트

추론 체인의 매 단계마다 자동 검증 게이트를 두어, 환경 상태와 비교해 사실 근거를 확인합니다. 구체적으로:

- 단계별 안전 분류기(레슨 21).
- 도구 호출 인수 검증(레슨 06).
- 검색된 콘텐츠를 알려진 사실과 교차 검증(레슨 05, CRITIC).
- 상태를 다시 조회해 성공 환각 감지(파일이 실제로 만들어졌나?).

### 실패 모니터링이 잘못되기 쉬운 지점

- **크래시만 태깅.** 에이전트 실패 대부분은 멀쩡해 보이는 출력을 냅니다. 콘텐츠 수준 검사가 필요합니다.
- **베이스라인 부재.** 드리프트 감지에는 마지막 정상 상태(last-known-good)가 필요합니다. 없으면 "나빠지고 있다"고 말할 수 없습니다.
- **알림 과잉.** 실패마다 호출이 울립니다. 묶어서 비율 제한을 두세요.

## 만들어 보기

`code/main.py`는 표준 라이브러리 기반 실패 모드 태거를 구현합니다.

- 다섯 가지 모드를 모두 담은 합성 트레이스 데이터셋.
- 모드별 감지 함수(도구 호출, 출력, 반복 행동에 대한 시그니처 패턴).
- 각 트레이스에 레이블을 붙이고 모드 분포를 보고하는 태거.

실행 방법:

```
python3 code/main.py
```

출력: 트레이스별 레이블 + 집계 분포. Phoenix의 트레이스 클러스터링이 드러내 주는 것을 값싸게 재현한 셈입니다.

`outputs/skill-failure-detector.md`는 여러분의 도메인에 맞춘 실패 모드 감지기를 만들어 트레이스 저장소에 연결합니다.

## 연습 문제

1. "성공 환각" 감지기를 추가해 보세요. 에이전트가 성공을 반환하지만 대상 상태는 그대로인 경우입니다.
2. 만든 제품의 실제 트레이스 100개에 태그를 붙여 보세요. 어떤 모드가 지배적이었나요? 고치는 데 드는 비용은?
3. "연쇄 반경(cascade radius)" 메트릭을 구현해 보세요. N단계에서 실패가 발생했을 때 하류 몇 단계에 영향을 줬는지 측정합니다.
4. MASFT의 14가지 실패 모드를 읽고, 여러분의 제품에 해당하는 세 가지를 골라 감지기를 작성해 보세요.
5. 감지기 하나를 CI 작업에 연결해 보세요. 트레이스의 5% 이상이 어떤 모드로 태깅되면 빌드가 실패하도록 합니다.
