과제 유형(예상 소요 시간, 단계 수, 트리거 종류, 지연 시간 예산)이 주어지면 런타임 형태를 고릅니다.

의사결정:

1. 30초 미만, 사용자가 대기 -> **요청-응답**.
2. 점진적 UX 또는 음성 -> **스트리밍**.
3. 수 분~수 시간, 사용자가 대기하지 않음 -> **큐 기반**.
4. 외부 이벤트에 반응 -> **이벤트 기반**.
5. 주기적 하우스키핑 -> **크론**.
6. 위 중 하나인데 재시작 비용이 크다 -> **내구성 있는 실행**을 추가합니다.

산출물:

1. 여러분의 스택에서 해당 형태의 뼈대.
2. 관측 가능성: OTel GenAI 스팬(레슨 23), 연결된 백엔드(레슨 24).
3. 큐의 경우: DLQ + 재시도 정책 + 큐 깊이 메트릭.
4. 이벤트의 경우: 명시적 구독자 레지스트리 + 리플레이 경로.
5. 크론의 경우: 실행 겹침을 막는 잠금 파일 또는 분산 잠금.
6. 내구성 있는 실행의 경우: 체크포인터 백엔드 + 재개 의미론.

하드 리젝(무조건 거절):

- 5분짜리 과제에 동기 HTTP. 사용자는 끊고, 워커는 쌓입니다.
- DLQ 없는 큐 기반. 실패한 작업이 증발합니다.
- 트레이스 내보내기 없는 백그라운드 작업. 사용자가 불평할 때까지 실패가 보이지 않습니다.
- "내구성 있는 상태는 없고, 그냥 재시도하겠습니다." 장기 과제는 반드시 체크포인트를 찍어야 합니다.

거절 규칙:

- 제품에 SLA + 리플레이 요구가 있으면 스웜 토폴로지 + 비내구성 런타임을 거절합니다.
- 과제가 컴플라이언스 구속을 받는다면 감사 추적 없는 이벤트 기반을 거절합니다.
- 크론 + 잠금 없음을 원하면 거절합니다. 겹치는 크론 실행은 최선의 경우 중복 작업, 최악의 경우 데이터 손상입니다.

출력: 런타임 뼈대 + 관측 가능성 훅 + SLA, 재시도 정책, 체크포인터 선택이 담긴 README. 마지막에는 "다음에 읽을 것"으로 레슨 23(OTel), 레슨 24(관측 가능성), 또는 호스팅 장기 실행은 레슨 17(Managed Agents)을 가리킵니다.
