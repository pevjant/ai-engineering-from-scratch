# 프로덕션 런타임: 큐, 이벤트, 크론

> 프로덕션 에이전트는 여섯 가지 런타임 형태로 동작합니다. 요청-응답, 스트리밍, 내구성 있는 실행(durable execution), 큐 기반 백그라운드, 이벤트 기반, 예약 실행. 프레임워크를 고르기 전에 형태를 고르세요. 어떤 형태에서든 관측 가능성은 구조를 떠받치는 기둥입니다.

**유형:** Learn(학습)
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 14 · 13(LangGraph), 페이즈 14 · 22(음성)
**시간:** 약 60분

## 학습 목표

- 여섯 가지 프로덕션 런타임 형태를 말하고, 각각을 프레임워크/제품 패턴에 대응시킬 수 있습니다.
- 장기 과제에서 내구성 있는 실행(LangGraph)이 왜 중요한지 설명할 수 있습니다.
- 이벤트 기반 런타임과 Claude Managed Agents가 맞는 시점을 설명할 수 있습니다.
- 다중 단계 에이전트에서 "관측 가능성이 곧 기둥"이라는 주장을 설명할 수 있습니다.

## 문제 상황

프로덕션 에이전트는 주피터 노트북에서는 드러나지 않는 방식으로 실패합니다. 37단계에서 네트워크 타임아웃, 음성 통화 도중 사용자 전화 끊기, 기계 재부팅으로 크론 작업 죽음, 백그라운드 워커 메모리 고갈. 런타임 형태가 어떤 실패를 견딜 수 있는지 결정합니다.

## 핵심 개념

### 요청-응답

- 동기 HTTP. 사용자가 완료를 기다립니다.
- 짧은 과제(30초 미만)에서만 사용할 수 있습니다.
- 스택: Agno(Python + FastAPI), Mastra(TypeScript + Express/Hono/Fastify/Koa).
- 관측 가능성: 표준 HTTP 접근 로그 + OTel 스팬.

### 스트리밍

- 점진적 출력을 위한 SSE 또는 WebSocket.
- LiveKit은 이것을 WebRTC로 확장해 음성/비디오를 지원합니다(레슨 22).
- 스택: 스트리밍을 지원하는 아무 프레임워크 + SSE/WS를 다루는 프런트엔드.
- 관측 가능성: 청크별 타이밍, 첫 토큰 지연 시간, 꼬리 지연 시간.

### 내구성 있는 실행(durable execution)

- 매 단계마다 상태를 체크포인트로 저장하고, 실패 시 자동으로 재개합니다.
- AutoGen v0.4 액터 모델은 실패를 하나의 에이전트로 고립시킵니다(레슨 14).
- LangGraph의 핵심 차별점입니다(레슨 13).
- 단계 수를 알 수 없고 복구 비용이 클 때 필수입니다.

### 큐 기반 / 백그라운드

- 작업이 큐에 들어가고, 워커가 꺼내 처리하며, 결과는 웹훅이나 pub/sub으로 돌아옵니다.
- 장기 에이전트에 필수입니다(Anthropic 컴퓨터 사용 발표 기준 과제당 수십~수백 단계).
- 스택: Celery(Python), BullMQ(Node), SQS + Lambda(AWS), 커스텀.
- 관측 가능성: 큐 깊이, 작업별 지연 시간 분포, DLQ 크기.

### 이벤트 기반

- 에이전트가 트리거를 구독합니다. 새 이메일, PR 오픈, 크론 발화.
- Claude Managed Agents가 이를 기본 제공합니다(레슨 17).
- CrewAI Flows(레슨 15)는 이벤트 기반 결정론적 워크플로를 구조화합니다.
- 관측 가능성: 트리거 원천, 이벤트→시작 지연 시간, 에이전트 지연 시간.

### 예약 실행

- 주기적으로 도는 크론 형태의 에이전트입니다.
- 내구성 있는 실행과 결합하면, 실패한 야간 작업이 다음 틱에 재개됩니다.
- 스택: Kubernetes CronJob + 내구성 프레임워크, 호스티드(Render cron, Vercel cron).

### 2026년 배포 패턴

- 이벤트 기반 프로덕션에는 **CrewAI Flows**.
- Python 마이크로서비스에는 **Agno**의 스테이트리스 FastAPI.
- 임베딩에는 **Mastra** 서버 어댑터(Express, Hono, Fastify, Koa).
- 관리형 음성에는 **Pipecat Cloud / LiveKit Cloud** (레슨 22).
- 호스팅된 장기 비동기에는 **Claude Managed Agents**.

### 관측 가능성은 곧 기둥

OpenTelemetry GenAI 스팬(레슨 23)과 Langfuse/Phoenix/Opik 백엔드(레슨 24)가 없다면, 40단계에서 실패한 다중 단계 에이전트를 디버깅할 수 없습니다. 프로덕션에서는 선택 사항이 아닙니다. "우리는 빨리 디버깅한다"와 "로깅을 더 붙여 처음부터 재생한다"의 차이입니다.

### 프로덕션 런타임이 실패하는 지점

- **잘못된 형태 선택.** 5분짜리 과제에 요청-응답을 선택. 사용자는 끊고, 워커는 쌓이고, 재시도는 겹칩니다.
- **DLQ 부재.** 데드레터 큐 없는 큐 워커. 실패한 작업이 증발합니다.
- **불투명한 백그라운드 작업.** 트레이스 내보내기 없이 도는 백그라운드 에이전트. 사용자가 불평할 때까지 실패는 보이지 않습니다.
- **내구성 있는 상태 생략.** 재시작을 감당할 수 없는 30초 초과 실행이라면 내구성 있는 실행이 필요합니다.

## 만들어 보기

`code/main.py`는 표준 라이브러리 기반 다중 형태 데모입니다.

- 요청-응답 엔드포인트(평범한 함수).
- 스트리밍 핸들러(제너레이터).
- DLQ가 있는 큐 기반 워커.
- 이벤트 트리거 레지스트리.
- 크론 형태 스케줄러.

실행 방법:

```bash
python3 code/main.py
```

출력: 같은 과제에 대해 각 형태의 동작을 보여 주는 다섯 개의 트레이스. 같은 에이전트 로직, 다른 바깥 껍데기. 여섯 번째 형태인 내구성 있는 실행은 의도적으로 레슨 13에서 LangGraph 체크포인팅으로 다룹니다.

## 활용하기

- **요청-응답** — 채팅 스타일 UX.
- **스트리밍** — 점진적 응답.
- **내구성 있는 실행** — 장기 과제.
- **큐** — 배치 / 비동기 / 장기 실행.
- **이벤트** — 에이전트의 반응성.
- **크론** — 하우스키핑(메모리 통합, 평가, 비용 보고).

2. 큐 기반 데모에 DLQ를 추가해 보세요. 10% 작업 실패를 시뮬레이션하고 DLQ 크기를 드러내 보세요.

4. 백프레셔가 있는 스트리밍을 구현해 보세요. 클라이언트가 느리면 에이전트를 일시정지합니다. 이것이 턴 예산과 어떻게 상호작용하나요?

## 핵심 용어

| 용어 | 사람들이 말하는 표현 | 실제 의미 |
|------|----------------|------------------------|
| 요청-응답 | "동기식" | 사용자가 대기. 짧은 과제만 가능 |
| 스트리밍 | "SSE / WS" | 점진적 출력. 더 나은 UX. 청크별 지연 시간 관측 가능 |
| 내구성 있는 실행 | "실패 지점에서 재개" | 체크포인트로 저장된 상태. 마지막 단계에서 재시작 |
| 큐 기반 | "백그라운드 작업" | 생산자 / 워커 풀 / DLQ |
| 이벤트 기반 | "트리거 기반" | 에이전트가 외부 이벤트에 반응 |
| DLQ | "데드레터 큐" | 실패한 작업의 주차장 |
| Claude Managed Agents | "호스티드 하네스" | Anthropic이 호스팅하는 캐싱 + 압축이 붙은 장기 비동기 |
