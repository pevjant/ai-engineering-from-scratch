# 에이전트 관측 가능성: Langfuse, Phoenix, Opik

> 2026년에는 오픈 소스 에이전트 관측 가능성(옵저버빌리티) 플랫폼 세 개가 시장을 주도합니다. Langfuse(MIT) — 월 600만 회 이상 설치, 트레이싱 + 프롬프트 관리 + 평가 + 세션 리플레이. Arize Phoenix(Elastic 2.0) — 에이전트 특화 평가와 RAG 관련성, OpenInference 자동 계측. Comet Opik(Apache 2.0) — 자동 프롬프트 최적화, 가드레일, LLM 판정 기반 환각 감지.

**유형:** Learn(학습)
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 14 · 23(OTel GenAI)
**시간:** 약 45분

## 학습 목표

- 상위 오픈 소스 에이전트 관측 가능성 플랫폼 세 개와 각 라이선스를 말할 수 있습니다.
- 각 플랫폼이 가장 강한 영역을 구분할 수 있습니다. Langfuse(프롬프트 관리 + 세션), Phoenix(RAG + 자동 계측), Opik(최적화 + 가드레일).
- 2026년까지 89%의 조직이 에이전트 관측 가능성을 갖췄다고 보고하는 이유를 설명할 수 있습니다.
- LLM 판정(LLM-judge) 평가가 붙은 표준 라이브러리 기반 트레이스→대시보드 파이프라인을 구현할 수 있습니다.

## 문제 상황

OTel GenAI(레슨 23)는 스키마를 제공할 뿐입니다. 스팬을 수집하고, 평가를 돌리고, 프롬프트 버전을 저장하고, 성능 하락(레그레션)을 드러내 주는 플랫폼은 따로 필요합니다. 경쟁하는 세 플랫폼은 각자 생명주기의 다른 부분을 강조합니다.

## 핵심 개념

### Langfuse (MIT)

- 월 600만 회 이상의 SDK 설치, GitHub 스타 19k 이상.
- 기능: 트레이싱, 버전 관리 + 플레이그라운드가 있는 프롬프트 관리, 평가(LLM-as-judge, 사용자 피드백, 커스텀), 세션 리플레이.
- 2025년 6월: 이전까지 상용 모듈이었던 기능들(LLM-as-a-judge, 어노테이션 큐, 프롬프트 실험, Playground)이 MIT 라이선스로 오픈 소스화되었습니다.
- 가장 강한 영역: 프롬프트 관리 루프와 긴밀히 맞물린 엔드투엔드 관측 가능성.

### Arize Phoenix (Elastic License 2.0)

- 더 깊은 에이전트 특화 평가를 제공합니다. 트레이스 클러스터링, 이상 감지, RAG 검색 관련성.
- OpenInference 자동 계측을 네이티브하게 지원합니다.
- 프로덕션에서는 관리형인 Arize AX와 함께 씁니다.
- 프롬프트 버전 관리는 없으며, 더 넓은 플랫폼과 나란히 쓰는 드리프트/행동 레그레션 도구로 포지셔닝되어 있습니다.
- 가장 강한 영역: RAG 관련성, 행동 드리프트, 이상 감지.

### Comet Opik (Apache 2.0)

- A/B 실험을 통한 자동 프롬프트 최적화.
- 가드레일(PII 마스킹, 주제 제약).
- LLM 판정 기반 환각 감지.
- Comet 자체 측정 벤치마크: Opik의 로그 + 평가는 23.44초, Langfuse는 327.15초(약 14배 차이) — 벤더 벤치마크는 방향성 참고로만 받아들이세요.
- 가장 강한 영역: 최적화 루프, 자동화된 실험, 가드레일 강제.

### 업계 데이터

Maxim(2026년 현장 분석) 기준: 조직의 89%가 에이전트 관측 가능성을 갖추고 있으며, 품질 문제가 최대 프로덕션 장벽입니다(응답자의 32%가 이를 꼽음).

### 고르기

| 필요 사항 | 선택 |
|------|------|
| 프롬프트 관리가 포함된 올인원 | Langfuse |
| 깊은 RAG 평가 + 드리프트 | Phoenix |
| 자동 최적화 + 가드레일 | Opik |
| 개방적 라이선스, ELv2 회피 | Langfuse(MIT) 또는 Opik(Apache 2.0) |
| Datadog / New Relic 연동 | 아무거나 — 모두 OTel을 내보냅니다 |

### 이 패턴이 잘못되기 쉬운 지점

- **평가 전략이 없음.** 평가 없는 트레이싱은 그저 비싼 로깅일 뿐입니다.
- **근거 없는 자체 제작 LLM 판정.** CRITIC 패턴(레슨 05)이 적용됩니다. 판정자도 사실 검증을 위해 외부 도구가 필요합니다.
- **트레이스와 묶이지 않은 프롬프트 버전.** 프로덕션에서 성능이 떨어져도 원인이 된 프롬프트를 좁혀 찾을 수 없습니다.

## 만들어 보기

`code/main.py`는 표준 라이브러리 기반 트레이스 수집기 + LLM 판정 평가기를 구현합니다.

- GenAI 형태의 스팬을 수집합니다.
- 세션별로 묶고, 실패한 실행에 태그를 붙입니다(가드레일 발동, 신뢰도 낮은 평가).
- 루브릭으로 에이전트 응답을 채점하는 스크립트화된 LLM 판정자.
- 대시보드 비슷한 요약을 출력합니다. 실패율, 상위 실패 원인, 평가 점수 분포.

실행 방법:

```
python3 code/main.py
```

출력: Langfuse/Phoenix/Opik이 보여 줄 것과 같은 세션별 평가 점수와 실패 분류.

## 연습 문제

1. 일주일 치 OTel 트레이스를 Langfuse 클라우드(무료 티어)로 내보내 보세요. 어떤 세션이 실패했나요? 이유는 무엇인가요?
2. 여러분의 도메인에 맞는 LLM 판정 루브릭을 작성해 보세요(사실 정확성, 어조, 범위 준수). 50개 트레이스로 시험해 보세요.
3. Langfuse의 프롬프트 버전 관리와 Phoenix의 트레이스 클러스터링을 비교해 보세요. 무엇이 무너졌는지 더 빨리 알려 주는 쪽은 어디인가요?
4. Opik의 가드레일 문서를 읽고, 에이전트 실행 하나에 PII 마스킹 가드레일을 연결해 보세요.
5. 여러분의 코퍼스로 세 플랫폼의 벤치마크를 측정해 보세요. 벤더가 발표한 수치는 무시하고 직접 재 보세요.
