# 하이브리드 메모리: 벡터 + 그래프 + KV

> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [en.md](en.md)

> 하이브리드 메모리는 세 개의 저장소를 병렬로 운영합니다 — 의미 유사도에는 벡터, 빠른 사실 조회에는 KV, 엔티티 관계 추론에는 그래프를 쓰고, 검색 시점에 이 셋을 하나로 합치는(퓨전) 스코어링 레이어가 붙습니다. 외부 메모리에서 널리 쓰이는 프로덕션(운영 환경) 패턴이며, Mem0(Chhikara 외, 2025)이 대표적인 참조 구현 중 하나입니다.

**유형:** 빌드
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 14 · 07 (MemGPT), 페이즈 14 · 08 (Letta Blocks)
**시간:** 약 75분

## 학습 목표

- 에이전트 메모리에 저장소 하나(벡터만, 그래프만, KV만)로는 왜 부족한지 설명할 수 있습니다.
- Mem0의 세 가지 병렬 저장소가 각각 무엇을 최적화하는지 말할 수 있습니다.
- Mem0의 퓨전 스코어링(관련성, 중요도, 최신성)과, 이것이 위계 구조가 아니라 가중치 합인 이유를 설명할 수 있습니다.
- 세 저장소 모두에 기록하는 `add()`와 결과를 퓨전하는 `search()`를 갖춘, 연습용 삼중 저장소 메모리를 표준 라이브러리로 구현합니다.

## 문제

저장소 하나만 쓰면 세 가지 질의 유형 가운데 하나는 엉터리로 답하게 됩니다:

- **의미 유사도** — "지난주에 에이전트 드리프트에 대해 뭐라고 이야기했죠?" 여기서는 벡터가 이깁니다. KV와 그래프는 놓칩니다.
- **사실 조회** — "사용자 전화번호가 뭐죠?" KV가 이깁니다. 벡터는 낭비고, 그래프는 과한 접근입니다.
- **관계 추론** — "같은 청구 엔티티를 공유하는 고객은 누구죠?" 그래프가 이깁니다. 벡터와 KV는 답할 수 없습니다.

프로덕션 에이전트는 한 세션 안에서 이 세 가지 질의를 모두 던집니다. 저장소 하나짜리 메모리는 그중 두 가지에서 항상 틀립니다. Mem0의 기여는 이 셋을 하나의 `add`/`search` 인터페이스 뒤에 연결하고, 결과를 합치는 스코어링 함수를 얹은 것입니다.

## 개념

### 병렬로 동작하는 세 저장소

Mem0(arXiv:2504.19413, 2025년 4월)에서 `add(text, user_id, metadata)`를 호출하면:

1. 텍스트에서 후보 사실을 추출합니다(LLM이 수행하는 단계입니다).
2. 각 사실을 벡터 저장소에 임베딩으로 기록해 의미 검색에 씁니다.
3. 각 사실을 (user_id, fact_type, entity) 키로 KV 저장소에 기록해 O(1) 조회를 가능하게 합니다.
4. 각 사실을 타입이 있는 엣지 형태로 그래프 저장소(Mem0g)에 기록해 관계 질의에 대응합니다.

`search(query, user_id)`를 호출하면:

1. 벡터 저장소가 임베딩 코사인 기준 상위 k개를 돌려줍니다.
2. KV 저장소가 질의에서 뽑아낸 (user_id, type, entity) 키로 정확히 일치하는 항목을 돌려줍니다.
3. 그래프 저장소가 질의 엔티티에서 도달 가능한 서브그래프를 돌려줍니다.
4. 스코어링 레이어가 이 셋을 하나로 합칩니다.

### 퓨전 스코어링

```
score = w_relevance * relevance(q, record)
      + w_importance * importance(record)
      + w_recency * recency(record)
```

- **관련성** — 벡터 코사인, KV 정확 일치, 그래프 경로 가중치.
- **중요도** — 기록 시점에 태그로 붙이거나 학습으로 얻습니다(이름, ID, 정책처럼 더 중요한 사실이 있습니다).
- **최신성** — 마지막 쓰기 또는 읽기 이후 경과 시간에 따라 지수적으로 감쇠합니다.

가중치는 제품별로 튜닝합니다. 채팅 에이전트는 `w_recency`를 높이고, 컴플라이언스(규정 준수) 에이전트는 `w_importance`를, 검색 에이전트는 `w_relevance`를 높입니다.

### Mem0g와 시간 추론

Mem0g에는 충돌 감지기가 더해져 있습니다. 새 사실이 기존 엣지와 모순되면 기존 엣지를 삭제하지 않고 무효 표시만 합니다. 시점을 묻는 질의("3월에 사용자가 어느 도시에 살았죠?")는 '그 시점에 유효한' 서브그래프를 따라 탐색합니다.

이것이 바로 Letta의 무효화(invalidation) 패턴을 일반화한, 컴플라이언스 등급의 동작입니다.

### 벤치마크 수치

Mem0 논문(2025)이 보고하는 수치입니다:

- **LoCoMo**(긴 대화 메모리): 91.6
- **LongMemEval**(장기 에피소드 메모리): 93.4
- **BEAM 1M**(백만 토큰 메모리 벤치마크): 64.1

비교 베이스라인(128k 전체 컨텍스트 LLM, 평면 벡터 저장소, 평면 KV)은 모두 10점 이상 차이로 집니다. 선택을 정당화하는 것은 어디까지나 운영 형태이지 벤치마크 점수만은 아닙니다 — 그래도 이 수치는 퓨전 설계가 무시할 수준의 차이가 아니라는 걸 보여줍니다.

### 스코프 분류

Mem0은 메모리를 스코프별로 나눕니다:

- **사용자 메모리** — 세션을 넘어 유지되며 `user_id`로 키가 잡힙니다.
- **세션 메모리** — 하나의 스레드 안에서 유지됩니다.
- **에이전트 메모리** — 에이전트 인스턴스별 상태입니다.

모든 쓰기는 스코프를 하나씩 지정합니다. 검색은 스코프별 가중치를 두고 여러 스코프에 걸쳐 질의할 수도 있습니다. 스코프를 아무 생각 없이 섞으면 "어시스턴트가 Bob의 프로젝트 이야기를 Alice에게 해줬다"는 사고가 터집니다.

### 이 패턴이 잘못되는 지점

- **임베딩 드리프트.** 처음 백 번쯤의 질의에선 멀쩡해 보이던 벡터 결과가 코퍼스가 커질수록 나빠집니다. 자주 쓰이는 상위 N개 레코드를 주기적으로 다시 임베딩하세요.
- **KV 스키마 비대화.** `(user_id, type, entity)`는 모든 팀이 제각기 자기들만의 `type`을 추가하기 전까지는 단순해 보입니다. 타입 집합을 분기마다 점검하세요.
- **그래프 폭발.** 엉터리 추출기 하나가 메시지당 엣지 50개를 추가합니다. `add` 호출마다 그래프 쓰기에 상한을 두고, 확신도 낮은 엣지는 버리세요.

## 직접 만들기

`code/main.py`가 삼중 저장소 패턴을 표준 라이브러리만으로 구현합니다:

- `VectorStore` — 임베딩 대용품으로 쓰는 순진한 토큰 겹침 유사도.
- `KVStore` — `(user_id, fact_type, entity)`를 키로 쓰는 딕셔너리.
- `GraphStore` — 타입이 있는 엣지(subject, relation, object, valid).
- `Mem0` — `add()`, `search()`, 퓨전 스코어링, 스코프 인식 검색을 갖춘 최상위 파사드.
- 여러 사용자, 여러 세션이 얽힌 대화에 대한 실제 동작 추적 예시.

실행 방법:

```
python3 code/main.py
```

출력에는 세 개의 개별 검색 경로와 퓨전된 상위 k개가 함께 나옵니다. `main()` 위쪽의 스코어링 가중치를 바꿔 보면 순위가 달라지는 걸 확인할 수 있습니다.

## 활용하기

- **Mem0 (Apache 2.0)** — 프로덕션에서 쓸 수 있는 수준입니다. Postgres + Qdrant + Neo4j로 직접 호스팅하거나 매니지드 클라우드를 쓰세요.
- **Letta** — core/recall/archival 삼층 구조입니다. 벡터·그래프 백엔드는 직접 골라 붙일 수 있습니다.
- **Zep** — 시간축 지식 그래프(temporal KG)와 사실 추출을 갖춘 상용 대안입니다.
- **자체 구현** — 추출기를 정밀하게 통제해야 하거나(컴플라이언스), 퓨전 가중치를 직접 다뤄야 할 때(최신성이 지배적인 음성 에이전트) 선택합니다.

## 연습 문제

1. 장난감 벡터 유사도를 실제 임베딩 모델(sentence-transformers, Ollama, OpenAI embeddings)로 바꿔 보세요. 합성으로 만든 긴 대화에서 recall@10을 측정합니다. 1000번 쓰고 나면 순위가 흐트러지나요?
2. 시간 질의를 추가하세요: `search(query, as_of=timestamp)`. 그 시점 또는 그 이전에 유효한 레코드만 돌려줍니다. 어느 저장소가 가장 많이 손봐야 할까요?
3. 충돌 감지기를 구현하세요. 들어온 사실이 그래프 엣지와 모순되면 기존 엣지를 무효화하고 양쪽 모두 로그로 남깁니다. "사용자는 베를린에 산다" → "사용자는 리스본에 산다"로 테스트해 보세요.
4. 퓨전 스코어러에 `user_feedback` 차원(검색된 레코드에 좋아요 누르기)을 추가하세요. 게임화(에이전트가 자기가 이미 좋아한 레코드만 돌려주는 것)는 어떻게 막을 수 있을까요?
5. Mem0 문서(`docs.mem0.ai`)를 읽어 보세요. 연습용 구현을 `mem0` 클라이언트 호출로 옮기고, 같은 20개 테스트 질의에서 검색 품질을 비교해 보세요.

## 핵심 용어

| 용어 | 사람들이 말하는 표현 | 실제 의미 |
|------|----------------|------------------------|
| 하이브리드 메모리 | "벡터에 그래프에 KV" | 세 저장소에 병렬로 쓰고, 검색 때 퓨전 |
| 사실 추출 | "메모리 수집(ingestion)" | 텍스트를 (엔티티, 관계, 사실) 튜플로 쪼개는 LLM 단계 |
| 퓨전 스코어링 | "관련성 랭킹" | 관련성, 중요도, 최신성의 가중치 합 |
| 스코프 | "메모리 네임스페이스" | user / session / agent — 누가 무엇을 볼지 결정 |
| Mem0g | "메모리 그래프" | 관계 질의를 위한, 시간에 따른 유효성이 있는 타입 엣지 |
| 시간 무효화 | "소프트 삭제" | 모순된 엣지는 무효 표시만 하고 절대 삭제하지 않음 |
| 임베딩 드리프트 | "검색 부패" | 코퍼스가 커질수록 벡터 품질이 떨어짐. 주기적으로 재임베딩 |
