> 🇰🇷 이 문서는 한국어 번역본입니다(ELI5 스타일). 원문: [skill-orchestration-picker.md](skill-orchestration-picker.md)

제품 도메인과 과제 유형이 주어지면 최소한의 토폴로지를 고릅니다.

의사결정:

1. 에이전트 1개 + 워크플로 패턴(레슨 12)으로 충분한가? -> 토폴로지를 아예 쓰지 않습니다.
2. 뚜렷한 책임을 가진 전문가가 2~4명인가? -> **슈퍼바이저-워커**.
3. 지연 시간이 핵심이고 전문가들이 깔끔하게 핸드오프할 수 있는가? -> **스웜**.
4. 전문가 10명 이상, 슈퍼바이저 컨텍스트 예산이 부족한가? -> **계층형**.
5. 비용보다 정확도가 중요하고, 다중 제안자 + 비판이 도움이 되는가? -> **토론** (레슨 25).

산출물:

1. 선택된 토폴로지의 뼈대.
2. 스웜에는 홉 카운터, 계층형에는 중첩 깊이 제한, 토론에는 라운드 상한.
3. 핸드오프별 또는 단계별 관측 가능성 훅(OTel GenAI 스팬, 레슨 23).
4. "왜 이것이고 저것이 아닌가" README 섹션.

하드 리젝(무조건 거절):

- LLM 호출 3번을 직렬로 돌리며 "멀티 에이전트"라 부르는 경우. 그것은 프롬프트 체인입니다.
- 홉 카운터 없는 스웜. 튕김은 필연적으로 일어납니다.
- 분기당 전문가 1명에서 끝나는 계층형. 평탄화하세요.

거절 규칙:

- 단일 ReAct 루프가 처리하는 과제에 멀티 에이전트를 원하면 거절하고 레슨 01을 제안합니다.
- 2단계 과제에 슈퍼바이저를 원하면 거절하고 프롬프트 체이닝(레슨 12)을 제안합니다.
- 도메인에 컴플라이언스/감사 요구가 있으면 스웜을 거절하고 슈퍼바이저 또는 계층형을 제안합니다.

출력: 토폴로지 뼈대 + 의사결정 근거가 담긴 README. 마지막에는 "다음에 읽을 것"으로, 슈퍼바이저 구현은 레슨 13(LangGraph), 도구로서의 핸드오프는 레슨 16(OpenAI Agents SDK), 토론 세부 사항은 레슨 25를 가리킵니다.
