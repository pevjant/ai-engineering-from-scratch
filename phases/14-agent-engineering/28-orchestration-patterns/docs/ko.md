# 오케스트레이션 패턴: 슈퍼바이저, 스웜, 계층형

> 2026년 프레임워크 전반에서 네 가지 오케스트레이션 패턴이 반복됩니다. 슈퍼바이저-워커, 스웜/피어투피어, 계층형, 토론. Anthropic의 조언: "요구에 맞는 올바른 시스템을 만드는 것이 중요합니다." 단순하게 시작하세요. 단일 에이전트 + 다섯 워크플로 패턴으로 부족할 때만 토폴로지를 더합니다.

**유형:** Learn + Build(학습 + 구축)
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 14 · 12(워크플로 패턴), 페이즈 14 · 25(멀티 에이전트 토론)
**시간:** 약 60분

## 학습 목표

- 반복되는 네 가지 오케스트레이션 패턴과 각각이 맞는 상황을 말할 수 있습니다.
- 2026년 LangChain 권고 사항을 설명할 수 있습니다. 슈퍼바이저 라이브러리 대신 도구 호출 기반 감독.
- Anthropic의 "올바른 시스템 만들기" 규칙과 이것이 토폴로지 선택을 어떻게 가두는지 설명할 수 있습니다.
- 공통 스크립트화 LLM을 상대로 네 패턴 모두를 표준 라이브러리로 구현할 수 있습니다.

## 문제 상황

팀들은 필요해지기도 전에 "멀티 에이전트"에 손을 뻗습니다. 프레임워크 전반에는 네 가지 패턴이 반복됩니다. 이름을 붙일 수 있게 되면 올바른 하나를 고를 수 있고, 토폴로지를 아예 건너뛸 수도 있습니다.

## 핵심 개념

### 슈퍼바이저-워커

- 중앙 라우팅 LLM이 전문가 에이전트들에게 작업을 나눠 줍니다.
- 결정하는 것: 자기 자신으로 루프백, 전문가에게 핸드오프, 종료.
- 전문가들은 서로 대화하지 않으며, 모든 라우팅은 슈퍼바이저를 거칩니다.

프레임워크: LangGraph `create_supervisor`, Anthropic 오케스트레이터-워커, CrewAI 하이어라키컬 프로세스.

**2026년 LangChain 권고:** `create_supervisor` 대신 직접 도구 호출로 감독을 구현하세요. 더 세밀한 컨텍스트 엔지니어링 제어가 가능합니다. 각 전문가가 무엇을 보게 할지 정확히 결정할 수 있습니다.

### 스웜 / 피어투피어

- 에이전트들이 공유 도구 표면을 통해 직접 핸드오프합니다.
- 중앙 라우터가 없습니다.
- 슈퍼바이저보다 지연 시간이 짧습니다(홉 수 감소).
- 추론하기는 더 어렵습니다(단일 통제 지점이 없음).

프레임워크: LangGraph 스웜 토폴로지, OpenAI Agents SDK 핸드오프(모든 에이전트가 모두에게 핸드오프할 수 있을 때).

### 계층형

- 슈퍼바이저들이 하위 슈퍼바이저를 관리하고, 하위 슈퍼바이저들이 워커를 관리합니다.
- LangGraph에서는 중첩 서브그래프로, CrewAI에서는 중첩 크루로 구현합니다.
- 운영 복잡성을 치르면서 대규모 에이전트 군집으로 확장합니다.

필요한 시점: 단일 슈퍼바이저의 컨텍스트 예산이 모든 전문가의 설명을 담지 못할 때.

### 토론

- 병렬 제안자 + 반복 교차 비판(레슨 25).
- 엄밀히는 오케스트레이션이라기보다 검증에 가깝지만, 프레임워크에서는 토폴로지 선택지로 나타납니다.

### 자율 크루 vs 결정론적 플로

CrewAI는 두 가지 배포 모드를 공식화했습니다.

- **Flow** — 결정론적 이벤트 기반 자동화(프로덕션의 권장 출발점).
- **Crew** — 자율적인 역할 기반 협업.

이것은 위 네 패턴과 직교하지만 토폴로지에 대응됩니다. Flow는 보통 슈퍼바이저 또는 계층형이고, Crew는 보통 LLM 라우터가 있는 슈퍼바이저입니다.

### Anthropic의 조언

"LLM 분야의 성공은 가장 정교한 시스템을 만드는 것이 아닙니다. 요구에 맞는 올바른 시스템을 만드는 것입니다."

의사결정 순서:

1. 단일 에이전트 + 워크플로 패턴(레슨 12) — 여기서 시작합니다.
2. 슈퍼바이저-워커 — 전문가가 2~4명일 때.
3. 스웜 — 추론 명확성보다 지연 시간이 중요할 때.
4. 계층형 — 슈퍼바이저 컨텍스트 예산이 부족할 때만.
5. 토론 — 비용보다 정확도가 중요할 때.

### 이 패턴이 잘못되기 쉬운 지점

- **토폴로지 우선 사고.** 멀티 에이전트가 무슨 문제를 푸는지 파악하기도 전에 "멀티 에이전트가 필요하다"고 말합니다.
- **스웜에서 핸드오프 튕기기.** A -> B -> A -> B. 홉 카운터를 사용하세요.
- **가짜 계층.** "엔터프라이즈니까" 세 층을 만들지만 실제 팀은 두 개. 접어 버리세요.

## 만들어 보기

`code/main.py`는 스크립트화된 LLM을 상대로 네 패턴 모두를 표준 라이브러리로 구현합니다.

- `Supervisor` — 중앙 라우터.
- `Swarm` — 직접 핸드오프하는 피어투피어.
- `Hierarchical` — 슈퍼바이저를 거느린 슈퍼바이저.
- `Debate` — 병렬 제안자 + 비판.

각 패턴은 같은 세 의도 과제(환불 / 버그 / 영업)를 처리합니다. 트레이스 모양은 각자 다릅니다.

실행 방법:

```
python3 code/main.py
```

출력: 패턴별 트레이스 + 연산 수. 슈퍼바이저가 가장 깔끔하고, 스웜이 가장 짧고, 계층형이 가장 깊고, 토론이 가장 비쌉니다.

## 활용하기

- **LangGraph** — 슈퍼바이저와 계층형(중첩 서브그래프).
- **OpenAI Agents SDK** — 도구로서의 핸드오프(슈퍼바이저 형태).
- **CrewAI Flow** — 프로덕션용 결정론적 자동화.
- **커스텀** — 토론이 필요하거나 정확한 제어를 원할 때.

## 연습 문제

1. 라우터를 제거해 슈퍼바이저-워커를 스웜으로 바꿔 보세요. 무엇이 무너지나요? 무엇이 나아지나요?
2. 스웜에 홉 카운터를 추가해 보세요. 3번 핸드오프 후 거절합니다. A->B->A 튕김을 잡아 내나요?
3. 전문가 12명 도메인을 위한 두 층 계층형 시스템을 만들어 보세요. 중첩이 없으면 컨텍스트 예산은 어디서 무너지나요?
4. 프로덕션 형태의 워크로드로 네 패턴의 성능을 측정해 보세요. 어떤 지표(지연 시간, 비용, 정확도, 디버깅 용이성)에서 무엇이 이기나요?
5. Anthropic의 "Building Effective Agents" 글을 읽고, 여러분의 프로덕션 플로 각각을 네 패턴 중 하나에 대응시켜 보세요. 깔끔히 대응되지 않는 것이 있나요?

## 핵심 용어

| 용어 | 사람들이 말하는 표현 | 실제 의미 |
|------|----------------|------------------------|
| 슈퍼바이저-워커 | "라우터 + 전문가" | 중앙 LLM이 전문가에게 배분. 전문가들은 서로 대화하지 않음 |
| 스웜 | "피어투피어" | 공유 도구를 통한 직접 핸드오프. 중앙 라우터 없음 |
| 계층형 | "슈퍼바이저의 슈퍼바이저" | 대규모 군집을 위한 중첩 서브그래프 |
| 토론 | "제안자 + 비판" | 병렬 제안자, 교차 비판(레슨 25) |
| 도구 호출 기반 감독 | "라이브러리 없는 슈퍼바이저" | 컨텍스트 제어를 위해 슈퍼바이저를 직접 도구 호출로 구현 |
| Crew | "자율 팀" | CrewAI의 역할 기반 협업 모드 |
| Flow | "결정론적 워크플로" | CrewAI의 이벤트 기반 프로덕션 모드 |
