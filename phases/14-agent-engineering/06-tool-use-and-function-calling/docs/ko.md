# 도구 사용과 함수 호출

> Toolformer(Schick 등, 2023)가 자기 지도 도구 주석을 시작했습니다. Berkeley Function Calling Leaderboard V4(Patil 등, 2025)가 2026년의 기준을 제시합니다. 에이전틱 40%, 멀티 턴 30%, 라이브 10%, 논라이브 10%, 환각 10%. 단일 턴은 해결됐습니다. 메모리, 동적 의사결정, 장기 지속형 도구 체인은 아직 아닙니다.

**유형:** Build
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 14 · 01 (에이전트 루프), 페이즈 13 · 01 (함수 호출 심화)
**시간:** ~60분

## 학습 목표

- Toolformer의 자기 지도 학습 신호를 설명합니다. 실행 결과가 다음 토큰 손실을 줄여 줄 때만 도구 주석을 유지한다는 것.
- BFCL V4의 다섯 평가 범주와 각각이 무엇을 측정하는지 말합니다.
- 스키마 검증, 인자 강제 변환, 실행 샌드박싱을 갖춘 표준 라이브러리 기반 도구 레지스트리를 구현합니다.
- 2026년의 세 가지 미해결 문제를 진단합니다. 장기 지속형 도구 체이닝, 동적 의사결정, 메모리.

## 문제 상황

초기 도구 사용의 질문은 이랬습니다. 모델이 올바른 함수 호출을 예측할 수 있을까? 현대 도구 사용의 질문은 이렇습니다. 모델이 40단계에 걸쳐 도구를 이어 쓸 수 있을까? 메모리와 부분 관측을 갖추고, 도구 실패에서 복구하면서, 존재하지 않는 도구를 환각하지 않고?

Toolformer가 기준선을 세웠습니다. 모델은 자기 지도만으로 언제 도구를 호출할지 배울 수 있습니다. BFCL V4가 2026년의 평가 목표를 정의합니다. 이 둘 사이의 간격이 바로 프로덕션(운영 환경) 에이전트가 살아가는 공간입니다.

## 개념

### Toolformer (Schick 등, NeurIPS 2023)

아이디어: 모델이 스스로 사전학습 코퍼스에 후보 API 호출을 주석 달게 합니다. 각 후보를 실행해 봅니다. 도구 결과를 포함했을 때 다음 토큰에 대한 손실이 줄어들 때만 주석을 유지합니다. 걸러진 코퍼스로 파인튜닝합니다.

다룬 도구: 계산기, QA 시스템, 검색 엔진, 번역기, 캘린더. 자기 지도 신호는 오직 "도구가 텍스트 예측에 도움이 되는가"에 관한 것입니다 — 사람 레이블 없이.

규모 결과: 도구 사용은 규모에서 자연스럽게 나타납니다. 작은 모델은 도구 주석 때문에 오히려 나빠지고, 큰 모델은 이득을 봅니다. 그래서 2026년 프론티어 모델에는 강한 도구 사용이 기본 내장되어 있는 반면, 대부분의 7B 모델은 믿음직하게 쓰려면 명시적인 도구 사용 파인튜닝이 필요합니다.

### Berkeley Function Calling Leaderboard V4 (Patil 등, ICML 2025)

BFCL은 2026년의 사실상 표준 평가입니다. V4의 구성:

- **에이전틱(Agentic, 40%)** — 완전한 에이전트 궤적: 메모리, 멀티 턴, 동적 의사결정.
- **멀티 턴(Multi-Turn, 30%)** — 도구 체인이 있는 대화형 대화.
- **라이브(Live, 10%)** — 사용자가 제출한 실제 프롬프트(더 어려운 분포).
- **논라이브(Non-Live, 10%)** — 합성 테스트 케이스.
- **환각(Hallucination, 10%)** — 어떤 도구도 호출하지 말아야 할 때를 탐지.

V3가 상태 기반 평가를 도입했습니다. 도구 시퀀스 후에 도구 호출의 AST를 대조하는 게 아니라 API의 실제 상태를 검사합니다(예: "파일이 생성됐는가?"). V4는 웹 검색, 메모리, 형식 민감도 범주를 추가했습니다.

2026년의 핵심 발견: 단일 턴 함수 호출은 거의 해결됐습니다. 실패는 여기에 몰려 있습니다. 턴 사이 맥락을 나르는 메모리, 이전 결과를 보고 도구를 고르는 동적 의사결정, 20단계를 넘으면 흐트러지는 장기 체인, 맞는 도구가 없을 때 호출을 거부하는 환각 탐지.

### 도구 스키마

모든 프로바이더에는 스키마가 있습니다. 디테일은 달라도 형태는 같습니다:

```
name: string
description: string (무엇을 하는지, 언제 쓰는지)
input_schema: JSON Schema (properties, required, types, enums)
```

Anthropic은 `input_schema`를 그대로 씁니다. OpenAI는 `function.parameters`를 씁니다. 둘 다 JSON Schema를 받습니다. 설명이 빠지면 안 되는 기둥입니다 — 모델은 설명을 읽고 맞는 도구를 고릅니다. 엉터리 도구 설명은 "엉뚱한 도구가 선택된" 실패의 1위 근본 원인입니다.

### 인자 검증

어떤 도구 호출도 믿지 마세요. 검증하세요:

1. **타입 강제 변환.** 스키마가 int인데 모델이 문자열 "5"를 반환할 수 있습니다. 모호하지 않으면 변환하고, 모호하면 거부합니다.
2. **열거값 검증.** 스키마가 `status in {"open", "closed"}`라 했는데 모델이 `"in_progress"`를 내놓으면, 설명이 붙은 오류로 거부합니다.
3. **필수 필드.** 필수 필드 누락 → 크래시가 아니라 즉시 오류 관찰을 모델에게 돌려보냅니다.
4. **형식 검증.** 날짜, 이메일, URL — 정규식이 아니라 구체적인 파서로 검증합니다.

모든 검증 실패는 구조화된 관찰로 돌아가야 모델이 올바른 형태로 재시도할 수 있습니다.

### 병렬 도구 호출

최신 프로바이더는 어시스턴트 턴 하나 안에서 병렬 도구 호출을 지원합니다. 루프:

1. 모델이 서로 다른 `tool_use_id`를 가진 도구 호출 3개를 내보냅니다.
2. 런타임이 실행합니다(독립적이면 병렬로).
3. 각 결과는 `tool_use_id`로 연결된 `tool_result` 블록으로 돌아갑니다.

엔지니어링 규칙: 상관관계 ID를 빠지면 안 되는 기둥으로 취급하세요. ID가 뒤바뀌면 "엉뚱한 결과가 엉뚱한 도구로" 라우팅됩니다.

### 샌드박싱

도구 실행이 바로 샌드박스 경계입니다. 자세한 것은 레슨 09를 보세요. 요약하면: 모든 도구는 읽기·쓰기 표면, 네트워크 접근, 타임아웃, 메모리 상한을 명시해야 합니다. 만능의 `run_shell(cmd)`은 위험 신호고, 구체적인 `git_status()`가 더 안전합니다.


## 만들어 보기

`code/main.py`는 프로덕션 형태의 도구 레지스트리를 구현합니다:

- JSON Schema 부분집합 검증기(표준 라이브러리만 사용).
- 설명, 입력 스키마, 타임아웃, 실행기를 갖춘 도구 등록.
- 인자 강제 변환과 열거값 검증.
- 상관관계 ID가 붙은 병렬 도구 디스패치.
- 구조화된 문자열로서의 오류 관찰.

실행:

```
python3 code/main.py
```

트레이스는 미니 에이전트가 한 턴에서 도구 세 개를 호출하는 모습을 보여 줍니다. 그중 하나는 일부러 잘못된 형식의 호출로, 모델이 행동에 옮길 수 있는 설명이 붙은 오류로 거부됩니다.

## 활용하기

모든 프로바이더는 자기 도구 스키마를 갖고 있습니다 — Anthropic, OpenAI, Gemini, Bedrock. 멀티 프로바이더가 필요하면 번역 계층(OpenAI Agents SDK, Vercel AI SDK, LangChain 도구 어댑터)을 쓰세요. BFCL이 참조 벤치마크입니다 — 도구 사용이 제품의 핵심이라면 출시 전에 여러분의 에이전트로 실행해 보세요.

## 출시하기

`outputs/skill-tool-registry.md`는 주어진 과제 도메인에 대해 도구 카탈로그, 스키마, 레지스트리를 생성합니다. 설명 품질 검사(각 도구의 설명이 모델에게 언제 쓰는지 알려 주는가?)를 포함합니다.

## 연습 문제

1. 모델이 다른 도구 사용을 명시적으로 거부할 수 있게 해 주는 "no-op" 도구를 추가해 보세요. BFCL류 환각 테스트로 측정해 보세요.
2. int-문자열과 float-문자열 강제 변환을 구현해 보세요. 어디서부터 강제 변환이 진짜 버그를 가리기 시작할까요?
3. 도구별 타임아웃과 서킷 브레이커(연속 3회 실패 시 60초간 그 도구 거부)를 추가해 보세요. 모델의 복구 방식에는 어떤 변화가 생길까요?
4. BFCL V4 설명을 읽어 보세요. 한 범주(예: "멀티 턴")를 골라 10개 예시 프롬프트를 여러분의 에이전트로 돌려 보세요. 통과율을 보고하세요.
5. 표준 라이브러리 검증기를 Pydantic이나 Zod로 이식해 보세요. Pydantic/Zod가 잡아 낸 것 중 장난감이 놓친 것은 무엇이었나요?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| 함수 호출(Function calling) | "도구 사용" | 검증된 스키마를 갖춘 구조화 출력 도구 호출 |
| Toolformer | "자기 지도 도구 주석" | Schick 2023 — 결과가 다음 토큰 손실을 줄이는 도구 호출만 유지 |
| BFCL | "Berkeley Function Calling Leaderboard" | 2026 벤치마크: 에이전틱 40%, 멀티 턴 30%, 라이브 10%, 논라이브 10%, 환각 10% |
| 도구 스키마(Tool schema) | "모델을 위한 함수 시그니처" | name, description, 인자의 JSON Schema |
| tool_use_id | "상관관계 ID" | 도구 호출을 그 결과와 묶음, 병렬 디스패치에 필수 |
| 환각 탐지(Hallucination detection) | "호출하지 말아야 할 때를 앎" | V4 범주: 맞는 도구가 없으면 호출을 거부 |
| 인자 강제 변환(Argument coercion) | "문자열을 정수로 수선" | 예측 가능한 스키마 불일치의 좁은 수정, 모호하면 거부 |
| 샌드박싱(Sandboxing) | "도구 실행 경계" | 도구별 읽기·쓰기 표면, 네트워크, 타임아웃, 메모리 상한 |
