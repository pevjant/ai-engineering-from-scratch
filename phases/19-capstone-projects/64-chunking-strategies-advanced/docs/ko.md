# 청킹 전략, 비교

> 청킹이 검색기가 무엇을 끌어올 수 있는지의 상한선을 정합니다. 경계를 잘못 자르면 어떤 임베딩 모델, 어떤 리랭커, 어떤 LLM도 다운스트림에서 그 피해를 복구할 수 없습니다.

**유형:** Build
**언어:** Python
**선수 지식:** 페이즈 11 레슨 04(임베딩), 06(RAG), 07(고급 RAG); 페이즈 19 트랙 B 기초(레슨 20-29)
**시간:** ~90분

## 학습 목표
- 고정 창(fixed-window), 문장, 재귀 분할(recursive-split), 의미 클러스터링, 구조적 마크다운 헤더 다섯 가지 청킹 전략을 직접 구현합니다.
- 정답 스팬에 골드 레이블을 단 고정 코퍼스에서 recall@k를 측정하고, 산문(prose)에서 이기는 전략과 기술 문서에서 이기는 전략이 왜 다른지 설명합니다.
- 청크 길이 분포를 읽고 각 전략이 주입하는 실패 모드 — 고아 문장, 기호 중간 절단, 헤더 전용 청크, 의미 표류 — 를 알아봅니다.
- 벤치마크를 돌리지 않고도 문서 유형, 평균 문단 길이, 포맷이 명시적 구조를 갖는지라는 세 가지 속성만 보고 새 코퍼스의 기본 전략을 고릅니다.

## 문제

모든 RAG 파이프라인은 원본 문서를 임베딩 모델이 담을 만큼 작고, 각 조각이 하나의 온전한 생각을 담을 만큼 큰 조각으로 자르는 일에서 시작합니다. 어디를 자를지 선택은 하이퍼파라미터가 아닙니다. 검색기가 돌려줄 수 있는 것의 상한선입니다.

"예산 중단 임계값이 어떻게 되어 있지?"라는 질의는 중단 임계값을 담은 청크에 도달할 수 있을 때만 성공합니다. 고정 창 분할기가 임계값 값을 주변 맥락에서 잘라 냈다면, 임베딩은 다른 클러스터로 밀려나고, BM25 점수는 떨어지고, 리랭커는 잡음만 보고, LLM이 만드는 답은 틀립니다. 2024년 논문 "LongRAG: Enhancing Retrieval-Augmented Generation with Long-context LLMs"는 청킹 선택만으로 검색 리콜이 35퍼센트나 절대적으로 흔들린다는 것을 측정했습니다. 2025년의 맥락적 청크 헤더(contextual chunk headers) 후속 연구는 격차를 좁혔지만 닫지는 못했습니다.

이 레슨은 다섯 전략을 나란히 만들고, 골드 레이블 스팬을 가진 고정 코퍼스에 대고 돌려서, 리콜 숫자를 직접 읽게 해 줍니다.

### 고정 창

무식하지만 성실한 베이스라인입니다. N자마다 자릅니다. 원한다면 겹침(overlap)을 줘서 위치 N에서 잘린 문장이 위치 N - overlap에서 시작하는 청크 안에 온전히 들어가게 할 수 있습니다. 빠르고, 결정론적이고, 경계 처리는 끔찍합니다. 기본값이 아니라 대조군으로 쓰세요.

### 문장

정규식이나 간단한 상태 기계로 문장 경계에서 자릅니다. 문장 하나 이상을 목표 문자 예산까지 청크에 담습니다. 단어 중간 자르기는 멈춥니다. 하지만 문단 중간과 섹션 중간 자르기는 그대로입니다. 초기 RAG 파이프라인 다수의 기본값이었고, 다른 구조가 없는 산문에는 합리적인 선택입니다.

### 재귀 분할

2023년대 라이브러리들이 유행시킨 계층 전략입니다. 가장 강한 분리자(이중 줄바꿈, 문단)부터 시도하고, 그다음(단일 줄바꿈), 그다음 문장, 마지막 문자로 내려갑니다. 청크가 예산에 맞으면 재귀가 멈춥니다. 지역마다 적응하기 때문에 구조가 일관치 않은 문서에서 강합니다.

### 의미 클러스터링

모든 문장을 임베딩합니다. 주제 중심점(centroid)을 공유하는 연속 문장들을 묶습니다. 중심점과의 누적 유사도가 임계값 아래로 떨어지면 자릅니다. 경계가 문자 수가 아니라 의미를 반영합니다. 만들기가 더 느리고 임베딩 모델에 의존하지만, 문단 한가운데서 주제를 바꾸는 문서에도 잘 버팁니다.

### 구조적 마크다운 헤더

명시적 구조를 갖는 문서(마크다운, reStructuredText, RFC 스타일 번호 매기기 섹션)는 헤딩 경계에서 자릅니다. 각 청크는 헤딩 + 같은 수준 이상의 다음 헤딩 직전까지의 내용이 됩니다. 주제당 청크가 가장 작지만, 코퍼스가 잘 짜여 있어야만 쓸 수 있습니다.

### recall@k가 경계 선택을 재는 방법

골드 레이블 질의는 원본 문서 안에서 정답 스팬의 정확한 문자 오프셋을 갖고 있습니다. 청킹 후 여러분은 묻습니다: 검색기가 돌려준 상위 k개 청크 중 하나라도 골드 스팬과 겹치는가? 그렇다면 그 질의의 recall@k는 1입니다. 아니라면 0입니다. 질의 집합 전체에서 평균을 냅니다. 같은 평가를 전략마다 돌리면, 그 스프레드가 여러분이 가진 코퍼스에서 어느 경계 정책이 살아남는지 보여 줍니다.

## 만들어 보기

`code/main.py`는 다음을 구현합니다:

- `fixed_window(text, size, overlap)` - 베이스라인.
- `sentence_chunks(text, target)` - 간단한 문장 패커.
- `recursive_split(text, separators, target)` - 계층적 재귀.
- `semantic_chunks(text, similarity_threshold)` - 결정론적 목 임베딩 위의 중심점 기반 클러스터링.
- `structural_markdown(text)` - 헤더 인식 분할기.
- `mock_embed(text, dim)` - 루프가 오프라인에서 돌도록 하는 해시 기반 임베딩.
- `DenseIndex` - 페이즈 19 트랙 B의 하이브리드 검색 레슨이 쓴 것과 같은 모양.
- `eval_recall(strategy, corpus, queries, k)` - 비교 루프.
- 고정 코퍼스의 모든 전략을 돌리고 recall@k 테이블을 출력하는 `main()`.

실행:

```bash
python3 code/main.py
```

출력은 전략당 한 행, k마다 한 열을 가진 작은 테이블입니다. 문장 분할은 구조화된 고정 코퍼스에서 집니다. 구조적 마크다운은 마크다운 고정 코퍼스에서 이깁니다. 재귀 분할은 재귀가 적응하기 때문에 혼합 고정 코퍼스에서 제 몫을 해 냅니다. 의미 클러스터링은 유용한 구조 단서가 없는 산문 고정 코퍼스에서 이깁니다.

## 테이블이 숨겨 주지 못하는 실패 모드

**고아 문장.** 문장 패킹이 주제 문장을 놓친 청크를 만듭니다. 임베딩이 잘못된 클러스터를 가리킵니다.

**기호 중간 절단.** 코드나 YAML 안에서의 고정 창은 식별자를 반으로 자릅니다. 두 반쪽은 잡음으로 임베딩됩니다.

**헤더 전용 청크.** 구조적 마크다운은 `## Title`만 담은 청크를 내놓을 수 있습니다. 걸러내거나 다음 청크의 첫 문단을 붙이세요.

**의미 표류.** 코퍼스가 일관되게 한 주제라면 의미 클러스터링이 잘 자르지 못합니다. 5000자짜리 청크는 구체적인 답변 여럿을 하나의 흐릿한 임베딩에 욱여 넣습니다. 의미 방식에 하드 문자 상한을 결합하세요.

**낡은 임베딩.** 의미 클러스터링은 임베딩 모델을 씁니다. 모델을 바꾸면 청크도 함께 바뀝니다. 청크 모델을 검색 모델과 별도로 고정(pin)하거나, 인덱스를 통째로 다시 만드세요.

## 벤치마크 없이 기본값 고르기

세 가지 속성이 새 코퍼스의 기본 청커를 결정합니다.

| 속성 | 값 | 기본값 |
|----------|-------|---------|
| 문서 유형 | 구조 없는 산문 | 재귀 분할, 목표 800 |
| 문서 유형 | 마크다운 / RFC / API 문서 | 구조적 마크다운 |
| 문서 유형 | 코드 | AST 인식 (범위 밖; 페이즈 19 레슨 02 참고) |
| 문단 길이 | 길고 단일 주제 | 문장, 목표 500 |
| 문단 길이 | 짧고 주제 혼합 | 의미, 임계값 0.6 |

자신이 없으면 재귀 분할을 고르세요. 단일 전략 베이스라인 중 가장 강합니다.

## 활용하기

프로덕션 패턴:

- 새 파이프라인을 출시하기 전에 평가를 돌리세요. 라이브러리 기본 전략을 믿지 마세요.
- 임베딩 모델이나 코퍼스 구성을 바꿀 때마다 평가를 다시 돌리세요. 승자는 코퍼스에 따라 달라집니다.
- 각 청크의 메타데이터에 전략 이름을 저장해서, 나중에 성능 하락의 원인을 귀속할 수 있게 하세요.

레슨 69의 트랙 F 엔드투엔드 RAG 시스템은 여기서 고른 청커를 1단계로 씁니다. 레슨 68의 평가 하니스는 이 레슨의 `eval_recall`이 돌려주는 것과 같은 모양에서 recall@k를 읽습니다. 여러분 코퍼스에서 이기는 전략을 골라 다음 단계로 넘기세요.

## 연습 문제

1. 여섯 번째 전략을 추가합니다: 문자 수 대신 `tiktoken`으로 세는 토큰 창. 같은 고정 코퍼스에서 고정 창과 비교하세요.
2. 산문 고정 코퍼스에 30퍼센트 비율로 코드 블록을 섞습니다. 테이블을 다시 돌리고, 구조적 마크다운을 제외한 모든 전략이 리콜을 잃는 이유를 설명하세요.
3. 결정론적 임베딩을 여러분 프로젝트의 실제 제공자(provider) 임베딩으로 바꿉니다. 의미 클러스터링의 리콜 델타를 측정하고, 전략 간 스프레드가 벌어지는지 좁아지는지 보고하세요.
4. 청크마다 `summary` 필드를 추가합니다: 한 문장짜리 중심점 설명입니다. 청크 본문 뒤에 요약을 붙여 평가를 다시 돌리고, 리콜 상승폭을 측정하세요.

## 핵심 용어

| 용어 | 사람들의 표현 | 실제 의미 |
|------|-----------------|------------------------|
| Recall@k | "맞는 청크를 찾았나?" | 상위 k개 청크 중 하나라도 골드 답변 스팬과 겹치는 질의의 비율 |
| 청크 겹침 | "슬라이딩 윈도우" | 이전 청크의 마지막 N자를 다음 청크에 다시 포함 |
| 구조적 분할기 | "헤더 인식 청크" | H1/H2/H3 경계에서 자름; 헤딩 텍스트가 청크의 일부 |
| 의미 청커 | "주제 인식 청크" | 문장을 임베딩하고, 중심점 유사도로 묶고, 표류 시 자름 |
| 중심점 표류 | "주제 전환" | 누적 평균과 다음 문장 사이의 코사인 유사도가 임계값 아래로 떨어짐 |
