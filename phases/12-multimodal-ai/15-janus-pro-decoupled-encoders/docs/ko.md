# Janus-Pro: 통합 멀티모달 모델을 위한 분리형 인코더

> 통합 멀티모달 모델에는 피할 수 없는 긴장이 있습니다. 이해(understanding)는 의미적 특성을 원합니다 — 개념 수준의 정보가 풍부한 SigLIP이나 DINOv2의 출력 벡터처럼요. 생성(generation)은 재구성에 유리한 코드를 원합니다 — 다시 선명한 픽셀로 조립될 수 있는 VQ 토큰처럼요. 이 두 목표는 하나의 인코더에서는 양립할 수 없습니다. Janus(DeepSeek, 2024년 10월)와 Janus-Pro(DeepSeek, 2025년 1월)는 해결책을 이렇게 제시합니다: 애초에 하나로 묶으려는 시도를 멈추고, 두 인코더를 분리하라는 것입니다. 트랜스포머 본체는 두 작업이 공유하되, 이해는 SigLIP으로, 생성은 VQ 토크나이저로 우회시키는 방식입니다. 7B 크기의 Janus-Pro는 GenEval에서 DALL-E 3를 이기면서도 MMMU에서는 LLaVA에 필적합니다. 이 레슨에서는 인코더 하나로는 실패하는 일을 왜 두 개면 해결되는지 읽어 봅니다.

**유형:** 빌드
**언어:** Python (표준 라이브러리, 듀얼 인코더 라우팅 + 공유 본체 시그널)
**선수 지식:** Phase 12 · 13 (Transfusion), Phase 12 · 14 (Show-o)
**소요 시간:** ~120분

## 학습 목표

- 인코더를 하나만 공유하면 이해 또는 생성 품질 중 하나가 타협될 수밖에 없는 이유를 설명할 수 있다.
- Janus-Pro의 라우팅 방식을 설명할 수 있다: 이해에는 입력 쪽에서 SigLIP 특성을, 생성에는 입력과 출력 양쪽에서 VQ 토큰을 사용한다.
- Janus가 실패한 지점에서 Janus-Pro가 성공하게 만든 데이터 믹스 스케일링을 추적할 수 있다.
- 분리형(Janus-Pro), 결합형-연속(Transfusion), 결합형-이산(Show-o) 아키텍처를 비교할 수 있다.

## 문제 상황

통합 모델은 이해와 생성에서 하나의 트랜스포머 본체를 공유합니다. 그동안의 시도(Chameleon, Show-o, Transfusion)는 모두 양방향에 하나의 시각 토크나이저를 사용했습니다. 그런데 이 토크나이저는 타협의 산물입니다:

- 재구성(생성)에 최적화된 경우: VQ-VAE는 픽셀의 세밀한 디테일을 잘 담아내지만, 의미적 일관성이 약한 토큰을 만들어 냅니다.
- 의미(이해)에 최적화된 경우: SigLIP 임베딩은 "고양이" 이미지를 "고양이" 토큰 근처에 모아 주지만, 좋은 재구성은 불가능합니다.

Show-o와 Transfusion은 이 대가로 한쪽 방향에서 뚜렷한 품질 저하(품질 세금)를 치릅니다. Janus-Pro는 이렇게 묻습니다: 두 작업의 요구가 다른데 굳이 토크나이저를 하나로 강제할 이유가 뭘까요?

## 개념

### 분리된 시각 인코딩

Janus-Pro의 아키텍처는 두 인코더를 분리합니다:

- 이해 경로. 입력 이미지 → SigLIP-SO400m → 2층 MLP → 트랜스포머 본체.
- 생성 경로. 입력 이미지(기존 이미지를 조건으로 삼을 경우) → VQ 토크나이저 → 토큰 ID → 트랜스포머 본체.
- 출력 생성. 트랜스포머가 예측한 이미지 토큰 → VQ 디코더 → 픽셀.

트랜스포머 본체는 공유됩니다. 본체의 상류와 하류는 모두 작업별로 특화되어 있죠.

입력은 프롬프트 형식으로 구분합니다. `<understand>` 태그가 붙으면 SigLIP 경로로, `<generate>` 태그가 붙으면 VQ 경로로 보냅니다. 또는 작업 종류에서 라우팅이 자동으로 결정되기도 합니다.

### 왜 이 방식이 통하는가

이해 손실은 SigLIP 특성을 받습니다. CLIP 계열 사전학습이 의미적 유사성에 맞춰 다듬어 온 특성입니다. 입력 특성이 과제에 더 적합하니, 모델의 지각(perception) 벤치마크 점수가 Show-o / Transfusion보다 올라갑니다.

생성 손실은 VQ 토큰을 받습니다. 토크나이저가 재구성에 맞춰 다듬어 온 토큰입니다. VQ 코드가 픽셀로 깔끔하게 되돌아가니, 이미지 품질도 Show-o보다 좋아집니다.

공유 트랜스포머 본체는 서로 다른 두 입력 분포(SigLIP과 VQ)를 보면서 둘 다 다룰 수 있게 배웁니다. 주장은 이렇습니다: 데이터와 파라미터가 충분하면 본체가 그 전환을 흡수한다는 것입니다.

### 데이터 스케일링 — Janus vs Janus-Pro

Janus(원조, arXiv 2410.13848)는 분리 개념을 소개했지만 규모가 작았습니다(1.3B 파라미터, 제한된 데이터). Janus-Pro(arXiv 2501.17811)는 규모를 키웠습니다:

- 7B 파라미터 (기존 1.3B 대비).
- 1단계(정렬)용 이미지-텍스트 쌍 9,000만 개 (기존 7,200만 개에서 증가).
- 2단계(통합)용 7,200만 개 (기존 2,600만 개에서 증가).
- 3단계에 이미지 생성 지시문 샘플 20만 개 추가.

결과는 이렇습니다: Janus-Pro-7B는 MMMU에서 LLaVA에 필적하고(60.3 대 ~58), GenEval에서는 DALL-E 3를 앞섭니다(0.80 대 0.67). 단 하나의 오픈 모델이 통합 스펙트럼의 양쪽 면에서 모두 경쟁력을 갖춘 것입니다.

### JanusFlow — 정정 흐름 변형

JanusFlow(arXiv 2411.07975)는 VQ 생성 경로를 정정 흐름(rectified flow) 생성 경로(연속형)로 바꾼 버전입니다. 분리 구조가 "이해에는 SigLIP + 생성에는 정정 흐름"으로 바뀌는 셈이죠. 품질 상한은 더 올라갑니다. 아키텍처는 여전히 "인코더는 분리, 본체는 공유"입니다.

### 공유 본체의 역할

트랜스포머 본체는 하나의 통합된 시퀀스를 처리하지만, 입력 분포는 두 가지입니다. 본체가 해야 할 일은 이렇습니다:

- 이해 시: SigLIP 특성 + 텍스트 토큰을 받아 → 텍스트를 자기회귀적으로 출력.
- 생성 시: 텍스트 토큰 + (선택적으로 이미지 VQ 토큰)을 받아 → 이미지 VQ 토큰을 자기회귀적으로 출력.

본체에는 블록마다 모달리티별 가중치가 없습니다. Qwen이나 Llama 안에 들어 있을 법한 범용 텍스트 스타일 트랜스포머에, 입력 어댑터 두 개를 얹은 것에 가깝습니다.

흥미롭게도 이 말은 Janus-Pro의 본체를 사전학습된 LLM으로 초기화할 수 있다는 뜻이기도 합니다. 실제로 Janus-Pro는 DeepSeek-MoE-7B로 초기화합니다. 이 선택이 중요합니다. 순수하게 밑바닥부터 학습한 통합 모델은 도달하기 어려운 추론 능력을, LLM이 그대로 기여해 주기 때문입니다.

### InternVL-U와 비교

InternVL-U(레슨 12.10)는 2026년의 후속작입니다. 다음을 결합합니다:

- 네이티브 멀티모달 사전학습 (InternVL3 백본).
- 분리형 인코더 라우팅 (입력은 SigLIP, 출력은 VQ + 디퓨전 헤드).
- 통합된 이해 + 생성 + 편집.

InternVL-U는 Janus-Pro의 아키텍처 선택을 더 큰 프레임워크 안에 흡수했습니다. 분리형 인코더 아이디어는 이제 대규모 통합 모델의 기본값이 되었습니다.

### 한계

인코더를 분리하면 아키텍처 복잡도가 늘어납니다. 학습해야 할 토크나이저가 둘, 유지해야 할 입력 경로가 둘, 실패 양상도 두 벌이 됩니다. 생성이 필요 없는 제품이라면 Janus-Pro는 과한 설계입니다 — LLaVA 계열의 이해 모델을 고르세요.

이해가 필요 없는 제품이라면 Janus-Pro는 과분한 모델입니다 — Stable Diffusion 3 / Flux 계열을 고르세요.

둘 다 필요한 제품이라면, Janus-Pro가 이제 참조용 오픈 아키텍처입니다.

## 직접 해보기

`code/main.py`는 Janus-Pro의 라우팅을 시뮬레이션합니다:

- 목업 인코더 두 개: SigLIP류(256차원 의미 벡터 생성)와 VQ류(정수 코드 생성).
- 작업 태그를 보고 인코더를 고르는 프롬프트 라우터.
- 어떤 인코더가 만든 토큰이든 처리하는 공유 본체(대역).
- 1단계(정렬)에서 3단계(지시문 튜닝)로 넘어가는 가중 샘플링 스케줄.

이미지 QA, T2I, 이미지 편집 세 가지 예제의 라우팅 경로를 출력해 보세요.

## 출시하기

이 레슨은 `outputs/skill-decoupled-encoder-picker.md`를 만듭니다. 프런티어급에 가까운 품질로 통합 생성 + 이해를 원하는 제품이 주어지면, 구체적인 데이터 규모 권고와 함께 Janus-Pro, JanusFlow, InternVL-U 중 하나를 선택해 줍니다.

## 연습 문제

1. Janus-Pro-7B는 GenEval에서 DALL-E 3를 이깁니다. 7B 오픈 모델이 생성에서는 프런티어 독점 모델과 어깨를 나란히 하면서도 이해에서는 그러지 못하는 이유를 설명해 보세요.

2. 라우터 함수를 구현해 보세요: 프롬프트 텍스트를 받아 `understand` 또는 `generate`로 분류합니다. "설명한 다음 스케치해 줘" 같은 모호한 프롬프트는 어떻게 처리하겠습니까?

3. JanusFlow는 VQ 경로를 정정 흐름으로 바꿉니다. 이제 트랜스포머 본체는 무엇을 출력하고, 손실에서는 무엇이 바뀔까요?

4. Janus-Pro 아키텍처에 인코더를 하나만 더 분리해서 붙일 수 있는 네 번째 작업을 제안해 보세요. 예: 이미지 세그멘테이션(DINO 스타일), 깊이 추정(MiDaS 스타일).

5. Janus-Pro의 4.2절(데이터 스케일링)을 읽어 보세요. Janus 대비 T2I 품질 향상에 가장 크게 기여한 데이터 단계는 어느 것인가요?

## 핵심 용어

| 용어 | 사람들이 말하는 표현 | 실제 의미 |
|------|-----------------|------------------------|
| 분리형 인코딩 (Decoupled encoding) | "시각 인코더 두 개" | 방향마다 별도의 토크나이저나 인코더를 쓰는 것: 이해에는 의미용, 생성에는 재구성용 |
| 공유 본체 (Shared body) | "트랜스포머 하나" | 단일 트랜스포머가 어느 인코더의 출력이든 처리하며, 모달리티별 가중치는 없음 |
| 이해용 SigLIP | "의미적 특성" | CLIP 계열 비전 타워. 풍부한 개념적 특성을 주지만 재구성은 못함 |
| 생성용 VQ | "재구성 코드" | 픽셀로 깔끔하게 디코딩되는 벡터 양자화 토큰 |
| JanusFlow | "정정 흐름 변형" | VQ 대신 연속형 흐름 매칭(flow matching) 생성 헤드를 쓴 Janus-Pro |
| 라우팅 태그 | "작업 태그" | 입력 인코더를 고르게 하는 프롬프트 표식(`<understand>` / `<generate>`) |
