# 투기적 디코딩 선택기

엔지니어가 기본 투기적 디코딩, Medusa, EAGLE, lookahead 디코딩 중에서 고르고, 특정 작업 부하에 맞게 `N`(드래프트 길이)을 튜닝하도록 돕습니다.

## 수집할 입력

1. **검증자 모델** — 최종 출력을 내는 LLM. 크기가 중요합니다(속도 향상을 위해 드래프트 비용이 검증자 비용보다 작아야 합니다).
2. **작업 부하 유형** — 코드, 채팅, 구조화된 출력, 요약. 수락률을 결정합니다.
3. **샘플링 전략** — 그리디, 저온도, 고온도, 빔. 고온도 샘플링은 수락률을 떨어뜨립니다.
4. **하드웨어 대상** — 메모리 예산이 별도의 드래프트 모델을 담을 수 있는지를 결정합니다.
5. **엔지니어링 예산** — Medusa와 EAGLE은 파인튜닝이 필요합니다; 기본 방식과 lookahead는 필요 없습니다.
6. **지연 시간 목표** — 대화형 채팅(TTFT 500ms 미만, 토큰당 50ms 미만) vs 배치(처음 우선).

## 결정 규칙

- **빠른 시작, 학습 없음**: 같은 계열 1B~3B 모델을 기본 드래프트로. 보통 2배.
- **파인튜닝이 가능하면**: 검증자의 은닉 상태를 쓰는 EAGLE-2 또는 EAGLE-3. 보통 3~4배.
- **파인튜닝은 가능하지만 모델 두 개를 못 돌리면**: Medusa(검증자에 헤드 추가). 2~3배.
- **학습 예산도, 쓸 수 있는 드래프트 모델도 없으면**: lookahead 디코딩. 1.3~1.6배.
- **배치 위주 서빙**: 연속 배칭이 더 중요합니다; 배치가 커지면 검증자가 이미 포화라 투기적 이득이 줄어듭니다.
- **고온도 또는 확률적 샘플링**: 수락률이 급락합니다. N을 낮추는(2~3) 것을 고려하거나 비활성화하세요.
- **구조화된 출력(JSON, 코드)**: 수락률이 높습니다. 최대 속도를 위해 N을 7 이상으로 밀어 보세요.

## 튜닝

- **N(드래프트 길이)**: 5에서 시작합니다. 수락률을 측정하세요. α > 0.9면 7로 올립니다. α < 0.6이면 3으로 내립니다.
- **드래프트 온도**: 검증자의 온도에 맞춥니다. 어긋난 드래프트 샘플링은 α를 잃게 합니다.
- **트리 깊이(EAGLE-2 / Medusa)**: 3~5개 분기; 넓은 트리는 α > 0.8에서만 도움이 됩니다.
- **드래프트 모델 크기**: α > 0.7을 만드는 가장 작은 것. 70B 검증자에는 1B 드래프트가 전형적입니다; 검증자의 토크나이저 / 임베딩 호환성 아래로 내려가지 마세요.

## 항상 표시할 것

- 드래프트와 검증자가 토크나이저를 공유하는지 확인하세요. 다른 BPE 분할은 투기적 보장을 깨뜨립니다.
- 투기 디코딩은 vLLM의 연속 배칭과 상호작용합니다: 배치가 이미 포화 상태면 요청당 속도 향상이 줄어듭니다.
- EAGLE의 은닉 상태 입력은 검증자 내부에 접근해야 합니다; HF API로 항상 노출되지는 않습니다. vLLM이나 SGLang 런타임을 선호합니다.
- Medusa 헤드는 검증자 자신의 출력으로 지도 파인튜닝이 필요합니다. 데이터 수집 단계가 흔히 지배적인 비용입니다.

## 출력 형식

다음을 반환합니다:

1. **추천** — 전략 이름 하나와 튜닝 파라미터(예: "EAGLE-2, N=5, tree_depth=4").
2. **기대 속도 향상** — 명시적인 α 가정과 함께.
3. **호환성 점검** — 토크나이저 일치, 런타임 지원, KV 캐시 롤백 지원.
4. **폴백 계획** — 1순위 전략이 기대에 못 미치면 다음으로 무엇을 시도할지.
5. **측정 계획** — 대표 샘플에서 수락률과 속도 향상을 어떻게 검증할지.
