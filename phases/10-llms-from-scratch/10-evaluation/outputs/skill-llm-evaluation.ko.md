# LLM 평가 전략

LLM 시스템을 평가할 때는 이 의사결정 프레임워크를 적용해 올바른 접근 방식을 고르세요.

## eval 유형별 사용 시점

**벤치마크 (MMLU, HumanEval, SWE-bench):** 초기 모델 선정 단계일 때입니다. 후보 10개 모델을 3개로 좁혀야 하는 상황이죠. 벤치마크는 비용 없이 대략적인 순위를 알려 줍니다. 단, 벤치마크를 최종 평가로 쓰지는 마세요.

**커스텀 eval:** 프로덕션(운영 환경)을 위해 만들고 있을 때입니다. 구체적인 실패 모드가 있는 구체적인 과제가 있죠. 커스텀 eval은 실전 성능을 예측할 수 있는 유일한 평가입니다. 프로토타입에는 최소 50개, 프로덕션에는 200개 이상의 테스트 케이스가 필요합니다.

**LLM-as-judge:** 과제가 자유 응답형일 때입니다(요약, 글쓰기, 대화). 정확 일치나 토큰 겹침 지표는 너무 경직되어 있습니다. LLM-as-judge는 건당 약 $0.01이 들고 인간 판단과 약 80% 일치합니다. 막연한 프롬프트가 아니라 반드시 루브릭(채점 기준표)을 사용하세요.

**휴먼 평가:** 위험 부담이 크고 자동 지표들끼리 의견이 갈릴 때입니다. 휴먼 평가가 정답 기준(ground truth)이지만 건당 $0.10~$2.00이 듭니다. 모호한 사례와 자동 지표의 주기적 보정(calibration)을 위해 아껴 두세요.

**쌍대 비교 기반 ELO:** 같은 과제에서 여러 모델을 비교할 때입니다. 인간(그리고 LLM 판정 모델)은 상대 판단을 더 잘하기 때문에, 쌍대 비교가 절대 점수 매기기보다 신뢰할 만합니다.

## 채점 함수 선택

- **정확 일치**: 분류, 개체명 추출, 정답이 정해진 구조화된 출력
- **토큰 F1**: 부분 점수가 중요한 추출 과제
- **ROUGE-L**: 요약, 번역
- **BLEU**: 기계 번역
- **LLM-as-judge**: 자유 응답형 생성, 대화 품질, 유용성
- **실행 기반**: 코드 생성 (코드를 실행하고 테스트가 통과하는지 확인)
- **스키마 준수**: 구조화된 출력 (JSON이 스키마와 일치하는가?)

## eval 설계의 경고 신호

- eval 세트가 50개 미만: 결과가 통계적으로 무의미함
- 엣지 케이스 없음: 해피 패스 성능만 측정하는 셈인데, 이는 항상 실전보다 높게 나옴
- 지표가 하나뿐: 지표마다 다른 이야기를 하므로 최소 두 개는 사용할 것
- 버전 관리 없음: 버전 관리된 eval 세트 없이는 개선을 추적할 수 없음
- eval 세트 오염: eval 예시를 파인튜닝 데이터나 퓨샷(few-shot) 프롬프트에 절대 넣지 말 것
- 한 모델만 테스트: 비교할 베이스라인(간단한 휴리스틱이라도)이 필요함

## eval 파이프라인 체크리스트

1. 과제를 정확히 정의 ("질문에 답하기"가 아니라 "지원 티켓을 5개 카테고리로 분류하기")
2. 해피 패스, 엣지 케이스, 알려진 회귀 사례에 걸쳐 테스트 케이스 생성
3. 과제 유형에 맞는 채점 함수 2~3개 선택
4. 프로덕션(운영 환경) 요구 사항에 맞춰 통과/실패 임계값 설정
5. 실행 자동화: 명령 한 줄로 전체 스위트 실행
6. 모든 것을 버전 관리: 테스트 케이스, 채점 함수, 프롬프트, 모델 버전
7. 모든 변경 시 실행: 프롬프트 업데이트, 모델 교체, 코드 배포
8. 추세 추적: 점수 하나는 노이즈이고, 추세선이 신호다
9. 분기별로 인간 판단과 보정(calibration)
10. 프로덕션 실패가 발견될 때마다 회귀 케이스 추가
