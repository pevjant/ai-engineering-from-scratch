# 비동기(Async)와 Hogwild! 추론

> 스페큘레이티브 디코딩(페이즈 10 · 15)은 하나의 시퀀스 안에서 토큰을 병렬화합니다. 멀티 에이전트 프레임워크는 시퀀스 전체를 넘어 병렬화하지만 명시적인 조율(투표, 하위 작업 분할)을 강제합니다. Hogwild! Inference(Rodionov 외, arXiv:2504.06261)는 다른 길을 갑니다. 같은 LLM 인스턴스 N개를 병렬로 돌리되, 하나의 공유 키-값 캐시를 두는 것입니다. 각 워커는 다른 모든 워커가 생성한 토큰을 즉시 볼 수 있습니다. QwQ, DeepSeek-R1 같은 현대의 추론 모델은 파인튜닝 없이도 이 공유 캐시를 통해 스스로 조율할 수 있습니다. 이 접근법은 실험적이지만, 스펙 디코딩과 직교하는(서로 다른 축의) 추론 병렬화의 완전히 새로운 축을 엽니다. 이 레슨에서는 표준 라이브러리만으로 워커 2개짜리 Hogwild! 시뮬레이터를 구현하고, 공유 캐시를 통한 협업이 기존 모델의 추론 능력에서 왜 자연스럽게 튀어나오는지 설명합니다.

**유형:** Build
**언어:** Python (표준 라이브러리)
**선수 지식:** 페이즈 10 · 12 (추론 최적화), 페이즈 10 · 15 (스페큘레이티브 디코딩)
**시간:** 약 60분

## 학습 목표

- 병렬 LLM의 세 가지 대표 토폴로지(투표, 하위 작업, Hogwild!)를 설명하고 각각이 겨냥하는 문제를 꼽을 수 있다.
- Hogwild!의 핵심 구성을 말할 수 있다: 여러 워커, 하나의 공유 KV 셀프 프롬프팅을 통한 자율적(self-prompting) 조율.
- 워커 수 `N`, 작업 수준 병렬화 비율 `p`, 조율 오버헤드 `c`에 대한 Hogwild!의 실제 시간(wall-time) 속도 향상을 계산할 수 있다.
- 간단한 문제에 두 워커 Hogwild! 시뮬레이터를 구현하고, 저절로 나타나는 작업 분할을 관찰할 수 있다.

## 문제 상황

현대의 LLM은 긴 추론 사슬을 만들어 어려운 문제를 풉니다. 단계별 논리 5,000토큰은 흔하고, 깊은 수학 문제에서는 수만 토큰이 나오기도 합니다. 70B 모델에서 초당 35토큰으로 디코드하면 5만 토큰은 24분입니다. 대화형으로 쓰기에는 너무 느립니다.

스페큘레이티브 디코딩(페이즈 10 · 15)은 한 시퀀스 안에서 병렬화해 3~5배 속도 향상을 줍니다. 그 이상은 자기회귀 디코딩의 순차 의존성이 만드는 단단한 천장입니다. 새 토큰 하나는 그 앞의 모든 토큰에 의존합니다.

당연한 질문: 시퀀스를 넘어 병렬화할 수는 없을까? 같은 모델의 사본 여러 개를 같은 문제에 돌리고, 서로 협력하게 하고, 일을 나누게 할 수는 없을까?

기존 연구: 투표 앙상블(모델 N개를 돌려 다수결 답 선택), tree-of-thought(추론 경로를 분기하고 재결합), 멀티 에이전트 프레임워크(에이전트마다 하위 작업 배정, 코디네이터 사용). 이것들은 특정 작업 영역에서 도움이 됩니다. 하지만 모두 명시적인 조율 장치 — 투표 규칙, 분기-가지치기 로직, 에이전트 간 메시징 프로토콜 — 를 요구합니다.

Hogwild! Inference는 다른 접근법을 택합니다. N개의 워커가 하나의 KV 캐시를 공유합니다. 각 워커는 다른 워커가 생성한 토큰을 마치 자기 컨텍스트인 것처럼 즉시 봅니다. 워커들은 어떤 학습이나 파인튜닝 없이도 일을 나누는 방법을 스스로 찾아냅니다. 현대의 추론 모델(QwQ, DeepSeek-R1, Claude 계열의 추론 모드)은 공유 캐시를 읽고 "워커 2가 이미 기저 사례를 처리했으니 나는 귀납 단계를 맡을게" 같은 말을 할 수 있습니다.

속도 향상은 작업 부하에 따라 달라지며, 2026년 4월 기준으로 실험적입니다. 하지만 추론 병렬화의 새로운 축을 여는 아이디어라서 알아둘 가치가 있습니다.

## 개념

### 구성

같은 LLM을 돌리는 워커 프로세스 N개를 초기화합니다. 워커별 KV 캐시 대신 하나의 공유 캐시를 유지합니다. 워커 `i`가 토큰 `t_j`를 생성하면, 그 토큰은 공유 캐시의 다음 위치에 기록됩니다. 워커 `k`가 다음 단계를 밟을 때는 캐시의 현재 상태(N개 워커가 지금까지 생성한 모든 것을 포함)를 읽습니다.

단계 시점에는 워커들이 토큰 쓰기를 두고 경쟁합니다. 워커별 위치 인덱스가 없습니다. 캐시는 하나뿐인 늘어나는 시퀀스이고, 순서는 쓰기 도착 시간으로 결정됩니다.

### 조율이 저절로 나타나는 이유

워커들은 프롬프트를 공유합니다. 보통 이런 내용입니다. "당신은 이 문제를 함께 푸는 N개 인스턴스 중 하나입니다. 각 인스턴스는 공유 메모리를 읽어 다른 인스턴스가 쓴 내용을 볼 수 있습니다. 중복 작업은 피하세요." 프롬프트와 공유 캐시면 충분합니다. 추론 모델은 캐시를 읽고, 문제의 어느 부분이 이미 시도됐는지 알아차리고, (항상 그런 것은 아니지만) 흔히 탐험하지 않은 부분으로 방향을 바꿉니다.

Hogwild! 논문(Rodionov 외, 2025)은 이런 관찰을 보고합니다:

- 워커들이 계획을 세우고 캐시를 통해 다른 워커에게 전달합니다.
- 워커들이 다른 워커의 추론 속 오류를 알아차리고 지적합니다.
- 계획이 실패하면 워커들이 적응하고 대안을 제안합니다.
- 중복 여부 확인을 요청받으면 워커들이 이를 감지하고 방향을 바꿉니다.

이 모든 것에 파인튜닝은 필요 없습니다. 저절로 나타나는 행동은 모델이 이미 갖고 있는 추론 능력에서 나옵니다.

### 이름의 유래

논문의 이름은 비동기 갱신 옵티마이저인 Hogwild! SGD(Recht 외, 2011)에서 따왔습니다. 비유는 이렇습니다. SGD의 비동기 워커들은 모두 공유 파라미터 벡터에 쓰고, Hogwild! Inference의 워커들은 모두 공유 KV 캐시에 씁니다. 둘 다 동기화 보장이 아니라 경험적 수렴에 의존합니다.

### RoPE가 이것을 가능하게 만든다

회전 위치 임베딩(RoPE, Su 외 2021)은 Q와 K 벡터의 회전으로 위치 정보를 인코딩합니다. 위치가 회전이지 박혀 있는 오프셋이 아니기 때문에, KV 캐시 항목을 다시 계산하지 않고도 토큰의 위치를 옮길 수 있습니다. 워커 `i`가 공유 캐시의 위치 `p`에 쓰면, 그 위치를 읽는 다른 워커들은 캐시 항목을 그대로 사용할 수 있습니다. 재회전이 필요 없습니다.

학습된 위치 방식이나 절대 위치 방식 모델이라면, Hogwild!는 동시 쓰기가 일어날 때마다 캐시 무효화가 필요했을 것입니다. RoPE 덕분에 캐시가 안정적으로 유지됩니다.

### 실제 시간 계산

`T_serial`을 한 워커가 혼자 문제를 푸는 데 걸리는 시간, `p`를 작업 수준에서 병렬화 가능한 비율, `c`를 단계당 조율 오버헤드(늘어난 캐시 읽기, 무엇을 쓸지 결정)라고 합시다.

워커 1개의 시간: `T_serial`.
조율이 공짜라면 N워커 Hogwild!의 시간: `T_serial * ((1 - p) + p / N)`. 고전적인 암달의 법칙입니다.
조율 오버헤드를 포함하면: `T_serial * ((1 - p) + p / N) + c * steps_per_worker`.

워커가 생산적이려면 `c`가 단계당 디코드 시간에 비해 작아야 합니다. 5k 이상 토큰을 만들어내는 추론 모델에서는 워커가 수백 토큰의 조율 오버헤더를 감수해도 이득입니다. 짧은 채팅 작업에서는 조율이 지배적이라 Hogwild!가 직렬 방식보다 나쁩니다.

### 구체적인 예

추론 문제: 사고 사슬(chain-of-thought) 1만 토큰. 이 문제에 병렬화 가능한 내용(서로 다른 증명 전략, 서로 다른 경우 분석)이 `p = 0.7`, 워커당 조율 오버헤드가 `c = 200`토큰이라고 합시다. 워커 `N = 4`개일 때:

- 직렬 시간: 10000 디코드 단계.
- Hogwild! 시간: 10000 * (0.3 + 0.7 / 4) + 200 * 4 = 10000 * 0.475 + 800 = 5550 디코드 단계.
- 속도 향상: 10000 / 5550 = 1.8배.

한편 정도입니다. 하지만 더 긴 추론 문제(5만 토큰)에서는 조율 오버헤드가 상쇄되어 속도 향상이 2.5~3배까지 올라갑니다. Hogwild!는 멀티스레드 코드를 자연스럽게 쓸 수 있는 언어에서 스레드 수준 병렬화를 쓰는 것과 같은, 추론 버전의 이야기입니다.

### Hogwild!가 맞는 순간

- 작업이 독립적인 하위 목표로 병렬화될 수 있는, 긴 추론 문제(수천 토큰).
- 단계별로 생각하도록 학습된 추론 모델. 비추론 모델은 자율 조율이 잘 안 됩니다.
- 공유 캐시 + 워커 프로세스 N개를 담을 만큼 VRAM이 넉넉한 단일 노드 배포. 캐시는 공유하지만 각 워커는 자기 활성값 메모리를 따로 둡니다.

### 아닌 순간

- 짧은 대화형 채팅. 조율 오버헤드가 지배합니다.
- 병렬화가 안 되는 작업(하나의 직선 증명, 하나의 컴파일). N=1이 최대입니다.
- 비추론 모델. 조율이 나타나지 않습니다.
- 멀티 노드 배포. 공유 캐시에는 매우 빠른 워커 간 동기화가 필요합니다. 노드 안에서는 괜찮지만, 노드를 넘으면 지연 시간의 재앙입니다.

### 실험적 단계라는 점

2026년 4월 기준으로 Hogwild!는 오픈소스 PyTorch 구현이 있는 연구 방법론입니다. 프로덕션 채택은 아직 일어나지 않았습니다. 세 가지 걸림돌:

1. 동시 프로세스 간 공유 KV 캐시 관리는 만만치 않은 엔지니어링 과제입니다.
2. 저절로 나타나는 조율은 작업에 따라 달라지고, 벤치마크는 아직 만들어지고 있습니다.
3. 스페큘레이티브 디코딩이 이미 주는 성능에 비해 속도 향상은 한편 정도입니다. 둘을 결합할 수 있지만 그 결합 자체가 또 한 겹의 엔지니어링입니다.

## 만들어 보기

`code/main.py`는 간이 Hogwild! 시뮬레이터를 구현합니다:

- 워커 프로세스 2개. 각각 알려진 확률로 여러 토큰 범주(작업 토큰, 관찰 토큰, 조율 토큰) 중 하나를 만들어내는 결정론적 "LLM"입니다.
- 두 워커가 읽고 쓰는 공유 캐시(그냥 토큰 리스트).
- 간단한 조율 로직: 한 워커가 다른 워커가 이미 어떤 범주에서 충분한 작업 토큰을 만들었음을 알아차리면, 다른 범주를 고릅니다.

시뮬레이터는 고정된 단계 예산으로 돌고 다음을 보고합니다:

- 생산된 작업 토큰 총수.
- 총 실제 시간(워커 단계 수).
- 워커 1개 대비 실효 속도 향상.
- 어떤 워커가 어떤 토큰을 썼는지에 대한 추적 기록.

### 단계 1: 공유 캐시

두 워커가 모두 추가(append)하는 리스트. 실제 구현에서는 간단한 잠금(Python `threading.Lock`)을 쓰겠지만, 여기서는 카운터로 흉내 냅니다.

### 단계 2: 워커 루프

각 워커는 매 단계마다:

- 현재 공유 캐시를 읽는다.
- 이미 있는 내용을 바탕으로 어떤 범주의 토큰을 쓸지 결정한다.
- 토큰 하나를 쓴다.

### 단계 3: 조율 휴리스틱

범주 X에 이미 K개의 토큰이 캐시에 있고 워커의 의도된 범주가 X라면, 워커는 범주 Y로 갈아탑니다. 이는 "이미 커버됐음을 알아차리고 다른 일을 한다"는 추론 모델 행동의 간이 대역(stand-in)입니다.

### 단계 4: 속도 향상 측정

같은 총 단계 예산으로 N=1 워커와 N=2 워커로 시뮬레이터를 돌립니다. 생산된 작업 토큰을 세어 봅니다. N=2는 조율에 의한 작업 분할 덕분에 대략 1.5~1.8배 더 많은 작업 토큰을 만들어야 합니다.

### 단계 5: 조율에 스트레스 주기

조율 휴리스틱의 민감도를 낮춥니다. 다시 실행합니다. 좋은 조율이 없으면 N=2가 같은 토큰을 중복 생산하고 속도 향상이 1 아래로 떨어짐을 관찰하세요. 이것은 논문의 관찰과 일치합니다. 이 비결은 워커가 스스로 조율할 만한 추론 능력을 갖추고 있을 때만 작동합니다.

실용적인 채택 경로:

1. 추론 작업 부하를 프로파일링하세요. 탐색적 토큰(여러 전략, 경우 분석, 탐색)과 직선형 토큰의 비율을 측정합니다.
2. 탐색이 지배적이면 워커 2개짜리 Hogwild! 실험을 돌려 보세요. 실제 시간 개선을 측정합니다.
3. 개선이 1.3배 미만이면 조율이 지배적인 영역에 있는 것입니다. 단일 워커로 되돌립니다.
4. 개선이 1.5배를 넘으면 N=4로 늘리고 다시 측정합니다. 수익 체감은 보통 N=4~8 근처에서 나타납니다.

스페큘레이티브 디코딩과 결합: 각 Hogwild! 워커는 독립적으로 스펙 디코딩을 쓸 수 있습니다. 두 속도 향상은 (대략) 곱해집니다. 3배 스펙 디코딩과 1.8배 Hogwild!가 결합하면 순진한 단일 워커 디코딩 대비 실효 5.4배가 됩니다.

## 출시하기

이 레슨은 `outputs/skill-parallel-inference-router.md`를 산출합니다. 추론 작업 부하 프로파일(토큰 예산, 작업 병렬화 프로파일, 모델 계열, 배포 대상)이 주어지면, 투표, tree-of-thought, 멀티 에이전트, Hogwild!, 스페큘레이티브 디코딩 전략 중 하나로 라우팅합니다.

## 연습 문제

1. `code/main.py`를 기본 설정으로 실행하세요. N=2 Hogwild! 구성이 같은 실제 시간에서 N=1 베이스라인보다 더 많은 작업 토큰을 만들어내는지 확인하세요.

2. 조율 휴리스틱의 강도를 낮추고(`coordination_weight=0.1`) 다시 실행하세요. 속도 향상이 무너지는 것을 보여주고 이유를 설명하세요. 워커들이 조율할 수 없으면 노력이 중복됩니다.

3. 5만 토큰 추론 작업에서 `p=0.8, c=500`, 워커 N=4일 때 기대 Hogwild! 속도 향상을 계산하세요. 같은 방법으로 1천 토큰 채팅 작업에서 `p=0.3, c=200`, N=4일 때도 계산하세요. 하나는 이득이고 하나는 손해인 이유는 무엇인가요?

4. Hogwild! 논문의 4장(예비 평가)을 읽으세요. 저자들이 보고하는 두 가지 실패 모드를 찾고, 더 나은 조율 프롬프트가 각각을 어떻게 완화할 수 있는지 설명하세요.

5. 간이 시뮬레이터에서 Hogwild!를 스페큘레이티브 디코딩과 결합하세요. 각 워커가 내부적으로 2토큰 스펙 디코딩을 씁니다. 곱셈적 속도 향상을 보고하세요. 두 워커가 같은 공유 캐시 접두사를 동시에 확장하려 할 때 어떤 장부 관리(bookkeeping) 문제가 생기나요?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| Hogwild! | "병렬 워커, 공유 캐시" | 같은 LLM 인스턴스 N개가 하나의 공유 KV 캐시로 동시 실행. 셀프 프롬프팅을 통한 자율 조율 |
| Shared KV cache | "조율의 매개" | 모든 워커가 읽고 쓰는 단일 증가 KV 버퍼. 워커 간 즉각적인 토큰 가시성을 가능하게 함 |
| Emergent coordination | "학습이 필요 없음" | 추론 능력이 있는 LLM은 파인튜닝이나 명시적 프로토콜 없이도 공유 캐시를 읽고 일을 나눌 수 있음 |
| Coordination overhead (c) | "방향 잡는 데 쓰는 토큰" | 늘어난 캐시를 읽고 무엇을 할지 결정하는 워커별 비용. 전체 디코드 시간 대비 작게 유지되어야 함 |
| Parallelizable fraction (p) | "병렬로 돌릴 수 있는 부분" | 작업 수준 병렬성: 전체 작업 중 본질적으로 순차적이지 않은 비율 |
| RoPE enables Hogwild! | "회전 위치는 이동 불변" | 위치가 회전이기 때문에 공유 캐시에 쓰더라도 이전 토큰을 다시 계산할 필요가 없음 |
| Voting ensemble | "N개 돌리고 다수결" | 가장 단순한 병렬 추론 토폴로지. 분류에는 유용, 장문 추론에는 덜 유용 |
| Tree of thought | "분기하고 가지치기" | 여러 분기를 탐색하고 가지치기하는 추론 전략. 명시적인 조율 로직 필요 |
| Multi-agent framework | "하위 작업 배정" | 에이전트마다 역할을 주고 코디네이터가 지휘. 무거운 프로토콜 오버헤드 |
